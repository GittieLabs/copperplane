# CTX-408.2: Implementation Context: The Product Video Script, and the Project It Needs

> **Spec Reference:** Links to [SPEC-408](../specs/SPEC-408-messaging-for-the-maker-who-is-leveling-up.md)

Asked for directly: *"I need to create product video that is 60-90 secs in length as an app
showcase and need a script and example to use in the product video."* Both are delivered here, and
one of them stops short of what it cannot honestly do — see §4.

## 1. Feature Definition & Execution Plan

### Phase 1: One story, timed
*   [x] A 75-second script with a shot list, on-screen actions and voiceover, in
        `docs/video/product-video-script.md`.
*   [x] Word-counted against the runtime: ~150 words at an unhurried 130 wpm is ~70 seconds inside a
        75-second cut, leaving the two silent beats room to breathe. A script that reads well and
        does not fit is not a script.
*   [x] **Everything else cut.** Component search, the parts library, community imports and provider
        settings are all real and all absent. `SPEC-408` §2 names the failure mode: a tour of eight
        features lands none of them.
*   [x] It opens and closes in KiCad, with Copperplane in the middle — so *"it does not replace
        KiCad"* is shown before it is said.

### Phase 2: Say what not to say
*   [x] A short list of lines to avoid: "AI-powered", the technology stack, the word "just", and any
        implication that the app authors a schematic. The last is the one that would do real damage,
        because a viewer who expects it will be disappointed by a product working correctly.

### Phase 3: The example project, specified rather than drawn
*   [x] `docs/video/example-project.md` — what it must contain, and the exact defects, with measured
        ERC results rather than plausible ones.
*   [x] The two edits that produce **nothing**, recorded so nobody repeats them.
*   [x] Handed to the maintainer with the reason stated: it has to be drawn in KiCad by a person.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the example project is specified, not built, and that is a limit rather than a
    shortcut.** `SPEC-408` asks for a downloadable quick start, and the honest position is that a
    KiCad schematic and board have to be *drawn*. Authoring them by writing s-expressions produces
    a file that opens badly, and I have direct evidence of how that goes: two attempts at editing a
    schematic by text — renaming a `Reference` to force a duplicate designator, and breaking
    `PWR_FLAG`'s `lib_id` — produced **no ERC violations at all**, because KiCad 7+ keeps effective
    references in `(instances)` blocks. I could have produced a file. I could not have produced one
    worth putting in front of a beginner.

*   **Deviation 2: the defect recipe is measured, and that changed what the video demonstrates.**
    Running real ERC against a modified copy of a real schematic gave: one deleted wire → 1
    `pin_not_connected`; deleted `PWR_FLAG` symbols → 2 `power_pin_not_driven` + 2
    `pin_not_connected`; all 34 wires deleted → 34 violations across three types. So the script
    demonstrates **variety, not volume** — 28 identical errors teach nothing that one does — and
    leads on `power_pin_not_driven`, which is the finding whose plain-language translation is worth
    the most: the schematic is usually correct and missing only a KiCad convention.

*   **Deviation 3: one project for the video, the docs screenshots and the quick start.** They were
    three deliverables in `SPEC-408`; making them one artifact means a reader who watches the video
    and then downloads the project sees the same board. It also halves the number of things that go
    stale when the UI changes, which `SPEC-408` §3 already names as a live risk.

*   **What is deliberately not automated.** The matrix has one pending row and it will stay pending:
    a test asserting a script's spoken runtime would be asserting my own arithmetic against my own
    prose. The word count is stated in the document so a reader can check it; that is the honest
    form of that claim.

## 5. Verification Notes

*   The script's shot list was written against the app as it actually is today — the PCB tab's Run
    Review, the switched-off-tests disclosure from `CTX-332.1`, the footprint detail view from
    `CTX-334.1`, and the Enclosure tab's generate — not against a remembered UI. Every screen it
    asks for exists.
*   The ERC numbers come from `kicad-cli sch erc --format json --severity-all` runs against a real
    schematic, recorded in `SPEC-332` §2 and repeated here.
*   **Not verified:** nothing has been recorded. The script is a plan, and the first take will show
    whether 75 seconds is generous or tight — my guess is that 0:22-0:38 is the beat most likely to
    run long, because it is the only one asking the viewer to read.
*   **Blocked on the maintainer:** the example project itself. Everything in this context that
    depends on it — the recording, the docs screenshots, the quick-start download — waits on a
    half-hour in KiCad that cannot be done from here.
