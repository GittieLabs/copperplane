# CTX-407.5: Implementation Context: Ask the Artifact What It Can Do

> **Spec Reference:** Links to [SPEC-407](../specs/SPEC-407-sidecar-build-integrity.md)

## 0. Why the existing checks could not catch this

`ensure_sidecar.inspect()` decides whether a sidecar is usable from four things: it exists, it is
not the committed placeholder, it is the right architecture, and it is newer than the newest source
it was frozen from. Every one is a property of the **file**.

`SPEC-407` §1 describes the failure they cannot see:

> a mis-frozen sidecar that starts, reports `daemon.ready`, passes the heartbeat shield, and runs
> with the **entire AI surface disabled** ... A crash sends you to the packaging; a healthy-looking
> daemon with no `chat.send`, no `agent.dispatch_tool` ... sends you hunting for a UI bug that does
> not exist.

That binary passes all four checks. `CTX-407.3` and `CTX-407.4` both shipped defects of exactly
this shape, and `CTX-407.3` Deviation 2 is the record of trying to catch it by grepping `strings`
for route names — a method that returns nothing for a healthy binary too, and so proved nothing.

**The check those four cannot be is to run the thing and ask it.**

## 1. Feature Definition & Execution Plan

### Phase 1: Let the daemon account for itself
*   [x] `daemon.list_routes` — every route this daemon can actually answer, plus which are async
        and which modules degraded. Synchronous: it reads two in-memory sets, and an async round
        trip would make a build gate slower for nothing.

### Phase 2: Compare the artifact against the checkout
*   [x] `ensure_sidecar.probe_routes()` runs the frozen binary, asks it, and fails the build when
        the artifact is missing routes this checkout defines, or reports degraded modules.
*   [x] It runs on **every freeze**, and on demand via `--probe`. Not on every build: see
        Deviation 4 — launching a frozen sidecar costs 14-17s, and `SPEC-407` §2 had already
        worried that "a build-time check that runs on every `cargo build` would break the debug
        loop".
*   [x] The failure message names the missing routes, and distinguishes the two causes: degraded
        modules are named when present, and their absence points at a bundled data file or a hidden
        import — `CTX-407.4`'s failure, where nothing reported itself degraded.

### Phase 3: Fail closed on disagreement, open on everything else
*   [x] A sidecar that cannot answer the route (an older build) is skipped, not failed.
*   [x] A binary that will not run at all is skipped, not failed. A probe that blocks a build on
        its own flakiness becomes a reason to delete the check.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: my first version only probed a sidecar it found, never one it had just made.**
    `main()` returns early when `inspect()` passes, and freezes in the other branch — so the probe
    sat entirely in the "already present" path. A bad freeze, the case this exists for, would have
    walked straight past it. Caught by running the script against a placeholder and watching the
    probe line never print.

*   **Deviation 2: the probe could not import the checkout it was comparing against.** It runs from
    `scripts/`, so `import daemon` failed and the check silently reported "skipped" — a
    fail-open path doing exactly what fail-open paths do, which is nothing, quietly. Two lines of
    `sys.path`, and worth recording because the *first* run after adding a check is the one that
    tells you whether the check is running at all.

*   **Deviation 3: every failing case is tested against a fake sidecar, because the real failure
    cannot be manufactured on demand.** A shell script that answers `daemon.list_routes` with a
    chosen route list exercises the comparison exactly, and the three failing cases —
    missing routes, degraded modules, and missing-routes-with-nothing-degraded — are asserted to
    **fail**. `CLAUDE.md`'s rule, applied to a check whose whole purpose is to fail rarely: if it
    passed against a broken artifact, it would be worse than nothing, because it would be believed.

*   **Deviation 4: I measured the cost only after building it, and it was 14-17 seconds per
    build.** The first version probed on every build, including the overwhelmingly common case
    where the sidecar was already fine. `SPEC-407` §2 had explicitly decided the check should be
    "a build-time file inspection, not a runtime behavioural probe", partly because "the fast path
    ... is a file read and exits immediately". I read that decision as scoped to placeholder
    detection — which it is, and its "exact rather than heuristic" reasoning genuinely does not
    cover a real-but-broken binary — and did not notice I was also discarding its performance
    argument until I timed it.

    Measured, not estimated: 14-17s, and PyInstaller startup rather than the read is what costs it.
    The answer is to **probe what you just made**: every freeze is probed, an already-present
    sidecar is not, and `--probe` re-asks on demand. A sidecar that passed at freeze time and has
    not changed since — which the existing mtime check proves — has nothing new to say. The fast
    path is back to 0.07s.

*   **Deviation 5: four attempts at reading the answer, and the first three were each wrong
    differently.** Worth the full list, because every one produced a *plausible* result:

    1.  `subprocess.run` waits for the process to exit. It worked, and part of the cost was waiting
        for a daemon that had nothing left to do.
    2.  A `readline` loop with a deadline checked between reads **hung forever** — `readline`
        blocks, so the deadline never came around. A build gate that can hang is strictly worse
        than one that is slow.
    3.  Reading on a thread, plus closing stdin so the fake sidecar would stop waiting for EOF.
        That fixed the tests and **broke the real daemon**, which no longer answered at all. The
        fake was wrong, not the probe: it slurped stdin where the daemon reads a *line*. A
        stand-in must behave like the thing it stands in for.
    4.  `for line in proc.stdout` uses an internal read-ahead buffer, so the answer sat unread and
        the probe reported "does not answer" against a sidecar that had answered in seconds.
        `iter(proc.stdout.readline, '')` returns each line as it arrives.

    Three of the four passed the unit tests. Only running it against the real frozen binary
    distinguished them — the same lesson as `CTX-334.1`'s stale sidecar, arrived at from the
    opposite direction.

*   **Deviation 6: the fail-open message lied, and I believed it about my own binary.** Right after
    a freeze, the probe reported *"this sidecar does not answer daemon.list_routes"* — and the
    binary answered perfectly well when asked directly a minute later. The first launch of a
    freshly frozen PyInstaller executable is cold and exceeded the 15s timeout, and the message
    could not tell "we gave up waiting" from "this build lacks the route". I spent the next step
    looking for a stale freeze that did not exist.

    The timeout is now 45s, and the two cases say different things: no output at all reports that
    it timed out and suggests `--probe`; output including `daemon.ready` but no route list reports
    that the sidecar *started* and does not implement it. Both still fail open — but a fail-open
    message that misdescribes the reason is worse than one that admits ignorance, because it sends
    the reader somewhere confidently wrong.

*   **What this does not cover, stated rather than implied.** A route being *present* is not a
    route *working*. `CTX-407.4`'s prompts-in-`datas` failure would be caught here only because it
    left routes unregistered; a bundled file that goes missing without affecting registration would
    not be. The honest boundary is: this proves the artifact has the same surface as the checkout,
    not that the surface functions.

## 5. Verification Notes

*   1077 daemon tests, zero failures.
*   Run against the real frozen sidecar on this machine:
    `ensure_sidecar: answers all 81 routes, no degraded modules`.
*   Cost measured rather than assumed: the probe takes ~17s against a real frozen sidecar — that
    is PyInstaller startup, not the read — so it runs at freeze time and on `--probe`, never on an
    ordinary build. The ordinary build path measures 0.07s, unchanged from before this context.
*   Final state confirmed against the real artifact:
    `17s -> ok=True answers all 81 routes, no degraded modules`.
*   The three failing paths are proven by test rather than by argument, against a fake sidecar that
    reports a deliberately short route list.
*   **Not verified:** no real broken freeze has been produced to trip this. The tests exercise the
    comparison; nobody has watched it stop an actually-bad build, and it would be dishonest to
    claim otherwise until it does.
