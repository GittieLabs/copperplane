# CTX-406.2: Correct the Contributor Build Tiers

> **Spec Reference:** Links to [SPEC-406](../specs/SPEC-406-contributor-local-builds.md)

`SPEC-406`'s deliverable was a documented build path in `CONTRIBUTING.md` for people who are not
maintainers. Two later contexts changed what that path actually does and neither updated the table,
so the document that outside contributors are explicitly asked to follow described a build that no
longer exists.

Found by the maintainer asking a plain question -- *"should i still use this build command:
`npx @tauri-apps/cli@2 build --bundles app`"* -- which is exactly the question the table is supposed
to answer, and could not.

## 1. Feature Definition & Execution Plan

### Phase 1: Pin the CLI version, as `release.yml` already does

*   [x] All three documented invocations pinned to `2.11.4`, matching `release.yml`.
*   [x] `CTX-402.7` pinned CI and named `npx @tauri-apps/cli@2` -- which *"silently resolves to
    whatever 2.x is newest at build time"* -- as the **real root cause** of `CTX-402.6`'s Linux
    updater-artifact regression. CI was fixed; `CONTRIBUTING.md` was not. A documented local
    command and the release could therefore drift apart in precisely the way that pin exists to
    prevent, which is worse than never having pinned either.
*   [x] A short note on keeping the two equal and bumping them together, so the next person does
    not treat the pin as noise to modernise.

### Phase 2: Make the tiers describe the build that exists

*   [x] Tier 2 promised *"no keys, no Python toolchain needed"* and a bundled **placeholder**
    sidecar. `SPEC-407` §2.3 put `ensure_sidecar.py` in `beforeBuildCommand`, which runs on every
    `tauri build` -- `--bundles app` included -- so a local build freezes a real daemon or stops
    and says why. That tier stopped existing and nothing said so.
*   [x] Tier 3's row read *"Tier 2, plus a real `pyinstaller daemon.spec` freeze in
    `services/python-daemon` first"* while the paragraph immediately beneath it read **"Tier 3 is
    one command."** `CTX-407.2` rewrote the prose and left the table contradicting it, on the same
    screen.
*   [x] The honest remaining distinction is `--bundles app` (no `.dmg`) versus a full build, so the
    tiers split on that instead. Both now state plainly that signing, notarization and updater
    artifacts come only from CI.
*   [x] A paragraph stating the trade `SPEC-407` made, rather than quietly dropping it: a first
    build now needs an interpreter PyInstaller can freeze with, where it previously did not. That
    is a real cost to a contributor and it buys an app that cannot silently launch with a dead
    daemon.
*   [x] `ensure_sidecar`'s described fast path gains "current", following `CTX-407.3`.

### Phase 3: Annotate the superseded non-goal rather than delete it

*   [x] `SPEC-406` §1's third Non-Goal -- *"Not making the frozen Python daemon a prerequisite of a
    local build ... This spec documents that boundary honestly; it does not move it"* -- is now
    false. `SPEC-407` moved that boundary deliberately.
*   [x] Annotated in place as **superseded**, matching the precedent set by the wrapper non-goal
    directly below it in the same list, which carries the same treatment for the same reason: what
    changed is the evidence, not the argument.
*   [x] `last_updated` bumped to 2026-08-31.

### Not in this context

*   **Bumping the pinned CLI version.** `2.11.4` is what the v0.3.0 release actually ran end to
    end. `CTX-402.7` is explicit that a bump must be verified by a real release run, not taken on
    faith, so raising it is its own piece of work.
*   **The Node.js 20 deprecation warning** on all four release legs (`actions/checkout@v4`,
    `setup-node@v4`, `setup-python@v5`, `upload-artifact@v4` are being force-run on Node 24).
    Harmless today, will eventually break the pipeline. `SPEC-402`'s to own.

There is no automated test here, and pretending otherwise with a plausible-looking test path would
be worse than saying so. **Every row was verified by running the documented command on a real
machine**, which for a document whose whole purpose is to be followed by hand is the verification
that matters:

*   `npx @tauri-apps/cli@2.11.4 build --bundles app` reported `Finished 1 bundle` and rebuilt
    `Copperplane.app` at 13:51:56, leaving `Copperplane_0.3.0_aarch64.dmg` untouched from 12:33:33
    -- so the "no `.dmg`" claim is measured, not assumed.
*   That bundle's `Contents/MacOS/hardware-agent-studio-daemon` is 47,528,112 bytes of
    `Mach-O 64-bit executable arm64`, not the 922-byte placeholder -- so the "real daemon behavior
    end to end" claim holds for `--bundles app` specifically, which is the claim that was wrong
    before.
*   `2.11.4` matches every `tauri build` invocation in `release.yml`.

**Not verified.** macOS `aarch64-apple-darwin` only. Tier 1 (`tauri dev`) was not re-run -- only its
version pin changed. Windows and Linux contributors follow the same table and nobody has run it
there; `SPEC-403` owns that.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: this was scoped as a copy fix and the spec was the actual defect.**
    *   *Reasoning:* The reported problem was three stale commands and two contradictory table
        rows. Fixing only those would have left `SPEC-406` §1 asserting a non-goal that `SPEC-407`
        had already falsified -- and that non-goal is *why* the table said what it said. The
        document would have been correct while the spec behind it stayed wrong, which is the
        condition that produced this drift in the first place.
    *   *Impact:* the spec edit is the substantive half. The repo had already established the
        pattern one bullet lower in the same list, so this followed it rather than inventing a
        convention.

*   **Deviation 2: two separate contexts each broke this table without touching it.**
    *   *Reasoning:* `CTX-402.7` pinned CI's CLI version and left the documented command unpinned.
        `CTX-407.2` rewrote the Tier 3 prose and left the Tier 2 and Tier 3 rows describing the
        superseded behaviour, on the same screen as the paragraph contradicting them. Neither was
        careless about its own scope; the table simply belonged to a third spec.
    *   *Impact:* worth naming as a pattern rather than two mistakes. `CONTRIBUTING.md` is
        `SPEC-406`'s artifact but is edited by whichever context happens to change build
        behaviour, so it drifts silently. A future context that changes what `tauri build` does
        should check this table by default, the way `parent_spec`/`child_specs` are checked in both
        directions.
