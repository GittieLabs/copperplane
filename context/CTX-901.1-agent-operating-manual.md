## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the slash-command mechanism SPEC-901 §2 flagged as an open question is
    confirmed, not assumed.**
    *   *Reasoning:* SPEC-901 §2 explicitly said "confirm the exact mechanism during CTX-901.1
        rather than assuming; do not guess a path and ship it unverified." The moment
        `.claude/commands/*.md` files were written in this session, the tool surfaced them as real,
        invokable skills (`spec-status`, `new-spec`, `new-context`, `close-context`) — direct
        evidence, not an assumption carried over from the task description.
    *   *Impact:* None — confirms the design. Noted here because the spec asked for confirmation
        explicitly, and "it worked when I tried it" is the confirmation.

*   **Deviation 2: SPEC-901 §3 does not actually contain "three traps," and the two traps
    specifically requested for `CLAUDE.md` aren't written there at all.**
    *   *Reasoning:* §3 has 2 "Known Issues" bullets and 4 "Gotchas & Hazards" bullets — six items,
        not three, and none of them state "Testing Matrix paths are repo-root-relative" (that fact
        is in `CONTRIBUTING.md` §4 Step 3, not `SPEC-901`) or "a literal `|` breaks the validator's
        column parsing" (not written anywhere in `SPEC-901`; only visible by reading
        `validate_spec_context.py`'s `line.split('|')` directly, which has no escape handling).
    *   *Impact:* Implemented `CLAUDE.md`'s "Three traps" section to cover both requested items
        anyway, since both are real and independently verified, plus "don't silently overwrite an
        existing file" (from §3's actual Gotchas list) as the third. `SPEC-901` §3 should probably
        be tightened to state both of these explicitly rather than leaving them implicit — flagging
        rather than fixing, since editing an already-reviewed spec's body isn't this context's call
        to make unilaterally.

*   **Deviation 3: the bootstrap self-check (comparing this hand-written file against what
    `/new-context` would have produced) found a real bug, not just a style question.**
    *   *Reasoning:* `new-context.md`'s original steps 2/6/7 built the context ID and branch name
        directly from `$1` (the full spec argument, e.g. `SPEC-901`), which would have produced
        `CTX-SPEC-901.1` and `feat/CTX-SPEC-901.1-...`. Every existing context in this repo drops
        the `SPEC-` prefix and uses just the number — `CTX-101.1`, `CTX-102.1`, `CTX-103.1`,
        `CTX-104.1`. The command's own instructions did not match the convention its own examples
        were supposed to follow.
    *   *Impact:* Fixed in `.claude/commands/new-context.md`: derive `NUM` by stripping the `SPEC-`
        prefix in step 1, and use `NUM` (not `$1`) everywhere a `CTX-*` id or branch name is built.
        This CTX-901.1 file itself already used the correct form by hand, so no rename was needed
        here — only the command needed fixing.

*   **Deviation 4: `/new-context`'s branch-creation step assumed `origin/develop` already contains
    the spec being worked on — false in this exact session.**
    *   *Reasoning:* `new-context.md`'s step 7 (`git checkout -b ... origin/develop`) implicitly
        assumes the target spec is already merged. It wasn't: PR #6 merged from commit `a2eecec`,
        one push behind what actually reached the open PR, so `specs/SPEC-901-agent-operating-manual.md`
        did not exist on `develop` at all when this branch was first created from it — the same
        early-merge pattern that hit PR #2 earlier in this project. Discovered by watching the spec
        file vanish from disk after `git checkout develop`. Required a separate prereq PR (#7)
        cherry-picking the missing commits onto `develop` before `feat/CTX-901.1-*` could be built
        on solid ground.
    *   *Impact:* Fixed in `.claude/commands/new-context.md`: added an explicit re-check
        immediately after branch creation that stops and reports (rather than silently recreating
        the spec from memory) if the spec disappeared. This is now the second time this exact
        failure mode has hit this repo — worth remembering as a repo-level pattern, not just a
        one-off.

*   **Non-deviation, confirmed as designed:** `SPEC-901` is still not wired as a `child_spec` of
    `SPEC-000`, per `SPEC-901` §4's own stated reasoning (parallel process concern, not a component
    of the product architecture `SPEC-000` describes). Implementation did not change this call.
