# CTX-402.5: Implementation Context: Windows & Linux Pre-Release Builds

> **Spec Reference:** Links to [SPEC-402](../specs/SPEC-402-release-signing-and-auto-update.md)

`CTX-402.1`-`.4` shipped a real, signed, notarized, two-architecture macOS release. This adds real,
**unsigned, explicitly pre-release** Windows and Linux builds -- SPEC-402's original Non-Goal
("Not Windows/Linux builds at all") is revised here, not silently ignored: real builds now exist,
labeled honestly as needing community testing rather than waiting on `SPEC-403`'s full cross-platform
CAD verification to exist first. Windows code signing itself remains out of scope -- a real, separate,
not-yet-made decision on cost/process (options include a traditional OV/EV certificate or Azure
Trusted Signing).

## 1. Feature Definition & Execution Plan

### Phase 1: real design verification, before writing any CI
*   [x] Confirmed real: `windows-latest`/`ubuntu-latest` are free-tier GitHub-hosted runners, already
    used in `rust-core-ci.yml`'s own `cargo test` matrix -- no Larger-Runners-style paywall the way
    macOS Intel has, so no cross-compile trick is needed; each gets a plain, native build leg.
*   [x] Confirmed real, via `pip download --platform ... --only-binary=:all:` against the real PyPI
    index (not assumed): every `requirements.txt`/`requirements-build.txt` dependency
    (`pynng`, `kicad-python`, `trimesh`, `pyyaml`, `certifi`, `gittielabs-agentflow`, `pyinstaller`)
    has a real prebuilt wheel for both `win_amd64`/`cp311` and `manylinux_2_28_x86_64`/`cp311`
    (`pyinstaller` itself ships as `manylinux2014_x86_64`, an older/more-compatible baseline) -- no
    compilation needed on either platform, the single biggest real risk this context could have had.
*   [x] Confirmed real, by reading `tauri-plugin-updater`'s own source at the exact version pinned in
    `Cargo.lock` (2.10.1): `target()` returns `format!("{os}-{arch}")` via `updater_os()`/
    `updater_arch()`, giving the real platform keys `windows-x86_64` and `linux-x86_64` -- not
    assumed from documentation, the same standard this repo's `darwin-aarch64`/`darwin-x86_64` keys
    were already held to.
*   [x] Confirmed real, from the same source: Linux's real updater artifact is
    `[AppName]_[version]_amd64.AppImage.tar.gz` (a gzipped AppImage) + `.sig` -- not `.deb`/`.rpm`,
    neither of which self-update. Windows' real updater artifacts are the NSIS `.exe` (or `.zip`) +
    `.sig` produced by `createUpdaterArtifacts`, alongside the plain `.msi` for direct download.
*   [x] Found and fixed a real regression risk before it shipped: `core/tauri-rust` only had
    `tauri.macos.conf.json` before this context, so `bundle.externalBin` was effectively **unset**
    on Windows/Linux -- meaning `rust-core-ci.yml`'s existing, currently-passing `cargo test` legs on
    `windows-latest`/`ubuntu-latest` had never needed a placeholder sidecar file. Adding
    `tauri.windows.conf.json`/`tauri.linux.conf.json` (below) makes `externalBin` real on those
    platforms for the first time, which would have broken that existing CI job without also adding
    the matching placeholder sidecar files (see Phase 2) -- caught by tracing through what `cargo
    test` on those runners actually does today, not assumed safe by analogy to macOS.
*   [x] Confirmed real: `cargo test`'s own Linux leg (`rust-core-ci.yml`) already installs a real,
    working apt package list for Tauri's WebKitGTK/GTK linkage -- reused verbatim here rather than
    guessing at a second list.

### Phase 2: Tauri platform configs + the placeholder-sidecar fix
*   [x] `core/tauri-rust/tauri.windows.conf.json` (new): the same real `bundle.externalBin`
    override pattern `tauri.macos.conf.json` already established.
*   [x] `core/tauri-rust/tauri.linux.conf.json` (new): same pattern.
*   [x] Two new committed placeholder sidecar files (matching `CTX-401.2`'s own real, established
    pattern exactly): `services/python-daemon/dist/hardware-agent-studio-daemon-x86_64-pc-windows-msvc.exe`
    and `services/python-daemon/dist/hardware-agent-studio-daemon-x86_64-unknown-linux-gnu`, both a
    tiny script that fails loudly if ever actually executed by mistake -- and `.gitignore` negations
    added for both, following the exact three-step shape (`!dir/`, `dir/*`, `!dir/specific-file`)
    the existing macOS entries already use.
*   [x] Verified locally: `cargo check` in `core/tauri-rust` still passes cleanly on this (macOS) dev
    machine -- the new platform-override files are additive and only merge on their own OS, zero
    effect on the existing macOS build path.

### Phase 3: `release.yml` -- real Windows/Linux build legs
*   [x] `build-windows` (new job, `runs-on: windows-latest`): `actions/setup-python@v5` for a plain
    CPython 3.11 (no shared-library/framework-build requirement on Windows, unlike macOS --
    `daemon.spec`'s `target_arch=None` already needs no change here either), `shell: bash` on every
    step for POSIX-style commands, PyInstaller freeze, sidecar rename with the real `.exe` suffix,
    `cargo tauri build --target x86_64-pc-windows-msvc` with only the `TAURI_SIGNING_*` updater
    keypair vars (no `APPLE_*`-equivalent signing exists for Windows), uploads `.msi`/`.exe`/`.sig`.
*   [x] `build-linux` (new job, `runs-on: ubuntu-latest`): the same real apt package list
    `rust-core-ci.yml` already uses, plain CPython 3.11, PyInstaller freeze, sidecar rename (no
    extension), `cargo tauri build --target x86_64-unknown-linux-gnu --bundles deb,appimage`
    (`rpm` deliberately excluded -- see Plan Drift), uploads `.deb`/`.AppImage`/`.AppImage.tar.gz`/
    `.sig`.
*   [x] `publish` job: `needs` extended to `[build-macos, build-windows, build-linux]`; the artifact
    download step drops its `macos-*` pattern filter to pick up every leg; the release `files:` glob
    list extended with every new Windows/Linux artifact path.

### Phase 4: `generate_update_manifest.py` -- two new platform keys
*   [x] `_TARGET_TRIPLE_TO_PLATFORM_KEY` gains `"x86_64-pc-windows-msvc": "windows-x86_64"` and
    `"x86_64-unknown-linux-gnu": "linux-x86_64"`, matching the real keys confirmed in Phase 1.
*   [x] The `publish` job's manifest-generation step gains two more `--platform` groups (four total),
    computing each leg's real signature file and download URL the same way the existing two already
    do.

### Phase 5: documentation
*   [x] `README.md` gains a new "Download a prebuilt build (Windows / Linux) — pre-release, needs
    testers" section: explicit pre-release framing, a real SmartScreen-bypass workaround for the
    unsigned Windows build, and plain install instructions for both `.deb` and `.AppImage`.
*   [x] `SPEC-402` itself: `§1 Non-Goals`, `§3 Known Constraints`, `§4 Module Map`, and `§5 User &
    Interaction` all updated to describe the real Windows/Linux pre-release scope, replacing the
    original "not Windows/Linux builds at all" text rather than leaving it stale alongside code that
    now contradicts it.
*   [x] Version bumped `0.1.2` -> `0.1.3` (`Cargo.toml`/`tauri.conf.json`, `Cargo.lock` regenerated),
    enabling the real `v0.1.3` verification tag.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `rpm` bundling deliberately excluded from the Linux leg (`--bundles deb,appimage`,
    not `--bundles all`).** `ubuntu-latest` has no `rpmbuild` installed, and adding it would be
    another unverified system dependency for a pre-release pass whose whole point is to trade some
    completeness for real, shippable builds now. `.deb` + `.AppImage` already cover the large majority
    of desktop Linux users; `rpm` support can be added later as its own small, separately-reviewable
    change if real demand shows up.
*   **Deviation 2: a real regression risk found and fixed before it ever reached CI, not after.**
    Adding `tauri.windows.conf.json`/`tauri.linux.conf.json` makes `bundle.externalBin` real on those
    platforms for the first time -- before this context, only macOS had it configured, so
    `rust-core-ci.yml`'s existing, currently-passing Windows/Linux `cargo test` legs had never needed
    a placeholder sidecar file there. Missing this would have broken already-working CI as a silent
    side effect of an unrelated release-pipeline change. Caught by tracing through what `cargo test`
    on those runners actually depends on today, and fixed with two new placeholder files plus
    matching `.gitignore` negations, following the exact pattern `CTX-401.2` already established for
    macOS.
*   **Deviation 3: no live end-to-end verification on real Windows/Linux hardware -- named honestly,
    not assumed safe by extrapolation from the real macOS x86_64 verification `CTX-402.4` did.** This
    dev machine is macOS-only; every check in Phase 1 was real (PyPI wheel availability, Tauri
    updater source, existing CI behavior) but stops short of an actual PyInstaller freeze or `cargo
    tauri build` run on the real target OS. The first real test is the CI run itself, the same
    deliberate stopping point every prior `CTX-402.*` has named for its own first real run.
*   **Deviation 4: `SPEC-402`'s original "not Windows/Linux builds at all" Non-Goal is revised, not
    superseded by a new spec.** The user's own framing -- ship real, working, clearly-labeled
    pre-release builds and ask the community to help test them, rather than waiting for `SPEC-403`'s
    full verification to exist first -- directly addresses the exact concern that Non-Goal was
    protecting against (a false "it works" claim). Revising the text in place keeps the real
    reasoning visible in one document instead of splitting it across a spec and its own later
    contradiction.
