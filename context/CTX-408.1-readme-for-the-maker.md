# CTX-408.1: Implementation Context: A README for the Maker Levelling Up

> **Spec Reference:** Links to [SPEC-408](../specs/SPEC-408-messaging-for-the-maker-who-is-leveling-up.md)

The README first, as `SPEC-408` §2 argued: every other artifact — the docs site, the tutorials, the
video script — quotes it, and settling the voice once is cheaper than reconciling five drafts of it.

## 0. Two things found before writing a word

**The spec was wrong about the docs site, and so is `SPEC-336`.** Both say it does not exist.
`docs/site` is a real Astro Starlight project with **16 authored pages**, deployed by
`.github/workflows/docs.yml`, and the README already links it. `SPEC-336` §3 used its absence to
justify linking provider docs instead of Copperplane's during guided setup — a decision that
happens to remain correct for a different reason (a provider's own key page is the better link
anyway), but the stated reason was false. Corrected in both specs by this context.

**The README is not merely aimed at the wrong reader; it is stale in ways that break a first
install.** Verified against `core/tauri-rust/tauri.conf.json` and the release list:

| README says | Actually |
| :--- | :--- |
| *"`v0.1.1` is the current release"* | `v0.3.1`, three releases later |
| drag **Hardware Agent Studio** into `/Applications` | the app is **Copperplane** (`SPEC-405`) |
| `xattr -cr /Applications/Hardware\ Agent\ Studio.app` | that path does not exist |

A macOS user following today's README looks for the wrong release, drags an app whose name does not
match, and runs a repair command against a path that is not there. That is a worse first impression
than anything the tone does.

## 1. Feature Definition & Execution Plan

### Phase 1: Address the reader who is actually arriving
*   [x] Open with the maker's problem in their words — a breadboard that works and a next step that
        looks like a cliff — not with "AI assistant for hardware engineers" followed by Tauri,
        Rust, React, a Python daemon and native IPC.
*   [x] Say early and plainly that it **does not replace KiCad or FreeCAD**, because a reader who
        expects it to draw the schematic will be disappointed by a product doing its job correctly.
*   [x] Keep the architecture, unchanged and accurate — moved below the point where someone has
        decided whether this is for them.

### Phase 2: Stop being wrong
*   [x] The product's real name, everywhere.
*   [x] No hardcoded release version. Link Releases instead: a version in prose is a fact with an
        expiry date, and this one expired three times.

### Phase 3: Ask for what the project actually needs
*   [x] Say what is unverified on Windows and Linux, in the section where a user of those platforms
        is deciding whether to bother — *"I need users and validators more. And users can become
        contributors."*
*   [x] Make reporting feel like the contribution it is, without turning the page into a call for
        pull requests.

### Phase 4: Keep it from going stale again
*   [x] A test asserting the README names the product's real name and no hardcoded version, and
        that every relative link resolves.

## 4. Plan Drift & Architectural Changes

*   **Deviation 0: the README's worst problem was not its tone.** `SPEC-408` framed this as a
    positioning task, and positioning was the smaller half. The README named a release three
    versions old, told a macOS user to drag an application by a name the product has not carried
    since `SPEC-405`, and gave a repair command against a path that does not exist. A reader would
    have hit all three before forming an opinion about the tone. Recorded because the spec would
    have been satisfied by a rewrite that fixed none of them.

*   **Deviation 1: the spec's own §2 rested on a false claim, found in the first ten minutes.**
    "The docs site does not exist" is repeated in `SPEC-336` §3 and inherited by `SPEC-408` §2. It
    does exist, with 16 pages and a deploy workflow, and the README links it. Corrected in both
    rather than worked around, because a spec that is wrong about the ground is how a context
    builds the wrong thing confidently.

## 5. Verification Notes

*   1087 daemon tests, two failures — both live-API, both passing alone: the datasheet-guidance job
    whose 60s deadline covers 15+ real calls, and a real footprint-query suggestion whose output is
    model-dependent. Neither touches anything here.
*   The four README checks pass, and `TEST-004` proves they notice a stale name, a hardcoded
    version and a dead link, rather than passing because their patterns match nothing.
*   The rewritten README was checked against reality rather than memory: product name from
    `tauri.conf.json`, current release from `gh release list`, KiCad/FreeCAD version requirements
    from the previous README's own text, and the build-from-source commands carried over unchanged
    because they were already correct.
*   **Not verified, and not verifiable here:** whether it actually reads as welcoming to the
    audience it targets. Nobody in that audience has read it. That is the whole subject of
    `SPEC-408` and the one thing this repo cannot test — the first honest signal will be whether a
    Windows or Linux user opens an issue.
*   **Deliberately not done:** the docs site's own voice, the quick-start project, the tutorials and
    the video script. All `SPEC-408`, all later contexts. This one settled the words everything else
    quotes.
