# CTX-401.3: Implementation Context: Dependency Security Triage

> **Spec Reference:** Links to [SPEC-401](../specs/SPEC-401-python-sidecar-packaging.md)

Six open Dependabot alerts on `develop` -- four high, two medium -- across three ecosystems. The
useful outcome here is not "bumped everything." Two of the six are fixable, one is fixable only by
breaking a release leg this project deliberately supports, and one cannot be fixed downstream at
all. Saying which is which, with the evidence, is the deliverable.

This belongs to `SPEC-401` because the deciding constraint is a packaging one: which wheels exist
for which platform, and therefore what the frozen sidecar can bundle.

## 1. Feature Definition & Execution Plan

### Phase 1: `cryptography` -- three highs and a medium, one of them takeable
*   [x] `requirements.txt` pinned `cryptography==48.0.0`, and the pin carries a long comment
    explaining why: as of `49.0.0` the project dropped macOS x86_64 wheels entirely, shipping only
    `macosx_11_0_arm64`. A real, failed CI run (`v0.1.3`'s first x86_64 macOS leg) proved the
    consequence -- PyInstaller's own architecture check caught the build-from-source `.so` as
    arm64-only when an x86_64 freeze needed it.
*   [x] Dependabot proposes `49.0.0` and `50.0.0`. Taking either **breaks the Intel macOS release
    leg**, which `CTX-402.4` exists to provide. Those alerts stay open on purpose.
*   [x] But the pin comment's own claim -- "48.0.0 is the newest release that still ships a real
    `macosx_10_9_universal2` wheel" -- had gone stale. Checked against PyPI's release metadata
    directly: `48.0.1` ships `macosx_10_9_universal2` too. Taking it costs nothing and closes the
    "Vulnerable OpenSSL included in cryptography wheels" high.
*   [x] Verified on the installed artifact rather than from the changelog:
    `lipo -archs` on `cryptography/hazmat/bindings/_rust.abi3.so` reports `x86_64 arm64`.
*   [x] Re-froze the sidecar and probed it. `cryptography` is bundled, so the source importing it
    proves nothing -- the frozen binary answers all 81 routes with no degraded modules.

### Phase 2: `sharp` -- takeable, and clean
*   [x] `docs/site` pinned `^0.34.0`, resolving to `0.34.5`, against an advisory fixed in `0.35.0`.
*   [x] Checked whether Astro would fight it before changing anything: `astro@7.2.4` declares
    `sharp: ^0.34.0 || ^0.35.0`, so bumping the direct dependency moves both and stays deduped.
    Now resolves to `0.35.4`, one copy, and the docs site still builds.

### Phase 3: `glib` -- not fixable here, and worth recording why
*   [x] `Cargo.lock` holds `glib 0.18.5` against an advisory fixed in `0.20.0`. It is not a direct
    dependency and `cargo update` cannot cross it: `cargo tree -i glib --target
    x86_64-unknown-linux-gnu` shows the whole gtk-rs 0.18 stack above it -- `atk`, `cairo-rs`,
    `gdk`, `gdk-pixbuf`, `gio`, `gtk 0.18.2`, `webkit2gtk`, and `gdkx11` under `wry 0.55.1`.
*   [x] Moving to `glib 0.20` means `wry`/`tauri` moving to gtk-rs 0.20. That is upstream of this
    project. Recorded rather than left looking like an oversight.
*   [x] Scope worth noting: this stack compiles on Linux only -- it does not appear in the
    dependency graph for the macOS or Windows targets at all.

## 4. Plan Drift & Architectural Changes

**1. The alert Dependabot most wants taken is the one that would break a release.** `50.0.0` closes
three advisories and drops the Intel macOS wheel with them. A session that treated "four high
alerts" as the thing to drive to zero would have taken it, and the breakage would have surfaced in
a tagged release build, after every other leg had already run. The pin comment in
`requirements.txt` is what prevented that -- it is the reason this repo writes those comments, and
it earned its place today.

**2. And that same comment was itself half-stale.** It named `48.0.0` as the last universal2
release; `48.0.1` is. The comment was right about the constraint and wrong about where the line
sits, which is the more dangerous kind of stale: convincing, specific, and load-bearing. Re-checked
against PyPI's own metadata rather than reasoned about. The comment now states the constraint and
names what was deliberately left open, so the next person meets the reasoning rather than the
conclusion.

**3. Two live-LLM tests failed locally and neither relates to this change.**
`TestRealDatasheetGenerateGuidanceJob` is the malformed-JSON failure `agentflow` PR #13 addresses.
`test_component_pipeline.TestRealGenerateComponent.test_003` failed differently -- the model
returned `ATtiny85-20SU` where the test expects `ATtiny85`, which is model output variance rather
than a parsing failure. Both skip in CI for want of an API key. Zero occurrences of
cryptography/SSL/OpenSSL anywhere in the run's output, checked rather than assumed.

**4. Not verified:** the x86_64 macOS freeze itself. `lipo` proves the wheel carries both
architectures and the local arm64 freeze is clean, but the Intel leg only actually runs in a tagged
release build. The constraint this whole context turns on will not be re-proven until then.
