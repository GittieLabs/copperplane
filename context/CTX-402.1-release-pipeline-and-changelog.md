# CTX-402.1: Implementation Context: Release Pipeline & Changelog

> **Spec Reference:** Links to [SPEC-402](../specs/SPEC-402-release-signing-and-auto-update.md)

The release-infrastructure half of `SPEC-402`: a real, tag-triggered, unsigned macOS release
pipeline, a real changelog generator reading `CTX-*.md`'s own implementation logs, and the
documented Gatekeeper bypass unsigned distribution requires. **No auto-updater in this context** --
`tauri-plugin-updater`'s own signing keypair generation and frontend UI are deliberately split into
a future `CTX-402.2`, the same daemon/UI-shaped split this project has used repeatedly (`CTX-309.1`/
`.2`, `CTX-310.1`/`.2`) applied here to infra-vs-feature instead.

## 1. Feature Definition & Execution Plan

### Phase 1: `scripts/check_release_version.py` -- real version/tag consistency
*   [x] `cargo_toml_version`/`tauri_conf_version`: parse the real, current version out of
    `core/tauri-rust/Cargo.toml` and `tauri.conf.json` respectively -- two real, independent sources
    of truth that must agree, not one.
*   [x] `check_tag_matches`: compares a pushed tag (with or without a `v` prefix) against both,
    raising a clean error naming exactly which source(s) disagree -- the whole point of a CI version
    check is a clear, actionable failure message, not a bare non-zero exit.
*   [x] Real, non-fixture test against this repo's own actual `Cargo.toml`/`tauri.conf.json`,
    confirming they currently agree (`0.1.0`) and that the real parser works against real files, not
    just a hand-crafted stand-in.

### Phase 2: `scripts/generate_release_notes.py` -- real changelog from `CTX-*.md` logs
*   [x] `changed_ctx_files`: every `CTX-*.md` path added or modified between two git refs, at any
    real depth this repo actually uses (root `context/`, `apps/tauri-ui/context/`,
    `services/python-daemon/context/`) -- filtered in Python against the diff output rather than
    relying on git pathspec globbing, which isn't portable across git configs.
*   [x] `extract_implementation_log_table`: pulls each context file's own real `## 3. Implementation
    Log & Commit History` table verbatim -- the real, already-collected asset `ROADMAP.md` itself
    names as currently unread, assembled here for the first time rather than reparsed into a new
    format.
*   [x] `latest_tag`/`first_commit`: real fallback chain when `--from-ref` is omitted -- the most
    recent tag, or this repo's own real first commit if it has never been tagged (the real state
    this pipeline's first-ever invocation will actually be in).
*   [x] Real, end-to-end verification against this repo's own actual git history (`f8bab4a..2bd71a4`,
    the real range containing `CTX-203.1`'s merge), confirming the script correctly found and
    formatted that real context file's real table.

### Phase 3: `.github/workflows/release.yml` -- the real, tag-triggered pipeline
*   [x] Triggers on a real `v*` tag push; runs `check_release_version.py` first and fails the whole
    job before any build work starts if the tag doesn't match.
*   [x] Installs a real Homebrew `python@3.11` specifically for the PyInstaller freeze step -- a
    deliberate departure from `python-ci.yml`'s own `uv`-managed venv, because `uv`'s downloaded
    interpreter is exactly the kind of shared-library-less build PyInstaller refuses (`CTX-401.1`'s
    own real, concrete finding).
*   [x] Freezes the daemon via `SPEC-401`'s already-committed `daemon.spec`, renames the output to
    Tauri's real `<name>-<target-triple>` sidecar convention (`rustc -vV`'s `host:` field, not
    `uname -m` -- `CTX-401.2`'s own real, verified reason those can disagree), then runs
    `npx @tauri-apps/cli@2 build` from `core/tauri-rust` -- `tauri.macos.conf.json`'s `externalBin`
    entry merges automatically since the job runs on macOS, no explicit `--config` flag needed
    (Tauri v2's own real platform-config-override convention).
*   [x] Publishes the built `.dmg` as a real GitHub Release via `softprops/action-gh-release`, with
    `generate_release_notes.py`'s real output as the release body.

### Phase 4: the real, documented Gatekeeper bypass
*   [x] `README.md` gains a "Download a prebuilt build (macOS)" section, ahead of "Build from
    source" -- the real, honest unsigned-app consequence named explicitly (`SPEC-402` §3's own
    "Known Constraints"), with the real right-click-Open workaround and the `xattr -cr` fallback for
    the stricter "is damaged" variant newer macOS versions sometimes show instead.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the real release workflow has never run in real CI -- named explicitly above,
    not silently treated as verified because its component scripts are.** This is a real,
    deliberate stopping point: the first actual run of this pipeline is itself a real release event
    (a public GitHub Release, an unsigned `.dmg` real users could download), which is this project
    owner's call to make, not something to trigger as a side effect of closing out a context file.
*   **Deviation 2: `check_release_version.py` checks Cargo.toml AND tauri.conf.json, not just
    Cargo.toml.** `SPEC-402` §3 named "a version/tag mismatch" as a real risk in general terms; while
    implementing the check, a second real source of truth became apparent -- `tauri.conf.json` also
    carries its own `version` field, independently maintainable, with no automatic sync to
    Cargo.toml's. Checking only one would leave exactly the mismatch this check exists to catch.
*   **Deviation 3: the PyInstaller freeze step in `release.yml` deliberately does not reuse
    `python-ci.yml`'s `uv`-managed venv pattern.** `CTX-401.1`'s own real, already-recorded finding
    (a Python interpreter without `--enable-shared`/`--enable-framework` fails PyInstaller outright)
    means this repo's two Python CI paths now have a genuine, real reason to differ, not an
    inconsistency to clean up later.
*   **Deviation 4: no auto-updater wiring in this context, despite `SPEC-402`'s own title.** Split
    into a future `CTX-402.2` for the same reason `CTX-309.1`/`.2` and `CTX-310.1`/`.2` split
    backend/UI work: the updater's real signing-keypair generation is a distinct, separately
    reviewable slice from the release pipeline that publishes the artifacts it will eventually sign
    updates for. Building both in one context would also mean generating a real Ed25519 keypair (a
    real secret) before this repo's very first release has even shipped once unsigned -- sequencing
    them lets the unsigned pipeline prove itself first.
