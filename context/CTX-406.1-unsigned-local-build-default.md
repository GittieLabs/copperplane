# CTX-406.1: Implementation Context: Unsigned Local Build Default

> **Spec Reference:** Links to [SPEC-406](../specs/SPEC-406-contributor-local-builds.md)

Single-phase context: inverts the default so `tauri build` in a fresh clone no longer demands
`TAURI_SIGNING_PRIVATE_KEY`, moves the release-only setting into an explicit overlay `release.yml`
merges on its own three build legs, and documents the three real local-build tiers in
`CONTRIBUTING.md`. No Rust/TypeScript/Python source changes, no test-suite changes -- exactly
`SPEC-406`'s own stated scope.

## 1. Feature Definition & Execution Plan

### Phase 1: invert the default
*   [x] `core/tauri-rust/tauri.conf.json`'s `bundle.createUpdaterArtifacts` changed `true` -> `false`
    -- the committed config now describes the common case (a contributor's own local build), not the
    release-only one.
*   [x] New `core/tauri-rust/tauri.release.conf.json`: `{"bundle": {"createUpdaterArtifacts": true}}`
    and nothing else -- a release-only overlay, matching the existing
    `tauri.macos/windows/linux.conf.json` platform-override convention already in this directory.
    Verified not gitignored (`git check-ignore` before committing).
*   [x] `.github/workflows/release.yml`'s three `tauri build` invocations (`build-macos`,
    `build-windows`, `build-linux`) each gain `--config tauri.release.conf.json`, confirmed against
    Tauri v2's own published CLI reference before writing: `--config` accepts a file path, merges
    with (not replaces) the existing config, and multiple `--config` passes merge in the order
    provided -- so the automatic per-platform merge (`tauri.macos.conf.json` etc.) is unaffected by
    adding this one alongside it.

### Phase 2: document the three tiers
*   [x] `CONTRIBUTING.md` gains a "Local builds — three honest tiers" section (Tier 1 `tauri dev`,
    Tier 2 unsigned bundle + placeholder daemon, Tier 3 unsigned bundle + real daemon), stating
    plainly that an unsigned local build runs fine (never quarantined, no Gatekeeper prompt) and that
    signed/update-capable builds only ever come from CI, by design -- a contributor's own generated
    updater keypair would produce artifacts the shipped app's pinned public key correctly rejects.

### Not in scope (per SPEC-406 §1's own Non-Goals, confirmed unchanged)
*   No change to `services/python-daemon` -- placeholder sidecars and `daemon.spec` are referenced by
    the new documentation, not modified.
*   No Windows/Linux code signing decision.
*   No wrapper script/Makefile -- the documented command is the deliverable.
*   The real Apple signing material observed at `developer-key/` on the maintainer's machine
    (`SPEC-406` §3) is a maintainer action, not touched by this context.

**Explicitly not verified in this session:**
*   Only Tier 2 (`--bundles app`) was run, on this one machine (macOS, Apple Silicon). Tier 3 (a real
    PyInstaller daemon freeze) was not exercised -- `SPEC-401`'s placeholder sidecar is sufficient to
    prove this specific fix (a config-default change), and freezing the real daemon is unrelated to
    what changed here.
*   Windows and Linux were not built locally (no such machine available in this session) -- the
    `release.yml` diff for those two legs is a mechanical, identical `--config` addition to the same
    already-proven-working macOS leg's pattern, not independently verified end to end on those
    platforms. `SPEC-403` (Cross-Platform Verification Matrix) is the spec that would close this gap
    generally.
*   `release.yml`'s actual CI run of the three build legs (with the real `--config` addition) has not
    executed yet as of writing this -- only `validate-specs-and-context` runs on every PR; the
    `release.yml` workflow itself is tag-triggered, not PR-triggered, so it will not be exercised
    until the next real release tag. This context did not wait for that.

## 4. Plan Drift & Architectural Changes

*   **No plan drift.** Implementation followed `SPEC-406` §2's own design exactly as written (invert
    the default, release-only overlay merged by `--config`, document three tiers) -- the spec's own
    "System Architecture & Design Choices" section had already weighed and rejected the alternative
    (documenting an override instead of inverting the default), so there was no decision left open
    for this context to make differently. The one thing this context did that the spec's own text
    flagged as unverified is exactly what got verified here: a real build, run for real, confirming
    the fix.
