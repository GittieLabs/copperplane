# CTX-402.2: Implementation Context: Auto-Updater

> **Spec Reference:** Links to [SPEC-402](../specs/SPEC-402-release-signing-and-auto-update.md)

The auto-updater half of `SPEC-402`, split from `CTX-402.1`'s release pipeline for the reason
recorded in that context's own Plan Drift: a real signing keypair is a real secret, better generated
and reviewed as its own slice than folded into the pipeline that publishes the artifacts it signs.
`tauri-plugin-updater`'s trust model is a standalone Ed25519 keypair, entirely unrelated to
Apple/Windows code signing (`SPEC-402` §2) -- no CA, no identity verification, no cost, and nothing
tied to a named individual or organization.

## 1. Feature Definition & Execution Plan

### Phase 1: real keypair generation and secret storage
*   [x] Generated via `npx @tauri-apps/cli@2 signer generate --ci -p <password> -w <path>` -- a real
    Ed25519/minisign keypair, password-protected.
*   [x] The private key and its password were pushed directly to this repo's GitHub Actions secrets
    (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`) via `gh secret set`, then
    deleted from local disk immediately after -- never committed, never left in the working tree or
    this session's own history longer than generation required.
*   [x] Only the public key (safe, non-secret) went into `tauri.conf.json`'s
    `plugins.updater.pubkey`, as the literal base64 content of the generated `.pub` file.

### Phase 2: Rust plugin registration + config
*   [x] `tauri-plugin-updater = "2"` added to `core/tauri-rust/Cargo.toml`; registered in
    `lib.rs`'s `setup()` closure guarded by `#[cfg(desktop)]` -- the updater plugin has no real
    mobile support, so this avoids a no-op registration on a target that will never use it.
*   [x] `tauri.conf.json` gains `plugins.updater` (`active`, `endpoints`: the real, predictable
    GitHub "latest release" download URL for `latest.json`, `pubkey`) and `bundle.createUpdaterArtifacts:
    true` -- the flag that makes a real `tauri build` additionally produce a signed
    `<app>.app.tar.gz`/`.sig` pair alongside the normal `.dmg`, when the two signing env vars above
    are present.

### Phase 3: `scripts/generate_update_manifest.py` -- the real `latest.json`
*   [x] `platform_key_for`: maps a real Rust target triple (`aarch64-apple-darwin`/
    `x86_64-apple-darwin`) to Tauri's own real `latest.json` platform-key convention
    (`darwin-aarch64`/`darwin-x86_64`) -- confirmed against the plugin's own documented manifest
    format, not guessed.
*   [x] `generate_manifest`: assembles the real `{version, notes, pub_date, platforms}` shape from a
    real `.sig` file's content and a real download URL. Exactly one platform key per manifest --
    this pipeline only ever builds the CI runner's single native macOS architecture (`CTX-401.2`'s
    own established scope, no universal binary), named explicitly as a real, pre-existing
    limitation, not something this script hides.

### Phase 4: `release.yml` wiring (extends `CTX-402.1`'s pipeline)
*   [x] The existing `tauri build` step now runs with `TAURI_SIGNING_PRIVATE_KEY`/
    `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` set from the real GitHub secrets -- producing the signed
    `.app.tar.gz`/`.sig` pair alongside the unsigned `.dmg` `CTX-402.1` already built.
*   [x] A new step locates the real `.sig` output, determines the real host target triple
    (`rustc -vV`), computes the real, predictable download URL for the `.tar.gz` asset, and runs
    `generate_update_manifest.py` to produce `latest.json`.
*   [x] The GitHub Release publish step now uploads four real assets: the `.dmg`, the
    `.app.tar.gz`, its `.sig`, and `latest.json`.

### Phase 5: frontend -- `lib/updater.ts` + Settings UI
*   [x] `checkForUpdates()`: wraps `@tauri-apps/plugin-updater`'s real `check()` (which fetches
    `latest.json` and verifies its signature against the embedded pubkey natively) -- returns the
    real `Update` object when one's available, `null` otherwise (a normal state, not an error).
*   [x] `installUpdateAndRelaunch(update)`: downloads, installs, and relaunches -- only ever called
    from an explicit user click (a new "Install & Restart" button), never automatically, matching
    this product's existing "every AI/external step confirmable, never silent" principle.
*   [x] Settings gains a new "Updates" section: "Check for Updates" button, "You're up to date."
    when none found, and the real available version/notes/Install button when one is.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `TAURI_SIGNING_PRIVATE_KEY_PATH` does not work for the actual build/signing step,
    despite `tauri signer generate`'s own help text listing it as a real option.** Found by direct,
    real local testing (this context's own `TEST-007`), not assumed from documentation: a local
    `tauri build` run with only `TAURI_SIGNING_PRIVATE_KEY_PATH` set failed with "A public key has
    been found, but no private key." Only the raw key-string env var
    (`TAURI_SIGNING_PRIVATE_KEY`) is actually honored by the bundler's signing step. `release.yml`
    was already written correctly (the GitHub secret holds the real key-file *content*, not a path),
    but this would have been a real, silent CI failure on the very first tagged release had it not
    been caught here first -- exactly the value of testing the actual mechanism locally with a
    throwaway keypair before trusting it in a real, harder-to-debug CI environment.
*   **Deviation 2: a real, harmless warning surfaced during the real local test build** ("The
    updater secret key... does not match the public key from `plugins > updater > pubkey`") --
    expected and correct, since the local test deliberately used a throwaway keypair, not the real
    production one stored in GitHub secrets. Recorded here as confirmation the mismatch-detection
    itself works, not as a bug.
*   **Deviation 3: `latest.json`'s `platforms` object always carries exactly one key, a real,
    pre-existing limitation this context inherits rather than introduces.** `CTX-401.2` already
    scoped this pipeline to the CI runner's single native macOS architecture, no universal binary.
    Named explicitly again here since it directly determines what the update manifest can honestly
    contain -- a user on the other macOS architecture gets no update entry at all from this release,
    the same real gap the `.dmg` itself already has.
