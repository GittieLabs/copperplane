# CTX-401.2: Tauri sidecar wiring: a real packaged app spawning the frozen daemon

> **Spec Reference:** Links to [SPEC-401](../specs/SPEC-401-python-sidecar-packaging.md)

`CTX-401.1`'s own real, deferred remainder: wiring the frozen daemon binary into Tauri's
`externalBin` mechanism, replacing `core/tauri-rust/src/lib.rs`'s `daemon_script_path()`
(`env!("CARGO_MANIFEST_DIR")`-relative) and `core/tauri-rust/src/daemon.rs`'s `spawn_daemon`
(`Command::new("python3")`) for real bundled builds, `cargo tauri dev` unchanged.

**A real, deliberate correction to `CTX-401.1`'s own Plan Drift, found by reading the real
`tauri-plugin-shell`/`tauri-bundler` crate source (both already cached locally) before writing any
code -- not guessed:** `CTX-401.1` predicted this phase would need to switch `spawn_daemon` from
`std::process::Command`/`ChildStdin` to `tauri_plugin_shell`'s own `Shell::sidecar()`/`Command::
spawn()` API, which returns a materially different shape (`(Receiver<CommandEvent>, CommandChild)`,
an async event-channel, not a raw `ChildStdin`/`ChildStdout`) -- a real risk to `SPEC-101`'s crash
shield, whose Windows Job Object assignment reads a raw process `HANDLE` off `std::process::Child`
directly. Reading `tauri_plugin_shell::process::Command::new_sidecar`'s real implementation shows it
does nothing more than resolve the sidecar's real on-disk path (`std::env::current_exe()`'s own
parent directory, per `relative_command_path`) and hand it to a plain `std::process::Command` --
and `tauri-bundler`'s real macOS bundling code (`copy_binaries_to_bundle`) copies `externalBin`
files into `Contents/MacOS/`, the exact same directory the main compiled binary itself lives in, with
the `-<target-triple>` suffix stripped. This means the *entire* existing `spawn_daemon`/`DaemonHandle`
/Windows-Job-Object architecture can stay completely unchanged -- only the resolved `program`/`args`
passed into the same `std::process::Command::new(...)` call needs to differ between dev and release
builds. This is dramatically more surgical than what `CTX-401.1` predicted, and is recorded here
precisely because a wrong prediction, caught before it shaped real code, is exactly what this
repo's own Plan Drift norm exists for.

**A second real, concrete finding, also caught before any code assumed otherwise:** this dev
machine's real, active Rust toolchain (`rustup show`) is `stable-x86_64-apple-darwin` -- despite
running on real Apple Silicon hardware (`uname -m` reports `arm64`). The externalBin binary must be
named with the `-x86_64-apple-darwin` target-triple suffix to match what `cargo`'s own build
actually targets, not the `-aarch64-apple-darwin` suffix `uname -m`'s hardware report would have
wrongly suggested.

## 4. Plan Drift & Architectural Changes

**The user directly click-tested the real running dev-mode app after this refactor landed and
confirmed existing functionality still works** -- the exact real, hands-on verification this
repo's own norms value, and the one piece this context's own automated/scripted checks couldn't
substitute for on their own.

**A real, pre-existing bug found while running `tauri build` for the first time in this project's
history.** `tauri.conf.json`'s `frontendDist` was `"../apps/tauri-ui/dist"` -- one level up from
`core/tauri-rust/`, resolving to `core/apps/tauri-ui/dist`, which has never existed. The correct
path is `"../../apps/tauri-ui/dist"` (two levels up, since `apps/` and `core/` are siblings under
the repo root). This was never caught before because `frontendDist` is only read by `tauri build` --
`cargo tauri dev` (the only build mode any prior `CTX-*.md` in this project has ever actually run)
uses `devUrl` instead, a completely separate config key. Fixed as part of this context, since
`CTX-401.2`'s own Phase 3 verification step is the first thing in this project to actually need a
real production build to succeed.

**A second real prediction this context's own intro got wrong, in the opposite direction from what
was expected -- also caught by real testing, not left standing.** The intro above predicted (from
`rustup show`'s real, verified "active toolchain: stable-x86_64-apple-darwin") that the sidecar
binary would need the `-x86_64-apple-darwin` suffix, explicitly correcting what `uname -m`'s `arm64`
hardware report would have wrongly suggested. The first real `tauri build` attempt failed instead
looking for `-aarch64-apple-darwin` -- and the compiled main binary is verifiably real x86_64
(`file` on the actual output confirms it). The proximate cause, read from `tauri-bundler`'s own real
source: its `target_triple()` doesn't ask cargo what it actually built -- it shells out fresh to
`rustc --print cfg` and parses `target_arch` from that output. Run directly in an interactive shell
in this same repo directory, that command reports `x86_64` (matching the real compiled binary,
matching the original prediction) -- yet the *same* command, run as a subprocess of `npx
@tauri-apps/cli@2 build`'s own Node process, evidently resolved differently (the output DMG that
build produced is literally named `hardware-agent-studio_0.1.0_aarch64.dmg`). The exact mechanism
for that divergence (some difference in the child process's `PATH`/`RUSTUP_TOOLCHAIN`/environment
between an interactive shell and `npx`'s own spawned subprocess) was not run to ground -- doing so
was judged not worth the time against this context's own real goal of proving the wiring works.
Worked around pragmatically and honestly: both suffix variants
(`hardware-agent-studio-daemon-x86_64-apple-darwin` and `-aarch64-apple-darwin`) of `CTX-401.1`'s
frozen binary were placed in `services/python-daemon/dist/`, so the build succeeds regardless of
which one the bundler's own subprocess resolution lands on. Recorded as a real, open, only
partially-understood environment quirk -- not silently resolved -- for whoever next touches release
tooling on this machine (`SPEC-402`) to actually root-cause if it matters there.

**A third, more serious problem -- self-found by reading real CI logs, not reported by the user --
that broke `cargo build`/`cargo test` on all three CI platforms, and the fix for it.** After
`6ccf620` pushed a top-level `externalBin` entry to `tauri.conf.json` and opened PR #81, real GitHub
Actions logs (`gh run view --log-failed`) showed `cargo test` failing on `macos-latest`,
`ubuntu-latest`, AND `windows-latest` -- each looking for a different target-triple-suffixed
sidecar filename that didn't exist. The root cause, confirmed by reading the actual failure output:
`tauri-build`'s own `build.rs` performs an unconditional existence check on every configured
`externalBin` resource path on **every** `cargo build`/`cargo test` invocation, not just `tauri
build`'s bundling step -- and `services/python-daemon/dist/` is (correctly) gitignored, so no fresh
CI checkout has ever had a file there. Simply having a non-empty `externalBin` entry in the
top-level config makes every cargo invocation on every platform require a real file to exist,
which is a far bigger blast radius than `SPEC-401`'s actual macOS-only scope.

Fixed in three parts, each verified for real rather than assumed:
1. Moved `externalBin` out of `tauri.conf.json`'s top-level `bundle` and into a new
   `tauri.macos.conf.json`, using Tauri v2's real platform-config-override mechanism (confirmed via
   `tauri-utils` crate source) -- merged only when actually building for macOS, so `ubuntu-latest`
   and `windows-latest` CI no longer have an `externalBin` entry at all and skip the check entirely.
2. Committed two tiny (922-byte) placeholder executable shell scripts at both real macOS
   target-triple paths (`-aarch64-apple-darwin` and `-x86_64-apple-darwin`) -- not the real 32MB
   PyInstaller binary -- so `macos-latest` CI's existence check passes without needing a frozen
   build artifact in version control. Each placeholder `exit 1`s loudly with a explanatory message
   if ever actually executed by mistake, rather than silently pretending to be the daemon.
3. Fixed the `.gitignore` rule that was supposed to let those two placeholders be tracked. The
   first attempt (three `!`-negation lines placed directly after the existing PyInstaller comment
   block, *before* the pre-existing blanket `dist/` rule further down the file) was verified with
   `git check-ignore -v` to **not work** -- both placeholders were still reported ignored. The real
   cause: gitignore is last-match-wins, and the blanket `dist/` rule appearing *later* in the file
   was re-excluding the directory regardless of the earlier negation. The fix was to move the
   negation block to *after* the blanket `dist/` rule, and use git's documented three-step shape
   (`!services/python-daemon/dist/` to un-ignore the directory itself, `services/python-daemon/dist/*`
   to re-ignore its contents, then two more specific `!` lines for the two placeholder files) -- a
   bare directory-level negation alone does not un-ignore files under an already-excluded parent.
   Re-verified with `git check-ignore -v` on all four relevant paths (both placeholders now
   correctly untracked-by-ignore; the real unsuffixed binary name and `apps/tauri-ui/dist/index.html`
   both still correctly ignored) before trusting it.

Worth stating plainly: none of this was caught by this context's own extensive local verification
(Phase 3's real `tauri build` and `.app` launch), because local verification always had a real or
placeholder binary already sitting on disk. It only surfaced once actual CI -- a genuinely fresh
checkout with nothing manually placed -- was exercised. This is exactly the gap this repo's "verify
against the real thing" norm exists to close, and a reminder that "the real thing" for a packaging
change includes a clean checkout, not just this machine's already-populated working tree.
