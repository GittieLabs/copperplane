# CTX-401.2: Tauri sidecar wiring: a real packaged app spawning the frozen daemon

> **Spec Reference:** Links to [SPEC-401](../specs/SPEC-401-python-sidecar-packaging.md)

`CTX-401.1`'s own real, deferred remainder: wiring the frozen daemon binary into Tauri's
`externalBin` mechanism, replacing `core/tauri-rust/src/lib.rs`'s `daemon_script_path()`
(`env!("CARGO_MANIFEST_DIR")`-relative) and `core/tauri-rust/src/daemon.rs`'s `spawn_daemon`
(`Command::new("python3")`) for real bundled builds, `cargo tauri dev` unchanged.

**A real, deliberate correction to `CTX-401.1`'s own Plan Drift, found by reading the real
`tauri-plugin-shell`/`tauri-bundler` crate source (both already cached locally) before writing any
code -- not guessed:** `CTX-401.1` predicted this phase would need to switch `spawn_daemon` from
`std::process::Command`/`ChildStdin` to `tauri_plugin_shell`'s own `Shell::sidecar()`/`Command::
spawn()` API, which returns a materially different shape (`(Receiver<CommandEvent>, CommandChild)`,
an async event-channel, not a raw `ChildStdin`/`ChildStdout`) -- a real risk to `SPEC-101`'s crash
shield, whose Windows Job Object assignment reads a raw process `HANDLE` off `std::process::Child`
directly. Reading `tauri_plugin_shell::process::Command::new_sidecar`'s real implementation shows it
does nothing more than resolve the sidecar's real on-disk path (`std::env::current_exe()`'s own
parent directory, per `relative_command_path`) and hand it to a plain `std::process::Command` --
and `tauri-bundler`'s real macOS bundling code (`copy_binaries_to_bundle`) copies `externalBin`
files into `Contents/MacOS/`, the exact same directory the main compiled binary itself lives in, with
the `-<target-triple>` suffix stripped. This means the *entire* existing `spawn_daemon`/`DaemonHandle`
/Windows-Job-Object architecture can stay completely unchanged -- only the resolved `program`/`args`
passed into the same `std::process::Command::new(...)` call needs to differ between dev and release
builds. This is dramatically more surgical than what `CTX-401.1` predicted, and is recorded here
precisely because a wrong prediction, caught before it shaped real code, is exactly what this
repo's own Plan Drift norm exists for.

**A second real, concrete finding, also caught before any code assumed otherwise:** this dev
machine's real, active Rust toolchain (`rustup show`) is `stable-x86_64-apple-darwin` -- despite
running on real Apple Silicon hardware (`uname -m` reports `arm64`). The externalBin binary must be
named with the `-x86_64-apple-darwin` target-triple suffix to match what `cargo`'s own build
actually targets, not the `-aarch64-apple-darwin` suffix `uname -m`'s hardware report would have
wrongly suggested.

## 1. Feature Definition & Execution Plan

### Phase 1: A real daemon-invocation resolver, dev/release-branched
*   [x] `core/tauri-rust/src/daemon.rs` gains `sidecar_binary_path()` (the resolved sidecar path --
    `std::env::current_exe()`'s own parent directory, joined with `hardware-agent-studio-daemon` --
    the exact convention verified against real `tauri-plugin-shell` source, not the Tauri "resource
    directory" `app.path().resource_dir()` this context's own earlier Plan Drift had assumed, which
    points at a *different* directory (`Contents/Resources/`) than where `externalBin` files
    actually land (`Contents/MacOS/`)) and `build_daemon_invocation(is_debug_build: bool)` (a real,
    injectable-flag pure function -- not reading `cfg!(debug_assertions)` internally -- specifically
    so both the debug and release branches are real, deterministic unit tests, not just whichever
    one the current build profile happens to be). `daemon_script_path()` (originally in `lib.rs`)
    moved here too, colocated with the rest of the daemon-spawning logic it's now only ever used
    from -- unchanged behavior, still `env!("CARGO_MANIFEST_DIR")`-relative, correct precisely
    because it's now only reached from the debug branch, which always runs from a real checkout.
*   [x] `core/tauri-rust/src/daemon.rs`'s `spawn_daemon` uses this resolved program/args in its
    existing `Command::new(...)` call -- `DaemonHandle`, the Windows Job Object assignment, the
    stdout-forwarding thread, and every other part of `SPEC-101`'s crash shield stay completely
    unchanged, since the underlying process is still a plain `std::process::Child` either way.
    `spawn_daemon`'s own signature simplified (`fn spawn_daemon(app: &AppHandle)`, no more external
    `script_path` param) since resolution is now fully internal to this module.
*   [x] Real verification: the full existing 29-test Rust suite plus 3 new tests (the debug branch
    resolves to `python3` + the real `daemon.py` path unchanged; the release branch resolves to the
    real sidecar path with no extra args; `sidecar_binary_path()` resolves to a path in the exact
    same directory as the real, currently-running test executable) all pass. `cargo tauri dev`
    restarted fresh and confirmed live via `ps aux` -- still spawns `python3 .../daemon.py` exactly
    as before this refactor, unchanged.

### Phase 2: Real `externalBin` wiring
*   [ ] `CTX-401.1`'s frozen `services/python-daemon/dist/hardware-agent-studio-daemon` copied/
    renamed to the real target-triple-suffixed convention Tauri's bundler expects --
    `hardware-agent-studio-daemon-x86_64-apple-darwin` on this machine, matching its real, active
    Rust toolchain (not the arm64 hardware's own architecture).
*   [ ] `core/tauri-rust/tauri.conf.json`'s `bundle` section gains a real `externalBin` entry naming
    it (base name, without the target-triple suffix -- Tauri's bundler appends that itself when
    looking for the source file).

### Phase 3: Real end-to-end verification of a built app bundle
*   [ ] A real `tauri build` (via `npx @tauri-apps/cli@2 build`, the same real invocation
    `CTX-110.1`'s dev-session recovery already established works in this environment) producing an
    actual `.app` bundle with the sidecar inside `Contents/MacOS/`, launched directly (not through
    `open`, so stdout/stderr stay visible) -- confirming the daemon actually starts from inside a
    packaged app with no `python3`/dev-checkout dependency, and a real KiCad round trip still works
    from the bundled sidecar.
