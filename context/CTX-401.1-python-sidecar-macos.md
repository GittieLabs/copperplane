# CTX-401.1: Python Sidecar Packaging: a working macOS freeze

> **Spec Reference:** Links to [SPEC-401](../specs/SPEC-401-python-sidecar-packaging.md)

`SPEC-401`'s own macOS-only scope: a real, reproducible PyInstaller freeze of
`services/python-daemon`, wired into Tauri's `externalBin`/sidecar mechanism, replacing the two
concrete blockers in `core/tauri-rust/src/lib.rs` (`daemon_script_path`'s `env!("CARGO_MANIFEST_DIR")`)
and `core/tauri-rust/src/daemon.rs` (`spawn_daemon`'s `Command::new("python3")`) -- for build/release
mode only, `cargo tauri dev` unchanged.

Phase 0 research (this same session, before any phase checklist item below) already produced real,
load-bearing findings that reshape this plan versus `SPEC-401`'s own speculative risk list -- see
Plan Drift. They're summarized here because they directly determine Phase 1's scope: a plain
`pyinstaller --onefile daemon.py`, run against a Homebrew-framework Python 3.11 (this repo's own
platformio-managed interpreter lacks the shared library PyInstaller requires -- a real, concrete
environment finding), already produces a working binary with **no hidden-imports needed** -- verified
with a real `kicad.get_version` round trip (KiCad 10.0.3) and a real HTTPS call to
`https://api.anthropic.com/v1/messages` (a deliberately-fake key, correctly rejected with a real 401)
through the frozen binary itself, not a mock.

## 4. Plan Drift & Architectural Changes

**`SPEC-401`'s own predicted hidden-imports risk was wrong, and real testing found that out before
any code shipped assuming otherwise.** The spec's own §2/§3 predicted `llm_providers.py`'s lazily
-imported provider SDK classes (`from agentflow import AnthropicProvider`, reached only inside an
`if provider == "anthropic":` branch, only at runtime) would likely need explicit
`--hidden-import` declarations, reasoning that PyInstaller's static analysis is "known to miss"
that pattern. A plain `pyinstaller --onefile daemon.py`, with zero `hiddenimports` entries, produced
a binary that made a real HTTPS POST to `https://api.anthropic.com/v1/messages` and got back a real
401 for a deliberately fake key -- proof the full import chain (AgentFlow's own package, `anthropic`,
`httpx`, `certifi`'s real TLS verification) survived intact. The actual mechanism: PyInstaller's
module-graph analysis parses `import`/`from X import Y` statements by walking a module's AST, not by
executing it -- a conditionally-reached `from agentflow import AnthropicProvider` inside an `if`
block is still *syntactically present* in `llm_providers.py`'s source, so it's found regardless of
whether that branch runs during analysis. The real risk PyInstaller's static analysis actually misses
is *fully dynamic* imports (`importlib.import_module(some_variable)`), which this codebase doesn't
use anywhere in the daemon's own provider-selection code. Recorded here per this repo's own norm --
a wrong prediction, corrected by real testing, is not a failure to hide.

**A real, concrete environment finding, not a hypothetical:** this repo's own dev-loop Python (a
platformio-managed interpreter every prior `CTX-*.md` in this project has used for every real KiCad/
FreeCAD verification) was built without a shared library, and PyInstaller refuses to run against it
outright ("Python was built without a shared library, which is required by PyInstaller"). A
Homebrew-installed `python3.11` (`brew install python@3.11`) provided a real, working alternative --
`sysconfig`'s own `Py_ENABLE_SHARED` reports a misleading `0` even on this real, working framework
build; the actual signal PyInstaller cares about is a real `Python.framework`/`libpython3.11.dylib`
on disk. Whatever CI or release-build environment eventually runs this freeze for real needs a
Python interpreter chosen for this property specifically, not assumed to already have it.

**A real, distribution-relevant Gatekeeper cold-launch delay, found while writing the verification
script, not designed around in advance.** The first (and, empirically, every subsequent) launch of
this ad-hoc-signed frozen binary took ~11 seconds of real wall-clock time before emitting anything on
stdout, despite only ~1.2s of actual CPU time -- a real macOS Gatekeeper/AMFI launch-verification
overhead for an unsigned/ad-hoc-signed executable, not a daemon startup bug. `verify_sidecar.py`'s
own timeouts (20s for `daemon.ready`) were sized generously specifically because of this, found by
direct measurement, not guessed. This is real, concrete evidence for why `SPEC-402` (code signing)
matters beyond just Gatekeeper's install-time warning dialog -- an unsigned sidecar's *every* cold
launch pays this real latency cost, which interacts directly with `SPEC-107`'s own heartbeat-timeout
crash-shield logic once this sidecar is wired into the real supervisor in Phase 2/3. Flagged here as
a real, load-bearing constraint for whoever picks up `SPEC-402`, not silently absorbed.

**Binary size came in real and small: 32MB**, not the "tens to a few hundred MB" `SPEC-401`'s own
§3 speculated for a `kipy` + `pynng` + `trimesh` + three LLM provider SDKs freeze. A real, corrected
number, worth recording precisely rather than leaving the spec's own speculative range standing
uncorrected.

**Phases 2 and 3 (Tauri `externalBin` wiring, a real built-`.app` end-to-end launch) are not yet
done.** This session's real, verified scope is Phase 1 only: a working, committed, re-verifiable
macOS freeze of the daemon binary itself, run and driven directly (not yet through Tauri's sidecar
mechanism or a real app bundle). That remaining, substantial work is named explicitly rather than
implied complete by this context's own real progress so far.
