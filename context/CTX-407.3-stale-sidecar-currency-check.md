# CTX-407.3: Stale Sidecar Currency Check

> **Spec Reference:** Links to [SPEC-407](../specs/SPEC-407-sidecar-build-integrity.md)

A ninth failure mode, found the way `SPEC-407`'s own eight were found -- by building the app and
using it, not by reading the code.

`SPEC-407` §2.2 defines the bundle-time checkpoint as two questions: is the file about to be
bundled the placeholder, and does its architecture match the build target. Both were asked and both
answered correctly. The build was green. The app launched, the daemon spawned, `daemon.ready`
arrived with `kicad_available: true` and `freecad_available: true`, and the Settings screen
rendered every provider correctly.

Then **Validate** returned `Method not found: llm.validate_model`.

The routes were not missing from the source. They were missing from the **binary**, which had been
frozen on 2026-08-27 at 17:52 -- four days before `a5e084f` added them on 2026-08-31 at 11:46.
`ensure_sidecar.py` reported *"present, real, and the right architecture"*, which was true, and
waved the build through.

This is failure mode 7's shape exactly -- *"a mis-frozen sidecar starts, reports ready, and runs
with every AI route disabled"* -- reached by a road §2.1's table does not list. The distance
between cause and symptom that `SPEC-407` §2.2 is written against is here at its widest: the cause
is a file's age, and the symptom is a button in a settings dialog.

## 1. Feature Definition & Execution Plan

### Phase 1: Decide currency at the one place that already decides usability

*   [x] `staleness(path, daemon_dir)` returning `(is_stale, reason)`, reported through
    `inspect()` rather than from `main()`. `inspect()`'s own docstring already claims to be *"the
    single place that decides whether a sidecar is usable, so the check-only mode and the freeze
    path can never disagree"* -- adding a fourth property anywhere else would falsify that.
*   [x] The reason names both timestamps and the file that moved, because "stale" alone sends
    someone to the packaging rather than to the freeze.
*   [x] `inspect()` takes `daemon_dir` as a parameter defaulting to this checkout's own, rather
    than reading the module global. Without it, calling `inspect()` on a temp file silently
    compares that file against the real repository's sources -- which is what the existing
    arch-mismatch tests were unknowingly doing the moment currency was added.

### Phase 2: mtime, not a content hash

*   [x] Compare the sidecar's mtime against the newest frozen source. **A hash was designed first
    and rejected** -- see §4 Deviation 1. It would have broken every release leg.
*   [x] Frozen sources are the top-level `*.py` modules plus `daemon.spec` and `requirements.txt`.
*   [x] `scripts/` and `tests/` are excluded. Neither is frozen into the binary, so editing this
    script or a test must not cost a contributor a multi-minute re-freeze -- exactly the friction
    `CTX-407.2` exists to remove.
*   [x] No readable sources means never stale. A source tarball or a vendored copy must not fail a
    build over a question it cannot answer.

### Phase 3: Repair TEST-002, which was already red

*   [x] `TEST-002` read the four placeholders from the **working tree**, but a real local freeze
    overwrites the host's placeholder there -- the documented, expected state that
    `ensure_sidecar` itself prints a NOTE about. So the test failed on any machine that had
    actually built the app, which is every machine a contributor runs it on. Confirmed pre-existing
    by stashing this context's changes and re-running it.
*   [x] It now reads the committed blob via `git show`, which is what *"the four REAL committed
    placeholders"* was always meant to mean.

### Not in this context

*   **Applying `docs/release-yml-spec-407.patch`.** `CTX-407.2` Phase 3 left it unapplied for lack
    of a `workflows` token. Still unapplied, so `release.yml`'s freeze sequence remains a second
    implementation. This context does not depend on it -- the currency check is deliberately inert
    in CI (§4 Deviation 1) -- but the "one implementation" property `CTX-407.2` claimed is still
    not true.
*   **Amending `SPEC-407` §2.1's table to add this as a ninth row.** A spec edit belongs in its own
    reviewed change, not as a side effect of the context that found it. Noted here so it is not
    lost. The table already says "seven failure modes" in prose while listing eight rows.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: a content hash was designed first, and would have broken every release.**
    *   *Reasoning:* Hashing was the initial choice, on the stated grounds that `git checkout`
        rewrites mtimes without changing content and `ensure_sidecar`'s own placeholder check
        deliberately prefers *"an exact test rather than a heuristic"*. That reasoning was sound in
        isolation and wrong in context. A hash needs a manifest written next to the binary, and
        `release.yml` freezes with raw `pyinstaller` rather than through `freeze_sidecar` -- so it
        would never write one. Every CI leg would then read "no manifest", declare a sidecar it had
        just built to be stale, and re-freeze it.
    *   *What made it visible:* checking whether `release.yml` calls `ensure_sidecar` at all. It
        does not directly -- but it runs `tauri build --config tauri.release.conf.json`, and that
        file sets only `createUpdaterArtifacts`. Tauri merges configs, so `tauri.conf.json`'s
        `beforeBuildCommand` still runs, and `ensure_sidecar.py` with it. An initial reading of
        "release.yml does not call it" was wrong in the direction that matters.
    *   *Impact:* mtime is not the weaker choice here, it is the correct one. It is self-recording:
        CI checks out sources and *then* builds, so the artifact is always newer and the check is
        inert in exactly the environment a false positive would be most expensive. The cost is a
        spurious re-freeze when a branch switch rewrites a source's mtime without net content
        change. That is rare, self-correcting, and errs toward a working app.

*   **Deviation 2: the diagnosis was confirmed by a test that could not have worked.**
    *   *Reasoning:* The first attempt to prove the binary was stale ran `strings` over it and
        grepped for route names. All three came back missing -- including
        `llm.get_provider_records`, which demonstrably worked in the running app. PyInstaller
        stores compiled `.pyc` inside an appended archive, so `strings` cannot see route names at
        all; the test would have "confirmed" the hypothesis for a fresh binary just as readily.
    *   *Impact:* replaced with a real JSON-RPC probe carrying a known-good control route. Worth
        recording because the bad test agreed with the correct conclusion -- a check that cannot
        fail is not evidence, even when the thing it appears to show is true.

*   **Deviation 3: an earlier daemon-level verification passed while the bug was live.**
    *   *Reasoning:* Before the UI was exercised, `list_models` and `validate_model` were driven
        against live Ollama by importing `llm_providers` directly. Real vendor, real server, no
        mocks -- and it passed, closing `CTX-324.1`'s stated "no real vendor was contacted" gap.
        It also skipped the frozen binary entirely, which is where the defect was.
    *   *Impact:* `CLAUDE.md`'s "verify against the real thing" was satisfied at the module level
        and still missed a shipped-artifact bug. For anything the sidecar carries, the frozen
        binary is the real thing, not the module it was built from.
