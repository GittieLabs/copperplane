# CTX-903.2: Implementation Context: Three Checks the Suite Could Not Make, and One Deadline

> **Spec Reference:** Links to [SPEC-903](../specs/SPEC-903-python-frontend-ci.md)

## 0. Chosen from defects, not from ideas

Five defects reached the maintainer this week and none was caught by 1077 daemon tests and 794 UI
tests. Two were in categories the suite **structurally cannot see**, and those are the ones worth
building checks for:

| Defect | Could a test have caught it? |
| :--- | :--- |
| A primary button invisible in both themes | No — nothing asserts a colour. **Guarded** in `CTX-336.1` |
| Every AI feature broken on Anthropic | Not as written — nothing asserted the constraint. **Guarded** in `CTX-204.2` |
| `included_severities` shipped and never rendered | **No** — an unread optional property is valid TypeScript |
| A config write reverting the provider just chosen | Yes, once the write's *shape* was asserted. **Guarded** in `CTX-336.1` |
| DRC wording on the Schematic tab | Only by a human reading it |

This context builds the check for the third, plus the one class nobody had hit yet but that the
same reasoning predicts: the UI naming a route the daemon does not have.

## 1. Feature Definition & Execution Plan

### Phase 1: A field the daemon sends and nothing reads
*   [x] `tests/deadFields.test.ts` — every field declared on a daemon-response type must be read
        somewhere in `src/`. `tsc` cannot catch this: an unread optional property is valid
        TypeScript, and a component test only asserts what is rendered, never what was promised and
        is not.
*   [x] Scoped to a named list of response types rather than every interface: these are the shapes
        where "we receive it and show nothing" is a defect. A payload type has no such expectation,
        and sweeping everything in would bury the signal.
*   [x] It found two on its first run, both now used — see §4.

### Phase 2: A route the UI calls and the daemon does not have
*   [x] `tests/test_ui_route_parity.py` — every `dispatch('x.y')` and `submitJob('x.y')` literal in
        the UI must exist in `daemon.ROUTES`. The same disagreement `CTX-407.5` checks between the
        frozen artifact and the checkout, one boundary further out: a renamed route compiles,
        type-checks, passes every unit test, and fails on the first click.
*   [x] Both checks include a test that they **notice** — a check that cannot fail is not evidence,
        and a guard against a rare event is exactly the kind that quietly stops working.

### Phase 3: One deadline for a parallel suite
*   [x] `asyncUtilTimeout: 5000` in a setup file, replacing a per-call bump.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the dead-field check found two on its first run, and both were worth showing
    rather than deleting.** `FootprintDetail.model_ref` and `model_path` were declared and never
    read — so the detail view said *"No 3D model is installed for this footprint"* while holding
    the path of the model KiCad expected. A footprint naming a `.step` that is not installed is a
    different problem from one naming none at all, and only that path tells them apart. It now
    says which. `ProjectsInRoot.root` was likewise unread while the storage-change modal said
    *"stored in the current location"* — it now names the folder. **A dead field is often a missing
    sentence, not dead weight.**

*   **Deviation 2: my own self-test passed while being wrong.** The dead-field guard's
    "would-it-notice" case declared two invented fields and asserted one was flagged; both were,
    because neither name appears anywhere. It looked green because the assertion compared the wrong
    list. Fixed by using a field name the codebase really does read. Recorded because it is the
    exact failure the check exists to prevent, committed inside the check itself.

*   **Deviation 3: the route-parity check found nothing, and is kept anyway.** All 73 routes the UI
    calls are registered. That is a real result rather than a wasted check: it says the boundary is
    currently sound, and it will fail the moment a rename breaks it. A guard is not judged by
    whether it fires on the day it is written.

*   **Deviation 3b: my fake sidecar was a POSIX shell script, and windows-latest said so.** The
    stand-in that answers `daemon.list_routes` was written `#!/bin/sh`, which cannot execute on
    Windows — so three of the six probe tests failed there and passed on this machine. `SPEC-903`
    exists for exactly this, and it caught it on the first run, the way `CTX-101.1` Deviation 4
    records it catching a Windows compile failure. The fake is now a Python script run through
    `sys.executable`, and `probe_routes` takes an optional `command` so a test can stand something
    in for a binary. **The alternative — skipping those tests on Windows — would have left the
    platform least represented here also least tested.**

*   **Deviation 4: raising a timeout twice was the signal that the timeout was not the problem.**
    `Overview.test.tsx` flaked in `CTX-331.1`, was "fixed" by raising one call from 1s to 5s, and
    then a *different* test in the same file failed the same way. The suite runs 44 files in
    parallel across 10 cores, and `waitFor`'s deadline is wall-clock: a test that finishes in 30ms
    alone can sit unscheduled for a second. The deadline is now set once, for the environment,
    rather than per test — and the per-call bump was removed, because leaving it implies one test
    is special when the condition is general.

    **This reduced the flake without eliminating it:** three consecutive full runs after the change
    gave 794 / 794 / 793. Stated plainly rather than declared fixed.

## 5. Verification Notes

*   794 UI tests across 44 files; 1079 daemon tests, one failure — the live-Anthropic
    datasheet-guidance test whose 60s deadline covers 15+ real API calls, which predates this work
    and passes alone. Lint clean.
*   Both new guards are proven to notice, not merely to pass.
*   **Where I stopped, and why.** The two remaining classes from this week's defects are the
    shared-component copy leak (DRC wording on the Schematic tab) and the residual test flake.
    The first I could only guard with a rule fuzzy enough to be wrong often — "a shared component
    must not contain tool-specific words" has no principled boundary, and a check that cries wolf
    gets deleted. The second is intermittent, load-dependent, and no longer reproducible on demand;
    chasing it further would cost more than the remaining risk. Both are recorded rather than
    half-built.
