# CTX-402.8: Implementation Context: Release Checksums and What Is Actually Published

> **Spec Reference:** Links to [SPEC-402](../specs/SPEC-402-release-signing-and-auto-update.md)

Two things, one cause. The maintainer asked for checksums, because the Windows build is unsigned and
a person downloading it has nothing to check it against. Confirming what a release currently ships
in order to write that up turned over the second thing: **Windows and Linux installers have been
published since `v0.2.0` on 2026-08-27, and every user-facing page still said they were not.**

`docs/site/.../install.md` -- the page whose entire job is getting someone installed -- carried a
table reading "❌ Not published. Build from source." for Windows, Linux, and Intel macOS. All three
have shipped in every release for eight days. `SPEC-408` exists to recruit Windows and Linux users
as validators; the install page was turning them away.

## 1. Feature Definition & Execution Plan

### Phase 1: establish what a release actually publishes
*   [x] `gh release view v0.3.1 --json assets` -- eleven real assets: `_aarch64.dmg`, `_x64.dmg`,
    `_x64-setup.exe`, `_x64_en-US.msi`, `_amd64.AppImage`, `_amd64.deb`, three `.sig` files, the
    `.app.tar.gz` updater payload, and `latest.json`. No checksum file of any kind.
*   [x] Checked backwards, not just the latest: `v0.2.0` and `v0.3.0` each carry four
    Windows/Linux assets too. The docs were not briefly stale, they were wrong for three releases.
*   [x] Confirmed the `.sig` files are `tauri-plugin-updater` Ed25519 signatures over update
    payloads (`CTX-402.2`), not code signatures -- they say nothing about a first manual download,
    which is exactly the gap the maintainer identified.

### Phase 2: generate and publish the checksums
*   [x] `scripts/generate_checksums.py` -- SHA-256 over the installers a human downloads, emitted in
    the exact `<hash><two spaces><basename>` form `sha256sum -c` and `shasum -a 256 -c` read back.
*   [x] Installers only. `.app.tar.gz`, `.sig` and `latest.json` are deliberately excluded, with the
    reason stated in the script: those already carry a real Ed25519 signature the updater verifies
    before installing anything, which is strictly stronger than a hash published beside the file.
    Hashing them would imply the weaker check is what protects an update. It is not.
*   [x] Fails loudly on an empty search and on two artifacts sharing a basename. An empty
    `SHA256SUMS.txt` is worse than none: `sha256sum -c` exits 0 on it having verified nothing, and
    the workflow writes the file with `>`, so a zero exit would publish exactly that.
*   [x] `release.yml` generates the manifest, `cat`s it into the run log, and uploads it. The log
    echo is deliberate: the Actions log for a tag is a second record of those hashes that editing a
    release asset cannot reach.

### Phase 3: say what a checksum is worth, and not more
*   [x] The manifest is published to the same release page as the files it describes. It proves
    integrity -- your download is complete and identical to what CI built -- and not authenticity
    against anyone able to rewrite the release itself. Stated plainly in the script docstring, the
    README, and a `:::caution` on the install page rather than left for a reader to work out.
*   [x] Windows section says what SmartScreen will do, why it is right to, and how to check the file
    before clicking through it -- rather than "click Run anyway", which is what a user would
    otherwise learn to do reflexively.

### Phase 4: correct every page that said the build did not exist
*   [x] `README.md` "Try it": a four-row table naming the exact file to take per platform and its
    signing state, replacing "there is no published build yet."
*   [x] `install.md`: rewritten -- real per-platform sections for Windows and Linux, a "Verify your
    download" section with a working command for each, and "Build from source" reframed from
    *required* to *optional*.
*   [x] `index.mdx`: said "one macOS build, for Apple Silicon." Missed the Intel build as well.

### Phase 5: tests that run the thing rather than assert about it
*   [x] Generate a manifest, run the real `shasum`/`sha256sum` against it, then flip one byte and
    require the same tool to reject it.
*   [x] Extract the verify command from `install.md` itself and run it, on the platform it is
    written for, staged the way a person really has it: one installer downloaded, six listed.
*   [x] Parity between the generator's installer set and `release.yml`'s publish globs.
*   [x] A structural guard that the install page names every installer the release publishes.

## 4. Plan Drift & Architectural Changes

**1. The stated task was checksums; the larger defect was the docs, and it was found by checking.**
The maintainer asked for a checksum file. Establishing what to hash meant listing a real release's
assets, which is the only reason anyone noticed that every install page had been wrong for three
releases. Had I written the checksum step from the workflow file alone -- which contains everything
needed to do it -- the docs would still say Windows users must build from source. Reading the
artifact rather than the source that produces it found this, same as the four defects
`CLAUDE.md` already records under that norm.

**2. I repeated the stale claim myself, in `CTX-408.1`, days ago.** The README rewrite for SPEC-408
carried "Windows and Linux: there is no published build yet" forward from the old README without
checking it. I fixed the version staleness and the product-name staleness in that same file, in that
same pass, and copied the platform claim across untouched because it read like prose rather than a
fact. It was a fact, and it was false when I wrote it.

**3. The first version of the documented macOS command was wrong, and only running it showed that.**
`shasum -a 256 -c SHA256SUMS.txt` verifies correctly and reports alarmingly: a person downloads one
installer, the manifest lists six, and the five they do not have print `FAILED open or read` before
it exits 1. A healthy download looks broken. `--ignore-missing` fixes it and is supported by macOS's
`shasum` -- confirmed by running both forms on this machine, not from documentation. The test that
caught it is the one that extracts the command from the page and runs it in the user's real
situation; a test asserting "the page mentions shasum" would have passed.

**4. The parity test caught its own author.** `.AppImage.sig` was missing from the hand-written
exclusion list, so the first run reported the release publishing something neither hashed nor
deliberately excluded. Fixed by making the exclusion a rule -- anything ending `.sig` -- rather than
an enumeration of compound extensions, which is exactly how the omission happened.

**5. Build provenance attestation was considered and deliberately not done here.** The repo is
public, so `actions/attest-build-provenance` is available at no cost, and it is the thing that would
actually give an unsigned Windows installer *authenticity* rather than integrity -- a signed
statement, verifiable with `gh attestation verify`, that this exact binary came from this repo's
workflow. It is left out of this context on purpose: it adds a step that can fail inside a release
pipeline that currently works, and it cannot be verified without pushing a real tag. It is the right
next step and belongs in its own context, with a real release to prove it.

**6. Recovered from my own mistake mid-session, and it cost the whole file.** After proving the
`--ignore-missing` guard failed on the real bug, I ran `git checkout -- install.md` to undo the
temporary damage. The file was not committed yet, so that discarded the entire rewrite rather than
the two-line experiment, and it had to be redone from scratch. Commit first, then experiment.

**7. Not verified:** every install instruction on this page for Windows and Linux -- SmartScreen's
exact wording, `sudo apt install ./…deb`, the AppImage's FUSE behaviour -- is written from
knowledge, not from a machine. The PowerShell verify command is executed by the `windows-latest` CI
leg, so that one command is genuinely proven on the platform it targets; the surrounding prose is
not. The install page says so, in the same caution block that already admitted the CAD integration
is unverified there.

**8. The Windows CI leg found two real defects in this change, and neither was reachable from a
Mac.** First: on Windows, text-mode stdout translates `\n` to `\r\n`, so the manifest carried CRLF
and `sha256sum -c` reported "No such file or directory" for every entry -- a manifest whose hashes
were all correct, unreadable by the tool it exists for. The publish job runs on macOS, so a real
release would never have shown it; a machine writing the file on Windows would ship a manifest that
verifies nothing. Fixed at the source (`reconfigure(newline='\n')`) rather than in the test, because
a checksum manifest is a wire format. Second: `Get-FileHash` came back as an unrecognized cmdlet
under the runner's `powershell`, so the test now runs `pwsh` -- PowerShell 7, which the runner ships
and which most current Windows desktops have. The documented command is unchanged; `Get-FileHash` is
the right thing to tell a person to run.

**9. The Windows verify command is now genuinely proven on Windows.** `TEST-010`/`TEST-011` ran on
`windows-latest` without skipping: the exact PowerShell block printed in `install.md` accepted a
real download and rejected a corrupted one. That is worth naming precisely, because it is rare here
-- almost everything else about Windows in this repo is unverified, and this context's own item 7
says so. One command is proven. The prose around it still is not.

**10. An unrelated pre-existing failure, recorded rather than fixed.**
`test_async_jobs.TestRealDatasheetGenerateGuidanceJob` fails roughly two runs in three on this
machine with `agentflow.workflow: Node validate failed: Extraction did not return valid JSON`. It
skips in CI (no `ANTHROPIC_API_KEY`), so it never blocked this PR, and it is untouched by this
change. It looks like a real intermittent failure of `datasheet.generate_guidance` in the shipped
app -- the model occasionally returns malformed JSON and the validate node gives up rather than
retrying. Reported to the maintainer; a fix belongs upstream in AgentFlow's extraction, not here.
Ubuntu also failed once on `test_context_index.TestNeedsRebuild.test_003` (mtime granularity) and
passed on re-run; `develop` is green, so that is a flake and not a regression.
