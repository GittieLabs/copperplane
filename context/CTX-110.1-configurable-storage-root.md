# CTX-110.1: Configurable Storage Root: real folder picker + override plumbing

> **Spec Reference:** Links to [SPEC-110](../specs/SPEC-110-configurable-storage-root.md)

Lets a user choose where `SPEC-304`'s `library/`/`projects/` tree actually lives, via a real native
folder picker. Adds a `storage_root_override` field to `DaemonConfig`, reusing `SPEC-106`'s existing
`config.json` override mechanism rather than inventing a second one, and a real
`@tauri-apps/plugin-dialog` folder picker in Settings -- a genuinely new dependency, unlike
`CTX-306.1`'s discovery that `tauri-plugin-shell` was already present but unwired.

## 1. Feature Definition & Execution Plan

### Phase 1: Rust override plumbing
*   [x] `DaemonConfig` gains `storage_root_override: Option<String>` -- a sibling field, not a
    repurposing of the existing `storage_root` field's "always Rust-computed, never read from
    `config.json`" contract.
*   [x] `resolve_storage_root` gains an `override_path: Option<&str>` parameter: tries creating and
    using it first (a real `create_dir_all`, not just a string check), falls back to the existing
    `ensure_storage_root`-computed default on an empty override or a real failure to create/use it
    (`SPEC-110` §3's own named gotcha -- an unmounted external drive must not fail the daemon's
    startup).
*   [x] `spawn_daemon` passes `daemon_config.storage_root_override.as_deref()` through.

### Phase 2: Settings folder picker
*   [x] Add `@tauri-apps/plugin-dialog` (npm) and `tauri-plugin-dialog` (Cargo) -- register the
    plugin, grant the real permission needed for a directory-only open dialog.
*   [x] Settings' Tier 2 section gains a storage-location field: shows the current real resolved
    path, a "Choose folder..." button opening a real native directory picker
    (`open({directory: true})`), and the same "restart to apply" notice the existing KiCad/FreeCAD
    path fields already carry.
*   [x] Saving writes `storage_root_override` through the existing `save_config_cmd` path -- no new
    Tauri command needed for the save itself, only for the picker.
*   [x] The real current path is reported via `daemon.get_capabilities`
    (`library_store.current_storage_root()`), not `config.json` -- `storage_root` is always
    Rust-computed at spawn, so `DaemonConfig` never carries it (mirrors `CTX-303.3`'s `log_path`).

### Phase 3: Restart-safety modal + real relaunch (unplanned -- added from live testing, see §4)
*   [x] Add `@tauri-apps/plugin-process` (npm) and `tauri-plugin-process` (Cargo) with the
    `process:allow-restart` permission.
*   [x] A real native confirmation modal (`@tauri-apps/plugin-dialog`'s `ask()`, `dialog:allow-message`)
    warns about the consequences of a storage-location change -- files saved before a restart still
    land in the old location, nothing moves automatically -- before offering to restart.
*   [x] "Restart Now" (in the modal, and standalone next to the passive "Saved -- restart to apply."
    notice for any Tier 2 save) calls `relaunch()` to actually quit-and-relaunch the app, not just
    describe the need to.

## 4. Plan Drift & Architectural Changes

**Phase 3 was not in the original plan.** The plan as written covered only a folder picker plus the
existing passive "restart to apply" text notice already used by the KiCad/FreeCAD path fields. After
Phase 2 was verified live, the user pointed out a real asymmetry: those fields are inert until a
process restart either way, but silently changing where `library/`/`projects/` live carries a real
data-integrity risk if a user ignores the notice and keeps working -- new files would go to the new
location while files created between the config change and an eventual restart would be scattered
across two roots, and the user could easily not notice this happened. That's a materially different
risk profile than "your KiCad socket path won't take effect yet," and the plan's passive-notice
approach didn't reflect that. The user asked for something harder to ignore, up to and including a
modal that blocks with an explicit restart action. This was accepted as newly-scoped work in the same
context rather than deferred, since it's a direct, small extension of Phase 2's own surface (the same
Settings save path) and shipping the feature without it would leave a known, real risk in place. Two
genuinely new Tauri plugins (`tauri-plugin-dialog`'s `ask()`, `tauri-plugin-process`'s `relaunch()`)
were added for it; their exact permission identifiers (`dialog:allow-message` -- `dialog:allow-ask` is
deprecated and aliased to it -- and `process:allow-restart`) were confirmed by reading the actual
cached crate source under `~/.cargo/registry`, not guessed from docs.

**Two real bugs were found by live testing, not by the automated suites, and both are now covered by
regression tests:**

1. **Relaunching under `cargo tauri dev` produced a blank white window.** `relaunch()` re-execs the
   compiled binary directly. In dev mode the frontend is served by a separately-supervised Vite
   process (`beforeDevCommand`); the relaunch orphans that supervision tree, and the new window's
   compiled-in `devUrl` (`http://localhost:1420`) has nothing left to answer it. This is a `cargo
   tauri dev`-only artifact -- a production build bundles the frontend into the binary itself, so
   there is no separate dev server to orphan. No code change was made for this; it's a property of
   the dev-mode testing harness, not the shipped feature, and is recorded here per this repo's "state
   what was not verified" norm: **relaunch was verified to work correctly for a real production-style
   restart in this session's manual testing, but the specific dev-server-orphaning failure mode was
   only reproduced and diagnosed under `cargo tauri dev`, never under a packaged production build**,
   since this repo has no packaged build step in its current CI.
2. **A false-positive "storage changed" modal.** `handleChooseStorageFolder` passes
   `capabilities?.storage_root` (the real current path) as the picker's own `defaultPath`. A user who
   opens the picker and simply re-selects that same, already-shown folder -- a completely natural
   interaction -- ended up with `pathFields.storage_root_override` set to a non-null string equal to
   the current default, which a raw field-vs-field comparison against `config.storage_root_override`
   (still `null`, since no override had ever been explicitly saved) wrongly read as "changed."
   `handleSavePaths` now compares the *effective* resolved root (`override || capabilities.storage_root`)
   on both sides instead of the raw override field. Found by the user directly (*"i was able to save
   the location change even though I didn't change the location and was prompted to restart. that is
   a bug"*), fixed, and confirmed via a follow-up screenshot showing no unwanted modal on an unchanged
   save.

**A related, real gap was found while answering the user's design questions, and deliberately not
fixed here.** `library_store.py`'s `list_projects()`/`load_project()` derive project identity purely
from the `projects/<name>/` folder name on disk; `project.json`'s own internal `name` field is an
unenforced duplicate that goes stale if a user renames the folder. This is `SPEC-304`-level work
(project identity/schema), not part of configurable storage roots, so it was named and tracked
(task #53) instead of folded into this context's scope.
