# CTX-407.1: Fail-Loud Daemon Startup & Packaging Gate

> **Spec Reference:** Links to [SPEC-407](../specs/SPEC-407-sidecar-build-integrity.md)

The first slice of `SPEC-407`: the two checkpoints that can be built and verified entirely in
Python, closing the spec's worst failure mode (a mis-frozen sidecar that looks healthy) and fixing
the gate that was supposed to catch it. The bundle-time check and the app-facing surface are
deliberately deferred — see "Not in this context".

## 1. Feature Definition & Execution Plan

### Phase 1: `daemon.ready` carries degraded state

*   [x] A module-level collector in `daemon.py`, populated by each of the fifteen existing
    `try/except` import guards alongside the `logger.exception` call they already make. The guards
    themselves are untouched — `SPEC-407` §1 is explicit that graceful degradation is correct and
    stays.
*   [x] `_detect_capabilities()` returns `degraded_modules`, a list of `{module, capability}`
    entries, alongside the capability flags it already reports. A copy, not the live list.
*   [x] Never prints. The collector runs at import time and appends to a list; `stdout` remains the
    JSON-RPC wire, per `CLAUDE.md`'s non-negotiable.

### Phase 2: `verify_sidecar.py` stops passing broken binaries

*   [x] Fail when `daemon.ready` reports any degraded module. This is the check the gate never had:
    "the daemon replied" was being treated as proof the artifact was good, which is exactly the
    state that shipped a working-looking app with no AI surface.
*   [x] Drain the child's `stderr` on its own thread and replay it on failure. It was piped and
    never read, which both hid every diagnostic and risked deadlocking the daemon once the pipe
    buffer filled.
*   [x] Count the `daemon.configure` failure. Its `_wait_for` result was discarded, so a run where
    only that check failed printed `FAIL` and still exited 0.

### Phase 3: the two documents that actively mislead

*   [x] `daemon.spec`'s header recommended a Homebrew interpreter that `CTX-402.4` superseded with
    python.org universal2. Corrected, with the `PYTHONFRAMEWORK`-not-`Py_ENABLE_SHARED` trap and
    the arch-consistency rule `target_arch=None` implies.
*   [x] `CONTRIBUTING.md`'s Tier 3 row named the freeze command and nothing else. It now carries
    the three requirements that each produced a silently-broken build, plus a copy-pasteable
    sequence ending in `verify_sidecar.py`.

### Not in this context

*   **The bundle-time placeholder and arch check** (`SPEC-407` §2.3). It needs a Tauri v2 build
    hook that fires on a real bundle but not on a plain `cargo build` — the spec's own §3 names
    this as the most likely thing to go wrong, and it cannot be verified in a Linux container with
    no Tauri build. `CTX-407.2`.
*   **The app-facing degraded-capability surface** (`SPEC-407` §5). It consumes Phase 1's field, so
    it could not have been built before it existed. `CTX-407.3`.

`TEST-003` and `TEST-004` were run against a **real degraded daemon**, not a mock. This Linux
container happens to lack `kipy`, `numpy`, `httpx` and others, so `daemon.py` starts here with nine
optional modules genuinely failing to import — the exact condition `SPEC-407` §2.1 failure mode 7
describes. Before and after were both captured against it:

*   **Before** (the script as it stands on `develop`): `PASS: daemon.ready`, no mention of the nine
    dead modules, no stderr, and the only failure an unrelated `llm.chat` check.
*   **After**: an explicit failure naming all nine capabilities, plus the replayed stderr carrying
    the real root cause (`ModuleNotFoundError: No module named 'kipy'`).

Full suite: `python3 -m unittest discover tests/` from `services/python-daemon` — **462 tests, up
from a 460-test baseline captured before any edit, with the failure and error counts unchanged**
(23 failures, 100 errors, 31 skipped, all pre-existing missing-dependency noise in this container).
The two new tests pass; nothing regressed.

**Not verified, named rather than assumed.** Nothing here ran on macOS or Windows, and no real
PyInstaller freeze, Tauri bundle, or `.app` launch was exercised — this container has no Tauri
build and no framework Python. So the end-to-end claim `SPEC-407` exists to make (a broken build
now fails loudly at the stage that knows) is proven for the daemon and the gate, and **unproven for
the bundle**. The maintainer's own in-flight macOS Tier 3 build is the real test of that, and it
has not been run against these changes.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — the container turned out to be a real test fixture, which changed the
    verification plan for the better.** The intent was to unit-test the degraded path with a mocked
    import failure. It turned out `daemon.py` starts genuinely degraded here, because the optional
    runtime dependencies are absent — nine real failed imports, from real `ModuleNotFoundError`s.
    So `TEST-003`/`TEST-004` were run against that instead of a mock, satisfying `CLAUDE.md`'s
    "verify against the real thing when it's available" norm at a fidelity that was not planned
    for. The before/after capture against the unmodified script is the actual evidence this slice
    works, and it would not have existed under the original plan.

*   **Deviation 2 — the failure count in the spec was seven, and one of them was mine to fix here
    rather than document.** `SPEC-407` §2.1 lists failure mode 6 as two defects in
    `verify_sidecar.py`. Reading it closely while implementing showed the second is worse than the
    spec states: it is not merely that a `FAIL` goes uncounted, it is that **the packaging gate can
    print a failure and exit 0**. A gate with that property has the same defect it exists to catch,
    which is why it was fixed in this first slice rather than deferred with the rest of §2.1.

*   **Deviation 3 — this context was written alongside the implementation, not before it.** The
    repo's loop is plan-then-build, and this inverted it: the findings came from a live debugging
    session with the maintainer earlier the same day, so the design was already settled and the
    code was written first. Recorded because the ordering is a real departure from
    `SPEC-901`'s sequence, not because the outcome was wrong.

*   **Deviation 4 — a factual claim in `SPEC-407` was wrong, and it was mine.** The spec, the
    ROADMAP entry and the new `CONTRIBUTING.md` text all stated that a bundled placeholder makes
    the app shut down about fifteen seconds after launch. Reading `DaemonHandle::shutdown` directly
    disproved it: it calls `supervisor::kill_child`, which is `child.kill()` plus `child.wait()` on
    the **daemon** process. The heartbeat monitor kills an already-dead child and breaks its loop;
    the app keeps running. What the user actually gets is a window that opens normally where every
    `dispatch_to_daemon` returns `Err` from writing to a closed pipe. Corrected in all four places.
    *   *Reasoning:* the claim was inferred from the monitor's own "treating as a hard crash" log
        line and never checked against what `shutdown` does. It was plausible, repeated
        confidently, and false.
    *   *Impact:* it does not change what this context builds — the fix is still to fail before
        that state is reachable — but it does change the symptom the spec tells a future reader to
        look for, which is the whole point of writing the failure modes down.

*   **Non-deviation, checked rather than assumed:** the fifteen import guards were instrumented by
    a scripted transformation over `daemon.py`, not by hand. All fifteen were confirmed matched and
    named individually, `daemon.py` was re-checked for stray `print()` calls afterwards
    (`stdout` is the JSON-RPC wire), and the real daemon was run to confirm the payload reports
    exactly the nine modules that actually failed — not a count derived from the log text.

*   **Open, unresolved and deliberately not guessed at:** `SPEC-407` §3 asks where the bundle-time
    check should live — a Tauri build hook, a release-gated `build.rs` addition, or a documented
    step — and whether CI should carry the same checks when it already does all three things
    correctly. Neither was decided here. Both belong to `CTX-407.2`, and deciding them needs a real
    Tauri build to test against.
