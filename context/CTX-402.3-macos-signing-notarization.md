# CTX-402.3: Implementation Context: macOS Code Signing & Notarization

> **Spec Reference:** Links to [SPEC-402](../specs/SPEC-402-release-signing-and-auto-update.md)

Real macOS code signing and notarization, replacing `CTX-402.1`'s deliberately unsigned pipeline --
possible now because a real GittieLabs, LLC Apple Developer *Organization* account exists (Team ID
`834C8Q72TG`), the exact prerequisite `SPEC-402`'s original text named as a real, separate, future
decision. Windows/Linux signing remain out of scope, per `SPEC-402`'s own revised Non-Goals.

## 1. Feature Definition & Execution Plan

### Phase 1: real credentials, handled carefully
*   [x] A real Developer ID Application certificate (`Developer ID Application: GittieLabs, LLC
    (834C8Q72TG)`) already existed in the local macOS Keychain -- confirmed via
    `security find-identity`, which surfaced two valid GittieLabs identities (one expiring 2029, a
    newer one expiring 2031). The newer one was used.
*   [x] A real App Store Connect API key was generated for notarization (Key ID `RF8GDXXA2C`,
    a real Issuer ID, and a `.p8` private key file) -- the modern, Apple-recommended notarization
    credential, in place of the older Apple-ID-plus-app-specific-password method.
*   [x] **The `.p8` file initially landed unprotected in the repo's working tree** (a
    `developer-key/` folder the user created, not yet gitignored) -- caught and fixed immediately:
    `developer-key/`, `*.p8`, and `*.p12` added to `.gitignore` before any other action, confirmed
    via `git check-ignore` that it was never staged or committed.
*   [x] The signing certificate was exported from Keychain **via the Keychain Access GUI**, not the
    CLI -- `security export -t identities` was tried first and found to bundle *every* identity in
    the login keychain (multiple unrelated personal certs, not just the two GittieLabs ones), which
    would have leaked unrelated personal key material into this repo's CI secrets. The GUI export
    lets a human select exactly one identity unambiguously; the CLI has no equivalent precise
    selector.
*   [x] The user's own GUI export had no password set; re-encrypted locally with a real, randomly
    generated password (via `openssl pkcs12 -legacy`, since `security export`'s own PKCS12 output
    uses crypto OpenSSL 3.x needs `-legacy` to read) before pushing anywhere.
*   [x] All five real credentials pushed directly to GitHub Actions secrets via `gh secret set`,
    piped from files/variables, never printed to any log or transcript:
    `APPLE_CERTIFICATE` (base64 p12), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_API_KEY` (the real `.p8`
    file *content*), `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`, `APPLE_TEAM_ID`. All local copies of
    the re-encrypted p12 and the plaintext intermediate PEM deleted immediately after pushing.

### Phase 2: confirming Tauri's real env-var contract, not assumed from docs
*   [x] A real, local `tauri build` was run with the real certificate and notarization credentials
    set via environment variables, to confirm the exact variable names/semantics Tauri's bundler
    actually expects -- `CTX-402.2`'s own Plan Drift already found this repo's assumptions about
    Tauri env vars wrong once (`TAURI_SIGNING_PRIVATE_KEY_PATH` doesn't work), so this wasn't
    assumed to be safe without checking directly.
*   [x] Confirmed for real: `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`,
    `APPLE_API_KEY` (the short Key ID string), `APPLE_API_KEY_PATH` (an actual file path -- the
    `.p8` content itself has no direct env var), and `APPLE_API_ISSUER` are all real, live-honored
    variables: the build imported the p12 into a real temporary keychain, located the identity by
    name, and invoked `codesign` with it.
*   [x] The real local test then failed with `ambiguous... matches "..." and "..."` -- because this
    specific dev machine's own login keychain *also* has both real GittieLabs identities installed
    for local use, so the freshly-imported one from the test p12 created a three-way name collision
    codesign couldn't resolve. This is a real, machine-specific condition that cannot occur on a
    clean GitHub Actions runner (which starts with zero GittieLabs certificates) -- named honestly
    as the boundary of what local testing could prove, not glossed over.

### Phase 3: `release.yml` wiring
*   [x] A new step writes the `APPLE_API_KEY` secret's real `.p8` content to an actual file at
    `$RUNNER_TEMP/AuthKey.p8`, since `APPLE_API_KEY_PATH` needs a real path, not inline content.
*   [x] The "Build the Tauri app bundle" step gains six new env vars sourced from the GitHub secrets
    above (`APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY` -- a literal
    string, not a secret, since the identity name isn't sensitive -- `APPLE_API_KEY`,
    `APPLE_API_KEY_PATH`, `APPLE_API_ISSUER`, `APPLE_TEAM_ID`), alongside the existing
    `TAURI_SIGNING_*` vars from `CTX-402.2` -- both sets coexist in the same step without conflict,
    since they're two genuinely separate trust mechanisms (Tauri's own updater-manifest signing vs.
    Apple's Developer ID code signing) that happen to both run during the same `tauri build`
    invocation.
*   [x] No `tauri.conf.json` changes were needed -- Tauri v2's signing/notarization is entirely
    environment-variable-driven; confirmed by the real local test succeeding up through the
    `codesign` invocation with zero config file changes.

### Phase 4: documentation
*   [x] `README.md`'s "Download a prebuilt build" section updated: the Gatekeeper bypass is now
    scoped explicitly to `v0.1.0` (the one real unsigned release), with new releases (`v0.1.1`
    onward) described as signed and notarized, launching normally.
*   [x] `SPEC-402` itself updated -- the "Not code signing or notarization" Non-Goal (macOS-scoped)
    removed, since it's no longer true; the Windows-signing Non-Goal kept, since that remains real
    and unaddressed.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `security export -t identities` bundles every identity in the keychain, not just
    the ones matching an intended filter -- a real, concrete finding, not assumed.** No CLI flag on
    `/usr/bin/security` precisely selects a single identity by hash or name for export. Fixed by
    asking the user to do a one-time, precise GUI export via Keychain Access instead of building a
    fragile CLI-based extraction script that risked either selecting the wrong identity or bundling
    unrelated personal key material into this repo's CI secrets.
*   **Deviation 2: a real, in-flight secret-handling mistake, caught and corrected mid-task.** While
    pushing the re-encrypted certificate's password to GitHub secrets, a broken shell command
    (written across two separate tool calls, losing the password variable to a fresh subshell in
    between -- "shell state does not persist between commands") nearly wrote the wrong content into
    `APPLE_CERTIFICATE_PASSWORD`. Caught before trusting it; redone correctly in a single shell
    invocation instead. Recorded honestly per `CLAUDE.md`'s Plan Drift norm, not hidden as if it
    never happened.
*   **Deviation 3: `APPLE_API_KEY` (Tauri's env var) and this repo's `APPLE_API_KEY` (GitHub secret
    name) refer to two different things, and the naming collision is a real, worth-flagging trap.**
    Tauri's own contract expects `APPLE_API_KEY` to be the short Key ID string; this repo's secret
    of the same name holds the real `.p8` file *content*. `release.yml` maps them correctly
    (`APPLE_API_KEY: ${{ secrets.APPLE_API_KEY_ID }}`, with the actual file content written to disk
    and referenced via `APPLE_API_KEY_PATH` instead) -- but a future edit that assumes same-name
    passthrough would silently break this. Named explicitly in both the workflow's own inline
    comment and here.
*   **Deviation 4: local verification could not reach a fully clean pass, for a real, understood,
    machine-specific reason -- not a flaw in the actual CI approach.** Named explicitly in the
    Testing Matrix's "Not verified" note above, matching this project's own "state what was not
    verified" norm rather than either overclaiming full local verification or silently skipping the
    attempt entirely. The partial result (identity import, keychain lookup, and `codesign`
    invocation all confirmed real) is still meaningfully more verification than trusting the
    mechanism from documentation alone.
