# CTX-901.2: User-Facing Product Gate: user_facing Field + Section 5

> **Spec Reference:** Amends [SPEC-901](../specs/SPEC-901-agent-operating-manual.md), and through it
> `SPEC-TEMPLATE.md`, `ROADMAP.md` §5.3, `CLAUDE.md`, `.claude/commands/new-spec.md`, `SPEC-902`, and
> `scripts/validate_spec_context.py`.

## 1. Feature Definition & Execution Plan

Twelve PRs of correct spec/context process (`SPEC-202` through `CTX-302.1`) still produced a UI
where three unrelated functions (`generate`/`inject`/plain-chat) share one text box, routed by
string-matching prose. Root cause: no section of `SPEC-TEMPLATE.md` ever asked what the user was
doing — every section is about mechanism. This context closes that gap across the whole framework:
the template, every existing spec, the roadmap norms, the agent-facing manual, the scaffolding
command, and the validator that gates every future PR.

### Phase 1: Template & framework docs
*   [x] `SPEC-TEMPLATE.md`: add required frontmatter field `user_facing: true | false`.
*   [x] `SPEC-TEMPLATE.md`: add `## 5. User & Interaction` (three bullets, required when
    `user_facing: true`); close a pre-existing unclosed code fence in §4 found while doing this
    (the new section rendered inside the old, never-closed fence otherwise).
*   [x] `ROADMAP.md` §5.3: append norms 8 and 9.
*   [x] `CLAUDE.md`: restate norms 8 and 9 for an agent that hasn't read `ROADMAP.md`, per
    `SPEC-901` §3's existing warning against copying `ROADMAP.md` prose verbatim.
*   [x] `.claude/commands/new-spec.md`: prompt for `user_facing`, scaffold `## 5.` when true.

### Phase 2: Backfill every existing SPEC-*.md
*   [x] Set `user_facing: false` on the 12 specs that don't add a user-facing surface
    (`SPEC-000/101/102/103/104/105/106/107/201/202/901/902/903`).
*   [x] Set `user_facing: true` + a TODO-marked `## 5.` stub on `SPEC-108`, `SPEC-301`, `SPEC-302` —
    honest about not inventing the answer after the fact.
*   [x] Flag the debt in the CTX files closest to each spec's shipped surface (`CTX-108.3`,
    `CTX-301.2`, `CTX-302.1`), not just in the spec itself.

### Phase 3: Validator + tests
*   [x] `SPEC-902`: document the two new hard failures and the changed-vs-repo-wide scoping
    resolution in §2/§3.
*   [x] `scripts/validate_spec_context.py`: add `user_facing` to `REQUIRED_SPEC_FRONTMATTER`
    (repo-wide); add `validate_user_facing_section()` and call it only for `spec_files_changed`
    (Rule 5).
*   [x] `scripts/tests/test_validate_spec_context.py`: update the `write_spec()` fixture helper and
    three raw-string fixtures to include `user_facing` (else every pre-existing fixture test breaks
    on the new required field); add `TestUserFacingFieldRequired` and `TestUserFacingSectionCheck`;
    add two real-CLI tests proving the changed-files-only scoping (a changed spec missing the
    section fails; an untouched one with the same gap doesn't).

### Phase 4: Framework docs describing what was actually built
*   [x] `SPEC-901` §3: correct the now-stale claim that the validator "never opens a `SPEC-*.md`"
    (`SPEC-902`/`CTX-902.1` already closed that before this context started); add the new
    known-issue this context itself introduces (structural checks can't verify a good answer, only
    that the question was asked).
*   [x] `SPEC-901` §4: fix the stale `SPEC-902 (not yet written)` reference and the stale
    `[Context 901.1] (not yet written)` diagram line, found while doing this context's required
    reading pass — pre-existing staleness, not something this context's own scope asked for, fixed
    as a low-risk drive-by correction rather than left for a future session to rediscover.

## 4. Plan Drift & Architectural Changes

*   **Non-deviation, confirmed as designed: the CLAUDE.md 150-line budget forced no real tradeoff.**
    The task anticipated this might not fit ("if it doesn't fit, say so rather than silently blowing
    it"). It did fit easily: `CLAUDE.md` went from 66 to 75 lines against a 150-line hard limit
    enforced by `scripts/tests/test_agent_docs.py::test_002_claude_md_within_line_budget`. Worth
    recording precisely because the task's own framing implied this was the likely friction point,
    and it wasn't — the file has roughly half its budget still free.

*   **Non-deviation, confirmed as designed: the changed-files-only vs. repo-wide conflict the task
    asked to be surfaced was real to check for, but resolves cleanly rather than requiring a
    compromise.** The concern: backfilling `SPEC-108`/`SPEC-301`/`SPEC-302` with `user_facing: true`
    in the same PR that adds the repo-wide field requirement makes those three files "changed," which
    would also trigger the changed-files-only section check — and the task explicitly forbids
    inventing real §5 content for them. Resolution: `validate_user_facing_section()` is a structural
    presence check (does the header exist), not a content-quality check — the same pattern
    `validate_testing_matrix()` already uses for its own section-header check. A TODO-marked stub
    satisfies "the header exists" without satisfying "the answer is good," which is exactly the
    honest state these three specs are actually in. No rule needed to be weakened.

*   **Deviation 1 (found during the required-reading pass, before Phase 1 started): `SPEC-901` §3's
    own claim that the validator "never opens a `SPEC-*.md`" was already false before this context
    began.**
    *   *Reasoning:* `SPEC-902`/`CTX-902.1` (`ROADMAP.md` §1.1, `Completed` 2026-08-08) already
        upgraded the validator into a full graph checker three days before this context's task was
        given. `SPEC-901` §3 and §4 were never updated to reflect that — §4 still said
        `SPEC-902 (not yet written)` and the module-map diagram still said
        `[Context 901.1] (not yet written)`, both of which had also become false once `CTX-901.1`
        and `CTX-902.1` landed.
    *   *Impact:* Fixed as part of this context's own required Phase 4 edit to `SPEC-901` §3/§4
        (the task already asked for a §3 update describing what this context built; correcting the
        adjacent stale claim in the same section, and the two related stale §4 lines, was in scope
        for "describe what you actually built" rather than a separate, unrequested cleanup). Not a
        deviation in what this context produced — a deviation in what `SPEC-901` claimed about the
        world before this context started touching it.

*   **Deviation 2: `SPEC-TEMPLATE.md` had a pre-existing unclosed code fence in §4, discovered only
    because this context needed to add content after it.**
    *   *Reasoning:* The template's `## 4. Module Map & Reference Links` section opened a
        ` ```text ` block and the file simply ended without a closing ` ``` `. Harmless as long as
        §4 was the last section — appending `## 5. User & Interaction` directly after it would have
        rendered the new section's real prose as part of the unclosed code block.
    *   *Impact:* Closed the fence as a one-line prerequisite fix before adding §5. `SPEC-TEMPLATE.md`
        is not glob-matched by `find_all_spec_files()` (it lives at the repo root, not inside a
        `specs/` directory), so this had no validator or test impact — pure Markdown-rendering
        correctness for humans reading the template.
