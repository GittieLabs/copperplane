# CTX-107.1: Structured Logging, Startup Handshake & Diagnostics

> **Spec Reference:** Links to [SPEC-107](../specs/SPEC-107-structured-logging-diagnostics.md)

## 1. Feature Definition & Execution Plan

### Phase 1: `stderr` logging + rotating log file (Python)
*   [x] `_configure_logging()` runs as the very first thing `daemon.py` does — before the
    `kicad_bridge`/`freecad_bridge` imports that could fail — configuring `logging.basicConfig` with
    a `stderr` handler plus a `RotatingFileHandler` under a per-OS log directory
    (`_default_log_dir()`, chosen without needing Rust to pass one in).

### Phase 2: Import failures no longer take down the whole daemon
*   [x] `kicad_bridge`/`freecad_bridge` imports wrapped in `try/except`, logged via
    `logger.exception(...)` rather than crashing before the read loop starts.
*   [x] `_build_routes()`: `kicad.get_version`/`freecad.generate_enclosure` are only registered if
    their bridge module actually imported — a broken `kipy` install no longer prevents the daemon
    from serving FreeCAD (or `job.cancel`/`daemon.configure`) requests.

### Phase 3: `daemon.ready` startup handshake
*   [x] `_detect_capabilities()`: cheap, non-blocking checks (KiCad IPC socket present? `freecadcmd`
    found?) — no live handshake, since `SPEC-103`/`104` already connect lazily.
*   [x] `main()` emits one `daemon.ready` notification, reporting detected capabilities, before
    entering the `stdin` read loop.

### Phase 4: `daemon.heartbeat` — closing `CTX-101.1`'s Deviation 1
*   [x] A background thread (independent of request handling, so an in-flight `freecadcmd` call
    can't starve it) emits `daemon.heartbeat` every 5 seconds.
*   [x] `core/tauri-rust`: on macOS only, a monitor thread tracks the last time a `daemon.ready`/
    `daemon.heartbeat` line was seen on `stdout`; if none arrives for 15s (3x the daemon's own
    interval), the daemon is treated as hard-crashed and the existing `DaemonHandle::shutdown()`
    cleanup path runs — the same cleanup `RunEvent::Exit` provides for a *graceful* quit, now also
    reachable for a hard crash on the one platform (`ROADMAP.md` §1.2) where it was missing.

### Phase 5: Testing
*   [x] Python: capability detection (real check — `freecad_available` is genuinely `True` on this
    machine — plus mocked false-branch coverage); `main()` emits `daemon.ready` before reading any
    input (a real, immediately-EOF `stdin`, not simulated); `_emit_heartbeat` writes the right
    notification shape; `_build_routes` omits a route whose bridge module didn't import.
*   [x] Rust: `is_heartbeat_signal` recognizes `daemon.ready`/`daemon.heartbeat` and rejects an
    ordinary response, a different notification, and malformed input.
*   [x] A **real**, manual end-to-end check: running the actual `daemon.py` as a subprocess (not
    through any test mock) with `stdin` held open showed a genuine `daemon.ready` line with accurate
    capabilities (`kicad_available: true`, `freecad_available: true` — both tools are actually
    installed on this machine) followed by a real `daemon.heartbeat` line at the 5-second mark, and a
    genuine `daemon.log` file was created and written to under `~/Library/Logs/hardware-agent-studio/`.

## 4. Plan Drift & Architectural Changes

*   **Deviation 0: the first CI run failed on all three OSes — `test_001` hardcoded
    `freecad_available: True`, true only on this dev machine, not on any CI runner.**
    *   *Reasoning:* The original `test_001_detect_capabilities_reports_freecad_available_for_real`
        called `assertTrue(caps["freecad_available"], ...)` unconditionally, reasoning it was a
        "real, non-mocked check" like `CTX-104.1`'s `TEST-004`. It missed the actual pattern
        `TEST-004` follows: that test calls `find_freecadcmd()` first and *skips itself* if FreeCAD
        isn't found, rather than asserting a fixed outcome. Mine asserted a fixed outcome. CI has no
        FreeCAD installed, so `freecad_available` was correctly `False` there — the test was wrong,
        not the code. Caught immediately: all three OS jobs failed fast (6-18s) with the exact
        assertion message, not a mysterious hang or timeout.
    *   *Impact:* Renamed and rewrote `test_001` to compute its own expected value from a real,
        live `find_freecadcmd()` call at test time (`True` if it succeeds, `False` if it raises
        `FreeCADUnavailableError`), then assert `_detect_capabilities()` agrees — honest and
        real on both this machine (FreeCAD installed) and CI (it isn't), rather than assuming
        either. Worth remembering as its own category, distinct from "mock when you should have
        used the real thing": a *real* check still needs to adapt to its actual environment, not
        just avoid mocking.

*   **Deviation 1: detecting `daemon.ready`/`daemon.heartbeat` requires Rust to parse JSON — a
    narrow, deliberate exception to this file's own "never parse the payload" principle.**
    *   *Reasoning:* `daemon.rs`'s header comment states the transport layer "never parses the
        JSON-RPC payload itself." Heartbeat-based crash detection is structurally impossible without
        *some* way to recognize these two specific notifications among every other line the daemon
        writes. `is_heartbeat_signal` does the smallest parse that could work — checking one field,
        `method` — rather than fully modeling the JSON-RPC schema in Rust. Every other aspect of
        `stdout` forwarding (the event emitted to the frontend) remains the raw, unparsed string.
    *   *Impact:* None on `SPEC-101`'s actual non-goal, which is about the frontend/daemon *request*
        contract (Rust doesn't need to understand a request to route it to `stdin`). This is a new,
        separate concern `SPEC-107` introduces on the `stdout` side, and the exception is scoped to
        exactly the two method names this mechanism needs.

*   **Deviation 2 (non-deviation, confirmed as designed): the heartbeat timeout is 3x the daemon's
    interval, not the roughly-2x the spec's design section estimated.**
    *   *Reasoning:* 15s (3x the daemon's 5s interval) leaves more real margin for scheduling jitter
        under load before concluding a live daemon crashed, at the cost of a slightly slower
        real-crash detection. Given this path only runs on macOS as a backstop (Windows/Linux already
        have working OS-level crash shields), a few extra seconds of detection latency is a better
        trade than a false-positive "crashed" signal killing a daemon that's just busy.
    *   *Impact:* None on the mechanism's correctness — a pure constant-value choice.

*   **Deviation 3 (non-deviation, confirmed as designed): the full "kill the daemon and watch Rust
    detect and clean it up" path was verified piece-by-piece, not end-to-end.**
    *   *Reasoning:* `is_heartbeat_signal` is unit-tested for real; the Python side's `daemon.ready`/
        `daemon.heartbeat` emission was verified for real by running the actual `daemon.py`
        subprocess and observing genuine output. But actually killing a running daemon out from under
        a live Tauri app and observing the macOS monitor thread fire `DaemonHandle::shutdown()`
        requires running the full GUI application, which this environment can't easily automate.
        Per `CLAUDE.md`'s "state what was not verified" norm: the individual pieces are proven real;
        their assembly into the full crash-recovery path has not been exercised end-to-end on a
        running app.
    *   *Impact:* None on what's claimed — this section exists so a future reader knows exactly
        where the verification boundary sits, rather than assuming "tests pass" means the whole
        macOS crash-shield gap is closed and proven under a real crash.
