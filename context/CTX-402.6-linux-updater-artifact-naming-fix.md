# CTX-402.6: Implementation Context: Linux Updater Artifact Naming Fix

> **Spec Reference:** Links to [SPEC-402](../specs/SPEC-402-release-signing-and-auto-update.md)

Found by actually cutting the real `v0.2.0` release -- the exact "verify against the real thing"
scenario this repo's own norms are built around. `release.yml`'s `publish` job has never once
succeeded: the same `Generate the real Tauri updater manifest` step failed identically on the
original `v0.1.3` tag push (2026-08-18, run `32085580353`) and again on `v0.2.0` (2026-08-26, run
`33020164900`) -- both times with the exact same `FileNotFoundError: ... ''` from
`generate_update_manifest.py`, meaning no GitHub Release has ever actually been published for this
app, consistent with the maintainer's own earlier confirmation that nobody has downloaded a build.

## 1. Feature Definition & Execution Plan

### Phase 1: diagnose against the real, failed CI run
*   [x] All four build legs (`build-macos` x2, `build-windows`, `build-linux`) succeeded on both the
    `v0.1.3` and `v0.2.0` runs -- only `publish` failed, both times, at the identical step.
*   [x] Read every leg's real build log directly (`gh run view --log`) rather than guessing: macOS
    (both arches) produces `.app.tar.gz` + `.app.tar.gz.sig`, exactly as `release.yml`'s glob expects
    -- unaffected. Windows produces **two** real updater signatures now (`.msi.sig` **and**
    `.exe.sig`) -- but the upload step's own glob (`msi/*.msi`, `nsis/*.exe`, `nsis/*.sig`) only ever
    picks up the `.exe`'s `.sig`, so this leg was already correct by accident, not by design update.
    Linux is the real bug: the current `@tauri-apps/cli` (`2.11.4`, resolved fresh by `npx` on every
    run -- never pinned) signs the raw `Copperplane_<version>_amd64.AppImage` directly
    (`.AppImage.sig`), with no `.tar.gz` wrapper at all -- `release.yml`'s upload-artifact glob still
    expected `.AppImage.tar.gz`/`.AppImage.tar.gz.sig` (`CTX-402.5`'s own assumption, correct for
    whatever Tauri version was current on 2026-08-17, since drifted). `if-no-files-found: error` on
    that step didn't catch it because the check is "did *any* pattern in the whole multi-line list
    match," not "did every pattern match" -- `*.deb`/`*.AppImage` still matched, so the step (and the
    whole `build-linux` job) reported success while silently never uploading a Linux `.sig` at all.
*   [x] `publish`'s own `LINUX_SIG=$(find ... -name '*.sig')` found nothing (the `.sig` was never in
    the downloaded artifact), producing the empty string that `generate_update_manifest.py` then
    tried to `open()`.

### Phase 2: the fix
*   [x] `release.yml`'s Linux leg's `Upload this leg's real build artifacts` step: dropped the two
    dead `*.AppImage.tar.gz`/`*.AppImage.tar.gz.sig` patterns, added the real `*.AppImage.sig`
    pattern (the raw `.AppImage` itself was already correctly listed).
*   [x] `publish`'s `Publish the GitHub Release` `files:` list: same substitution, so the real `.sig`
    actually gets attached to the GitHub Release as a downloadable asset (`generate_update_manifest.py`
    only builds `latest.json`'s reference to it; the actual file still has to be a real release
    asset for `tauri-plugin-updater` to fetch at update-check time).
*   [x] `LINUX_SIG=$(find artifacts/linux-x86_64-unknown-linux-gnu -name '*.sig')` needed no code
    change -- the broad glob already relies on exactly one `.sig` file existing in that directory,
    which is true again now that only the AppImage's (not the deb's) gets uploaded.
*   [x] Updated both nearby comments (the Linux build step's, and a new one on the manifest-generation
    step) to state the real, current behavior and record the version-drift finding, rather than
    silently fixing the glob and leaving a comment that would still tell the next reader something
    false.

### Not touched
*   `scripts/generate_update_manifest.py` itself needed no change -- it already generically opens
    whatever `--platform ... <sig-file>` path it's handed; the bug was entirely in which real file
    `release.yml` handed it for Linux.
*   macOS and Windows legs -- both already correct, confirmed by reading their real build logs
    directly, not assumed safe by similarity to Linux.

## 4. Plan Drift & Architectural Changes

*   **No pre-existing plan to drift from -- this context exists entirely because of what cutting the
    real `v0.2.0` release surfaced,** not because it was anticipated. Recorded here as the honest
    origin story rather than retrofitted into `SPEC-402`'s own original design: `SPEC-402`/`CTX-402.5`
    made a specific, verified-at-the-time claim about Tauri's Linux updater artifact shape that has
    since drifted, silently, because `@tauri-apps/cli@2` is never version-pinned in this pipeline
    (`npx` always resolves the latest `2.x` at build time) -- a real, structural risk this fix does
    not remove. Pinning the CLI version is a real, separate decision (trading "always current" for
    "always reproducible") this context does not make unilaterally.
*   **This is the first time `SPEC-402`'s own release pipeline has ever actually been proven to
    reach a real, published GitHub Release** -- both prior tag pushes (`v0.1.0`? not checked;
    `v0.1.3`, confirmed) failed at this exact step. `CTX-402.1` through `CTX-402.5`'s own Testing
    Requirements Matrices verified each *build leg* worked; none of them verified `publish` itself
    against a real, live tag-triggered run all the way through -- an honest gap in this repo's own
    prior verification, worth naming plainly rather than leaving implicit.
