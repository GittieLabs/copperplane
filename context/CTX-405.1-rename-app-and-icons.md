# CTX-405.1: Implementation Context: Rename App and Icons

> **Spec Reference:** Links to [SPEC-405](../specs/SPEC-405-product-rename-copperplane.md)

The mechanical rename: every presentation string across code, config, top-level docs and the docs
site changes to **Copperplane**, while the five identity strings `CTX-405.3` already guards stay
byte-for-byte frozen. Landed after `CTX-405.3` deliberately, so the guard tests were already green
and already able to fail loudly on the very first accidental touch of a frozen string.

**Three explicit scope decisions made before touching a single file, confirmed with the user rather
than assumed:**
1.  **New GitHub repo slug: `GittieLabs/copperplane`.** Baked into every URL now; they 404 until
    the actual GitHub rename happens.
2.  **The user renames the GitHub repository themselves**, once this PR is ready to merge -- this
    session does not perform that action.
3.  **The sidecar binary name (`hardware-agent-studio-daemon`) is left alone**, taking SPEC-405
    §3.3's own "defensible alternative" explicitly rather than defaulting into either choice.
    Confirmed unchanged in `.gitignore`, `core/tauri-rust/src/daemon.rs`, all three platform
    `tauri.*.conf.json` `externalBin` entries, `.github/workflows/release.yml`'s three `mv`
    commands, and `services/python-daemon/scripts/verify_sidecar.py`/`daemon.spec`.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `library_store.py`'s `ProjectNotLinkedError` message and `llm_providers.py`'s
    `managed_auth_invalid` message were judged "presentation," not left alone, despite reading almost
    like frozen identity strings at first glance.**
    *   *Reasoning:* both are real, user-facing sentences describing the *product*, informally --
        not the literal `_PROJECT_STATE_SUBDIR`/keychain-service constants themselves, which stay
        frozen and untouched a few lines away in the same files. Confirmed by checking downstream
        consumption: neither string is asserted against by any test, and both clearly name the
        product for a human reader rather than encode a technical identifier a stored file depends
        on.
    *   *Impact:* updated to "Copperplane," and `SPEC-320`'s own corresponding table entry updated
        in the same phase so the two can't drift apart from having been touched at different times.
*   **Deviation 2: three specs (`SPEC-000`, `SPEC-320`, `SPEC-404`) were updated even though SPEC-405
    §3.5 only explicitly discusses fourteen named `CTX-*.md` files.**
    *   *Reasoning:* SPEC-405 §3.5's principle is "completed historical records stay as they were
        written; living documents get updated" -- it just didn't enumerate every spec, since two of
        these three (`SPEC-404`, `SPEC-320`) didn't exist yet when `SPEC-405` was drafted. Applying
        the same principle by their own `status` field: `SPEC-000` is `Approved` (the living
        architecture record) and `SPEC-320`/`SPEC-404` are `Draft` (describing not-yet-built work) --
        neither is a dated, completed record the way the fourteen `CTX-*.md` files and
        `SPEC-110`/`SPEC-206` (`status: Completed`) are.
    *   *Impact:* consistent product naming across every currently-active document, at the cost of
        touching two specs (`SPEC-320`, `SPEC-404`) whose own features haven't shipped yet -- a
        judgment call, recorded here rather than silently made.
*   **Deviation 3: `docs/site/public/favicon.svg` was added -- not named anywhere in SPEC-405's own
    file inventory.**
    *   *Reasoning:* the docs site had no favicon configured at all before this phase (Starlight was
        silently serving its own generic default). SPEC-405 §5 frames the docs site the reader lands
        on "before they ever install anything" as squarely in scope for this rename.
    *   *Impact:* small, low-risk, and directly in the spirit of the spec even though not in its
        literal inventory -- verified via a real rebuild rather than assumed to just work.
*   **Deviation 4 (non-decision, confirmed rather than defaulted into): the sidecar binary name, the
    actual GitHub repository rename, and the new repo slug were all confirmed with the user directly
    before this phase began**, per SPEC-405 §3.3's own instruction that the sidecar-name call "should
    make that call explicitly rather than defaulting into it." See this file's own introduction for
    the three answers.
