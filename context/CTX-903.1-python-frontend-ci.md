## 1. Feature Definition & Execution Plan

### Phase 1: Skip-verification mechanism
*   [x] `scripts/ci/check_expected_skips.py`: runs `services/python-daemon/tests` and
    `scripts/tests` programmatically via `unittest.TestLoader().discover(...)`, and asserts the two
    known live-CAD tests (`test_002_real_kicad_version_round_trip`,
    `test_004_real_enclosure_round_trip`) actually land in `TestResult.skipped` — not just that the
    suite exited 0 — per SPEC-903 §2's "skip verification, not just exit-code trust."

### Phase 2: Python CI workflow
*   [x] `.github/workflows/python-ci.yml`: matrix over `ubuntu-latest`/`windows-latest`/
    `macos-latest`, `uv venv --python 3.12` + `uv pip install -r requirements.txt`, then run
    Phase 1's script via the venv's own Python **by explicit path**, not `source .venv/bin/activate`
    (see Plan Drift — this bit locally before it ever reached CI).

### Phase 3: Frontend CI workflow
*   [x] `.github/workflows/frontend-ci.yml`: single `ubuntu-latest` job, Node 22 (pinned, not the
    runner default), `npm ci` + `npx tsc -b` + `npm run lint` (`oxlint`) + `npx vitest run`.

### Phase 4: Fix what Phase 3 found before it could ship
*   [x] `apps/tauri-ui/package-lock.json` was out of sync with `package.json` — `npm ci` (what the
    workflow actually runs) failed immediately with `EUSAGE`, even though `npm install` (what every
    prior session in this repo used) had been silently patching around it the whole time. Fixed by
    regenerating the lockfile. See Plan Drift.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: dogfooding `/new-spec` via the `Skill` tool surfaced a real argument-mapping
    bug — but the fix isn't in the command files.**
    *   *Reasoning:* Invoking `/new-spec` with `args: "SPEC-903 Python & Frontend CI"` produced
        `$1 = "Python"`, not `"SPEC-903"` — confirmed reproducible with a second, unambiguous probe
        (`args: "AAA111 BBB222 CCC333"` → `$1 = "BBB222"`, the **second** word both times, not the
        first). This is a real, consistent off-by-one, discovered by actually trying the command
        rather than assuming the `$1` positional-substitution convention documented in `CLAUDE.md`
        and the command files works as designed.
    *   *Impact:* **Not fixed**, deliberately. This appears specific to invoking a command
        programmatically through the `Skill` tool's `args` field — a path an actual human typing
        `/new-spec SPEC-903 Python & Frontend CI` directly in chat may not hit at all, and the root
        cause (how this specific harness's `Skill` tool splits `args` into positional slots) is
        outside what a markdown instruction file can control or verify. Rewriting the command files
        around an invocation-path-specific quirk risked making them *wrong* for the primary,
        human-typed use case they were designed for. Proceeded manually instead — exactly per
        `CLAUDE.md`'s own guidance to state what was not verified. Worth a real test by Keith typing
        the command directly, next time one of these is used, to learn whether this is a `Skill`-tool
        artifact or a genuine bug in the command files themselves.

*   **Deviation 2: `npm ci` failed immediately on a lockfile that `npm install` had been quietly
    tolerating.**
    *   *Reasoning:* `apps/tauri-ui/package-lock.json` was missing `@testing-library/dom` and its
        transitive dependencies (`@babel/code-frame`, `aria-query`, `pretty-format`, and others) —
        present in `package.json` via `@testing-library/react`, added during `CTX-101.1`, but the
        lockfile was never regenerated to match. `npm install` (what every session so far in this
        repo has used) silently patches a lockfile back into a runnable state; `npm ci` (what
        `frontend-ci.yml` actually runs, and what CI should run, because it's the only npm command
        that guarantees the lock file is authoritative) refuses instead, with `EUSAGE`.
    *   *Impact:* This exists precisely because SPEC-903 has never run before — nothing in this repo
        had ever actually invoked `npm ci` until this context wrote a workflow that does. Fixed by
        running `npm install` once to resync the lockfile, then confirming `npm ci` succeeds
        cleanly. Committed alongside this context's other changes. This is the second time in this
        session that actually running a command turned up a real bug a plausible-looking assumption
        would have missed (the first being `freecadcmd -c <script>`'s stdin hang in `CTX-104.1`) —
        worth remembering as a pattern, not a coincidence.

*   **Deviation 3: `astral-sh/setup-uv@v3`, my first guess, doesn't exist as a currently-relevant
    tag — real latest is `v9.0.0`.**
    *   *Reasoning:* Checked via `gh api repos/astral-sh/setup-uv/releases` rather than trusting
        memory. `v3` may well have existed at some point, but shipping a stale, possibly-unsupported
        major version into new CI config is exactly the kind of thing worth one API call to avoid.
    *   *Impact:* Used the verified `v9.0.0` tag. No functional impact beyond avoiding a
        foreseeable, easily-avoided failure on the very first CI run.

*   **Deviation 4: `source .venv/bin/activate` does not persist across separate shell
    invocations — confirmed locally, not assumed for CI.**
    *   *Reasoning:* Activating the daemon's venv in one local shell command and then invoking
        `python3` in a *separate* command silently fell back to the system Python (missing `kipy`/
        `pynng`/`trimesh`), producing `errors=3` instead of a clean run. Each `run:` step in a
        GitHub Actions job is exactly this: a fresh shell, with no activation carried over from the
        previous step.
    *   *Impact:* `python-ci.yml` resolves the venv's own Python by explicit path
        (`services/python-daemon/.venv/bin/python` / `...\.venv\Scripts\python.exe`) in every step
        that needs it, rather than relying on activation. Confirmed correct by re-running with the
        explicit path locally and getting the expected result (real KiCad/FreeCAD present → the two
        live tests correctly do NOT skip, and the checker correctly flags that as a mismatch on this
        machine — see `TEST-001`).

*   **Deviation 5: the first real CI run failed exactly the way the note below predicted it might —
    a YAML syntax error invisible to local testing.**
    *   *Reasoning:* `run: "${{ env.VENV_PYTHON }}" scripts/ci/check_expected_skips.py` is invalid
        YAML: a double-quoted scalar (`"${{ env.VENV_PYTHON }}"`) followed by trailing unquoted
        text on the same line has no valid YAML grammar. GitHub couldn't parse the file at all —
        confirmed three independent ways: the workflow's displayed name fell back to the literal
        file path (`.github/workflows/python-ci.yml`) instead of `"Python Daemon CI"`; the matrix
        never expanded into three jobs (`gh api .../jobs` returned `{"total_count":0,"jobs":[]}`);
        and no check-run for it appeared on the PR at all — only `frontend-ci` and the gatekeeper
        showed up in `gh pr checks`. None of the local command-by-command testing in Deviations
        2-4 could have caught this, because none of it ever asked anything to actually parse the
        YAML file itself.
    *   *Impact:* Fixed by removing the inner quotes:
        `run: ${{ env.VENV_PYTHON }} scripts/ci/check_expected_skips.py`. Verified the fix parses
        with `python3 -c "import yaml; yaml.safe_load(open(...))"` before pushing, and confirmed no
        other `run:` step in either workflow has the same `run: "..."<trailing text>` pattern.
        Awaiting the re-run to confirm the fix actually works, not just that it parses — a workflow
        can be syntactically valid YAML and still be semantically wrong.

*   **Verified vs. not, stated plainly per `CLAUDE.md`'s own norm:** everything in Deviations 2-4
    was verified by running the exact same commands locally that the workflow YAML specifies — that
    catches command-level bugs but, as Deviation 5 shows directly rather than hypothetically, cannot
    catch a YAML syntax error, a wrong `working-directory`, or a GitHub-hosted-runner-specific
    difference. `TEST-004` stays ⏳ Pending until the fixed workflow actually runs green.
