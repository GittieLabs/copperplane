# CTX-402.4: Implementation Context: Intel (x86_64) macOS Build

> **Spec Reference:** Links to [SPEC-402](../specs/SPEC-402-release-signing-and-auto-update.md)

`CTX-402.1`-`.3` shipped a real, signed, notarized macOS release -- but only for whatever
architecture `macos-latest` happens to resolve to today (Apple Silicon). This adds a real second
build leg for Intel (`x86_64-apple-darwin`), so the GitHub Release offers both, clearly labeled.
KiCad/FreeCAD are not bundled by this app (confirmed by reading `kicad_cli.py`/`freecad_bridge.py`:
both PATH/glob-resolve a separately-installed KiCad/FreeCAD via subprocess), so their own
architecture support is not a blocker here -- this context is purely about this repo's own build
matrix.

## 1. Feature Definition & Execution Plan

### Phase 1: real design decisions, verified before committing to them
*   [x] Confirmed real: GitHub-hosted Intel macOS runners (`macos-latest-large`,
    `macos-26-intel`/`macos-15-large`/`macos-14-large`) are now gated behind GitHub's paid "Larger
    Runners" offering -- plain hosted macOS runners are Apple-Silicon-only today (checked
    `actions/runner-images`' own current README directly, not assumed from memory). Cross-compiling
    from the existing `macos-latest` (arm64) runner is the real, free alternative, not a fallback of
    convenience.
*   [x] Confirmed real: Rust cross-compilation to `x86_64-apple-darwin` needs no emulation --
    `rustup target add x86_64-apple-darwin` plus `cargo tauri build --target x86_64-apple-darwin`
    compiles natively on the arm64 host. Both targets were already installed on this dev machine
    (`rustup target list --installed` showed `aarch64-apple-darwin` and `x86_64-apple-darwin`
    already present), confirming this path needs no new toolchain work.
*   [x] Confirmed real: PyInstaller cannot cross-compile -- it must actually execute a real
    interpreter of the target architecture to introspect imports. On an arm64 host, freezing for
    x86_64 means running an x86_64 Python under Rosetta 2 (`arch -x86_64 <python>`). GitHub's arm64
    macOS runner images do not list Rosetta as pre-installed software (checked the real, current
    `macos-15-arm64-Readme.md` directly -- no mention), so `release.yml` needs an explicit
    `softwareupdate --install-rosetta --agree-to-license` step, not an assumption that it's already
    there.
*   [x] Confirmed real, by installing and testing directly on this dev machine (a real,
    already-installed python.org 3.11.6 universal2 framework build was present at
    `/Library/Frameworks/Python.framework/Versions/3.11`): `arch -x86_64 python3.11` and
    `arch -arm64 python3.11` both correctly select their respective slice from the same universal2
    interpreter, and `sysconfig.get_config_var('PYTHONFRAMEWORK')` returns `Python` under both --
    satisfying the same framework-build requirement `CTX-401.1` already established for the existing
    arm64 leg. This means **one** python.org universal2 3.11 install can serve both matrix legs
    (arch-selected via `arch -x86_64`/no prefix), rather than needing a second, separate
    Homebrew-under-Rosetta installation -- a real simplification found by testing, not assumed.
*   [x] Confirmed real, end to end, on this dev machine: created a throwaway x86_64 venv from that
    interpreter, installed `requirements.txt` + `requirements-build.txt` under `arch -x86_64`
    (all real wheels resolved for x86_64, including `pynng`'s native extension, which turned out to
    already ship as a universal2 `.so` -- no build-from-source risk), then ran the real, unmodified
    `daemon.spec` under `arch -x86_64 pyinstaller`. Real output: `EXE target arch: x86_64`, and
    `file` on the resulting binary confirmed `Mach-O 64-bit executable x86_64`. Launched it directly
    (`arch -x86_64 ./hardware-agent-studio-daemon`) and it started cleanly with no stray stdout
    output -- consistent with `CLAUDE.md`'s "stdout is sacred" JSON-RPC contract. `daemon.spec`
    itself needed zero changes -- its existing `target_arch=None` already means "match the invoking
    interpreter," which is exactly right for an `arch`-prefixed invocation.
*   [x] Confirmed real, by reading `tauri.macos.conf.json`'s `externalBin` entry: Tauri's own
    sidecar convention appends the **build target's** triple to the configured base name at build
    time, not the build **host's**. The current `release.yml` derives its rename suffix from
    `rustc -vV`'s `host:` field, which stays the build machine's own arch even when cross-compiling
    with `--target`. Left as-is, the x86_64 leg would freeze a real x86_64 binary but rename it with
    the wrong (`aarch64-apple-darwin`) suffix, and Tauri would silently look for the wrong sidecar
    file. Fixed by keying the rename off `${{ matrix.target }}` directly instead of `rustc -vV`.

### Phase 2: `release.yml` -- matrix build
*   [x] Converted the single `build-and-release-macos` job into `build-macos`, a real
    `strategy.matrix.target: [aarch64-apple-darwin, x86_64-apple-darwin]` build, each leg producing
    its own `.dmg` + `.app.tar.gz` + `.sig` as a real, named `actions/upload-artifact` artifact (not
    published directly -- publishing happens once, after both legs finish).
*   [x] `dtolnay/rust-toolchain@stable` gains `targets: ${{ matrix.target }}`.
*   [x] A new, explicit `softwareupdate --install-rosetta --agree-to-license` step, gated
    `if: matrix.target == 'x86_64-apple-darwin'`.
*   [x] Python interpreter step is now a real python.org universal2 3.11 pkg install (`curl` +
    `installer -pkg`), replacing the Homebrew-only step so both legs share one install path; the
    dependency-install and freeze steps are prefixed by an `ARCH_PREFIX` env var (`arch -x86_64` or
    `arch -arm64`, selected by `matrix.target`) -- the exact same prefix pattern verified locally in
    Phase 1, reused unchanged rather than approximated.
*   [x] The sidecar rename step uses `${{ matrix.target }}` directly, not `rustc -vV`'s host field.
*   [x] `cargo tauri build` gains `--target ${{ matrix.target }}`.
*   [x] A new `publish` job, `needs: build-macos`, downloads both matrix legs' artifacts (via
    `actions/download-artifact@v4` with `pattern: macos-*`), generates release notes once, calls the
    updated `generate_update_manifest.py` once with both platforms' real signature/URL data to
    produce a single `latest.json` covering both architectures, and publishes one real GitHub Release
    with all four macOS files (two `.dmg`, two `.app.tar.gz` + `.sig` pairs) plus `latest.json`.

### Phase 3: `scripts/generate_update_manifest.py` -- real multi-platform manifest
*   [x] Changed `--target-triple`/`--signature-file`/`--download-url` (three single-value flags) into
    a single repeatable `--platform TARGET_TRIPLE SIGNATURE_FILE DOWNLOAD_URL` flag (`nargs=3,
    action='append'`); `generate_manifest()`'s own signature changed from three scalar args to a
    `platforms: list[tuple]`, building the full `platforms` dict in one pass.
*   [x] Updated its own module docstring -- the old text explicitly said this repo "only ever builds
    for the CI runner's single native macOS architecture," which stops being true here.

### Phase 4: documentation -- users need to know which file to pick
*   [x] `README.md`'s "Download a prebuilt build (macOS)" section: lists both real download options
    plainly labeled "Apple Silicon (M-series Macs)" and "Intel Macs" -- not just the raw
    `aarch64`/`x86_64` filename suffixes Tauri's bundler already produces, which a non-technical user
    would not reliably map to their own hardware.
*   [x] `SPEC-402` itself: `§2 System Architecture & Design Choices` updated to describe the real
    two-leg matrix build instead of the single-arch text written when only one architecture existed.
*   [x] Version bumped `0.1.1` -> `0.1.2` in `Cargo.toml`/`tauri.conf.json` (and `Cargo.lock`
    regenerated), enabling the real `v0.1.2` tag this context's own CI-only remaining verification
    needs.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: GitHub-hosted Intel macOS runners are not freely available the way they once
    were -- a real, current-state finding, not an assumption carried over from when this repo's
    release pipeline was first designed.** `SPEC-402`'s own original text never named this because
    Intel was never in scope until now. Checked directly against `actions/runner-images`' current
    README rather than trusting general knowledge, which could easily be stale here given how often
    GitHub's runner offering changes. This is the real reason the design is "cross-compile on the
    arm64 runner," not "add a second `runs-on: macos-13` leg" as a naive first instinct might assume.
*   **Deviation 2: one shared python.org universal2 interpreter, not two separate per-arch Python
    installs.** The natural first design (mirroring the existing Homebrew-based arm64 step, plus a
    second Homebrew-under-Rosetta install for x86_64) turned out to be more moving parts than
    necessary -- testing directly on this dev machine showed a single already-installed universal2
    3.11 framework build satisfies both legs via `arch` selection alone. Simpler, and removes an
    entire second Homebrew-install failure surface from the matrix build.
