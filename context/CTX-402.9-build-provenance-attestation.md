# CTX-402.9: Implementation Context: Build Provenance Attestation

> **Spec Reference:** Links to [SPEC-402](../specs/SPEC-402-release-signing-and-auto-update.md)

`CTX-402.8` published `SHA256SUMS.txt` and was careful to say what it is not: a checksum hosted on
the same page as the file it describes proves integrity, never authenticity. This closes that gap
properly. The runner signs a statement -- this digest, built by this workflow, from this repo, at
this commit -- with a short-lived Sigstore certificate, and records it in a public transparency log.
`gh attestation verify` checks it against that log rather than against anything this project hosts,
so replacing the installer *and* the checksums on the releases page still cannot forge it.

This is deliberately not a claim to have solved Windows code signing. SmartScreen has no knowledge
of an attestation and will warn exactly as it did before. What changes is that a person who wants to
check a download now has a real cryptographic answer available to them.

## 1. Feature Definition & Execution Plan

### Phase 1: the workflow
*   [x] `actions/attest-build-provenance@v4` -- the current major, confirmed against the action's
    own releases (`v4.2.2`, 2026-08-06) rather than assumed, and pinned to the major to match this
    repo's existing convention for `actions/checkout@v7` and `softprops/action-gh-release@v3`.
*   [x] Runs **before** the publish step, on purpose. If attestation fails, no release is published
    at all -- which is better than a published release that the install page describes as attested
    and which is not.
*   [x] An explicit `permissions:` block on the `publish` job. This replaces the job's defaults
    outright, so `contents: write` has to be restated alongside `id-token: write` and
    `attestations: write` -- omitting it breaks the release upload itself, and only during a real
    tagged release, where it is most expensive to find.

### Phase 2: the docs
*   [x] `install.md`'s "Verify your download" now leads with the provenance check and presents the
    checksum second, as the weaker option for someone who does not want to install the GitHub CLI.
    The caution block is retitled from what a checksum does not prove to *why it is the weaker of
    the two*, since there is now a stronger one to point at.
*   [x] Says plainly that older releases predate this and will report no attestation found -- that
    is expected, not a failure, and a reader hitting it should not think their download is bad.
*   [x] `README.md` leads the Windows paragraph with the attestation command rather than the hash.
*   [x] `SPEC-402`'s Non-Goal, which `CTX-402.8` had left saying attestation was not done yet.

### Phase 3: guards
*   [x] The attestation step keeps its own list of subject globs, separate from the publish step's
    file list. Two hand-maintained lists of the same thing drift, and this one drifts silently: the
    release publishes fine and one platform's installer simply has no provenance. A test asserts
    the attested extensions equal the set of installers this project publishes.
*   [x] A test asserts attestation is ordered before publication, and that the job holds all three
    permissions.

## 4. Plan Drift & Architectural Changes

**1. Nothing here is proven end to end, and it cannot be until a tag is pushed.** Every check in the
matrix is a check of the *configuration*: the step exists, it is ordered correctly, its subject list
matches, the permissions are present, the YAML parses. Whether GitHub actually mints a certificate
and whether `gh attestation verify` accepts the result can only be known from a real release. The
argument shape of the verify command was confirmed against `gh attestation verify --help` on this
machine, so the command in the docs is at least real; that it will pass is not yet demonstrated.
This is the single largest caveat in this context and it is stated here rather than left implied.

**2. The failure mode was chosen deliberately, and it is the loud one.** Ordering attestation before
publication means a bad token, a permissions problem, or a Sigstore outage fails the release
outright rather than publishing without provenance. For a project whose install page will now tell
people to run `gh attestation verify`, a missing attestation is worse than a delayed release.

**3. The permissions block is the likeliest thing to bite.** An explicit `permissions:` on a job
does not merge with the workflow's defaults, it replaces them. The `publish` job had none before
and relied on the default `contents: write` to upload the release. `TEST-003` exists because
forgetting to restate it produces a failure that appears only during a real tagged release, after
every build leg has already spent its time.
