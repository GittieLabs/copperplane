# CTX-209.2: Delta-Only Config, Moving Defaults & Reset

> **Spec Reference:** Links to [SPEC-209](../services/python-daemon/specs/SPEC-209-provider-parameter-contract-and-model-defaults.md)

`SPEC-209`'s user-facing half, and the half that carries all its risk. `CTX-209.1` shipped the
transport; this makes shipped defaults movable and gives a user a way back.

**Planned, not implemented.** `SPEC-209` §3 names the migration as the risky part rather than the
feature, and it operates on a real install's only copy of its provider configuration. It should be
read before it is run.

## The defect this exists to fix

The app **cannot currently tell a shipped default from a user's choice.** Two properties combine:

*   `saveProviderConfig` persists all provider records as a whole — *"never a partial delta"*,
    `SPEC-208` §2.5's own contract.
*   `_resolve_provider_records` does `records[record_id] = entry`, replacing a preset outright
    rather than merging.

So the first time anyone opens Settings and saves, **all five presets freeze into their
`config.json` verbatim**, and no future release can move any default for them — including presets
they never touched. Verified against a real install on 2026-08-31.

## 1. Feature Definition & Execution Plan

### Phase 1: Merge field-by-field instead of replacing

*   [ ] `_resolve_provider_records` merges a `config.json` entry **over** the preset per field,
    rather than replacing the record. An absent field means "use the shipped value", which is what
    makes a default movable.
*   [ ] A record id with no preset (a user-added provider) keeps today's behaviour exactly — there
    is nothing to merge over, so the entry is the record.
*   [ ] `models` and `capabilities` are nested dicts and must merge **per key**, not wholesale.
    Replacing `models` wholesale would re-freeze the role a user did not touch, reintroducing the
    defect one level down.

### Phase 2: Write deltas, not whole records

*   [ ] `saveProviderConfig` sends only fields differing from the shipped preset.
*   [ ] **This amends `SPEC-208` §2.5's whole-record contract**, which `SPEC-209` §2.3 already
    records. The amendment lands with this context, annotated in place rather than silently
    contradicted — the precedent `CTX-406.2` set for `SPEC-406`'s superseded non-goal.
*   [ ] An empty delta means the record is omitted from `config.json` entirely rather than written
    as `{}`, so "identical to shipped" has exactly one representation.

### Phase 3: The migration — the risky part

*   [ ] Existing installs have all five presets written in. For each field, decide whether a value
    equal to the current preset was **chosen** or merely **persisted**.
*   [ ] **That information is genuinely gone.** There is no clever recovery, and pretending
    otherwise would be worse than picking. `SPEC-209` §3 requires the assumption be stated in this
    file rather than inferred from behaviour.
*   [ ] **Proposed assumption, for review before implementation:** a field equal to the current
    shipped preset is treated as *not chosen* and dropped to a delta; a field differing is kept.
    The failure mode is a user who deliberately typed today's default and later finds it moved with
    a release. Judged acceptable against the alternative — every install permanently frozen — but
    it is a real loss for a real person and should be an explicit decision, not mine alone.
*   [ ] The migration runs once, is idempotent, and **must not be destructive on failure**: write
    the new shape, keep the old file recoverable, and never leave an install with neither.

### Phase 4: Reset, at two levels, never touching secrets

*   [ ] Per-provider **Reset to defaults** — deletes that record's differing fields so the preset
    applies again. A deletion, never writing today's default in, which would re-pin it and defeat
    Phase 1.
*   [ ] A global revert restoring every default, which **must not remove any configured API key**.
    Keys are `SPEC-106`'s keychain concern, not config data; deleting one on a settings reset would
    be a destructive surprise.

### Phase 5: Documentation, and telling people when a default moves

*   [ ] A `docs/` table of recommended models and parameters per provider — the shipped defaults,
    plus one or two real Ollama models. `SPEC-209` §1's responsibility argument only holds if the
    user has somewhere to look; recommendations without documentation is just an undocumented
    default.
*   [ ] A release that moves a shipped default says so in its release notes (`SPEC-402`). A user
    who never touched a model gets the new value silently — that is the point of Phase 1 — but
    their install's observable behaviour changed without them acting, so it must be stated.

### Not in this context

*   **Surfacing `params` in the editor.** `CTX-209.1` shipped the transport with no UI; a record
    carries params only by hand-editing `config.json`. Which surface exposes them is a design
    question this context does not settle.
*   **Pinning the vendor SDKs.** Recorded in `CTX-209.1` §4 Deviation 2 as the root enabler of a
    bug that shipped in v0.3.0, and still its own decision.

**Verification this context commits to beyond the matrix.** `SPEC-209` is `user_facing: true` and
`CTX-209.1` shipped no user-facing surface, so this context inherits that obligation in full:

*   **The migration must be run against a copy of a real, already-frozen `config.json`** — the
    maintainer's own is the obvious candidate — and the result inspected by a human before this
    ships. A test fixture cannot tell you whether the assumption in Phase 3 feels right on a real
    install.
*   **Reset must be clicked in the real window**, both levels, with the API keys confirmed still
    present afterwards. This repo's history is unambiguous that a settings surface is not verified
    until someone has used it.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — planned rather than implemented alongside `CTX-209.1`, deliberately.**
    *   *Reasoning:* the transport half is additive and safe — nothing behaves differently until a
        record carries params. This half rewrites the storage contract and migrates the only copy
        of a real install's provider configuration, on an assumption that cannot be derived from
        the data. `SPEC-209` §3 names it as the risky part rather than the feature.
    *   *Impact:* the Phase 3 assumption is written down as a proposal for review rather than
        chosen and buried in a diff. A user who deliberately typed today's default will lose that
        choice on a future release, and that is a real cost to a real person — it should be a
        maintainer's decision, made knowingly.
