# CTX-902.4: Parentless Allowlist Gap & Spec-Graph Bookkeeping Repair

> **Spec Reference:** Links to [SPEC-902](../specs/SPEC-902-spec-graph-validator-v2.md)

Everything here was found by a single `/spec-status` run, not by a failure. The command is
read-only by contract, so its findings are fixed here instead.

## 1. Feature Definition & Execution Plan

### Phase 1: `KNOWN_PARENTLESS_SPEC_IDS` was missing SPEC-904

`scripts/validate_spec_context.py` exempts a fixed set of parentless framework specs from the
`ORPHAN ROOT SPEC` informational finding. The set held `SPEC-000`, `SPEC-901`, `SPEC-902` and
`SPEC-903` but not `SPEC-904`, which is the same class of 9xx framework spec and carries no
`parent_spec` by design. Every run of the validator therefore reported it as a possible mistake.

A standing informational finding that is always wrong is worse than no finding: it trains the
reader to skim the whole informational block, which is where the real "confirm this is
intentional" signals live. Fixed by adding `SPEC-904` to the set, and pinned by a test so the
omission cannot silently return.

### Phase 2: Seven shipped specs had no ROADMAP record

`SPEC-308`, `SPEC-309`, `SPEC-310`, `SPEC-311`, `SPEC-317`, `SPEC-319` and `SPEC-904` had neither
a §1.1 "Built and recorded" row nor a §3 backlog entry. Four of them appear in `ROADMAP.md` only
as cross-references inside *other* specs' entries, which is why a mention-count check misses them.
One entry each was written in the existing format, with dependencies read from each spec's own §4
Module Map rather than inferred from context filenames.

### Phase 3: Three stale statements

`SPEC-300` was still `Draft` with all fifteen of its `child_specs` `Completed`; flipped to
`Completed`, matching how `SPEC-201`/`SPEC-318`/`SPEC-402` mark umbrella parents whose children
have shipped. `ROADMAP.md` claimed `SPEC-406` was "Not yet contexted" while the same entry's own
header already linked `CTX-406.1` as done. `SPEC-205`'s entry header omitted `CTX-205.9`, which
exists and is `Completed`. §3.3's intro said "the four entries below" when sixteen follow it.

### Phase 4: Two round-trip `parent_spec` paths

`SPEC-308` and `SPEC-311` wrote `parent_spec` as a path out of and back into their own directory
where their thirteen siblings use the bare filename. Resolves identically either way; normalized
for consistency only.

## 4. Plan Drift & Architectural Changes

**Deviation 1 — the missing-entry count was wrong on first report, and the check was the reason.**
The initial `/spec-status` report named `SPEC-317` and `SPEC-319` as the only specs absent from
`ROADMAP.md`, on the basis that they had zero mentions in the file. `SPEC-308`–`SPEC-311` and
`SPEC-904` *are* mentioned, but only as cross-references inside other entries, with no record of
their own. Mention count was the wrong predicate; presence of a `####` heading or a §1.1 table row
was the right one. Seven, not two. Worth recording because the wrong check looked authoritative:
it produced a specific, confident, small number.

**Deviation 2 — local validation gave false confidence, because it ran against uncommitted work.**
The validator was run and reported green before committing, including the line
`Code files modified: False`. That is true of an uncommitted tree and false of the resulting
commit: the check is `git diff <base>...HEAD`, so it sees committed history only. The first CI run
then failed on `validate-specs-and-context` with `Code files modified: True` and the missing
context file, because `scripts/validate_spec_context.py` is a `.py` file under `scripts/`, which
is not in `EXCLUDE_DIR_NAMES`. The green local run had been reported as evidence the change would
pass CI. It was not evidence of that. **Validate after committing, not before** — or the check is
answering a different question than the one CI will ask.

**Deviation 3 — a reflow script corrupted `ROADMAP.md`, and the file was reverted rather than
repaired.** After the entries were inserted, a script re-wrapped the new prose to the file's
roughly 100-column convention. Its tokenizer treated `[label](target)` as atomic and was tripped by
the literal `ReviewFinding[]` in the `SPEC-319` entry, swallowing a 661-character span as a single
token; it also consumed the blank line before every heading it touched. `ROADMAP.md` was reset to
`HEAD` and every edit redone with hand-wrapped prose instead of patching the damaged output. Both
failure modes became explicit checks afterwards: no added line over 100 characters outside headings
and `*Module:*` lines, and a blank line before every `####`. Recorded because the corruption was
not visually obvious in a diff — the entries still read correctly at a glance.

**Non-deviation, decided and declined:** `docs/research/SPEC-203-supplier-api-exploration.md`
shares the `SPEC-203` number with the real, `Deprecated`
`services/python-daemon/specs/SPEC-203-supplier-api-integration.md`. Renaming it was considered and
rejected: `docs/site/src/content/docs/attribution.md` links to it by its GitHub `develop` URL, so a
rename breaks a published link for a cosmetic gain. The file already identifies itself as research
in its first two lines and sits outside every directory the validator scans.
