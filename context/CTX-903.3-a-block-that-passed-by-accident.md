# CTX-903.3: A Block That Only Passed Because Of The Block Above It

> **Spec Reference:** Links to [SPEC-903](../specs/SPEC-903-python-frontend-ci.md)

PR #445 bumps `vitest` 4.1.11 to 5.0.0 and is the only open PR with a failing check. Three tests in
`apps/tauri-ui/src/App.test.tsx`, all in `App: loading the project list`, die at
`Error: Test timed out in 20000ms`. 962 of 968 passed.

The interesting part is not vitest 5. It is that **those three tests have never been able to pass on
their own, on either version.** Run the block alone on the vitest the repo ships today and it fails
3 of 3 with `TypeError: Cannot read properties of undefined (reading 'then')`. The block is one of
three in that file with no `beforeEach` of its own, so it runs on whatever mock state its neighbour
happened to leave behind. It was green in CI for the same reason a stopped clock is right twice a
day.

This belongs to `SPEC-903` for the reason `CTX-903.2` did: it is a defect in what the suite is
capable of asserting, not in the product. `CTX-903.2` set one suite-wide async deadline because a
number had been raised twice; this one is the matching case where **the number was never the
problem at all**, and the fix raises nothing.

## 1. Feature Definition & Execution Plan

### Phase 1: Find the actual hang, not the deadline — DONE

*   [x] Read the failing attempt rather than a re-run, per `ci-flake-read-the-failing-attempt`. The
      log was past `gh run view --log` retention; `gh api .../actions/jobs/<id>/logs` still had it.
*   [x] Locate the single unbounded `await` in the path. `renderAppOpen` derives the project to open
      from `await listProjectsMock.mock.results[0]?.value`. All three tests deliberately make
      `listProjects` return a promise they never resolve until mid-test, so if index 0 is *their*
      pending promise, the helper waits forever and the test dies at `testTimeout` having rendered
      nothing.
*   [x] Establish that index 0 was only ever settled by accident: it was a leftover result from a
      test in an earlier block, because nothing between them clears it.
*   [x] Reproduce the hidden dependency on the currently shipping vitest, so the finding does not
      rest on the upgrade being at fault.

### Phase 2: Give the block its own ground — DONE

*   [x] A `beforeEach` for `App: loading the project list` that sets the mocks the initial render
      consumes, modelled on the block at line 864 it had been borrowing from.
*   [x] `listProjects` deliberately only `mockReset()` there, with a comment saying why: every test
      in the block sets it to a promise it controls, and a default would mask that.
*   [x] The three tests call `render` directly instead of `renderAppOpen`. The helper's contract is
      "open the first project once the list has loaded", which is meaningless in a test whose
      subject is the list not having loaded. There is nothing to open.
*   [x] `renderAppOpen` now documents the precondition that made it a trap, so the next caller who
      holds a promise open is told rather than left to find a 20-second hang.
*   [x] **Nothing raises a deadline.** `testTimeout` stays at 20000 and `asyncUtilTimeout` at 5000.

## 4. Plan Drift & Architectural Changes

**1. I assumed vitest 5 cleared all mock state between tests. It does not, and the evidence was
already in the failure.** If implementations were cleared, the file's two other `beforeEach`-less
blocks would have failed too — they depend just as much on inherited `mockResolvedValue` setups.
Under vitest 5 they passed; only the three tests that read `mock.results` broke. So whatever
changed is scoped to recorded results, not to implementations.

I have **not** verified which vitest 5 change does this, and the fix does not depend on knowing:
it removes the read of `mock.results` from the hang path entirely, and that read was the only
unbounded `await` between `render` and the assertion. Naming the upstream mechanism would need
vitest 5 actually installed, which was deliberately out of scope.

**2. Two more blocks have the same defect and are deliberately left alone.** `App: the project
header` fails 8 of 8 run alone, and `App: creating a project owns the main area` 4 of 4. Both
survived vitest 5, so neither is what #445 is failing on, and widening a CI fix into a
twelve-test refactor is how a green PR turns into a red one. They are latent, they are recorded
here, and they will surface on some future upgrade exactly the way this one did.

**3. What was not verified.** Everything above ran on vitest 4.1.10, resolved from the lockfile on
one Apple Silicon Mac. The fix has never been executed against vitest 5.0.0, so the claim is
"removes the dependency that can produce the hang", not "observed green on vitest 5". #445 is the
test of that, and it is a rebase away from giving a real answer. The three platforms the frontend
job does not run on are unaffected here, since this is a jsdom test with no OS-specific path.
