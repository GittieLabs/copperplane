# CTX-110.2: Implementation Context: A Storage Change Says Which Projects Disappear

> **Spec Reference:** Links to [SPEC-110](../specs/SPEC-110-configurable-storage-root.md)

## 0. What the maintainer hit, and why the current warning did not prevent it

He lost sight of two projects and asked the right question: *"how are projects found by the app bc
there was another project not found when the app was loaded?"*

The answer is that there is no project registry at all:

```python
def list_projects() -> list:
    projects_root = _ensure_dir("projects")          # <storage_root>/projects
    return sorted(entry for entry in os.listdir(projects_root)
                  if os.path.isfile(os.path.join(projects_root, entry, "project.json")))
```

A project exists if and only if a folder holding `project.json` sits inside
`<storage_root>/projects/`. Nothing records a path, so nothing can point outside that one root.
**Changing the storage root therefore replaces the entire project list in one action** — the old
projects are not deleted, they are simply no longer where the app looks. In his case
`~/Desktop/projects/` held `Hello Blinky` and `test 1`, and the root reverted to the app default.

The existing confirmation already says something true:

> *"New files will be saved to the new location once you restart. Anything already saved stays at
> the old location and will not move automatically. Restart now to apply this safely?"*

Accurate, and it never mentions the consequence a person actually cares about: **the projects you
can see are about to change.** "Anything already saved stays at the old location" is a statement
about files; the user's model is a list of projects.

His second observation is the same gap from the other side: *"I see that the settings handle
setting a storage location and doesn't specify a default project location."* There is no separate
project location to specify — the storage root *is* it, and the Settings copy never says so.

## 1. Feature Definition & Execution Plan

### Phase 1: Say what will disappear, by name — done
*   [x] Count the projects under the current root before the change, and name them in the
        confirmation — "3 projects (Hello Blinky, test 1, Test) are stored here and will no longer
        appear until you point Copperplane back at this folder."
*   [x] Count what is at the *new* location too, since it may be a root that already holds
        projects, in which case the list changes rather than empties.
*   [x] Say plainly that nothing is deleted and the change is reversible by pointing back.

### Phase 2: Say what the setting is, before it is changed — done
*   [x] Settings names the storage location as where projects and the library live, not as a
        generic file location. Answering his question in the UI rather than only in a modal he
        sees after deciding.

### Phase 3: Make the answer discoverable after the fact — done
*   [x] Decide whether the no-project landing view should say where it is looking. A user staring
        at an empty list has no way to learn that the list is a function of one setting.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1, before implementation: the warning that exists is honest and still failed.**
    It is tempting to record this as "the warning was wrong". It was not — every clause is true.
    It describes files, and the user's mental model is a list of projects, and nothing bridged the
    two. Worth stating because the fix is not "warn harder": it is to name the specific projects
    that will vanish, which is the only version of this sentence that could have stopped him.

*   **Prediction, checked: right, and it had a second half I had not seen.** Counting at an
    unconfigured root did need a pure function over a path — `list_projects_at(root)`. The part I
    had not predicted is that `list_projects` goes through `_ensure_dir`, which **creates** the
    directory. Reusing it would have made a `projects/` folder inside whatever the user was merely
    considering: a side effect of asking a question. `list_projects_at` creates nothing, and
    `list_projects` now delegates to it so a later change to what counts as a listed project —
    `SPEC-333`'s removal flag — applies to both.

*   **Deviation 2: the fallback keeps the old wording deliberately.** If either root cannot be
    read, the modal shows the original sentence rather than a version naming projects. A confident
    claim about projects we could not actually look at would be worse than the honest sentence
    that failed.

    fills rather than empties, which is the branch a warning written only for the loss case would
    have got wrong.
