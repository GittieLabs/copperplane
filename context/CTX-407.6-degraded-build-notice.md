# CTX-407.6: Implementation Context: The App Says Its Own Build Is At Fault

> **Spec Reference:** Links to [SPEC-407](../specs/SPEC-407-sidecar-build-integrity.md)

## 0. The half the build gate cannot reach

`SPEC-407` has five contexts and, until this one, no implementation of its own §5. Found by
auditing spec statuses rather than by anything failing:

> the daemon reports degraded modules in `daemon.ready`, in `daemon.get_capabilities` and now in
> `daemon.list_routes`, and `ensure_sidecar` fails a build on them — but **nothing in
> `apps/tauri-ui` reads any of it**.

Every check `SPEC-407` had was a *build-time* check. They protect the person doing the build. They
do nothing for a person running an app that was already built badly — and that is the case §1
describes as worse than a crash:

> a crash sends you to the packaging; a healthy-looking daemon with no `chat.send`, no
> `agent.dispatch_tool` ... sends you hunting for a UI bug that does not exist.

`CTX-407.5` made that failure impossible to *create* on a machine that builds. It did nothing for
one already installed, and I did not notice the asymmetry while building it.

## 1. Feature Definition & Execution Plan

### Phase 1: Say what was lost, in the user's terms
*   [x] `lib/degradedModules.ts` maps each of the 18 modules `daemon.py` can report to what the
        user cannot do — *"The project chat and the AI reviews"*, not *"chat_agents"*.
*   [x] A module with no entry is **named as itself** rather than glossed. Both this app and KiCad
        gain modules, and inventing a description for an unrecognised one would be a confident
        guess exactly where a user is already confused.

### Phase 2: The notice
*   [x] States plainly that the build is at fault and the app is working correctly — the point of
        §5 is that a user must not file a bug against a UI that is fine.
*   [x] Points at the daemon log, where the reason actually is.
*   [x] **No retry button.** §5, verbatim: *"nothing the user can do at runtime will fix a bad
        build."*
*   [x] **Dismissible** — the opposite of `RequirementsBanner`, deliberately. That one describes
        something the user can fix, so it never goes away. This describes something they cannot,
        and an unfixable notice kept on screen forever is nagging without a remedy.
*   [x] Rendered above everything, including the onboarding surfaces: a broken build is not a
        configuration problem a wizard can fix, and it explains failures the wizard would otherwise
        present as its own.

### Phase 3: Keep the two lists together
*   [x] A test asserting every module `daemon.py` can degrade has a plain-language entry, and that
        the map describes no module the daemon never reports.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: this context exists because a status audit found it, not because anything
    failed.** `SPEC-407` sat `In-Progress` with five Completed contexts and every phase box ticked.
    Nothing was broken; a whole section of the spec had simply never been claimed by any context,
    and the spec's own status was the only thing still saying so. That is an argument for walking
    the graph rather than trusting a summary of it — including this session's own summaries, which
    had twice described `SPEC-407` as delivered.

*   **Deviation 2: the parity test failed on three modules that were perfectly well described.**
    My regex matched `module: '...'` and three entries use double quotes, because their text
    contains an apostrophe — `"Searching KiCad's installed footprints"`. The check reported them
    missing. Caught by reading the failure rather than trusting it, which is the whole reason a new
    check's first red run deserves suspicion: **a guard that is wrong about its subject is worse
    than no guard, because its silence later will be believed.**

*   **Deviation 3: dismissible here, never dismissible in `RequirementsBanner`, on purpose.**
    `SPEC-336` §3 calls a dismissible banner "the trap in a different costume" — correct, for
    something the user can fix. `SPEC-407` §5 asks for the opposite, and is also correct, because
    nothing the user does at runtime fixes a bad build. Two banners, opposite rules, each right for
    its own subject. Recorded so the next person does not "fix" the inconsistency.

## 5. Verification Notes

*   806 UI tests across 45 files, lint clean. Daemon suite: 1082 tests, one failure — the
    live-Anthropic datasheet-guidance test whose 60s deadline covers 15+ real API calls, which
    predates this work and passes alone.
*   The map is checked against `daemon.py`'s own `_note_degraded` calls in both directions, so a
    new degradable module fails the suite rather than reaching a user as a bare module name.
*   **Not verified:** not seen in the built app, and **deliberately hard to see** — it requires a
    genuinely broken sidecar, which every other check in `SPEC-407` now exists to prevent. The
    honest way to exercise it is to hand `daemon.py` a deliberately unimportable optional module
    and launch. Nobody has.
