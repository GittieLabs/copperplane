# CTX-105.1: Daemon Async Job Protocol & Worker

> **Spec Reference:** Links to [SPEC-105](../specs/SPEC-105-daemon-async-job-progress-protocol.md)

**Scope note:** this is the daemon-side slice SPEC-105 names as `CTX-105.1` — the job protocol,
worker execution, notifications, cancellation, and parameter validation inside `daemon.py`. The
frontend's job/progress client that replaces CTX-101.1's single-in-flight guard is `CTX-105.2`,
deliberately out of scope here.

## 1. Feature Definition & Execution Plan

### Phase 1: Atomic `stdout` emission
*   [x] Add a module-level lock and an `emit(obj)` helper in `daemon.py` that serializes every
    `stdout` write (JSON-encode, write, newline, flush) under that lock. Route both `main()`'s
    existing response writes and every new notification through it — this is the one invariant
    every later phase depends on (SPEC-105 §3).

### Phase 2: Async job dispatch
*   [x] `ASYNC_ROUTES`: a set naming which `ROUTES` keys run asynchronously.
*   [x] `submit_job(method, params)`: generates a `job_id`, records it in an in-memory job
    registry, starts a daemon worker thread running the route function, and returns
    `{"job_id": ...}` as the *request's* result immediately — the read loop is never blocked
    waiting on the route's actual work.
*   [x] `handle_request` checks `ASYNC_ROUTES` before dispatch and calls `submit_job` instead of
    invoking the route function inline for those methods.

### Phase 3: Progress / completion / failure notifications
*   [x] `job.progress`, `job.completed`, `job.failed` JSON-RPC notifications (no `id`, per the
    JSON-RPC 2.0 spec), each carrying `job_id` in `params`, emitted via Phase 1's `emit()`.

### Phase 4: Real cancellation
*   [x] `job.cancel` route: sets a per-job `threading.Event`.
*   [x] Thread that `Event` through to `freecad_bridge.generate_enclosure` (the one route this
    slice wires as async — see Phase 6) so a cancelled job actually terminates the underlying
    `freecadcmd` subprocess, not just stops being reported on (SPEC-105 §3's cancellation gotcha).
    Requires converting `generate_enclosure`'s subprocess wait from `subprocess.run(timeout=...)`
    to a poll loop so it has a point to check the event and `kill()` early.
*   [x] `job.cancelled` notification (distinct from `job.failed`) when a worker observes its own
    cancellation.

### Phase 5: Per-route parameter validation
*   [x] Before dispatch, validate `params` against each route function's real signature
    (`inspect.signature`) — a missing required parameter or an unexpected keyword now returns
    `-32602 Invalid params` instead of the opaque `-32000` a bare `TypeError` produces today.

### Phase 6: Wire the proof case, and test all of the above for real
*   [x] Flag `freecad.generate_enclosure` as this slice's one async-dispatched route — the
    multi-second cold-boot case `ROADMAP.md` §3.1 names.
*   [x] Mocked unit tests: job submission returns immediately with a `job_id` (route never
    actually runs on the calling thread); notification shapes; invalid params → `-32602`.
*   [x] A concurrency stress test proving Phase 1's atomicity: many threads emitting through
    `emit()` at once, assert every captured `stdout` line parses as one complete, uncorrupted
    JSON object.
*   [x] A **real** integration test: submit a real `freecad.generate_enclosure` job, cancel it,
    and assert the actual `freecadcmd` process is gone — not just that a notification fired. Skips
    itself cleanly when no `freecadcmd` is found, same pattern as `CTX-104.1`'s `TEST-004`.

## 4. Plan Drift & Architectural Changes
*Document any deviations from SPEC-105 encountered during build.*

*   **Deviation 1: real cancellation required rewriting `CTX-104.1`'s already-`Completed`
    `generate_enclosure`, including two of its existing mocked tests.**
    *   *Reasoning:* `subprocess.run(timeout=...)` blocks uninterruptibly until the process exits
        or the timeout fires — there is no way to reach in and kill it early once it's called. SPEC-105
        §3's cancellation gotcha explicitly demands real cancellation, not a flag that only stops
        *reporting*. That forced converting the subprocess wait from `subprocess.run` to a
        `Popen` + short-interval `communicate(timeout=...)` poll loop (`_wait_with_cancellation`),
        which can check a `cancel_event` between polls and `kill()` the process immediately.
    *   *Impact:* `test_freecad_bridge.py`'s `TEST-002` and `TEST-003` (both from `CTX-104.1`,
        already merged and `Completed`) had their mocks changed from `subprocess.run` to
        `subprocess.Popen` to match — their asserted *behavior* (non-zero exit → `FreeCADBuildError`;
        timeout → `FreeCADBuildError`) is unchanged, only the mocked call site moved. `TEST-004`
        (the real integration test) needed no changes at all; re-ran clean against the actually-installed
        FreeCAD 1.1.1. Worth remembering: a "Completed" context's tests aren't necessarily frozen —
        a later spec can legitimately need to change how an earlier one's implementation is verified,
        as long as the earlier behavior itself doesn't silently regress.

*   **Deviation 2: cancellation is judged by `cancel_event.is_set()`, not by catching a specific
    exception type — a deliberate decoupling `SPEC-105` didn't explicitly call for.**
    *   *Reasoning:* The alternative was having `daemon.py` import and catch each bridge module's
        own cancellation exception (`freecad_bridge.FreeCADCancelledError`, and whatever a future
        AgentFlow-backed route would raise). That would make `daemon.py`'s generic job-worker code
        grow a dependency on every bridge module's exception vocabulary. Instead, `_run_job`'s
        `except Exception` branch just checks whether the job's own `cancel_event` is set: if so,
        *any* exception the route raised while cancelling is treated as `job.cancelled`; otherwise
        it's `job.failed`. This keeps the worker generic across whatever async routes get added later
        (SPEC-201+), at the cost of one edge case: a route that happens to raise for an unrelated
        reason in the same instant a cancel was requested would be misreported as cancelled rather
        than failed. Judged an acceptable trade — narrow window, and "cancelled" is the more honest
        label for the user's intent in that instant anyway.
    *   *Impact:* None on the tested behavior; documenting the choice since it's not spelled out in
        `SPEC-105` itself and a future context extending this worker should know the rule.

*   **Deviation 3 (non-deviation, confirmed as designed): `JOBS`, the in-memory job registry, has no
    explicit lock guarding it.**
    *   *Reasoning:* Every access is a single `dict.get`/`dict[key] = ...`/`dict.pop` — each
        individually atomic under the GIL for CPython's built-in dict. Adding a second lock
        alongside `_stdout_lock` for operations that are already atomic would be unjustified
        complexity for what this slice actually needs.
    *   *Impact:* None — flagged here so a future context adding real cross-job coordination (e.g.
        job priority, a max-concurrent-jobs cap) knows this assumption exists and re-checks it if the
        access pattern gets more complex than single-key get/set/pop.

*   **Deviation 4 (non-deviation, confirmed as designed): the real cancellation test
    (`test_async_jobs.py`, `TEST-005`) has a small, inherent race, and is not made artificially
    deterministic.**
    *   *Reasoning:* `cancel_event.set()` is called immediately after `submit_job` returns, but
        nothing guarantees it lands before the real `freecadcmd` subprocess finishes on its own —
        an unusually fast machine could complete the box-generation before the cancel is even sent.
        Slowing the underlying build script down artificially to make the race un-losable would test
        a synthetic scenario instead of the real one. Ran clean (well under the 10s deadline,
        alongside `test_freecad_bridge.py`'s own real round-trip test in the same suite run) on this
        machine — per `CLAUDE.md`'s norm, stating plainly that this has not been verified on a
        machine fast enough to lose the race, rather than claiming the test eliminates that
        possibility.
    *   *Impact:* None on this slice's correctness. `test_freecad_bridge.py`'s `TEST-005`
        (mocked, deterministic) is what actually proves `cancel_event` → `proc.kill()` under full
        control; this real test proves the end-to-end wiring through the daemon on top of that.
