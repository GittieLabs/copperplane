# CTX-106.1: Configuration & Secrets Store

> **Spec Reference:** Links to [SPEC-106](../specs/SPEC-106-configuration-secrets-store.md)

**Scope note:** implements the full mechanism `SPEC-106` §2 decided (Rust owns config + secrets,
injects at spawn) and wires it into the two real consumers that already exist and need it:
`freecad_bridge.find_freecadcmd()`'s path override, and `kicad_bridge`'s connection settings
(`kipy.KiCad.__init__` really does accept `socket_path`/`timeout_ms` — confirmed by inspecting its
signature before writing this, not assumed). The LLM-provider/API-key fields `SPEC-106` names are
stored and injected by this same mechanism, but have no real consumer yet — `SPEC-201` is the first
context that will actually read them.

## 1. Feature Definition & Execution Plan

### Phase 1: Non-secret config file (Rust)
*   [x] `core/tauri-rust/src/config.rs`: a `DaemonConfig` struct (`freecadcmd_path_override`,
    `kicad_socket_path`, `kicad_timeout_ms`, `llm_provider`, `llm_model`, all `Option<...>`), loaded
    from `app.path().app_config_dir()?/config.json` via `tauri::Manager`, defaulting to all-`None`
    if the file doesn't exist yet (first run).

### Phase 2: OS keychain secrets (Rust)
*   [x] `core/tauri-rust/src/secrets.rs`: `get_secret(key)` / `set_secret(key, value)` via the
    `keyring` crate (real, checked version — see Plan Drift for how it was verified). Distinguishes
    "no secret stored for this key yet" (a normal first-run state, returns `None`) from a genuine
    keychain-access failure (a real `Err`, per `SPEC-106` §3's gotcha).

### Phase 3: Injection at spawn (Rust)
*   [x] `daemon.rs`'s `spawn_daemon` gains two pure, unit-testable helpers: `build_daemon_env`
    (non-secret `DaemonConfig` → env var(s) for the `Command`) and `build_configure_request`
    (a secrets map → the `daemon.configure` JSON-RPC request line). `spawn_daemon` itself calls
    both, sets the env var(s) on the `Command` before spawning, and writes the configure line via
    the existing `write_request` helper as the very first line on the child's `stdin` — before
    `spawn_daemon` returns the `DaemonHandle` a frontend request could ever reach.

### Phase 4: Daemon-side application (Python)
*   [x] `daemon.py`: reads the env-injected non-secret config once at import time, applies it via
    `freecad_bridge.configure(...)` / `kicad_bridge.configure(...)` before `main()`'s loop starts.
*   [x] `daemon.configure` route: merges the handshake's `secrets` into an in-memory `CONFIG` dict.
    No special-casing needed in `main()`'s read loop — it's an ordinary route dispatched through the
    existing `ROUTES` registry; Phase 3's ordering guarantee is what makes it arrive first, not any
    daemon-side logic.

### Phase 5: Wire the two real consumers
*   [x] `freecad_bridge.configure(path_override=None)`: `find_freecadcmd()` checks the override
    first (real file-existence check; a configured-but-missing path is a clean, specific error, not
    a silent fallback to the PATH search).
*   [x] `kicad_bridge.configure(socket_path=None, timeout_ms=None)`: resets the held-open `_client`
    so the *next* `get_client()` call reconnects using the new settings via `KiCad(socket_path=...,
    timeout_ms=...)`.

### Phase 6: Testing
*   [x] Rust: `build_daemon_env` and `build_configure_request` unit tests (pure functions, no real
    child process needed); a **real** round-trip test against the actual OS keychain on this machine
    (`set_secret` then `get_secret`, then clean up) — skips itself (prints and returns, matching the
    stable-Rust idiom for this) if no keychain service is reachable.
*   [x] Python: `daemon.configure` merges into `CONFIG`; `freecad_bridge.configure`'s override path
    is honored (real filesystem check) and a missing override path raises cleanly; `kicad_bridge.configure`
    resets the client and the next connection attempt is constructed with the new `socket_path`/`timeout_ms`
    (mocked at the `KiCad` constructor — a live socket on a *custom* path isn't available to test for
    real on this machine, only the default path CTX-103.1 already verified).

## 4. Plan Drift & Architectural Changes
*Document any deviations from SPEC-106 encountered during build.*

*   **Deviation 1: the `keyring` crate's real API turned out to be a completely different shape
    than a version-agnostic guess would have assumed — checked before writing any code, not after.**
    *   *Reasoning:* An initial guess reached for feature flags (`apple-native`, `windows-native`,
        `sync-secret-service`) that matched the crate's old (`v3`-era) design. Checking the real
        `4.1.6` feature list via `crates.io`'s API first showed it's been restructured into a
        meta-crate over `keyring-core` + separate backend crates, with a `v1` feature (the default)
        that already bundles all three platform backends under a `keyring::Entry` API compatible in
        shape with the old one. The guessed feature names don't exist in `4.1.6` at all — they would
        have failed to compile, not silently misbehaved, but confirming first avoided a wasted
        edit-compile-fail loop. (This mirrors the `astral-sh/setup-uv@v9` incident from
        `CTX-902.1` — a plausible-sounding version-specific detail that turned out wrong, caught by
        checking the registry directly instead of trusting memory.)
    *   *Impact:* `Cargo.toml` uses plain `keyring = "4.1.6"` (the `v1` default feature is exactly
        what's needed); `secrets.rs` uses `keyring::{Entry, Error}`, confirmed against the crate's
        actual vendored source under `~/.cargo/registry/src` before writing a single line against it.

*   **Deviation 2 (non-deviation, confirmed as designed): `KNOWN_SECRET_KEYS` is an empty list.**
    *   *Reasoning:* `SPEC-106` names "supplier API keys" and "LLM provider... API keys" as the
        secrets this store needs to hold, but neither `SPEC-201` (LLM provider abstraction) nor
        `SPEC-203` (supplier API integration) exists yet — there is no real key name to fetch today.
        Inventing a placeholder key (e.g. `"openai_api_key"`) to make the list non-empty would be
        scope creep into specs that haven't been designed. The mechanism (an explicit allowlist,
        not "fetch everything stored under our service name") is real and tested via
        `build_configure_request`; the list itself is deliberately empty until a real consumer
        exists to add its own key.
    *   *Impact:* None today — `spawn_daemon` sends `daemon.configure` with an empty secrets map on
        every launch, which `configure_daemon` handles identically to a populated one. `SPEC-201`/
        `SPEC-203` are expected to add their key name to this one-line list, not build a parallel
        mechanism.

*   **Deviation 3 (non-deviation, confirmed as designed): `kicad_bridge.configure`'s override is
    verified mocked, not against a live KiCad instance listening on a custom socket path.**
    *   *Reasoning:* This dev machine's KiCad only listens on the default IPC socket path
        (`CTX-103.1` already verified that path for real). Testing a *custom* path for real would
        require actually reconfiguring KiCad's own IPC settings to listen somewhere else, which is
        a real, separate manual step outside this context's scope. `TEST-006` instead mocks
        `kicad_bridge.KiCad` and asserts the constructor is called with the configured
        `socket_path`/`timeout_ms` — proving the plumbing is correct, while being explicit that the
        live custom-path behavior itself is unverified (`CLAUDE.md`'s "state what was not verified"
        norm).
    *   *Impact:* None on this context's correctness claim; flagged so a future session doesn't
        assume this path has been exercised for real just because `TEST-002` (the default path) has.
