# CTX-107.2: FreeCAD Version in Diagnostics

> **Spec Reference:** Links to [SPEC-107](../specs/SPEC-107-structured-logging-diagnostics.md)

Closes issue #249 — *"FreeCAD's version is not reported in diagnostics"*. KiCad's real version has
been in the copied diagnostics blob since `CTX-303.3`; FreeCAD's only ever reported
reachable/not reachable.

**The substance of this work is an outside contribution** (PR #301). What follows is that
contribution plus the review fixes needed to satisfy `SPEC-107` §3, which the original approach
could not.

## 1. Feature Definition & Execution Plan

### Phase 1: Read the real version

*   [x] `freecad_bridge.get_freecad_version(cli=None)` shells out to `freecadcmd --version`.
*   [x] Returns `--version`'s **raw output rather than parsing it**. The contributor's own reasoning
    and it is right: FreeCAD's version string has changed shape across releases, and a wrong parse
    that silently reports the wrong version is worse than an unparsed string a human can read.
*   [x] Accepts an already-resolved path, so a caller that has just run `find_freecadcmd()` does not
    pay for a second filesystem walk and the two can never disagree about which binary was
    inspected.
*   [x] Timeout bounded at 5s.

### Phase 2: Report it on demand, never from the startup probe

*   [x] `freecad.get_version` route, registered in `ROUTES` **and `ASYNC_ROUTES`** — it spawns a
    subprocess, and a sync route runs inline in the daemon's stdin read loop (`CTX-314.2`).
*   [x] Never raises. A version that cannot be read is `{"version": None, "reason": str}`, because
    not knowing the version is an ordinary state — the same rule `SPEC-324` §2.1 applies to a
    provider that cannot list its models.
*   [x] `_detect_capabilities` is **unchanged**. See §4 Deviation 1 — this is the whole review.

### Phase 3: Surface it where diagnostics already live

*   [x] `copyDiagnostics()` fetches it, in the same place and on the same terms as KiCad's version
    directly above it, so the two read as one pattern rather than two.
*   [x] Only when `freecad_available` is true, matching the existing KiCad branch.
*   [x] A failed lookup degrades to `unknown` and never costs the user the rest of their
    diagnostics.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — the version call could not live in `_detect_capabilities`, for two independent
    reasons.** The original change put it inside that function's availability `try`:

    ```python
    try:
        freecad_path_checked = freecad_bridge.find_freecadcmd()
        freecad_available = True
        freecad_version = freecad_bridge.get_freecad_version()   # added here
    except Exception as e:
        freecad_available = False
        freecad_error = str(e)
    ```

    *   **It made a cosmetic diagnostic into a kill switch.** Any failure of `--version` — a
        timeout, a permissions problem, a broken install — set `freecad_available = False`. FreeCAD
        would be installed and working while Settings rendered "not reachable" and the enclosure
        feature area was disabled. CI caught this as a real reproduction, not a mock artifact:
        `test_002h` patches `find_freecadcmd` to a path that does not exist, and the new code tried
        to execute it.
    *   **`SPEC-107` §3 forbids it outright, and names this exact hazard.** Capability probes must
        be *"cheap and non-blocking"*, because the probe feeds `daemon.ready` on every launch. §3
        goes further and says *"a long `freecadcmd` call would starve [the heartbeat] and produce a
        false 'crashed' signal"* — the precise call this added. `_detect_capabilities`'s own
        docstring restates the constraint three lines above the change.
    *   *Impact:* the version moved to its own on-demand route. Nesting the `try` alone would have
        fixed the kill switch and still violated §3 on every startup.

*   **Deviation 2 — `SPEC-107` §3's constraint had no test, which is why this got as far as it
    did.** The rule existed in prose in the spec and in a docstring, and nothing executable held
    the line. `TEST-020` now does. Recorded because it generalises: a constraint stated only in
    prose is one an outside contributor cannot discover by running the suite, and the repository's
    own gate is the right place to teach it.

*   **Deviation 3 — the review scope grew from "report a version" to "report it where diagnostics
    already are".** The original change added a capability field with no consumer, so #249 would
    have stayed open in practice — nothing displayed it. Following `copyDiagnostics()`'s existing
    KiCad precedent put it where a user actually looks, and made the two versions read as one
    pattern instead of two.

*   **Deviation 4 — the contribution's core judgement was right and was kept.** Returning
    `--version`'s raw output rather than parsing it is the contributor's decision, with their own
    stated reasoning, and it survives unchanged. The defect was where the call was made, not what
    it did.
