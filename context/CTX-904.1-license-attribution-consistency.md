## 4. Plan Drift & Architectural Changes

*   **Deviation 1: bundled the AgentFlow pin bump into this CTX instead of giving it its own
    branch/CTX.**
    *   *Reasoning:* The user's own instructions treated these as two separate asks (license
        metadata fixes; a follow-up pin bump once 0.9.0 published), but by the time this CTX was
        written 0.9.0 was already live on PyPI (verified directly: `pip index versions
        gittielabs-agentflow` showed `0.9.0` as `LATEST` before this pin was touched). Both the
        instructions to relicense `~/repos/hardware-agent-studio`'s own metadata and to bump the
        pin trip the exact same gatekeeper rule for the exact same reason (`requirements.txt` and
        `Cargo.toml`/`package.json` are all in `CODE_EXTENSIONS`), and are the same shape of
        change: a metadata/pin correction with no new application logic. Splitting them into two
        branches would have meant writing a second near-duplicate SPEC/CTX pair for no real
        isolation benefit — this repo's own norm is to avoid unnecessary abstraction, and two
        near-identical governance CTXs in flight at once is exactly that.
    *   *Impact:* One branch, one PR, one CTX covers both. If a future session needs to bump this
        pin again independently of any license work, it should get its own CTX at that point --
        this bundling was specifically because both landed in the same session, not a precedent for
        pin bumps in general.

*   **Deviation 2: neither `feat/CTX-901.2-product-gate` nor `chore/bump-agentflow-0.8.2` (the two
    branches the originating instructions offered as "option (a)") were still open.**
    *   *Reasoning:* Both had already merged (`feat/CTX-901.2-product-gate` via PR #42,
        `chore/bump-agentflow-0.8.2` via PR #33) by the time this work started — confirmed via
        `gh pr list --head <branch> --state all` before assuming either was foldable-into. Option
        (a) as literally described was no longer available.
    *   *Impact:* Took option (b): a new branch (`chore/relicense-metadata-apache2`) with its own
        CTX. Rather than pointing that CTX's `spec_ref` at an unrelated existing spec just to avoid
        writing a new one (which would have been dishonest metadata — this change has nothing to do
        with, say, `SPEC-201`'s LLM provider abstraction), wrote a small, real `SPEC-904` in the
        9xx meta range alongside `901`/`902`/`903`. `SPEC-904` isn't yet in
        `validate_spec_context.py`'s `KNOWN_PARENTLESS_SPEC_IDS`, so the validator will emit an
        "ORPHAN ROOT SPEC" informational note for it — informational only, never blocks the exit
        code, and not touched here per the explicit instruction not to weaken the validator to get
        around anything.

*   **Deviation 3: this CTX's own first draft tripped its own validator.**
    *   *Reasoning:* Wrote `TEST-002`'s Test File Location cell as `N/A -- CI gatekeeper, not a
        test file`, intending the placeholder to be self-explanatory. `validate_testing_matrix()`
        checks `test_file.lower() not in ['n/a', 'none', '-']` after stripping backticks — an exact
        match, not a prefix or substring check — so the extra text made it fall through to
        `os.path.exists()` on the literal string `n/a -- ci gatekeeper, not a test file`, which of
        course doesn't exist, and `python3 scripts/validate_spec_context.py --base origin/develop`
        failed with `MISSING TEST FILE` before this was ever pushed.
    *   *Impact:* Moved the explanation into the Test Description column and left the cell as
        exactly `N/A`. Caught locally, before push, by actually running the validator rather than
        assuming a plausible-looking placeholder would be accepted — worth remembering as a
        concrete instance of this file's own gotcha #2 in `CLAUDE.md`.
