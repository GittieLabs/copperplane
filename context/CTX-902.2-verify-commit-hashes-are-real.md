# CTX-902.2: Verify Commit Hashes Are Real

> **Spec Reference:** Links to [SPEC-902](../specs/SPEC-902-spec-graph-validator-v2.md)

## 1. Feature Definition & Execution Plan

A real, standing gap in `scripts/validate_spec_context.py` found while reviewing a merged PR's own
close-out against this repo's conventions, then confirmed against my own prior work in the same
session: the existing `EMPTY COMMIT HASHES` check only verifies the field is non-empty, never that
a recorded hash actually resolves to a real commit. Ten of this session's own context files
(`CTX-205.5` through `CTX-306.2`) each recorded a commit hash from *before* `git commit --amend` was
used to fold that same hash back into the commit -- amend rewrites history, silently discarding the
original, pre-amend commit before it was ever pushed, so the recorded hash referred to nothing real,
even though the work itself shipped correctly and the validator passed every time. Found and fixed
by hand across all ten files ([PR #204](https://github.com/GittieLabs/hardware-agent-studio/pull/204));
this context is the mechanical check so a human doesn't have to find it by ad-hoc audit again.

**Real design constraint, discovered while building this, not assumed**: a naive reachability check
(`git cat-file -e <hash>`) is not sufficient -- a commit discarded by `git commit --amend` remains a
real, loose object in `.git/objects/` until eventual garbage collection, so `cat-file -e` reports it
present right after the very amend that orphaned it (confirmed directly: this is exactly why the
first version of `test_001` in this context's own test suite failed against its own fix). The real
check needed is *reachability* -- `git merge-base --is-ancestor <hash> HEAD` -- which correctly
distinguishes "this hash is really part of history" from "this hash still happens to sit in the
object store."

**A second real design constraint, also discovered directly, not assumed**: checking every hash in
every context file's `commit_hashes`, repo-wide, on every PR, would produce real false failures
against this repo's own already-established, legitimate convention. Confirmed directly: a real,
already-merged, correctly-recorded commit hash from a since-deleted feature branch (e.g. `CTX-315.2`'s
own precedent) is **not fetchable** in an unrelated, later PR's own scoped checkout --
`git fetch <url> <that-hash>` against a fresh clone fails once the branch ref is gone, even though the
commit is completely real and permanently visible on the merged PR's own GitHub page. Scoping this
check to only hashes **newly added** in the current diff (comparing a changed context file's
`commit_hashes` against its own value as of `--base`) avoids this false-positive entirely, while still
catching the real bug at the one moment it's actually verifiable and actually matters: while the hash
is still genuinely part of the current branch's own reachable history, before any future squash or
branch deletion could make re-verifying it later unreliable.

### Phase 1: `scripts/validate_spec_context.py`
*   [ ] `extract_hash_token(entry)` -- pulls the leading hex hash out of either this repo's own
    `"<hash> - <description>"` convention or a bare hash; returns `None` for anything that doesn't
    look like a real 7-40 character hex hash at all.
*   [ ] `git_commit_is_reachable(commit_hash)` -- `git merge-base --is-ancestor <hash> HEAD`, not
    `git cat-file -e`, for the real reason above.
*   [ ] `validate_commit_hashes_are_real(ctx_file, base_branch, frontmatter)` -- diffs the file's own
    `commit_hashes` against its value at `base_branch` (via `git show <base>:<path>`); checks only the
    newly-added entries; a malformed entry is `MALFORMED COMMIT HASH`, an unreachable one is
    `DANGLING COMMIT HASH`, both hard failures (matching SPEC-902 §2's own severity split -- "these
    are unambiguously bugs, never a legitimate in-progress state").
*   [ ] Wired into `validate_pr`'s existing per-context-file loop, right after the pre-existing
    `EMPTY COMMIT HASHES` check.

### Phase 2: tests
*   [ ] `scripts/tests/test_validate_spec_context.py`: `TestCommitHashesAreReal`, real CLI-via-
    subprocess tests against constructed temporary git repos (SPEC-902 §3's own explicit requirement
    -- "real, direct test coverage... including a case that exercises the actual CLI against a
    constructed temporary git history, not only unit tests of individual helper functions in
    isolation"). Four cases: the real `git commit --amend` mechanism reproduced exactly (commit,
    record that commit's own real hash, amend) is detected; a real, never-amended, reachable hash
    passes cleanly; an older file's already-existing, unchanged hash is never re-flagged when the
    file is edited for an unrelated reason; a malformed (non-hash) entry is flagged.

  and passing, including the 4 new tests and every pre-existing test unaffected (in particular
  `TestEndToEndCLI.test_003`, whose own fixture context file happens to carry a deliberately-fake,
  too-short placeholder hash `"abc123"` -- still passes, since that test only asserts its own
  `DANGLING spec_ref` failure is present, not that it's the *only* failure).
- `python3 scripts/validate_spec_context.py --base origin/develop` -- run against this repo's own
  real, current diff.
- **Named, honest, real limitation**: this check can only verify a hash that's genuinely part of the
  current checkout's own fetched history. A CI runner whose checkout for some reason doesn't include
  the full depth of the PR's own branch (this repo's `validate-specs-and-context` job currently uses
  `fetch-depth: 0`, confirmed by reading `.github/workflows/*.yml` directly) would produce false
  failures for real, correctly-recorded hashes -- not attempted to be defended against beyond
  confirming today's actual CI configuration is sufficient.

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

**The first implementation attempt used `git cat-file -e <hash>^{commit}` and was wrong** -- it
passed a test asserting the real bug should be caught, revealing that a commit discarded by
`git commit --amend` is still a real, present object in the local store, not yet garbage collected.
Corrected to `git merge-base --is-ancestor <hash> HEAD`, which checks real reachability, not mere
object presence. Recorded here per this repo's own norm of writing Plan Drift honestly, including a
wrong first attempt caught by the test suite itself -- exactly the value this framework's own
"verify against the real thing" norm names, demonstrated on the very tool that enforces it.
