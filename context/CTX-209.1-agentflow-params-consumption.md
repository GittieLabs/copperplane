# CTX-209.1: Consume AgentFlow's Vendor Parameter Passthrough

> **Spec Reference:** Links to [SPEC-209](../services/python-daemon/specs/SPEC-209-provider-parameter-contract-and-model-defaults.md)

`SPEC-209` §2.1's half of the work: the transport exists upstream now, so this repo uses it. The
defaults and delta-storage half is `CTX-209.2`, which is planned and deliberately not implemented
here — see §4 Deviation 3.

**The upstream change landed first, and this context could not have been verified without it.**
`CTX-323.1` §4 found that AgentFlow's `chat()` had no channel for a parameter it does not name, so
per the standing rule that AgentFlow limitations are fixed upstream rather than worked around, two
AgentFlow releases shipped before a line of this was written:

*   **0.11.0** — `params: dict` on the provider protocol and all three providers, `AgentConfig.params`
    forwarded by `AgentExecutor`, reserved-key refusal, and removal of the `-low`/`-medium`/`-high`
    model-name suffix convention.
*   **0.11.1** — a **pre-existing, shipped bug** found while diagnosing this work. See §4
    Deviation 2; it is the most important thing in this file.

## 1. Feature Definition & Execution Plan

### Phase 1: Pin the released package

*   [x] `gittielabs-agentflow[anthropic,openai,google]` 0.10.0 → **0.11.1**.
*   [x] Verified against the real published artifact, not a local checkout: installed from PyPI,
    `agentflow.__version__` reports `0.11.1`, and `params` is present on the protocol.

### Phase 2: `params` on a provider record

*   [x] `ProviderRecord.params: NotRequired[dict[str, Any]]` (`SPEC-209` §2.1). Optional, so every
    existing record and every `config.json` on disk stays valid unchanged.
*   [x] **No preset ships params.** A default parameter would be a claim about what a model
    supports, which is exactly what `SPEC-209` §1 declines to make.
*   [x] Absent and `{}` are deliberately the same request. AgentFlow treats a falsy `params` as
    "send nothing", so a record that never had params and one whose params were cleared produce an
    identical call — there is no third state to reason about.

### Phase 3: Reach the vendor call

*   [x] `record_params(config, provider_id)` resolves through the same
    `migrate_legacy_config`/`_resolve_provider_records` path `llm.get_provider_records` uses, so
    the editor and the dispatch path cannot disagree about what a record is.
*   [x] A **separate lookup rather than a fourth element on `resolve()`'s return tuple**: widening
    that arity would break every existing caller for a value most of them do not want, and the
    three-tuple is `SPEC-208` §2.6's own documented contract.
*   [x] Returns a copy, so a caller cannot mutate the stored record by editing what it got back.
*   [x] `chat_agents` puts them on `AgentConfig`, which is **AgentFlow's own per-agent channel** —
    this repo adds no second mechanism for something the framework already carries.
*   [x] `chat()` takes an explicit `params` argument, mirroring how `model` already works.
*   [x] An unknown provider id returns `{}` rather than raising. This is called on every dispatch;
    raising would turn a stale role binding into a crash instead of the existing, clearer error.

### Not in this context

*   **Delta-only config storage, the field-by-field preset merge, and the migration**
    (`SPEC-209` §2.3). `CTX-209.2`.
*   **Any UI.** Nothing surfaces `params` yet — a record can carry them only by hand-editing
    `config.json`. Stated plainly because it means this slice ships no user-facing behaviour.
*   **Pinning the vendor SDKs themselves.** See §4 Deviation 2; it is the root enabler of the bug
    found here and it is a real decision, not a detail to fold in silently.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — the transport had to be built upstream first, and that was most of the work.**
    *   *Reasoning:* `CTX-323.1` had already established there was no channel. Following the
        standing rule rather than adding a downstream shim meant two AgentFlow releases, published
        to PyPI, before this repo could consume anything.
    *   *Impact:* this context's own diff is small because the difficult part is in another
        repository. Recorded so the size of the change here is not mistaken for the size of the
        work.

*   **Deviation 2 — diagnosing a test failure found a shipped bug, and the diagnosis method was
    itself the finding.**
    *   *What happened:* after the pin bump, `TestRealProviderCalls.test_001_real_anthropic_chat`
        failed with `AsyncMessages.create() got an unexpected keyword argument 'temperature'`. The
        obvious reading — "the upgrade broke it" — was wrong.
    *   *The real cause:* `anthropic` 1.x **removed `temperature`** from `messages.create`. Sending
        it raises a plain `TypeError` **client-side, before any network call**, which AgentFlow's
        `BadRequestError` retry cannot catch. Every chat with a non-1.0 temperature failed
        outright, and `AgentConfig.temperature` defaults to `0.7`. Fixed upstream in **0.11.1**.
    *   **This was live in the shipped v0.3.0.** `anthropic` is not pinned here — it floats in
        through AgentFlow's extras — so the release CI's fresh venv resolves whatever is current,
        which is 1.2.0. Every Anthropic call in that build fails. It went unnoticed only because
        both model roles are bound to `google` on the maintainer's install.
    *   **Why it hid for so long, and the method lesson:** every earlier full-suite run in this
        session used the **system `python3`**, which carries `anthropic` 0.121.0, where
        `temperature` is still accepted. The `.build-venv` that actually freezes the shipped
        sidecar carries 1.2.0. Same repository, same tests, opposite results, decided entirely by
        which interpreter ran them. `CTX-407.3` Deviation 3 recorded that the frozen binary is the
        real thing rather than the module it was built from; this is the same lesson one step
        earlier — **the interpreter that builds the artifact is the one whose results count.**
    *   *Impact:* the suite is now run with `.build-venv/bin/python`. The root enabler — unpinned
        `anthropic`, `openai` and `google-genai` floating through AgentFlow's extras — is
        **deliberately not fixed here**. `CTX-402.6` pinned a transitive dependency for exactly
        this class of problem, so there is precedent for pinning these too, but it changes what
        every release build resolves and belongs in its own reviewed change with a maintainer
        decision behind it.

*   **Deviation 3 — this slice ships no user-facing behaviour, and that is a deliberate split.**
    *   *Reasoning:* `SPEC-209` is `user_facing: true`, but its user-visible half is the defaults,
        reset surfaces and documentation table. A record can currently carry `params` only by
        hand-editing `config.json`.
    *   *Impact:* `CTX-209.2` inherits the whole user-facing verification obligation. Splitting
        transport from storage keeps the migration — which `SPEC-209` §3 names as the risky part,
        because deciding whether a value equal to the current preset was *chosen* or merely
        *persisted* needs information that is genuinely gone — out of a change that is otherwise
        additive and safe.
