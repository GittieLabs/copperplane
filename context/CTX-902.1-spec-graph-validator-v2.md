# CTX-902.1: Spec Graph Validator v2

> **Spec Reference:** Links to [SPEC-902](../specs/SPEC-902-spec-graph-validator-v2.md)

## 1. Feature Definition & Execution Plan

### Phase 1: Fix the path-exclusion matcher (real, currently-triggering bug)
*   [x] Replace bare `str.startswith(...)` in `EXCLUDE_PATHS`/`CODE_EXTENSIONS` with real
    path-segment/basename matching: exempt any `README.md` by basename (not just root), any path
    with a `.github`/`specs`/`context` directory component at any depth, and lockfiles
    (`package-lock.json`, `Cargo.lock`, `uv.lock`) by basename.

### Phase 2: Parse `SPEC-*.md` frontmatter
*   [x] Reuse the existing `parse_frontmatter()` (already generic — it just reads YAML between
    `---` fences) to discover and parse every `SPEC-*.md` in the repo, not only the ones changed in
    the current diff.

### Phase 3: Graph-integrity checks (hard failures)
*   [x] `id` uniqueness across every discovered spec.
*   [x] `id` matches the file's own name (`SPEC-902` must live in a file named `SPEC-902-*.md`).
*   [x] `location:` frontmatter field matches the file's actual path relative to the repo root.
*   [x] Every `parent_spec`/`child_specs` path resolves to a real file on disk, resolved relative to
    the referencing file's own directory (matching how the markdown links in the same files work).
*   [x] Bidirectional check: if `A.parent_spec` points at `B`, `B.child_specs` must list `A` back.
*   [x] Extend the existing `CTX-*.md` check so `spec_ref` also resolves to a real file (today the
    validator only checks the field is *present*, never that its path is real).

### Phase 4: Informational findings (never block)
*   [x] Report specs with no matching `CTX-*.md` context file anywhere in the repo ("no context
    yet") and specs with `parent_spec: null` that aren't `SPEC-000`/`SPEC-901`/`SPEC-902`/`SPEC-903`
    (a soft "orphan" signal). Printed in the report; never contributes to the exit code.

### Phase 5: Real test coverage for a script that gates every future PR
*   [x] `scripts/tests/test_validate_spec_context.py`: unit tests for the new path-matcher against
    real repo paths (root/module README, lockfiles, nested `specs/`/`context/` dirs, ordinary code
    files), unit tests for each new graph check against constructed fixture files in a temp
    directory (never against this repo's own real `specs/`/`context/` trees), and **one true
    end-to-end test**: a real temporary git repo, a real commit history, a deliberately broken spec
    file, and the actual CLI invoked via `subprocess` — asserting the real exit code and error
    text, not just a helper function's return value.
*   [x] Confirm every existing check (`CTX-*.md` frontmatter/hashes/testing-matrix) still passes
    against this repo's real, current state after the change — this script must keep working for
    every PR that comes after this one, including ones this session already opened.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `ROADMAP.md` §1.3's specific claim about module READMEs doesn't actually
    reflect a live bug — verified directly before writing any fix.**
    *   *Reasoning:* Tested the real matcher logic with `services/python-daemon/README.md` and the
        root `README.md` as input before touching any code: both produced `counts_as_code=False`,
        identically, because `.md` was never in `CODE_EXTENSIONS` to begin with — the
        `EXCLUDE_PATHS` check is never even reached for either. The roadmap's framing of this as an
        active bug doesn't hold up under direct testing.
    *   *Impact:* Fixed the underlying mechanism anyway (real path-segment/basename matching
        instead of bare `str.startswith`), since it's still wrong in principle and would bite the
        moment a non-`.md` file ever lands under a module-level `specs/`/`context/` dir. But the
        `.json` lockfile claim in the same roadmap paragraph *is* real and currently triggering —
        confirmed directly the same way before fixing it. Worth remembering as a pattern: two
        claims presented with equal confidence in the same bullet list were not equally true.

*   **Deviation 1.5: the first real CI run failed for a reason none of the local testing above
    could have caught — `pyyaml` was never in `services/python-daemon/requirements.txt`.**
    *   *Reasoning:* `scripts/validate_spec_context.py` has imported `yaml` since before this
        context existed — that's not new. But `scripts/tests/` never had a file that actually
        imported it until `test_validate_spec_context.py`; `test_agent_docs.py` only checks file
        existence. `python-ci.yml` runs both `services/python-daemon/tests` and `scripts/tests`
        through the *same* daemon venv (`uv pip install -r services/python-daemon/requirements.txt`),
        which never included `pyyaml`. Locally this was invisible because a system-wide `pip install
        pyyaml` earlier in this session (to run the gatekeeper manually, before any of this CTX's
        work began) silently supplied it outside the venv every single time — including every
        "verify for real" check run against the real repo in Deviations 1-3.
    *   *Impact:* Added `pyyaml==6.0.3` to `services/python-daemon/requirements.txt`. Re-verified in
        a genuinely fresh venv built in the scratchpad directory (not this session's already-primed
        one) — all 22 `scripts/tests` tests pass with only `services/python-daemon/requirements.txt`
        installed, nothing from the ambient system Python. This is the second time in this session a
        "local success" turned out to be resting on unstated ambient state rather than what the
        workflow actually declares (the first being `source .venv/bin/activate` not persisting
        across steps, `CTX-903.1` Deviation 4) — worth treating as a recurring category, not two
        unrelated incidents: local verification is only as good as the isolation it runs under.

*   **Deviation 1.6: the second real CI run failed on `windows-latest` only — a genuine,
    pre-existing Windows bug in `validate_spec_context.py` itself, not a git-config or subprocess
    quirk in the new end-to-end tests.**
    *   *Reasoning:* The user's working hypothesis going into this run was a git-config issue
        (`init.defaultBranch`, `user.email`/`user.name`, or `git branch -m` behaving differently on
        CI runners) — that hypothesis was wrong. All three `TestEndToEndCLI` subprocess tests build
        their temp repos identically on every platform and passed on `ubuntu-latest` and
        `macos-latest`; only `windows-latest` failed, and the traceback pointed somewhere else
        entirely: `print(f"\U0001f50d Analyzing diff against {base_branch}...")` raised
        `UnicodeEncodeError: 'charmap' codec can't encode character '\U0001f50d'` because Windows'
        default console codepage (`cp1252`) can't represent the 🔍/❌/✅/ℹ️ emoji this script has
        always printed. `test_002_real_cli_passes_on_a_clean_graph` is the one test in the suite
        that reaches the "all clean, exit 0" path — the only path that executes that specific
        `print` line — so it's also the only one of the three that failed on the actual encoding
        error; the other two failed as a side effect (empty stdout) because the script crashed
        before reaching its own error-reporting prints. This bug was real and latent before this
        CTX touched the file — nothing about the graph-validator changes introduced it — it simply
        had never been exercised on Windows before, because `test_agent_docs.py` never invoked the
        script as a subprocess and `spec-container-gatekeeper.yml` only runs on `ubuntu-latest`.
    *   *Impact:* Added `sys.stdout.reconfigure(encoding='utf-8')` /
        `sys.stderr.reconfigure(encoding='utf-8')` right after the imports in
        `scripts/validate_spec_context.py`, unconditionally (not gated on `sys.platform`) since a
        subprocess with no attached console can hit the same fallback-codepage behavior regardless
        of OS. Re-ran the full `scripts/tests` suite locally (macOS, where this specific failure
        can't reproduce) to confirm the reconfigure call itself doesn't break anything — 22 passed —
        then re-pushed for CI to confirm the actual fix on `windows-latest`. Correcting the record:
        the user's git-config hypothesis was a reasonable guess given the test file's use of real
        `git commit`/`git branch -m` subprocesses, but the true cause was Unicode output encoding,
        unrelated to git configuration entirely.

*   **Deviation 1.7: fixing Deviation 1.6 on the child-process side surfaced a matching bug on the
    parent side — the test harness's own `subprocess.run(..., text=True)` calls decoded the child's
    now-UTF-8 stdout with the wrong codec.**
    *   *Reasoning:* After `sys.stdout.reconfigure(encoding='utf-8')` made the script itself emit
        valid UTF-8, the third CI run still failed on `windows-latest` — a different traceback this
        time: `UnicodeDecodeError: 'charmap' codec can't decode byte 0x8d`, raised inside Python's
        own `subprocess._readerthread`, not inside `validate_spec_context.py`. `subprocess.run(...,
        capture_output=True, text=True)` without an explicit `encoding=` argument decodes the
        child's stdout/stderr using `locale.getpreferredencoding(False)` — `cp1252` on this runner —
        regardless of what the child process actually wrote. The three `TestEndToEndCLI` calls in
        `scripts/tests/test_validate_spec_context.py` (lines 187, 213, 250) all had this gap. Two
        genuinely separate encoding assumptions had to agree — the child's output encoding and the
        parent's decode encoding — and fixing only one side left the other as the new failure.
    *   *Impact:* Added `encoding='utf-8'` to all three `subprocess.run` calls. Re-verified locally
        (all 22 tests pass) before pushing a third time. Worth flagging as its own lesson distinct
        from Deviation 1.6: "the script now emits UTF-8" and "every reader of the script's output
        expects UTF-8" are two different claims, and CI caught the gap between them exactly once
        each, in sequence — a reminder that a Windows-specific encoding bug is rarely confined to a
        single call site once any part of a pipeline assumes a non-UTF-8 default.

*   **Deviation 2: the whole-graph check runs on every invocation, not only when a PR's diff
    touches a `SPEC-*.md` file — a deliberate scope decision beyond what `SPEC-902` §2 stated.**
    *   *Reasoning:* `SPEC-902`'s own Gotcha says the check must cover the whole graph, not just the
        diff, because a change to `SPEC-A`'s `child_specs` can break a link *from* `SPEC-B` that
        this PR never touched. Taken to its logical conclusion, that means the graph's validity is
        an invariant that should hold on every run, regardless of what a given PR happens to touch —
        a code-only PR that never touches any spec should still be protected if the graph is
        somehow already broken. The cost is negligible (reading and parsing eight small YAML
        frontmatter blocks) compared to the value of catching drift immediately rather than only on
        PRs that happen to touch `specs/`.
    *   *Impact:* `validate_spec_graph()` is called unconditionally in `validate_pr()`, not gated
        behind `if spec_files_changed`. Confirmed via `TEST-006` that this doesn't introduce any
        false positive against the repo's real, current state.

*   **Deviation 3: this script gates every PR in the repo, including this one's own — verified
    the CLI contract is unchanged before relying on that.**
    *   *Reasoning:* `.github/workflows/spec-container-gatekeeper.yml` invokes
        `python scripts/validate_spec_context.py --base origin/$BASE_REF` with no other changes
        needed for this spec — confirmed by re-reading the workflow file rather than assuming the
        CLI surface (`--base` flag, exit codes, stdout format) was preserved. `TEST-006` and the two
        end-to-end `subprocess` tests (`TEST-005`, `TEST-007`) are what actually prove this, not just
        a read-through of the diff.
    *   *Impact:* None — confirms the contract held. Noted because a script this load-bearing
        deserved the extra confirmation step rather than trusting the diff looked reasonable.
