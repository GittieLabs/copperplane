# CTX-408.7: Three Cuts That Point At The Finding

> **Spec Reference:** Links to
> [SPEC-408](../specs/SPEC-408-messaging-for-the-maker-who-is-leveling-up.md)

SPEC-408 is `In-Progress` for one reason: the video has not been recorded. This context records
it, but not as one 75-second screen recording. The maintainer asked for **15s, 30s and ~60s cuts
for viewers with short attention spans, with captions and no sound**, and asked that they **pull the
finding out of the UI** rather than wait for the viewer to spot a warning in a full window.

The technique is adapted from a public write-up of the Opus 5.5 motion-design pipeline. The post's
own claim is "the prompt is 10% of the video, the other 90% is the harness". Kept from it:

- a render that is a pure function of time,
- closed-form springs,
- a beat-by-beat shot list instead of a mood,
- **real product UI only, cropped, never redrawn**,
- a critique loop where the agent looks at its own frames.

Dropped: music, beat detection, synthesized sound and voice.

**Depended on #472, merged as `435a247`.** That PR carries the script's "shoot it against a
build" and segment-5 notes. It is now merged into this branch.

## 1. Feature Definition & Execution Plan

### Phase 1: Amend the spec to say what is being made

*   [x] SPEC-408 §2 names Screen Studio as the capture tool and asks for one 60-90s video. Replace
      both with the capture method below and the three cuts, saying why.
*   [x] State the rule for captions: with no sound, the captions carry the whole story, so they
      are part of the design. Burn them into the frame, and also export an `.srt` file.

### Phase 2: Capture harness — the agent drives the real app

Proven feasible on 2026-10-10 (Section 4), with these constraints:

*   [x] Shoot against a production build (`tauri build --bundles app`), launched by full path. Never
      `tauri dev`. Use a signed release instead if one with the SPEC-340 and SPEC-343 fixes exists
      by shoot day.
*   [x] **Stills:** `screencapture -x -o -l<windowid>`, wrapped in `scripts/capture_still.py`.
      Each still is recorded in the session manifest with its SHA-256, pixel size and the
      build on screen: core build time and sidecar SHA-1. That is what lets Phase 3 trace a
      caption number back to a specific capture of a specific build. This captures the window even when covered,
      at 2560×1800, ~5 fps. Most shots are stills, because the pullouts add the motion.
*   [ ] **Motion takes** (the 3D enclosure, a live scroll, KiCad's DRC dialog) use the `cap-cli`
      dev build. It records a screen region, so each take needs Copperplane in front and nobody
      using the screen. Keep takes short, and announce each one to the maintainer.
*   [ ] Run a fixed session order:
      1. Launch the build.
      2. The maintainer clears the keychain prompts and says go.
      3. Lock the window size.
      4. Capture the stills.
      5. Record the motion takes.
      6. Contact-sheet every clip before closing the app.
*   [x] **Waiting on LLM calls:** run each "Run Review" once off camera; the saved review then loads
      instantly on camera. The board check's summary is one LLM call: capture before, progress,
      after, and cut the wait to a ~0.5s beat. Never show a result the app did not produce.
*   [x] Clear `.kicad_dru` before segments 2, 4 and 5, and do not rebuild between them (script,
      after #472).
*   [x] **Decided 2026-10-10: shoot the app in light mode, and set it on a dark background in the
      video.**
      - Pullouts lift a card with a drop shadow. Shadows read on light and vanish on dark, where
        the card would need a glow, which is a banned look.
      - KiCad's black board editor (segments 1 and 2) cutting to a light Copperplane shows "hard
        thing, then help" before any caption is read.
      - Thin light text on dark, and orange on dark worst of all, smears under platform
        re-compression at phone size.
      - Cost: the video no longer matches the dark screenshots in the docs.
*   [x] **Before any PCB or Review shot, re-run every saved result on the build being filmed.**
      The probe found the PCB tab showing a result saved 16 days earlier: "Against KiCad's own
      defaults" above **16 violations at 0.15 mm** and the `copperplane-verification-canary` rule.
      That is the exact wrong number SPEC-340 fixed. A fresh build displays old saved results until
      **Check again** is pressed, and the stale one carries a "Checked 16 days ago" stamp that
      would itself be in the shot.
*   [ ] Hide Cap's rendered cursor in the export settings for segment 3, or park the cursor
      outside the window. Cap draws the pointer into the video, and segment 3's claim is that
      nothing moved.

### Phase 3: Shot list and pullout data

*   [ ] One shot list feeds all three cuts. Each shot carries a priority tag; each cut is a
      subset, never a separate edit.
*   [ ] Each pullout is one data entry:
      - the source frame,
      - the crop rectangle in source pixels,
      - the phrase to highlight,
      - the caption.
*   [ ] **Every number in a caption is read off its source frame.** The entry carries that frame,
      so a reshoot that changes a number breaks a check instead of shipping a stale caption. This
      script has been wrong about a number twice.
*   [ ] Redact file paths by crop rectangle or with `scripts/redact_screenshots.py`. The Schematic
      tab and the project header both show the full path.
*   [ ] Segment 3's claim is "nothing was clicked". A pullout is a camera move, so the frame under
      it must keep a visibly still cursor. Decide the treatment before building it.

### Phase 4: Compositor

*   [ ] Choose the renderer: Remotion (handles mixing in the motion clips and many data-driven
      variants) or a plain HTML page with a `seek(t)` function, rendered frame by frame. Remotion's
      license is fine for a one-person company. Record the choice and the reason.
*   [ ] The pullout beat, in four steps:
      1. Establish: the full window.
      2. Isolate: everything except the finding dims.
      3. Lift: the real crop rises out as a card, on a spring, with no overshoot on text.
      4. Emphasize: a highlight sweeps across the key phrase.
*   [ ] Lay shots out with a layout function, so 9:16, 1:1 and 16:9 each get their own framing
      rather than a crop of one render.
*   [ ] Banned looks: centred title on a gradient, everything fading in, labels in the corners,
      glows, dead beats.

### Phase 5: Critique loop and the three cuts

*   [ ] For every render, make a contact sheet, a 12-frame strip around each fast move, and a
      360px-wide phone test. Look at them.
*   [ ] Score each 1-10 on:
      - a hook in the first 2s,
      - phone readability,
      - motion,
      - something new every 2-3s,
      - accuracy to the real app.
      Fix the worst three and repeat until every score is 8+. Log every round.
*   [ ] Cuts:
      - **15s**: hook → seg 3 → seg 5 → close.
      - **30s**: adds segments 2 and 4.
      - **~60s**: adds segments 6 and 7.

### Phase 6: Verify as the user

*   [ ] The maintainer watches each cut on a phone, muted, as a viewer would. Record what they
      said, not just that they watched.

## 4. Deviations & Discoveries (Plan Drift)

### Shoot session s1 (2026-10-10)

14 stills covering segments 1-6, in `video-captures/s1/` (gitignored). All came from one build:
sidecar `13ecec9cf1…`, core built 23:05 UTC. Two LLM calls on the maintainer's key: "Check again"
and "Run Review". The motion takes and Cap's pointer are still open; they need the maintainer
at the screen.

*   **Segments 2 and 4 now agree, number for number.**
    - KiCad's own DRC dialog: Violations (4), all "min annular width 0.1000 mm; actual 0.0850 mm"
      on D1; Unconnected Items (1); Ignored Tests (5).
    - Copperplane's fresh check: "Against KiCad's own defaults. KiCad reports 4 design-rule
      violations, 1 unconnected item", and "5 DRC tests switched off".
    This is the match the script says the pair exists to show. It held because the `.kicad_dru`
    had already been moved aside on 09-24 and the check was re-run on this build.
*   **The board review was stale too, not just the board check.** It read "Reviewed on
    9/24/2026", and one of its findings still said "the rule wants at least 0.15mm". Re-running
    it fixed that.
*   **The fresh review contradicts its own header.**
    - The panel says the board check's 5 problems are listed above and "This review does not
      repeat them".
    - Its first five findings are exactly those 5 problems (four annular findings and the GND
      gap), each tagged "DRC finding".
    - The two findings segment 5 needs ("Not reported by ERC or DRC": D1, SW1) come after them
      and are correct.
    This is a product defect, outside this context; it was flagged separately. For the video,
    the segment 5 pullouts crop to the origin line and the D1 card, so the repeat is never on
    screen as a claim.
*   **KiCad's DRC dialog is too narrow for the line segment 2 must show.** At 665 px it cut off
    at "actual 0.0850 m". Background drags moved it a few pixels at most. System Events
    (`set size of window "Design Rules Checker"`) widened it to 887 px, and the whole line reads.
*   **Overview's "Where you are" card says "The board has been checked."** Left in frame, that
    undercuts segment 3's "nothing was clicked". Crop it out, or hide the card, for segment 3.
*   **My capture script failed CI on Windows, in a test I wrote to pass anywhere.**
    - `build_identity` called `os.path.relpath(bundle, repo)`.
    - On the Windows runner the temp directory is on `C:` and the checkout on `D:`, and
      `relpath` raises across drives.
    - I had reasoned that a macOS-only script needs only platform-independent tests. The tests
      were platform-independent; the function under test was not.
    - Fixed with `repo_relative`, which falls back to an absolute path. A test now pins the
      outside-the-repo case on every OS.
*   **Not timed:** how long the board check and the review take. Both finished inside the waits
    used (about 2 min and 75 s), which bounds them but measures nothing.

### Feasibility probe (2026-10-10, before Phase 1)

These are from the feasibility probe on 2026-10-10, before Phase 1. All of it ran on one machine:
macOS on Apple silicon, with Cap built from `~/repos/Cap` rather than a released Cap.

*   **I predicted Cap's `--window` recording would capture the window. It captures that region of
    the screen.** The 15-second probe clip shows the Claude window and four macOS permission
    dialogs on top of Copperplane, and Copperplane itself as a black rectangle. That is why Phase 2
    splits capture into stills and motion takes. The export also came out at 1536×1080, not the
    window's shape: Cap's studio mode adds its own background and padding.
*   **A second take with the screen cleared worked.** The maintainer moved every other window out of
    the way. A 31s Cap take (launch → open project → PCB tab → back to Overview) has only
    Copperplane in every frame, at 2560×1800 raw. That is the Phase 2 protocol. Two costs:
    - About 10s of the take is dead time from tool-call latency between clicks. That is fine,
      since the edit trims it, but a take cannot be shorter than its slowest step.
    - The pointer is drawn into the video.
    On relaunch of the same, unchanged build there was **no keychain prompt**: the earlier "Always
    Allow" held. The prompts return only after a rebuild.
*   **I reported "the A1 finding never appeared". That was my timing, not the app.** The findings
    are computed in the background after the tab opens. A screenshot taken a few seconds later
    showed both findings and "What you got right", with no click. Phase 2's session order waits for
    them.
*   **I assumed the recorded segment clips existed.** There are none: no `.mp4`, `.mov` or `.cap`
    in the repo, `~/Movies`, `~/Desktop` or `~/Downloads`. Everything is shot fresh in this
    context.
*   **The only local `.app` was v0.4.0 from 09-11, before the SPEC-340 fix.** It was rebuilt on
    2026-10-10 from `develop`'s code, and the sidecar hash matched `dist/`. The bundle still reads
    0.4.0 because nothing bumped it, so the version string cannot tell the two builds apart; only
    the build time can.
*   **Not verified:**
    - the ~5 fps still rate (measured on one 10-frame burst);
    - whether the macOS permission prompts stay answered across launches of the same build;
    - any of this on a Cap release rather than a dev build.
