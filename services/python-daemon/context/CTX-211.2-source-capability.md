# CTX-211.2: What The Source Can Actually Supply

> **Spec Reference:** Links to
> [SPEC-211](../specs/SPEC-211-power-path-review.md)

`SPEC-211` §2.1 item 3 — *"Current budget against what the source can actually supply. Twelve LEDs
off a USB port."* The one item `CTX-211.1` left unbuilt that is actually buildable; item 2 is not,
for the reason §2.1's status note gives.

Both halves of what this needs already exist: `input_supply.source` distinguishes `usb`, `adapter`,
`battery` and `host_board`, and `current_budget.milliamps` is a number the user gave us.

---

## 1. Feature Definition & Execution Plan

### Phase 1: The one source with a published number — DONE

*   [x] Fire only on `usb`, and cite the USB specification for the figure.
*   [x] Say what the standard **guarantees** rather than predicting a failure — what a user
      actually gets depends on what they plug into, which is not a fact about their board.
*   [x] Stay silent on `adapter`, `battery` and `host_board`, which have no capability this app
      holds, rather than inventing a limit for them.
*   [x] Reinforce when the budget fits, per `SPEC-343` §2.7 — a source the board comfortably sits
      inside is worth saying once.

## 4. Deviations & Discoveries (Plan Drift)

*   **The pack fires on one of four supply sources, and that is the design rather than a first
    cut.** Only USB has a published figure this app can honestly hold. An adapter's capability is
    printed on the adapter, a battery's depends on the cell and the discharge rate, and a host
    board's is a regulator datasheet figure — and `SPEC-211` §2.0 item 8 already measured that this
    app holds no datasheet numbers at all. Three silences and one claim is the honest ratio.

*   **`considerations.cleared()` builds a `computed` claim, and this one had to be `cited`.** The
    helper hardcodes the class, which is right for the packs that have used it — they compute their
    own reinforcement. Here the good news rests on USB's number exactly as much as the bad news
    does, and `SPEC-210` §2.1's rule is about the claim class, not about whether the news is
    welcome. So the satisfied case goes through `make` directly with `state=SATISFIED` and its
    source attached.

    Worth knowing rather than worth fixing: `cleared()` is a convenience for the common case, not
    the only way to build a satisfied consideration, and the record shape is identical either way.

*   **The hard part was the framing, not the threshold.** The easy sentence to write is *"your board
    draws more than USB can supply"*, and it is false — the charger on the user's desk almost
    certainly delivers two amps. What is true is that the board has stopped being portable between
    the things they might plug it into, and that a hub or an older laptop port is where it would
    fail.

    That is a better teaching outcome as well as a more accurate one, because it describes a
    symptom the user would otherwise spend an evening chasing. `TEST-002` pins it, since a confident
    *"this will not work"* about a board that works fine is `SPEC-211` §3's named worst case and it
    is the easier thing to write.

*   **A real cross-pack interaction showed up over JSON-RPC and it was correct.** With the supply
    set to USB at 900mA on the maintainer's own board, `trace_too_narrow_for_current` fired
    alongside this pack: the 0.2mm ground trace carries about 745mA by IPC-2221. Two packs built in
    separate phases, agreeing about the same board for different reasons, with no shared code
    between them beyond the current budget.

*   **Verified against the real project and the record put back.** Setting `input_supply` and
    `current_budget` to exercise the route writes to the maintainer's own project file, so both
    fields were cleared again afterwards and the record checked back to `{}`.
