# CTX-402.10: Implementation Context: The macOS Install Window

> **Spec Reference:** Links to [SPEC-402](../../../specs/SPEC-402-release-signing-and-auto-update.md)

Drag-to-Applications already worked -- `v0.4.0`'s DMG carries the `Applications` symlink. What it
had no trace of was a `.background` folder or a `.DS_Store`, so the volume opened with two items in
whatever arrangement Finder chose and no indication of what to do with them.

## 1. Feature Definition & Execution Plan

### Phase 1: find out what actually shipped
*   [x] Mounted the published `v0.4.0` DMG rather than reading the config. It contains
    `Copperplane.app`, an `Applications` symlink and `.VolumeIcon.icns` -- and no background, no
    saved icon layout.
*   [x] Read the DMG options out of the installed CLI's own `config.schema.json` rather than from
    documentation: `background`, `windowSize`, `appPosition`, `applicationFolderPosition`,
    `windowPosition`, with defaults of 660x400 and icons at (180,170) and (480,170).

### Phase 2: the brand tools could not run
*   [x] `brand/tools/build.py` and `render.py` both hardcoded `/home/claude/copperplane/brand` --
    the machine they were written on. `brand/README.md` documents two commands, and neither could
    execute anywhere else. The kit was effectively frozen. Both now resolve from the file's own
    location.
*   [x] `build.py` additionally needs `fontTools` (undocumented) and `render.py` needs `playwright`,
    neither installed here. The background generator therefore imports only `geometry.py`, which is
    pure numbers, and needs neither.

### Phase 3: the background
*   [x] `brand/tools/dmg_background.py`, generated like every other asset. Not a generic arrow: the
    mark is a routed trace broken at 45 degrees with a via at each open end, so the cue is drawn in
    the same language -- a trace leaving a via, ending in an arrowhead under the Applications
    folder. Both icon positions are held clear by 74px.
*   [x] Rendered at 1320x800, twice the window size. Tauri accepts one image rather than a
    multi-representation TIFF, so retina crispness comes from rendering at 2x and letting Finder
    scale down.

### Phase 4: verified by building one
*   [x] Built a real DMG, mounted it, and confirmed `.background/background.png` is byte-identical
    to the generated source and that a 10 KB `.DS_Store` is present -- the saved icon layout that
    was missing before.

## 4. Plan Drift & Architectural Changes

**1. The renderer silently dropped every stroke, and the first two attempts looked like design
problems.** ImageMagick rasterised the background with the mark missing and the trace invisible
while the arrowhead came out bright green. Two different bugs with one cause: its SVG renderer
honours `fill` and ignores `stroke`, and the mark and trace are stroke-only. `rsvg-convert` was
already installed and produced it correctly first time. The lesson is narrow and repeatable: when
one element of a drawing renders and another does not, suspect the renderer before the drawing.

**2. The SVG `mask` had to go, and for the same reason.** The kit's marks punch their via holes with
a `mask`, which is correct SVG that ImageMagick renders as a white rectangle over the artwork.
Since the background is one known solid colour, the holes are overdrawn in the ground colour
instead -- identical output, no dependency on mask support.

**3. I misdiagnosed the build failure last night, and it cost the maintainer a build.**
`ensure_sidecar`'s freeze failed with `[Errno 66] Directory not empty: 'python3.11'`. I concluded
it was my recreating the venv while their build ran, apologised for it, and recorded that as the
cause. It happened again today with nothing else running. The real cause is
`shutil.rmtree` walking a directory while Finder writes a `.DS_Store` back into it -- three of them
were sitting in `.build-venv`, including one in `python3.11/`, the directory the error names.
Retrying the removal fixes it. My apology was sincere and the diagnosis behind it was wrong, which
is worth writing down: a plausible cause that arrives with a confession attached still needs
checking.

**4. `git reset --hard` destroyed the frozen sidecar, exactly as `ensure_sidecar` warns.** Its own
output says "note that `git checkout -- .` would destroy this freeze". Switching branches with a
hard reset does the same thing, and cost a full re-freeze. The warning is right and it is not
prominent enough to survive a busy session.

**5. Not verified: what it looks like when a person opens it.** The background is in the volume,
the layout is saved, and the positions match the drawing. Nobody has double-clicked the DMG and
looked at the window. That is a thirty-second check and it is the only one that matters.
