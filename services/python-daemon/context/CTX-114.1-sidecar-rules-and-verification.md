# CTX-114.1: Implementation Context: Capability Profile Rules and the Verification Run

> **Spec Reference:** Links to [SPEC-114](../specs/SPEC-114-fabrication-capability-profiles.md)

## 1. Feature Definition & Execution Plan

The phase order here is deliberate and inverted from the obvious one. The natural first phase is the
`CapabilityProfile` object, because it is the thing the feature is *about*. It is second.

`SPEC-114` section 2.2, Limit 2 is why: a malformed `.kicad_dru` is discarded **entirely and
silently**, so a generated sidecar cannot be trusted to have taken effect. Writing the file is not
the deliverable; writing it *and proving the rules fired* is. If the verification run is built last,
as a test afterthought, then every phase before it is unfalsifiable — the app would report a
strengthened check while a single typo had quietly disabled every rule in the file. That is the
worst failure this feature could have, and it is the failure that looks exactly like success.

So Phase 1 builds the harness against hand-written sidecars, before any profile exists to generate
one. Everything after it is verifiable the moment it is written.

Verification is cheap because each violation names the rule that produced it, e.g.
`Annular width (rule 'min-annular-ring' min annular width 0.1300 mm; actual 0.0850 mm)`. Asserting a
named rule appears is a substring check, not a parser.

### Phase 1: The verification harness

*   [x] `write_and_verify` in a new `kicad_dru.py`: given a board and a rule set, write the sidecar,
    run DRC, and report which named rules actually fired.
*   [x] Reproduce the measured baseline as a test: the example board with no sidecar yields 4
    `annular_width` violations, so the harness has a known-good floor.
*   [x] Regression test for Limit 2, the silent discard: one valid rule alone fires; the same valid
    rule plus one misspelled constraint name fires **nothing**, and the run still exits 0 with a
    clean stderr. This test asserts the hazard exists, so it fails loudly if a future KiCad fixes it.
*   [x] Same regression for an unclosed parenthesis and an unparseable unit.
*   [x] Regression test for Limit 1, the `ignore` gate: a `track_width` rule produces nothing when
    the project sets that check to `ignore`, and still nothing with an explicit severity in the rule.
*   [x] Every one of the above runs against real `kicad-cli` and skips cleanly when KiCad or the
    example project is absent, matching `test_structural_checks.py`'s existing skip pattern.
*   [x] Unplanned, and the core of the phase: a **canary rule** separating "my rule found nothing"
    from "my file was discarded". Without it the harness cannot tell a compliant board from a
    thrown-away sidecar, and both Deviations below come out of building it.

### Phase 2: The CapabilityProfile record

*   [x] Define the record with per-field provenance — value, source URL, date recorded, user-confirmed
    flag — mirroring the provenance `library_store.py` already enforces on `Part`.
*   [x] Every field optional. An absent field must produce no rule rather than a guess; assert this
    directly rather than trusting it.
*   [x] Record mask dam and mask expansion as fields that are displayed but never enforced, since
    section 2.1 measured no matching DRC constraint class for them.
*   [x] Persist and reload through `library_store.py`, per project rather than per install.

### Phase 3: Profile to rules

*   [x] Generate `.kicad_dru` text for the twelve constraint classes section 2.1 confirmed.
*   [x] Emit generated rules at `(severity warning)`, so the sidecar's findings separate visually
    from KiCad's own errors without inventing a marker (section 2.3).
*   [x] Write only `<project>.kicad_dru`, never a user-authored file. Assert the app refuses to touch
    `.kicad_pro`.
*   [x] Route every write through Phase 1's harness. A write whose rules did not fire is an error the
    user sees, never a silent pass.

### Phase 4: Reporting what could not be checked

*   [x] Read the project's ignored checks and report them rather than presenting a clean result.
    Prefer the DRC report's own `ignored_checks`, which `SPEC-332` already renders.
*   [x] Name the fields recorded but unenforceable, so the gap is stated rather than dropped.

### Phase 5: The before-and-after route

*   [x] One route returning both runs: KiCad defaults versus the chosen profile.
*   [x] Verify the measured headline end to end — 4 findings becoming 27 on the example board, the
    three headline ones landing on D1.
*   [x] Drive the route into the frozen sidecar over JSON-RPC before believing it works, per
    `CLAUDE.md`. The module it was built from is not the artifact that ships.

## 4. Plan Drift & Architectural Changes

*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Deviation 1: the canary was overriding the very rule it existed to verify.** The harness
    appends a canary rule -- an absurd threshold no board satisfies -- so that its presence in the
    report proves the file parsed. The first version put the canary on `track_width` unconditionally.
    Measured: for a given constraint class **the last matching rule wins**, and rules on different
    classes do not interfere. So on any profile that also set `track_width`, the canary silently
    replaced the real rule, which then reported nothing while appearing to run.
    *Fix:* the canary takes a class the profile is not using. When a full profile uses every
    candidate class -- which is the normal case, not an edge case -- verification takes two runs: one
    with the canary to prove the file parses, one without it for the user's real findings. That is
    sound because the verified file is the real file plus a trailing well-formed rule, and removing
    a trailing rule cannot introduce a parse error.

*   **Deviation 2: "an absurdly large minimum always fires" is false, and it failed silently.**
    The canary assumed any constraint set to 500mm would be violated by every feature on the board.
    True for six classes, measured. False for `connection_width`, which fires 4 times at 1mm and
    **zero** times at both 10mm and 500mm. Had it been chosen as a canary, every healthy sidecar
    would have been reported as discarded. `connection_width` is now excluded from the candidate
    list with the measurement written next to it. Note this does not contradict `SPEC-114` section
    2.1, which confirmed the class fires -- it was measured there at a small value.

*   **Deviation 3: the first run of these tests passed while testing nothing.** `OK (skipped=17)` --
    the example-project path was resolved one directory short of the repo root, so every test
    skipped and the suite went green. This is exactly the trap `CLAUDE.md` names: a check that
    cannot fail is not evidence, even when its conclusion looks right. Caught by reading the skip
    reasons rather than the summary line. A `FixturePathGuard` test that never skips is now the
    tripwire, since `examples/` is committed and its absence is always a path bug here.

*   **Prediction 2 held.** The realistic profile returns exactly **27** findings through the real
    code path, with the type breakdown matching `SPEC-114` section 2.4 line for line: `silk_overlap`
    14, `annular_width` 4, `hole_to_hole` 3, `text_thickness` 2, `text_height` 2, `silk_over_copper`
    2. TEST-016 still asserts the shape rather than the total, per the original reasoning.

*   **Deviation 4: a constraint class and the check that gates it are not the same name.** Phase 4
    matched each profile rule's constraint against the project's `rule_severities` keys to report
    what had been switched off. Those keys are KiCad's **violation type** names, not constraint
    names: `hole_size` is gated under `drill_out_of_range`, `edge_clearance` under
    `copper_edge_clearance`, and `silk_clearance` under *two* keys. The check silently missed four
    of ten fields — and its test passed, because the test picked `annular_width`, one of the six
    where the two names happen to coincide. `SPEC-114` section 2.1's own table had the mapping all
    along, in the "violation type KiCad reported" column. Now mapped explicitly, with a test that
    uses `min_drill` precisely because its names differ, and a partial-gating case for
    `silk_clearance`.

*   **Deviation 5: `ignored_checks` entries are objects, not strings.** Assumed to be a list of
    check names; KiCad returns `{"key", "description"}`. Every caller downstream raised
    `TypeError: unhashable type: 'dict'` the first time the real report reached them. The
    descriptions turn out to be worth keeping -- "Footprint has no courtyard defined" says something
    to a user that `missing_courtyard` does not.

*   **Deviation 6: bundled profiles for named board houses were not built, deliberately.** Section
    2.7 asks for starter profiles for the houses makers actually use. Section 2.9 lists getting real
    numbers for real houses as the largest open question in the spec and calls it a research task,
    and section 3 warns that a too-strict profile spends the credibility this family runs on.
    Shipping invented figures under a real vendor's name would have closed that question by
    fabricating it. What ships instead is `fabrication.generic_profile`: an explicitly unbranded
    standard-process starting point, carrying no source URL that claims a vendor published it, with
    every field unconfirmed. The mechanism is complete; the attributed numbers are still the
    research task the spec says they are.

*   **Prediction 1 was wrong, and cheaply so.** It predicted the writer would be hand-generated text
    rather than `kiutils`' `dru.py`. Hand-generated text is what shipped, so the prediction held --
    but the reasoning behind it (that `kiutils` might be unreliable here) was never tested, because
    the grammar turned out to be four lines and no library was needed at all. Right answer, untested
    reason.

*   **Prediction 1, recorded before implementation starts:** the sidecar writer will be hand-generated
    text rather than `kiutils`' `dru.py`. Section 2.5 leaves this open; the grammar is small and
    `kiutils`' `Board().from_file()` already raises `IndexError` on real boards from this machine
    (`CTX-314.1`). If `kiutils` turns out to write cleanly and this prediction is wrong, that belongs
    here as a correction rather than a quiet substitution.
*   **Prediction 2:** TEST-016's count of 27 will hold. It was measured once, on one machine, with
    illustrative profile numbers not sourced to a real house. If the count moves when the numbers are
    replaced with a real profile's, the test asserts the wrong thing and should pin the *shape* — the
    three headline findings landing on D1 — rather than the total.

## 5. What was verified, and what was not

**Verified against the real thing.** Every measurement in this context was taken with real
`kicad-cli` 10.0.3 against a throwaway copy of `examples/Copperplane_Blink_LEDs`; the board in the
repo is never modified by these tests. The full feature was then driven into the **frozen sidecar**
over JSON-RPC, not just exercised from source: `fabrication.review_board` returned `applied`, 4
findings before and 27 after, the five ignored checks named, and nine unconfirmed fields. The probe
carried a negative control -- a deliberately bogus method returning `-32601` -- so a passing result
means the probe could have detected a missing route. Before the rebuild, the committed sidecar
answered `-32601` for exactly these routes, which is `CTX-407.3`'s failure mode reproduced and then
closed.

`TEST-017` now automates that check. `CTX-407.4` section 4 recorded as still open that every sidecar
checkpoint *inspects* the binary and none *runs* it; this is one route's worth of that gap closed,
not the general checkpoint `SPEC-407` still wants.

**Not verified.**

*   **One machine, one board, one KiCad.** Every constraint-class measurement is macOS aarch64,
    KiCad 10.0.3, and the tutorial board. Nothing has been re-run on Windows or Linux, or against
    KiCad 9 or 11. `SPEC-403` owns that gap and the constraint table is the first thing to re-run.
*   **No user has used this.** There is no UI. `SPEC-114` section 5 describes a user choosing a
    board house per project and seeing the difference that choice made, and none of that surface
    exists -- these are daemon routes only. Under this repo's own norm ("verify as the user, not
    just as the capability", written after `SPEC-302` shipped), this feature is **not** verified.
    The UI belongs to a separate `apps/tauri-ui` context, and this one should not be read as having
    delivered it.
*   **No real board house's numbers.** See Deviation 6. The bundled profile is unbranded on purpose.
*   **`via_diameter` and `thermal_spoke_width` remain untested**, because the example board has no
    vias and no zones. They are excluded from the confirmed list rather than assumed working.
