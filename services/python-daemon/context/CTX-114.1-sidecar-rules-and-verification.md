# CTX-114.1: Implementation Context: Capability Profile Rules and the Verification Run

> **Spec Reference:** Links to [SPEC-114](../specs/SPEC-114-fabrication-capability-profiles.md)

## 1. Feature Definition & Execution Plan

The phase order here is deliberate and inverted from the obvious one. The natural first phase is the
`CapabilityProfile` object, because it is the thing the feature is *about*. It is second.

`SPEC-114` section 2.2, Limit 2 is why: a malformed `.kicad_dru` is discarded **entirely and
silently**, so a generated sidecar cannot be trusted to have taken effect. Writing the file is not
the deliverable; writing it *and proving the rules fired* is. If the verification run is built last,
as a test afterthought, then every phase before it is unfalsifiable — the app would report a
strengthened check while a single typo had quietly disabled every rule in the file. That is the
worst failure this feature could have, and it is the failure that looks exactly like success.

So Phase 1 builds the harness against hand-written sidecars, before any profile exists to generate
one. Everything after it is verifiable the moment it is written.

Verification is cheap because each violation names the rule that produced it, e.g.
`Annular width (rule 'min-annular-ring' min annular width 0.1300 mm; actual 0.0850 mm)`. Asserting a
named rule appears is a substring check, not a parser.

### Phase 1: The verification harness

*   [ ] `dru_verify` in a new `kicad_dru.py`: given a board, a written sidecar, and the rule names it
    should contain, run DRC and report which named rules actually fired.
*   [ ] Reproduce the measured baseline as a fixture-backed test: the example board with no sidecar
    yields 4 `annular_width` violations, so the harness has a known-good floor.
*   [ ] Regression test for Limit 2, the silent discard: one valid rule alone fires; the same valid
    rule plus one misspelled constraint name fires **nothing**, and the run still exits 0 with a
    clean stderr. This test asserts the hazard exists, so it fails loudly if a future KiCad fixes it.
*   [ ] Same regression for an unclosed parenthesis and an unparseable unit.
*   [ ] Regression test for Limit 1, the `ignore` gate: a `track_width` rule produces nothing when
    the project sets that check to `ignore`, and still nothing with an explicit severity in the rule.
*   [ ] Every one of the above runs against real `kicad-cli` and skips cleanly when KiCad or the
    example project is absent, matching `test_structural_checks.py`'s existing skip pattern.

### Phase 2: The CapabilityProfile record

*   [ ] Define the record with per-field provenance — value, source URL, date recorded, user-confirmed
    flag — mirroring the provenance `library_store.py` already enforces on `Part`.
*   [ ] Every field optional. An absent field must produce no rule rather than a guess; assert this
    directly rather than trusting it.
*   [ ] Record mask dam and mask expansion as fields that are displayed but never enforced, since
    section 2.1 measured no matching DRC constraint class for them.
*   [ ] Persist and reload through `library_store.py`, per project rather than per install.

### Phase 3: Profile to rules

*   [ ] Generate `.kicad_dru` text for the twelve constraint classes section 2.1 confirmed.
*   [ ] Emit generated rules at `(severity warning)`, so the sidecar's findings separate visually
    from KiCad's own errors without inventing a marker (section 2.3).
*   [ ] Write only `<project>.kicad_dru`, never a user-authored file. Assert the app refuses to touch
    `.kicad_pro`.
*   [ ] Route every write through Phase 1's harness. A write whose rules did not fire is an error the
    user sees, never a silent pass.

### Phase 4: Reporting what could not be checked

*   [ ] Read the project's ignored checks and report them rather than presenting a clean result.
    Prefer the DRC report's own `ignored_checks`, which `SPEC-332` already renders.
*   [ ] Name the fields recorded but unenforceable, so the gap is stated rather than dropped.

### Phase 5: The before-and-after route

*   [ ] One route returning both runs: KiCad defaults versus the chosen profile.
*   [ ] Verify the measured headline end to end — 4 findings becoming 27 on the example board, the
    three headline ones landing on D1.
*   [ ] Drive the route into the frozen sidecar over JSON-RPC before believing it works, per
    `CLAUDE.md`. The module it was built from is not the artifact that ships.

## 4. Plan Drift & Architectural Changes

*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Prediction 1, recorded before implementation starts:** the sidecar writer will be hand-generated
    text rather than `kiutils`' `dru.py`. Section 2.5 leaves this open; the grammar is small and
    `kiutils`' `Board().from_file()` already raises `IndexError` on real boards from this machine
    (`CTX-314.1`). If `kiutils` turns out to write cleanly and this prediction is wrong, that belongs
    here as a correction rather than a quiet substitution.
*   **Prediction 2:** TEST-016's count of 27 will hold. It was measured once, on one machine, with
    illustrative profile numbers not sourced to a real house. If the count moves when the numbers are
    replaced with a real profile's, the test asserts the wrong thing and should pin the *shape* — the
    three headline findings landing on D1 — rather than the total.
