# CTX-208.3: Implementation Context: Capability Declarations & Preflight

> **Spec Reference:** Links to [SPEC-208](../specs/SPEC-208-provider-records-and-model-roles.md)

Phase 3 of 3 (SPEC-208 §4's own module map) -- the last phase of SPEC-208. Eleven of the twelve
prompt files gain a real `requires:` declaration (`tool_use` or `strict_json`); `resolve()` checks
it against the resolved record's own `capabilities` before constructing any provider client, raising
a `LLMProviderError` naming the agent, the missing requirement, and the record on a mismatch --
never a silent degrade into an ungrounded answer or empty JSON. Also fixes a real gap CTX-208.2 left
behind: `datasheet_guidance.py` has its own separate call chain into `component_pipeline
._build_agent_executor` that never got `app_config`/`model_role` threaded through in that phase.

## 1. Feature Definition & Execution Plan

### Phase 1: `requires:` declarations, based on what each agent's prompt body actually needs
*   [x] **`requires: [tool_use]`** -- the five `chat_*` agents (all five declare real `tools:` in
    their own frontmatter already).
*   [x] **`requires: [strict_json]`** -- `board_advisor`, `component_extraction`, `component_search`,
    `connection_guidance`, `datasheet_guidance_extraction`, `footprint_query_suggestion`. Verified
    per file, not assumed from SPEC-208's own rough heuristic ("respond with ONLY"): a
    line-wrap-and-case-insensitive search initially over-matched
    `datasheet_guidance_synthesis.prompt.md` too (it does say "Respond with ONLY the paragraph
    itself"), but its real downstream consumer (`datasheet_guidance._run_synthesis_workflow`)
    returns `synthesize_output.text.strip()` directly -- no JSON parsing anywhere. `requires: []`
    (absent) is correct for it; the phrase describes "no wrapper prose", not "must be valid JSON",
    and the spec's own heuristic isn't a reliable proxy for the real requirement.
*   [x] `agent_roles.py` needed no changes -- CTX-208.2 already built `requires` parsing/validation
    into the sidecar (SPEC-208 §2.3.3's own text keeps `model_role`/`requires` together), it simply
    had nothing real to return until this phase's frontmatter edits landed.

### Phase 2: the preflight check itself
*   [x] `_check_capabilities(agent_name, requires, record)` in `llm_providers.py` -- checks each
    entry in `requires` against `record["capabilities"]`; a `False`/absent capability raises
    `LLMProviderError` naming the agent, every missing requirement, and the record's id.
*   [x] `resolve()` gained `agent_name`/`requires` parameters and calls `_check_capabilities` after
    the record and model are resolved, before `_build_provider_from_record` -- "before the first
    call", never after a client already exists.
*   [x] **Deliberate deviation from the spec's literal cache key** (Plan Drift Deviation 1): cached
    per `(record_id, agent_name)`, not `(record, role)` -- this repo's own real data proves two
    agents sharing a role do not necessarily share `requires` (every `fast`-role `chat_*` agent
    needs `tool_use`; `datasheet_guidance_synthesis`, also `fast`, needs nothing), so a
    `(record, role)` cache would let one agent's passing check wrongly exempt a different agent's
    real, unchecked requirement against the same record. Proven with a real regression test
    (`test_007_caching_is_per_agent_not_per_role_or_record_alone`).
*   [x] Both callers (`chat_agents._dispatch`, `component_pipeline._build_agent_executor`) already
    look up the agent's own role via `agent_roles.load_agent_roles` (CTX-208.2) -- this phase adds
    `agent_name=`/`requires=agent_role.get("requires")` to their existing `resolve()` calls.

### Phase 3: the real gap CTX-208.2 left in `datasheet_guidance.py`
*   [x] **Found while auditing every real caller of `_build_agent_executor` for this phase, not
    assumed complete from CTX-208.2's own claim.** `datasheet_guidance.py` imports
    `component_pipeline._build_agent_executor` directly and calls it at two sites
    (`_run_category_workflow`, `_run_synthesis_workflow`) -- neither gained `app_config` in
    CTX-208.2, and `daemon.py`'s own `datasheet_generate_guidance` route never passed one either.
    Since `daemon.py` already threads an explicit `provider`/`model` override from
    `CONFIG.get("llm_provider")`/`["llm_model"]` into this path (resolution order step 1, unaffected
    by role), a *configured* install was never actually broken by this gap -- but an unconfigured
    one, or a future `provider_roles`-only config with no legacy fields set, would have silently
    ignored real Settings/role state for these two agents specifically.
*   [x] `app_config` threaded through the whole chain: `generate_datasheet_guidance` ->
    `_run_all_categories_and_close` -> `_run_category_workflow`/`_run_synthesis_workflow` ->
    `_build_agent_executor`; `daemon.py`'s `datasheet_generate_guidance` route now passes
    `app_config=CONFIG`.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the preflight cache is keyed on `(record_id, agent_name)`, not the spec's own
    literal `(record, role)` phrasing.**
    *   *Reasoning:* SPEC-208 §2.4 says "before the first call of a session for a given (record,
        role) pair" -- but this repo's own real data disproves role as a safe proxy for identical
        requirements: every `fast`-role `chat_*` agent needs `tool_use`, while
        `datasheet_guidance_synthesis` (also `fast`) needs nothing. A `(record, role)` cache would
        let checking the synthesis agent first silently exempt a real chat agent's own, different,
        unchecked requirement against the same record.
    *   *Impact:* caching per `(record_id, agent_name)` instead -- strictly more granular, satisfies
        the same "don't recheck every single call" goal the spec's own cache is for, and is
        impossible to under-check relative to the spec's literal wording. Proven with a dedicated
        regression test (`TEST-007`) rather than just asserted.
*   **Deviation 2: a real gap in CTX-208.2's own wiring, found while auditing this phase rather than
    assumed already complete.** `datasheet_guidance.py`'s own separate call chain into
    `component_pipeline._build_agent_executor` never received `app_config`/`model_role` in
    CTX-208.2 -- see Phase 3 above for the full mechanism and why a *configured* install was never
    actually affected (the explicit `provider`/`model` override path already carried the right value
    through).
    *   *Reasoning:* CTX-208.2's own Testing Requirements Matrix asserted "every pre-existing
        chat_agents/component_pipeline test... unaffected", which was true but incomplete --
        `datasheet_guidance.py` is a third module with its own direct import of
        `_build_agent_executor`, not exercised by either of those two test files, and nothing in
        this repo's test suite asserted `app_config` reaches it.
    *   *Impact:* fixed in this phase (Phase 3) rather than left for later, since it directly serves
        this phase's own goal (role/config resolution must actually reach every real agent, not just
        the ten reachable through `chat_agents.py`/`component_pipeline.py`'s own top-level entry
        points). Recorded here as an honest correction to a prior context's claim, per this repo's
        own norm that a Plan Drift entry documenting a real miss is more valuable than a clean
        record.
