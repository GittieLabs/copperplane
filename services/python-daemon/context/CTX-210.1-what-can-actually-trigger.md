# CTX-210.1: What Can Actually Trigger

> **Spec Reference:** Links to
> [SPEC-210](../specs/SPEC-210-design-considerations-model.md)

## 1. Feature Definition & Execution Plan

`SPEC-210` generalises what this project has now built by hand five times — `SPEC-113` for
structural defects, `SPEC-332` for ERC, `SPEC-334` for footprints, `SPEC-114`/`340`/`342` for
manufacturability, `SPEC-328` for intent. Each has its own findings shape, its own glossary, its own
explanation call. `SPEC-210` is the spec that says stop doing that one at a time, and it carries the
computed/cited/judgement discipline those five have kept by convention rather than by mechanism.

Its safety property is one sentence, §2.2: **no consideration exists without a trigger that names
something real in the project.** Everything else rests on that. Without it the family degenerates
into a generative best-practices essay, which is exactly what a language model produces fluently and
wrongly.

So the question this context has to answer first is not how to model a consideration. It is whether
there is enough computable signal in a real project to trigger one at all. If the answer is "almost
nothing", then the computed and cited classes are empty, every consideration is a judgement, a
judgement may not be raised unprompted (§1's initiative rule) — and the whole family collapses into
the chat surface that already exists. That is much cheaper to find out now.

### Phase 1: Find out what can actually trigger, before modelling anything — DONE

*   [x] Enumerate what the app already holds about a real project, from the real routes rather than
        from reading the code: board components with positions and footprints, schematic components,
        ERC and DRC findings, `structural_checks` output, `intent` and `intent_fields`, the chosen
        board house.
*   [x] For each, state concretely what consideration it could trigger and in which claim class.
        Named triggers only — *"a part"*, *"a net"*, *"a stated intent field"* — per §2.1.
*   [x] Run it against the maintainer's own board, the one the whole family is written about, and
        **count what triggers and what does not.**
*   [x] Judge against a bar written down before the run: is there enough computed and cited signal
        to justify a category, or is this a chat feature wearing a framework's clothes?
*   [x] Write the finding into `SPEC-210` §2, including if it says build less.

### Phase 1b: The netlist read the measurement turned up — DONE

*   [x] `kicad_cli.export_netlist` — `sch export netlist --format kicadxml`, beside the DRC and ERC
        exports that module already owns.
*   [x] **`kicadxml`, not the default s-expression netlist.** The XML parses with the standard
        library; the s-expression form would need a second parser beside `kicad_board`'s.
*   [x] Keeps KiCad's own **pin electrical type** (`power_in`, `passive`, `bidirectional`). Not in
        the plan, and it matters: *"this power pin"* is a different claim from *"this pin"*, and the
        distinction is the file's rather than an inference of ours.
*   [x] Zero nets fails loudly. A schematic with components always has nets, so an empty return is a
        format this app cannot read — and it would read to a user as *"nothing on your board is
        connected"*, the most alarming available way to be silently wrong.
*   [x] A node with no reference is dropped rather than carried as `None`: a node naming nothing
        cannot anchor a claim, so it must not reach a caller looking like one.

### Phase 2: The record, with the trigger discipline enforced rather than described

*   [ ] `considerations.py` — the record `SPEC-210` §2.1 describes: `id`, `domain`, `claim_class`,
        `trigger`, `source`, `explanation`, `arithmetic`, `state`.
*   [ ] **A consideration with no trigger is refused at construction.** §2.2 is the safety property;
        a rule written only in prose is one the next caller bypasses, which is what `SPEC-342` §2.6
        and `CTX-326.4` both learned the expensive way.
*   [ ] `source` required for `cited`, refused for `computed` — §2.1 says empty is legal only for a
        computed claim, so the validator enforces both directions.
*   [ ] Inherits `SPEC-113`'s `copperplane.` type prefix, so a consideration is visibly this app's
        own and never mistaken for KiCad's.

### Phase 3: The initiative rule

*   [ ] A `computed` or `cited` consideration may be raised unprompted. A `judgement` may not.
*   [ ] Enforced at the point of raising, not left to each caller: §1 makes this the line between
        `SPEC-113` correctly volunteering D1 and the same surface volunteering *"you should use a
        switching regulator here"*.
*   [ ] A judgement is still reachable when the user asks — the rule is about initiative, not about
        hiding it.

### Phase 4: State, storage, and not asking twice

*   [ ] `raised`, `answered`, `satisfied`, `dismissed` with a reason, persisted on the project.
*   [ ] **Settles §2.6's storage question, which `SPEC-113` left open for structural findings.**
        The two are answered together per that spec's own instruction, not separately.
*   [ ] Reuses `SPEC-339`'s staleness mechanism for a dismissal that a design change makes relevant
        again. §2.6 says explicitly: reuse it rather than inventing a second one.

### Phase 5: One real pack, proving the second is data

*   [ ] One domain, built as `SPEC-210`'s goal describes — *"adding a second and third subject area
        is a data file and a trigger rather than a rebuild"*.
*   [ ] **Fixtures broken on purpose**, committed, in the way `parity_match.kicad_pcb` already
        serves the board reader. §3 names this as a real work item with real effort, not a footnote:
        without it a pack can only be tested when a user happens to have the bug.
*   [ ] False positives counted against a real board, per §3's bar — *"measurement against a real
        board with its false positives counted, not plausibility"*.

### Phase 6: The surface — deliberately not planned yet

`SPEC-210` §2.6 asks what a question *is* as a surface, and warns that a third shape would repeat
`SPEC-328`'s own warning about adding a fifth. Planning that now means planning against Phase 1's
result before it exists — the `CTX-341.1` mistake, made deliberately there and worth not repeating
here. The likeliest answer is already written in §2.6 (answerable cards in the review, turns in
chat, one shared record) and it stays a proposal until Phases 1 through 5 have run.

## 4. Plan Drift & Architectural Changes

*   **Prediction 1 was wrong, and wrong in the direction that makes this spec more viable.** I
    predicted the computed half would be thin, because concluding anything needs net topology that
    "neither the board file nor the datasheet pipeline currently yields in a usable form."

    The board file does not. **`kicad-cli` does**, and it takes one command:
    `sch export netlist --format kicadxml` returns 33 nets on the maintainer's board with full
    `ref.pin` nodes, including `Net-(D1-A)` joining `D1.2` to `R1.1` — the *"does this LED have a
    series resistor"* fact, as a file fact rather than a model's opinion.

    I had checked `kicad_board`, `structural_checks` and both component readers and found no net
    anywhere, which is true and was the wrong place to stop. The right question was not *"does the
    app hold connectivity"* but *"can it get it"*, and I only asked the second because the first
    answer would have killed `SPEC-211` and that seemed too convenient.

    The practical consequence: topology considerations are **unbuilt, not blocked**. A netlist read
    becomes a prerequisite this context did not know it had — one `kicad-cli` call and an XML parse,
    belonging in `kicad_cli.py` beside the DRC and ERC exports it already owns.

*   **`lib_id` is a functional taxonomy and nothing was using it as one.** The eleven symbols read
    `Device:LED`, `Device:R`, `Switch:SW_Push`, `power:+5V`, `MCU_Module:Arduino_UNO_R3`,
    `Mechanical:MountingHole`. KiCad's own classification of what a part *is*, in a file the app
    already parses, and a **computed** fact in §2.1's sense — read, not inferred.

    `SPEC-210` §1's worked example needs exactly two facts — *"you are powering this from USB"* and
    *"you have twelve LEDs"* — and both are computable **today**, without the netlist: the second
    from `lib_id`, the first from `input_supply`. The spec's own illustration turns out to be its
    cheapest possible first pack.

*   **(Original wording of Prediction 1, for the record)** The computed half will be thinner than
    the spec assumes, and the questions will carry it. `SPEC-210` §1 says the interesting output shape is the question, not the finding,
    and I expect Phase 1 to make that concrete in an uncomfortable way — that the app holds plenty
    to *ask* about and little to *conclude* from, because concluding needs electrical facts
    (net topology, part function, current draw) that neither the board file nor the datasheet
    pipeline currently yields in a usable form.

    If that is right, the honest shape is smaller than a framework: a question mechanism with a
    small computed core, rather than a consideration engine with packs. Recorded before the run.

*   **Prediction 2, still open.** `board_stage` may be the highest-value field in the family, and it
    already exists. §1's scope rule — a board built for yourself does not get warned about a
    connector nobody else will touch — is the only mechanism in the product that changes what gets
    said based on a user's declared goal. `CTX-328.1` Phase 2 shipped that field. If Phase 1 finds
    little else to trigger on, this one field plus the intent set may be most of what the family
    actually has.


*   **The calculators are the bridge, and the maintainer saw it before I did.** Asked while looking
    at KiCad's own Calculator Tools: *"would these tie into what we get from the netlists?"*

    They do, and it changes what a pack is. Measuring the board file for the answer turned up more
    than connectivity: every routed segment carries `(width …) (layer …) (net "…")` with real
    endpoints, so per-net width, layer and length are computed facts. On the maintainer's board,
    `GND` is 21.50 mm at 0.2 mm, `Net-(A1-D3)` 38.99 mm at 0.2 mm.

    What is missing is **current**, and it is missing from the files rather than from the parser.
    KiCad's calculators — IPC-2221 track width and spacing, via current, fusing current — are the
    standards formulas that turn geometry into an answer, which makes them this spec's `cited` class
    and puts them in §2.1's `arithmetic` field.

    So the loop is: netlist says `+5V` reaches these pins (computed) → board says routed at 0.2 mm
    (computed) → **question** asks what current this board draws (the user answers) → calculator
    gives the standard's minimum width (cited) → a claim about this board with its arithmetic shown.

    **Step three is why the question mechanism is not decoration.** The calculators cannot run
    without a current, the files do not contain one, and asking is the only honest way to get it.
    Written into `SPEC-210` as §2.0.1, including the correction it implies: a pack is a trigger, a
    formula **and** a shown calculation, where §2.1 reads as though `arithmetic` were an optional
    extra.

*   **A constraint recorded before anyone builds on it.** A trace-width number is a `cited` claim and
    its constants must be read from the standard, never recalled. I know IPC-2221's shape and not its
    exponents to the precision a real claim needs. §3 says the first time this app is confidently
    wrong about a board the user understands better than it does, the whole family is spent — and a
    plausible formula with a misremembered exponent is the likeliest way to spend it.

*   **What was not verified.** `export_netlist` is exercised against `parity_match.kicad_sch` and the
    maintainer's own board, both on macOS with KiCad 10. The `kicadxml` shape is a CLI contract that
    can change between KiCad majors, which is why an unrecognised shape raises rather than returning
    an empty list — the same rule `export_schematic_bom` already states, and the mutation check
    confirms it fails when that guard is removed.
