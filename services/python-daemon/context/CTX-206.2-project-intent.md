# CTX-206.2: Implementation Context: Project Intent

> **Spec Reference:** Links to [SPEC-206](../specs/SPEC-206-agent-context-store.md)

**Scope note:** the second slice of `SPEC-206`, scoped to exactly §2.1 -- the optional `intent`
field on the Project record, its round trip through the existing `save_project`/`load_project`
directory-aware routing (`CTX-312.1`), and the new `project.set_intent` route. Deliberately does not
touch the frontend project-creation form or Overview's editable summary surface `SPEC-318` §2.4
describes -- those are real, separate UI work with no daemon-side dependency left once this record
exists. Chosen as the next slice after `CTX-206.1` for the same reason: small, self-contained,
testable with no agent, chat surface, or index involved.

## 1. Feature Definition & Execution Plan

### Phase 1: Storage layer (`library_store.py`)
*   [x] `_validate_project_intent` -- a real, minimal type check (`str | None`); no structured shape
    to validate, unlike `design_guidance`/`connection_guidance`.
*   [x] `_backfill_project_intent` -- `setdefault("intent", None)`, wired into `save_project`'s
    returned record (backfilled *before* writing, so even a fresh save writes the key explicitly,
    matching `_backfill_design_guidance`'s own convention) and both of `load_project`'s two real
    return paths (linked and unlinked -- confirmed by reading the function in full, not assumed
    single-exit).
*   [x] `set_project_intent(name, intent)` -- loads the project fresh, sets `intent`, delegates to
    `save_project`, inheriting `CTX-312.1`'s real pointer/manifest routing for free rather than
    re-deriving it. No special handling needed to keep `intent` out of the storage-root pointer for a
    *linked* project -- `save_project`'s pointer branch already hard-codes exactly
    `{name, directory, schema_version}`, confirmed by reading it, not assumed.

### Phase 2: Route (`daemon.py`)
*   [x] `project_set_intent(name, intent)` -- thin wrapper, matching every other `project.*` route's
    convention; registered as `project.set_intent`, synchronous (not `ASYNC_ROUTES` -- fast local
    file I/O, no LLM call, unlike `SPEC-206`'s later `chat.send`).

### Phase 3: Tests
*   [x] `tests/test_library_store.py`: `TestProjectIntent` -- backfill-to-`None`, a real intent
    string round trip, rejects a non-string/non-null value, `None` vs. `""` stay distinguishable,
    `set_project_intent` persists and preserves the record's other fields. `TestProjectDirectoryLink`
    gained a test confirming a linked project's intent lands in the real manifest, not the pointer.
    One pre-existing test (`test_003_an_unlinked_project_still_behaves_exactly_as_before_ctx_312_1`)
    updated for real -- its exact-dict-equality assertion needed the new backfilled `intent: None`
    key, the same class of collateral update `CTX-205.4`'s own design_guidance backfill caused.
*   [x] `tests/test_daemon.py`: `TestProjectSetIntentRoute` -- persists for real, registered as a
    synchronous (not async) route.
*   [x] Full suite: `python3 -m unittest discover tests` -- **504 passed, 6 skipped**, 0 failures.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (non-deviation, confirmed as designed): `load_project`'s backfill is applied at
    both of its two real return points, not refactored into a single exit.**
    *   *Reasoning:* `load_project` has two genuinely different return paths -- an unlinked project
        returns the pointer record directly; a linked one reads the full manifest from its own real
        directory. Restructuring the function into a single exit point purely to apply one backfill
        call would be an unrelated refactor of an already-working, already-tested function, for no
        behavioral gain. Wrapping the return value at each of the two real sites (`_backfill_project_
        intent(pointer)` / `_backfill_project_intent(record)`) is the smaller, more reviewable change,
        matching this repo's own "don't design for hypothetical future requirements" norm.
    *   *Impact:* None on correctness -- both real paths are directly tested
        (`TestProjectDirectoryLink`'s linked-path tests, `TestProjectIntent`'s unlinked-path tests).
