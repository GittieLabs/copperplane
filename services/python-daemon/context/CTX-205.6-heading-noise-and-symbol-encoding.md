# CTX-205.6: Heading Noise & Symbol Encoding Fixes

> **Spec Reference:** Links to [SPEC-205](../specs/SPEC-205-datasheet-design-guidance.md)

## 1. Feature Definition & Execution Plan

Two more real, mechanical bugs found by the user's own continued live use of `CTX-205.4`'s shipped
UI against the real ATtiny85 datasheet, after `CTX-205.5` fixed the JSON-truncation crash: a
garbled degree sign in the "Absolute Maximum Ratings" citations, and a "Power" section built
entirely from meaningless pin-listing labels ("1.1.1 VCC Supply voltage.", "1.1.2 GND Ground.").
Both root-caused against the real document, not guessed at.

**Bug 1, confirmed by direct inspection of the real extracted text**: the real ATtiny85 datasheet's
embedded font places the degree sign at PDF Private Use Area codepoint `U+F0B0` (the classic Adobe
Symbol-font "degree" slot, shifted into the PUA -- a real, common consequence of a font with no
`ToUnicode` CMap entry for that glyph). `pdfplumber` surfaces the raw codepoint rather than "°", so
a real citation like "-55°C to +125°C" came back as raw PUA characters and rendered as
replacement-character boxes in the UI (exactly what the user's screenshot showed). Fixed narrowly:
`_normalize_pdf_text` substitutes this one, unambiguous, high-frequency codepoint at extraction
time, so every downstream consumer (citation quotes, structure-pass keyword matching) sees "°".
**Deliberately not generalized**: a broader scan of the same real document found several other real
PUA codepoints (register-transfer arrows, multiplication dots, in the "Instruction Set Summary"
section -- `←`, `·`, `Ω`, `Δ`) that are real but lower-confidence without a full Adobe Symbol
encoding table, and none of them appear on any page this module's own candidate-section logic
actually surfaces to a user -- fixing them now would be speculative, unverified work against pages
nothing in this pipeline ever reads.

**Bug 2, confirmed by directly running the real structure pass against the real document**: the
"power" category's *only* heading match anywhere in the whole 234-page, 286-heading document was
`"1.1.1 VCC"` -- a single pin-name entry from the real `"1.1 Pin Descriptions"` listing, not a
narrative section. Since `CTX-205.5`'s own heading-based section logic extends a match from its
heading's page up to the next real heading anywhere, the entire "power" candidate section was built
from that one pin label with essentially nothing else in the excerpt, so the extraction LLM had
nothing real to cite except the label itself. Measured, not assumed, before designing a fix: bucketed
all 286 real detected headings and found exactly 8 are a single all-caps word -- `VCC`, `GND` (x2),
`RESET`, `SLEEP`, `LSB`, `N/A`, `S8S1` -- and every one is a pin name, an instruction mnemonic (from
the Instruction Set Summary), or a stray table-cell fragment, never a real section title (which in
this document is always a Title Case phrase of two or more words: "Reset Sources", "Clock Systems
and their Distribution"). Fixed by excluding single-all-caps-word headings from `_find_headings`'s
output entirely (`_is_catalog_entry_title`) -- a category whose only heading match was one of these
now correctly falls back to the real per-page keyword search instead, same treatment as a category
with no heading match at all.

**Real, measured result against the same real document, verified end-to-end with a real Anthropic
call**: "power" now returns 5 real cited items instead of 2 pin labels, including real prose about
keeping RESET active during low-supply-voltage conditions (p19) -- still includes one lower-value
item (the bare "1.1.1 VCC / Supply voltage." label itself, since the fallback keyword scan still
matches its own literal "VCC" text) and one borderline-generic overview quote (p4), named honestly
below rather than silently claimed as fully solved. "Decoupling" correctly returned an empty result
-- its one fallback candidate page (an ADC block-diagram figure) was correctly rejected by the
extraction LLM's own relevance filter, which is the real, working safety net this fix relies on for
the fallback path's remaining noise, not a second bug.

**A larger, real, NOT-solved-here question, surfaced by the same live testing and explicitly
deferred, not silently absorbed into this fix**: the user's own direct feedback is that even
*correct*, well-cited Class B prose is not actually useful to this feature's real target audience --
a maker/hobbyist, not a practicing hardware engineer -- because raw datasheet citations are still
dense, technical, and (per a further real finding during this session's own live verification)
sometimes garbled by subscript-variable line-wrapping (`"V RESET Pin Threshold Voltage V = 3V 0.2 V
0.9 V V\nRST CC CC CC"`, real text extracted from p165 -- `pdfplumber`'s non-layout-aware extraction
splits a subscripted variable like V_CC across separate lines). This is a real, open product
question (does the guidance panel need a synthesis/plain-language layer on top of Class B citations,
not just cleaner citations) that this context does **not** attempt to answer -- named honestly here
as the next real decision point, to be taken up with the user directly rather than guessed at
unilaterally, since it changes SPEC-205's own Class A/B/C contract, not just this module's
mechanics.

### Phase 1: `datasheet_structure.py` -- symbol encoding fix
*   [x] `_PUA_CHARACTER_SUBSTITUTIONS` -- a real, narrow, single-entry substitution table (`U+F0B0`
    -> `°`), applied at extraction time via `_normalize_pdf_text`.
*   [x] `extract_pages` calls `_normalize_pdf_text` on every real extracted page's text.

### Phase 2: `datasheet_structure.py` -- catalog-entry heading exclusion
*   [x] `_is_catalog_entry_title(title) -> bool` -- a single all-caps word is a real pin
    name/instruction mnemonic/table fragment, never a real section title in this document class.
*   [x] `_find_headings` excludes a catalog-entry title from its real output.

### Phase 3: tests
*   [x] `tests/test_datasheet_structure.py`: `TestNormalizePdfText` (a real PUA degree-sign
    codepoint is normalized; ordinary text is untouched), `TestIsCatalogEntryTitle` (a single
    all-caps word is a real catalog entry; a real multi-word Title Case section title is not; a
    real multi-word all-caps title is deliberately left alone, not guessed at with a broader rule),
    and a new `TestLocateCandidateSectionsHeadingBased` case proving a catalog-entry heading no
    longer hijacks a real section range -- it falls back to the real per-page keyword search
    instead, matching a category with zero heading matches.

## Verification
- `services/python-daemon/.venv/bin/python3 -m unittest tests.test_datasheet_structure -v` -- 26/26
  real and passing.
- `services/python-daemon/.venv/bin/python3 -m unittest tests.test_datasheet_guidance -v` -- 17/17
  real and passing, unaffected by this fix.
- **A real, live, full end-to-end run against the actual, user-provided `ATTINY85-20PU.pdf`** (234
  real pages, not committed -- copyrighted vendor content, verified locally only): confirmed the
  real degree sign now renders correctly ("-55°C to +125°C") and "power" now returns 5 real cited
  items instead of 2 meaningless pin labels.
- **Named, honest, real limitations not fixed here, left for a future pass**:
  1. The "power" category's fallback keyword scan still re-includes the bare "1.1.1 VCC / Supply
     voltage." pin label itself (since its own literal text still matches the keyword pattern) and
     one borderline-generic overview quote -- reduced noise, not eliminated.
  2. Subscripted variable names (`V_CC`, `V_RST`, `V_POT`) extract with the subscript wrapped onto a
     separate line, garbling some real quotes on pages like 165 -- a `pdfplumber` layout-extraction
     limitation, not attempted here.
  3. The larger "is verbatim Class B citation the right shape for a hobbyist audience" question
     (§1 above) is real, open, and explicitly deferred to a direct conversation with the user, not
     answered by this context.
