# CTX-109.4: Enclosure .glb unit-scale fix: found while investigating SPEC-311's board-overlay idea

> **Spec Reference:** Links to [SPEC-109](../specs/SPEC-109-parametric-enclosure-generator.md)

Found while investigating a real user follow-up question for `SPEC-311` (not yet implemented): could
the real, assembled board (via `kicad-cli pcb export glb`) be shown *inside* the generated enclosure,
as a visual fit check? Testing whether the two `.glb` files could actually share a scene surfaced a
real, independent, previously-unnoticed bug in the shipped enclosure pipeline: `freecad_bridge.py`'s
build scripts write real millimeter values (`box.Height = {height}`, etc.) directly, with no unit
conversion, into the intermediate `.stl`; `.stl` itself carries no unit metadata, so `trimesh` reads
those numbers as bare floats when converting to `.glb`. glTF's own spec fixes its base unit at
meters — so a real 20mm-tall enclosure has always been exported as a `.glb` reporting a 20 *meter*
tall object, 1000x too large relative to the format's own real scale. Purely cosmetic on its own
(`EnclosureViewer`'s camera was evidently tuned empirically around this same wrong scale, so the
single-model viewer has always looked correct) — but a real, confirmed blocker to ever compositing
this output with any other, correctly-scaled real-world model in the same scene, which is exactly
what `SPEC-311`'s own board-overlay idea needs. Verified live (see this session's own investigation,
recorded in `SPEC-311` §2): applying a `0.001` scale correction to the loaded mesh before `.glb`
export produces a real, correct bounding box (a real enclosure came back as `54.50 × 111.50 × 20.00mm`
after the fix, versus `54500 × 111500 × 20000mm` before it).

## 1. Feature Definition & Execution Plan

### Phase 1: real investigation before writing any code
*   [x] Confirmed live, not assumed: loaded an already-generated (buggy) enclosure `.glb`, applied
    `scene.apply_scale(0.001)`, re-exported it, and re-loaded the fresh export to confirm the
    correction survives a real round trip -- `54.50 × 111.50 × 20.00mm`, matching the real input
    dimensions.
*   [x] Confirmed the fix's blast radius is exactly one line: `freecad_bridge.py`'s `.step` export
    is unaffected (FreeCAD exports it directly from the same mm-native document, and STEP embeds
    its own real unit, so any real STEP reader already interprets it correctly) -- only the derived
    `.glb` conversion path needed correction.

### Phase 2: the fix
*   [x] `freecad_bridge.py`'s `generate_enclosure`: `mesh.apply_scale(0.001)` added between
    `trimesh.load(stl_path)` and `mesh.export(glb_path)`, with a comment naming the real bug, why
    it was invisible until now, and why `.step` doesn't need the same fix.

### Phase 3: tests
*   [x] `test_freecad_bridge.py::TestFreeCADBridge::test_004_real_enclosure_round_trip` (already a
    real, no-mocks test against `freecadcmd`) extended with a direct, human-readable regression
    check: load the real output `.glb`, convert its real bounding box to mm, and assert it matches
    the real `width=50, depth=30, height=20` input -- the single clearest test for exactly this bug.
*   [x] `TestBoardDrivenEnclosure::test_001`/`test_002` (both real, no-mocks volume assertions)
    updated: `mesh.volume` is now real m³ (not the "mm numbers treated as bare floats" convention
    the tests' own `expected_volume` was computed in before this fix) -- both now convert the loaded
    mesh's volume back to mm³ (`* 1e9`) before comparing, so the same exact-volume discrimination
    these tests already provided keeps working, not just their glb-header presence check.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: this bug was found by investigating a completely different, not-yet-implemented
    feature idea (SPEC-311's board-overlay preview), not by anyone suspecting the shipped enclosure
    viewer was wrong.** `CTX-109.1`/`CTX-109.2`/`CTX-109.3`'s own real, no-mocks tests all verified
    the enclosure's *shape* (volumes, floor presence) correctly, and a human looking at the existing
    single-model viewer had no way to notice a self-consistent 1000x scale error, since nothing else
    was ever in the same scene to compare against. It took introducing a *second*, correctly-scaled
    real model (`kicad-cli`'s own board export) into the investigation before the mismatch became
    visible at all. Recorded here as a real, concrete instance of this repo's own norm: verifying a
    capability in isolation is not the same as verifying it composes with something else, and a bug
    can sit invisible in shipped, tested code for multiple contexts until a genuinely new use case
    exposes it.
