# CTX-308.3: Implementation Context: KiCad Built-in Footprint Libraries (Table-entry resolution)

> **Spec Reference:** Links to [SPEC-308](../../../apps/tauri-ui/specs/SPEC-308-footprints-schematic-advisor.md)

**The real gap this closes:** `CTX-308.1` deliberately skipped `(type "Table")` `fp-lib-table`
entries -- a recursive pointer to another `fp-lib-table` file. On this real machine that nested
file (`.../KiCad.app/Contents/SharedSupport/template/fp-lib-table`) lists 155 real footprint
libraries (Audio_Module, Battery, Capacitor_SMD, ...), every one of KiCad's own built-in libraries,
each `uri` using a `${KICAD10_FOOTPRINT_DIR}`-style placeholder. Search today only reaches a user's
own directly-configured libraries (one entry, `MyPCBLibs`, on this machine) -- the built-in set,
almost certainly what most searches actually want, is invisible.

**Design, grounded in the real nested table file, not a guessed per-OS install path:** the
placeholder's real target directory doesn't need to be guessed from KiCad's typical install
location (fragile -- a user could install it anywhere). The `Table` entry's own `uri` already names
the real path to the nested table file (verified: `.../Contents/SharedSupport/template/fp-lib-table`
on this machine) -- the placeholder's target (`.../Contents/SharedSupport/footprints`) is a real
sibling directory, two levels up from that known file. Verified directly against this machine: `os
.path.join(os.path.dirname(os.path.dirname(nested_table_uri)), "footprints")` resolves to a real,
existing directory. No new per-OS path guessing needed -- this derives correctly from whatever path
the user's own `fp-lib-table` already, genuinely points at.

## 1. Feature Definition & Execution Plan

### Phase 1: resolve `Table`-type entries in `fp_lib_table.py` ✅
*   [x] `_resolve_placeholder(uri: str, footprints_base_dir: str) -> str`: replaces any
    `${KICAD<digits>_FOOTPRINT_DIR}`-shaped placeholder (regex, not just the literal `KICAD10` --
    a future KiCad major version will use a different number, and this must not silently stop
    working) with `footprints_base_dir`. Verified against this machine's real nested table: exactly
    one placeholder variable appears across all 155 real entries, so a single substitution per URI
    is sufficient for this real file -- an entry with an unrecognized/different placeholder pattern
    is logged and skipped, not a crash.
*   [x] `parse_fp_lib_table` gains real `Table`-type handling: for each `Table` entry, read the
    nested file at its `uri`, derive `footprints_base_dir` from that same `uri`
    (`dirname(dirname(uri))/footprints`), parse the nested file's own `(lib ...)` entries, and
    substitute the placeholder in each nested entry's own `uri`. Nested `Table` entries (a table
    pointing to another table) are read but not recursed into further -- named, deliberate scope
    limit, not attempted to be exhaustive against a hypothetical multi-level nesting this real
    machine's own file never actually has.
*   [x] Real unit tests using a self-contained temp-dir fixture modeled on this machine's own real
    nested table shape -- proves placeholder substitution produces real, existing directory paths.
    **Real correction made mid-implementation:** `CTX-308.1`'s own original `TestParseFpLibTable`
    fixture happened to use this real machine's *actual* nested-table path as its Table entry's
    `uri` -- once `Table` entries started being genuinely followed instead of skipped, that old test
    started pulling in all 155 real built-in libraries instead of testing direct-entry extraction in
    isolation, an environment-dependent test bug this session's own real machine masked rather than
    caught cleanly. Fixed by pointing that fixture's `Table` entry at a deliberately nonexistent
    path instead, restoring test isolation.

### Phase 2: real, live verification ✅
*   [x] Real, live test (skips cleanly if this machine's real KiCad install isn't found, matching
    `CTX-308.1`'s own established pattern): `search_footprints("Battery")` finds real entries from
    KiCad's own built-in `Battery.pretty` library -- proving the full path (outer table → Table
    entry → nested table → placeholder resolution → directory listing) works end to end against the
    real, installed KiCad on this machine (verified manually before writing the formal test too: 156
    total real entries resolved, up from 1).
*   [x] Confirmed the existing `MyPCBLibs` direct-entry result still appears too -- not regressed.

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Deviation 1: an old test's fixture happened to encode this real machine's own real
    filesystem path, which only became a problem once this context made that path actually
    resolvable.** See Phase 1 above for the full account. `CTX-308.1`'s own `TestParseFpLibTable`
    fixture used the real, actual path to this machine's nested `fp-lib-table` as its `Table` entry
    -- harmless while `Table` entries were unconditionally skipped, but once this context made them
    real, that test silently started asserting against 156 real, live-machine-dependent entries
    instead of the 1 it meant to isolate. Fixed by using a deliberately nonexistent path in that
    fixture instead, restoring the test's original isolation intent. Worth noting for future
    fixtures in this file: a "realistic-looking" absolute path in a test fixture can accidentally
    become a real, resolvable path on the machine that wrote it.
*   **Deviation 2: real `windows-latest` CI failure, caught by CI itself (not local macOS testing),
    diagnosed and fixed on the same PR before merge.** `_resolve_placeholder`'s first implementation
    passed `footprints_base_dir` directly as `re.sub`'s string replacement argument. `re.sub`
    parses backslash sequences in a *string* replacement as backreferences (`\1`, `\g<...>`) -- a
    real Windows path like `C:\hostedtoolcache\windows\Python\3.12.10\x64\footprints` contains
    `\U`, which isn't a valid backreference, and raised `re.error: bad escape \U`. This machine's
    own macOS forward-slash paths never exercise this code path at all, which is exactly why local
    verification here didn't catch it -- the real CI matrix (this repo's own norm) did. Fixed by
    switching to a callable replacement (`lambda _match: footprints_base_dir`), whose return value
    `re.sub` inserts literally, never re-parsed for backreferences. Reproduced the exact failure
    locally with a simulated Windows-style path before trusting the fix, and added a permanent
    regression test using that same real path shape.
*   **Deviation 3: a second, more subtle real `windows-latest` CI failure, found immediately after
    pushing Deviation 2's fix -- the `re.error` was gone, but a genuine separator mismatch remained.**
    Real KiCad `fp-lib-table` files always write the path *after* the placeholder with a forward
    slash (confirmed against this machine's own real file: `${KICAD10_FOOTPRINT_DIR}/Battery.
    pretty`), even inside files a Windows KiCad install itself writes. `footprints_base_dir` is
    OS-native (backslash-joined on Windows), so the naive substitution produced a *mixed*-separator
    path (`...footprints/Battery.pretty`). Fixed with `os.path.normpath` on the resolved URI. A real
    second-order bug this introduced and fixed in the same pass: the existing "unrecognized
    placeholder" check compared the pre- and post-substitution strings for equality, which
    `normpath`'s own separator cleanup would have made a false positive on Windows (an
    already-clean, placeholder-free URI would look "changed" just from forward-slash-to-backslash
    conversion) -- fixed by checking for placeholder presence with a direct regex search before
    substitution, not a before/after string comparison.
    **Honestly not fully verified locally, by necessity:** this session has no Windows machine.
    `ntpath.normpath`'s real backslash-conversion behavior on Windows was reasoned about from
    documented behavior, not directly executed -- `os.path.normpath` on this session's own macOS
    machine is POSIX `normpath`, which does not convert backslash-separated strings at all, so local
    verification here could only prove the fix doesn't break macOS/Linux, not that it's correct on
    Windows. Real `windows-latest` CI re-running on this same PR is the actual verification for the
    Windows-specific behavior -- stated explicitly per this repo's own "state what was not verified"
    norm, not silently assumed correct from reasoning alone.
