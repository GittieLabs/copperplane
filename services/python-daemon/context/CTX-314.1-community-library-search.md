# CTX-314.1: Implementation Context: Community Library Search (Allowlist + Real GitHub Search)

> **Spec Reference:** Links to [SPEC-314](../../../apps/tauri-ui/specs/SPEC-314-community-library-discovery.md)

The search-only first slice, matching `SPEC-308`'s own "installed-library search first" precedent
(`CTX-308.1`): find real candidate footprint/symbol files in a real, verified allowlist of
GitHub-hosted community libraries. No import, no persistence, no UI yet -- those are `CTX-314.2`'s
job, once this slice's own real, highest-risk question (can a real parser actually read these
files) is resolved.

**Real allowlist, verified by direct inspection during planning, not guessed:**
[`espressif/kicad-libraries`](https://github.com/espressif/kicad-libraries) (148 commits, active, a
real `LICENSE.md`, plain files -- no submodules -- in `symbols/`/`footprints/*.pretty/`) and
[`sparkfun/SparkFun-KiCad-Libraries`](https://github.com/sparkfun/SparkFun-KiCad-Libraries) (1,488
commits, very active, explicit **CC-BY-4.0** license permitting commercial use with attribution,
plain files in `symbols/`/`footprints/`). `kitspace/kicad_footprints` -- named in `SPEC-314` itself
as the original real find -- uses git submodules and is deliberately **not** in this first
allowlist: each submodule is its own real repo needing separate resolution, real added complexity
this slice defers rather than takes on immediately.

## 1. Feature Definition & Execution Plan

### Phase 1: Resolve the real parsing risk first
*   [x] Fetched real `.kicad_mod` files live from `espressif/kicad-libraries`
    (`ESP32-C3-MINI-1.kicad_mod`) and `sparkfun/SparkFun-KiCad-Libraries`
    (`C_0201_0603Metric.kicad_mod`) -- two genuinely different KiCad format generations
    (Espressif's older `fp_text`-based format, `version 20221018`; SparkFun's newer
    `property`-based format, `version 20240108`) -- and parsed both with `kiutils==1.4.8` in an
    isolated test venv. **Both parsed correctly**: real pad counts, positions, and sizes extracted
    (61 pads / 4 pads respectively).
*   [x] Same real check for real `.kicad_sym` files (`SparkFun-Capacitor.kicad_sym`, 73 symbols;
    `Espressif.kicad_sym`, 49 symbols) -- both parsed correctly, real pin counts extracted per
    symbol.
*   [x] Documented the real, verified outcome below (Plan Drift) -- `kiutils` is real and reliable
    for footprints/symbols specifically, `CTX-314.2`'s own import/persist work is realistic.

### Phase 2: The curated allowlist module
*   [x] New `community_libraries.py`: a real, small, hand-verified allowlist (the two repos above),
    each entry recording its own real license identifier and the real subdirectory holding
    footprints vs. symbols -- not assumed uniform across repos (Espressif nests footprints under
    `footprints/Espressif.pretty/`; SparkFun's own layout differs).
*   [x] Real GitHub Git Trees API call (`GET /repos/{owner}/{repo}/git/trees/{sha}?recursive=1`) per
    allowlisted repo, filtered for `.kicad_mod`/`.kicad_sym` paths -- a deliberate choice over
    GitHub's code-search endpoint, which requires authentication and caps at 10 requests/minute even
    authenticated (verified directly against GitHub's own rate-limit docs during planning, not
    assumed). The Trees API falls under the general core rate limit (60/hour unauthenticated,
    5,000/hour with a token) instead, and a curated allowlist never needs GitHub's own search index
    -- it only ever walks repos it already knows about.
*   [x] Optional `github_token` parameter, unauthenticated by default -- this context does not yet
    wire a real OS-keychain entry for it (`CTX-314.2`'s job, alongside the Settings UI field); real,
    honest interim state, not a placeholder pretending to be complete.
*   [x] A simple in-process TTL cache for each repo's own fetched tree (matching
    `library_store.load_supplier_pricing`'s -- now-removed, `CTX-203.2` -- own TTL convention in
    spirit, but scoped to this module, not `library_store.py` itself) so repeated searches against
    the same small allowlist don't re-fetch the same multi-thousand-entry tree on every call.

### Phase 3: A real, thin daemon route
*   [x] `daemon.py`: `library.search_community_footprints(query: str) -> list[dict]` -- matches this
    codebase's own `library.*` route-naming convention (`library.list_parts`, etc.). Returns real
    candidates: repo, real file path, real download URL, real license -- no file content fetched or
    parsed yet at this stage, matching `CTX-308.1`'s own "list matches first, fetch geometry only on
    selection" shape.
*   [x] New `get_capabilities` entry, `github_token_configured: bool` -- real today (always `False`,
    since no keychain wiring exists yet in this context), becomes real and dynamic once `CTX-314.2`
    adds the keychain key.

## 4. Plan Drift & Architectural Changes

- **Positive `kiutils` finding, in direct contrast to `SPEC-310`'s own earlier negative one.**
  `SPEC-310`'s own real, documented finding was that `kiutils==1.4.8` raises an `IndexError` when
  asked to parse a full `.kicad_pcb` board file via `kicad_pcb_import.py` -- this context's own
  Phase 1 plan treated that as a real, open reason `kiutils` might not be usable here either, and
  named `kicad-cli` validate/convert or a hand-rolled S-expression reader as fallbacks. Neither
  fallback was needed: real, live-fetched `.kicad_mod` and `.kicad_sym` files from both allowlisted
  repos parsed correctly on the first attempt, across two different real KiCad format generations
  (Espressif's older `fp_text`-based footprints, `version 20221018`; SparkFun's newer
  `property`-based footprints, `version 20240108`/`generator_version "8.0"`). The working theory,
  worth recording since it will matter again for any future kiutils-adjacent work in this repo:
  standalone footprint/symbol files are simple, self-contained S-expressions, while a full board
  file pulls in the much larger and more failure-prone net/track/zone graph -- `kiutils` handles the
  former reliably even though it chokes on the latter. This means `CTX-314.2`'s own real
  import/persist work can build on `kiutils` directly rather than needing a fallback parser.
- **Real test coverage exceeded the Testing Matrix's own five rows.** While implementing Phase 2's
  error handling (`_github_request`'s real HTTPError/TimeoutError/non-200 branches) and Phase 3's
  `github_token` threading, it became clear those real failure paths and the new capability flag
  needed their own direct tests, matching this codebase's own existing convention of testing error
  branches and capability flags explicitly rather than only the happy path. Added, beyond the
  original plan: `TestTreeCache.test_002` (expired-entry re-fetch), three
  `TestGithubRequestErrorHandling` tests, and `test_daemon.py`'s `test_007b`/`test_007c`/`test_008`.
  Not a scope change to what ships -- the module and route are exactly what Phase 2/3 specified --
  just more real verification of it than the matrix originally called out.
- No other deviation from the original plan. The allowlist, the Trees-API choice, the
  in-process-only cache, and the deliberately-deferred `github_token` keychain wiring all shipped
  exactly as scoped in `SPEC-314` and this context's own Phase 1-3 plan.
