# CTX-204.1: Implementation Context: Agent Tool Registry

> **Spec Reference:** Links to [SPEC-204](../specs/SPEC-204-agent-tool-registry.md)

## 1. Feature Definition & Execution Plan

`SPEC-204`'s own §2/§3 identified two real gaps in the installed `gittielabs-agentflow==0.8.2`
(`LocalToolDispatcher`'s string-only tool results, and its exception-swallowing) plus a
confirmation-gating need that may belong in AgentFlow itself. Per this repo's own
[[agentflow-fix-upstream]] norm, both land in `~/repos/agentflow` first, released through PyPI,
*before* any daemon-side wiring depends on them. Phases 1-2 are real work in a different repo;
Phases 3-4 are this repo's own daemon code, built against the upgraded pin.

### Phase 1: AgentFlow upstream — structured tool results
*   [ ] In `~/repos/agentflow`: branch `feat/tool-dispatcher-structured-results`, add a structured
    (non-`str`) result path to `ToolDispatcher`'s protocol / `LocalToolDispatcher`, additive so
    every existing string-returning tool stays valid.
*   [ ] Real AgentFlow-side tests under `~/repos/agentflow/tests/` (that repo's own test suite, not
    this CTX's matrix below — see §2's note on cross-repo verification).
*   [ ] `pytest` and `ruff check src/` green; version bumped in both `pyproject.toml` and
    `src/agentflow/__init__.py`; `docs/changelog.md` entry added.
*   [ ] PR into `main`, merge, tag `vX.Y.Z`, verify `pip index versions gittielabs-agentflow` shows
    the new release.

### Phase 2: AgentFlow upstream — confirmation-gating primitive
*   [ ] Resolve `SPEC-204`'s open question: is a `requires_confirmation` flag + generic
    pending/confirm dispatch protocol worth adding to `ToolRegistry`/`LocalToolDispatcher` itself
    (real, reusable value for any AgentFlow consumer gating a destructive tool), or does this app's
    specific need stay daemon-side? Decide before writing code, record the reasoning here in §4
    regardless of which way it goes.
*   [ ] If upstreaming: same branch/test/version/changelog/tag/release cycle as Phase 1 (can ship in
    the same AgentFlow release as Phase 1's structured-result change, or its own — whichever the
    real diff size warrants).
*   [ ] Bump `services/python-daemon/requirements.txt`'s `gittielabs-agentflow` pin to the new
    version once Phases 1-2 are actually published to PyPI, and record why in §4.

### Phase 3: Daemon-side tool registration
*   [ ] New module `services/python-daemon/tool_registry.py`: build a `ToolRegistry` +
    `LocalToolDispatcher` registering the subset of `daemon.py`'s `ROUTES` an agent plan would
    plausibly call (`kicad.inject_component`, `freecad.generate_enclosure`, `kicad.generate_component`,
    `component.search` — per `SPEC-204` §1's explicit non-goal against registering all ~20 routes on
    day one). Each registration wraps the existing `ROUTES` handler unchanged.
*   [ ] `kicad.inject_component`'s registration sets whatever confirmation-gating mechanism Phase 2
    landed (the only route that mutates a live, already-open board — verified in `SPEC-204` §2
    against every other route in the table).
*   [ ] Unit tests in `services/python-daemon/tests/test_tool_registry.py` (stub already committed):
    registry construction, that `kicad.inject_component` is gated and every other registered tool
    is not, and that a gated tool's first call does not invoke the real handler.

### Phase 4: Confirmation round trip, wired and verified for real
*   [ ] Wire the pending-confirmation result through `SPEC-105`'s existing job-progress channel so a
    gated tool call surfaces as an explicit pending state rather than a bare string the caller has
    to pattern-match.
*   [ ] Real integration test in `services/python-daemon/tests/test_tool_registry.py` (extends the
    Phase 3 stub) driving the daemon's actual JSON-RPC wire per this repo's "verify against the real
    thing" norm: a non-gated tool call executes and returns immediately; a gated tool call returns
    pending without mutating anything; a confirmed re-call actually dispatches to the real handler.
*   [ ] Update the Testing Requirements Matrix below from ⏳ Pending to ✅ Passed as each real test
    lands, per this repo's own established `CTX-*.md` convention.
