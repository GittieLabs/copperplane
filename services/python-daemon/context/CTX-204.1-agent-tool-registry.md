# CTX-204.1: Implementation Context: Agent Tool Registry

> **Spec Reference:** Links to [SPEC-204](../specs/SPEC-204-agent-tool-registry.md)

## 1. Feature Definition & Execution Plan

The original plan (see §4 Plan Drift) called for two AgentFlow-upstream phases before any daemon
work. Real verification against the installed library (two scripts run directly, not just source
reading) disproved both apparent gaps `SPEC-204`'s first draft named — see §4 for the full account.
`SPEC-204` itself has already been corrected to match. This context now has two phases, both
entirely inside `services/python-daemon`, no AgentFlow version bump required.

### Phase 1: Daemon-side tool registration ✅
*   [x] New module `services/python-daemon/tool_registry.py`: builds a `ToolRegistry` registering
    the subset of `daemon.py`'s `ROUTES` an agent plan would plausibly call (`kicad.inject_component`,
    `freecad.generate_enclosure`, `kicad.generate_component`, `component.search` — per `SPEC-204`
    §1's explicit non-goal against registering all ~20 routes on day one), via `add_tool()` (inline
    registration), not `LocalToolDispatcher` — see `SPEC-204` §3 for why that choice matters. Each
    registration wraps the existing `ROUTES` handler unchanged. Registration is conditional on the
    route actually existing in `daemon.ROUTES` (mirrors `daemon.py`'s own SPEC-107 §2 conditional
    registration when a bridge module fails to import).
*   [x] `kicad.inject_component`'s wrapper checks `tool_input.get("confirmed")`; absent or false,
    returns a pending-approval result (string + `last_raw_tool_result` structured payload) without
    calling the real handler; `confirmed: true` calls through (the only route that mutates a live,
    already-open board — verified in `SPEC-204` §2 against every other route in the table).
*   [x] Unit tests in `services/python-daemon/tests/test_tool_registry.py`: registry construction
    registers exactly the intended, actually-present routes; `kicad.inject_component`'s first call
    (no `confirmed` flag) does not invoke the real handler and its confirmed call does; a non-gated
    tool executes immediately; a handler's raised exception actually propagates through
    `ToolRegistry.dispatch` — proving the `add_tool()` choice over `LocalToolDispatcher` is real, not
    just documented. All 5 pass; full daemon suite (179 tests) still green.
*   **Known limitation, deliberately deferred to Phase 2:** every tool wrapper here calls its
    `daemon.ROUTES` handler directly and synchronously. Four of the five routes wrapped
    (`kicad.inject_component`, `freecad.generate_enclosure`, `kicad.generate_component`,
    `component.search`) are normally invoked through `daemon.py`'s `ASYNC_ROUTES`/`submit_job`
    machinery (`SPEC-105`) instead — this module bypasses that entirely for now. Nothing in
    `tool_registry.py` is wired into `daemon.py`'s real JSON-RPC surface yet.

### Phase 2: Confirmation round trip, wired and verified for real ✅
*   [x] New route `agent.dispatch_tool` (`daemon.py`, registered conditionally on `tool_registry`
    having imported) is the real JSON-RPC entry point for the confirmation-gating policy.
    Deliberately does **not** go through `tool_registry.build_tool_registry()`'s `ToolRegistry` —
    that object exists for a future `AgentExecutor` conversation loop (out of this spec's scope, see
    `SPEC-204` §1). Instead it reuses `submit_job` (`SPEC-105`) directly for real dispatch, exactly
    like every other `ASYNC_ROUTES` caller — no job tracking/progress notification reinvented.
    `agent.dispatch_tool` itself is *not* an async route: an unconfirmed gated call returns
    synchronously (nothing async happens); a confirmed/non-gated call returns `submit_job`'s
    `{"job_id": ...}` immediately, same as calling the underlying route directly always has.
*   [x] Verified manually against the real, unmocked daemon before writing the automated test: a
    real `component.search` call through `agent.dispatch_tool` returned a job id, and a real
    `job.progress` notification followed on stdout (it then hit `job.failed` for a real, expected
    reason — no API key configured in that ad-hoc script, not a bug); a gated
    `kicad.inject_component` call with no `confirmed` flag returned `pending_confirmation`
    synchronously with zero job.* notifications and zero entries in `daemon.JOBS`; an unknown tool
    name returned a real `-32000` JSON-RPC error.
*   [x] Real integration test class `TestAgentDispatchToolEndToEnd` in
    `services/python-daemon/tests/test_tool_registry.py`, modeled on `test_daemon.py`'s own
    `test_004_async_route_returns_job_id_immediately` pattern (a temporary fake route registered
    into the real `daemon.ROUTES`/`ASYNC_ROUTES`, not a live KiCad/FreeCAD call): an unconfirmed call
    returns pending and submits no job; a confirmed call actually dispatches through the real async
    job protocol, polling for the real `job.completed` notification rather than a fixed sleep; an
    unknown tool returns a real JSON-RPC error. All 3 pass; combined with Phase 1's tests,
    `test_tool_registry.py` is 8/8. Full daemon suite: 182 tests, all green (one live-LLM-call test
    elsewhere flaked on a non-deterministic model response on first run, passed cleanly on
    isolation and re-run — confirmed unrelated, no diff touches that file, see §4).

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Deviation 1: the original two-AgentFlow-upstream-phase plan was wrong, caught before writing
    any AgentFlow code by actually running scripts against the library instead of only reading its
    source.** `SPEC-204`'s first draft (and this context's original Phase 1/2) claimed
    `gittielabs-agentflow==0.8.2` had two real gaps — `LocalToolDispatcher` handlers return
    strings only with no structured-result path, and `LocalToolDispatcher.dispatch` swallows
    exceptions into strings — and planned to fix both upstream per [[agentflow-fix-upstream]],
    including committing/pushing to `~/repos/agentflow` and running its PyPI release workflow.
    *   *What actually happened:* before writing any AgentFlow code, two small scripts were run
        directly against the installed library (not the daemon, not assumed from reading
        `local_dispatcher.py`'s method signature alone). Script 1 proved `agentflow.tools.
        http_dispatcher.last_raw_tool_result` — a `ContextVar[dict | None]` already wired into
        `AgentExecutor`'s `TOOL_RESULT` event emission — lets a handler hand back a real structured
        dict alongside its string return value; it worked exactly as `runtime.py`'s own code
        suggested it should. Script 2 proved `ToolRegistry.add_tool()`'s inline handlers propagate
        real exceptions all the way to `AgentExecutor`'s `is_error`/`ERROR`-event handling —
        `LocalToolDispatcher` is the *only* path that swallows them, not a library-wide behavior.
    *   *Reasoning for the original mistake:* the first draft read `LocalToolDispatcher.register()`'s
        method signature and stopped there, without reading `agent/runtime.py`'s actual event-
        emission code or comparing `ToolRegistry.dispatch()`'s two different call paths
        (`add_tool()`'s inline handlers vs. `add_dispatcher()`'s registered dispatchers) against each
        other. `LocalToolDispatcher` is also the more obviously-named class for "a locally-running
        tool," which made it easy to reach for without checking whether an equally-valid alternative
        registration path (`add_tool`) behaved differently.
    *   *Impact:* `SPEC-204` §§1-3 corrected in place on 2026-08-14 (same day, before any AgentFlow
        commit was made — `~/repos/agentflow`'s git state was never touched). This context's Phase
        1/2 (AgentFlow upstream work) dropped entirely; the former Phase 3/4 daemon-side work
        renumbered to Phase 1/2, now built directly against the already-released `0.8.2` with no
        version bump. Confirmed with the user before proceeding rather than unilaterally deciding
        whether the also-real, still-open confirmation-gating question was worth a library
        contribution regardless of necessity — the user chose to keep it daemon-side.
    *   *Why this matters beyond this one context:* this is exactly the case
        [[agentflow-fix-upstream]]'s "verify before assuming a gap is real" spirit exists for, in the
        opposite direction from what that memory usually guards against — it stops a fix-upstream
        default from being applied to a gap that was never real, which would have shipped a wasted
        AgentFlow version bump and an unnecessary PyPI release. Reading a method's signature is not
        the same as verifying its actual runtime behavior across every path that reaches it.
*   **Deviation 2: `agent.dispatch_tool` deliberately bypasses `tool_registry.py`'s own
    `ToolRegistry` for real dispatch, reusing `submit_job` directly instead.** The Phase 2 plan
    implicitly assumed the new route would call through `tool_registry.build_tool_registry()`. In
    practice, that `ToolRegistry` exists for a future `AgentExecutor` conversation loop (an LLM
    deciding which tool to call) — this context never built one, matching `SPEC-204` §1's own
    non-goal against a chat UI. Since `agent.dispatch_tool`'s caller already names the tool
    directly (no model-driven selection happening yet), routing through `ToolRegistry.dispatch()`
    would have added an indirection with no real consumer, and would have required bridging
    `daemon.py`'s synchronous route-handler world into `asyncio.run()` twice (once for the registry
    dispatch, once implicitly inside whatever ran the job) for no benefit. Calling `submit_job`
    directly reuses `SPEC-105`'s real job-tracking/progress-notification machinery unmodified,
    exactly as every other `ASYNC_ROUTES` caller already does. `tool_registry.py`'s `ToolRegistry`
    remains real, tested, and ready for that future conversation loop — just not consumed by this
    route.
*   **A genuinely unrelated test flake, verified as such before moving on, not silently ignored.**
    The first full-suite run after Phase 2 showed one failure:
    `test_component_pipeline.TestRealGenerateComponent.test_003_real_extraction_via_an_overridden_
    provider`, a live Google LLM call that returned `'ATtiny85-20SU'` instead of the expected
    `'ATtiny85'` — real model non-determinism, not a regression. Confirmed unrelated two ways before
    treating it as such: `git diff --stat` showed this branch touches nothing in
    `tests/test_component_pipeline.py`, and re-running that single test in isolation passed cleanly.
    Recorded here rather than silently re-run-until-green, per this repo's own "state what was not
    verified" norm — a flaky live-network test is a real, standing fact about this suite, not
    something to paper over.
