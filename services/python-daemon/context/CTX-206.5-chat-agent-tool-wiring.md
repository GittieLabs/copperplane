# CTX-206.5: Implementation Context: Chat Agent Tool Wiring

> **Spec Reference:** Links to [SPEC-206](../specs/SPEC-206-agent-context-store.md)

SPEC-206 §2.1-§2.4 are already built (`CTX-206.1`-`CTX-206.4`: project intent, conversation
thread storage, connection-guidance persistence, the `SourceRef` resolver/validation model).
§2.5 ("Agent dispatch") is what actually makes the five `SPEC-318` chat agents callable -- this
context builds the real, minimal tool set every one of the five already-drafted
`chat_*.prompt.md` files' own `tools:` frontmatter references, verified directly against those
five files rather than against `SPEC-206` §2.5's own table (which lists a few tools -- 
`kicad.check_schematic`, `kicad.check_board`, `library.save_confirmed_part` -- that, per explicit
product decisions recorded below, no real agent prompt ends up needing).

**Deliberately not attempted here:** `context.search` (needs `SPEC-206` §2.6's whole retrieval
index -- its own, larger, separate context), and the actual `router.prompt.md`/`chat.send`
wiring that dispatches a conversation to one of these agents at all (the next context,
`CTX-206.6`). This context only makes the tools *available* to register; nothing calls them yet.

## 1. Feature Definition & Execution Plan

### Phase 1: `datasheet.read_pages` -- the one genuinely new route
*   [x] `daemon.py`: guarded `import datasheet_structure` (matching `datasheet_guidance`'s own
    try/except pattern -- `pdfplumber` is an optional dependency chain).
*   [x] `datasheet_read_pages(part_id, pages) -> dict`: loads the real Part, reuses
    `library_store.ensure_datasheet_cached` (never re-fetches), calls
    `datasheet_structure.extract_pages` (which always extracts the *whole* document -- it has no
    page selector of its own) and filters down to the requested 1-indexed page numbers. Also
    returns the real `content_hash` of the cached PDF at read time, so a mechanically-derived
    `datasheet_page` `SourceRef` (the next context's job) can carry a real hash without a second
    file read.
*   [x] Registered in `_build_routes()` (gated on both `datasheet_structure` and `library_store`
    being real) and in `ASYNC_ROUTES` -- `ensure_datasheet_cached` can still be a real, first-time
    network fetch, the same reasoning `component.cache_datasheet` is already async for.

### Phase 2: `TOOL_DEFINITIONS` for the tools that already have real routes
*   [x] `tool_registry.py` gains four new entries: `datasheet.read_pages`, `library.load_part`,
    `library.list_parts`, `kicad.get_component_heights` -- real `description`/`input_schema` per
    their real daemon.py signatures, not guessed.
*   [x] **Deliberately not added**, despite appearing in `SPEC-206` §2.5's own table: 
    `kicad.check_schematic`/`kicad.check_board` (no agent prompt's `tools:` list references
    either -- both need an explicit file path no chat agent reliably has, per the same reasoning
    already recorded in `chat_schematic.prompt.md`/`chat_pcb.prompt.md`'s own bodies) and
    `library.save_confirmed_part` (a real product decision, see Plan Drift below: Components stays
    read-only in v1, and instead tells the user to search for and add a part themselves, since a
    real search can surface multiple plausible candidates that only the user should choose among).
*   [x] `chat_components.prompt.md`'s own body gained one paragraph making this explicit --
    written during this same context, since the gap (the agent had no instruction at all for "the
    user wants to add a part that isn't saved yet") was found while resolving the
    `library.save_confirmed_part` question.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (real, deliberate product decision): Components stays read-only in v1 --
    `library.save_confirmed_part` is not one of its tools, despite `SPEC-318`'s own Non-Goals
    text ("The single write they may propose is adding a component to the library...") reading as
    though it should be.**
    *   *Reasoning:* discussed directly with the user before writing any code. A real search
        commonly returns several plausible candidates (different packages, manufacturers, close
        variants); letting the chat agent pick and save one on the user's behalf would reintroduce
        exactly the silent-substitution risk `SPEC-306` was written to prevent in the first place,
        just one layer removed (through a chat tool instead of a ranked list). The agent instead
        tells the user to search for and add the part themselves, through the same disambiguation
        UI every other search already goes through.
    *   *Impact:* `chat_components.prompt.md` gained an explicit paragraph saying exactly this,
        since the prior draft had no instruction at all for this case. `library.save_confirmed_part`
        was never added to `TOOL_DEFINITIONS` -- there was no real caller for it to serve.
*   **Deviation 2 (non-deviation, confirmed as designed): `kicad.check_schematic`/
    `kicad.check_board` were not added to `TOOL_DEFINITIONS` either, despite `SPEC-206` §2.5's own
    table listing them.**
    *   *Reasoning:* verified directly against all five `chat_*.prompt.md` files -- none references
        either tool. This matches a design decision already recorded in `chat_schematic.prompt.md`/
        `chat_pcb.prompt.md`'s own bodies from the earlier prompt-drafting session: both routes
        need an explicit file path the model doesn't reliably have, and re-checking is a real,
        separate user action (the app's own "Check" button), never something the agent triggers.
        `SPEC-206`'s table is a real, honest inventory of *available* routes worth wiring
        eventually, not a mandate that every agent must use every one.
    *   *Impact:* none -- adding an unused `TOOL_DEFINITIONS` entry would be dead weight with no
        real caller, the exact thing `SPEC-204`'s own Phase 1 scope note already warned against
        ("not local project/library CRUD -- non-goal against registering all ~20 routes on day
        one").
*   **Deviation 3 (non-deviation, confirmed as designed): `context.search` is completely absent
    from this context, even though four of the five agent prompts declare it as a tool.**
    *   *Reasoning:* discussed and confirmed directly with the user -- `context.search` needs
        `SPEC-206` §2.6's whole retrieval index (FTS5 store, chunk extraction, staleness rebuild),
        which does not exist yet and is real, separate, substantial work. Sequencing decision: wire
        everything else in §2.5 first (this context, plus `CTX-206.6`'s router/`chat.send`), then
        build the retrieval index as its own next context.
    *   *Impact:* every agent's declared tool list still names `context.search`, but no route or
        `TOOL_DEFINITIONS` entry exists for it yet -- `AgentExecutor` will simply never be able to
        dispatch it until `CTX-206.6`'s successor lands. Named here so nobody assumes this context
        silently finished the whole tool surface.
