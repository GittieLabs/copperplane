# CTX-108.1: KiCad Write Path — Footprint Injection

> **Spec Reference:** Links to [SPEC-108](../specs/SPEC-108-kicad-write-path-footprint-symbol-injection.md)

**Scope note:** implements the board **footprint** write path only. `SPEC-108`'s own title
promises "Footprint & Symbol Injection," but `kipy`'s `Schematic` class — the only real way to
write a symbol into a schematic through the IPC API — is marked
`.. versionadded:: 0.7.0 (KiCad 11)` in the installed `kicad-python==0.7.1` source, and this
machine's actually-running KiCad is `10.0.3` (confirmed live in `CTX-103.1`). Per this repo's
"verify against the real thing when it's available" norm, schematic symbol injection **cannot be
verified for real on any machine currently available to this project** and is deferred to a future
context (`CTX-108.2`, once KiCad 11 is available) rather than built against KiCad 11's API blind.
See Plan Drift.

## 1. Feature Definition & Execution Plan

### Phase 1: Pad-layout geometry generator — the real gap `SPEC-202`'s schema leaves open
*   [x] `services/python-daemon/kicad_write.py`: a new, package-family-keyed layout generator.
    `SPEC-202`'s schema gives pin count, pitch, and package/courtyard dimensions, but no per-pin
    `(x, y)` — something has to derive real pad positions before any pad object can be created, and
    that derivation is new domain logic this context owns, not something `SPEC-202` already solved.
*   [x] Covers, for this context: 2-pad passives (`0603`, `0805`); dual-row surface-mount
    (`SOIC-8/14/16`, `TSSOP-8`); dual-row through-hole (`DIP-8/14`) — standard IC pin numbering
    (pin 1 top-left, down the left column, then up the right column), derived from each pin's
    `number` field alone.
*   [x] Explicitly does **not** cover `TQFP-32/44`/`QFN-16/24` (four-side perimeter numbering,
    genuinely different geometry) or `SOT-23` (irregular 3-pin layout) — deferred to a follow-up
    context, named here rather than silently missing from `PACKAGE_REFERENCE`'s otherwise-full
    coverage.
*   [x] Pad dimensions (width/length per pin) are **conservative, generic defaults per package
    family — not IPC-7351 nominal/least/most land patterns.** Good enough to prove the write path
    end-to-end and to visually inspect in KiCad; not something to fabricate a board from without
    human review. `SPEC-204`'s confirmation gate (not yet written) is the intended safety net for
    that gap, per `ROADMAP.md` §6's own risk-register framing of this spec.

### Phase 2: Footprint/FootprintInstance builder
*   [x] `kicad_write.build_footprint_instance`: translates a validated `SPEC-202` schema + Phase 1's
    generated layout into a real `kipy.board_types.FootprintInstance`: one `Pad` per pin (position
    from Phase 1, `pad_type` `PT_SMD` for surface-mount / `PT_PTH` for through-hole with a real
    drill), a `BoardRectangle` courtyard shape on `BL_F_CrtYd` sized from the schema's own
    `courtyard` field, `reference_field`/`value_field` set from `part_number`.
*   [x] **Board-local only — no footprint-library-table save.** `kipy`'s real API has no method to
    write into KiCad's own footprint-library management (confirmed by inspecting the installed
    package: `Board`/`KiCad` expose no library-write call). Resolves `SPEC-108` §3's open question
    on this axis: a board-local `FootprintInstance` is this context's whole scope, not a partial
    step toward a library save that doesn't exist yet as a real capability. `LibraryIdentifier`
    still gets a real, descriptive `(library="HardwareAgentStudio", name=<part_number>)` — metadata
    only, so a human reviewing the board can see at a glance which footprints this pipeline
    generated.

### Phase 3: The write transaction
*   [x] `kicad_bridge.py` gains `inject_component(schema: dict, position_mm: tuple)`:
    `board.begin_commit()` → `board.create_items([footprint_instance])`. On failure,
    `board.drop_commit(commit)` and raise `KiCadWriteError` — the board is provably unchanged. On
    success, `board.push_commit(commit, message)`, then `board.save()` in its own `try`, reported as
    a distinct `KiCadWriteError` ("added but not saved") if it fails — a save failure happens
    *after* the commit already succeeded, so retrying `drop_commit` against an already-pushed commit
    would be wrong; this is a real, different failure mode, not a variant of the first one. Verified
    for real: both paths (Plan Drift).
*   [x] Reuses `kicad_bridge.get_client()` unchanged — no new, stricter version-check for writes
    beyond `CTX-103.1`'s existing `FutureVersionError`-as-warning policy. Resolves `SPEC-108` §3's
    open question on this axis: there is no new signal available at write-time that the read-time
    policy didn't already have; a second, stricter check would be guessing at a failure mode never
    actually observed. Revisit if a real KiCad major-version bump ever breaks the wire protocol —
    stated as an open risk, not resolved by invention.

### Phase 4: The `kicad.inject_component` route
*   [x] `daemon.py`: `kicad_inject_component(schema, x_mm, y_mm)` calling `kicad_bridge.inject_component`,
    gated on the same conditional-import pattern as every other real bridge route
    (`get_kicad_version`, `kicad_generate_component`).
*   [x] Registered as an **async route** (`SPEC-105`) — a real board mutation plus save is
    multi-second, same reasoning as every other real route this product has added.
*   [x] **The route mutates the board the instant it's called — no additional confirmation check
    of its own.** Resolves `SPEC-108` §3's confirmation-gate-boundary question explicitly: the
    caller (eventually `SPEC-204`'s gate) is solely responsible for only invoking this route after
    approval. Stated plainly here since it's a real, live safety boundary, not an implementation
    detail.
*   [x] Frontend wiring (a UI trigger in `apps/tauri-ui`) is **out of scope for this context** —
    `SPEC-108`'s own Cross-Module Impacts section names it, but the daemon-side write path is
    already substantial (a new geometry generator plus a new transactional write). Deferred to a
    follow-up context rather than expanding this one's phase count past what can be verified
    carefully in one pass.

### Phase 5: Testing — real, against the actually-running KiCad on this machine
*   [x] Mocked/local: the Phase 1 layout generator produces the right pin count, the right side
    assignment per pin number, and pad positions symmetric about the package center for each
    covered family; an unsupported family (e.g. `TQFP-32`) raises a clean error rather than
    guessing a layout. The Phase 2 builder produces the right pad count/types/courtyard/fields —
    pure object construction, no live connection needed.
*   [x] **Real**, skipping cleanly when no live KiCad IPC socket is reachable, or a socket exists but
    no board is open in the PCB Editor (same skip condition as `CTX-103.1`'s own tests, extended):
    a real SMD (`SOIC-8`) and a real PTH (`DIP-8`) footprint each created against the actually-open
    board via `begin_commit`/`create_items`, verified via `board.get_footprints()`'s count, then
    **always discarded via `drop_commit`** — never `push_commit`, never `save()`. See Plan Drift for
    why the real tests never exercise `inject_component`'s own `save()` call directly.
*   [x] Mocked: `inject_component`'s own orchestration (does it call `push_commit`+`save()` on
    success, `drop_commit` and neither of those on a `create_items` failure, never call
    `begin_commit` at all for an unsupported package, and correctly distinguish a `save()` failure
    from a `create_items` failure) — this is the only place that control flow is exercised, since
    the live tests deliberately never let `save()` run for real. See Plan Drift.
*   [x] A full end-to-end test: `kicad.inject_component` submitted through `handle_request` exactly
    as a real client would, against the actually-running KiCad, with `board.save()` patched to a
    no-op for the whole test and the created footprint removed from the live in-memory board
    afterward — proving the full route/param-resolution/async-dispatch/real-kipy-construction chain
    without ever touching disk.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (resolved before implementation, not found mid-build): `SPEC-108`'s own title
    promises "Footprint & Symbol Injection," but real schematic writes are unverifiable on any
    machine available to this project right now.**
    *   *Reasoning:* `kicad-python==0.7.1`'s own `Schematic` class docstring states
        `.. versionadded:: 0.7.0 (KiCad 11)` — the Python binding exists in the installed package,
        but the KiCad *application* must be version 11+ for the IPC server to actually implement
        schematic commands. `CTX-103.1` confirmed this machine's real, running KiCad is `10.0.3`.
        Building against an API this project cannot exercise for real would violate the "verify
        against the real thing when it's available" norm the moment it was written, not eventually.
    *   *Impact:* This context's real scope is the board/footprint write path only. Schematic symbol
        injection becomes `CTX-108.2`'s job once KiCad 11 is actually available to test against —
        named explicitly here so it doesn't quietly vanish from the record the way an unstated scope
        cut would.

*   **Deviation 2: real write verification needed a running PCB Editor session, not just a running
    KiCad app — a heavier real-verification bar than `SPEC-103`/`104`'s read-only precedent, found
    by actually trying it, not assumed.**
    *   *Reasoning:* `kipy.KiCad.get_board()` calls `GetOpenDocuments` internally, and that command
        returned `"no handler available"` against a bare-launched KiCad project manager, and
        identically against a *standalone* `pcbnew.app` launched independently — only a PCB Editor
        window opened *from within* an already-running project-manager session answers it. Getting
        there required a real, disposable scratch project (a copy of KiCad's own bundled
        `Arduino_Pro_Mini` template, never one of the user's real `~/repos/PCBs/*` projects) and a
        one-time manual step (opening the PCB Editor) that couldn't be automated headlessly without
        granting this session macOS accessibility/screen-recording permissions — deliberately not
        done unilaterally; the user was asked to click it instead.
    *   *Impact:* None to the shipped code — this is a real fact about the IPC API worth recording so
        a future real-write context (`CTX-108.2`, `SPEC-109`) doesn't have to rediscover it. Once a
        PCB Editor session was open, every real API call in this context (`begin_commit`,
        `create_items`, `push_commit`, `drop_commit`, `remove_items_by_id`, `save`) was exercised for
        real, including both a real SMD and a real through-hole footprint, and cleaned up completely
        (board footprint count confirmed back at its original value after every real test run).

*   **Deviation 3: an automated test suite must never be able to call `board.save()` for real — a
    safety constraint this context's own design (`inject_component` calls `save()` as real,
    intended production behavior) creates, not one `SPEC-108` anticipated.**
    *   *Reasoning:* `CTX-103.1`/`104.1`'s "skip cleanly if the real dependency isn't available"
        precedent assumes the worst case of a real test running is a no-op skip. That assumption
        breaks here: any developer or CI runner with KiCad open and a socket reachable would have a
        REAL board open — possibly their own real work — and `inject_component`'s own designed
        behavior is to save the board file. A real test that called the full `inject_component()`
        function as designed would risk silently overwriting a real `.kicad_pcb` file on disk the
        moment the test suite ran, which is a materially different and much worse risk than
        `CTX-103.1`/`104.1`'s read-only tests ever carried.
    *   *Impact:* Split real verification into two tiers: (1) the pad/footprint construction and the
        `begin_commit`/`create_items`/`drop_commit` cycle are exercised for real, live, against
        whatever board is actually open — but every real test always ends in `drop_commit`, never
        `push_commit` or `save`, so the board is provably unchanged afterward regardless of what
        state it started in; (2) `inject_component`'s own orchestration (which of `push_commit`/
        `drop_commit`/`save` gets called, and in what order, on success vs. each failure mode) is
        verified with a fully mocked `Board`, never a live one. The one true end-to-end test (through
        `daemon.handle_request`, `TEST-005`) does exercise the real function, but with
        `kipy.board.Board.save` patched to a no-op for the test's duration and the created footprint
        explicitly removed from the live in-memory board afterward — real verification of everything
        except the literal disk write, which is the one piece that was never safe to run for real in
        an automated suite.

*   **Deviation 4: `push_commit` vs. `save()` failure are genuinely different failure modes, found by
    testing the actual sequencing, not assumed from the API's shape.**
    *   *Reasoning:* A first draft of `inject_component` wrapped `create_items`, `push_commit`, and
        `save()` all inside one `try`/`except` that called `drop_commit` on any exception. That's
        wrong: `drop_commit` operates on a `Commit` handle that `push_commit` has already consumed by
        the time `save()` could fail, and a save failure means the component *does* exist in the live
        KiCad session — the user hasn't lost their edit, only the on-disk persistence of it — which is
        a materially different, better outcome than a `create_items` failure that never touched the
        board at all.
    *   *Impact:* `drop_commit` only wraps `create_items`; `push_commit` runs unconditionally once
        `create_items` succeeds; `save()` runs in its own `try`, reporting a distinct
        `KiCadWriteError` message ("added ... but the board file could not be saved") rather than
        conflating the two. Verified for real with a mocked `save()` failure (`TestInjectComponent`,
        `test_004`): `push_commit` is called exactly once, `drop_commit` is never called.
