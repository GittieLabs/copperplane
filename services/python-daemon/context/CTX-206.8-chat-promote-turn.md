# CTX-206.8: Implementation Context: chat.promote_turn

> **Spec Reference:** Links to [SPEC-206](../specs/SPEC-206-agent-context-store.md)

The last piece of the user's confirmed build order (chat.send → retrieval → **promotion**). SPEC-206
§2.7's own framing: a retrieval index doesn't deliver answer consistency by itself -- the same
question over the same retrieved context still samples different prose. What delivers it is moving a
settled conclusion out of a transcript and into a durable record. With this context, **SPEC-206's own
backend is fully built** -- everything remaining (`SPEC-318`'s actual chat UI) is frontend work with
no backend prerequisite left unbuilt.

## 1. Feature Definition & Execution Plan

### Phase 1: `library_store.py` -- real note storage
*   [x] `part["notes"]`/`project["notes"]`: backfilled to `None` (not `[]`) -- the same "never
    generated" vs. "generated, empty" distinction `design_guidance`/`connection_guidance` already
    preserve, even though promotion is additive-only (a note list, once real, never reverts to
    empty).
*   [x] `add_part_note(part_id, note)`/`add_project_note(project_name, note)`: round-trip through
    `load_part`/`save_part` and `load_project`/`save_project`, the same "load fresh, never
    blind-overwrite" shape `set_project_footprint_override` already established.
*   [x] `update_thread_turn(scope, scope_id, turn_id, updates)`: the one real caller is
    `promote_turn` marking a turn's own `promoted_note_id` once its note exists. A real, rare,
    user-initiated action, so a read-all-rewrite-all update is the right cost -- unlike
    `append_thread_turn`'s hot per-turn single-line append.

### Phase 2: `chat_agents.py` -- `promote_turn`, and a real `note` resolver
*   [x] `promote_turn(scope, scope_id, turn_id, target_scope, target_id)`: loads the source turn,
    fails closed on an unknown turn id, a non-assistant turn, or an unknown `target_scope`. Copies
    the turn's own **already-validated** `sources` verbatim -- no re-validation, per SPEC-206 §2.7's
    own exact framing. Builds the real note record, writes it via `add_part_note`/`add_project_note`,
    then marks the source turn's `promoted_note_id`.
*   [x] Always user-initiated, never automatic (SPEC-206 §2.7's own explicit requirement) -- this
    function has no caller anywhere in this codebase except the real `chat.promote_turn` route; no
    agent code path invokes it on its own judgement.
*   [x] Deliberately does not block re-promoting an already-promoted turn -- a user might
    legitimately want the same settled answer to become a note on a second target (a Part and the
    Project it's used in); the module doesn't second-guess where a conclusion belongs.
*   [x] `_resolve_note`: the real resolver replacing `_resolve_deferred` for this one kind --
    `check_finding` is still the only genuinely deferred `SourceRef` kind now (no persisted
    ERC/DRC findings exist to resolve against).

### Phase 3: `daemon.py` wiring
*   [x] `chat_promote_turn(...)`: thin wrapper, synchronous (real local file I/O, no LLM call) --
    unlike `chat.send`. Registered independent of `tool_registry` (unlike `chat.send`, promotion
    never touches the tool registry at all).

### Phase 4: proving the cross-context connection, not just isolated tests
*   [x] `context_index.py`'s own `note` chunk extractor (CTX-206.7) was wired but inert -- no real
    `notes` field existed anywhere to read. A real integration test (`TestPromotedNoteIndexing`)
    proves the two contexts actually connect: a real `add_part_note`/`add_project_note` call, then a
    real `rebuild_index()`, then a real search that finds the promoted note and resolves its
    `SourceRef` -- not just that each context's own isolated tests pass.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (non-deviation, confirmed as designed): re-promoting an already-promoted turn is
    allowed, not blocked.**
    *   *Reasoning:* SPEC-206 §2.7's own text doesn't forbid it, and a real, legitimate use case
        exists (the same settled answer becoming a note on two different targets). Blocking it would
        be the backend guessing at user intent the spec never asked it to guess at.
    *   *Impact:* each promotion creates its own independent note with its own `note_id`; the source
        turn's `promoted_note_id` reflects only the most recent promotion, which is an honest,
        acceptable v1 limitation -- a future UI wanting "every note this turn produced" would need a
        real reverse lookup, not something this context's own scope required.
*   **Deviation 2 (real completion milestone, not a deviation): this closes out SPEC-206's entire
    backend.**
    *   *Reasoning:* `CTX-206.1` through `CTX-206.8` together cover every section SPEC-206 §2
        names -- project intent, conversation store, source references, connection-guidance
        persistence, agent dispatch, retrieval, and now promotion.
    *   *Impact:* `SPEC-318` (the actual `AgentChat` frontend surface, the `PRODUCT-PLAN.md`
        amendment it requires, and `parseCommand`'s retirement) is the only remaining SPEC-206/318
        work, and it has no backend prerequisite left unbuilt -- confirmed directly against
        `SPEC-206`'s own §2 heading list, not assumed.
