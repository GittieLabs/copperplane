# CTX-205.8: Implementation Context: Tolerant JSON Extraction and a Retry

> **Spec Reference:** Links to [SPEC-205](../specs/SPEC-205-datasheet-design-guidance.md)

`datasheet.generate_guidance` was failing roughly two runs in three against a real datasheet, and
had been for some time. It skips in CI for want of an `ANTHROPIC_API_KEY`, so nothing ever reported
it; it surfaced only because the full suite was run locally with real keys present.

The cause was two separate gaps that compounded. The model occasionally returns something that is
not quite JSON, and this route's parser could not read it; and unlike `component_pipeline`, this
route had no retry, so one bad response failed the entire job.

## 1. Feature Definition & Execution Plan

### Phase 1: find out what the model actually returns
*   [x] The error carried nothing useful -- `Expecting ',' delimiter: line 1 column 9` says a
    response was malformed and nothing about how. Captured the real payloads instead of guessing.
*   [x] Two distinct shapes, both real. One is a **self-correction**: a malformed array, then the
    line "Wait, must output JSON array only.", then the correct array. The right answer was in the
    response and `json.loads` could not reach it. The other is simply missing the opening brace of
    its first object, and contains no valid JSON at all.

### Phase 2: fix it upstream, where the gap actually was
*   [x] AgentFlow had no JSON-response parser, so this repo had hand-rolled one **twice** --
    `datasheet_guidance._extract_json` and `component_pipeline._extract_json`, both a fence-stripper
    plus `json.loads`, the duplication deliberate and documented.
*   [x] `parse_json_response` added in `agentflow` 0.12.0 (PR #13), published to PyPI. Handles
    fences, prose either side, and self-correction -- last valid candidate wins, because a model
    writes forwards and does not revise what it has already written. Both captured payloads are
    committed there as fixtures.
*   [x] Pinned to `==0.12.0` here and adopted at both sites.

### Phase 3: give this route the retry the other one already had
*   [x] `component_pipeline.generate_component` has retried malformed extraction since `SPEC-202`.
    That is why component generation mostly recovers from a bad response and guidance did not.
    Mirrored its shape rather than inventing one: two attempts, retry only on the JSON-parse error
    class, never on a citation failure.
*   [x] A citation that fails validation is the model being wrong about the datasheet, not about
    JSON. Asking again there invites a second answer that looks more plausible, not one that is
    more true.

## 4. Plan Drift & Architectural Changes

**1. I reported this bug to the maintainer as an AgentFlow bug. It was not.** The log line reads
`agentflow.workflow: Node validate failed: ...`, and I attributed it upstream on that basis.
AgentFlow was only logging a node failure; the exception came from this repo's own
`datasheet_guidance.py`. The fix still belonged upstream, but for a different reason -- AgentFlow
offered no JSON-response parser, so two consumers here had written weaker ones. Reading which
module raised the exception would have cost one grep.

**2. `expect=` was the wrong tool at both call sites, and the existing tests said so.**
`expect=dict` on `component_pipeline._extract_json` broke `search_components`, whose response is
legitimately a JSON array -- the `-> dict` annotation had been describing one of its two callers.
`expect=list` on the guidance side turned a documented behaviour into an error: `test_014` pins
that a non-list response is a real empty result, not a failure. Both constraints were dropped. The
feature is fine; these two call sites are polymorphic and cannot use it. Two tests I did not write
prevented me from shipping a behaviour change disguised as a bug fix.

**3. The executor is now built inside the retry loop, not once outside it.** The first version
reused one `WorkflowExecutor` across both attempts, which would have re-run an executor that had
already completed a pass. Caught while writing the test that counts calls, not while writing the
code.

**4. The measurement, since "it works now" is not a claim worth making about a stochastic route.**
Five consecutive live runs of `TestRealDatasheetGenerateGuidanceJob` passed, against a baseline of
roughly two failures in three. That is evidence, not proof: five runs cannot distinguish a real fix
from a quiet afternoon at the provider. What supports it beyond the count is that one of the two
captured failure shapes is now handled deterministically and pinned by a test, and the other is
what the retry exists for.

**5. A second route was failing the same way and is fixed by the same change.**
`test_component_pipeline.TestRealGenerateComponent.test_003` failed during this work with
`ATtiny85-20SU` where the test expects `ATtiny85` -- model output variance rather than a parse
error, so not this bug. But `search_components` and `generate_component` share the extractor and
both now get the tolerant parser. Neither had a test for the self-correction shape before.

**6. Not verified: the retry firing against a real provider.** The retry path is exercised by
mocks. Nothing here has watched a real model return malformed JSON and then succeed on the second
attempt, because that shape cannot be summoned on demand -- which is also why it went unnoticed for
so long.
