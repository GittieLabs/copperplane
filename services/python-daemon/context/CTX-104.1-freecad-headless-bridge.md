# CTX-104.1: FreeCAD Headless Bridge

> **Spec Reference:** Links to [SPEC-104](../specs/SPEC-104-freecad-headless.md)

## 1. Feature Definition & Execution Plan

**Scope note:** builds the subprocess handoff pipeline itself — path resolution, script generation, execution, output conversion, error handling — proven with one real shape (`freecad.generate_enclosure`, a parametric box). Richer geometry (mounting holes, fillets) is follow-up work once this pipeline is trusted.

### Phase 1: Path Resolution
*   [x] `find_freecadcmd()`: check `PATH` first, then standard per-OS install locations (SPEC-104 §3, "Path Resolution"), returning a clean error if none found.

### Phase 2: Subprocess Handoff
*   [x] Generate a temporary Python script per SPEC-104 §2 and run it via `freecadcmd <script>`, **not** `freecadcmd -c <script>` — `-c`/`--console` is a mode flag with no argument, not "run this file" (see Plan Drift).
*   [x] `stdin` must be explicitly redirected (e.g. `/dev/null`) — `freecadcmd` drops into an interactive console after running the script and hangs forever waiting on stdin otherwise (see Plan Drift; discovered by hitting a real 30s hang).
*   [x] Enforce a subprocess timeout; clean up the temp script (and any intermediate mesh file) once done.

### Phase 3: Output Conversion
*   [x] FreeCAD's own Python API has no direct `.glb`/glTF exporter (`Part.Shape` only exposes `exportStep`/`exportStl`/`exportBrep`/`exportIges`; confirmed by inspection — see Plan Drift). FreeCAD exports `.stl`; the daemon converts that to `.glb` itself via `trimesh`, outside the FreeCAD subprocess.

### Phase 4: JSON-RPC Route
*   [x] Add `freecad.generate_enclosure` to `daemon.py`'s `ROUTES`, backed by the bridge module.

### Phase 5: Testing
*   [x] Mocked unit tests: `freecadcmd` not found, build script fails (non-zero exit), subprocess timeout.
*   [x] A **real** integration test that actually runs `freecadcmd` and `trimesh` and checks the resulting `.glb` is valid — not just mocks. Skips itself gracefully if `freecadcmd` isn't found (e.g. in CI, where FreeCAD isn't installed).

## 4. Plan Drift & Architectural Changes

*   **Discovery: this machine has FreeCAD 1.1.1 installed, so the happy path can be verified for real, same as SPEC-103's KiCad bridge.**
    *   *Reasoning:* `/Applications/FreeCAD.app/Contents/Resources/bin/freecadcmd --version` → `FreeCAD 1.1.1`. Confirmed a real box → STEP export before writing any of this feature's code.
    *   *Impact:* `TEST-004` exercises a genuinely running `freecadcmd`, not a mock. CI (no FreeCAD installed there) only runs the mocked tests — `TEST-004` skips itself cleanly rather than failing when `freecadcmd` isn't found.
*   **Deviation 1: `freecadcmd` has no direct `.glb`/glTF export at the Python scripting level.**
    *   *Reasoning:* SPEC-104's data flow says FreeCAD "saves a `.glb`," but `Part.Shape`'s only export methods are `exportStep`/`exportBrep`/`exportBrepToString`/`exportIges`/`exportStl`/`exportBinary` — confirmed by direct inspection inside a running `freecadcmd` session. The OpenCASCADE glTF writer (`libTKDEGLTF`) is present in the app bundle, but not exposed through FreeCAD's own Python API in this build; reaching it would mean depending on FreeCAD's bundled `OCC.Core` pythonocc bindings directly, with real risk of an ABI mismatch between FreeCAD's statically-linked OCC and that bundled pythonocc package.
    *   *Impact:* Chose the lower-risk path: `freecadcmd` exports `.stl` (well-supported, confirmed working), and the **daemon itself** (not FreeCAD) converts `.stl` → `.glb` via `trimesh` — a new daemon dependency, added to `requirements.txt`. Confirmed the full round trip produces a real, valid glTF binary (`file` reports `glTF binary model, version 2`), not just a renamed STL.
*   **Deviation 2: `freecadcmd -c <script>` does not run a script file — hung for a real 30 seconds discovering this.**
    *   *Reasoning:* `-c`/`--console` is documented as "Starts in console mode," a mode flag with no argument — not `python -c` semantics. Passing a script path as if it were `-c`'s argument actually passed the script as a separate positional file argument, which `freecadcmd` did run correctly — but console mode then drops into an interactive Python prompt afterward and blocks on stdin forever if not redirected. The fix is `freecadcmd <script>` (positional, no `-c`) with `stdin=subprocess.DEVNULL` so EOF is immediate and it exits after the script completes.
    *   *Impact:* Without this, any real deployment would silently hang forever on the very first request. `bind_child_lifetime`-style crash-shield concerns from SPEC-101 don't apply here (this daemon calls `subprocess.run(..., timeout=...)`, not a long-lived child), but the timeout is still essential as the second layer of defense.
