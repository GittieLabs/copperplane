# CTX-308.5: Implementation Context: Datasheet-Generated Footprint (Source Three)

> **Spec Reference:** Links to [SPEC-308](../../../apps/tauri-ui/specs/SPEC-308-footprints-schematic-advisor.md)

**The third and, until now, fully open of `PRODUCT-PLAN.md` §8 item 3's three ranked footprint
sources.** `CTX-308.1`/`CTX-308.3` (installed KiCad libraries) and `CTX-308.4` (the user's own
saved library) both explicitly named this as deferred, not attempted. This context closes it:
generate a Footprint from a Part's own already-extracted datasheet package dimensions, with no
second LLM call.

## 1. Feature Definition & Execution Plan

### Phase 1: Persist `package_dimensions`/`courtyard` on Part (a real, pre-existing gap)
*   [x] Confirmed by direct code read, not assumed: `library_save_confirmed_part` (`daemon.py`)
    silently dropped `extraction["package_dimensions"]`/`extraction["courtyard"]` even though
    `component_extraction.prompt.md`'s own schema already returns them alongside `package`/`pins`.
    Without this fix, a saved Part carries no usable dimensions for footprint generation at all.
*   [x] `daemon.py::library_save_confirmed_part`: persist both fields on the saved Part, with
    `llm_extraction` provenance recorded for each (same shape as `package`/`pins`).
*   [x] `library_store.py::PART_PROVENANCE_REQUIRED_FIELDS`: added `package_dimensions`/
    `courtyard` -- SPEC-300 §2.2's "every inferred field must record its source" rule applies to
    them exactly as much as `package`/`pins`, not a lesser field.

### Phase 2: `kicad.generate_footprint_from_part` route
*   [x] `daemon.py`: new synchronous route (no LLM call, no live KiCad IPC -- pure computation
    over an already-saved Part, matching `kicad.search_footprints`'s own precedent for why it's
    NOT in `ASYNC_ROUTES`). Loads the Part, reuses `kicad_write.generate_pad_layout` (the same
    pure geometry function `SPEC-108`'s live inject path already calls) on its `package`/`pins`/
    `package_dimensions`, builds a Footprint record, and persists it via
    `library_store.save_footprint`.
*   [x] Fails closed, not a silent guess: a Part missing any of `package`/`pins`/
    `package_dimensions`/`courtyard` (e.g. one saved before Phase 1's fix) raises a clean,
    specific `SchemaValidationError` before `generate_pad_layout` is ever called. A package
    outside `kicad_write.SUPPORTED_PACKAGES` propagates `UnsupportedPackageError`'s own message
    unwrapped -- the same fail-closed choice `component_pipeline.validate_schema` already makes
    for an unrecognized package.
*   [x] `kicad_write` given its own guarded import in `daemon.py` (matching every other bridge
    module's pattern) rather than importing it through `kicad_bridge`, since this route needs no
    live KiCad connection at all -- `kicad_bridge.py`'s own module docstring scopes it to
    "Connection lifecycle to a running KiCad instance," which this genuinely isn't.
*   [x] Footprint provenance recorded (`source: "datasheet_generation"`, `generated_from_part_id`,
    `verified: false`) but deliberately NOT enforced as a required field on `save_footprint` --
    `SPEC-308` §3 itself scopes this slice to *recording* provenance for generated footprints,
    not retrofitting a hard requirement onto the already-shipped found-footprint attach flow
    (`CTX-308.2`), which never sent provenance and would break under a new required-field check.

### Phase 3: Frontend wiring
*   [x] `apps/tauri-ui/src/lib/footprints.ts`: `generateFootprintFromPart(part)` -- calls the new
    route, then re-saves the Part with the resulting `footprint_id`, mirroring
    `attachFootprintToPart`'s own two-call shape.
*   [x] `apps/tauri-ui/src/components/PartDetail.tsx`: a "Generate from datasheet dimensions"
    button in the Find Footprint section, always available (not gated behind a zero-result
    search -- a user who already expects nothing installed will match shouldn't have to search
    first). On success, "Footprint linked" shows an amber "(generated from datasheet dimensions —
    unverified)" annotation a found footprint never gets.
*   [x] That annotation is deliberately local-only UI state (`footprintGenerated`), not derived
    from `savedPart` itself -- there's no cheap way to tell "generated" from "found" apart from
    `footprint_id` alone without a second `load_footprint` round trip. Named as a real, narrow
    limitation in Plan Drift below, not silently glossed over.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: source three needed no new LLM call at all, once a real, pre-existing gap was
    found -- a significant, favorable scope reduction from what `SPEC-308` §3 implied.**
    *   *Reasoning:* `SPEC-308` framed "datasheet generation" as parallel to `SPEC-202`'s
        extraction pipeline, which read as needing a second AgentFlow workflow. Reading
        `component_pipeline.py` and `daemon.py::library_save_confirmed_part` directly first (this
        repo's own "verify against the real thing" norm) found that the extraction call already
        returns `package_dimensions`/`courtyard` -- `library_save_confirmed_part` just never
        persisted them. `kicad_write.generate_pad_layout` (already real, already used by `SPEC-108`'s
        live inject path) turns exactly those fields into real pad geometry. No new prompt, no new
        AgentFlow workflow, no new LLM cost or latency, and no risk of a second extraction
        disagreeing with the first.
    *   *Impact:* Phase 1 (persisting the two fields) became this context's real prerequisite,
        not a footnote -- without it, source three would have had nothing to work from. Documented
        here explicitly because it changes what "source three" actually costs in the future: it's a
        genuinely cheap, synchronous, already-known-data operation, not a second network-bound
        extraction.

*   **Deviation 2: `kicad.inject_component`'s real, current caller (the old chat/command surface,
    `App.tsx`) doesn't read from a saved Part or Footprint at all -- confirmed directly, not
    assumed, before deciding this context's own scope boundary.** `App.tsx`'s inject flow holds
    the full extraction schema in React state (`latestSchema`) from a just-run
    `kicad.generate_component` call and passes it straight to `kicad.inject_component`, entirely
    independent of `library_store`. `PRODUCT-PLAN.md` §5.2 already marks this surface as being
    phased out. This context's new Footprint records are real and persisted, but wiring them into
    an actual board-write path is out of scope here -- matching `SPEC-308` §1's own explicit
    non-goal ("Not redesigning `kicad.inject_component`'s own write path") -- and would need to
    happen through Part Detail's real flow once that inject path exists there, not this one.

*   **Deviation 3: the "generated vs. found" badge is real but shallow -- session-local UI state,
    not derived from persisted truth.** `footprintGenerated` in `PartDetail.tsx` is set only when
    the user takes the generate action *in this session*; reopening the app or revisiting the part
    would lose it, since the UI never re-fetches the linked Footprint record to check its
    provenance. The real provenance (`source: "datasheet_generation"`, `verified: false`) is
    genuinely persisted on the Footprint record itself and survives -- only the UI's own display of
    it doesn't yet. Named here rather than silently accepted: a correct fix is a
    `library.load_footprint` call when `savedPart.footprint_id` is set, which was judged out of
    this context's own scope (an extra round trip and loading state for a cosmetic badge) rather
    than silently assumed unnecessary.

*   **Deviation 4: real verification stopped at automated tests -- no live click-through in the
    actual running Tauri window this session, consistent with this project's own documented
    verification gap.** Every backend behavior is verified for real (real file I/O against a real
    temp `storage_root`, real geometry compared directly against `kicad_write.generate_pad_layout`'s
    own output, not a mock of it). The frontend is verified through Testing Library against the
    real component tree, not just type-checked. But no human (or automated) click-through happened
    in the real, native Tauri window -- the same gap this repo's own memory already tracks for prior
    UI work (accessibility permissions not available in this session). State explicitly: this is
    unverified as a real user would experience it, not verified-and-omitted.

*   **Deviation 5: a real, live-LLM test flake surfaced during full-suite verification, unrelated
    to this change.** `tests.test_component_pipeline.TestRealGenerateComponent
    .test_003_real_extraction_via_an_overridden_provider` failed once (expected `"ATtiny85"`, a
    real live model call returned `"ATtiny85-20SU"`), then passed 3 of 4 times on repeated,
    isolated reruns. Confirmed via `git diff` that this branch touches neither
    `component_pipeline.py` nor its test file. Non-deterministic real LLM output, not a regression
    this context introduced or should attempt to fix.
