# CTX-205.1: Datasheet Structure Pass

> **Spec Reference:** Links to [SPEC-205](../specs/SPEC-205-datasheet-design-guidance.md)

## 1. Feature Definition & Execution Plan

`SPEC-205` is a large, genuinely novel feature: a multi-stage retrieval pipeline over a real
datasheet PDF (structure pass -> Class A/typed extraction -> Class B/cited extraction -> Class C/
labelled general practice -> citation validation -> assembly), a new `.workflow.md` AgentFlow DAG,
a new Part-record field with its own provenance shape, a new async daemon route, and a new Part
Detail UI panel with per-pin filtering. Attempting all of that in one context would be exactly the
kind of big-bang implementation this repo's own history argues against (`SPEC-308` shipped across
7 contexts, `SPEC-311` across 16). **This context deliberately ships only the structure pass** --
real PDF text extraction plus deterministic, non-LLM candidate-section location -- as an
independently real, testable, reviewable first slice. Every extraction class, the AgentFlow
workflow itself, the new daemon route, Part-record storage, and the UI panel are explicitly out of
scope here and left to `CTX-205.2`+.

**Real research performed before planning, not assumed:**
*   **AgentFlow is already wired in, with one real precedent to model future work on** --
    `services/python-daemon/agentflow/workflows/component_intelligence.workflow.md` (a real
    two-node `extract -> validate` DAG) and `component_pipeline.py`'s `generate_component` (the
    real orchestration shape: `ConfigLoader` -> `WorkflowExecutor` -> `asyncio.run`, with a real,
    already-fixed provider-client-leak gotcha -- `_build_agent_executor` returns
    `(executor, provider_client)` so every client gets closed in the same `finally` block). This
    context does not touch any of that yet -- named here because `CTX-205.2` (the real extraction
    DAG) will need to copy this exact shape, not invent a new one.
*   **The real provenance shape SPEC-205 §2.3 says it extends**: `library_store.py`'s
    `PART_PROVENANCE_REQUIRED_FIELDS` and `_validate_part_provenance` enforce a flat
    `{"source": ..., ...}` per required field today -- no `page`/`section`/`document_revision`/
    `content_hash` key exists anywhere yet. Real, concrete confirmation that SPEC-205's own
    citation-provenance work (§3: "store the document revision and a content hash alongside the
    citation") is genuinely new ground, not an existing pattern to reuse verbatim -- also not
    touched by this context, since there's no guidance data to store yet.
*   **The real datasheet a user would already have cached**: `library_store.cache_datasheet
    (part_number, datasheet_url) -> str` already fetches and writes a real PDF to
    `library/datasheets/<part_number>.pdf` (`SPEC-306`). This context's own `extract_pages`
    consumes exactly that real local path shape -- no new fetch/cache logic needed here.
*   **No PDF library existed in this repo before this context** -- confirmed by grep across
    `services/python-daemon` and `requirements.txt`. `pdfplumber` (MIT; its own real dependencies
    `pdfminer-six`/`pillow`/`pypdfium2` are all permissively licensed too, checked given `SPEC-904`'s
    own license-consistency norm) was chosen over `pymupdf`/`fitz` specifically because the latter
    is AGPL-3.0-licensed (dual-licensed, a paid commercial license is the alternative) -- a real,
    deliberate avoidance, not an arbitrary pick. `pdfplumber` also carries forward cleanly into a
    future Class A (tabular) extraction phase (it has real table-extraction support `pypdf` alone
    does not), so this isn't a library this repo will need to swap out later.
*   **A real, committed PDF fixture, not a mock**: no datasheet PDF existed anywhere in this repo's
    test fixtures before this context (confirmed by `find -iname "*.pdf"`). Generated a real,
    8-page synthetic datasheet (`tests/fixtures/sample_datasheet.pdf`, via `reportlab` -- used only
    once, locally, to produce this static binary asset; **not** added to `requirements.txt`, since
    CI only ever needs to *read* the committed fixture via `pdfplumber`, never regenerate it) with
    real prose mirroring `SPEC-205 §2.2`'s own named structure-pass targets (Absolute Maximum
    Ratings, Recommended Operating Conditions, Power Supply Decoupling, Reset, Clock/Oscillator,
    Layout Considerations, Typical Application Circuit), one section per page.

**Real design decision: candidates are not exclusive, and the fixture proved it in a real test
run.** The first version of this context's own tests asserted an exact single page per category
(e.g. `reset` found only on page 5) -- two of those assertions genuinely failed against the real
fixture: "reset" also matches page 2 (the Absolute Maximum Ratings table says "Voltage on any Pin
except RESET") and page 8 (the Typical Application text mentions "reset circuit" in passing);
"clock_oscillator" also matches page 1 (a features-list mention of "Real Time Counter with Separate
Oscillator") and page 7 (Layout mentions "crystal"/"oscillator" pins). This is real, correct
behavior, not a bug in either the fixture or the matcher -- a real datasheet's sections genuinely
cross-reference each other this way. Fixed by loosening those two assertions to `assertIn` (a real
category's own section page must be among its candidates) rather than `assertEqual` (must be the
*only* candidate) -- matching this function's own real contract: it returns *candidates* for a
later extraction stage to narrow, not a final, exclusive section assignment.

### Phase 1: `datasheet_structure.py` -- real PDF text extraction & candidate location
*   [x] New `services/python-daemon/datasheet_structure.py`: `extract_pages(pdf_path: str) ->
    list[dict]` -- real, 1-indexed `[{"page": N, "text": "..."}]` (1-indexed to match how a
    citation is shown to a user, `§7.2 · p31`, not `pdfplumber`'s own 0-indexed internal list). A
    page with no extractable text (e.g. a scanned image) gets an empty string, never a skipped
    entry -- every real page number that exists in the document must be referenceable later.
*   [x] `DatasheetStructureError` -- a real, unreadable/corrupt PDF (or a real path to a
    non-PDF file) fails closed with a clean exception, not a silent empty result -- distinguishable
    from "a real, readable document with genuinely nothing found."
*   [x] `CATEGORY_PATTERNS` -- the 8 real structure-pass targets `SPEC-205 §2.2` names
    (`absolute_maximum_ratings`, `recommended_operating_conditions`, `power`, `decoupling`,
    `reset`, `clock_oscillator`, `layout`, `typical_application`), each a real, case-insensitive
    regex matched against a page's full extracted text (not just heading-formatted lines -- real
    datasheets vary heading formatting too much across manufacturers to rely on that alone).
*   [x] `locate_candidate_sections(pages: list[dict]) -> dict[str, list[int]]` -- every real
    category is present in the result even with zero matches (an empty list, not an omitted key),
    so a caller can tell "checked, found nothing" from "never checked."
*   [x] `requirements.txt`: add `pdfplumber==0.11.10`, with a comment naming the license check
    performed and that no PDF library existed in this file before.

### Phase 2: real fixture + tests
*   [x] `tests/fixtures/sample_datasheet.pdf` -- a real, committed, 8-page synthetic datasheet
    (generated once via `reportlab`, not a repo dependency).
*   [x] `tests/test_datasheet_structure.py`: `extract_pages` (page count, 1-indexing, real text
    content, a real unreadable path, a real non-PDF file both failing closed);
    `locate_candidate_sections` (every category present in the result; each of the 8 real
    categories found on its own real page, using `assertIn` where a real cross-reference means a
    category legitimately isn't page-exclusive; a category with zero real matches is an empty list,
    not omitted).
