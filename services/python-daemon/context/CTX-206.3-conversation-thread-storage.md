# CTX-206.3: Implementation Context: Conversation Thread Storage & Migration

> **Spec Reference:** Links to [SPEC-206](../specs/SPEC-206-agent-context-store.md)

**Scope note:** the third slice of `SPEC-206`, scoped to the storage substrate of §2.2 -- thread
path resolution (project-scoped by area, part-scoped globally), the real turn record shape, migration
from the legacy `conversation.jsonl`, and the two read-only routes the spec names for this layer
(`chat.load_thread`, `chat.list_threads`). Deliberately does **not** build `chat.send` or an
`append_turn` write API -- both need the agent/router layer `SPEC-206` §2.5 defines, which is real,
separate, later work. The one write path this context does build (`_write_thread_turns`) exists only
because migration itself needs to write the upconverted thread once; it has no other caller yet.
`SPEC-206` §2.3's `SourceRef` validation is likewise not built here -- turns in this slice carry an
empty `sources: []` by construction (real turns, from migration, never had any), so there is nothing
yet to validate.

## 1. Feature Definition & Execution Plan

### Phase 1: Thread path resolution (`library_store.py`)
*   [x] `_project_thread_path(project_name, area)` -- resolves a project-scoped thread's real path,
    following `CTX-312.1`'s directory link exactly like `save_project`/`load_project` already do
    (read the storage-root pointer directly, not `project_directory()`'s single return value, since
    linked vs. unlinked need different subpath nesting -- `.hardware-agent-studio/chats/<area>.jsonl`
    for linked, `chats/<area>.jsonl` directly for unlinked). Validates `area` against the four
    real project-scoped areas (`overview`/`schematic`/`pcb`/`enclosure` -- "components" is
    Part-scoped, never project-scoped, per `SPEC-206` §2.2's own table).
*   [x] `_part_thread_path(part_id)` -- `<storage_root>/library/chats/parts/<part_id>.jsonl`, always
    global, matching `_parts_dir()`'s own `_ensure_dir` convention.
*   [x] `_thread_path(scope, scope_id)` -- the real dispatcher: `scope_id` for `"project"` is
    `"<project_name>:<area>"` (parsed via `str.partition`, rejecting a missing area rather than
    guessing one); `scope_id` for `"part"` is just the part id.

### Phase 2: Turn storage + migration
*   [x] `_read_thread_turns`/`_write_thread_turns` -- plain JSONL read/write, matching this file's
    existing canonical-JSON convention (`sort_keys=True`, same as `append_conversation_turn`).
*   [x] `_upconvert_legacy_turn` -- the real `SPEC-206` §2.2 turn shape from a legacy
    `{role, content, timestamp?}` record: `timestamp` preserved verbatim (even `None`), never
    re-stamped with the current time; `general_practice: True` for an upconverted assistant turn
    (it genuinely was never grounded in a cited record).
*   [x] `_migrate_legacy_conversation` -- on first read of a project's `overview` thread with no
    `chats/overview.jsonl` yet, upconverts the real legacy turns and writes them once; the legacy
    file is left in place; `migrated_from` lands on the first new record only.
*   [x] `load_thread(scope, scope_id)` -- the real public read, triggering migration exactly once
    (a second read finds the new file and never re-migrates, confirmed by a real test appending a
    legacy turn *after* the first migration and proving it never reappears).
*   [x] `list_threads(project_name)` -- real areas with history, including an as-yet-unmigrated
    legacy `overview` thread so a caller can discover it before ever calling `load_thread`.

### Phase 3: Routes (`daemon.py`)
*   [x] `chat_load_thread(scope, scope_id)` / `chat_list_threads(project_name)` -- thin wrappers,
    registered synchronously (real, fast local file I/O; not `ASYNC_ROUTES` -- `chat.send` is where
    an LLM call actually happens, a separate slice).

### Phase 4: Tests
*   [x] `tests/test_library_store.py`: `TestChatThreads` (scope/area validation, real round trips
    for both project- and part-scoped threads), `TestChatThreadDirectoryLinkFix` (the real bug
    `SPEC-206` §2.2 names -- a linked project's thread now lives inside its own real directory, not
    stranded under the storage root), `TestChatThreadMigration` (9 tests: real upconversion,
    `general_practice` correctness, `migrated_from` placement, non-destructive legacy file,
    migrate-once semantics, the no-legacy-history case, `list_threads` in every state).
*   [x] `tests/test_daemon.py`: `TestChatThreadRoutes` -- both routes work end-to-end through a real
    migration, both registered synchronously.
*   [x] Full suite: `python3 -m unittest discover tests` -- **524 passed, 6 skipped**, 0 failures.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (non-deviation, confirmed as designed): `general_practice: True` for every
    upconverted legacy assistant turn was a real judgment call, not spelled out verbatim by
    `SPEC-206`.**
    *   *Reasoning:* `SPEC-206` §2.2 defines the turn shape and says `general_practice` means
        "assistant turn not grounded in a cited record," but doesn't explicitly say what a migrated
        legacy turn (which never had a citation mechanism at all) should carry. `True` is the
        honest, structurally-forced answer: it genuinely was never grounded in anything, and marking
        it otherwise would misrepresent history the app has no way to retroactively cite.
    *   *Impact:* Migrated turns render (once a frontend reads them) with whatever visual treatment
        `SPEC-318`'s general-practice segregation uses -- correct, since no old turn has real sources
        to show either way.
*   **Deviation 2 (non-deviation, confirmed as designed): `_project_thread_path` re-reads the
    storage-root pointer directly rather than calling the existing `project_directory()` helper.**
    *   *Reasoning:* `project_directory()` returns one path (linked directory or storage-root project
        dir) with no signal about *which* case produced it -- but the two cases need different
        subpath nesting (`.hardware-agent-studio/chats/<area>.jsonl` vs. `chats/<area>.jsonl`
        directly), the same real distinction `save_project`/`load_project` already handle by reading
        the pointer's `directory` key themselves rather than through that helper. Reusing the
        3-line pointer-read pattern those functions already establish, rather than reusing a helper
        whose return value can't disambiguate the case that matters here.
    *   *Impact:* None on correctness; confirmed directly by `TestChatThreadDirectoryLinkFix`'s own
        real linked-directory test.
