# CTX-204.2: Implementation Context: Tool Names Every Provider Accepts

> **Spec Reference:** Links to [SPEC-204](../specs/SPEC-204-agent-tool-registry.md)

## 0. The report

Reported from the built app, immediately after `SPEC-336`'s guided setup configured the first
Anthropic key this project has ever actually used:

```
Error code: 400 - {'type': 'error', 'error': {'type': 'invalid_request_error',
'message': "tools.0.custom.name: String should match pattern '^[a-zA-Z0-9_-]{1,128}$'"}}
```

**Every AI feature was broken on Anthropic.** Not the review alone — every chat turn, every part
lookup, every agent that is offered a tool. Anthropic validates each tool name against
`^[a-zA-Z0-9_-]{1,128}$` and rejects the entire request if any one fails. All nine of this app's
tools are named for their dotted JSON-RPC routes — `kicad.check_board`, `context.search` — and a
dot is not in that character class. Not one of them was ever acceptable.

**Why it survived this long:** the maintainer's `provider_roles` were bound to Google, which
accepts dots. The app has been shipping an Anthropic provider record, an Anthropic API key field
and Anthropic as `_DEFAULT_PROVIDER` for months, against an Anthropic integration that could not
execute a single tool call. The first person to actually bind the roles to Anthropic found it in
one click.

## 1. Feature Definition & Execution Plan

### Phase 1: Translate at the registry boundary
*   [x] `tool_name_for_route()` — the one place a route name becomes a tool name.
*   [x] `ROUTE_FOR_TOOL` — the reverse map, so a call dispatches back to `daemon.ROUTES`.
*   [x] Routes keep their dots. They are the JSON-RPC wire and nothing about that changes.
*   [x] `_wrap_route` still receives the route, so confirmation gating and every existing
        comparison against a route name work untouched.

### Phase 2: The prompts
*   [x] Rename every tool reference in the five `chat_*.prompt.md` files. A prompt naming
        `context.search` describes a tool the model is never offered under that name.

### Phase 3: Prove it, including against the real API
*   [x] A guard asserting every registered name matches the pattern, confirmed to fail against the
        reintroduced bug.
*   [x] Collision and reversibility tests — two routes mapping to one tool name would silently
        dispatch to the wrong handler.
*   [x] One real Anthropic request carrying this app's actual nine-tool payload.
*   [x] A real DRC review driven into the **frozen sidecar** on Anthropic, end to end.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: this is not AgentFlow's bug, and it was worth checking before assuming.**
    `agentflow/providers/anthropic.py` forwards `tools` verbatim into `messages.create`, which is
    correct — a provider adapter that silently rewrote caller-supplied tool names would be worse.
    The invalid names are ours. Recorded because this repo's standing rule is to fix AgentFlow bugs
    upstream, and applying that rule here would have shipped a rewrite into a shared library to
    paper over a naming choice in one app.

*   **Deviation 2: the test that existed asserted the wrong side of the translation.**
    `test_001_every_tool_named_by_a_real_agent_prompt_is_registered_and_available` checked prompt
    names against `TOOL_DEFINITIONS` keys — the routes. It passed throughout, because the prompts
    and the definitions agreed with each other while both disagreed with what Anthropic accepts.
    Two artifacts can be perfectly consistent and both wrong. It now checks the name the *model*
    is offered.

*   **Deviation 3: a regex test would not have been enough on its own.** `TEST-001` asserts the
    names match a pattern I copied out of an error message. That proves the names match my
    reading of the error, not that the API accepts them. So the fix is also verified by one real
    Anthropic request carrying the actual nine-tool payload, and then by a real DRC review through
    the frozen sidecar. The review came back with a genuine plain-language explanation of two
    unconnected-item errors on the maintainer's own board — the operation that had returned a 400.

*   **What this says about the test suite.** 1031 daemon tests passed against a build where no AI
    feature could work on the default provider. Every one of them either mocked the provider or
    used Google. There is no test that runs a tool-using agent against Anthropic, and until this
    context there was nothing asserting the constraint either. The new guard is cheap and static;
    the gap it closes was neither.

    the same way before this change.
*   **Not verified:** Google, OpenAI and Perplexity were not re-tested after the rename. They
    accepted the dotted names and the new names are a strict subset of what they allow, so the risk
    is low — but "low risk" is an argument, not a test, and it is recorded as such.
