# CTX-308.7: Implementation Context: Per-Pin Connection Guidance

> **Spec Reference:** Links to [SPEC-308](../../../apps/tauri-ui/specs/SPEC-308-footprints-schematic-advisor.md)

`SPEC-308` §1's third named concern -- "connection guidance (decoupling, protection, power) once a
part and its footprint are both real" -- and `PRODUCT-PLAN.md` §6 M3's last remaining piece. Unlike
`CTX-308.5`/`.6`, this was completely unstarted before this context: no route, no prompt, no UI
placeholder, confirmed by a repo-wide grep before any code was written.

## 1. Feature Definition & Execution Plan

### Phase 1: `connection_guidance` agentflow prompt + pipeline function
*   [x] New `agentflow/agents/connection_guidance.prompt.md`: given a part's number, package, and
    real pin list (number/name/electrical_type), returns per-pin guidance (required for every
    `power`/`ground` pin, optional elsewhere -- no manufactured advice for a plain I/O pin with
    nothing real to say) plus one general-notes string. Modeled directly on
    `component_search.prompt.md`'s own "respond with ONLY a single JSON object" convention.
*   [x] `component_pipeline.py::generate_connection_guidance` + `_validate_connection_guidance`: a
    single standalone agent call (like `search_components`, no DAG/handler-node split needed) with
    one real safety check -- every `pin_number` the response references must be a real pin on the
    part. A hallucinated pin reference would point the user at the wrong physical pin, the same
    category of consequence `validate_schema`'s courtyard/pitch checks exist to prevent for
    footprint geometry, applied here to advisory text.

### Phase 2: `kicad.generate_connection_guidance` route + frontend
*   [x] `daemon.py`: new route, loads the Part (`package`/`pins`) and threads
    `CONFIG["llm_provider"]`/`["llm_model"]`/secrets through exactly like
    `kicad_generate_component`/`component_search` already do. A real LLM call, so registered in
    `ASYNC_ROUTES` -- unlike `CTX-308.5`'s footprint-generation route, which genuinely needed no
    network call at all.
*   [x] `apps/tauri-ui/src/lib/partDetail.ts::getConnectionGuidance` (via `submitJob`, matching
    `extractPartDetail`'s own async-route precedent) + `PartDetail.tsx`: a "Get Connection Guidance"
    button in the Footprint-linked state, available once a part and its footprint are both real
    (`SPEC-308` §5's own stated product stage) -- not gated on the footprint being generated
    (`footprintGenerated`); guidance is exactly as useful for a found footprint as a generated one.
*   [x] Renders per-pin guidance as a list plus the general notes; an empty `pin_guidance` list
    renders an honest "No pin-specific guidance for this part" message, not an error -- a real,
    legitimate answer the schema itself allows (see `TestValidateConnectionGuidance.test_007`).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: guidance is deliberately not persisted on the Part record -- session-local,
    regenerable on demand, a scope decision made explicitly rather than by default.** Unlike Part's
    `package`/`pins`/`package_dimensions`/`courtyard` (all real, structural facts about the part,
    `CTX-308.5` made these provenance-required), connection guidance is advisory text, not a fact --
    it can legitimately change if regenerated (a different model, a different day). Persisting it
    would mean designing a new provenance shape and a staleness story (does it get invalidated if
    the part's pins change?) for content whose real value is "ask again when you want it," not "read
    once and trust forever." Kept out of scope here; `guidance`'s own local `useState` in
    `PartDetail.tsx` is lost on remount, same tradeoff `CTX-308.5`'s `footprintGenerated` badge
    already made and named explicitly.
*   **Deviation 2: no deterministic validate-DAG handler node, unlike `generate_component`.**
    `generate_component`'s two-node DAG (`extract` then a separate `validate` handler) exists
    because `SPEC-202`'s validation (package/pin-count/pitch/courtyard cross-checks against
    `PACKAGE_REFERENCE`) is real, multi-field, domain-specific logic worth isolating as its own
    testable unit. This context's one real check (every `pin_number` is real) is a single
    membership test against data already in hand -- cheap enough to run inline in
    `generate_connection_guidance` itself, mirroring `search_components`' own single-agent-call
    shape (no DAG) rather than inventing a one-line handler node for symmetry with
    `generate_component`.
*   **Deviation 3: this closes out `SPEC-308`'s full stated scope.** All three ranked footprint
    sources (`CTX-308.1`/`.3`/`.4`/`.5`), export to a real `.pretty` library (`CTX-308.6`), and
    per-pin connection guidance (this context) are now real. `PRODUCT-PLAN.md` §6 M3 and the root
    `README.md`'s M3 status line are both updated in this same commit to reflect that -- `SPEC-308`
    itself is left at `status: Draft` in its own frontmatter, consistent with every other completed
    spec in this repo (confirmed via `/spec-status`: almost none of the shipped specs have ever had
    their frontmatter flipped, tracked as a known, pre-existing inconsistency, not something this
    context's own job is to fix).
