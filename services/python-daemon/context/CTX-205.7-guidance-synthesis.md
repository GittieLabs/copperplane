# CTX-205.7: Plain-Language Guidance Synthesis

> **Spec Reference:** Links to [SPEC-205](../specs/SPEC-205-datasheet-design-guidance.md)

## 1. Feature Definition & Execution Plan

The real, direct answer to a live product question the user raised after using `CTX-205.4`'s
shipped panel against the real ATtiny85 datasheet, after `CTX-205.5`/`CTX-205.6` had already fixed
every real extraction/citation bug found: even *correctly* cited, verbatim datasheet prose is not
the right reading experience for this feature's real audience. The user's own words: the audience is
"a maker/hobbyist... not a practicing hardware engineer," who needs "practical information that lets
them use [the part] in a project, the limitations, pin functions, and other things that can provide
insights" without "going too technical" -- since a reader who wants the deep technical version can
already read the datasheet directly, which is the whole reason this feature exists.

**Real design decision, made with the user rather than guessed at unilaterally**: of three real
directions considered (a synthesis layer over existing citations; a full category-taxonomy
redesign around hobbyist tasks; something else), the user chose to proceed on the synthesis
direction and iterate from a real, concrete result. `SPEC-205` §1/§2.1.1/§5 were amended in this
same context to record this real decision and its rationale before implementing it -- **not** a
fourth output class, and **not** a weakening of the citation contract: no new citable fact is ever
introduced by synthesis; it is a grounded translation of already-validated Class B items, skipped
entirely for a category with zero validated items (same real "empty is honest, don't call the LLM"
discipline `CTX-205.2`/`.3` already established for extraction itself).

**Real implementation, mirroring the established `extract -> validate` DAG pattern**: a second,
single-node AgentFlow workflow (`datasheet_guidance_synthesis.workflow.md`) runs a
`datasheet_guidance_synthesis` agent over one category's already-validated items (never the raw
page excerpts -- only what already survived citation validation), producing one short (2-4
sentence) plain-language paragraph. The prompt is explicit and testable about what "plain language"
means here: no invented facts, no general electronics tutoring, honest about sparse input rather
than padding it, and reads past known PDF-extraction artifacts (subscript variable names wrapped
across lines, a real, separate, not-yet-fixed issue found during `CTX-205.6`'s own verification)
rather than reproducing them.

**Real, verified quality** against the actual, live ATtiny85 PDF that started this whole thread
(with a real Anthropic call, not asserted from the prompt text alone): the four categories checked
(`power`, `reset`, `clock_oscillator`, `absolute_maximum_ratings`) each produced a genuinely
readable, accurate, hobbyist-pitched paragraph -- e.g. `power`'s summary correctly surfaces the
brown-out/EEPROM-corruption risk and the Brown-out Detector mitigation from its own cited excerpts,
in plain language, without inventing anything beyond what those excerpts state. Full real output
recorded in this session's own working transcript, not reproduced here verbatim (the underlying
datasheet is copyrighted vendor content).

**Storage, following this repo's real, established schema-evolution convention** (read-time
backfill via `setdefault`, never a `schema_version` bump): `design_guidance` gains a sibling
`category_summaries: {category: str | None}` dict, alongside the existing `categories` dict --
deliberately NOT nested inside `categories` (would have required migrating/re-validating the
existing item-list shape) and deliberately NOT collapsing `categories`'s own `None`-for-never-
generated semantics into this new field (a summary of `None` for one category means "this specific
category had no valid items to summarize," a real, different state from the whole
`design_guidance` being `None`). A record saved before this context shipped backfills
`category_summaries` to `{}` on read, never re-triggering generation.

**Explicitly out of scope for this pass, named honestly rather than silently deferred**: the
frontend does not yet render `category_summaries` at all (`CTX-205.8`, next); Class A (typed
facts) and Class C (general practice) still don't exist on the backend; the category taxonomy
itself (Power/Decoupling/Reset/Clock/Layout/etc.) is unchanged, even though the user's second
proposed direction (task-oriented categories) remains a real, live option for a future pass if the
synthesis layer alone doesn't fully solve the audience-fit problem once shown in the running app.

  -- 260/260 real and passing, including 3 real live LLM-call tests (2 pre-existing extraction, 1

  four real categories (`power`, `reset`, `clock_oscillator`, `absolute_maximum_ratings`), verified
  by direct read of each real generated summary for accuracy and groundedness against its own
  underlying cited excerpts -- not just that the call succeeded.
- **Named, honest, real limitation**: the synthesis prompt cannot itself verify groundedness beyond
  instructing the model not to invent facts -- there is no automated check (e.g. entailment scoring)
  that a given summary sentence is actually supported by its category's cited items, unlike the
  hard, mechanical citation check `_quote_appears_on_page` already provides for the items
  themselves. This is a real, structural difference between the summary (soft-constrained by prompt)
  and the citations underneath it (hard-constrained by code) -- named honestly, not glossed over.
