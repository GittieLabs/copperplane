# CTX-202.5: Implementation Context: The Symbol Fix That Did Not Work, and Advice That Did Not Help

> **Spec Reference:** Links to [SPEC-202](../specs/SPEC-202-component-intelligence-pipeline.md)

Two fixes from `CTX-202.4` were wrong. Both shipped, both were reported from the running app within
the hour, and both were wrong in the same way: plausible, tested, and never once looked at.

## 1. Feature Definition & Execution Plan

### Phase 1: the symbol still overlapped
*   [x] `CTX-202.4` widened the symbol body from the longest pin name **on each side**, reasoning
    that if each side's longest name fits its own half, nothing can cross the middle.
*   [x] That is the wrong constraint. KiCad draws a pin name inward from the body edge, so on any
    given row the left name and the right name grow **towards each other** and it is their sum that
    has to fit. A 17-character name opposite a 25-character one satisfies "each side fits its half"
    and collides anyway -- which is exactly the ATTINY85 row that was reported, twice.
*   [x] The character advance was also wrong: 0.85mm, chosen as "deliberately generous". Measured
    off the reported screenshot it is about 1.24mm, and KiCad's stroke font advances roughly one
    text-height per character. Now 1.27mm.
*   [x] Sizing is per row. For that ATTINY85 the body goes from 45.72mm to 55.88mm, holding 53.34mm
    of text.

### Phase 2: verified by rendering it, not by arithmetic
*   [x] Generated the `.kicad_sym`, exported it with `kicad-cli sym export svg`, rasterised it, and
    **looked at the result**. No overlap. Both previous versions of this fix passed their tests.

### Phase 3: advice that sent the user in a circle
*   [x] `CTX-202.4` rewrote the provenance error to end "Re-running the part search and saving again
    usually fills this in." Reported against a real part with a cached datasheet open beside it.
*   [x] The part had no `package_dimensions` and no `courtyard` **at all** -- not missing provenance
    for them, missing the fields. It was added by confirming a search result, and that path records
    `{"source": "search"}` for what the search returned. Only the extraction path produces
    measurements.
*   [x] So the advice was worse than the developer-facing message it replaced: it was readable, and
    it sent someone to repeat the exact step that produced the problem. Both messages now name
    "Generate directly from a part number", which is the path that actually reads the datasheet.

### Phase 4: stop charging for an answer before checking it can be delivered
*   [x] `datasheet.generate_guidance` loaded the part, fetched the PDF, ran the whole
    multi-category pipeline -- twenty to forty seconds -- and only then reached `save_part`, whose
    provenance check refused a part that had been ineligible since before the first token. Every
    token of that work was discarded. Reported as "it took a long time in the generation step just
    to return the error."
*   [x] `library_store.assert_part_can_be_saved` raises now what `save_part` would raise later.
    Same checks, same order, so it can only be a false alarm if the save would refuse too. The
    route calls it before touching the network. Failure is now milliseconds.
*   [x] Deliberately a check and not a repair: it backfills nothing, because guessing where a
    measurement came from is what the provenance rule exists to prevent.
*   [x] The route stored a `content_hash` of the datasheet it generated from and **never compared
    it**, so asking twice for the same answer cost twice. Guidance whose hash matches the current
    PDF is now returned as-is. A revised datasheet changes the hash and regenerates, which is what
    the hash was stored for.
*   [x] A stored record with no categories is not treated as a hit -- serving that back would make
    a failed run permanent.

### Phase 5: say it on the part screen, not three screens later
*   [x] Checking costs nothing -- it is field presence against the same list
    `PART_PROVENANCE_REQUIRED_FIELDS` uses, no round trip -- so Part Detail now says a part is
    missing its measurements the moment it is opened.
*   [x] The notice names the fields in plain words ("package dimensions and courtyard", not
    `package_dimensions`), says what still works so the part does not read as broken, and offers
    the repair with its cost stated: **about 10 seconds**.
*   [x] Offered, not performed. `refreshPartMeasurements` runs the same extract-then-save the
    confirm path already runs, but only when asked -- somebody glancing at a part should not pay
    for a re-read they did not request. A test asserts nothing is spent merely by opening it.

## 4. Plan Drift & Architectural Changes

**1. The first symbol fix was tested and wrong, and the tests were the reason.** Five tests were
written for it, all passing, all asserting the property I had reasoned my way to -- "each side's
longest name fits its own half" -- rather than the property that matters, which is that two names on
one row do not touch. The tests encoded the misunderstanding, so they could only ever confirm it.
The character advance made it worse: the test restated `0.85` as a local constant specifically so it
would not agree with the implementation by construction, and then both were wrong by the same 45%.

**2. What actually settled it was rendering the thing.** `kicad-cli sym export svg`, rasterise,
look. Ten seconds, and it would have caught the first version before it shipped. The repo's norm
already says to verify against the real thing; a symbol is a picture, and the real thing is the
picture.

**3. The corrected error message was worse than the developer-facing one it replaced.** The old text
said `SPEC-300 §2.2`, which is useless to a user but at least does not send them anywhere. The
replacement told them to re-run a search, which is the step that produced the part without
measurements in the first place. Legible and wrong beats illegible; both are worse than accurate.

**4. Left alone, and worth a product decision: confirming a search result gives you a part that
cannot do half the features.** No dimensions means no footprint generation and no design
requirements, and nothing says so until you try. The fix is not another message -- it is either
extracting measurements on confirm, or telling people at the point of confirming rather than three
screens later.

**5. Not verified: the app itself.** The symbol is proven through `kicad-cli`, the messages are
proven by the AST guard, and the suite passes -- but nobody has clicked either path in a built app
since the change. Both need a rebuild, and the symbol needs the part re-saved, because the
`.kicad_sym` is written at save time and an existing library entry keeps its old geometry.

**6. The reported part was three weeks old, and that changes what the bug is.** It was saved
2026-08-12, before `CTX-308.5` began persisting `package_dimensions` and `courtyard` at all. A part
confirmed today already carries both: the confirm path runs an extraction anyway, and measured live
that extraction takes **8.2 seconds** and returns dimensions and courtyard for the same part that
was reported as missing them. So this is a legacy-data problem, not an ongoing one -- which means
the answer is not to make confirm slower, because confirm already pays that cost and already
records the result.

**7. What was actually wrong was where the time went, not how much.** Nothing here made anything
faster. The extraction still takes eight seconds and guidance still takes twenty to forty. What
changed is that a failure now costs milliseconds instead of a full generation, and an answer
already paid for is not bought twice.

**8. The notice is placed where checking is free, which is what decided it.** Two options were on
the table: repair legacy parts automatically when they are opened, or say something and let the
person choose. Automatic repair costs eight seconds unasked, on a part someone may only be glancing
at. Saying something costs nothing measurable, because the check is field presence. That asymmetry
is the whole argument -- it is not a preference about interruption, it is that one option spends
the user's time without being asked and the other does not.

**9. Still not verified in the app.** The notice is proven by five frontend tests and the repair
path by mocks. Nobody has opened a legacy part in a built app and clicked the button. The reported
`ATTINY85-20PU` is exactly that part, so it is available as a test case whenever the next build
happens.
