# CTX-202.1: Component Intelligence Pipeline

> **Spec Reference:** Links to [SPEC-202](../specs/SPEC-202-component-intelligence-pipeline.md)

## 1. Feature Definition & Execution Plan

### Phase 1: AgentFlow content — the first real files in `agentflow/`
*   [x] `services/python-daemon/agentflow/agents/component_extraction.prompt.md` — the extraction
    agent. Instructs the LLM to respond with only the SPEC-202 §2 schema JSON, using real package
    names and real-world estimates rather than blank/impossible values.
*   [x] `services/python-daemon/agentflow/workflows/component_intelligence.workflow.md` — the
    two-node DAG: `extract` (agent node) → `validate` (handler node), connected via
    `inputs: {message: "extract.text"}`.

### Phase 2: `component_pipeline.py` — the handler's real substance
*   [x] `PACKAGE_REFERENCE`: pin count + sane pitch range per recognized package family (`SOIC-8`,
    `SOIC-14/16`, `TSSOP-8`, `TQFP-32/44`, `QFN-16/24`, `DIP-8/14`, `SOT-23`, `0603`, `0805`).
*   [x] `validate_schema`: the three SPEC-202 §2 checks (pin count, pitch sanity, courtyard
    clearance ≥ `_COURTYARD_MIN_CLEARANCE_MM`), each raising a specific `ComponentValidationError`.
    An unrecognized package fails closed (SPEC-202 §3's explicitly-flagged open question, resolved
    here).
*   [x] `_extract_json`: tolerates a markdown code fence around the LLM's JSON response.
*   [x] `validate_component_schema`: the workflow's handler-node function (AgentFlow's `HandlerFn`
    signature) — plain Python, no LLM call, per SPEC-202 §3's "must stay genuinely deterministic"
    constraint.
*   [x] `generate_component`: builds the `WorkflowExecutor`, runs the DAG via `asyncio.run`
    (the same sync/async boundary pattern `llm_providers.chat` established for SPEC-201), and turns
    a `validate` node error back into a clean `ComponentValidationError`.

### Phase 3: `daemon.py` wiring
*   [x] Conditional import of `component_pipeline` (mirrors `kicad_bridge`/`freecad_bridge`'s own
    "import failure disables the route, doesn't crash the daemon" pattern).
*   [x] Removed `mock_generate_component` (the old `time.sleep(1.5)` + fabricated-filename mock)
    entirely; added `kicad_generate_component`, registered only when `component_pipeline` imported.
*   [x] `kicad.generate_component` added to `ASYNC_ROUTES` — a real LLM-backed extraction is
    multi-second, same reasoning as `llm.chat`/`freecad.generate_enclosure`.

### Phase 4: Fix a real frontend gap SPEC-202 itself claimed didn't exist
*   [x] `apps/tauri-ui/src/App.tsx`'s `handleGenerate` used `dispatch()` with a `{ query }` param
    against the old mock's synchronous shape. The real route takes `{ part_number }` and is now an
    async job. Rewrote to use `submitJob`/`JobHandle`, mirroring `EnclosurePanel`'s existing
    pattern. See Plan Drift — this directly corrects SPEC-202 §2's "no impact on apps/tauri-ui"
    claim.

### Phase 5: Fix a real resource leak the first real test run surfaced
*   [x] `AgentExecutor.run()` calls the provider's raw `.chat()` directly, bypassing
    `llm_providers.chat()`'s own `_close_provider_client` fix from CTX-201.1 entirely.
    `_build_agent_executor` now returns `(executor, provider_client)`; `generate_component` tracks
    every constructed client and closes each one via `llm_providers._close_provider_client` inside
    a `finally` block, all within the single `asyncio.run()` call.

### Phase 6: Testing — real, per SPEC-201/CTX-201.1's `.env.local` convention
*   [x] Mocked/local: `_extract_json` (bare JSON, markdown-fenced JSON, bare-fenced JSON, invalid
    JSON) and `validate_schema` (correct schema passes; wrong pin count, insane pitch, undersized
    courtyard, unrecognized package all rejected; a package with no meaningful pitch — `0603` —
    skips that one check without raising).
*   [x] **Real**, skipping cleanly when `ANTHROPIC_API_KEY` isn't set: `generate_component("ATtiny85")`
    end-to-end against the real Anthropic API, asserting the extracted package is real and the pin
    count matches; a nonexistent part number asserted to raise only `ComponentValidationError`
    (never anything else) or succeed.
*   [x] A full end-to-end test: `kicad.generate_component` submitted through `handle_request` exactly
    as a real client would, asserting `job.completed` with the real validated schema.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the extraction agent's default provider/model changed from Ollama/`llama3.2:1b`
    to Anthropic/`claude-sonnet-4-6` — found by running the real pipeline, not by inspection.**
    *   *Reasoning:* `llama3.2:1b` extracted only 2 pins for a real 8-pin ATtiny85 (SOIC-8) —
        `validate_schema` correctly caught this as a validation error, proving the safety net works,
        but revealing the model itself is too weak for reliable structured extraction. The same
        prompt against real Anthropic (`claude-sonnet-4-6`) correctly extracted all 8 pins and
        passed every check.
    *   *Impact:* `component_extraction.prompt.md`'s frontmatter default changed. This is an
        evidence-based correctness call, not a preference — Ollama/local models remain available to
        any caller that explicitly asks for them (the workflow config, not this pipeline's code,
        picks the provider), just no longer the *default* for a check this consequential.

*   **Deviation 2: SPEC-202 §2's own "no impact on `core/tauri-rust` or `apps/tauri-ui`" claim was
    wrong — a real gap, not a hypothetical one.**
    *   *Reasoning:* The old mock's route was dispatched synchronously with a `{ query }` param;
        the spec assumed "same route name" meant "no frontend change," but the real pipeline is
        both a different param name (`part_number`) and, per SPEC-202 §4's own async-job note two
        lines later in the same document, an async job — `App.tsx`'s `handleGenerate` was still
        written against the old synchronous mock shape and would have broken the "Generate" button
        the moment this context shipped, caught only by actually reading `App.tsx`, not by trusting
        the spec's own claim.
    *   *Impact:* Rewrote `handleGenerate` to use `submitJob<Record<string, unknown>>` +
        `{ part_number }`, mirroring `EnclosurePanel`'s existing async-job pattern exactly. Worth
        remembering for future specs: "same route name" is not the same claim as "no caller
        changes," and a spec's own Cross-Module Impacts section is not a substitute for reading the
        actual caller.

*   **Deviation 3: the pipeline's `asyncio.run()` leaked an unclosed provider client — the same
    class of bug as CTX-201.1 Deviation 4, but in a location that fix didn't cover.**
    *   *Reasoning:* CTX-201.1's `_close_provider_client` fix wraps calls made *through*
        `llm_providers.chat()`. AgentFlow's `AgentExecutor.run()` calls the provider's raw `.chat()`
        method directly, entirely bypassing that wrapper — a real gap in the fix's coverage, found
        by running `test_async_jobs.py`'s new real end-to-end test and observing a
        `ResourceWarning: unclosed transport` / `RuntimeError: Event loop is closed` in stderr right
        after it ran, not by code review.
    *   *Impact:* `_build_agent_executor` now returns the provider client alongside the executor;
        `generate_component` tracks every client built across the DAG's nodes and closes each one
        via the same `llm_providers._close_provider_client` helper, inside a `finally` block, inside
        the single `asyncio.run()` call — reusing CTX-201.1's helper rather than duplicating it.
        Re-ran the full suite after the fix: the warning is gone, no regressions.

*   **Deviation 4 (non-deviation, confirmed as designed): an unrecognized package fails closed.**
    *   *Reasoning:* SPEC-202 §3 raised this explicitly as a decision this context needed to make.
        Resolved: a package this pipeline can't check against the pin-count/pitch reference table is
        treated identically to a package that fails a check — a validation error naming the package
        as unrecognized — never a silent pass-through. `ROADMAP.md` §6's risk register names a
        hallucinated-but-plausible component as the single highest-consequence failure mode in this
        product; an unchecked package is exactly that risk with the checks disabled.
    *   *Impact:* `PACKAGE_REFERENCE` is a real but necessarily incomplete table. Extending it to a
        new package family is the documented way to support it — not silently permissive by default.

*   **Note on scope**: SPEC-202's own text describes the pre-existing mock as
    `kicad_bridge.py`'s `mock_generate_component` — it actually lived in `daemon.py` (`kicad_bridge.py`
    is the real KiCad IPC connection module from CTX-103.1 and never contained a mock). Noted here
    rather than silently corrected, since it doesn't change any behavior — just a small inaccuracy in
    the spec's own prose.
