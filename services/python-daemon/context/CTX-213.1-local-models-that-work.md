## 4. Deviations & Discoveries (Plan Drift)

1.  **I predicted that a capable 7B model would make part lookup work locally. It made it run, and
    run wrong.** `qwen2.5:7b` held every contract mechanically: JSON for the board advisor, a real
    tool call (`library_list_parts`, seen in the daemon log), and strict JSON for extraction. But
    the facts were wrong. Five common parts went through `kicad.generate_component`, and all five
    came back with the wrong package. NE555P came back as `MSOIC-8`, and LM7805CT and 2N2222A as
    `TO-220`; the validator rejected all three. ATtiny85-20PU came back as SOIC-8 (it is PDIP-8),
    and ATmega328P-PU as TQFP-32 (it is PDIP-28). Those two passed every check and would have been
    saved. Their footprints would be wrong on a real board. The maintainer chose to gate it: a
    third declared capability, `part_facts`, is now required by `component_extraction` and
    `component_search`. Only the hosted presets claim it. The SPEC-213 draft had none of this, and
    it was updated in `10b3059`.
2.  **The defect in §1 item 1 was narrower than the prompt described, and also wider.** It was
    narrower because the agent routes already resolved through roles whenever `llm_provider` was
    unset: Phase 7's own matrix showed explanations *refused* on ollama roles, which proves they
    reached the ollama record. Only `llm.chat` ignored roles outright. It was wider because the
    routes passed `llm_provider` as an *explicit override*, which outranks roles. So any install
    carrying a stale legacy field silently ignored its Model roles on every agent.
    `bindBothRolesTo` kept the two equal, but a Settings → Model roles save did not.
3.  **A local model breaks output formats that a large model keeps.** Through the frozen binary,
    qwen wrapped chat's `<<<CITATIONS>>>` block in a code fence, prefixed it with `CITATIONS:`,
    and once closed it as `<<<END_Citations>>>`. The user saw all of it. `chat_agents` now strips
    from the first citation marker on. This was not predicted. It was found only by reading real
    output, not by any test.
4.  **Found in the window, not in any test:** the welcome screen still said a provider meant
    "bring an API key". Fixed in `391393f`. That copy change has **not** been re-checked in the
    window: it was made after the click-through, and it is frontend-only and covered by
    `Welcome`'s tests.
5.  **`test_readme_claims` was already failing on `develop`.** `watch.mdx` names `v0.7.0`, which
    the test forbids. No docs-only PR triggers Python CI, so it went unnoticed, and this PR would
    have gone red on it. Reworded in `10b3059`.
6.  **Branched from PR #484's head, not from `origin/develop`.** The `install.md` and release-notes
    lines this context updates were written in `CTX-408.9` Phase 7, which was still open as
    GittieLabs/copperplane#484. This branch carries #484's two commits (`18f109c`, `8d59259`),
    and rebases onto `develop` once #484 merges.
7.  **The docs describe unreleased behaviour the moment this merges.** `docs.yml` deploys on every
    push to `develop`. The current release is v0.7.0, and on it Ollama does not work this way.
    Merge this together with the release that carries it, or hold the docs commit back.

**Verified, and how:**

*   The frozen sidecar (`ensure_sidecar.py --check-only`: present, real, current) was driven over
    JSON-RPC against a real local Ollama 0.40.0, in the same matrix as CTX-408.9 Phase 7:
    *   No provider: every AI route says "No AI model is set up yet … Settings, under Model roles",
        with no SDK text. The check still returns its 2 findings.
    *   Roles on ollama with a stale `llm_provider: anthropic`: chat answers from `qwen2.5:7b`, the
        ERC explanations are generated, and chat makes a real tool call. Search and extraction
        refuse with the part-facts message.
*   As the user, in a Tier 2 `.app` built from this branch: first-run → Ollama → "qwen2.5:7b is
    ready" → Use Ollama → `config.json` showed both roles on `ollama`. The Overview chat answered,
    and `ollama ps` showed qwen loaded by the app. The schematic review returned 3 findings in
    about 90 s, including a real SW1 pin/pad mismatch. A component search for "NE555 timer"
    showed the part-facts refusal. The maintainer's `config.json` was backed up first and
    restored after.

**Not verified:**

*   One machine only: an Apple-silicon Mac with 64 GB. Nothing ran on Windows, Linux, Intel, or a
    smaller-memory Mac. The "about 5 GB of memory" claim comes from `ollama ps` (6.6 GB with a
    32k context), not from an 8 GB machine.
*   The "Ollama not running" and "model not pulled" states were not seen in the window; vitest
    covers them. Ollama was running, with the model pulled, throughout.
*   The Overview chat (`llm.chat`) on qwen gives a generic, not project-aware answer with raw
    LaTeX (`\[ … \]`). `llm.chat` takes no project context on any provider, so this is not new,
    but a local model makes it more visible.
*   Datasheet guidance, connection guidance and suggested parts were not driven on qwen.
