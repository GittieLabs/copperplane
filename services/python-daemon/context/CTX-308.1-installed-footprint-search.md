# CTX-308.1: Implementation Context: Installed Footprint Library Search (direct entries)

> **Spec Reference:** Links to [SPEC-308](../../../apps/tauri-ui/specs/SPEC-308-footprints-schematic-advisor.md)

**Scope, decided 2026-08-14 after a real, significant finding while researching this context (see
`SPEC-308`'s own corrected §2):** KiCad's real global `fp-lib-table` on this machine
(`~/Library/Preferences/kicad/10.0/fp-lib-table`) has one direct `(type "KiCad")` entry (the user's
own `MyPCBLibs`) and one `(type "Table")` entry that recursively points to another `fp-lib-table`
file containing ~100+ of KiCad's own built-in libraries, each using a `${KICAD10_FOOTPRINT_DIR}`-
style placeholder. Resolving `Table`-type entries and placeholder expansion is real, separate work,
explicitly deferred to `CTX-308.2` rather than attempted here. **This context handles direct entries
only** -- real, useful (a user's own custom libraries), but not KiCad's built-in library set yet.

## 1. Feature Definition & Execution Plan

### Phase 1: `fp_lib_table.py` -- discover and parse the real config file ✅
*   [x] New module `services/python-daemon/fp_lib_table.py`.
*   [x] `default_fp_lib_table_path() -> str | None`: per-OS resolution matching `daemon.py`'s own
    `_default_log_dir()` convention -- macOS `~/Library/Preferences/kicad/<version>/fp-lib-table`
    (verified directly against this real machine), Windows `%APPDATA%\kicad\<version>\fp-lib-table`,
    Linux `~/.config/kicad/<version>/fp-lib-table` (both from KiCad's own documented convention, not
    yet verified on a real Windows/Linux machine -- named honestly as unverified in §2 below).
    Globs for version directories, picks the highest-versioned match if more than one exists (sorted
    by a real int-tuple key, not a plain string sort -- "10.0" would otherwise sort before "9.0").
*   [x] `parse_fp_lib_table(path: str) -> list[dict]`: reads the real file, regex-extracts each
    `(lib (name "X") (type "Y") (uri "Z") ...)` entry into `{"name", "type", "uri"}`. `(type
    "Table")` entries are recognized and explicitly skipped with a logged warning -- not silently
    dropped, not a crash -- per this context's own named scope limit.
*   [x] `FpLibTableNotFoundError` (new, this module's own -- `KiCadUnavailableError` in
    `kicad_bridge.py` is about the IPC connection specifically, a different failure mode from a
    missing config file).
*   [x] Real unit tests using this machine's own actual `fp-lib-table` content as a fixture
    (captured directly, not fabricated) -- proves the parser correctly extracts the direct
    `MyPCBLibs` entry and correctly skips the `Table`-type entry without crashing.

### Phase 2: search within resolved `.pretty` directories ✅
*   [x] `list_footprint_names(pretty_dir_path: str) -> list[str]`: lists `*.kicad_mod` filenames
    (stem only) in a real directory. A missing/moved directory (a stale table entry) logs a warning
    and returns an empty list for that one library -- it must not take down search across every
    other configured library.
*   [x] `search_footprints(query: str, fp_lib_table_path: str | None = None) -> list[dict]`: parses
    the table (direct entries only, per this context's scope), lists footprint names per library,
    case-insensitive substring-filters by `query`, returns `[{"library": name, "footprint_name":
    ...}, ...]`.
*   [x] Real, live integration test (skips cleanly if this machine's own `MyPCBLibs.pretty` isn't
    present, matching `CTX-103.1`/`CTX-104.1`'s established pattern): `search_footprints("MP1584")`
    against the real, current `fp-lib-table` finds the real, currently-present
    `MP1584EN_5V_Module.kicad_mod` -- verified running for real against this actual machine before
    the formal test was even written, and again as the formal test itself.

### Phase 3: `kicad.search_footprints` daemon route ✅
*   [x] New `daemon.py` route, named `kicad_search_footprints` (a small naming deviation from the
    plan's `search_footprints_route` -- matches every sibling route's own naming convention, e.g.
    `kicad_generate_component`, `kicad_inject_component`, more closely than the originally-planned
    name would have). Wraps `fp_lib_table.search_footprints`. Registered conditionally on
    `fp_lib_table` having imported (mirrors the existing `try: import X except Exception: X = None`
    pattern this file already uses for every other bridge module).
*   [x] **Deliberately not an `ASYNC_ROUTES` entry** -- unlike every other `kicad.*`/`freecad.*`
    route, this is local filesystem I/O (a config file read plus a directory listing), not a
    multi-second network/IPC round trip. Registering it synchronously is the honest reflection of
    its real cost, not an oversight.
*   [x] Real `daemon.handle_request` round-trip test (mocked `fp_lib_table.search_footprints`,
    matching this file's own established test style for other routes) -- proves the response comes
    back with no `job_id`, confirming the synchronous (not `ASYNC_ROUTES`) design actually took
    effect. A second test mirrors `test_006`/`test_007`/`test_008`'s own established
    route-omission-on-failed-import pattern.

## 4. Plan Drift & Architectural Changes

*   **Non-deviation, confirmed as designed: `Table`-type entries are out of scope for this context,
    not an oversight discovered mid-implementation.** Found and scoped out *before* writing any
    code, during real research for this very context (see the scope note above and `SPEC-308` §2's
    own corrected account) -- the user was asked directly whether to handle both entry types in one
    pass or split them, and chose the split. Recorded here so this reads as a deliberate decision
    when this context is reviewed later, not a gap someone has to rediscover.
*   **Per-OS `fp-lib-table` path convention is verified for macOS only.** Windows/Linux paths above
    are from KiCad's own documented convention, not confirmed against a real machine this session --
    named honestly, matching this repo's "state what was not verified" norm.
