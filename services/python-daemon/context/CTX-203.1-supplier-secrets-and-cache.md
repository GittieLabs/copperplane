# CTX-203.1: Implementation Context: Supplier Secrets & Pricing Cache

> **Spec Reference:** Links to [SPEC-203](../specs/SPEC-203-supplier-api-integration.md)

The credential-independent half of `SPEC-203`: OS-keychain secret storage for DigiKey/Mouser/
Octopart, a Settings UI section to enter them, real `get_capabilities` flags reflecting whether
each supplier is configured, and a local TTL-based price/stock cache module. **No real per-supplier
HTTP client exists yet** -- DigiKey/Mouser/Octopart developer credentials don't exist in this repo's
history, so this context deliberately stops short of any live network call (`SPEC-203` §3's own
named blocker). Each supplier's real integration becomes its own future `CTX-203.n` once that
supplier's credentials exist.

## 1. Feature Definition & Execution Plan

### Phase 1: OS-keychain secret keys (`core/tauri-rust`)
*   [x] `KNOWN_SECRET_KEYS` extended with `digikey_client_id`, `digikey_client_secret`,
    `mouser_api_key`, `octopart_api_key`. DigiKey's real OAuth2 client-credentials flow needs two
    secrets, not one -- named explicitly as the reason its naming departs from the single
    `<provider>_api_key` convention the four LLM provider keys already use.
*   [x] No new Rust code needed beyond the allowlist itself -- `validate_known_key`,
    `collect_known_secrets`, `save_secret`/`clear_secret` are all already generic over
    `KNOWN_SECRET_KEYS`, and their own existing tests iterate the allowlist rather than hardcoding
    key names, so all four new keys are covered by tests that already existed.

### Phase 2: Settings UI section (`apps/tauri-ui`)
*   [x] `lib/settings.ts`: `SUPPLIERS` -- an array of `{id, label, fields}`, since a supplier can
    carry more than one credential field (unlike `KEY_BASED_PROVIDERS`' always-exactly-one-key
    shape). `DaemonCapabilities` gains `digikey_available`/`mouser_available`/`octopart_available`.
*   [x] `Settings.tsx`: a new "Supplier APIs" section between "API Keys" and "Connectivity".
    Save is disabled until *every* field for that supplier is filled (all-or-nothing -- a lone
    DigiKey client ID with no secret can't authenticate, so a partial "configured" state would be
    misleading). Saving/clearing all of a supplier's fields happens as one action, sequentially, not
    one button per field.

### Phase 3: `get_capabilities` flags (`services/python-daemon`)
*   [x] `daemon._detect_capabilities`: `digikey_available` requires *both*
    `digikey_client_id` and `digikey_client_secret` present; `mouser_available`/`octopart_available`
    each require only their own single key. Mirrors `freecad_available`'s existing capability-gating
    pattern -- true means "ready to call," never "a real call has succeeded."

### Phase 4: local price/stock cache (`library_store.py`)
*   [x] `save_supplier_pricing`/`load_supplier_pricing`: a real, TTL-based
    (`library/supplier_pricing/<part_number>__<supplier>.json`) cache, reusing `library_store.py`'s
    existing JSON-file-per-record convention. `load_supplier_pricing` returns `None` (a normal cache
    miss, not an exception) for both "never cached" and "cached but stale." Every cached record
    carries a real `cached_at` timestamp so a future UI can always show real recency, not a bare
    number implying real-time accuracy this cache can't promise (`SPEC-203` §3).
*   [x] `SUPPLIER_PRICING_REQUIRED_FIELDS = ("price_breaks", "stock_quantity", "currency")` --
    a schema check, not a convention, matching `PART_PROVENANCE_REQUIRED_FIELDS`'s own precedent.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: no daemon route or Part Detail UI trigger added in this context, despite
    `SPEC-203` describing a "Check pricing" action.** A route wrapping `save_supplier_pricing`/
    `load_supplier_pricing` with nothing behind it yet (no real supplier HTTP client to actually
    populate the cache) would be dead code -- a route and a UI button that can only ever return
    "nothing cached" is not a real, useful feature. Deferred to the first per-supplier CTX, where a
    real HTTP call gives the route and UI something genuine to do. This context's own real,
    complete, useful slice is: a user can save real supplier credentials in Settings today, before
    any per-supplier integration exists, and the cache layer is ready for a real client to write
    into.
*   **Deviation 2: DigiKey's two-field shape forced `SUPPLIERS`' design away from
    `KEY_BASED_PROVIDERS`' one-key-per-provider assumption.** Rather than force DigiKey into a
    single synthetic key (e.g. concatenating client ID and secret, or inventing a delimiter), each
    supplier definition carries its own list of `{key, label}` fields, and Settings' Save button is
    disabled until every field for that supplier is filled -- an honest reflection of DigiKey's own
    real two-secret auth requirement, not a UI shortcut that would produce a misleadingly
    "configured" state with only half the real credential saved.
*   **Deviation 3: `SUPPLIER_PRICING_REQUIRED_FIELDS` intentionally omits any per-supplier schema
    differences (e.g. DigiKey's real response shape vs. Mouser's).** Every supplier's real response
    will differ in its raw shape; this context's cache schema only enforces the three fields any
    future per-supplier client is expected to normalize into (`price_breaks`, `stock_quantity`,
    `currency`) before calling `save_supplier_pricing` -- normalization is each future client's own
    job, not this cache module's.
