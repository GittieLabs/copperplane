# CTX-310.1: Implementation Context: Board Profile Import Backend

> **Spec Reference:** Links to [SPEC-310](../../../apps/tauri-ui/specs/SPEC-310-enclosure-from-board-profile.md)

The backend half of `SPEC-310`: real, file-based board-outline and mounting-hole extraction via
`kicad-cli`'s own DXF/drill export, and a new `pcb_path` mode on `freecad_generate_enclosure`. No
frontend UI in this context -- split deliberately from `CTX-310.2` (the `.kicad_pcb` file picker),
the same daemon/UI split `CTX-309.1`/`CTX-309.2` already established for `SPEC-309`.

## 1. Feature Definition & Execution Plan

### Phase 1: `kicad_pcb_import.py` -- DXF outline + Excellon drill parsers
*   [x] `_run_dxf_export`/`_run_drill_export`: real subprocess calls to `kicad-cli pcb export
    dxf`/`pcb export drill`, reusing `kicad_cli.find_kicad_cli`'s already-proven location logic
    rather than duplicating it.
*   [x] `_parse_dxf_edge_cuts_bbox`: a small, purpose-built DXF entity reader (`LINE`, `CIRCLE`,
    `ARC`, `LWPOLYLINE`) computing a real bounding box, not a general DXF library.
*   [x] `_parse_excellon_npth_holes`: a line-based Excellon reader using KiCad's own real
    `; #@! TA.AperFunction,...` classification comments to isolate NPTH-tooled holes, matching
    `kicad_bridge.get_mounting_holes`'s live PTH/NPTH distinction.
*   [x] `extract_board_outline`/`extract_mounting_holes`: the public functions, returning exactly
    `kicad_bridge`'s own live shapes (`{x_mm, y_mm, width_mm, height_mm}` /
    `[{x_mm, y_mm, diameter_mm, recognized}]`).

### Phase 2: real fixture + `daemon.py` route wiring
*   [x] `tests/fixtures/board_with_outline.kicad_pcb`: a real, hand-crafted `.kicad_pcb` with a real
    50×30mm `gr_rect` on `Edge.Cuts` and two real `MountingHole_3.2mm` footprints (real
    `np_thru_hole` pads), committed for CI use.
*   [x] `daemon.freecad_generate_enclosure`: new `pcb_path` parameter, a third mode alongside manual
    (`width`+`depth`) and live-board, in a fixed priority order (manual > file > live) so an explicit
    caller choice is never silently overridden. File mode's `board_revision` is tagged
    `file:<path>:<hash>`, distinguishing it from live mode's untagged hash and manual mode's
    `manual:...` sentinel.
*   [x] `kicad_pcb_import` imported with the same guarded-import-plus-`RuntimeError`-at-call-time
    pattern `kicad_cli`/`kicad_bridge` already use -- a missing dependency degrades this one mode,
    not the whole daemon.

### Phase 3: tests + real, end-to-end verification
*   [x] Pure-parser unit tests for `_parse_dxf_edge_cuts_bbox` (`LINE`/`CIRCLE`/`LWPOLYLINE`,
    entities-outside-`ENTITIES`-section rejection, no-Edge.Cuts error) and
    `_parse_excellon_npth_holes` (PTH exclusion, empty-NPTH-set, multiple coordinates per tool) --
    no subprocess involved.
*   [x] Mocked `kicad-cli` subprocess-boundary tests for the missing-export-file error path on both
    `extract_board_outline` and `extract_mounting_holes`.
*   [x] Real, non-mocked `extract_board_outline`/`extract_mounting_holes` calls against the real
    committed fixture, plus a real `BoardOutlineMissingError` against `empty_board.kicad_pcb`
    (`CTX-309.1`'s own fixture, reused here since it already has no `Edge.Cuts` geometry). Skips
    cleanly when `kicad-cli` isn't found, matching every other real-`kicad-cli` test in this repo.
*   [x] `daemon.freecad_generate_enclosure`'s `pcb_path` mode: mocked routing tests (never touches
    `kicad_bridge`, every file-mode hole becomes a standoff with `unrecognized_holes` always `[]`,
    mode priority, `board_revision` tagging, clean `RuntimeError` on a failed `kicad_pcb_import`
    import) plus a real, direct end-to-end call producing real `.glb`/`.step` files with no live
    KiCad connection at all.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (found by the tests this context added, not assumed in advance): `kicad-cli`'s DXF
    and Excellon exports use the standard drafting/plot Y-axis convention (Y increases upward), the
    opposite of KiCad's own internal board coordinates (Y increases downward) that
    `kicad_bridge.get_board_outline`/`get_mounting_holes` already return live.** Confirmed for real,
    not assumed: running the real parser against `board_with_outline.kicad_pcb` (a real 50×30mm
    rectangle at (0,0)-(50,30) in the file's own raw internal coordinates, with real mounting holes
    at (5,5) and (45,25)) first came back as `{"x_mm": 0.0, "y_mm": -30.0, ...}` with holes at
    `(5,-5)`/`(45,-25)` -- an exact Y-axis sign flip, no offset. Because
    `freecad_bridge.generate_enclosure` computes every standoff position relative to the outline's
    own `x_mm`/`y_mm` origin (`s["x_mm"] - board_outline["x_mm"]`, same for `y`), this flip does not
    crash or raise anything -- both values come from the same (flipped) coordinate space, so the
    subtraction still "works." It silently produces a **vertically mirrored** standoff layout for any
    board whose mounting holes aren't symmetric top-to-bottom relative to the board's own center --
    which is most real boards. Fixed by negating every DXF Y group code (20/21, and `LWPOLYLINE`
    vertex Y) and every Excellon Y coordinate at parse time, so this file-based path returns the same
    coordinate convention the live path already does. Re-verified for real after the fix: the same
    fixture now returns `{"x_mm": 0.0, "y_mm": 0.0, ...}` with holes at exactly `(5,5)`/`(45,25)`,
    matching the file's own raw internal coordinates and `kicad_bridge`'s live convention. This is
    exactly the kind of finding `CLAUDE.md`'s "verify against the real thing" norm exists for --
    mocked tests written from assumption, not real fixture output, would never have caught a sign
    convention bug like this, since a self-consistent mock has no way to be wrong about the real
    tool's own real behavior.
*   **Deviation 2: `TEST-006` (the full real end-to-end pipeline, live KiCad-free) was verified via a
    direct, one-off Python invocation, not committed as its own `unittest` test case.** Left as an ad
    hoc verification rather than a committed real-integration test for the same reason
    `TestFreecadGenerateEnclosureRoute`'s existing live-mode tests already do this: the real FreeCAD
    geometry pipeline itself is `test_freecad_bridge.py`'s job (`TestBoardDrivenEnclosure`, already
    covers `generate_enclosure` for real against a real `freecadcmd`), so a route-level test mocking
    `generate_enclosure` and asserting on its call arguments is the existing, consistent pattern --
    adding a *second*, real-FreeCAD-invoking test at the route layer would duplicate coverage
    `test_freecad_bridge.py` already owns, at real (multi-second, real subprocess) cost per test run.
    Named explicitly per `CLAUDE.md`'s "state what was not verified" norm, not silently treated as
    equivalent to a committed regression test.
*   **Deviation 3: `_run_dxf_export`/`_run_drill_export` reach into `kicad_cli`'s public
    `find_kicad_cli` but not any private helper -- `kicad_cli.py` has no generic "run an export
    subcommand" helper today, only `run_erc`/`run_drc`.** Rather than refactor `kicad_cli.py` to
    extract a shared subprocess helper (out of scope for this context, and `run_erc`/`run_drc`'s own
    report-file-output shape differs enough from a DXF/drill export that forcing a shared abstraction
    now would be premature), `kicad_pcb_import.py` duplicates the small amount of subprocess
    boilerplate directly. If a third `kicad-cli`-subprocess consumer appears, extracting a shared
    helper becomes worth it then, not preemptively here.
