# CTX-103.1: KiCad IPC Bridge

> **Spec Reference:** Links to [SPEC-103](../specs/SPEC-103-kicad-ipc.md)

## 1. Feature Definition & Execution Plan

**Scope note:** SPEC-103's data-flow example (injecting a generated `.kicad_mod` into the open canvas) is a larger feature than this first context covers. This CTX builds the *bridge* itself — connection lifecycle, version gating, error handling — and proves it end-to-end with one real read-only call (`kicad.get_version`). Footprint/symbol injection is follow-up work once the bridge is trusted.

### Phase 1: Dependencies
*   [x] Add `kicad-python` (imports as `kipy`) and `pynng` as daemon dependencies (`requirements.txt`, matching the README's existing `uv pip install -r requirements.txt` workflow — since no dependency manifest existed yet).

### Phase 2: Connection Manager
*   [x] `kicad_bridge.py`: lazily connect a `kipy.KiCad` client, held open for the daemon's lifetime (per SPEC-103 §2, to avoid per-call handshake latency).
*   [x] Version gate: catch `kipy.errors.FutureVersionError` — logged as a warning, not a hard failure (see Plan Drift, Deviation 1). A genuinely unreachable/too-old KiCad surfaces as `ConnectionError`/`ApiError` instead, which *is* a hard failure.

### Phase 3: JSON-RPC Route
*   [x] Add a real `kicad.get_version` route to `daemon.py`'s `ROUTES`, backed by the connection manager, alongside the existing mocked `kicad.generate_component`.
*   [x] Wrap every call through the bridge in `try/except` for `ConnectionError`/broken-pipe (SPEC-103 §3, "State Desync" — user closes KiCad mid-session).

### Phase 4: Testing
*   [x] Mocked unit tests: connection refused (KiCad not running), and the broken-pipe/State-Desync path.
*   [x] A **real** integration test against a live, locally running KiCad instance — not just mocks. Skips itself gracefully if the IPC socket isn't present (e.g. in CI, where KiCad isn't installed) rather than failing.

## 4. Plan Drift & Architectural Changes

*   **Discovery: this machine has KiCad 10.0.3 installed, and its IPC API can be enabled locally.**
    *   *Reasoning:* `~/Library/Preferences/kicad/10.0/kicad_common.json` has an `api.enable_server` flag (was `false`). Flipping it to `true` and launching KiCad opens a real socket at `/tmp/kicad/api.sock`. Confirmed a live round-trip: `KiCad().get_version()` returned `"10.0.3 (10.0.3)"` against the actually-running app, before any of this feature's code was written.
    *   *Impact:* Unlike SPEC-101's Windows Job Object path, this bridge's happy path can be verified for real on this dev machine, not just mocked. `TEST-002` exercises that live connection. CI (no KiCad installed there) will only run the mocked tests — `TEST-002` needs to skip itself cleanly rather than fail when the socket is absent.
*   **Deviation 1: `kipy.KiCad.check_version()`'s `FutureVersionError` is treated as a warning, not a connection blocker.**
    *   *Reasoning:* Hit this for real on the first live test: `kicad-python==0.7.1` declares API support for KiCad `10.0.1`, but the actually-installed app is `10.0.3` — a routine patch-version lag between the PyPI package and the app, not an incompatibility. `check_version()` raises on *any* case where the connected KiCad is newer than the library declares, which would make the daemon fail to connect for most real users who keep KiCad updated more recently than the pip package. SPEC-103's own "Version Dependency" risk is about KiCad being *too old* (8 or earlier, which surfaces as a connection failure instead — no socket exists at all), not too new.
    *   *Impact:* `get_client()` now logs a warning and proceeds on `FutureVersionError`, and only raises `KiCadUnavailableError` for genuine `ConnectionError`/`ApiError` (KiCad absent, too old, or IPC API disabled). Worth revisiting if a future KiCad *major* version bump turns out to actually break the wire protocol — this assumption (patch/minor bumps are safe) hasn't been tested against a real breaking change, only against a benign patch lag.
