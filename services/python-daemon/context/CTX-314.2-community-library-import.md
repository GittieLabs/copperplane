# CTX-314.2: Implementation Context: Community Library Import (Fetch, Parse, Persist, UI)

> **Spec Reference:** Links to [SPEC-314](../../../apps/tauri-ui/specs/SPEC-314-community-library-discovery.md)

`CTX-314.1` shipped search-only: real candidates (repo, path, license, download URL) from the
curated allowlist, no fetch, no parse, no persistence, no UI. This slice is everything it
deliberately deferred: the real `github_token` keychain key, fetching and parsing a selected
file's real content, persisting it through `library_store.py` with real provenance, and the
Settings + Part Detail UI surfaces a user actually touches (`SPEC-314` §5).

**Real design decision made during this context's own planning, not assumed:** a `.kicad_mod`
file is one footprint -- direct import. A `.kicad_sym` file, verified directly against real
repo content during planning (`sparkfun/SparkFun-KiCad-Libraries`'s `SparkFun-Capacitor.kicad_sym`
has 73 real symbols in one file), is a *library* of many symbols, not one -- exactly like this
app's own hand-built `.kicad_sym` files are NOT (`library_store._build_kicad_sym_text` writes one
symbol per file, this app's own simplification, not a real KiCad requirement). `CTX-314.1`'s
search can only match a symbol *library file's* path, not an individual symbol name inside it, so
a symbol import is real two-step: fetch + parse the file, return the real symbol names and pin
counts found inside (`library.import_community_footprint` with no `symbol_name` given), then a
second call with a real, chosen `symbol_name` actually persists. Never silently picks "the first
symbol in the file" -- a real, honest disambiguation step, not an invented abstraction; a
`.kicad_mod` file needs no equivalent step since it's already exactly one footprint.

**Real design decision: persist raw content, not a re-derived internal schema.** Converting a
real, community-verified `.kicad_mod`/`.kicad_sym` into this app's own hand-built Pad/Symbol JSON
schema (the same shape `kicad_write.generate_pad_layout`/`_build_kicad_sym_text` produce for
LLM-generated geometry) would be lossy and would defeat the entire point of importing a real,
already-proven file over generating one -- SPEC-314 §1's own stated value ("someone else has
already used it on a real board"). Instead, `library_store.save_footprint`/`save_symbol` gain a
new optional field each (`raw_kicad_mod`/`raw_kicad_sym`) holding the real, verbatim fetched text,
and `export_footprint_kicad_mod`/`export_symbol_kicad_sym` write that raw text directly to disk
when present, falling back to their existing hand-built-from-JSON path otherwise -- the two
representations never need to agree with each other because a raw-backed record never goes
through the hand-built path at all.

## 1. Feature Definition & Execution Plan

### Phase 1: Rust -- the real `github_token` secret key
*   [x] `core/tauri-rust/src/daemon.rs`: add `"github_token"` to `KNOWN_SECRET_KEYS`, alongside a
    real doc-comment note that unlike the four LLM provider keys, this one is consumed by
    `community_libraries.py` for GitHub API rate-limit headroom, not an LLM call.

### Phase 2: Python -- real fetch, parse, and raw-content persistence
*   [x] `community_libraries.py`: new `fetch_raw_content(download_url: str) -> str` -- a plain
    HTTPS GET against the real `raw.githubusercontent.com` URL `CTX-314.1`'s search already
    returns (not the GitHub REST API, so it does not consume the API rate limit this module's own
    docstring already documents -- verified directly: `raw.githubusercontent.com` is served by
    GitHub's CDN, a separate real system from `api.github.com`). Reuses this module's own
    `_SSL_CONTEXT`/timeout/error-translation conventions exactly.
*   [x] `community_libraries.py`: new `parse_footprint(content: str) -> dict` /
    `parse_symbol_library(content: str) -> list[dict]`, using `kiutils.utils.sexpr.parse_sexp` +
    `kiutils.footprint.Footprint.from_sexpr` / `kiutils.symbol.SymbolLib.from_sexpr` -- real,
    verified directly during this context's own planning against real fetched content from both
    allowlisted repos (a footprint returns real `pad_count`; a symbol library returns every real
    symbol's `name` (`libId`) and real `pin_count`, summed across `Symbol.units` -- verified
    directly that a real vendor symbol's own pins live on its sub-units, not the top-level
    `Symbol` object, exactly like this app's own hand-built `_0_1`/`_1_1` sub-symbol convention).
    Raises a clear `CommunityLibraryError` (not a bare kiutils exception) on real unparseable
    content -- never silently persists something that didn't actually parse.
*   [x] `daemon.py`: new `library.import_community_footprint(owner, repo, path, kind, license,
    download_url, symbol_name=None) -> dict` route:
    *   `kind == "footprint"`: fetch, parse (real-verifies + gets `pad_count`), persist via
        `library_store.save_footprint` with `raw_kicad_mod`, `pad_count`, and a real `provenance`
        dict (`source: "community_library"`, `owner`, `repo`, `path`, `license`, `blob_sha` if the
        search result carried one). `footprint_id` = `f"{owner}__{repo}__{stem}"` (the same `__`
        separator `attachFootprintToPart`'s own doc comment already established as the real,
        cross-platform-safe choice over KiCad's `:` reference syntax -- Windows-unsafe, a real bug
        this app already hit once).
    *   `kind == "symbol"`, no `symbol_name`: fetch, parse the real library file, return
        `{"symbols": [{"name": ..., "pin_count": ...}, ...]}` -- a real browse response, nothing
        persisted yet.
    *   `kind == "symbol"`, with `symbol_name`: same fetch/parse, but requires the named symbol be
        present in the real parsed list (`SchemaValidationError` with the real available names if
        not -- never silently imports a different one); persists via `library_store.save_symbol`
        with `raw_kicad_sym` (the real, complete library file content -- not a re-serialized
        single-symbol slice, avoiding any kiutils round-trip fidelity risk), `symbol_name`,
        `pin_count` (for that one named symbol), and the same real `provenance` shape as above.
        `symbol_id` = `f"{owner}__{repo}__{symbol_name}"`.
*   [x] `library_store.py`: `export_footprint_kicad_mod`/`export_symbol_kicad_sym` each gain a
    real raw-content branch checked first (`if footprint.get("raw_kicad_mod"):` /
    `if symbol.get("raw_kicad_sym"):`) that writes the stored raw text verbatim, before falling
    through to the existing hand-built-from-JSON path -- the existing fail-closed
    no-pads/no-courtyard error stays exactly as-is for the generated-footprint case.

### Phase 3: Frontend -- Settings field + Part Detail UI
*   [x] `apps/tauri-ui/src/lib/settings.ts`: add `github_token_configured: boolean` to
    `DaemonCapabilities` (the real flag `CTX-314.1` already added daemon-side; the frontend type
    never picked it up since that context was deliberately backend-only).
*   [x] `apps/tauri-ui/src/components/Settings.tsx`: a new, small "Community Library Search"
    section -- one optional GitHub token field, `saveSecret('github_token', ...)` /
    `clearSecret('github_token')` directly (no new provider-list abstraction; this is one field,
    not `SUPPLIERS`-style N-provider list `CTX-203.2` already removed for exactly that reason),
    showing `capabilities.github_token_configured` the same "configured"/clear-vs-save pattern the
    LLM provider keys already use.
*   [x] `apps/tauri-ui/src/lib/footprints.ts`: `searchCommunityFootprints(query)` wrapping
    `library.search_community_footprints`; `importCommunityFootprint(candidate, symbolName?)`
    wrapping the new route, returning either a real imported record or a real `{symbols: [...]}`
    browse response the caller must handle before a second call.
*   [x] `apps/tauri-ui/src/components/PartDetail.tsx`: a new "Community libraries" block inside
    the existing Find Footprint UI, alongside the installed-library search results -- each result
    shows its real repo, path, and license with an "Import" action. A `.kicad_mod` result imports
    directly. A `.kicad_sym` result's "Import" first shows the real symbol names/pin counts found
    inside that file (the Phase 2 browse response), then a second click imports the chosen one.
    Matches this app's own "every AI/external step confirmable, never silent" precedent (SPEC-314
    §1's own stated non-goal boundary) -- nothing is ever imported without an explicit, named
    selection.

## 4. Plan Drift & Architectural Changes

- **A real, pre-existing bug found and fixed in `CTX-314.1`'s own shipped code, not introduced by
  this context.** `library.search_community_footprints` was never added to `ASYNC_ROUTES` when
  `CTX-314.1` shipped it -- a real, live GitHub API round trip (`community_libraries._github_request`)
  ran synchronously inside `handle_request`, which `main()`'s own `for line in sys.stdin` loop calls
  directly per request. Any real network latency there blocked the daemon's entire stdin read loop,
  freezing every other IPC command (chat, board checks, everything) for the duration -- not a
  hypothetical risk, a real, reproducible consequence of this repo's own documented async-routing
  convention (SPEC-105 §2) not being followed for that one route. Fixed here, alongside registering
  the new `library.import_community_footprint` route the same way, since both make real network
  calls and this context was already touching that exact code. Recorded honestly as a fix to prior
  work, not framed as new scope for this slice.
- **Symbol import is a real two-step flow, not assumed away.** The original Phase 2 plan already
  anticipated this (a `.kicad_sym` file is a real multi-symbol library), but the actual shape --
  `library.import_community_footprint` returning a real `{"symbols": [...]}` browse response when
  `symbol_name` is omitted, requiring a second call to actually persist -- was implemented exactly
  as planned, with no deviation. Worth noting as a confirmation, not a drift: the real, live-fetched
  `SparkFun-Capacitor.kicad_sym` file used during verification (73 real symbols) made this design
  choice concrete rather than theoretical.
- **`footprints.ts`/`Settings.tsx` test files did not previously exist for some of this codebase's
  own async-registered lib functions** (e.g. no `boardAdvisor.test.ts` covers `checkBoard`'s own
  `submitJob` usage) -- this context's own `footprints.test.ts` is a new, standalone file, matching
  the established convention seen in `enclosure.test.ts` (mock `submitJob`/`dispatch` from `./ipc`
  directly) rather than only covering the new functions indirectly through `PartDetail.test.tsx`.
- No other deviation from the original plan. The raw-content persistence design (skip the lossy
  hand-built-from-JSON path entirely for a community-imported record), the `owner__repo__stem`
  naming convention, and the deliberately-scoped Settings UI (one field, no `SUPPLIERS`-style
  abstraction) all shipped exactly as scoped in this context's own Phase 1-3 plan.
