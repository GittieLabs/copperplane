# CTX-208.1: Implementation Context: Provider Records, Kinds, Presets & One Resolver

> **Spec Reference:** Links to [SPEC-208](../specs/SPEC-208-provider-records-and-model-roles.md)

Phase 1 of 3 (SPEC-208 §4's own module map). Replaces `llm_providers.py`'s hardcoded
name-if-chain with `kind`-based construction against a `ProviderRecord`, reseeds today's five
providers as presets with identical values, and consolidates the two duplicated override blocks in
`chat_agents._dispatch`/`component_pipeline._build_agent_executor` into one `resolve()` function
(SPEC-208 §2.6). **Deliberately does not yet close coupling #2** (per-agent model
differentiation) -- no `.prompt.md` declares a `model_role` until CTX-208.2 rewrites all twelve, so
every real caller today still resolves by provider *id*, byte-behavior-identical to before this
phase. `SPEC-207`'s own sequencing note ("landing SPEC-208 first makes SPEC-207 smaller") is why
this phase exists before any SPEC-207 work starts.

## 1. Feature Definition & Execution Plan

### Phase 1: `ProviderRecord`, kind-based construction, presets
*   [x] `ProviderRecord` (`TypedDict`): `{id, kind, base_url, api_key_ref, models, capabilities}`.
    `models` is role-keyed (`reasoning`/`fast`) even though no real caller supplies a role yet --
    seeded with today's single per-provider default for both roles, honestly, rather than inventing
    a differentiated pair (SPEC-208 §2.2.2's own live-verification requirement is CTX-208.2's job).
*   [x] `_preset_records()` -- today's five providers reseeded with their exact current values
    (`_DEFAULT_MODELS`, `_OLLAMA_BASE_URL`, `_PERPLEXITY_BASE_URL`), built fresh per call so no
    caller can mutate a shared global.
*   [x] `_build_provider_from_record(record, api_key, model)` -- the real kind-based switch
    (`anthropic` / `google` / `openai_compat`), replacing the old provider-name if-chain's body.
    The Ollama-only empty-key-to-placeholder substitution is now keyed off `record["id"] ==
    "ollama"` specifically (not the `openai_compat` kind broadly), so a real user-authored
    `openai_compat` record still requires a real key.
*   [x] `_build_provider(provider, api_key, model)` -- kept as a thin, **preset-only**, name-based
    lookup on top of `_build_provider_from_record`, for `llm_providers.chat()` and this module's
    own pre-existing test suite. Verified byte-behavior-identical: every one of
    `TestBuildProvider`'s six pre-existing tests, and `TestRealProviderCalls`'s three live-key
    tests (real Anthropic/Google/Perplexity calls), pass unchanged.
*   [x] `_RESERVED_PROVIDER_IDS = {"managed"}` -- reserved now, forward-compatibly, even though no
    `managed` preset record exists yet (`SPEC-207` hasn't landed its gateway constant). A
    `config.json` entry claiming this id is ignored with a logged warning, never merged.

### Phase 2: `resolve()` -- the one consolidated entry point
*   [x] `_resolve_provider_records(config)` -- presets overlaid with `config.get("providers", [])`,
    by id; a user record can add a new id or replace a preset's id outright.
*   [x] `_resolve_api_key(record, secrets)` -- looks up `record["api_key_ref"]` in the secrets
    dict; `None` (no real key concept, i.e. Ollama today) resolves to `""`.
*   [x] `resolve(default_provider, default_model, secrets, provider=None, model=None,
    config=None) -> (provider_client, resolved_provider, resolved_model)` -- reproduces today's
    exact override precedence (explicit `model` wins; explicit `provider` alone falls back to
    *that* provider's own default, never the old provider's model; neither given keeps the
    caller's default) through the records layer. `config` is accepted and already reachable
    end-to-end (proven by `TestResolve::test_006`), but **no real caller threads
    `daemon.CONFIG`'s `providers`/`provider_roles` through yet** -- see Plan Drift.
*   [x] `chat_agents._dispatch` and `component_pipeline._build_agent_executor` -- both duplicated
    `overrides = {}` / `api_key = secrets.get(...)` / `_build_provider(...)` blocks deleted,
    replaced by one `llm_providers.resolve(...)` call each, `model_copy`'d back onto
    `agent_config`/`config` exactly as before (so `provenance`, and every other read of
    `.provider`/`.model`, sees the same values it always did).
*   [x] `llm_providers.chat()` deliberately left calling `_build_provider` directly, not
    `resolve()` -- see Plan Drift Deviation 1.

### Phase 3: Rust side -- carry the new fields, interpret nothing
*   [x] `core/tauri-rust/src/config.rs`: new `ProviderRecord` struct (serde round-trip only, no
    daemon-side interpretation in Rust, matching how every other `DaemonConfig` field this crate
    doesn't read is already handled) and two new `DaemonConfig` fields, `providers:
    Option<Vec<ProviderRecord>>` and `provider_roles: Option<HashMap<String, String>>`.
*   [x] Legacy `llm_provider`/`llm_model` fields are untouched -- migration/interpretation is
    Python's job (SPEC-208 §2.5), not this struct's.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `llm_providers.chat()` was left calling `_build_provider` directly, not the new
    `resolve()`, even though SPEC-207 §2.2.1 names it as one of the "three call sites."**
    *   *Reasoning:* `chat()`'s callers (`daemon.py`'s `llm_chat` route) already resolve a single,
        final `provider`/`model`/`api_key` before calling it -- there is no "agent default vs.
        override" computation inside `chat()` to consolidate, unlike the real duplication in
        `chat_agents.py`/`component_pipeline.py`. Routing it through `resolve()` would mean
        threading a `secrets` dict and an `api_key_ref` lookup through a function whose callers
        already have a concrete key in hand, for no behavioral gain.
    *   *Impact:* `chat()`'s provider construction still goes through `_build_provider`, which is
        itself now record/kind-based underneath -- so the actual if-chain SPEC-208 exists to
        remove is gone from every path, just not through the identical function name at every
        call site. Worth revisiting if a future phase gives `chat()` an override-computation
        reason to exist that it doesn't have today.
*   **Deviation 2: the Ollama preset's `reasoning` model was NOT replaced, despite SPEC-208 §2.2.2
    calling `llama3.2:1b` unfit for this repo's JSON/tool-call contracts.**
    *   *Reasoning:* the spec is explicit that the replacement "must be chosen by running the real
        `component_extraction` and `datasheet_guidance_extraction` prompts against candidates on a
        real local server" -- and no local Ollama server is reachable on this machine (`curl
        localhost:11434` refused). Guessing a replacement from reputation is exactly the mistake
        `CTX-201.1`/`CTX-202.1`'s own Plan Drift already recorded once.
    *   *Impact:* the Ollama preset keeps `llama3.2:1b` for both roles, with an inline comment
        naming this as a known, not-yet-verified gap. `capabilities: {tool_use: False, strict_json:
        False}` is set honestly (matching what's actually true of a 1B model) so CTX-208.3's
        preflight will correctly flag it once that phase lands, rather than silently claiming a
        capability the current default doesn't have.
*   **Deviation 3: role-based resolution (`provider_roles`, `model_role`) is scaffolded but not
    wired end-to-end in this phase, narrower than SPEC-208 §2.3.2's full resolution order.**
    *   *Reasoning:* SPEC-208's own module map splits this deliberately (`CTX-208.1` = "provider
        records, kinds, presets, one resolver"; `CTX-208.2` = "model roles across the twelve
        prompt files"). Until `.prompt.md` files declare a `model_role`, there is no real role
        value for `resolve()` to receive from a real caller -- building the full role-resolution
        path now would mean testing it only against synthetic call sites.
    *   *Impact:* `resolve()`'s signature and `_resolve_provider_records()` already accept and
        merge a `config` argument end-to-end (proven for real by `TestResolve::test_006`), so
        `CTX-208.2` only needs to add the sidecar `model_role` reader and thread `daemon.CONFIG`
        through the three call sites -- no further change to `resolve()`'s own resolution logic
        for an explicit-provider-override call, which is unaffected either way.
