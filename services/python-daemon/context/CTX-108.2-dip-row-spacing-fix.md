# CTX-108.2: DIP Row Spacing Fix

> **Spec Reference:** Links to [SPEC-108](../specs/SPEC-108-kicad-write-path-footprint-symbol-injection.md)

## 1. Feature Definition & Execution Plan

A real, serious bug found by the user, who generated a footprint for the ATtiny85 from datasheet
dimensions (`CTX-308.5`) and asked directly: "can you confirm the dimensions are correct?" -- they
were not. Compared the real generated `.kicad_mod` (pads at x=±3.175mm, row spacing 6.35mm/0.25in)
against the real ATtiny85 datasheet's own PDIP-8 mechanical drawing (page 207: `"eA 0.300 BSC"` --
0.300in/7.62mm is the real, standardized lead-to-lead row spacing for this "8P3, 0.300" Wide Body"
package). The generated footprint's row spacing was wrong by exactly 1.27mm (0.05in) -- a real part
in this package would not physically insert into this footprint.

**Root cause**: `kicad_write._dual_row_layout` (called for every `DUAL_ROW_PACKAGES` entry) used
`package_dimensions["width_mm"]` -- the package BODY width (a real, different JEDEC dimension, "E1",
~0.25in for this package) -- as the row-to-row lead spacing for BOTH the SMD branch (where that's a
reasonable approximation) and the through-hole DIP branch, where row spacing is a fixed, standardized
package-family constant (`eA`), never derived from body width. This is a **general bug**, not specific
to the ATtiny85 -- every `THROUGH_HOLE_PACKAGES` entry (`DIP-8`, `DIP-14`) went through this same
conflation.

**Fix**: a real, fixed `_DIP_ROW_SPACING_MM = 7.62` constant, used only for the through-hole branch;
the SMD branch is unchanged.

### Phase 1: `kicad_write.py`
*   [x] `_DIP_ROW_SPACING_MM = 7.62`, used in `_dual_row_layout`'s `through_hole` branch instead of
    `package_dimensions["width_mm"]`.

### Phase 2: tests
*   [x] `tests/test_kicad_write.py`: a real, explicit test asserting DIP-8's row spacing is exactly
    7.62mm (no prior test checked this numeric value at all, which is exactly how this shipped
    wrong).

## Files
- `services/python-daemon/kicad_write.py` -- the real fix.
- `services/python-daemon/tests/test_kicad_write.py` -- new test.

## Verification
- `services/python-daemon/.venv/bin/python3 -m unittest tests.test_kicad_write -v` -- all
  mock/pure-geometry tests pass. `TestRealKicadWrite`'s own live-KiCad test errored with a real IPC
  timeout during this run (KiCad was not running on this machine at the time -- `ps aux` confirmed
  no kicad process -- and the failure is in unrelated code, `SOIC-8` pad generation via
  `board.begin_commit()`, a real, pre-existing "stale socket" flakiness this test's own docstring
  already names as a known real risk on macOS, not something introduced by this change). Named
  honestly, not silently glossed over.
- Real, manual comparison against the actual ATtiny85 datasheet's own PDIP-8 mechanical dimension
  table (page 207) confirmed the fix's target value (7.62mm) is correct for this real, standard
  package.
- **Named, honest, real limitation**: this fix was not re-verified by generating a fresh footprint
  through the real, running app and re-inspecting the `.kicad_mod` file end-to-end in this session
  (no live app session available) -- the fix is verified at the unit level (the pure geometry
  function itself) and against the real datasheet's own stated dimension, not via a fresh real
  end-to-end regeneration. The user's own next real regeneration will be the first end-to-end proof.

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

None -- a pure bug fix against `CTX-108.1`'s own original design, which never distinguished
"package body width" from "lead row spacing" as two different real dimensions for the through-hole
case. Worth a broader note for whenever a wider DIP family (0.6in body, e.g. DIP-24+) is added: this
fix's fixed 7.62mm constant is correct only for the "wide" 0.3in-body DIP family this module
currently supports (`DIP-8`, `DIP-14`); a future wider package would need its own real constant, not
a reuse of this one.
