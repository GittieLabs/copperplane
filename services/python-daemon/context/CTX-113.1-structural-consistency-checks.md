# CTX-113.1: Implementation Context: Symbol and Footprint Pin Counts

> **Spec Reference:** Links to [SPEC-113](../specs/SPEC-113-structural-consistency-checks.md)

The first check in `SPEC-113`'s family: a symbol's pin count against the pad count of the footprint
assigned to it. It is the defect the tutorial and the product video both lead with, and today it
only surfaces if the user knows to ask.

## 1. Feature Definition & Execution Plan

### Phase 1: read the schematic's symbols and their pin counts
*   [x] Parse the `.kicad_sch` with `kicad_board`'s existing s-expression parser rather than
    writing a third one. `lib_symbols` carries each symbol definition; pins live in its unit
    sub-symbols, so they are summed across units.
*   [x] Each instance gives a reference designator, a `lib_id`, and the assigned `Footprint`
    property.
*   [x] `kicad_cli.export_schematic_bom` is not the source here: it reports reference, value and
    footprint, and no pin count at all.

### Phase 2: count a footprint's numbered plated pads
*   [x] **`footprint_detail._pads` cannot be reused.** It counts every `(pad ...)` including
    `np_thru_hole`, and does not deduplicate by pad number. On the example board it reports 36 for
    the Arduino's footprint where the electrically meaningful count is 32.
*   [x] The count is distinct pad numbers, excluding unplated pads and pads with an empty number.
*   [x] Resolve the footprint file through `kicad_bridge.resolve_footprint_model`, which already
    returns `footprint_path`.

### Phase 3: the comparison, and only two exclusions
*   [x] A symbol with no footprint assigned is skipped. That is the power symbols and nothing else.
*   [x] Unplated and unnumbered pads are not counted. That is the Arduino's four mechanical holes
    and nothing else.
*   [x] A footprint that cannot be resolved reports that it could not be compared, never a
    mismatch.

### Phase 4: enter the review as a third source, never as a discovery
*   [x] `chat_agents._check_status_note` already assembles ERC or DRC findings and, since
    `CTX-319.7`, the real component list. Structural findings join it there, so the model explains
    a finding rather than noticing one.
*   [x] They must also appear in the deterministic fallback, alongside
    `_findings_from_check_alone`. A finding computed from the user's own files should survive the
    model's prose failing, exactly as KiCad's own findings already do.
*   [x] Marked as Copperplane's own, distinguishable from anything KiCad reported.

### Phase 5: verify against the real project
*   [x] Expect exactly two findings on `examples/Copperplane_Blink_LEDs`, D1 and SW1, and silence
    for everything else.

## 4. Plan Drift & Architectural Changes

**1. Measured before planning, and the design got simpler.** The spec anticipated needing a rule to
keep mounting holes quiet, since a board-only `MountingHole` footprint has a pad and no symbol. It
does not: `MountingHole:MountingHole_2.2mm_M2` has one pad, unplated and unnumbered, so it counts
**zero** -- and `Mechanical:MountingHole`'s symbol has zero pins. Zero equals zero and H1 through H4
are silent with no rule mentioning them at all. Measured against the real files rather than
assumed, and it removes the special case the spec expected to need.

**2. Reading the library footprint rather than the board's copy, and it was checked.** The board
carries a copy of each footprint taken at placement time, so the two can disagree. Counting from
the library `.kicad_mod` means the check works from a schematic alone, before any board exists.
Verified they agree today on every footprint in the example: 4 for D1, 5 for SW1, 32 for A1 after
excluding the unplated holes, 2 for R1.

**3. The obvious reuse was wrong, which is why it was opened.** `footprint_detail._pads` looks like
exactly this function and is not: it counts `np_thru_hole` pads and never deduplicates by number,
so it reports 36 where this needs 32. Reusing it on the strength of its name would have produced a
false positive on the one component in the example that is correct.

**4. Severity is settled, and the answer is not to grade it.** The spec left open how to separate
D1, which was never going to work, from SW1, whose extra legs are internally common and probably
functions. Nothing deterministic separates them -- both are a two-pin symbol on a
more-than-two-pad footprint. So the check states the fact and the counts, and the explanation is
the model's job with the component data `CTX-319.7` now supplies. That is the same split KiCad's own
findings already use here, and inventing a severity heuristic is where false positives would come
from.

**5. The deterministic fallback was about to credit KiCad with our finding.**
`_findings_from_check_alone` prefixes every finding *"Reported by KiCad's own check"*. Carrying
structural findings through it unchanged would have attributed them to a checker that does not
report them -- the exact confusion this spec exists to prevent, arriving through the back door and
only on the path where the model's prose already failed. Found by reading the fallback's real
output, not by reasoning about it. Structural findings now carry their own prefix.

**6. Findings are appended after the cap, not merged before it.** `_MAX_LIVE_FINDINGS` trims
KiCad's findings at 25 because the block goes into a context window. Merging first would let a
board with two hundred DRC violations push out the one finding nothing else in the toolchain
reports -- silently, on exactly the busy board where it matters most.

**7. The parser is now shared rather than copied.** `.kicad_pcb`, `.kicad_sch` and `.kicad_mod` are
the same s-expression format, and `kicad_board` already had a correct parser handling quoted
parentheses. Its `_parse`/`_sym`/`_value` are now public rather than a third implementation being
written. Nothing outside the module referenced the private names, and its own tests still pass
unchanged.

**8. Not verified: what the review actually says about these.** Every deterministic layer is tested
-- the findings compute, they reach both tabs, they cite the schematic, they survive the model
failing, and they are not labelled as KiCad's. Nobody has run the review in the app and read the
explanation. That is the check `SPEC-302` and `CTX-319.7` were both closed without, and it is the
one that matters.

**9. `test_kicad_write` and `TestRealInjectComponentJob` error intermittently with "KiCad is busy
and cannot respond to API requests right now".** They talk to the maintainer's running KiCad over
`kipy`. Environment-dependent and unrelated to this change; one full run of all 1184 was clean.
Recorded rather than re-run until green.
