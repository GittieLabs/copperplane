# CTX-206.1: Implementation Context: Persist Connection Guidance

> **Spec Reference:** Links to [SPEC-206](../specs/SPEC-206-agent-context-store.md)

**Scope note:** the first slice of `SPEC-206`, scoped to exactly §2.4 -- the `connection_guidance`
key on the Part record, its `pins_hash`, its read-time backfill, its storage-shape validator, and
persisting from the existing `kicad.generate_connection_guidance` route. Deliberately does not touch
the retrieval index, the chat store, or any frontend code -- `PartDetail.tsx` keeps holding the
result in local `useState` for now, unchanged; wiring it to read the now-persisted record is real,
separate, future work. Continues on `docs/SPEC-318-agent-chat` rather than a fresh `feat/CTX-206.1-...`
branch off `origin/develop`, since `SPEC-206` itself hasn't merged there yet -- matching the same
precedent `CTX-317.1` set for a spec and its first context landing in one PR.

## 1. Feature Definition & Execution Plan

### Phase 1: Storage layer (`library_store.py`)
*   [x] `_CONNECTION_GUIDANCE_REQUIRED_FIELDS` + `_validate_connection_guidance_record` -- a real,
    minimal shape check on the stored record, mirroring `_validate_design_guidance`'s own role.
    Named `..._record`, not `_validate_connection_guidance`, so it never collides in a grep with
    `component_pipeline._validate_connection_guidance` (the pin-number safety check at generation
    time, which SPEC-206 §2.4 explicitly says must stay where it is, unharmonised).
*   [x] `_backfill_connection_guidance` -- `setdefault("connection_guidance", None)`, wired into
    both `save_part`'s returned record and `load_part`'s return, matching
    `_backfill_design_guidance`'s exact two-call-site pattern (`CTX-205.4`'s own real fix for the
    same class of miss).
*   [x] `compute_pins_hash(pins)` -- sha256 over `json.dumps(pins, sort_keys=True)`, the same
    canonical-JSON convention `_write_json`/`append_conversation_turn` already use.
*   [x] `save_part_connection_guidance(part_id, pin_guidance, general_notes, provenance)` -- loads
    the part fresh, computes `pins_hash` from that fresh record's own `pins` (never a caller-supplied
    value), builds the record, delegates to `save_part`.

### Phase 2: Provenance plumbing (`component_pipeline.py`)
*   [x] `generate_connection_guidance` now attaches a real `provenance: {"provider", "model"}` to
    its returned dict, read from `executor.config` -- the actual resolved provider/model after
    `_build_agent_executor`'s override logic, not the caller's raw (possibly `None`) arguments. See
    Plan Drift for how this was verified rather than assumed.

### Phase 3: Persist from the existing route (`daemon.py`)
*   [x] `kicad_generate_connection_guidance` now calls `library_store.save_part_connection_guidance`
    with the pipeline's result before returning it. The wire response to the frontend is byte-for-byte
    unchanged (same dict); persistence is a real side effect this route now also performs.

### Phase 4: Tests
*   [x] `tests/test_library_store.py`: `TestConnectionGuidanceStorage` -- backfill-to-`None`, shape
    validation (missing field, malformed pin entry, non-dict provenance), persist-and-reload,
    `pins_hash` computed from the real current record (not a stale caller copy), and
    `compute_pins_hash`'s own determinism/content-sensitivity.
*   [x] `tests/test_component_pipeline.py`: `TestGenerateConnectionGuidance` (mocked) -- provenance
    reflects `executor.config`, not raw `None` arguments; `TestRealGenerateConnectionGuidance`
    (real, skip-if-no-key) gained a provenance assertion.
*   [x] `tests/test_daemon.py`: existing `test_001` updated for the route's now-required
    `provenance` key in the mocked pipeline return; new `test_001b` proves the route actually
    persists onto the real Part record (the prerequisite this context exists to close).
*   [x] Full suite: `python3 -m unittest discover tests` -- **496 passed, 6 skipped** (real-provider
    tests with no credential in this environment), 0 failures.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (non-deviation, confirmed by reading real installed source): `AgentExecutor.config`
    is a real public property, used directly rather than changing `_build_agent_executor`'s shared
    return signature.**
    *   *Reasoning:* Recording `provenance` requires the *resolved* provider/model (Settings override
        vs. the prompt file's own default), which only exists inside `_build_agent_executor`'s local
        `config` variable -- not exposed by its `(executor, provider_client)` return tuple. The first
        option considered was widening that tuple to `(executor, provider_client, config)`, but
        `_build_agent_executor` has four real call sites in `component_pipeline.py`
        (`search_components`, `generate_connection_guidance`, the board-advisor path, and a
        workflow-node loop), so that would have touched three call sites that don't need this value,
        for a change scoped to one. Checked the installed `agentflow/agent/runtime.py` directly before
        deciding: `AgentExecutor.__init__` stores `config` as `self._config` and exposes it via a real
        `@property config`, so `executor.config.provider`/`.model` already gives the exact same
        resolved value with zero signature changes anywhere.
    *   *Impact:* `component_pipeline.py`'s only change is inside `generate_connection_guidance`
        itself; `_build_agent_executor` and its other three callers are byte-for-byte unchanged.

*   **Deviation 2 (non-deviation, confirmed as designed): a second, independent
    `_validate_connection_guidance`-named function was deliberately *not* created; the storage-side
    check is named `_validate_connection_guidance_record` instead.**
    *   *Reasoning:* `component_pipeline.py` already has a real `_validate_connection_guidance` (the
        fail-closed pin-number check at generation time, `CTX-308.7`). `library_store.py` needed its
        own, differently-scoped check (a minimal shape check before writing to disk, matching
        `_validate_design_guidance`'s role) -- giving it the identical name in a different module
        would be legal Python but a real landmine for a future grep across the two files, especially
        since `SPEC-206` §2.4 itself insists these two checks must not be harmonised into one.
    *   *Impact:* Purely a naming choice; no behavioral difference from what the spec described.
