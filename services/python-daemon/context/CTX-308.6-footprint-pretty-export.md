# CTX-308.6: Implementation Context: Footprint Export to a Real .pretty Library

> **Spec Reference:** Links to [SPEC-308](../../../apps/tauri-ui/specs/SPEC-308-footprints-schematic-advisor.md)

`SPEC-308` §1's own stated goal: "...create one from datasheet package dimensions; **export it to a
real `.pretty` library**; link it to a Part." `CTX-308.5` shipped generation; this context ships the
export half, closing the remaining piece of that sentence.

## 1. Feature Definition & Execution Plan

### Phase 1: Hand-build a real `.kicad_mod` writer
*   [x] Format confirmed by reading actual `.kicad_mod` files on this machine before writing any
    code -- a plain SMD 2-terminal part (`Resistor_SMD.pretty/R_0603_1608Metric.kicad_mod`) and a
    real through-hole pad (`Package_DIP.pretty`) -- the same verification standard
    `_build_kicad_sym_text` already held itself to for symbols, not guessed from documentation.
*   [x] `library_store.py::_build_kicad_mod_text`: builds a real `(footprint ...)` S-expression from
    a Footprint's own `pads`/`courtyard` -- exactly the shape `kicad_write.generate_pad_layout`
    already produces and `kicad_write.build_footprint_instance` already consumes for a live board
    write. Pad shape choices (`rect` for SMD, `circle` for a PTH's copper layer/drill) deliberately
    mirror `build_footprint_instance`'s own `PadStackShape` choices, so a footprint looks the same
    whether it reaches KiCad via a live inject or this exported file.
*   [x] A KiCad footprint library is a directory whose name ends in `.pretty` -- confirmed against
    every real footprint library on this machine, unlike a symbol library (a single `.kicad_sym`
    file, no wrapper directory). `library/footprints.pretty/` is a new, real directory this context
    introduces, distinct from `library/footprints/`'s existing JSON records -- directly addable from
    a real `fp-lib-table` entry if a user ever wanted to.

### Phase 2: `export_footprint_kicad_mod` + `library.export_footprint` route + frontend
*   [x] `library_store.py::export_footprint_kicad_mod(footprint_id)`: loads the Footprint, requires
    `pads`/`courtyard` to be present, writes `library/footprints.pretty/<footprint_id>.kicad_mod`,
    returns the path.
*   [x] Fails closed with a clear, specific reason for a footprint with no real geometry -- every
    footprint reachable through `CTX-308.2`'s own found-footprint attach flow (`{footprint_id,
    library, footprint_name}`, no pads at all), since that footprint is already a real `.kicad_mod`
    sitting in the user's own KiCad library or this app's saved-library record; there is nothing new
    to export. Only a `CTX-308.5`-generated footprint has geometry to export at all.
*   [x] `daemon.py`: new `library.export_footprint` route (mirrors `library.export_symbol`'s own
    naming and shape exactly).
*   [x] `apps/tauri-ui/src/lib/footprints.ts::exportFootprint` + `PartDetail.tsx`: an "Export
    Footprint (.kicad_mod)" button in the Footprint-linked state, mirroring "Export Symbol"'s own
    UI pattern (button → path shown → "Open footprint" via the shell plugin). Shown for any linked
    footprint, not gated on `footprintGenerated` -- the daemon's own honest error is what tells the
    user a found footprint has nothing to export, rather than the UI silently hiding the option.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: deliberately no "footprint_id containing a double quote" escaping test, unlike
    the equivalent symbol export test.** `TestExportSymbolKicadSym.test_003` tests `_sexpr_str`
    escaping via a pin *name* containing a quote -- safe, since a pin name is just text inside the
    file. For footprints, `footprint_id` is both the S-expression name *and* this file's own on-disk
    filename (`<footprint_id>.kicad_mod`) -- a literal `"` is invalid on Windows, the exact class of
    bug `CTX-308.4` already found and fixed for `:` in this same field. `footprint_id` is already
    required to be filesystem-safe by that established convention, so writing a test that
    deliberately violates it would be testing an unrealistic input while introducing a real
    cross-platform failure into this context's own test suite -- caught and removed before it ever
    reached CI, not discovered by a real Windows run. `_sexpr_str`'s escaping correctness is already
    covered by the symbol export test (same shared helper function).
*   **Deviation 2: `kicad-cli fp export svg`'s real CLI contract differs from `sym export svg`'s --
    confirmed by actually running it, not assumed from `--help` text.** `sym export svg` accepts a
    single `.kicad_sym` file path directly. `fp export svg` returned "Footprint library does not
    exist or is not accessible" when pointed at a single `.kicad_mod` file the same way -- it expects
    the containing `.pretty` *directory*, with `--footprint <name>` naming which footprint inside it
    to export. Both real test cases (`TEST-002`/`TEST-003`) pass the directory, not the file, for
    exactly this reason.
*   **Deviation 3: export is real but genuinely only useful for generated footprints today --
    confirmed directly, not assumed, before scoping this context.** Every footprint reachable
    through `CTX-308.1`/`.3`/`.4`'s own search-and-attach flow already exists as a real `.kicad_mod`
    file (in the user's installed KiCad library, or this app's own prior save of one). This
    context's export path only ever produces new value for a `CTX-308.5`-generated footprint, which
    is exactly the case the daemon route accepts and every other case it cleanly rejects -- not a
    gap, the correct scope.
