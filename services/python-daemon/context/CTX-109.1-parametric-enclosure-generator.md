# CTX-109.1: Parametric Enclosure Generator: board extraction + real geometry + persistence

> **Spec Reference:** Links to [SPEC-109](../specs/SPEC-109-parametric-enclosure-generator.md)

The first (and, per `SPEC-109`'s own scope, only planned) slice: real board-outline and
mounting-hole extraction from a live KiCad connection, a real hollow/walled/standoff enclosure
build extending `freecad_bridge`'s existing subprocess pipeline, and real `Artifact` persistence
closing `SPEC-304`'s already-enforced `board_revision` requirement. UI changes to the Enclosure
tab's current width/depth/height form are explicitly **not** covered here — `SPEC-109`'s own
Cross-Module Impacts note this is likely a later child context, the same way `CTX-108.3` followed
`CTX-108.1` for the KiCad write path's own UI trigger.

## 1. Feature Definition & Execution Plan

### Phase 1: Board data extraction (`kicad_bridge.py`)
*   [x] `get_board_outline()`: reads real `BoardShape` items via `Board.get_shapes()`, filters to
    the `Edge.Cuts` layer (`BL_Edge_Cuts`), and unions each shape's own real `bounding_box()` (every
    concrete shape type -- `BoardRectangle`/`BoardSegment`/`BoardPolygon`/`BoardCircle`/`BoardArc` --
    already exposes one, as a real callable method, not a property -- see Plan Drift) into a single
    real board bounding box in mm. This is not a fallback: `SPEC-109` §1's own non-goal is a fixed
    rectangular enclosure only, so a bounding box *is* the real, sufficient board-outline data --
    true arbitrary-polygon outline tracing would be needless complexity for a shape this spec
    explicitly isn't building. Positions convert from `kipy`'s internal nm units to mm
    (`x / 1_000_000`) the same way `CTX-108.1` already established on the KiCad-write side of this
    boundary — a known, expected conversion, not a place to rediscover the bug independently.
*   [x] `get_mounting_holes()`: reads real `FootprintInstance` items via `Board.get_footprints()`
    (not raw pads — a `Pad` from `Board.get_pads()` carries no link back to its parent footprint,
    but a `FootprintInstance`'s own `.position` is already real, absolute board-space, and its
    `.definition.pads` gives the real drill diameter). A footprint is a recognized mounting hole
    when its library identifier (`instance.definition.id.library`) case-insensitively contains
    `"MountingHole"` — KiCad's own standard library for exactly this purpose — or its
    `reference_field` matches the `H<digits>` convention that library's footprints get by default.
    Every `PT_NPTH` pad on a recognized footprint is returned with real position (mm) and drill
    diameter (mm); an `PT_NPTH` pad on an *unrecognized* footprint is still returned, with
    `recognized: False` — the caller (Phase 3's route) decides whether to fail closed on it, not
    this extraction function, so the real board data stays fully inspectable either way.
*   [x] A board with no `Edge.Cuts` shapes at all raises a clear, new
    `BoardOutlineMissingError` — never a silent empty/zero-size outline.

### Phase 2: Real enclosure geometry (`freecad_bridge.py`)
*   [x] Extend `generate_enclosure`'s signature: alongside the existing `width`/`depth` (now
    optional, kept as the explicit no-board-data fallback `SPEC-109` §3 requires), accept an
    optional `board_outline` (Phase 1's real return shape), `wall_thickness_mm`, `clearance_mm`, a
    list of real `standoffs` (`x_mm`/`y_mm`/`diameter_mm`/`height_mm`), and `fillet_radius_mm`.
    `height` is always required in both modes -- a board outline is 2D and has no Z dimension to
    derive it from.
*   [x] The generated FreeCAD build script becomes a real boolean shell (outer box minus an inset
    inner box sized from outline + clearance + wall thickness) with a cylinder unioned in at each
    real standoff position, and `fillet_radius_mm` applied to every vertical edge of the result
    (outer corners and the inner cavity's own corners alike) — still built inside `SPEC-104`'s
    unchanged temp-script → `freecadcmd` → export → exit subprocess pattern.
*   [x] Export **both** `.glb` (unchanged) and a new `.step` file from the same build. Return value
    changes from a bare `.glb` path string to `{"glb_path": ..., "step_path": ...}` — a real,
    intentional breaking change to this function's own contract (see Plan Drift for the route-level
    consequence, which Phase 3 resolves).

### Phase 3: Route wiring + real Artifact persistence (`daemon.py` + `library_store.py`)
*   [x] A new `freecad_generate_enclosure` daemon-level route wrapper (matching
    `kicad_generate_component`/`component_search`'s own established pattern of a thin function
    composing bridge modules) replaces the direct `routes["freecad.generate_enclosure"] =
    generate_enclosure` binding.
*   [x] **Mode selection is explicit, not connection-sniffed:** when the caller supplies both
    `width` and `depth`, the route always uses the no-board-data fallback -- unchanged from today's
    behavior, and never silently overridden just because a KiCad connection happens to be open (a
    caller who explicitly typed manual dimensions did not ask for the daemon to substitute different
    ones). Board-driven mode only runs when the caller omits `width`/`depth`, at which point a real
    KiCad connection is required -- there's no further fallback once the caller has asked for it.
*   [x] **Recognized-only standoffs, not fail-closed on the whole build:** re-examined from the
    spec's original framing. Failing the entire generation over one unrecognized `PT_NPTH` pad would
    block real boards that have legitimate non-mounting-hole NPTH pads (test points, thermal vias)
    unrelated to this feature. The real risk `SPEC-109` §3 names is drilling a standoff where one
    doesn't belong -- so only `recognized: True` holes become real standoff cylinders; unrecognized
    ones are excluded from the geometry but still named in the route's own return value
    (`unrecognized_holes`), so a future UI can surface them rather than the daemon either guessing or
    blocking outright.
*   [x] `board_revision` is a real `sha256` hex digest of the exact board outline + recognized-hole
    data actually used to build the enclosure (deterministic, self-contained, no extra KiCad calls
    needed) -- `"manual:{width}x{depth}x{height}"` in the no-board-data fallback, honestly
    distinguishing "no live board data was used" from a real hash.
*   [x] The route calls `library_store.save_artifact` with `kind: "enclosure"` and the real
    `board_revision` above -- for the first time actually satisfying the schema requirement
    `library_store.py` has enforced (but never been called against for an enclosure) since
    `CTX-304.1` -- **only when the caller supplies `project_name`** (optional, default `None`). This
    keeps today's frontend contract (`App.tsx`'s `dims` object, no `project_name`) working
    unmodified: artifact persistence is real and available the moment a caller supplies it, without
    requiring the UI-wiring child context `SPEC-109` already names to land first.

## 4. Plan Drift & Architectural Changes

**Phase 3's route design changed twice from the original Phase 3 plan sketch, both times before any
code was written against the stale version.** The original plan (written when only Phase 1 existed)
said the route should read board data "when a live KiCad connection is available" and "fail closed"
on any unrecognized mounting hole. Re-examined while actually implementing the route:
1. **Connection-sniffing would silently override an explicit request.** If a user's KiCad happens to
   be open, `App.tsx`'s existing manual width/depth/height submission would have silently switched to
   board-driven geometry the user never asked for — a surprising behavior change, not a fallback.
   Mode selection is now explicit: supplying `width`/`depth` always means manual mode, board-driven
   mode only runs when the caller omits them.
2. **"Fail closed" was the wrong response to one unrecognized hole.** The real risk `SPEC-109` §3
   names is drilling a standoff where none belongs — not the mere presence of an NPTH pad the
   recognizer doesn't understand, which could just as easily be a test point or thermal via
   unconnected to mounting at all. Aborting the entire build over that would block real, legitimate
   boards. Unrecognized holes are now excluded from standoff geometry but still reported
   (`unrecognized_holes`) rather than either guessed into service or silently dropped.

Both corrections are recorded here, not just made silently, because `SPEC-109` §3's own text (the
"fails closed" language) still reads as the original framing — a reader following that spec directly
to this context would reasonably expect the stricter behavior this implementation deliberately does
not do.

**A real, full end-to-end verification, no mocks anywhere in the chain**, run after all three phases
landed: `daemon.freecad_generate_enclosure(height=15, project_name="real-e2e-test")` against the same
live KiCad 10.0.3 connection Phase 1 used, the same real `freecadcmd` 1.1.1 Phase 2 used, and a real
`library_store` temp storage root. Produced a real `.glb` and `.step` file (confirmed to exist on
disk), and a real `Artifact` record with `kind: "enclosure"` and a real `sha256` `board_revision`,
loaded back via `library_store.load_artifact` afterward. The currently-open board has no
`MountingHole`-library footprints, so `unrecognized_holes` was empty and no standoffs were built —
consistent with Phase 1's own earlier live result, not a new gap.

**A real bug in Phase 1, found only by live verification against an actually-running KiCad 10.0.3,
not by the mocked test suite.** `get_board_outline`'s first draft accessed `shape.bounding_box` as a
property, matching every concrete `kipy.board_types` shape class's own `dir()` listing (which lists
attribute *names* but doesn't distinguish a property from a plain method). Running it for real
against a live board immediately raised `AttributeError: 'function' object has no attribute 'pos'`
— `bounding_box` is a real, callable *method* (`shape.bounding_box()`), not a property, despite its
naming convention suggesting otherwise. The mocked unit tests written alongside the first draft
passed cleanly, because they encoded the same wrong assumption (`_FakeShape.bounding_box` was set as
a plain attribute) rather than the real interface — a mock can only be as honest as the assumption
that built it. Fixed in both the real function and the test fakes (`_FakeShape.bounding_box` is now
a real callable), and re-verified against the same live KiCad session afterward: a real, currently
open board's outline resolved to `{"x_mm": 100.0, "y_mm": 82.22, "width_mm": 33.02, "height_mm":
17.78}`. `get_mounting_holes` was verified live too and correctly returned an empty list — the real
board open at verification time has no `MountingHole`-library footprints, a legitimate result, not a
bug, and not something this task should fabricate by mutating a real board just to exercise a
non-empty case.

**Phase 2's geometry was prototyped directly against `freecadcmd` before being wired into
`freecad_bridge.py` at all**, not written speculatively and then debugged through a failing test —
`Part.Shape` has no built-in "select the vertical edges" helper, and fillet operations on boolean-cut
shapes with unioned cylinders are exactly the kind of real solid-modeling behavior that's easy to get
subtly wrong (e.g. a cylinder's own vertical seam edge technically matches a naive "two vertices,
same X/Y, different Z" filter too). A standalone script run through the real, locally installed
FreeCAD 1.1.1 confirmed the exact approach — filtering `result.Edges` by real vertex geometry, then
calling `result.makeFillet(radius, vertical_edges)` — produces a valid, correctly-filleted solid
before any of it was written into this module. The real board-driven tests in
`TestBoardDrivenEnclosure` (hollow-shell volume, standoff-cylinder volume, a real STEP header) are
that same verification, kept as permanent regression coverage rather than a throwaway prototype.

**`generate_enclosure`'s return value changed from a bare `.glb` path string to
`{"glb_path", "step_path"}` — a real, intentional breaking change to this function's own contract,
landing ahead of Phase 3.** `daemon.py` still wires `routes["freecad.generate_enclosure"] =
generate_enclosure` directly (unchanged from `SPEC-104`/`CTX-105.1`), so between this commit and
Phase 3's route rewiring, the exposed JSON-RPC route technically returns the new dict shape instead
of the string `apps/tauri-ui/src/App.tsx`'s `submitJob<string>('freecad.generate_enclosure', dims)`
still expects. This is a real, deliberate mid-implementation inconsistency, safe only because it
never leaves this feature branch in this state — Phase 3 replaces the direct route binding with a
wrapper that both supplies real board data and restores a frontend-compatible contract (or the
frontend's own contract is updated in the later child context `SPEC-109` already names for UI work).
Flagged here explicitly rather than left implicit, per this repo's "state what was not verified"
norm — this repo has no packaged build/release step that would have caught it as a live regression
either way.

**`get_mounting_holes`'s `recognized` heuristic is real but genuinely untested against a live board
with an actual mounting hole**, since none was available to verify against without writing to a real
board (out of scope for a read-only extraction task, and this repo's own established norm against
mutating a developer's real KiCad session in an automated/verification pass). The mocked coverage in
`test_kicad_bridge.py` is the only verification this specific path has — worth a real check with an
actual `MountingHole`-footprint board before this feature ships, flagged here rather than silently
assumed correct.
