# CTX-211.1: The Power Path Review

> **Spec Reference:** Links to
> [SPEC-211](../specs/SPEC-211-power-path-review.md)

The second pack under `SPEC-210`, and the one carrying the *"this would have cooked"* story. Phase 1
was run before any of it was planned, and it moved two of the spec's load-bearing claims — so this
plan is built on what five real boards actually contain rather than on what the spec assumed in
September.

---

## 1. Feature Definition & Execution Plan

### Phase 1: What is actually on a board — DONE, and it moved the spec

*   [x] Read the netlist of all five available boards and count discrete linear regulators.
*   [x] Test the obvious "power_in plus power_out" regulator heuristic before building on it.
*   [x] Check whether `lib_id` classifies regulators the way it classified `Device:LED`.
*   [x] Check whether the supply rail is derivable, since `SPEC-343` §2.5.2 forbids asking first.
*   [x] Write the findings into `SPEC-211` §2.0 and correct every claim they falsify.

Recorded in full as `SPEC-211` §2.0. The three that change this plan: connectivity now exists so
item 2 is a finding rather than a question; `lib_id` library membership closes the spec's largest
stated unknown; and **no board available to this project has a discrete linear regulator at all.**

### Phase 2: Identifying a linear regulator, and refusing to guess — DONE

*   [x] Classify on `lib_id` library membership, not on pin roles and not on the value string.
*   [x] `Regulator_Linear` is the pack's subject. `Regulator_Switching` is explicitly **not** —
      the dissipation arithmetic is nonsense there, and it is what the pack recommends as the fix.
*   [x] Read `Vout` from the symbol name where the name encodes it, and yield nothing where it
      does not, rather than falling back to a default.
*   [x] Split compound `pintype` values on `+` wherever pins are read at all.
*   [x] A pack that finds no regulator reports nothing, and is not an error.

### Phase 3: The dissipation finding, its arithmetic, and its caveat

*   [ ] `(Vin - Vout) x Iout` against the package thermal limit, emitted as a `computed` claim.
*   [ ] Lead with the ceiling, not the wattage — `SPEC-211` §1 settled that the teachable number is
      *"your 1A regulator is a 130mA regulator on this supply"*.
*   [ ] The copper-area caveat travels with the number, as a UI requirement rather than a footnote.
*   [ ] A regulator with no thermal data produces silence or an explicit "cannot compare", never an
      assumed thermal resistance. This is `SPEC-211` §2.6's one surviving open question.

### Phase 4: Input voltage against an absolute maximum, now that the netlist can prove it

*   [ ] Use the netlist to establish that the rail and the part's supply pin are one net. Without
      that proof this stays a question, exactly as §2.4 originally argued.
*   [ ] Derive the supply from the rail name before asking the user for it.
*   [ ] Fall back to `input_supply` intent when the rail is unnamed, and to a question when neither
      is available.

### Phase 5: What the pack says when the regulator is inside a module — DONE

*   [x] Settle with evidence what `A1` pin 8 `VIN_8` on a `+5V` rail should produce. The §1
      arithmetic applies to the Arduino's internal regulator, whose datasheet this app does not
      hold.
*   [x] Whatever it produces must not claim a number the app cannot source.

## 4. Deviations & Discoveries (Plan Drift)

*   **I tested the obvious heuristic before building on it, and it was 0% precise.** "A part with a
      `power_in` pin and a `power_out` pin is a regulator" is the rule I would have written from the
      spec alone. Across five boards it returns `Arduino_UNO_R3`, `Adafruit-Feather-ESP32-S3` and
      `XIAO_ESP32-S3` — three dev board modules, no regulators.

    What makes it dangerous is that it is not obviously wrong: those modules *do* contain
    regulators, so every hit looks defensible until you ask which datasheet the pack is about to do
    arithmetic against. `lib_id` membership was the answer the whole time, and `SPEC-210` had
    already found it once for `Device:LED`.

*   **`pintype` is a compound string and I would have written an equality check.** The real values
    include `power_out+no_connect`. `type == "power_out"` drops every unconnected power pin and
    raises nothing — a silent undercount, which is the failure mode that survives a test suite.

*   **The spec's central constraint had expired between drafting and starting.** `SPEC-211` was
    written on 2026-09-07 around *"nothing here needs schematic connectivity"*, and `CTX-210.1`
    shipped netlist reading on 2026-09-09. §3's own risk list argued netlist reading should be
    *"the next platform investment after these two packs land"* — it landed first, before the pack
    that wanted it.

    The lesson is about reading order, not about either decision: a spec more than a few days old in
    this repo has to be re-checked against what shipped in between, because the specs do not know
    when they have been overtaken.

*   **No board we have exercises the lead case, and that is the finding I would most like to be
    wrong about.** Zero discrete linear regulators across all five. The *"this would have cooked"*
    story — the reason this pack was prioritised — can only be demonstrated against a schematic
    authored for the test.

    A fixture is a real KiCad file read by real `kicad-cli` and it is worth building, but it proves
    the arithmetic, not the triggering, and those are different claims. What five real boards *do*
    show is the case the spec did not lead with: power arrives through a devkit module or a battery,
    every single time.


*   **Phase 2's real work turned out to be the parse refusing to answer.** The checklist item read
    *"read `Vout` from the symbol name where the name encodes it"*, which sounds like a regex. 440 of
    `Regulator_Linear`'s 1,626 symbols end in a numeric group, and parsing all of them is wrong about
    a third of the time.

    The absurd failures are the safe ones: `LM317_SOT-223` reading as a 223V regulator gets noticed.
    The dangerous shape is `APE8865N-12-HF-3` — 125 symbols where the trailing `-3` is a variant code
    and the real output is the `-12` in the middle. A naive parse reports **3V for a 1.2V part**, and
    nothing about "3V" looks wrong. `TC1262-33` is the same trap from the other side: it genuinely
    *is* 3.3V under the decimal-elided convention, and telling it apart from a real 33V part needs a
    rule there is no evidence for.

    Restricting to an explicit decimal point keeps 226 symbols spanning 1.0V to 10.0V with no
    package-code collisions at all — and keeps `AMS1117-3.3`, which is the part the whole spec is
    about. Verified across all 1,626 real symbols, not against examples I chose: `TEST-008`.

*   **The test that earns its keep is `test_a_dev_board_module_is_not_a_regulator`.** It pins the
    three parts Phase 1's rejected heuristic actually returned. Without it, someone reintroducing a
    pin-role shortcut later gets a green suite.

*   **One run of the full suite errored and I did not capture it, so I ran it again properly rather
    than calling it a flake from memory.** Captured on a targeted re-run: `test_002_real_google_chat`,
    where Google omits `output_tokens` and the assertion compares `None` to an int. Intermittent,
    already tracked, unrelated to this change — but "already tracked" is a claim that needed the
    traceback behind it, not a recollection. Two subsequent full runs: 1,449 tests, OK.


*   **Phase 5 was taken before Phases 3 and 4, and it was the right order.** It is the phase that
    decides whether this pack says anything at all about the boards this project has, and Phase 1
    had just measured that the answer might be *nothing*.

    It is not nothing. On `Copperplane_Blink_LEDs` the `+5V` rail lands on `A1` pin 8, whose pin name
    is `VIN` — and the same part declares a separate `+5V` output pin, which sits unconnected. The
    symbol itself says those are different pins with different jobs, so the claim needs no datasheet:
    the app is reading what the schematic states, not reciting what it knows about Arduinos.

*   **It asks instead of asserting, and that is a design decision rather than hedging.** The app
    cannot see inside the module. A buck-boost converter accepts 5V on `VIN` perfectly happily, so a
    flat *"this is wrong"* would be confidently wrong on a legitimate design — `SPEC-211` §3's named
    worst case. `TEST-010` pins both halves: the explanation ends in a question, and every
    voltage-shaped figure in it appears on the schematic. The Arduino's real `VIN` minimum is a
    datasheet fact this app does not hold, and it must not appear.

*   **Ground is typed `power_in` on two boards and `power_out` on a third.** `Arduino_UNO_R3` and
    `Adafruit-Feather-ESP32-S3` declare their ground pins `power_in`; `XIAO_ESP32-S3` declares its
    `power_out`. Same electrical node, opposite declarations, three boards in one project. Any rule
    reading "power_in means a supply input" treats every Arduino's ground as one — which is the same
    class of mistake that withdrew `power_pin_without_decoupling` back in `CTX-210.1`, arriving from
    a new direction. Ground is excluded by **name**.

*   **`XIAO_ESP32-S3` has no `pinfunction` on any pin at all.** Its pins are *numbered* `5V`, `3V3`
    and `GND`. A rule keyed only on `pinfunction` reads nothing from that board, silently, and it
    looks exactly like a board with no power pins rather than like a bug.

*   **I read the wrong voltage, and only running it against the real board found it.** A supply pin
    is named for its role — `VIN` — so it has no voltage of its own; the voltage is on the net
    (`+5V`). An output pin is the reverse. My first version read the pin name for both, so the pack
    returned **zero findings on all five boards**, including the one case it was written for.

    Every unit test I had would have passed on a version that could never fire. What caught it was
    running the pack against five real files and noticing that the expected hit was missing — and
    the failure mode is worth naming, because a pack that is silent everywhere looks identical to a
    pack that is correct and has nothing to say.

*   **One of my own tests was wrong, not the code.** `test_it_claims_no_number_it_cannot_source`
    extracted every digit from the explanation and failed on the `1` in `A1`. A reference designator
    is not a claim about anything; the property I actually wanted was about voltage-shaped figures.
    Tightened to match its own docstring.

*   **Not verified: the frozen sidecar.** `power_path` is a plain top-level `import` in
    `consideration_packs`, which `daemon.spec`'s own note says PyInstaller's static analysis handles
    without a `hiddenimports` entry — so there is good reason to expect it bundles. That is reasoning,
    not evidence. The `dist/` binary on this machine predates this work, so exercising it would prove
    nothing about this change, and a rebuild belongs with the close-out rather than mid-phase.
