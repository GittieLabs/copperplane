# CTX-308.4: Implementation Context: Search the User's Own Saved Footprint Library

> **Spec Reference:** Links to [SPEC-308](../../../apps/tauri-ui/specs/SPEC-308-footprints-schematic-advisor.md)

**The second of `PRODUCT-PLAN.md` §8 item 3's three ranked footprint sources.** `CTX-308.1`/
`CTX-308.3` cover source one (installed KiCad libraries, including the built-in set). This context
covers source two: footprints this app has already saved into `library/footprints/`
(`library_store.save_footprint`, first wired by `CTX-308.2`'s attach flow) -- real, already-persisted
records this app should be able to find again, not just KiCad's own libraries. Source three
(datasheet generation) remains fully open, not attempted here.

**Design:** `library_store.py` has `save_footprint`/`load_footprint` but no listing/search
function -- unlike `list_parts()`, which already exists for Parts. This context adds the missing
`list_footprints()`/`search_footprints()` pair, mirroring `list_parts()`'s own real pattern (list
`.json` files in the footprints dir, strip the extension). `daemon.py`'s existing
`kicad_search_footprints` route merges both sources -- KiCad-installed results first, the user's
own saved results second, matching `PRODUCT-PLAN.md`'s own stated ranking -- each result tagged
with a real `source` field (`"kicad_library"` / `"your_library"`) so the UI can tell them apart
rather than presenting a single undifferentiated list.

## 1. Feature Definition & Execution Plan

### Phase 1: `library_store.list_footprints()` / `search_footprints()` ✅
*   [x] `list_footprints() -> list[str]`: mirrors `list_parts()` exactly -- lists `.json` files in
    `_footprints_dir()`, strips the extension, sorted.
*   [x] `search_footprints(query: str) -> list[dict]`: case-insensitive substring match against each
    saved footprint's `footprint_name` field. Real, verified-necessary fallback: some footprint
    records (e.g. `{"footprint_id": "SOIC-8", "pads": [...]}`, a shape this repo's own existing
    tests already save) have no `footprint_name` at all -- falls back to matching against
    `footprint_id` itself for those, rather than crashing on a missing key or silently excluding
    them from search.

### Phase 2: merge into the real `kicad.search_footprints` route ✅
*   [x] `daemon.kicad_search_footprints` now calls both `fp_lib_table.search_footprints` and (when
    `library_store` imported successfully -- this route must not require it) `library_store.
    search_footprints`, concatenating KiCad-installed results first, tagging each result with a real
    `source: "kicad_library" | "your_library"` field.
*   [x] Route name/shape stays the same (`kicad.search_footprints`, still synchronous, still not in
    `ASYNC_ROUTES`) -- both underlying searches are local file I/O, no new async concern introduced.
*   [x] Graceful degradation verified for real: `library_store` failing to import returns KiCad-only
    results, not a crash -- mirrors every other route's own established pattern in this file.

### Phase 3: frontend -- distinguish the two sources, tests, verification ✅
*   [x] `apps/tauri-ui/src/lib/footprints.ts`'s `FootprintCandidate` gains a `source` field; the real
    UI in `PartDetail.tsx` shows a small label distinguishing "your library" results from "KiCad
    library" results, so a user understands *why* a candidate appeared (already saved before, vs.
    found in an installed library) rather than presenting them identically.
*   [x] Real unit tests for `list_footprints`/`search_footprints` (`library_store.py`'s own
    established `LibraryStoreTestCase` pattern) -- 4 new; a daemon-route test proving the merge/
    tagging happens for real, plus the graceful-degradation case -- 2 new (existing `TEST-001`
    updated too, since it now exercises the real merge and needed `library_store.search_footprints`
    mocked alongside the pre-existing `fp_lib_table` mock); a `PartDetail.test.tsx` update proving
    the source label renders for both source types -- 1 new.
*   [x] `tsc -b`, `oxlint` (only the two pre-existing unrelated warnings), full `vitest run` --
    111/111, `vite build` clean, full daemon suite -- 203/203.

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Non-deviation, confirmed as designed: the existing `TEST-001` daemon route test needed
    updating, not a regression.** Merging `library_store.search_footprints` into the real route
    means the pre-existing test (which only mocked `fp_lib_table.search_footprints`) started
    calling the real, unconfigured `library_store` and erroring -- expected once the merge landed,
    fixed by mocking both real sources in that test, matching this repo's own norm of updating a
    test's assumptions when the code under test genuinely changed, not treating every red test as a
    bug to work around.
*   **Deviation 2: a real, pre-existing bug in `CTX-308.2`'s own `footprint_id` scheme, caught for
    real for the first time by this context's own new tests -- fixed here since this is where it
    surfaced.** `CTX-308.2` built `footprint_id` as `` `${library}:${footprintName}` ``, mirroring
    KiCad's own `library:name` reference syntax. `footprint_id` is also the on-disk filename
    `library_store.py` persists a Footprint under (`{footprint_id}.json`), and `:` is a reserved
    character in Windows filenames. `CTX-308.2`'s own tests never caught this because
    `attachFootprintToPart` was always mocked in its own frontend tests -- no colon-containing id
    ever reached real file I/O until this context's `test_007_search_footprints_matches_on_
    footprint_name` (a real `library_store` round trip) ran on real `windows-latest` CI and failed
    with `0 != 1` -- a silent failure to find the saved footprint again, not an exception. Fixed by
    switching the separator to `__` in `lib/footprints.ts`, and retroactively noted in `CTX-308.2`'s
    own Plan Drift too, since that's the context that actually introduced the bug.
    **Named, not solved: broader filename-safety of `footprint_id` remains real, narrower risk** --
    a library or footprint name containing some other Windows-reserved character
    (`< > " / \ | ? *`) would still break. Real KiCad library/footprint names observed so far
    (`Battery`, `MyPCBLibs`, `MP1584EN_5V_Module`) don't use any of these, and `library_store.py`'s
    other `save_*` functions apply no filename sanitization either -- exhaustive sanitization was
    judged out of this context's own scope, not silently assumed unnecessary.
