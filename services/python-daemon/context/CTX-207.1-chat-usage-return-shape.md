# CTX-207.1: Implementation Context: llm_providers.chat() Usage Return Shape

> **Spec Reference:** Links to [SPEC-207](../specs/SPEC-207-managed-provider-adapter.md)

The prerequisite phase SPEC-207 §2.2/§3 explicitly asks to land first, before any `managed` branch
work: `llm_providers.chat()` widens its return from a bare `str` to `{"text", "usage", "model"}`.
AgentFlow already normalises token usage into the same shape across all three provider classes
(verified directly against the installed source, not assumed) -- what discarded it was this
function's own `return response.text`. This is the free build's first real per-call token
accounting, independent of the managed tier itself.

## 1. Feature Definition & Execution Plan

### Phase 1: widen `chat()`'s return shape
*   [x] `chat()` returns `{"text": str, "usage": {"input_tokens": int, "output_tokens": int} | None,
    "model": str | None}` instead of a bare string. `usage` is `None` only when a provider reports
    an empty usage dict (observed: Google, when `response.usage_metadata` is absent) -- never a
    fabricated `{0, 0}`.
*   [x] `_resolved_model_for(provider, model)` -- a small, independent helper computing the model
    `_build_provider`/`_build_provider_from_record` would actually construct with, added rather than
    changing `_build_provider`'s own return contract (a bare provider client, separately asserted by
    `TestBuildProvider` since CTX-201.1 and left untouched here).
*   [x] Google's raw usage dict carries a third `thinking_tokens` key (verified against the
    installed source) -- dropped in `chat()`'s own return so the shape is identical across every
    provider, matching SPEC-207 §2.2's own claim.

### Phase 2: the one real Python caller
*   [x] `daemon.llm_chat`'s return type annotation updated `str` -> `dict`; its body is unchanged
    (`return llm_providers.chat(...)` already forwards whatever shape `chat()` returns).
*   [x] Confirmed via grep across the whole daemon: `daemon.py`'s `llm_chat` route is the *only* real
    caller of `llm_providers.chat()` in application code (`component_pipeline.py` only mentions it in
    a docstring, contrasting it with `AgentExecutor`'s own separate call path).

### Phase 3: the one real frontend caller
*   [x] `Overview.tsx`'s `handleSend` -- the only real frontend call site of the `llm.chat` route
    (confirmed by grep across `apps/tauri-ui/src`) -- updated: `submitJob<LlmChatResult>` instead of
    `submitJob<string>`, extracting `.text` for the rendered reply and the persisted conversation
    turn. A new local `LlmChatResult` interface documents the shape; `usage`/`model` aren't rendered
    anywhere yet (no surface exists until `SPEC-320`), but the daemon's own accounting now reaches
    the frontend for the first time.
*   [x] A real regression test added (`Overview.test.tsx`) and verified to actually catch the bug it
    targets: temporarily reverting the `.text` extraction reproduced a real React "objects are not
    valid as a child" crash, confirming the test is load-bearing, not just present.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: this phase touches one frontend file, despite SPEC-207 being `user_facing:
    false`.**
    *   *Reasoning:* SPEC-207 §2.2 itself says the return-shape change should "reach the job
        result" -- and the only way to keep that job result usable at all is to update its one real
        consumer (`Overview.tsx`) rather than let a wire-contract change silently corrupt an existing
        surface. This is a mechanical fix to keep an existing surface working through a backend
        contract change, not a new user-facing feature -- the same category of change
        `CTX-303.2`/`CTX-308.x` already made when other backend shapes changed underneath an
        existing UI.
    *   *Impact:* `usage`/`model` reach the frontend now but are not rendered anywhere -- no new UI
        surface was added, matching SPEC-207's own `user_facing: false` scope. A real display for
        this data is `SPEC-320`'s job.
*   **Deviation 2: two additional real test failures were found and fixed that neither this phase's
    own initial plan nor a first full-suite run caught in one pass.**
    *   *Reasoning:* the full backend suite passed on a first run limited to
        `test_llm_providers.py`/`test_daemon.py`; a subsequent full-suite run surfaced a real,
        live-call assertion in `test_async_jobs.py` (`TestRealLLMChatJob`) that also assumed a bare
        string, and the full frontend suite surfaced two real `App.test.tsx` chat-flow tests with
        the same assumption. Neither was found by grepping for `llm_providers.chat(` /
        `'llm.chat'` in application code alone -- both were test-only assumptions about the wire
        shape, invisible to a code-only grep.
    *   *Impact:* fixed in this same phase rather than left as a follow-up gap, and the fix is
        recorded here as a reminder that "no application code depends on it" does not mean "no test
        encodes the old contract" -- both need checking after a return-shape change, not just the
        first.
