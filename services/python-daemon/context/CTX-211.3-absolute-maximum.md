# CTX-211.3: A Rail Above What The Part Allows

> **Spec Reference:** Links to
> [SPEC-211](../specs/SPEC-211-power-path-review.md)

`SPEC-211` §2.1 item 2 — *"the literal fry case: a 12V input and a part rated to 6V."* The last of
the five, and the one both `CTX-211.1` and `CTX-211.2` declined on the same grounds: it needs a
number, and `SPEC-205` stores datasheet quotes rather than numbers.

It is built here because measuring the real quotes showed the extraction is tractable when it is
keyed on the row's own label — and, more importantly, showed how to make a wrong parse harmless.

---

## 1. Feature Definition & Execution Plan

### Phase 1: Read the supply maximum, or refuse to — DONE

*   [x] Key on the row's label, never on "a voltage somewhere in the absolute-maximum section".
*   [x] Rule out pin ratings, currents and temperatures explicitly.
*   [x] Carry the quote and its page with the number, always.

### Phase 2: The finding, and the asymmetry that makes it safe — DONE

*   [x] Emit only on exceedance, so a bad parse is a visible false positive or silence, never a
      false reassurance.
*   [x] Show the datasheet row in the claim and say that the finding is wrong if the row is.
*   [x] Use the netlist to prove the rail reaches the part's supply pin.

## 4. Deviations & Discoveries (Plan Drift)

*   **The naive parse is not merely unreliable, it is wrong in the dangerous direction.** Measured
    against this library's two real part records. The ATTINY85's absolute-maximum section contains:

        Voltage on RESET with respect to Ground......-0.5V to +13.0V
        Maximum Operating Voltage............................................6.0V

    A regex for "a voltage in the absolute-maximum section" finds **13.0V** first. That is a pin
    rating standing in for the rail, more than double the real figure, and it would report a 12V
    supply as safe on a part rated to 6V — `SPEC-211` §1's own fry case, answered backwards. §2.3
    predicted exactly this and I would not have believed how cleanly until I ran it.

    The dot leaders are a second, smaller trap: without stripping them the 6.0V row parses as
    `............6.0`.

*   **The NE555's rows show the other failure mode: extraction loss.** `V Supply voltage(2) 18 V`
    has lost `VCC`'s subscript, and `V Input voltage CONT, RESET, THRES, TRIG V V` has lost its
    numbers **entirely**. There is no parser that recovers the second row, and the honest response
    is to skip it rather than to infer.

*   **What makes this safe is the asymmetry, not confidence in the parse.** This is the decision of
    the context and it is worth stating plainly, because "we built the risky extraction anyway" is
    otherwise indistinguishable from carelessness.

    The pack emits a claim **only when the rail exceeds the parsed maximum.** So:

    * a parse reading too **low** → a visible false positive, displayed next to the datasheet quote
      that contradicts it, which the user can judge and dismiss;
    * a parse reading too **high** → silence, which is precisely what this app did before the pack
      existed.

    There is no path from a bad parse to a false *"you are fine"*. `SPEC-211` §3 forbids confident
    wrongness, and a warning a user can check against a quoted datasheet row is a different
    category of thing from a reassurance they cannot.

*   **So the quote is in the claim, not summarised out of it**, and the explanation ends by saying
    the finding is wrong if the row is. That sentence is the extraction's honesty made visible, and
    `TEST-006` asserts it rather than trusting it to survive an edit.

*   **I built this on `develop` instead of branching first**, and moved it onto
    `feat/CTX-211.3-absolute-maximum` before committing. Nothing had been committed, so the cost was
    nil, but the sequence in `CLAUDE.md`'s loop exists precisely so this is caught by habit rather
    than by noticing.

*   **A heredoc quoting mistake silently made three edits no-ops.** A Python replacement script used
    `"\\n\\n#: The registry..."` as an anchor, which is a literal backslash-n rather than a
    newline, so `str.replace` matched nothing — and the script still printed `ok`, because I had not
    asserted the anchor existed. Two of five edits in the same script did apply, leaving the file
    half-changed and looking fine.

    Caught by grepping for the function that should have been added. The fix in the rewrite was an
    `assert anchor in s` before replacing, which is what any of these scripts should have carried
    from the start.

*   **Not verified against a real board that exercises it.** No project here links a part whose
    board it is actually on — `Copperplane Blink LEDs` links `NE555`, and the board it points at has
    no NE555, so the route correctly stays silent. The firing case runs through the real pipeline
    (real `kicad-cli`, real datasheet quotes) against `attiny_on_12v.kicad_sch`, which is authored
    for the test. The part-loading half of the route was verified separately against the real
    `NE555` record, which extracts 18V from page 4.
