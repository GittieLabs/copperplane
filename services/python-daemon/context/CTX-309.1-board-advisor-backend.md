# CTX-309.1: Implementation Context: Board Advisor Backend

> **Spec Reference:** Links to [SPEC-309](../../../apps/tauri-ui/specs/SPEC-309-board-advisor.md)

The backend half of `SPEC-309`: real ERC/DRC execution, path resolution, and the explain-and-suggest
LLM step. No frontend UI in this context -- split from it deliberately (SPEC-308 §3's own precedent:
"splitting these into separate implementation phases... is the honest reflection of that gap"), the
same way `CTX-308.1`/`CTX-308.2` split daemon and UI work.

## 1. Feature Definition & Execution Plan

### Phase 1: `kicad_cli.py` module + real committed fixtures
*   [x] `find_kicad_cli`: configured override → PATH → per-OS glob fallback, mirroring
    `freecad_bridge.find_freecadcmd`'s exact, already-proven pattern.
*   [x] `run_erc`/`run_drc`: real subprocess (`kicad-cli {sch erc|pcb drc} --format json -o
    <tmpfile>`), real JSON parsing. A nonzero exit is only ever treated as "kicad-cli itself failed"
    (`KicadCliError`), never "violations exist" -- confirmed directly: both real commands exited 0
    with real violations present during `SPEC-309`'s own research.
*   [x] Two real, minimal, hand-written fixture files committed to the repo
    (`tests/fixtures/empty_board.kicad_pcb`, `tests/fixtures/empty_schematic.kicad_sch`) --
    personal real board files that produced the real JSON schema during spec research live only
    outside this repo (`~/repos/PCBs/`), so aren't usable in CI. `empty_board.kicad_pcb`
    deterministically produces a real `invalid_outline` error (no `Edge.Cuts` outline at all);
    `empty_schematic.kicad_sch` is genuinely ERC-clean (0 violations) by KiCad's own real rules --
    both confirmed by actually running `kicad-cli` against them, not assumed.

### Phase 2: PCB path auto-resolution via live IPC
*   [x] `kicad_bridge.get_open_board_path()`: `client.get_open_documents(DOCTYPE_PCB)` →
    `project.path` + `board_filename` → the real, full resolved path. Returns `None` (not an
    exception) when nothing is open -- a normal state the route handles, not an error.
    Deliberately PCB-only: `DOCTYPE_SCHEMATIC` has no live handler at all (`SPEC-309` §2's own
    confirmed finding) -- not attempted here.

### Phase 3: `board_advisor` prompt + `explain_violations` pipeline function
*   [x] `agentflow/agents/board_advisor.prompt.md`: given real, indexed violations plus a
    `check_type`, returns plain-language explanation + a concrete suggested fix per violation, plus
    an overall summary.
*   [x] `component_pipeline.explain_violations`: single agent call (no DAG, mirrors
    `generate_connection_guidance`'s own shape). Real safety check: every response index must be a
    real index into the violations given, and every real violation must get an explanation -- a
    skipped one would silently hide a real problem, the opposite of this feature's purpose.
*   [x] `_MAX_VIOLATIONS_PER_EXPLANATION_CALL = 15`, errors-first prioritization -- `SPEC-309` §3's
    own explicitly-flagged-unresolved risk (a real board can produce dozens of violations, real
    token-limit truncation already bit `component_search`, per `CTX-308.7`'s own Plan Drift), now a
    real, named decision rather than left open.
*   [x] An empty violations list short-circuits before any LLM call -- a clean board/schematic is
    the honest, deterministic, zero-cost answer, not a wasted network call.

### Phase 4: `kicad.check_board`/`kicad.check_schematic` routes + capability reporting
*   [x] `kicad_check_board(pcb_path=None)`: auto-resolves the currently open board when `pcb_path`
    isn't given; a clean `KicadCliError` when nothing is open and no path was given either.
*   [x] `kicad_check_schematic(sch_path)`: always an explicit path -- no default, no
    auto-resolution, consistent with Phase 2's own confirmed real IPC limitation. Flattens ERC's
    real per-sheet violation nesting into one list, each violation tagged with its real
    `sheet_path`.
*   [x] Both registered in `ASYNC_ROUTES` (a real subprocess plus a real LLM call, both genuinely
    multi-second). `kicad.check_board` requires `kicad_bridge` (for auto-resolution);
    `kicad.check_schematic` doesn't -- registered independently, not both-or-nothing.
*   [x] `daemon.get_capabilities`: new `kicad_cli_available`, mirroring `freecad_available`'s exact
    pattern (a broken/missing `kicad-cli` surfaces as an honest capability gap, doesn't take down
    the rest of the app).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: real personal board files (used during `SPEC-309`'s own spec-writing research)
    live outside this repo and can't be committed as CI fixtures -- required hand-writing new,
    minimal, real fixture files instead of reusing what already proved the JSON schema.** Rather
    than fabricate a plausible-looking fixture, each hand-written file was verified the same way the
    real personal boards were: actually run through `kicad-cli`, confirmed to produce the exact
    documented real violation (or real cleanliness). `empty_board.kicad_pcb`'s `invalid_outline`
    error is a fully deterministic, real KiCad output, not a synthetic stand-in.
*   **Deviation 2: no hand-crafted schematic fixture that produces a real ERC violation.** Writing a
    minimal but valid `.kicad_sch` with a real symbol instance and an unconnected pin (to trigger a
    real, non-empty ERC report) requires hand-authoring a correct KiCad symbol S-expression block --
    judged not worth the time against the value gained, since `run_drc`'s own real fixture already
    exercises the "has violations" code path end-to-end (same JSON shape family, same
    `explain_violations` function downstream). The "clean schematic" fixture still proves the real
    subprocess + JSON-parsing round trip for ERC specifically; only the "has violations" path is
    ERC-untested for real. Named explicitly here, not silently accepted.
*   **Deviation 3: `component_pipeline.py` is an increasingly inaccurate module name.** It now holds
    `SPEC-202`'s component extraction, `SPEC-306`'s search, `SPEC-308`'s connection guidance, and now
    `SPEC-309`'s board-violation explanation -- none of the latter three are "component" concerns in
    any real sense. Kept here anyway, following the same precedent `connection_guidance` already set
    in `CTX-308.7`: all four share the same `_build_agent_executor`/`_extract_json`/
    `_run_agent_and_close` AgentFlow plumbing, and splitting it out would duplicate that
    infrastructure for no functional gain. Flagged as real, accumulating naming debt -- a rename
    (e.g. `agent_pipeline.py`) is a real, standalone future cleanup, not attempted here since it
    would touch every existing caller for a purely cosmetic reason unrelated to this context's own
    scope.
*   **Deviation 4: `kicad.check_board` requires `kicad_bridge`; `kicad.check_schematic` does not --
    registered independently, not gated together.** A prior CTX (`CTX-308.5`) established the
    precedent of gating a route on every module it actually calls, not the broadest common set --
    followed here: `check_schematic` never touches `kicad_bridge` at all (always an explicit path),
    so a broken kipy install shouldn't hide it, only `check_board`'s own real auto-resolution
    dependency.
