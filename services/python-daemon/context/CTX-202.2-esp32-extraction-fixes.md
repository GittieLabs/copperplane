# CTX-202.2: Implementation Context: ESP32-S3 Extraction Fixes

> **Spec Reference:** Links to [SPEC-202](../specs/SPEC-202-component-intelligence-pipeline.md)

Real, user-reported bug: searching for and confirming a real ESP32-S3 in the running app failed with
`Extraction did not return valid JSON: Expecting value: line 33 column 69 (char 2216)`. Investigated
against the real Anthropic API throughout (not assumed), which changed the diagnosis twice along the
way -- see Plan Drift. Three real, separate problems were found and fixed, in the order they were
uncovered:

1. **An intermittent, non-deterministic malformed-JSON generation.** The original hypothesis --
   `component_extraction.prompt.md`'s `max_tokens: 2048` truncating a large, 56+-pin response --
   was tested directly and disproven: three fresh, real calls all succeeded at ~4400 characters
   (~1100 tokens), well under the ceiling, while the reported failure was at only ~2216 characters
   (~550 tokens) -- roughly half a complete response, not near any token limit. `generate_component`
   now retries once, specifically on this failure class (`_extract_json`'s own
   `"Extraction did not return valid JSON"` prefix), never on a real, deterministic validation
   failure.
2. **`QFN-56` was not in `PACKAGE_REFERENCE` at all**, so any 56-pin part -- the ESP32-S3 included --
   failed closed deterministically, every time, regardless of the JSON issue above. Added, with the
   same pitch range the table's other QFN entries already use.
3. **A real, live re-test after both fixes above still failed** -- `Package 'QFN-56' expects 56
   pins, got 57`. A second real extraction's raw pin list, read directly, showed the 57th pin is
   `GND_PAD`: the ESP32-S3's own datasheet numbers its exposed thermal/ground pad as a real,
   documented electrical contact, not a hallucination. `PACKAGE_REFERENCE["QFN-56"]` gained
   `"exposed_pad": True`, and `validate_schema`'s pin-count check now accepts either the package's
   nominal lead count or that count plus one for a documented pad -- specific to this real,
   confirmed exception, not a general loosening (every other package keeps the exact-match check).

All three fixes verified together against the real API: three fresh, live `generate_component
("ESP32-S3", ...)` calls all succeeded end-to-end after this context, none did before it.

## 1. Feature Definition & Execution Plan

### Phase 1: Retry on malformed-JSON extraction (`component_pipeline.py`)
*   [x] `_MAX_EXTRACTION_ATTEMPTS = 2`, `_JSON_PARSE_ERROR_PREFIX`. `generate_component` retries the
    whole extract -> validate DAG once, only when the validate node's error text starts with the
    JSON-parse prefix; any other validation failure (unrecognized package, hallucinated pin,
    missing field) raises immediately on the first attempt, matching SPEC-202's own fail-closed
    design -- a retry would not fix a real, deterministic problem.
*   [x] A real `logger = logging.getLogger(__name__)` added to `component_pipeline.py` (it had none
    before); a retry logs a real warning naming the attempt number and the error, via `logging`,
    never `print()` -- the `stdout` rule applies here like everywhere else in this daemon.

### Phase 2: Recognize `QFN-56`, with its real exposed pad (`component_pipeline.py`)
*   [x] `PACKAGE_REFERENCE["QFN-56"]` added (`pin_count: 56`, the same `(0.40, 0.60)` pitch range
    the other QFN entries use, `exposed_pad: True`).
*   [x] `validate_schema`'s pin-count check widened: a package with `exposed_pad: True` accepts
    either its nominal `pin_count` or `pin_count + 1`; every other package's check is byte-for-byte
    unchanged (a single-count set still formats identically to the original error message).

### Phase 3: Tests
*   [x] `tests/test_component_pipeline.py`: `TestGenerateComponentRetry` (new) -- retries once on
    malformed JSON then succeeds; a deterministic validation failure never retries; exhausting every
    retry on repeated malformed JSON still raises. Mocks only the LLM boundary
    (`_build_agent_executor`), matching `TestExplainViolations`'s own established pattern; the real
    `validate_component_schema` handler and its real `_extract_json`/`validate_schema` checks run
    for real against the fake extract text.
*   [x] `TestValidateSchema` gained `QFN-56` coverage: recognized at its nominal 56-pin count,
    recognized at 57 with a real `GND_PAD` pin, and still rejects any other count (58).
*   [x] Full suite: `python3 -m unittest discover tests` -- **558 passed, 6 skipped**, 0 failures.
*   [x] Real, live end-to-end verification (not just mocked): three fresh calls to
    `generate_component("ESP32-S3", ...)` against the real Anthropic API, using the repo's own
    `.env.local` key -- all three succeeded, 57 pins each, after every fix in this context.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the original `max_tokens` truncation hypothesis was disproven by direct evidence,
    not assumed correct.**
    *   *Reasoning:* Before writing any fix, three fresh, real calls to the extraction agent alone
        (bypassing the package-reference check that was blocking full reproduction) were run against
        the real API. All three succeeded at ~4400 characters, and the reported failure was at only
        ~2216 characters -- about half a complete response, nowhere near the 2048-token ceiling a
        truncation theory would predict. Raising `max_tokens` would not have fixed the real bug; the
        real cause is an occasional, non-deterministic malformed-JSON generation, mitigated by a
        retry, not a bigger budget.
    *   *Impact:* `max_tokens` in `component_extraction.prompt.md` is unchanged. The real fix
        (Phase 1) is a narrowly-scoped retry, not a parameter tune.
*   **Deviation 2: a third, separate bug (the QFN-56 pin count) was found only after the first two
    fixes were already verified live, not predicted in advance.**
    *   *Reasoning:* A real end-to-end run after Phases 1-2 still failed, with a new, different
        error (`Package 'QFN-56' expects 56 pins, got 57`). Reading the real raw pin list directly
        (rather than guessing) showed pin 57 was `GND_PAD` -- the ESP32-S3's real, documented
        exposed thermal pad, not a hallucination -- which is what Phase 3's `exposed_pad` widening
        addresses.
    *   *Impact:* None negative -- confirms the value of verifying against the real API at every
        step rather than declaring victory after the first two fixes passed their own tests.
*   **Deviation 3 (non-deviation, confirmed as designed): `QFN-16`/`QFN-24` were not given
    `exposed_pad: True`.**
    *   *Reasoning:* Real QFN packages commonly expose a thermal pad, and it's plausible these two
        have the same real characteristic -- but that was not verified against a real datasheet in
        this context, only inferred by family resemblance. Marking them without real evidence would
        be exactly the kind of unverified claim this repo's own norms warn against.
    *   *Impact:* If a real extraction for a `QFN-16`/`QFN-24` part hits the same class of failure,
        that's the real evidence needed to widen those two entries the same way -- named here so a
        future session doesn't have to rediscover this reasoning from scratch.
