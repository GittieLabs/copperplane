# CTX-207.2: Implementation Context: Managed Provider Branch & Structured Error Taxonomy

> **Spec Reference:** Links to [SPEC-207](../specs/SPEC-207-managed-provider-adapter.md)

The core of SPEC-207: `managed` becomes a real, locked `ProviderRecord` (SPEC-208's own §2.2.3
already reserved the id; this phase adds the record itself), and its HTTP errors map to SPEC-207
§2.3's six structured codes, retried per its own policy, surfacing on `SPEC-105`'s `job.failed`
payload as a real `code` field -- never a string a UI would have to pattern-match. Lands after
CTX-207.1 (the `chat()` usage-return-shape prerequisite) per SPEC-207's own explicit sequencing.

## 1. Feature Definition & Execution Plan

### Phase 1: the locked `managed` preset + its secret
*   [x] `_preset_records()` gains a sixth entry, `id: "managed"`, `kind: "openai_compat"`. `base_url`
    reads a build-time env var (`HAS_MANAGED_GATEWAY_URL`) with **no hardcoded production
    fallback** -- see Plan Drift Deviation 1 for why. `api_key_ref: "managed_token"`.
*   [x] `models: {}` -- deliberately no default alias for either role. SPEC-207 §2.1 is explicit
    that "the daemon must not validate a Managed model name"; inventing a plausible-looking default
    (e.g. SPEC-404 §2.3's own illustrative `has-standard`/`has-deep` examples) would be exactly that
    kind of validation-by-assumption. A role bound to `managed` with no explicit model override now
    hits SPEC-208 §2.3.2's existing "no model for role" `LLMProviderError`, unchanged machinery.
*   [x] `capabilities: {tool_use: True, strict_json: True}` -- the gateway proxies to real hosted
    vendor APIs (SPEC-404 §2.2), unlike Ollama's honestly-limited declaration.
*   [x] `core/tauri-rust/src/daemon.rs`'s `KNOWN_SECRET_KEYS` gains `"managed_token"` -- the one new
    keychain entry SPEC-207 §2.6 names. Mechanism unchanged; `secrets.rs`'s own allowlist test
    (`validate_known_key_accepts_every_real_provider_key`) iterates `KNOWN_SECRET_KEYS` itself, so
    it covers the new key with no separate edit.
*   [x] `_build_provider_from_record` raises a clear `LLMProviderError` naming the env var when
    `managed` is selected with no gateway configured -- never silently constructs a client pointed
    at `None`.
*   [x] A real timeout (`_MANAGED_TIMEOUT_SECONDS`) applied post-construction via
    `client._client.timeout` (confirmed mutable on the real `openai.AsyncOpenAI` instance,
    live-checked before relying on it) -- `OpenAICompatProvider.__init__` has no timeout parameter
    of its own to pass one through (confirmed by reading the installed source), and adding one would
    be an AgentFlow change SPEC-207 §1 rules out.

### Phase 2: structured error mapping
*   [x] `_map_managed_error(exc)` -- translates a real `openai` SDK exception into one of the six
    codes, verified directly against the installed SDK's own `_make_status_error` (401/403/404/409/
    422 -> named classes, 429 -> `RateLimitError`, >=500 -> `InternalServerError`, everything else
    -> a bare `APIStatusError` with `.status_code` still set) rather than assumed. `402` -- not one
    of OpenAI's own defined codes -- falls through to the generic `APIStatusError` branch, confirmed
    real by constructing one directly in the test suite.
*   [x] `ManagedProviderError(LLMProviderError)` carries `.code` and `.extra` (`reset_at` for
    `managed_quota_exhausted`, `retry_after` for `managed_rate_limited`) -- a real subclass, not a
    generic exception with attributes bolted on ad hoc.
*   [x] `_ManagedProviderWrapper` wraps whatever real client `_build_provider_from_record` built for
    `managed`, intercepting `.chat(...)` -- SPEC-207 §2.2.1's own "belongs in a shared post-call
    helper, not in chat()" requirement, satisfied by wrapping at the client level so it's transparent
    to *every* caller of `.chat()`: `llm_providers.chat()`'s own code, and `AgentExecutor.run()`
    calling the provider client directly from inside `chat_agents._dispatch`/`component_pipeline
    ._build_agent_executor`. **Verified directly, not assumed:** `AgentExecutor.run()` has no
    try/except around its own `self._llm.chat(...)` call at all (read the installed source), so a
    raised `ManagedProviderError` -- `.code`/`.extra` intact -- propagates completely unwrapped
    through all three call sites to `daemon._run_job`'s generic catch.
*   [x] Retry policy (SPEC-207 §2.3): `managed_upstream_unavailable` (503) retries with linear
    backoff up to `_MANAGED_MAX_RETRIES`; `managed_rate_limited` (429) retries honoring the
    gateway's own `Retry-After` header value; `managed_auth_invalid` (401) and
    `managed_quota_exhausted` (402) are never retried -- the outcome cannot change before the
    account is fixed or the period resets.

### Phase 3: the job-failure payload
*   [x] `daemon._run_job`'s except branch: `getattr(e, "code", None)` (duck-typed, matching this
    function's own existing "never needs to know about any one bridge module's exception classes"
    design, stated in its own docstring) adds `code` plus any `.extra` fields to the `job.failed`
    payload when present. Strictly additive -- an exception with no `.code` (every pre-existing
    failure mode) produces byte-identical output to before this phase.
*   [x] `managed_unreachable` reaching `SPEC-101`'s crash shield: **confirmed already impossible by
    the existing architecture**, not new code. `_run_job` already runs on its own worker thread and
    already catches every `Exception` generically; a `managed_unreachable` `ManagedProviderError` is
    just one more exception through that same, pre-existing path. The "crash shield" is the
    heartbeat-gap mechanism (`SPEC-107` §3) Rust judges independently -- it only fires if the
    daemon's own read/heartbeat loop stalls, which this phase's retry loop (bounded, `asyncio.sleep`,
    never blocking) cannot do.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: no hardcoded production gateway URL is set anywhere in this phase.**
    *   *Reasoning:* the real GittieLabs gateway does not exist yet -- `SPEC-404` §1 is explicit that
        building it is external, out-of-repo work. Inventing a plausible-looking production domain
        now (even a clearly-fictional one) risks being mistaken for a real endpoint later, or
        silently accepted as "the real value" by a future reader who doesn't check.
    *   *Impact:* `_MANAGED_GATEWAY_ENV_VAR` (`HAS_MANAGED_GATEWAY_URL`) is the only source of the
        base URL; selecting `managed` with it unset raises a clear, specific `LLMProviderError`
        rather than silently constructing a client against `None`. The real production value is
        SPEC-207's own next real finding, once GittieLabs' gateway is actually deployed --
        recorded here so that step isn't forgotten as "already done."
*   **Deviation 2: the managed preset's `models` map is empty, with no default alias for either
    role -- SPEC-404 §2.3's own illustrative `has-standard`/`has-deep` names were deliberately NOT
    used as defaults.**
    *   *Reasoning:* SPEC-207 §2.1 states plainly that "the daemon must not validate a Managed model
        name" -- seeding a default alias the daemon itself invented would be exactly that kind of
        validation-by-assumption, and if the real gateway's actual alias names differ even slightly,
        a hardcoded wrong default would fail in a more confusing way than an explicit "no model
        configured" error.
    *   *Impact:* selecting `managed` via role binding with no explicit model override raises
        `LLMProviderError` today (SPEC-208 §2.3.2's pre-existing "no model for role" rule, unchanged
        by this phase) -- correct and honest, but means `managed` is only reachable via an explicit
        per-call model override until either a real default alias is confirmed against the real
        gateway, or `SPEC-320`'s UI lets a person type one in directly.
*   **Deviation 3: `_MANAGED_TIMEOUT_SECONDS` (900s) is a reasoned default, not a live-measured one.**
    *   *Reasoning:* SPEC-207 §2.4 asks for a value "with the measurement behind it," which requires
        a real gateway to measure against -- none exists. `openai-python`'s own default
        (600s read/write, confirmed by inspecting a real constructed client) already comfortably
        covers every real LLM call observed in this repo (SPEC-205's own ~20-23s multi-category
        datasheet extraction is the longest real one on record); 900s adds real headroom for "the
        gateway adds a hop and may itself be retrying upstream" without being an arbitrary multiple.
    *   *Impact:* revisit once a real gateway's own latency profile exists to measure against,
        per SPEC-207 §2.4's own instruction -- flagged here rather than left as an unstated
        assumption.
