# CTX-206.7: Implementation Context: Context Retrieval Index

> **Spec Reference:** Links to [SPEC-206](../specs/SPEC-206-agent-context-store.md)

The second piece of the user's confirmed build order (chat.send → **retrieval** → promotion). Builds
`PRODUCT-PLAN.md` §4's `.index/` and finally closes the `context.search` gap `CTX-206.5` explicitly
left open ("`AgentExecutor` will simply never be able to dispatch it until CTX-206.6's successor
lands" -- that successor is this context, one slice later than originally guessed, since `CTX-206.6`
itself became `chat.send`).

## 1. Feature Definition & Execution Plan

### Phase 1: `context_index.py` -- schema, chunk extraction, rebuild
*   [x] New module (SPEC-206 §3's own explicit instruction -- `library_store.py` is already large and
    growing; the index belongs in its own file). `<storage_root>/.index/context.sqlite3`: a `chunks`
    table, a standalone FTS5 virtual table (`chunk_id UNINDEXED, body` -- not `content=`-linked, so a
    full rebuild needs no incremental-sync trigger machinery), and a `meta` table for
    `last_indexed`/`schema_version`.
*   [x] `fts5_available()`: SPEC-206 §3's own explicit instruction -- probes with a real
    `CREATE VIRTUAL TABLE ... USING fts5(...)` against an in-memory database, never sniffs
    `sqlite3.sqlite_version`. Confirmed real (`True`) on this dev machine before writing any test
    against it.
*   [x] Chunk extractors, one real, honest `SourceRef` per chunk: `guidance_item` for a real per-item
    quote (resolvable -- the quote really is one of `categories[category]`'s own items);
    `connection_guidance` for a real per-pin entry; `part_field` for identity fields
    (`manufacturer`/`package`), pin names (cited as `field: "pins"`, the real list they live in), a
    category's own generated summary text (cited as `field: "design_guidance"`, since a summary is
    real content but *not* a literal quoted excerpt -- citing it as `guidance_item` would produce a
    `SourceRef` that could never resolve), and `connection_guidance.general_notes` the same way;
    `project_intent` for a real project intent; `note` for Part/Project notes -- inert today (no
    `notes` field exists until `SPEC-206` §2.7 ships), wired now the same "safe until it activates"
    way `chat_agents.py`'s own deferred resolvers already are.
*   [x] `needs_rebuild()`/`rebuild_index()`/`ensure_fresh_index()`: `PRODUCT-PLAN.md` §4's own
    staleness contract -- newest real mtime under `library/`/`projects/` compared against
    `meta.last_indexed`; a missing index file, or one whose `meta` table is missing/partial, both
    trigger a rebuild -- "delete the file" is a real, already-supported recovery action with zero
    special-casing.
*   [x] `Retriever` protocol + `Chunk` dataclass; `Fts5Retriever` (real `bm25()`-ranked `MATCH`
    query, every token individually phrase-quoted so arbitrary user text can never raise a real
    `sqlite3.OperationalError` from malformed FTS5 syntax) and `LikeScanRetriever` (the real,
    correct-but-unranked substring fallback).
*   [x] **Verified against the real thing, not mocked**: a live smoke test against this machine's own
    real `sqlite3` (FTS5 confirmed available) proved real chunk extraction → real indexing → real
    search → a real result whose `source_ref` passes `chat_agents.resolve_source_ref` unchanged,
    before a single test was written.

### Phase 2: `daemon.py`/`tool_registry.py` wiring
*   [x] `context_search(query, part_id=None, project_name=None, limit=8)`: a friendlier, LLM-callable
    surface over `context_index.search`'s own lower-level `scopes` list -- a tool call names one part
    or one project, never an arbitrary scope list. Synchronous (real, cheap local FTS5/SQLite lookup,
    matching `kicad.search_footprints`'s own "real but cheap" precedent) -- unlike `chat.send`.
*   [x] `context_rebuild_index()`: the manual trigger `PRODUCT-PLAN.md` §4 requires. A real,
    potentially non-trivial full scan, so registered in `ASYNC_ROUTES` (unlike `context.search`,
    which only re-scans when its own automatic staleness check finds one stale).
*   [x] `daemon.get_capabilities` gains a real, probed `fts5_available` flag (SPEC-206 §3).
*   [x] `tool_registry.TOOL_DEFINITIONS["context.search"]`: the real entry every `chat_*.prompt.md`
    file already declared as a tool but had nothing to dispatch to. `test_tool_registry.py`'s own
    `test_001` no longer needs to exempt `context.search` -- the gap it was named against is closed.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (real, honest gap, named not fixed): `last_results`/`export_history` entries are
    not indexed at all.**
    *   *Reasoning:* SPEC-206 §2.3's `SourceRef` union has no kind covering a generated check result
        or an export record. Indexing that content anyway would either produce a chunk with no
        honest citable form, or force a `SourceRef` kind onto it that could never resolve -- the same
        category of problem `guidance_item`-vs-`part_field` for summaries already avoids by design.
    *   *Impact:* named here rather than silently worked around; would need a new `SourceRef` kind
        (a real spec change, not something this context's own scope covers) to index honestly.
*   **Deviation 2 (real, honest gap, named not fixed): the staleness check (`needs_rebuild`) only
    scans `library/`/`projects/` under the storage root -- a *linked* project's real content, which
    lives under its own external directory, isn't scanned.**
    *   *Reasoning:* matches SPEC-206 §2.6's own literal staleness heuristic text exactly; a linked
        project's real content living outside the storage root is a genuinely separate, larger
        problem (the same one `CTX-312.1` already solved for save/load routing, not for a derived
        cache's own staleness detection).
    *   *Impact:* `context.rebuild_index`'s own manual trigger, plus the fact that a full rebuild is
        always cheap, are the real backstop -- not a claim this heuristic is perfectly precise for
        every real storage layout. Worth a future context if a real, observed staleness miss for a
        linked project ever surfaces.
*   **Deviation 3 (non-deviation, confirmed as designed): `note` chunk extraction is wired now but
    yields nothing today.**
    *   *Reasoning:* Parts/Projects have no real `notes` field until `SPEC-206` §2.7 ships. Same
        "wire it now, safe until it activates" pattern `chat_agents.py`'s own `_resolve_deferred`
        already established for the `note`/`check_finding` `SourceRef` kinds.
    *   *Impact:* none today; `_extract_all_chunks` will start yielding real `note` chunks the moment
        §2.7 starts writing them, with zero further change needed here.
