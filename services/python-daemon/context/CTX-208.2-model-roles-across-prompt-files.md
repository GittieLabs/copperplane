# CTX-208.2: Implementation Context: Model Roles Across the Twelve Prompt Files

> **Spec Reference:** Links to [SPEC-208](../specs/SPEC-208-provider-records-and-model-roles.md)

Phase 2 of 3 (SPEC-208 §4's own module map). Closes coupling #2 from SPEC-208 §2.1: all twelve
`.prompt.md` files now declare a `model_role` (`reasoning` or `fast`) instead of a hardcoded vendor
`provider`/`model`, a new sidecar (`agent_roles.py`) reads it (since `AgentConfig`'s `extra="ignore"`
silently drops unknown frontmatter keys), and `llm_providers.resolve()` (from CTX-208.1) gained a
`model_role` parameter plus a real `migrate_legacy_config()` so a pre-SPEC-208 `config.json`
(`llm_provider`/`llm_model`, no `provider_roles`) still routes correctly. All nine daemon.py call
sites, and every function between them and `resolve()` in `chat_agents.py`/`component_pipeline.py`,
now thread the daemon's own config dict through.

## 1. Feature Definition & Execution Plan

### Phase 1: the sidecar (`agent_roles.py`)
*   [x] `load_agent_roles(agents_dir) -> {agent_name: {model_role, requires}}` -- re-reads every
    `*.prompt.md` with AgentFlow's own `parse_prompt_file` (confirmed importable at
    `agentflow.config.parser.parse_prompt_file`), not a second hand-rolled parser.
*   [x] Validates its own two keys itself: a missing/unrecognized `model_role`, or an unrecognized
    `requires` entry, raises `AgentRoleError` at load time -- the exact gotcha SPEC-208 §2.3.3 names
    (`extra="ignore"` would otherwise silently discard a typo the same way it discards a valid
    unknown key). `requires` parsing exists now (returns `[]` today, since no file declares one yet)
    so CTX-208.3 doesn't need to touch this module again -- it only needs to start acting on it.

### Phase 2: the twelve prompt files
*   [x] `provider: anthropic` / `model: claude-sonnet-4-6|claude-sonnet-5` replaced with one
    `model_role:` line in every file, per SPEC-208 §2.3.1's split:
    **reasoning** -- `board_advisor`, `component_extraction`, `component_search`,
    `connection_guidance`, `datasheet_guidance_extraction`, `footprint_query_suggestion`.
    **fast** -- `chat_components`, `chat_enclosure`, `chat_overview`, `chat_pcb`, `chat_schematic`,
    `datasheet_guidance_synthesis`. Verified for real: `ConfigLoader` still loads all twelve cleanly
    (pydantic's own defaults fill the now-absent `provider`/`model` fields, unused once role
    resolution takes over), and `agent_roles.load_agent_roles` against the real, edited directory
    returns the exact 6/6 split.

### Phase 3: `resolve()` gains `model_role`, and a real `migrate_legacy_config()`
*   [x] `migrate_legacy_config(config)` -- a `config` with `llm_provider` set and no
    `provider_roles` is read as binding both roles to that provider id, using `llm_model` for the
    `reasoning` role specifically if set (the `fast` role keeps that provider's own untouched
    default). No `llm_provider` either binds both roles to `_DEFAULT_PROVIDER`. An existing
    `provider_roles` is returned unchanged -- real configuration always wins. Never mutates its
    input.
*   [x] `resolve()`'s resolution order is now the real three-step SPEC-208 §2.3.2 describes:
    (1) explicit per-call `provider`/`model` override, unaffected by role; (2) `model_role` resolved
    through `config`'s migrated `provider_roles` map to a record, then that record's own model for
    the role -- an unknown bound id, or a record missing a model for the role, is a real
    `LLMProviderError`, never a silent fall-through; (3) the caller's own `default_provider`/
    `default_model` for a caller with no role concept at all.

### Phase 4: threading `config`/`model_role` through every real call site
*   [x] `chat_agents._dispatch` looks up the routed agent's own role via `agent_roles.load_agent_roles`
    and passes it to `resolve()` alongside a new `config` parameter; `send()`/`review()` both gained
    and forward `config`.
*   [x] `component_pipeline._build_agent_executor` does the same, with its new parameter named
    `app_config` rather than `config` specifically to avoid shadowing this function's own
    long-standing local `config` (the agent's `AgentConfig`). `search_components`,
    `generate_connection_guidance`, `suggest_footprint_query`, `explain_violations`,
    `generate_component` (including its inner workflow `runner_factory`) all gained and forward
    `app_config`.
*   [x] `daemon.py`'s nine call sites into the two modules above each gained the matching keyword:
    `config=CONFIG` for the two `chat_agents` calls (`chat_send`, `chat_review`), `app_config=CONFIG`
    for the seven `component_pipeline` calls (`kicad_generate_component`, `component_search`,
    `kicad_generate_connection_guidance`, `kicad_suggest_footprint_query`, and both
    `kicad_check_board`/`kicad_check_schematic` calls into `explain_violations`).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `component_pipeline.py`'s new parameter is named `app_config`, not `config`,
    diverging from `chat_agents.py`'s `config` naming for the identical concept.**
    *   *Reasoning:* `_build_agent_executor` (and every function that calls it) already has a
        long-standing local variable named `config` -- the agent's own `AgentConfig` from
        `loader.get_agent()`. Naming the new parameter `config` too would either shadow that local
        or force renaming it everywhere in a file that didn't ask for that churn.
    *   *Impact:* purely a naming asymmetry between the two modules, not a behavioral one --
        `daemon.py`'s two call sites into `chat_agents` use `config=CONFIG`, its seven call sites
        into `component_pipeline` use `app_config=CONFIG`. Documented in both modules' own
        docstrings so a future reader isn't surprised by the mismatch.
*   **Deviation 2: `requires` is parsed and validated by `agent_roles.py` now, a phase earlier than
    the module map's own split suggests.**
    *   *Reasoning:* SPEC-208 §2.3.3 itself describes the sidecar as keeping
        `{agent_name: {model_role, requires}}` together -- building the reader twice (once for
        `model_role` now, again for `requires` in CTX-208.3) would be pure rework for two keys
        parsed by the same frontmatter re-read.
    *   *Impact:* no behavioral effect yet -- every prompt file's `requires` is `[]`, and nothing
        currently reads the `requires` value back out of `load_agent_roles`'s return. CTX-208.3 adds
        real `requires:` entries to the prompt files and the actual preflight check that consumes
        them; it does not need to touch `agent_roles.py`'s own parsing/validation logic.
*   **Deviation 3: no live LLM call was made to prove role-based routing end-to-end, unlike CTX-208.1's
    provider-construction tests.**
    *   *Reasoning:* role-based resolution changes *which* provider/model `resolve()` selects, not
        the provider-construction/call mechanics themselves -- CTX-208.1 already proved those live.
        Re-running a live call here would re-verify the same SDK call path CTX-208.1 covered, not
        anything new to this phase.
    *   *Impact:* every `resolve()`/`migrate_legacy_config` test in this phase is a real function
        call with real assertions on the resolved provider/model/records, but stops short of an
        actual network request. Named explicitly per this repo's own honesty norm, not silently
        assumed equivalent to CTX-208.1's live coverage.
