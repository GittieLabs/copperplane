# CTX-206.6: Implementation Context: chat.send Router/Agent Dispatch

> **Spec Reference:** Links to [SPEC-206](../specs/SPEC-206-agent-context-store.md)

`CTX-206.5`'s own text named `chat.send`/router wiring as "the next context" -- this is that context.
Resumed after the user's own explicit instruction to finish SPEC-206's backend before touching
SPEC-318's frontend, with an important correction made mid-scoping: a background research report had
marked §2.5 "Implemented," but `CTX-206.5`'s own text only ever built tool *registration* -- the real
router/dispatch mechanism (`router.prompt.md`, `RouterEngine`, `AgentExecutor` construction,
`chat.send` itself) did not exist until this context. Confirmed the dependency-correct order with the
user directly: chat.send → retrieval (§2.6) → promotion (§2.7).

## 1. Feature Definition & Execution Plan

### Phase 1: `router.prompt.md` -- five real areas, hard-error on a sixth
*   [x] `agentflow/router.prompt.md`: `routingRules` matching `area == '<area>'` for all five real
    `SPEC-318` §2.3 areas, `llmFallback: false` (SPEC-206 §2.5's own explicit requirement -- a sixth
    area must be a hard error, never an LLM guess). `chat_agents.send()`'s own `_KNOWN_AREAS` check
    runs *before* the router is even consulted -- the real, primary enforcement; `llmFallback: false`
    is a second, defensive line, since a well-formed caller never reaches the router with a bad area
    at all.

### Phase 2: `chat_agents.py` -- context assembly, dispatch, citation extraction
*   [x] `_assemble_context(area, scope, scope_id, project_name)`: real, per-area context built from
    real Part/Project records (`SPEC-318` §2.3's own "grounded in" list per agent), prepended fresh to
    the user's message on every call rather than baked into history -- a stored turn carries only its
    own raw text.
*   [x] **Real, honest gap found, not fixed here:** `chat_schematic`/`chat_pcb`'s own prompts describe
    "the real ERC/DRC findings already produced by the user's last check" as known context, and
    `chat_enclosure`'s describes "the board's real outline and mounting holes" the same way -- neither
    is actually persisted anywhere today. `SchematicAdvisor.tsx`/`BoardAdvisor.tsx` hold check results
    in local React state only; board outline/mounting holes are only ever computed live via
    `kicad_bridge`/a real PCB file import, never saved to the Project record. `_check_status_note`
    always honestly reports "not checked this session" for schematic/pcb -- exactly the fallback both
    prompts already anticipated in their own text ("if another area shows nothing, say plainly that
    it hasn't been checked this session, never that it passed"). Named as a real, later prerequisite
    (the same category CTX-206.1 already fixed for connection guidance), not silently worked around.
*   [x] Citation format -- SPEC-206 §2.3's "both, layered" design, confirmed with the user earlier
    this session: `_mechanical_source_refs` derives real `datasheet_page` refs from real
    `datasheet.read_pages` `TOOL_RESULT` events (via a minimal `EventBus` subscriber,
    `_ToolResultCollector` -- `AgentExecutor` never surfaces tool calls on its own return value,
    confirmed directly against the installed source); `_extract_self_reported` parses a structured
    `<<<CITATIONS>>>{"sources": [...], "general_practice": bool}<<<END_CITATIONS>>>` block the model
    is now instructed (all five `chat_*.prompt.md` files) to always emit and which is always stripped
    before the user sees it; `_enrich_source_ref` fills in the one field the model cannot compute
    itself (`guidance_item`'s real `content_hash`). Both halves merge into one list validated through
    the already-built `validate_source_refs` (`CTX-206.4`).
*   [x] `send(scope, scope_id, area, message, project_name=None, ...)`: loads prior history *before*
    appending the new user turn (a real ordering bug caught before shipping -- loading history after
    would have duplicated the current turn in what's sent to the model), dispatches, appends the
    assistant turn with its real `sources`/`sources_dropped`/`general_practice`/`tool_calls`/
    `provenance`, returns it.
*   [x] `library_store.append_thread_turn`: a real, single-line append (mirroring
    `append_conversation_turn`'s own efficient shape), not `_write_thread_turns`'s read-all-
    rewrite-all -- `chat.send` calls this twice per turn.

### Phase 3: `daemon.py` wiring
*   [x] Guarded `import chat_agents`; `chat_send(scope, scope_id, area, message, project_name=None)`
    thin wrapper threading `CONFIG`'s provider/model/secrets through, matching every other real LLM
    route's own precedent. Registered in `_build_routes()` (gated on `chat_agents`, `library_store`,
    `tool_registry` all being real) and in `ASYNC_ROUTES`.
*   [x] **Deliberately does not thread a `cancel_event`**, despite SPEC-206 §2.5's own text naming it
    -- verified directly against every other single-shot agent-call route already in `daemon.py`
    (`kicad.generate_connection_guidance`, `kicad.suggest_footprint_query`, `kicad.generate_component`):
    none of them do either. Only the genuinely multi-call routes (`datasheet.generate_guidance`,
    `freecad.generate_enclosure`) support cancellation, since those have a real per-item checkpoint a
    single agent turn's own internal tool-loop does not.

### Phase 4 (raised mid-session, resolved, filed as separate follow-up): AgentFlow's own NodeOutput
*   [x] Building `_mechanical_source_refs` required an `EventBus` subscriber to see real tool calls at
    all -- `AgentExecutor.run()`'s own `NodeOutput` never surfaces them. The user asked directly
    whether this should be fixed upstream in AgentFlow (which they own) rather than worked around
    downstream. Confirmed with the user: ship this context now using the `EventBus` approach (a real,
    supported AgentFlow mechanism, not a hack), and file the `NodeOutput.metadata["tool_calls"]`
    enhancement as separate, later AgentFlow work rather than blocking this slice on a full upstream
    release cycle. Filed as a background task (`task_9787f1d2`).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (a real correction to the prior context's own claim): §2.5 was not actually
    "Implemented" going into this context, despite an earlier report saying so.**
    *   *Reasoning:* `CTX-206.5`'s own text was unambiguous ("the next context, CTX-206.6") but a
        background research summary mislabeled the section anyway. Re-read `CTX-206.5` directly
        before proceeding rather than trusting the summary, and surfaced the discrepancy to the user
        before starting -- who then confirmed the dependency-correct build order.
    *   *Impact:* none on the real work -- this context's own scope was always "build chat.send,"
        just confirmed explicitly rather than assumed complete.
*   **Deviation 2 (a real, honest gap, named not fixed): ERC/DRC check results and board outline/
    mounting-hole data are not actually persisted anywhere `chat_schematic`/`chat_pcb`/`chat_enclosure`
    can read them, despite their own prompts describing that data as already-known context.**
    *   *Reasoning:* discovered by tracing the real data path (`SchematicAdvisor.tsx`/
        `BoardAdvisor.tsx` hold check results in local React state only; board outline/mounting holes
        are only ever computed live) rather than assuming the prompts' own claims were already true.
    *   *Impact:* both areas' context assembly honestly reports "not checked this session"/omits the
        unavailable data, matching language the prompts themselves already anticipated. A real,
        separate future prerequisite -- persisting ERC/DRC results (and, if ever needed, board
        outline data) onto the Project record, the same category of fix `CTX-206.1` already made for
        connection guidance -- is named here for whichever future context builds it, not silently
        deferred.
*   **Deviation 3 (raised by the user mid-session, resolved directly): should the tool-call
    visibility gap in `AgentExecutor.run()` be fixed upstream in AgentFlow instead of worked around
    here?**
    *   *Reasoning:* the user owns AgentFlow and has a standing norm (fix real gaps upstream, not
        downstream) recorded from prior sessions. Assessed the gap honestly: the `EventBus` mechanism
        used here is a real, supported public API, not a hack, so shipping this context now doesn't
        compromise correctness -- but a genuine, low-risk, additive improvement exists
        (`NodeOutput.metadata["tool_calls"]`, populated from data `AgentExecutor.run()` already
        computes internally).
    *   *Impact:* filed as a separate background task (AgentFlow PR, not merged/released without the
        user's explicit go-ahead) rather than blocking this SPEC-206 slice on a full upstream release
        cycle. `chat_agents.py`'s own `_ToolResultCollector`/`EventBus` code can be simplified once
        that lands -- named here so a future session knows why it still exists.
