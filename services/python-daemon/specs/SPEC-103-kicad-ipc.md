# SPEC-103: KiCad IPC Bridge

## 1. Executive Summary & Goals
*   **High-Level Goal:** Connect the Python JSON-RPC daemon directly to a running instance of KiCad to dynamically inject components, route nets, and read schematic data.
*   **Business / Technical Value:** Bypasses legacy SWIG bindings. By using the official Protocol Buffers (protobuf) API introduced in KiCad 9+, we can manipulate the CAD canvas in real-time without freezing the user's GUI.
*   **Non-Goals:** We are not parsing raw `.kicad_sch` text files directly unless absolutely necessary; all interaction should occur via the live API server.

## 2. System Architecture & Design Choices
*   **Protocol:** Sockets via PyNNG / Protobuf (using the `kicad-python` package).
*   **Connection Lifecycle:** 
    1. The Python daemon receives a task from Tauri.
    2. It attempts to connect to `127.0.0.1` on the default KiCad IPC port.
    3. If connected, it executes the payload (e.g., placing a footprint at coordinate X/Y).
    4. The connection is held open for the duration of the daemon's life to reduce handshake latency on subsequent calls.
*   **Supplier API Handoff:** This module takes standardized component data (pinouts/dimensions) generated by the AI/Supplier modules and translates it into KiCad's specific protobuf messages.

## 3. Known Constraints & Risks
*   **Version Dependency:** This fails entirely on KiCad 8 or older. The daemon must gracefully catch connection refusals and return a clean JSON-RPC error instructing the user to upgrade.
*   **State Desync:** If the user manually closes KiCad while the Python daemon is routing, the socket will break. All PyNNG calls must be wrapped in `try/except` blocks to handle broken pipes gracefully.
