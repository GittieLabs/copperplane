# CTX-209.1: the three vendor SDKs AgentFlow's extras pull in, pinned
# explicitly rather than left to float. They were the only unpinned direct
# dependencies in this file, and the float shipped a real bug: v0.3.0's
# release CI resolved anthropic 1.2.0, which had REMOVED `temperature` from
# messages.create, so every Anthropic call in that build raised TypeError
# client-side before reaching the network. It went unseen because a local
# interpreter still carried anthropic 0.121.0, where the parameter works --
# same repo, same tests, opposite results, decided by which SDK pip happened
# to resolve. Fixed upstream in agentflow 0.11.1; pinned here so a release
# cannot acquire an incompatible SDK again without someone choosing to.
#
# CTX-402.6 already pinned `cryptography` for exactly this reason, naming
# these same three SDKs as the source of the float. This is that fix one
# level up.
#
# Pinning bounds PARAMETERS, not models. A model is a runtime string passed
# straight through, so any pinned SDK accepts any model a user types. But
# none of these three accept `**kwargs` -- checked directly -- so an unknown
# argument is rejected client-side, which means SPEC-209's `params`
# passthrough can only send what the pinned SDK's own signature allows.
# Reaching a newly-added vendor parameter therefore needs a deliberate bump
# here, verified by a real release, which is the intended trade.
anthropic==1.2.0

google-genai==2.21.0

# Pinned explicitly (CTX-402.6): a transitive dependency (of anthropic/
# openai/google SDKs pulled in above) that would otherwise float to
# whatever's newest. Real, direct-to-PyPI checking found cryptography
# dropped macOS x86_64 wheels entirely as of 49.0.0 (only macosx_11_0_arm64
# ships from there on) -- 48.0.1 is the newest release that still ships a
# real macosx_10_9_universal2 wheel (both Apple Silicon and Intel in one
# file) alongside win_amd64/manylinux wheels for every other platform this
# repo's release pipeline builds for. Confirmed via a real, failed CI run
# (v0.1.3's first x86_64 macOS leg): PyInstaller's own arch check caught
# the resulting build-from-source .so as arm64-only when a x86_64 freeze
# needed it, since Rust's build backend doesn't respect the parent
# process's `arch -x86_64` the way a prebuilt wheel install does.
# Held on the 48.0.x line by the wheel-platform constraint above, NOT by
# inattention. Dependabot proposes 49.0.0/50.0.0 for three real advisories;
# taking either drops the Intel macOS wheel and breaks that release leg, so
# those alerts stay open deliberately. 48.0.1 is reachable and is taken
# here: it carries the "Vulnerable OpenSSL included in cryptography wheels"
# fix and still ships macosx_10_9_universal2 -- confirmed against PyPI's own
# release metadata, not inferred from a changelog.
cryptography==48.0.1
