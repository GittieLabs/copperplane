# CTX-326.2: Interior Height Recommendation & Height Entry

> **Spec Reference:** Links to [SPEC-326](../specs/SPEC-326-component-volume-placeholders.md)

`CTX-326.1` produced envelopes. This turns them into the answer a user actually wants — *how tall
does the box need to be, and which part decided that* — and asks for the one height the app cannot
measure.

## The demonstration this exists for

On the maintainer's own `Hello_World_Blinky`, KiCad closed:

| | minimum interior height | set by |
| :--- | :--- | :--- |
| **With** `BT1`'s supplied height | **20.0 mm** | `BT1` (stated) |
| **Without** it | 15.5 mm | `R1` (measured), `BT1` unknown |

Sizing from measured parts alone yields a 15.5mm box **the battery does not fit in**. The one
component KiCad ships no model for is the one that decides the enclosure — `SPEC-326` §2.2
predicted this, and the real board confirms it.

## 1. Feature Definition & Execution Plan

### Phase 1: Compose envelopes into an answer

*   [x] `kicad.component_envelopes` joins the schematic read to `CTX-326.1`'s envelopes and reports
    `min_interior_height_mm` plus the component setting it.
*   [x] `ASYNC_ROUTES`-registered — `kicad-cli` plus a `freecadcmd` read per modelled component.
*   [x] **A recommendation, never an override.** `SPEC-311`'s enclosure height stays user-entered.
    Silently resizing a box from a partly-stated set of volumes is exactly the confident-wrong
    answer this spec exists to avoid.

### Phase 2: Ask for the height that cannot be measured

*   [x] An inline height entry on any component whose footprint has no model — the only remaining
    source in `SPEC-326` §2.3's order.
*   [x] Keyed by **footprint** per §2.5 and remembered on the project, so ten identical resistors
    are one decision that survives a schematic renumber.
*   [x] Never offered for a component that already has a real model.

### Phase 3: Keep measured and stated distinguishable

*   [x] The banner names the source of the driving height — *measured from its 3D model* versus
    *height you supplied*.
*   [x] Counts reported as measured / stated / unknown.
*   [x] **An unknown height gets its own warning**: "the real minimum may be taller." A recommendation
    computed over an incomplete set must say so, or it is worse than no recommendation.

### Phase 4: Correct advice that had become wrong

*   [x] `EnclosurePanel` told users to *"fix their footprint's 3D model assignment"*. For 25 of
    KiCad's own 53 battery footprints **there is nothing to fix** — the model was never shipped. It
    now says so and points at the height entry.

### Not in this context

*   **Placeholder solids in the 3D view** (`SPEC-326` §2.4's visual distinction). The recommendation
    is a number, not geometry. Rendering a labelled volume in `EnclosureViewer` is `CTX-326.3`, and
    it is the remaining half of §2.4.
*   **Feeding the recommendation into `generate_enclosure` automatically.** Deliberate — see
    §4 Deviation 2.
*   **`package_dimensions` as a source**, still blocked on `SPEC-325` §2.5's library matching.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — there was no enclosure height calculation to add placeholders to.**
    *   The plan assumed `SPEC-311` derived an interior height from component heights, so
        `SPEC-326`'s job would be substituting placeholder volumes into it. Reading
        `EnclosurePanel` first showed otherwise: **the height is typed by the user**, and
        `kicad.get_component_heights` feeds only a "these have no model" disclosure.
    *   *Impact:* the shape of the work changed from *substitute into a calculation* to *make the
        calculation exist, as advice*. That turned out better — the app now states a number and its
        provenance rather than silently changing a box, which is what §2.4's honesty requirement
        wanted anyway.

*   **Deviation 2 — the recommendation deliberately does not drive the enclosure.**
    *   It would be a small change to feed `min_interior_height_mm` into `generate_enclosure`'s
        `height` parameter.
    *   *Reasoning:* that number is computed over a set that may be partly stated and partly
        unknown, and `SPEC-326` §3 names "a placeholder that is too small" as worse than none —
        it produces a confident "it fits" for a box that does not close. A user typing 20mm because
        the app told them their battery needs it is making a decision; a box that silently became
        20mm is one they cannot audit.

*   **Deviation 3 — existing UI advice had quietly become wrong.**
    *   `EnclosurePanel` instructed users to fix a footprint's 3D model assignment. The assignment
        is usually correct; the *file* is missing, for 25 of 53 footprints in KiCad's own battery
        library. Following that advice would waste a user's time on a problem they cannot solve.
    *   *Impact:* corrected, and worth recording as a pattern — advice written when a subsystem
        behaved one way survives unchanged after the understanding moves on, exactly as
        `CTX-406.2` found for `CONTRIBUTING.md`'s build tiers.
