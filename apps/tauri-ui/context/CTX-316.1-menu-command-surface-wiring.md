# CTX-316.1: Native Menu Command Surface -- Structure & Wiring

> **Spec Reference:** Links to [SPEC-316](../specs/SPEC-316-native-menu-command-surface.md)

## 1. Feature Definition & Execution Plan

**Real API surface verified directly against the vendored `tauri 2.11.5` source before planning**
(`~/.cargo/registry/src/index.crates.io-*/tauri-2.11.5/src/`): `AppHandle::set_menu(Menu<R>) ->
Result<Option<Menu<R>>>`, `Menu::get(&id) -> Option<MenuItemKind<R>>`, `Submenu::set_enabled(bool)`,
and `PredefinedMenuItem::{hide, hide_others, show_all, services}` (`menu/predefined.rs`) all
confirmed real and present at this version -- not assumed from general Tauri knowledge.

**Real, honest scope split, decided while planning, not discovered mid-build:** `SPEC-316`'s own
Known Constraints named two real technical gaps -- the Library menu's custom-library items need
live daemon data the menu doesn't have at build time, and per-action enable/disable state needs a
frontend->Rust sync channel that doesn't exist yet. Both are genuinely separable from "the menu
exists with the right structure and every included action works." This context (`.1`) ships the
full static structure: the native app-name menu, the grouped `Design` menu with real per-area
actions, and a `Library` menu with `Default Library` + `Manage Libraries...` (both already
real navigational targets -- no live per-library data needed for either). Dynamic custom-library
listing and Design-menu enable/disable sync are `CTX-316.2`, not invented here.

**Real, honest scope limit on "Design" actions, discovered while reading the actual components
(not assumed):** `SchematicAdvisor.tsx`/`BoardAdvisor.tsx`/`EnclosurePanel.tsx`'s own handlers
split into two real kinds -- parameterless ones that act on already-selected/current state
(`handleOpenKicad`, `handlePickManually`, `handlePickPcbFile`, `handleGenerate`), and ones that
require a specific candidate as an argument (`handleCheck`, `handleCheckBoard`, `handleSelectBoard`
-- you check *a* candidate from a list, there's no single "the" candidate to act on). Only the
parameterless ones are real menu actions in this pass:
*   Schematic: Open in KiCad, Pick Schematic Manually...
*   PCB: Open in KiCad (`BoardAdvisor` has no manual-pick equivalent today -- a real, current
    limitation of that component, not an oversight here)
*   Enclosure: Open in KiCad, Pick PCB File..., Generate

**Real mounting fact confirmed by reading `App.tsx` directly:** `SchematicAdvisor`/`BoardAdvisor`/
`EnclosurePanel` already stay mounted at all times once a project is open (rendered in
`className={view.area === X ? undefined : 'hidden'}` wrapper divs, per the component's own existing
comment) -- a Design menu action does not need to first switch `view.area` for the target
component's handler to be callable; it works whether or not that area's tab is currently visible.
This context still switches `view.area` to match, purely so the user can see the result of an
action they just triggered from the menu (e.g. Enclosure's `handleGenerate` populates a 3D preview
they'd otherwise not be looking at).

### Phase 1: Rust -- restructure `menu.rs`
*   [x] New leftmost app-name `Submenu` (macOS replaces its displayed title with the real bundle
    name regardless of the string passed, confirmed OS behavior): `PredefinedMenuItem::about`,
    separator, new `MenuItemBuilder::with_id("app_settings", "Settings...").accelerator("CmdOrCtrl+,")`,
    separator, `PredefinedMenuItem::services`, separator, `PredefinedMenuItem::{hide, hide_others,
    show_all}`, separator, `PredefinedMenuItem::quit` (moved out of `File`).
*   [x] `File` menu: Save Project, Open Project..., unchanged except Quit removed (now lives in the
    app-name menu above).
*   [x] `Help` menu: GitHub Repository only, unchanged except About removed (now lives in the
    app-name menu above).
*   [x] New `Design` top-level `Submenu` built with `SubmenuBuilder::with_id(app, "menu_design",
    "Design")` (the explicit id is required so a later context can look it up via `Menu::get` for
    enable/disable -- `CTX-316.2`, not used yet in this phase), containing three nested submenus:
    `Schematic` (Open in KiCad, Pick Schematic Manually...), `PCB` (Open in KiCad), `Enclosure`
    (Open in KiCad, Pick PCB File..., Generate). New item ids: `design_schematic_open_kicad`,
    `design_schematic_pick_manually`, `design_pcb_open_kicad`, `design_enclosure_open_kicad`,
    `design_enclosure_pick_pcb`, `design_enclosure_generate`.
*   [x] New `Library` top-level `Submenu` built with `SubmenuBuilder::with_id(app, "menu_library",
    "Library")` (same reason -- `CTX-316.2` appends real custom-library items to this by id later),
    containing `Default Library` (id `library_open_default`) and `Manage Libraries...` (id
    `library_manage`).
*   [x] `handle_menu_event` gains match arms for all 9 new ids, each emitting its own dedicated
    event -- reusing `CTX-312.3`'s exact idiom (one const, one `app.emit(EVENT, ())` call each), not
    a new payload-parsing pattern:
    `MENU_OPEN_SETTINGS_EVENT`, `MENU_OPEN_DEFAULT_LIBRARY_EVENT`, `MENU_MANAGE_LIBRARIES_EVENT`,
    `MENU_DESIGN_SCHEMATIC_OPEN_KICAD_EVENT`, `MENU_DESIGN_SCHEMATIC_PICK_MANUALLY_EVENT`,
    `MENU_DESIGN_PCB_OPEN_KICAD_EVENT`, `MENU_DESIGN_ENCLOSURE_OPEN_KICAD_EVENT`,
    `MENU_DESIGN_ENCLOSURE_PICK_PCB_EVENT`, `MENU_DESIGN_ENCLOSURE_GENERATE_EVENT`.
*   [x] Verified via `cargo build`/`cargo check` only -- matching `CTX-312.3`'s own established,
    honest precedent that this crate has no real unit-test surface for native menu construction.

### Phase 2: Frontend -- event constants + `App.tsx` listeners
*   [x] `lib/ipc.ts`: the 9 new `MENU_*` string constants above, each with a doc comment naming the
    matching Rust const it must stay in sync with (mirroring the existing
    `MENU_SAVE_PROJECT_EVENT` comment's own convention).
*   [x] `App.tsx`: extend the existing menu-listener `useEffect` (`CTX-312.3`) with `listen(...)`
    calls for all 9 new events, added to the same cleanup/`unlisten` pattern already there.
    *   Settings -> `setView({ kind: 'settings' })`.
    *   Open Default Library -> `setView({ kind: 'library', initialLibraryId: 'default' })`.
    *   Manage Libraries -> `setView({ kind: 'library' })`.
    *   Each Design event -> if `view?.kind === 'project'`, set `view.area` to the matching area
        (`'schematic'`/`'pcb'`/`'enclosure'`) and set a new `menuCommand` state value
        `{ area, command, nonce: menuCommand ? menuCommand.nonce + 1 : 0 }` (`nonce` so the same
        command fired twice in a row still re-triggers the consuming component's effect); if no
        project is open, the event is a real, silent no-op for this phase --
        `CTX-316.2`'s own enable/disable sync is what prevents the click from being possible in the
        first place, not this handler.
*   [x] `View` type gains `{ kind: 'library'; initialLibraryId?: string }` (widening the existing
    `{ kind: 'library' }` case, not a new variant) so the sidebar's own existing plain click keeps
    working unchanged (`initialLibraryId` simply undefined there).

### Phase 3: Frontend -- area components consume `menuCommand`
*   [x] `SchematicAdvisor`/`BoardAdvisor`/`EnclosurePanel` each gain an optional
    `menuCommand?: { area: Area; command: string; nonce: number } | null` prop, passed down from
    `App.tsx` unconditionally (all three are always mounted once a project is open, per the real
    mounting fact above -- no conditional-render gating needed).
*   [x] Each component gets one `useEffect(() => { ... }, [menuCommand?.nonce])` that checks
    `menuCommand?.area === '<this component's own area>'` and calls the matching already-existing
    handler (`handleOpenKicad`/`handlePickManually`/`handlePickPcbFile`/`handleGenerate`) by
    switching on `menuCommand.command`. No new business logic in any of the three components --
    every command dispatches to a handler that already exists and is already tested.

### Phase 4: Frontend -- `LibraryArea` deep-link
*   [x] `LibraryArea` gains an optional `initialLibraryId?: string` prop. A new effect: once
    `libraries` has loaded (existing `refreshLibraries()` effect) and `initialLibraryId` is set,
    find the matching `LibrarySummary` by `id` and call the existing `setView({ kind: 'detail',
    library })` -- reusing the component's own already-existing detail-view transition, not a new
    code path. If no match is found (a genuinely real edge case -- e.g. `Default` didn't load, or
    was renamed), fall back to the existing `{ kind: 'list' }` view rather than erroring.
*   [x] `App.tsx` passes `initialLibraryId={view?.kind === 'library' ? view.initialLibraryId :
    undefined}` to `<LibraryArea />`.

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Deviation 1: `Area`/`MenuCommand` types extracted to a new `lib/areas.ts`, not defined in
    `App.tsx` as originally planned.** The plan's own Phase 3 said `SchematicAdvisor`/`BoardAdvisor`/
    `EnclosurePanel` would import the `MenuCommand` type -- but `App.tsx`'s own `Area` type was
    private (never exported) before this context, and importing a type from `App.tsx` into a
    component `App.tsx` itself imports would be a circular import. Rather than export `Area`
    directly from `App.tsx` and accept that circularity (type-only imports are erased at build time
    so it would have *worked*, but it's an avoidable smell), pulled both types into their own tiny
    module. *Impact:* none on behavior; `App.tsx` now imports `Area`/`MenuCommand` from
    `./lib/areas` like everything else does, instead of defining them.
*   **Deviation 2: a `viewRef` was added, not in the original plan.** The plan's Phase 2 text said a
    Design event should check `view?.kind === 'project'` before dispatching -- written assuming
    `view` was simply readable inside the listener closure. In practice the menu-listener effect
    only re-subscribes on `currentProject` changes (an intentional, pre-existing `CTX-312.3`
    decision, not something this context should undo), so a closure over `view` directly would see
    a stale value after any area-tab switch that didn't also change `currentProject` -- silently
    misjudging whether a project was "open" on every Design click after the first tab switch. Fixed
    with a `viewRef` kept fresh by a separate one-line effect, read at dispatch time instead of
    closed over. *Impact:* real, would have been a genuine bug (TEST-006's own no-project no-op
    check singled it out during writing this test, before it ever shipped) -- caught by design, not
    by a failing test in CI.
*   **Deviation 3: a real, pre-existing test-isolation gap in `App.test.tsx` surfaced by TEST-006.**
    `openKicadMock` was never reset in the "Enclosure tab persists across area switches" describe
    block's own `beforeEach` (unlike every other mock declared there) -- harmless before this
    context because no existing test in that block asserted `openKicadMock` was *not* called.
    TEST-006 is the first to make that assertion, and it initially failed against a stale call count
    left over from an earlier test in the same block, not a real product bug. Fixed narrowly with an
    explicit `openKicadMock.mockClear()` inside TEST-006 itself rather than editing the shared
    `beforeEach` (out of scope for this context, and editing shared test setup for a single new
    test's benefit risks masking a similar gap in some other, not-yet-written future test).
