# CTX-311.12: Real, distinct interior color for the cavity's own walls and floor

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

`CTX-311.11`'s near-plane clipping fix shipped. The user's next message was a direct question, not a
bug report: "is it possible to have the inner surfaces a different color than the outside of the
enclosure" -- a real, forward-looking request growing directly out of this whole chain's repeated
feedback ("can't see the inside corners," "hard to see where the edges of the floor meet the floor").
The camera/lighting/clipping fixes (`CTX-311.4` through `CTX-311.11`) all made the correct geometry
*visible*; none of them gave the cavity's own edges a real color cue independent of shading angle or
light position. This context is that real, distinct fix.

## 1. Feature Definition & Execution Plan

### Phase 1: real face classification
*   [x] `_split_inner_outer_faces(mesh)` (`services/python-daemon/freecad_bridge.py`) -- classifies
    every triangle of the real shell mesh as cavity-facing (inner) or exterior-facing (outer) by
    comparing each face's own normal to the direction from the mesh's real bounding-box center out to
    that face's own centroid. A real, closed, manifold mesh's face normals always point away from the
    solid material they bound -- on an outer wall that means pointing away from the box's own center
    (positive dot product); on a cavity wall or the cavity's own floor, the solid material is on the
    far side from the cavity, so the normal points back toward the center (negative dot product).
    Verified by hand for a real box before writing the implementation: outer left wall (`x=0`, normal
    `-x`) and the cavity's own inner left wall (`x=wall_thickness`, normal `+x`) land on opposite
    sides of zero; the cavity floor's own top face (normal `+z`, sitting below the box's mid-height)
    does too.
*   [x] **Real, named limitation**: this is a global, whole-box heuristic, not a watertight flood-fill
    from the cavity -- a standoff post's own side facing *away* from the box's overall center can
    misclassify as "outer" even though the whole post sits inside the cavity. Not built out further;
    see Plan Drift.

### Phase 2: fix
*   [x] `_export_glb`'s new `inner_color_rgb` parameter (default `None`, unchanged single-material
    path when omitted): when given, splits the mesh via `_split_inner_outer_faces` and
    `mesh.submesh([outer_faces, inner_faces], append=False)` into two real geometries, assigns each
    its own real matte `PBRMaterial`, and exports both together in one `trimesh.Scene` -- the same
    "fix at the data source" approach `CTX-311.7` established, so any real glTF viewer (not just this
    app's own `<Canvas>`) sees the same real distinct colors, and no `EnclosureViewer.tsx` change is
    needed at all.
*   [x] `_BODY_INNER_COLOR_RGB = (241, 245, 249)` (slate-50) -- a real, distinctly brighter interior
    color from the existing `_BODY_COLOR_RGB` (slate-400) exterior, chosen for contrast rather than
    hue-matching, so the cavity reads as visually separate from the outer shell regardless of shading.
*   [x] Wired only into the body shell's own `_export_glb` call (`inner_color_rgb=_BODY_INNER_COLOR_RGB`)
    -- the lid's own call site is unchanged, deliberately: the lid is a flat, convex slab with no real
    cavity of its own to split (see Phase 3 edge case below), and the reported problem was always about
    the body's cavity, not the lid's underside.
*   [x] **Real edge case found and fixed while wiring this in, not by the user**: manual-dims mode
    (`width`/`depth`, no `board_outline`) builds a plain solid `Part::Box` -- convex, with no cavity at
    all -- so every face classifies "outer" and `inner_faces` comes back empty; the original
    `mesh.submesh([outer_faces, inner_faces])` call raised `ValueError: not enough values to unpack`
    the first time the real test suite ran this path (`test_004_real_enclosure_round_trip`, etc., all
    of which use `generate_enclosure`'s own default plain-box path). Fixed with a real fallback: when
    either face group comes back empty, `_export_glb` keeps the single-material path instead of
    attempting a split that has nothing real to split.

### Phase 3: tests
*   [x] `test_010_real_cavity_walls_and_floor_get_a_distinct_brighter_color_from_the_outer_shell` --
    real, board-driven `generate_enclosure` call; confirms the base shell's own `.glb` now contains
    exactly two real geometries with the two real, distinct expected colors, and that the geometry
    carrying the inner color has vertices genuinely closer (mean horizontal radial distance) to the
    shell's own center than the outer-colored geometry's -- a geometric sanity check that "inner" was
    classified correctly, not just that two colors happen to exist.
*   [x] `test_011_real_lid_stays_a_single_uniform_color_not_split` -- confirms the lid's own `.glb`
    still contains exactly one real geometry, unchanged.
*   [x] `test_009` (existing, `CTX-311.7`) updated rather than left stale: the base shell's own `.glb`
    is now a real two-geometry `Scene`, so this test now picks out the geometry whose own material
    matches `_BODY_COLOR_RGB` (the outer one) for the cross-part distinctness check against the lid,
    keeping the same real thing it always verified.
*   [x] Full real suite: `python3 -m pytest tests/test_freecad_bridge.py -v` -- 24 passed, all against
    real `freecadcmd`, no mocks. Full backend suite: `python3 -m pytest .` -- 347 passed, 1 skipped, no
    regressions.
*   [x] No frontend changes -- `EnclosureViewer.tsx` renders whatever materials the `.glb` carries
    (the `CTX-311.7` decision), so this is a backend-only fix; `npx vitest run`/`npx tsc -b` untouched
    by this change (not re-run as part of this context, since no frontend file changed).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the interior-color treatment is deliberately scoped to the body shell only, not the
    lid.** The lid is a flat, convex slab (`CTX-311.2`) with no real cavity of its own; the centroid-
    relative normal classification this fix uses only produces a meaningful split on a genuinely
    concave shape. Giving the lid's own underside a distinct color would need a different, shape-
    specific rule (e.g. "the face whose normal points down"), and the reported problem was always
    about seeing the *body's* cavity, not the lid's underside -- not built out, to keep this change
    scoped to the actual complaint rather than symmetric-for-its-own-sake.
*   **Deviation 2: the classification is a known, named approximation, not a true flood-fill from the
    cavity.** A standoff post's own side facing away from the box's overall center can misclassify as
    "outer" even though the whole post sits inside the cavity -- real connected-component/ray-casting
    analysis would classify it correctly, but standoffs are a small interior detail, not the wall/floor
    surfaces this fix targets, and building that out now would be solving a cosmetic edge case nobody
    has reported instead of the real, reported one.
*   **Deviation 3: a real edge case (manual-dims mode's solid box) was found and fixed by this
    session's own real test suite, not by the user.** The first implementation applied the split
    unconditionally to every body export; the very next real test run (not a hypothetical) surfaced
    `ValueError: not enough values to unpack` on the plain-box path, since a convex solid has no
    cavity-facing faces at all. Recorded here as a real example of "verify against the real thing,"
    this repo's own norm -- a mocked test with a hand-built face-index list might never have exercised
    a genuinely convex real mesh.
