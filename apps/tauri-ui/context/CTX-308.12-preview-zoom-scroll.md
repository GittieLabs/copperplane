# CTX-308.12: Implementation Context: Enlarged Preview Zoom & Scroll

> **Spec Reference:** Links to [SPEC-308](../specs/SPEC-308-footprints-schematic-advisor.md)

Real user follow-up on `CTX-308.11`'s own click-to-enlarge modal: "when using [the enlarged view],
there is no option to scroll and that means you can't see the entire image. we should make this
scaled view enable scrolling and optionally have a shortcut key to scale up/down." Both the root-cause
bug and the requested zoom/scroll/keyboard feature are fixed in this one slice.

## 1. Feature Definition & Execution Plan

### Phase 1: root cause -- a missing definite height, not a CSS-scaling myth
*   [x] Confirmed directly, not assumed: `CTX-308.11`'s own modal set `max-h-[90vh]` (a *cap*) on the
    outer flex column, never a real `height`. Its SVG container relied on `flex-1` + `h-full` to
    reach the SVG, but a percentage height inside an indeterminate-height ancestor is a textbook CSS
    pitfall -- the chain never resolved to a real pixel value, so the SVG fell back to its own
    real-world-unit (`mm`) intrinsic size instead of scaling to fit, which is exactly "can't see the
    entire image, no way to scroll."
*   [x] Verified against a **real** `kicad-cli`-generated symbol SVG (not a synthetic stand-in) in a
    real browser tab, before and after: confirmed the real file does carry a real `viewBox`
    (`19.2024mm x 20.7518mm`, `viewBox="0 0 19.2024 20.7518"`), so the fix only needed a real,
    definite height for the scale-to-fit chain to resolve -- not a workaround for a missing viewBox.
*   [x] Fix: the SVG's own scroll container now has a real, definite height (`h-[70vh]`, not
    `max-h-*`), so both the default 100% scale-to-fit case and any zoomed-past-100% case have a real
    percentage basis to resolve against.

### Phase 2: the requested zoom + scroll + keyboard shortcut feature
*   [x] `zoomLevel` state (0.5-4.0, 0.25 steps), applied via a CSS custom property (`--zoom`, set
    inline per-render) rather than a Tailwind arbitrary value -- a runtime-computed className string
    isn't statically extractable by Tailwind's build-time scanner, so the actual `calc(var(--zoom) *
    100%)` rule lives once in `index.css`, referencing a variable that changes freely at runtime.
*   [x] Real `width`/`height` scaling (not a `transform: scale`), so the element's real layout box
    grows past 100% -- giving the scroll container's own `overflow-auto` something real to
    scroll/pan, which a cosmetic transform alone would not.
*   [x] Zoom in/out buttons plus a click-to-reset percentage readout; keyboard shortcuts `+`/`=` (in),
    `-`/`_` (out), `0` (reset) alongside the existing `Escape` (close), scoped to only listen while
    the modal is actually open.
*   [x] `zoomLevel` resets to 1 every time a preview is (re)opened -- a fresh `openEnlargedPreview`
    wrapper around the existing state setter, so a lingering zoom level from a previous image never
    carries over to the next one.
*   [x] **Verified against the real thing, not just unit tests**: jsdom doesn't perform real CSS
    layout, so a passing test proves the right classes/CSS variable are applied, not that the
    percentage-height chain actually resolves in a real browser. Loaded the real `kicad-cli` SVG in
    the Browser pane, confirmed the full symbol renders with no cropping at 100%, zoomed to 195% via
    real clicks, and confirmed via `scrollHeight`/`scrollWidth` exceeding `clientHeight`/`clientWidth`
    (973 vs 504, 1668 vs 862) that the container is genuinely scrollable -- then scrolled to the
    bottom-right and confirmed pins 7/8 and the part label, both off-screen at that zoom level,
    became visible.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (non-deviation, confirmed as designed): zoom uses `width`/`height` percentages via
    a CSS custom property, not a `transform: scale` or a JS-measured pixel calculation.**
    *   *Reasoning:* a `transform` only affects paint, never layout -- the scroll container's own
        `scrollHeight`/`scrollWidth` would never grow past `clientHeight`/`clientWidth`, so
        `overflow-auto` would have nothing real to scroll regardless of the visual zoom. A real
        layout-affecting size change was the only way to make "zoom in, then scroll to see the rest"
        actually work, not just look zoomed.
    *   *Impact:* none -- this was the correct approach from the start, named here because it was a
        real design decision worth recording, not something arrived at by trial and error.
