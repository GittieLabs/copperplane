# CTX-315.4: Reopen Part Detail From the Library

> **Spec Reference:** Links to [SPEC-315](../specs/SPEC-315-library-browsing-and-organization.md)

## 1. Feature Definition & Execution Plan

Real, user-reported gap: once a Part is saved, "Save to Library" is the only door into its own
Part Detail view (pin table, Design Requirements, footprint export). `CTX-315.2`/`CTX-315.3` built
a real Library browsing view that lists a saved Part's identifying info, but selecting one did
nothing -- the only way back into a Part's full detail was starting a brand-new search from
scratch, which re-runs `SPEC-202`'s LLM extraction as if the part were a fresh, unconfirmed
candidate rather than something the user already confirmed and saved. `SPEC-315` §5's own stated
goal ("find a Part... they already saved... without re-searching or re-generating it") already
named this outcome; this closes the one real hole left in it.

Root cause was two gaps stacked together, both already flagged by an earlier investigation:
`apps/tauri-ui/src/lib/library.ts`'s `loadPart` narrows the real backend response (`library.load_part`
already returns the whole Part record) down to a summary shape (`LibraryPartSummary`) meant only for
list rows; and `PartDetail.tsx` only ever accepted a fresh `candidate: ComponentCandidate` prop,
unconditionally re-running `extractPartDetail` on mount with no path for an already-saved record to
skip it.

### Phase 1: a properly-typed full loader
*   [x] `apps/tauri-ui/src/lib/partDetail.ts`: new `loadPart(partId): Promise<SavedPart>`, reusing
    the same `library.load_part` route `lib/library.ts`'s own narrower `loadPart` already calls, via
    plain `dispatch` (fast file I/O, matching `saveConfirmedPart`'s own precedent) -- not `submitJob`.

### Phase 2: `PartDetail` accepts an already-saved Part
*   [x] `apps/tauri-ui/src/components/PartDetail.tsx`: new discriminated prop shape -- `{ candidate }`
    (unchanged, existing behavior) or `{ initialPart: SavedPart }`. The `initialPart` path skips
    `extractPartDetail` entirely, hydrates `extraction`/`savedPart`/`savedSymbol` directly from the
    saved record, and starts at `status: 'ready'` (no `'extracting'` flash). Every other action on
    the page (Add to library…, footprint search/attach/generate, Design Requirements, connection
    guidance) is unchanged and works identically from either entry point, since they all key off
    `savedPart`/`savedSymbol`, not `candidate`.

### Phase 3: reachable from the Library
*   [x] `apps/tauri-ui/src/components/LibraryArea.tsx`: a Part row becomes a real `<button>` calling
    a new optional `onSelectPart(partId)` prop when provided; falls back to the original
    non-interactive `<div>` when it isn't (defensive default, not a real second code path any real
    caller exercises).
*   [x] `apps/tauri-ui/src/App.tsx`: new top-level `{ kind: 'partDetail'; partId }` view -- a Part is
    a global `SPEC-304` object, not project-scoped, so reopening one doesn't require a project to be
    open; folding it into the existing project-scoped `components` area would have forced that
    dependency for no real reason. A new small `PartDetailView` component owns the
    load-then-render step (`loadPart` → `<PartDetail initialPart>`) and a "← Library" back link;
    `Rail`'s Library entry now also highlights while this view is open.

### Phase 4: tests
*   [x] `lib/partDetail.test.ts`: `loadPart` dispatches `library.load_part` and returns/propagates
    the real whole record.
*   [x] `PartDetail.test.tsx`: `initialPart` renders without calling `extractPartDetail`, starts
    already in the "Saved to library." state (never shows "Save to Library"), and "Add to library…"
    still works from that entry point.
*   [x] `LibraryArea.test.tsx`: clicking a Part row calls `onSelectPart` with the real `part_id`;
    without the prop, the row stays plain text (no regression).
*   [x] `App.test.tsx`: selecting a Part from the Library loads it and renders Part Detail; "← Library"
    returns to the Library view.

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Routing decision `SPEC-315` left open: a new top-level `partDetail` view, not the existing
    project-scoped `components` area.** `SPEC-315` names Part Detail as the destination but doesn't
    say how a global, non-project object should route into a shell built around per-project area
    tabs. Chose a sibling of `library`/`project`/`settings` in `App.tsx`'s own `View` union, since a
    saved Part is exactly as project-independent as the Library itself (`SPEC-304`'s global object
    model) -- routing through `components` would have forced a project to be open first, for no
    reason the data model requires.
*   **`SavedSymbol.reference_prefix` is synthesized as an empty string on the `initialPart` path**,
    not fetched via a second `loadSymbol` round trip. Grep-verified unused anywhere in `PartDetail.tsx`'s
    own render or logic (`exportSymbol` only reads `symbol_id`) -- a real, minor debt if that
    changes later, not a functional gap today.
*   **A real crash the test suite caught, not predicted in advance:** the first pass lazily
    initialized only `status` to `'ready'` when `initialPart` was passed, leaving `extraction`/
    `savedPart`/`savedSymbol` at their `null` defaults for React's first render -- the effect that
    would populate them hasn't run yet at that point (effects commit after paint, not during it).
    Render immediately threw `Cannot read properties of null (reading 'part_number')`. The three new
    `PartDetail.test.tsx` tests for the `initialPart` path caught this on the very first run, exactly
    the value this repo's own "verify against the real thing" norm names -- fixed by lazily
    initializing `extraction`/`savedSymbol`/`savedPart` themselves from `initialPart` (via two small
    shared helpers, reused by the effect too), not just `status`.
