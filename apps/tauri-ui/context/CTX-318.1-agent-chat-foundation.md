## 1. Feature Definition & Execution Plan

### Phase 1: `lib/chat.ts` -- the client module SPEC-318 §2.7 names
*   [x] Real TypeScript types this repo's frontend has never had: `SourceRef` (the eight-kind union
    `services/python-daemon/chat_agents.py`'s `_RESOLVERS` already implements -- confirmed directly,
    `grep -rn "SourceRef" apps/tauri-ui/src/` returns zero matches today) and `ChatTurn` (the real,
    richer shape `chat_agents.py`'s own `_make_turn` builds -- `turn_id`, `role`, `content`,
    `timestamp`, `agent`, `sources`, `sources_dropped`, `general_practice`, `tool_calls`,
    `provenance`, `promoted_note_id`). Deliberately does **not** touch `lib/projects.ts`'s existing
    `ConversationTurn` -- that's the older, narrower SPEC-302 shape backing
    `project.append_conversation_turn`/`project.load_conversation`, a real, separate, still-used code
    path this phase does not migrate (Phase 5 -- deleting Overview's old chat handling -- is where
    that shape actually goes away).
*   [x] `loadChatThread(scope, scopeId)`, `listChatThreads(projectName)`, `promoteChatTurn(...)`,
    `searchContext(...)` -- plain `dispatch()`, matching `chat.load_thread`/`chat.list_threads`/
    `chat.promote_turn`/`context.search`'s own real synchronous-route status (confirmed directly
    against `daemon.ROUTES`/`daemon.ASYNC_ROUTES` -- none of the four are in `ASYNC_ROUTES`).
*   [x] `sendChatMessage(scope, scopeId, area, message, projectName?)` -- `submitJob()`, matching
    `chat.send`'s own real `ASYNC_ROUTES` membership (a real LLM call).

### Phase 2: real, honest progress -- scoped down from what SPEC-318 §3 assumes
*   [x] **Real finding, not assumed:** SPEC-318 §3 says real per-call progress ("reading the ATtiny85
    datasheet") is "achievable with what exists" via `SPEC-105`'s job protocol and AgentFlow's
    `EventBus`. Verified directly against the real code before building anything: it is not. Today
    `_run_job` (`daemon.py`) emits exactly one `job.progress` notification, unconditionally, at job
    start, with a hardcoded `{"status": "running"}` payload -- no route, including `chat.send`, has
    any hook to emit its own progress mid-call. `ipc.ts`'s own `job.progress` handler already
    discards everything except `job_id`. `chat_agents.py`'s `_ToolResultCollector` only subscribes to
    `TOOL_RESULT` (for mechanical `SourceRef` derivation, `CTX-206.6`), never `LLM_CALL_STARTED`/
    `TOOL_CALLED`, and its events are read back only after `executor.run()` already returned, not
    streamed live.
*   [x] Building real, route-emitted, tool-aware progress text is genuine, separate backend *and*
    frontend plumbing (a `progress_callback` threaded into `_run_job` the way `cancel_event` already
    is; `chat_agents.py` subscribing its `EventBus` to the richer event set and forwarding through it;
    `ipc.ts`'s notification handler carrying real payload data instead of discarding it) -- not a
    small addition, and out of scope for this foundation slice.
*   [x] `AgentChat` ships instead with an honest, static "Thinking…" state while a `chat.send` job is
    in flight -- spec-compliant either way, since `SPEC-318`'s own non-goal is "no streaming," not
    "no progress at all," and a static state cannot misrepresent itself as one. The richer version is
    named here as real, deferred, separately-scoped follow-up work, not silently downgraded.

### Phase 3: the shared `AgentChat` component
*   [x] Collapsible, default-collapsed on first visit, remembered per `area` via `localStorage`
    (matching `lib/theme.ts`'s own already-established localStorage convention -- SPEC-318 §2.2's
    own explicit requirement: "the flag is per-area UI state, not a project record"). Built with a
    controlled `<details open onToggle>`, matching `PartDetail.tsx`'s own only two existing
    collapsible uses in this codebase (its pin table and its citations block) rather than inventing a
    new pattern -- confirmed directly there is no existing `Collapsible`/`Accordion` component
    anywhere in `apps/tauri-ui/src` to reuse instead.
*   [x] Loads the real thread on mount (`loadChatThread`, keyed on `scope:scopeId` so switching Parts
    or projects reloads, matching this repo's own established `useEffect`-keyed-on-identity reset
    convention); draft text and in-flight state are plain component state, correctly surviving an
    area *tab* switch for free once each area's own parent component follows the mount-always pattern
    (`ComponentDiscovery`/`SchematicAdvisor`/`BoardAdvisor`/`EnclosurePanel` already do; `Overview`
    doesn't yet -- Phase 5's own job, named there, not fixed here).
*   [x] Sends via `sendChatMessage`, appends the real returned `ChatTurn` directly (no thread re-fetch
    -- the route's own response already carries everything needed for this turn).
*   [x] Renders each assistant turn's sources as chips inside a `<details>` (mirroring the citations
    UI `PartDetail.tsx` already established for `CTX-205.7`/`CTX-205.8`), with `general_practice`
    visually marked, never described as "verified" anywhere (SPEC-318 §2.2's own explicit
    instruction). Real "open the source" behavior is wired for the two kinds with a genuine, direct
    open target -- `datasheet_page` (`part_id`+`page` it already carries) and `guidance_item`
    (resolves its real page by loading the part and matching `category`+`quote` against its stored
    `design_guidance`, since the chunk-index's own `guidance_item` `SourceRef` deliberately carries no
    `page` field) -- generalizing `PartDetail.tsx`'s own `handleOpenCitation`
    (`cacheDatasheet`+`open(...#page=N)`) rather than copying it. The other five kinds
    (`connection_guidance`, `part_field`, `project_intent`, `chat_turn`, `note`) render as real,
    labeled, non-interactive chips -- `check_finding` never actually resolves today (its own resolver
    is still the deliberate `_resolve_deferred` stub), so it's handled defensively, not expected in
    practice.
*   [x] "Save as note" on an assistant turn -- `promoteChatTurn`, with `promotionTargets` supplied by
    the caller (e.g. Components supplies `[{label: 'This part', scope: 'part', id: partId}]`; a
    project-scoped area additionally offers `[{label: 'This project', scope: 'project', id:
    projectName}]` when both are known). Shows a real confirmation and disables re-promoting the same
    turn to the same target it was just promoted to (re-promoting to a *different* target is still
    allowed, matching `chat_agents.promote_turn`'s own deliberate design).
*   [x] Deliberately not mounted anywhere real in this phase -- verified via a standalone render in
    its own test file, not a live area. Phase 2 is the first real integration.
