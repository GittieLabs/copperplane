# CTX-304.3: Project holds real references to Parts, not just a described intent

> **Spec Reference:** Links to [SPEC-304](../specs/SPEC-304-project-library-storage.md)

Closes a real, user-reported gap: a user exported a Symbol and a Footprint from Part Detail while a
project was open and found both correctly written to the shared global Library, but with nothing
tying the new Part to the project they were actually working in. `SPEC-304` §2's own directory
diagram already named the missing piece -- `project.json # metadata, KiCad project link,
**component refs**` -- and its own prose already decided the shape: "a named workspace holding
*references* to library Parts (not copies)." Neither was ever built:
`library_store.py`'s `save_project` accepts an arbitrary dict with no `parts` field, and
`SPEC-307`'s "Save to Library" action (`library.save_confirmed_part`) writes a Part and Symbol to
the global library with no reference back to whichever project is open. `PartDetail.tsx` does not
even receive a `currentProject` prop today, confirmed directly.

Deliberately **not** in scope: Symbols and Footprints stay purely global, exactly as `SPEC-300`
§2.1/`SPEC-308` already specify ("many parts share one footprint"). The reference this context adds
is Part-level only, non-exclusive, many-to-many -- adding a Part to Project B never removes it from
Project A, and never duplicates the underlying Symbol/Footprint record or file. This is `SPEC-304`'s
own already-decided design, not a new product decision (confirmed with the user before this context
was drafted).

## 1. Feature Definition & Execution Plan

### Phase 1: `project.json` gets a real `parts` reference list
*   [x] `library_store.py::add_project_part_reference(project_name, part_id)`: loads the project,
    appends `part_id` to its `parts` list if not already present (idempotent), and calls the
    existing `save_project` to persist it -- the same load/mutate/save shape as `set_project_intent`.
    Mirrors `save_project`'s own pointer-vs-linked-directory routing (`CTX-312.1`) automatically,
    since it delegates to `save_project` rather than reimplementing the write.
*   [x] `_backfill_project_intent` (now backfilling more than just intent) gained
    `record.setdefault("parts", [])`, called from every one of `load_project`'s existing return
    paths -- every project saved before this context (no `parts` field at all) loads cleanly with
    `parts: []`, never `None` and never a missing key.
*   [x] `daemon.py`: new `project.add_part_reference` route (`project_name: str, part_id: str`),
    matching `project_save_artifact`'s own existing `project_name`-first-argument shape.

### Phase 2: Thread the active project into Part Detail and call it from Save to Library
*   [x] `apps/tauri-ui/src/lib/projects.ts`: added `parts?: string[]` to the `Project` interface,
    and a new `addProjectPartReference(projectName: string, partId: string): Promise<Project>`
    wrapper over `project.add_part_reference`, matching `appendConversationTurn`'s own
    `unwrap`/`dispatch` shape.
*   [x] `App.tsx` passes `currentProject` down into `<ComponentDiscovery />` (matching `Overview`'s
    own existing `project={currentProject}` pattern); `ComponentDiscovery.tsx` accepts it as an
    optional prop and forwards it to `<PartDetail candidate={...} currentProject={...} />`. No new
    state -- `currentProject` already existed in `App.tsx`, only threaded one level further.
*   [x] `PartDetail.tsx`'s `handleSave`: after `saveConfirmedPart` succeeds, if `currentProject` is
    set, calls `addProjectPartReference(currentProject.name, saved.part.part_id)`. A failure here is
    surfaced as a real, separate, non-blocking warning (`projectLinkWarning`, distinct from
    `saveError`) next to the already-succeeded "Saved to Library" state -- the Part is genuinely
    saved either way; only the linkage step can fail independently.
*   [x] No `currentProject` (Library browsed with no project open, or an `initialPart` view -- a
    Part opened from the Library is already saved): "Save to Library" behaves exactly as before --
    global save only, no reference added, no error, no linkage call at all.

### Phase 3: Real, hands-on verification
*   [x] Real daemon test: two saves of the same part while the same project is open converge on one
    `parts` entry, not two (`TestProjectPartReferences.test_003`).
*   [x] Real daemon test: a project saved before this context (no `parts` key on disk) loads and
    accepts a new reference without error (`TestProjectPartReferences.test_001`/`test_002`).
*   [ ] Manual, as-the-user verification (per `CLAUDE.md`'s norm): not done this session -- named
    honestly below rather than assumed.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (non-deviation, confirmed as designed): `_backfill_project_intent` now backfills
    more than just `intent`.**
    *   *Reasoning:* the function is called from every one of `load_project`'s three return paths,
        exactly where `parts` also needs backfilling to `[]`. Adding a second, separately-named
        backfill function called at the same three sites would be pure duplication for no real
        benefit -- the function's docstring was expanded to explain both fields honestly rather than
        inventing a new abstraction for a one-line addition.
    *   *Impact:* none -- `TestProjectDirectoryLink.test_003`'s own exact-record-shape assertion
        needed updating to include `parts: []`, the only pre-existing test that asserted the full
        record shape verbatim.
*   **Deviation 2 (real, honest gap): manual verification not performed.**
    *   *Reasoning:* this session's real Save-to-Library flow needs a live daemon and a real KiCad-
        adjacent project open; the automated tests already exercise the real file-write path (a real
        temp storage root, not a mocked filesystem), which is the highest-value part of this to get
        right automatically -- but a human clicking through the actual UI is still the only way to
        confirm the end-to-end experience matches what the tests assert.
    *   *Impact:* named here rather than silently assumed; a real follow-up before this is
        considered fully done, not before it's mergeable.
