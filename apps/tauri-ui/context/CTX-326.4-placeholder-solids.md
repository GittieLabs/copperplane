# CTX-326.4: The Labelled Bounding Solid

> **Spec Reference:** Links to
> [SPEC-326](../specs/SPEC-326-component-volume-placeholders.md)

## 1. Feature Definition & Execution Plan

`SPEC-326` §1 promises *"a footprint with no resolvable model gets a labelled bounding solid, a
clearance proxy, never presented as a real model."* Three contexts have built everything that feeds
it — `CTX-326.1` reads courtyards, `CTX-326.2` sources Z and recommends an interior height,
`CTX-326.3` made the board the source of truth — and **nothing renders any of it**. The enclosure
preview today is a shell, standoffs and a lid; no component geometry of any kind has ever appeared
in it.

So this context is the one that puts a volume in the box, and its whole risk is that a solid in the
**wrong place** renders perfectly and is silently wrong. That is the failure this repo keeps paying
for, so Phase 1 is verification rather than plumbing — the `CTX-114.1` ordering, for the same
reason.

### Phase 1: Prove a solid lands where it is supposed to, before building the pipeline that makes many

*   [x] Parse `(at x y [rot])` from each board footprint in `kicad_board.read_board_footprints`.
        It is not read today; the record carries reference, footprint, value and layer only.
*   [x] Place **one** box into a real generated enclosure and assert its position **in the exported
        file**, not in the arguments passed to the exporter. A test that checks what it just passed
        in cannot fail for the reason this phase exists.
*   [x] Assert against the transform standoffs already use — `x - board_outline["x_mm"] + margin`.
        That mapping is established and correct; reusing it is the point, and a placeholder landing
        somewhere a standoff would not is the bug being hunted.
*   [x] Verify with FreeCAD actually installed, skipping cleanly when it is not.

### Phase 2: Every component that has a height, and none that does not

*   [x] A solid per component whose envelope carries `x_mm`, `y_mm` **and** a non-null `z_mm`.
*   [x] **A component with `source: "unknown"` gets no solid at all.** `SPEC-326` §2.3: there is no
        fifth source, and a default height fails as a physical object that does not fit. An absent
        volume is the honest rendering of an unknown one.
*   [x] Rotation applied from the footprint's own `at` angle, so a rotated rectangular part occupies
        the space it really occupies.
*   [x] Components read from the **board**, per `CTX-326.3` — the same read the numbers are quoted
        from, not a second one that can drift.

### Phase 3: Measured and stated are visibly different, and neither is mistaken for real geometry

*   [x] Placeholder solids exported as their own mesh group with a distinct material, reusing the
        mechanism `CTX-311.6` built for the shell's inner and outer surfaces.
*   [x] **Preview only: placeholders are in the GLB and never in the STEP.** The GLB answers "will
        the lid close" and carries the visual distinction that labels it. The STEP is the
        fabrication artifact — a stated envelope inside it opens in any CAD tool as ordinary solid
        geometry with nothing to mark it, which is exactly the mistaking `SPEC-326`'s second
        non-goal forbids.
*   [x] A solid whose height came from a real model and one whose height a user typed are
        distinguishable, because `SPEC-326` §2.4 asks the user to be able to tell without asking.

### Phase 4: Say it in words too

*   [x] The enclosure panel names how many volumes are shown, how many are stated rather than
        measured, and how many components are missing entirely because their height is unknown.
*   [x] The last of those is the one that matters and the easiest to omit: a preview showing eight
        of ten parts looks complete. `CTX-326.2` already warns that the real minimum may be taller;
        this is the same warning made visible in the geometry.

## 4. Plan Drift & Architectural Changes

*   **Prediction 1: the coordinate transform will be right first time and the rotation will not.**
    The transform is already written and proven for standoffs, so reusing it is low risk. Rotation
    is new: KiCad's `at` angle is counter-clockwise in a Y-down board coordinate system, and the
    enclosure is built in FreeCAD's Y-up frame. A sign error there produces a box that is rotated
    the wrong way, which for a symmetric part is invisible and for an asymmetric one is a clearance
    answer that is wrong in a direction nobody checks. If this turns out to be backwards, it belongs
    here.

*   **Prediction 2: building the boxes will not need FreeCAD.** They are axis-aligned rectangular
    solids at known positions, and the GLB export already goes through `trimesh`. Generating them
    directly rather than round-tripping through a headless FreeCAD subprocess should be simpler,
    faster and easier to test — and it keeps placeholders structurally separate from the shell,
    which Phase 3 needs anyway. Recorded as a prediction because "should be simpler" is exactly the
    kind of claim that turns out to have a reason it was not done that way.


*   **Prediction 1 was half right, and the half that was wrong was wrong in my favour.** It
    predicted the coordinate transform would be right first time and the rotation would not. The
    transform was right first time. **The rotation was too**, which I did not expect and should not
    be read as skill: `TEST-006` uses a 10 x 2 box precisely because a square one hides a rotation
    error, and it passed on the first run.

    What made this checkable rather than lucky is that `TEST-003` reads the exported `.glb` and
    locates the geometry in it. Deleting the Y-up rotation fails two tests; deleting the
    millimetre-to-metre scale fails two; and **both mutations still export a file that loads and
    renders**, which is exactly the silent wrongness the phase was ordered first to catch.

*   **Prediction 2 was right.** The boxes are `trimesh` primitives and never touch FreeCAD. That
    turned out to matter more than "simpler": because the placeholder never enters the solid FreeCAD
    builds, keeping it out of the STEP is structural rather than a rule someone has to remember.
    `TEST-008` pins it — the STEP is the same length with and without.

*   **Two keys spelled the same, meaning different things, joined to place geometry.** A resolved
    component record carries `courtyard["x_mm"]`, which is a **size**; the position I added was also
    `x_mm`. Both end up in one join whose entire job is putting geometry somewhere. Renamed to
    `pos_x_mm`/`pos_y_mm` one commit after introducing them. Cheap now; the alternative was a
    comment explaining the hazard, and a comment is not a guard.

*   **Found while wiring it: the enclosure panel ignored every height the user had supplied.** It
    called `componentEnvelopes(null, pcbPath, {})` — a literal empty object. `SPEC-326` §2.3's third
    source is *"a user-supplied height, entered once per footprint and remembered"*, and it worked
    in the components table and nowhere else. The recommended interior height was therefore quietly
    too short for any board with an unmodelled part, which is every board this spec was written for.
    Not a rendering bug and not in this context's plan; it surfaced only because the placeholders
    needed the same overrides and there were none to pass.

*   **The real board is the argument for reporting what is missing.** On the maintainer's own
    tutorial board, `2` of `8` components can be drawn — six have no height from any source. A
    preview showing two parts, with nothing said, reads as a finished picture of a nearly empty
    board. That is why `omitted` is reported and why `TEST-010` exists; it is the number a
    reasonable implementation leaves out, because everything it describes is absent.

*   **A stale `__pycache__` cost about twenty minutes.** A mutation-test experiment wrote bytecode
    that outlived the source restore, so a reverted file kept running the mutated code and the
    restore looked broken. `python -B` does not help: it stops bytecode being *written*, not *read*.
    Worth knowing because mutation-checking a claim is a norm in this repo, and this is the failure
    mode that makes the check itself lie.

*   **What was not verified.** No click-through in the running app — the geometry was driven through
    the real route and read back out of the real exported `.glb`, on macOS with FreeCAD 1.0. The
    frozen sidecar has not been rebuilt since these routes changed, so this has not run from the
    artifact that ships.


*   **The feature drew volumes on exactly the parts that did not need them, and the maintainer's
    question found it.** Reported from the running app as *"what project pcb board did you use to
    test it? i don't see any volumes created"* — the toggle was off, but ticking it would have shown
    something worse than nothing.

    On the tutorial board the only two volumes drawn were `D1` and `R1`: the only two components
    with resolvable STEP models, already rendered as real geometry by the board overlay. `SW1` and
    `A1` — a tactile switch and the **Arduino UNO module, the largest object on the board** — got
    nothing.

    `SPEC-326` §2.3 says this in its own first line and I read past it: *"A real STEP model, if one
    resolves. **Not a placeholder at all**; `SPEC-311`'s existing path."* A stated envelope drawn
    over measured geometry is precisely the confusion §2.4 exists to prevent, and it inverted the
    feature: the parts that had an answer got a second one, and the parts that needed an answer got
    none.

    Fixed by excluding `source == "model"` from the join. The count shape changed with it, because
    **a placeholder can never be "measured"** — a measured component has a model and is drawn as
    one. So the surface now reports three separate things: what was drawn, what did not need
    drawing, and what could not be drawn.

    | On the tutorial board | before | after |
    | :--- | :--- | :--- |
    | volumes drawn | 2 (`D1`, `R1` — both already modelled) | 0 |
    | already modelled | not reported | 2 |
    | no height from any source | 6 | 6 |

    With heights entered for `SW1` and `A1` it draws those two instead — the switch at 9.9 x 7.9 x
    5mm and the Arduino at 75.4 x 53.8 x 15mm inside an 85.5 x 75mm cavity, which is a real fit
    check rather than a decoration.

    The lesson is not "read the spec more carefully", which is unfalsifiable. It is that every test
    written for this had a `source` I chose, so nothing in the suite could notice that the *set* of
    components being drawn was wrong. The measurement that caught it — running the real board and
    listing which references got a volume — took one command and existed only because a user asked
    where the volumes were.

*   **The two placeholder colours were redefined rather than deleted.** They originally meant
    measured versus stated, which is now a distinction placeholders cannot express. They now mean a
    height derived from a package dimension versus one the user typed — genuinely unequal, because
    §2.2 measured a CR2032 whose package height reads 3.2mm while the cell stands on edge and is
    really 20mm.

*   **A live-provider test failed once during this work and is not related to it.**
    `test_llm_providers.TestRealProviderCalls.test_002_real_google_chat` asserts
    `usage["output_tokens"] > 0` against a real Google API call; Google returned `None` once and it
    passed on re-run. Recorded rather than dismissed as a flake: the weakness is real — the test
    depends on a live provider populating an optional field — and it is tracked separately.


*   **The warning counted four things nobody can act on, and this had been found before.** With the
    inversion fixed, the tutorial board reported *"6 components are missing from this preview ...
    Add a height in the Components tab to include them."* Four of the six were `H1`-`H4`, KiCad
    `MountingHole` footprints. A screw hole has no height because it is a hole in the board, not a
    part standing on it, and the enclosure already represents it as standoff geometry.

    `CTX-311.15` found exactly this once already, from a real click-through, on the neighbouring
    height-derivation route — it was reporting unannotated MountingHole footprints as *"missing a 3D
    model"*, which `kicad_bridge`'s own docstring calls *"technically true but misleading."* The
    recognition rule and the reasoning were both already written down, in a module this code sits
    next to. I wrote a new count without them.

    So `SPEC-109` §2's convention now lives in exactly one place — `kicad_board.is_mounting_hole`,
    in the pure file-parsing module, because `kicad_bridge` needs `kipy` importable and the
    file-reading path does not. Both call sites use it.

    | tutorial board | before | after |
    | :--- | :--- | :--- |
    | omitted, no heights entered | 6 | 2 |
    | omitted, `A1` height entered | 5 | 1 |
    | omitted, `A1` and `SW1` entered | 4 | 0 |

    Every remaining item is something the user can fix, and the count reaches zero. A warning whose
    items are mostly unactionable teaches people to skip the warning, which costs more than the
    four lines it saved.

*   **The check is on the library, not the whole footprint id, and that is load-bearing.**
    `Module:Arduino_UNO_R3_WithMountingHoles` has *MountingHoles* in its footprint **name** and
    `Module` as its library. Matching the whole id would silently drop the Arduino — the largest
    object on the board and the single component the missing-height warning most needs to name.
    Pinned by its own test rather than left to the comment.
