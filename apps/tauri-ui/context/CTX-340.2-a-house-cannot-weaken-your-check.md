# CTX-340.2: Implementation Context: A House Cannot Weaken Your Check

> **Spec Reference:** Links to
> [SPEC-340](../specs/SPEC-340-ordering-this-board-from-a-real-house.md)

## 1. Feature Definition & Execution Plan

Four defects in shipped `SPEC-340` work, found by using it. One of them is a safety defect and is
why this context is named after it.

### Phase 1: A house's limits can never replace a stricter setting of the user's own

*   [x] Measure what a sidecar rule does to the board's own constraint. It **replaces** it: a
    sidecar `annular_width` of 0.05mm against a board setup requiring 0.1mm took four genuine errors
    to **zero**.
*   [x] Establish that the shipped generic profile was looser than KiCad's defaults on two of nine
    fields, so this was live rather than theoretical.
*   [x] Read the project's own values and refuse to emit any rule it already beats.
*   [x] Report those fields rather than silently doing nothing, because "your own settings are
    stricter than your fab requires here" is worth knowing.
*   [x] Regression test with a control, so a build that writes no rules at all cannot pass it.

### Phase 2: The check result survives a tab switch

*   [x] Persist what the UI is showing, separately from `last_results`, which is the same check
    shaped for the review agent and capped because it goes into an LLM context.
*   [x] Restore it on mount with a relative timestamp, matching the review's wording.
*   [x] A Dismiss that clears it, matching the review's affordance.

### Phase 3: Changing the house cannot leave stale findings looking current

*   [x] Record which house a result was produced against.
*   [x] Say so, visibly, when that differs from the house now selected.
*   [x] Offer a re-run, which had no affordance at all.

### Phase 4: Say where the settings live and what the nine are

*   [x] Name KiCad's own menu path, the way the ignored-tests block already does.
*   [x] State that the nine are neither KiCad's defaults nor a superset of them.
*   [x] Show, per field, where the user's own setting is already tighter.

## 4. Plan Drift & Architectural Changes

*   **A re-check was only reachable by changing the board house.** Reported: *"a button to recheck
    which the user may want to do if they changed their details in the actual board file. the
    re-check option only shows if you change the house."*

    The "Run board check" button rendered only when there was no result, and "Check again" lived
    inside the stale-house warning. So the ordinary case — edit the board in KiCad, come back, run
    it again — had no control at all. Editing the board is the most likely reason to re-run and has
    nothing to do with the profile.

    Now a re-check sits beside Dismiss whenever a result is on screen, and the duplicate inside the
    stale block is gone. The same gap existed on the Schematic tab and is fixed with it, since that
    surface was flagged for the same reason a round earlier.

    The timestamp also now carries an actual clock time next to the relative phrase, rather than
    only "just now" — relative for scanning, absolute because it is meant to be a timestamp.

*   **The state preservation shipped completely broken, and my own test design is why.**
    Reported immediately: *"i chose a different project and then came be to the test project and the
    board check was gone."*

    `set_project_check_display` raised `AttributeError` on **every** call. `library_store` already
    does `from datetime import datetime, timezone`; the `import datetime` I added shadowed it, so
    `datetime.datetime` did not resolve. The feature never stored anything, ever.

    It was invisible for two reasons, and the second is the real fault. The frontend wrote
    `.catch(() => undefined)` — swallowing the error — **two lines below an existing `catch` in the
    same function whose comment reads "never swallow it silently"**. And every test of this path
    mocked `setProjectCheckDisplay`; not one called the real function, so the whole suite agreed a
    function that could not execute was working.

    Fixed by matching the module's own import, surfacing the write failure the way the neighbouring
    `setProjectCheckResult` already does, and adding daemon tests that call the real store. Those
    were confirmed to fail against the reintroduced bug before being kept.

    The lesson is narrower than "test more". A mock asserts the caller's intent, which was correct
    here — the call was well-formed and the arguments were right. Nothing about the intent was
    wrong; the function on the other side simply could not run. Only touching the real thing finds
    that, which is the norm this repo already writes down for KiCad and for the frozen sidecar, and
    which I did not extend to a route I had just written.

*   **The safety defect was found by answering a question, not by looking for a bug.** The question
    was *"isn't the generic option kicad's default or something different?"*. Answering it properly
    meant reading the board's own rule values, which showed the generic profile was looser on two
    fields, which raised the question of what a looser rule actually does. It replaces the stricter
    one. Nobody was looking for that.

*   **The first attempt to measure it proved nothing.** Testing `edge_clearance` at values above and
    below the board's own setting returned zero violations in all three cases, because no copper on
    this board is near the edge at any of them. A check that cannot fail. The real measurement used
    `annular_width`, where the board already had four genuine violations to lose.

*   **Two test failures were the machine, not the code.** Three `kicad-cli` timeouts during a suite
    run turned out to be a load average of 35 from an unrelated game and four antivirus scanners.
    The failures were timeouts, not assertions, and the same tests passed in seven seconds once the
    machine was quiet. Worth recording because "it failed in the suite and passed alone" is exactly
    the shape of a claim that needs evidence.

*   **Two of my own tests failed for a real reason and I nearly attributed them to the same load.**
    `KeyError: 'report'` and `KeyError: 'hits'` — written against the pre-fold return shape of
    `fabrication_review.review`. The error type is what distinguished them from the timeouts.

*   **`unittest -k` does not support `or`.** `-k "looser or stricter"` matched nothing and reported
    `Ran 0 tests ... OK`, which is a passing result that checked nothing.

*   **Deliberately not built here:** everything about *multiple* houses — clone, rename, remove,
    switching, bundled vendors, JSON import and export. All of it was requested in the same message
    and none of it is a defect in shipped work; it is a feature, and it is specced as `SPEC-342`
    rather than smuggled into a bug-fix context.
