# CTX-311.15: Board-inside-enclosure visual fit check

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

`SPEC-311` §2 named this directly as the payoff of the whole-board `kicad-cli pcb export glb`
research (`CTX-311.1`): load the real, assembled board's own `.glb` *inside* the generated
enclosure's own `.glb`, in one scene -- a genuine visual "does this fit" check instead of trusting a
number. `CTX-311.1` built the backend half (`kicad_cli.export_board_glb`, the
`kicad.export_board_glb` route) and deliberately deferred wiring it into the frontend. This context
does that wiring, plus solves the one real problem that made it non-trivial: two entirely separate
toolchains (`kicad-cli` for the board, `freecadcmd` for the enclosure) with no shared coordinate
convention guaranteed a priori.

## 1. Feature Definition & Execution Plan

### Phase 1: real coordinate-alignment prototype (before writing any implementation code)
*   [x] Confirmed by direct `kicad-cli` experimentation and `trimesh` bounding-box inspection against
    a real board (`NFC_Reader_ESP32.kicad_pcb`): `kicad-cli pcb export glb`'s own **default** output
    (no origin flag) already lands in the exact same real, absolute board-layout coordinate frame that
    both `kicad_bridge.get_board_outline()` and `kicad_pcb_import.extract_board_outline()` already
    report `x_mm`/`y_mm` in -- the exported glb's X/Z extents matched the real outline's own
    `x_mm..x_mm+width_mm` / `y_mm..y_mm+height_mm` exactly.
*   [x] Confirmed `kicad-cli`'s own `--user-origin VAR` flag (e.g. `--user-origin 70.25x41.25mm`) sets
    a new local origin at that real absolute point -- with it set to the board's own real outline
    `x_mm`/`y_mm`, the exported glb's bounds shift so the board's own bounding-box corner lands exactly
    at local `(0, *, 0)`.
*   [x] Confirmed the board glb is already real Y-up (kicad-cli's own native convention, unlike
    `freecad_bridge`'s raw STL which needed `CTX-311.5`'s explicit rotation) -- already matching the
    enclosure's own post-`CTX-311.5` Y-up convention.
*   [x] Confirmed the enclosure's own local origin (its outer box's own corner) is a pure,
    untranslated `(0,0,0)` in its exported glb (`_export_glb` only ever rotates/scales, never
    translates), and that per `daemon.py`'s own standoff-position math, that corner sits `margin`
    (`wall_thickness_mm + clearance_mm`) away from the board's own real edge, with the board's bottom
    surface at `wall_thickness_mm + standoff_height_mm` above the enclosure's local floor.
*   [x] **Design conclusion:** no coordinate math needs the board's own real outline position at the
    frontend at all. Exporting the board glb with `--user-origin` set to its own real outline
    normalizes it to local `(0, *, 0)` server-side; placing it inside the enclosure client-side is
    then just a constant, already-known translation.

### Phase 2: backend -- real-origin export and outline derivation
*   [x] `kicad_cli.export_board_glb` gains optional `origin_x_mm`/`origin_y_mm` params -- when both
    are given, passes `--user-origin {x}x{y}mm` to the real subprocess call. `None`/`None` (default)
    keeps every other caller's behavior byte-for-byte unchanged.
*   [x] `daemon.py`'s `kicad_export_board_glb` route derives the real outline via
    `kicad_pcb_import.extract_board_outline(pcb_path)` and passes it through as the origin.

### Phase 3: frontend -- lib wrapper, viewer compositing, panel wiring
*   [x] `lib/enclosure.ts`: `exportBoardGlb(pcbPath)` (thin `submitJob` wrapper, mirrors
    `generateEnclosure`/`exportEnclosure`) and `getComponentHeights()` (wraps the already-existing,
    previously-uncalled `kicad.get_component_heights` route from `CTX-311.1`).
*   [x] `EnclosureViewer.tsx`: new pure `computeBoardOffset(marginMm, floorAndStandoffMm)` (mm-to-glb-
    scale conversion, matching this file's own established pure-function convention); a third
    `useGlbScene` call for the board; composited as a `<primitive>` inside the same `<Canvas>`,
    gated on `boardVisible` and a real, resolved `boardOffsetMm`. Deliberately **not** included in
    `computeFrame`'s own camera-fit array -- the camera keeps framing on the enclosure (body+lid)
    alone; if the board doesn't fit inside that frame, that mismatch is itself real, useful
    information, not something to hide by silently zooming out.
*   [x] `EnclosurePanel.tsx`: a "Show board (visual fit check)" checkbox, enabled only once a board-
    driven result exists (`resultBoardParams`). First check lazily fetches and caches the board glb;
    a fresh Generate clears the whole board-overlay state (`resultBoardParams`, `boardGlbPath`,
    `boardVisible`, etc.) since a new result's own geometry params may no longer match what was shown.
    A real, honest amber disclosure names any reference designator with no resolvable 3D model
    (`SPEC-311` §5), sourced from `getComponentHeights()`'s own `unknown` list.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: outline lookup is always file-based, never live-first, despite the approved plan
    text saying "live-first, file fallback."** The plan (matching `freecad_generate_enclosure`'s own
    live-first/file-fallback pattern) was written before implementation started. While implementing,
    found that `kicad_bridge.get_board_outline()` reads whatever board is *currently live* in KiCad,
    which can genuinely differ from the explicit `pcb_path` this route receives -- e.g. a manually-
    picked file that isn't open in KiCad at all. Further investigation confirmed `EnclosurePanel.tsx`'s
    Board mode *always* supplies `pcb_path` to `freecad_generate_enclosure`, meaning the enclosure
    itself is *always* built via the file-based `kicad_pcb_import.extract_board_outline(pcb_path)`
    path in every real UI-driven call -- never the live kipy path. For the board overlay's own local
    origin to actually match the enclosure it's composited inside, it must derive from that exact same
    file-based source, unconditionally. Self-corrected before writing any code; reflected in both the
    real implementation (`daemon.py`'s `kicad_export_board_glb`) and its own test suite
    (`test_002_never_touches_the_live_kicad_bridge_outline_even_when_a_connection_is_available`
    explicitly asserts `kicad_bridge.get_board_outline` is never called).
    *   *Impact:* Simpler than the original plan (one lookup path, not two), and correctness-motivated
        rather than a shortcut -- the plan's own "Real, named gap" callout about live-mode's
        coordinate convention never having been directly cross-checked is now moot, since live mode is
        never used for this route at all.
*   **Deviation 2: the plan's own live-vs-file cross-check verification step no longer applies.** The
    approved plan's Verification section called for confirming live mode's coordinate alignment
    specifically, "since that's the real, named unverified gap." Per Deviation 1 above, live mode is
    never reached by this route, so that specific check is no longer meaningful -- the real remaining
    unverified gap is the plain click-through named in this file's own Testing Requirements Matrix
    above (does the board visually land in a plausible spot inside the enclosure), not a live-vs-file
    coordinate discrepancy.
*   **Deviation 3: fixed a pre-existing, unrelated CI-flaky test found while shipping this context,
    out of scope but blocking.** `TestFreecadGenerateEnclosureRoute.test_004_no_longer_accepts_
    project_name_or_saves_anything` (`test_daemon.py`, added by `CTX-311.13`, untouched by this
    context's own diff) calls `daemon.freecad_generate_enclosure(height=20)` -- board-driven mode,
    since no `width`/`depth`/`pcb_path` is given -- without mocking `daemon.kicad_bridge.get_board_
    outline`/`get_mounting_holes`, unlike its own sibling tests `test_002`/`test_003` right above it
    in the same class, which do. It silently depended on a real, live KiCad connection: it passed
    locally against a real open KiCad session, failed in this PR's own CI (no KiCad there at all,
    "Connection refused"), and cross-referencing `CTX-311.13`'s own PR #151 CI history shows the exact
    same test/job combination failed there too before a rerun happened to pass -- a real, pre-existing
    flake, not something this context's diff introduced. Fixed by adding the same two mocks its
    siblings already use, matching the established pattern in this class rather than inventing a new
    one.
    *   *Impact:* One test file changed outside this context's own stated scope
        (`services/python-daemon/tests/test_daemon.py`), same file this context already touches for
        its own `TestKicadExportBoardGlbRoute` tests. No behavior change to any route -- test-only.
