# CTX-308.11: Implementation Context: Preview Scaling/Enlarge + currentProject Wiring Fix

> **Spec Reference:** Links to [SPEC-308](../specs/SPEC-308-footprints-schematic-advisor.md)

Two real bugs found in the same live-testing round, right after `CTX-306.7`/`CTX-308.9`/`CTX-308.10`
shipped: (1) a real screenshot showed the symbol preview SVG cropped/overlapping instead of scaled
to fit its box; (2) real follow-up feedback -- "i dont see how to change the footprint linked... what
happened to the footprint search?" -- traced to a real wiring bug that silently dropped
`currentProject` on the most common Part Detail entry point, hiding `CTX-308.9`'s own per-project
override controls (and every other `currentProject`-gated feature) from anyone reopening an
already-saved Part from the Project Parts list.

## 1. Feature Definition & Execution Plan

### Phase 1: Fix the SVG preview scaling (the reported visual bug)
*   [x] Root cause: the preview containers used `max-h-64 overflow-auto` with `[&_svg]:h-auto
    [&_svg]:w-full` -- if the SVG's own real-world-unit intrinsic aspect ratio made the scaled
    height exceed the box, `overflow-auto` clipped/scrolled instead of shrinking to fit, producing
    exactly the cropped, overlapping-text screenshot reported.
*   [x] Fix: a **fixed** height (`h-64`, not `max-h-64`) with `overflow-hidden`, and both `[&_svg]:h-full
    [&_svg]:w-full` (not `h-auto`) on the svg -- this lets the browser's own default SVG
    `preserveAspectRatio="xMidYMid meet"` behavior do the real scale-to-fit-and-center work using the
    exported SVG's own `viewBox`, standard, well-established web-platform behavior that needed no new
    library or hand-rolled aspect-ratio math.

### Phase 2: "Resize the view" / click-to-enlarge
*   [x] Both preview thumbnails are now real `<button>`s (`cursor-zoom-in`, a real `aria-label`/
    `title`) that open a shared enlarged-view modal (`fixed inset-0` overlay, real `role="dialog"`/
    `aria-modal`) showing the same SVG scaled to fit a much larger area. Closable via its own Close
    button, clicking the backdrop, or Escape -- a real, if simple, alternative to a hand-rolled
    resizable panel, which is more machinery than the actual complaint ("the thumbnail is too small/
    cropped to read") needs.

### Phase 3: the real currentProject wiring bug (found while investigating the user's own
    follow-up question, not part of the original visual-bug report)
*   [x] Root cause, found by tracing every real render site of `<PartDetail>`:
    `ComponentDiscovery.tsx`'s own "reopen an already-saved Project Part" render site
    (`if (openedPartId) { ... <PartDetail initialPart={openedPart} /> ... }`) never passed
    `currentProject` through, unlike the sibling "freshly confirmed candidate" render site a few
    lines below it, which always had. This is the single most common way to revisit an already-saved
    Part (the "Open" button in a project's own Project Parts list) -- every `currentProject`-gated
    feature (`CTX-308.9`'s per-project footprint override chief among them) was silently invisible
    from this path, with no error, no visual sign anything was missing.
*   [x] Fix: one line -- `<PartDetail initialPart={openedPart} currentProject={currentProject} />`,
    matching the sibling render site's own existing shape exactly.
*   [x] A real, pre-existing test (`CTX-306.4`'s own "opening a project part shows its detail...")
    had unknowingly locked this exact bug in as expected behavior -- its own stub assertion checked
    for `'PartDetail stub for ATtiny85'` with **no** project suffix, which only ever passed *because*
    `currentProject` was never forwarded. Updated to assert the real, now-fixed
    `'PartDetail stub for ATtiny85 (project: test-project)'` text instead, with an explicit comment
    naming what the old assertion had silently been protecting.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (the significant one): a real bug was found and fixed that had nothing to do with
    the originally-reported visual complaint.**
    *   *Reasoning:* the user's own follow-up question ("i dont see how to change the footprint
        linked... what happened to the footprint search?") didn't match what `CTX-308.9`'s own
        shipped design should have produced (a project was open, per the user's own screenshot, so
        the override control should have been visible) -- tracing every real `<PartDetail>` render
        site directly, rather than assuming the design was simply confusing, found the actual cause.
    *   *Impact:* fixed at the source, with the specific pre-existing test that had locked the bug in
        as "expected" corrected to assert the real, intended behavior, and an explicit comment left
        so a future reader understands why that assertion changed shape.
*   **Deviation 2 (named honestly, not fixed here): footprint search *results* still show no image,
    only the final linked/overridden selection does (`CTX-306.7`'s own Phase 3 gap, still open).**
    *   *Reasoning:* the user's own follow-up explicitly re-raised this ("having suggestions with
        footprint images") in the same message as the bug above -- real, valid, and worth doing, but
        a distinct, separate piece of backend work (rendering a preview for a candidate that isn't
        yet a `library_store` record, e.g. an installed KiCad library path or an unimported community
        candidate) from either bug fixed in this context.
    *   *Impact:* named here as real, scoped follow-up work rather than silently bundled in or
        silently dropped -- not started in this context.
