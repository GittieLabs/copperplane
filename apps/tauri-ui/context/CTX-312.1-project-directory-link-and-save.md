# CTX-312.1: Project directory link, Save Project manifest, and portable state

> **Spec Reference:** Links to [SPEC-312](../specs/SPEC-312-application-shell-project-portability-persistence.md)

`SPEC-312` resolves three connected `ROADMAP.md` §3.3 questions. This context covers two of them --
Save semantics and project portability -- as the persistence/portability core. The native
`File`/`Edit`/`View`/`Help` menu (the third question) is deliberately deferred to its own
`CTX-312.2`: it's independent Rust-only work with no schema changes, and doesn't need to block this.

**The real, previously-unbuilt gap this closes, found during research, not assumed:** `SPEC-304`
§2.1 already *describes* a `Project` as holding "a link to a KiCad project directory on disk," but
`SPEC-304`'s own Non-Goals explicitly deferred *resolving* where that directory lives, and neither
`CTX-304.1` nor `CTX-305.1` ever built it. Today `library_store.py`'s real `Project` record is just
`{name, schema_version}` -- no directory field exists at all, and every area tab
(`EnclosurePanel.tsx`, `BoardAdvisor.tsx`) independently picks its own `.kicad_pcb`/`.kicad_sch`
file via plain component-local `useState`, lost on tab switch, unmount, or restart.

## 1. Feature Definition & Execution Plan

### Phase 1: `Project.directory` -- the foundational link
*   [x] `library_store.py`: `save_project` accepts and persists an optional `directory` field --
    `None`/absent means a project not yet linked to any real files (today's behavior, unchanged).
    A storage-root pointer record always exists (`{name, directory, schema_version}` when linked,
    the full manifest when not) so `list_projects()`/`load_project()` can always discover a link.
*   [x] `lib/projects.ts`: `Project` interface gains `directory?: string`; a real
    `pickProjectDirectory` wrapper reuses the already-available `openDialog({directory: true})`
    (`@tauri-apps/plugin-dialog` -- confirmed already supported, no new Rust command needed).
*   [x] A real "Link to folder…" UI trigger -- see Deviation 1 below for where it actually landed.

### Phase 2: Save Project -- a real manifest, not a name-only stub
*   [x] `project.json`'s real saved shape grows: `directory`, a per-area-tab summary of the most
    recent real generated result (`last_results.enclosure`: wall/clearance/standoff params + real
    `glb_path`/`step_path`), and a real export history array (`export_history`, one entry per real
    `freecad.export_enclosure` call).
*   [x] A real "Save Project" action (button, wired now even though the menu itself is
    `CTX-312.2`'s own scope) calls `project.save` with the current in-memory state.
*   [x] Generate itself keeps its existing no-save-side-effect behavior (`CTX-311.13`/`CTX-311.2`'s
    precedent) -- Save Project only ever reflects the last real Export, never an unsaved Generate.
*   [x] See Deviation 2 below: export history is persisted automatically the moment a real Export
    succeeds, not deferred to a separate manual Save click.

### Phase 3: Portable state -- move it into the project's own directory
*   [x] When `Project.directory` is set, `project.save` writes `project.json` to
    `<directory>/.hardware-agent-studio/project.json` instead of
    `<storage_root>/projects/<name>/project.json`. Unset stays on today's `storage_root` fallback.
*   [x] `load_project`/`list_projects` gain a real, honest error (`ProjectDirectoryMissingError`)
    for a project whose `directory` no longer exists or was moved -- a clean error, not a bare
    exception.
*   [x] Existing `storage_root`-based projects keep working unchanged until a user explicitly links
    a directory -- no forced migration. `project_directory()` (the Export dialog's own real default,
    `CTX-311.13`) now returns the linked directory once one exists, falling back to the original
    storage-root path otherwise.

### Phase 4: Tests + real verification
*   [x] Real tests for `directory`-set vs. `directory`-unset `save_project`/`load_project`, and the
    missing-directory-on-load error path -- verified directly against a real filesystem (real
    `tempfile.TemporaryDirectory`, not mocked) before the formal test suite was written.
*   [x] Frontend tests for the new "Link to folder…"/"Save Project" UI and the real, full Export
    click-through that persists `export_history`.
*   [ ] **Not verified**: an actual human click-through in the running app. Backend logic was
    verified against a real filesystem; frontend flow was verified via `App.test.tsx`'s full render
    + click simulation, mocked at the IPC/dialog boundary -- consistent with, not beyond, this
    file's own established testing depth for this describe block. Nobody has yet linked a real
    folder in the real running app and looked at the real file it wrote.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: "Link to folder…" / "Save Project" landed in a new project-scoped header row in
    `App.tsx`, not the Rail as the approved plan tentatively suggested.** The Rail (`Rail.tsx`) lists
    *all* projects for selection -- it has no concept of the *currently open* one, and neither action
    makes sense without a real project already selected. `Overview` was considered instead, but
    `SPEC-312`'s own Non-Goals deliberately leave Overview's eventual purpose (per-project dashboard
    vs. cross-project landing page) undecided; entangling a real, already-scoped action with a
    surface whose future shape isn't settled risked having to un-entangle it later. Landed instead as
    a new row shown above every area tab in `App.tsx`, visible regardless of which tab is selected --
    genuinely project-scoped chrome, not specific content.
*   **Deviation 2: export history is persisted automatically the instant a real Export succeeds, not
    deferred to a separate "Save Project" click, as the plan's own Phase 2 text originally implied
    ("Save Project... calls project.save with the current in-memory state").** Real risk found while
    implementing: `CTX-311.13`'s Export is already the one real "keep this" action -- if recording
    that it happened depended on the user *also* remembering to click Save afterward, the real file
    on disk and the manifest's own record of it could silently disagree. `EnclosurePanel.tsx` now
    reports a real `onExportSuccess` event straight from the point `handle.result` actually resolves;
    `App.tsx`'s own handler appends the entry and calls `saveProject` immediately. The plain "Save
    Project" button still exists for on-demand saves (e.g. after linking a directory), but export
    history no longer depends on it. Named explicitly here since it's the one place this context's
    real behavior differs from what the approved plan literally said, not a silent improvement.
*   **Deviation 3: `daemon.py`/`project.save`/`project.load` route signatures needed zero changes.**
    The approved plan named these as possibly needing new pass-through params; in practice both were
    already thin, fully-transparent wrappers around `library_store.py`'s own dict-based functions
    (`project_save(project: dict) -> dict: return library_store.save_project(project)`), so every new
    field (`directory`, `last_results`, `export_history`) flows through unchanged. Only
    `project_get_directory`'s own docstring was updated to reflect its real, changed return value
    once a project is linked.
*   **Not a deviation, but named per this repo's own norm ("state what was not verified"):** the real
    click-through in the running app remains unverified -- see Phase 4's own checklist above.
