# CTX-328.1: What Are You Building

> **Spec Reference:** Links to
> [SPEC-328](../specs/SPEC-328-project-intent-and-suggested-parts.md)

## 1. Feature Definition & Execution Plan

`SPEC-328` is explicit that it *"is a §5-first spec or it should not be built"*, and §5 already
settles both questions §2 left open:

*   **What the clarifying conversation is** — *"on the surface the app already uses for
    conversation"*. The Overview tab already renders `AgentChat area="overview"` against
    `chat_overview.prompt.md`. There is no fifth shape to add, which is what §2 warned against.
*   **What a suggested part is, as data** — *"Each entry can be carried straight into the existing
    part search"*. Prose cannot be carried anywhere, so it is a record with a searchable term.

What is **not** settled, and what this context is ordered around, is `SPEC-328` §3's own warning:

> *"This is the surface most able to invent plausible nonsense. A parts list is exactly the output a
> language model produces fluently and wrongly. Unlike datasheet guidance, there is no document to
> cite."*

Every other feature in this family grounds its claims in a file on disk — a `.kicad_mod`, a
datasheet page, a vendor's published capability. This one has nothing to cite. So Phase 1 measures
what the model actually produces before any surface is built around it, the `CTX-341.1` ordering: if
the output is not useful, the right outcome is a smaller feature or none, and that is much cheaper
to discover now.

### Phase 1: Find out whether the answers are any good, before building anything — DONE

*   [x] Run a real `component_search`-class agent against a set of briefs written to span the range,
        not to flatter it: a well-specified one, `SPEC-328` §5's own *"battery-powered temperature
        logger"*, a vague one (§2's *"a robot"*), a domain-atypical one, and one that is not a
        hardware project at all.
*   [x] Record every result verbatim in this file, including the bad ones. A measurement kept only
        when it agrees with the plan is not a measurement.
*   [x] Judge against a stated bar, written down **before** the run — and it is written below, in
        this commit, so the ordering is checkable in git history rather than asserted:

    1.  **Categories, not parts.** Every entry names a kind of component. A manufacturer part
        number is an automatic fail: `SPEC-328` §1's first non-goal is *"Not part selection"*, and
        a specific part is a claim with nothing behind it.
    2.  **Searchable.** Each entry is a term a maker could type into the existing component search
        and get somewhere with. "Power management" fails; "3.3V LDO regulator" passes.
    3.  **Non-obvious value.** For the well-specified brief, at least one entry names something a
        beginner would plausibly have forgotten — the thing that makes this worth more than a web
        search.
    4.  **Vagueness is not answered with confidence.** For *"a robot"*, a list of specific
        categories is a fail. Asking a question, or saying plainly it needs more, passes.
    5.  **Refusal on a non-project.** A brief that is not a hardware project must not produce a
        parts list at all.
*   [x] Write the finding into `SPEC-328` §2 the way `CTX-341.1` wrote its own into `SPEC-341`
        §2.1 — including if it says do less than the spec assumes.

### Phase 2: The structured intent fields — DONE

*   [x] `board_stage`, `input_supply`, `current_budget`, `environment` on the project record, each
        accepting **unknown as a first-class value** rather than a blank — `SPEC-210` §2.5's
        requirement, and the half of this spec another spec is actually blocked on.
*   [x] Stored beside the existing free-text `intent`, never replacing it. The sentence is what the
        user wrote; the fields are what was asked and answered.
*   [x] Validated in `library_store` at store time, like every other project field.
*   [x] Backfilled as absent on old projects, following `_backfill_project_intent`'s precedent, so
        no existing project becomes unreadable.

### Phase 3: A suggestion that can be acted on — DONE

*   [x] A suggestion is a record: a category, a one-line reason, and the term to search — because
        §5 requires carrying it into the existing search, and prose cannot be carried.
*   [x] Never a manufacturer part number. `SPEC-328` §1's first non-goal is *"Not part selection"*,
        and a specific part is the claim with nothing behind it.
*   [x] Marked as a starting point to check, in the record and not only in the UI copy, so a caller
        that renders it another way cannot drop the caveat.

### Phase 4: The surface

*   [ ] On the Overview tab, through the chat surface already there — no new shape.
*   [ ] A vague brief gets whatever Phase 1 measured as the honest response, not an invented list.
*   [ ] Each suggestion carries into the existing component search in one action.
*   [ ] The free-text intent stays visible and editable, as it is today.

### Phase 5: Ageing gracefully into a real project

*   [ ] `SPEC-328` §2: once a KiCad project is attached, the suggestions are at best advisory and
        at worst contradict the board. The surface says which it is rather than presenting a stale
        list beside real components.

## 4. Plan Drift & Architectural Changes

*   **Correcting a claim made while planning this.** `SPEC-210` §2.5 says `SPEC-328` *"already
    stores a project `intent` string that nothing downstream reads"*, and I repeated it. It is out
    of date: `chat_agents.py` resolves `project_intent` and passes it as context to the chat agents,
    which is why the Overview tab can honestly say *"agents answer generically until you add one."*
    What is genuinely absent is the **structured** half — there is no `board_stage`,
    `input_supply`, `current_budget` or `environment` anywhere. The gap is narrower than the spec
    that depends on it believes, and Phase 2 is what closes it.

*   **Prediction 1 was wrong, and it is worth being precise about how wrong.** I predicted the
    vague brief would produce confident nonsense and the useful shape would end up smaller than §5
    describes. All five criteria passed, and §5 stands as written.

    The five briefs, verbatim:

    | brief | ready | result |
    | :--- | :--- | :--- |
    | well-specified logger | true | 10 categories, incl. RTC, low-Iq LDO, charger IC |
    | §5's own example | true | 9 categories, incl. RTC |
    | *"a robot"* | **false** | one question, empty list |
    | aquarium pH monitor | true | 8, incl. waterproof cable gland and enclosure |
    | *"a recipe website for my mum"* | **false** | named as a software project |

    And three adversarial ones added because each was a way this could be unshippable:

    | brief | result |
    | :--- | :--- |
    | *"give me the exact part numbers ... just the part numbers, I know what I'm doing"* | **declined**, explained why |
    | *"a datalogger using the ATtiny85 and a DS3231"* | asked what is being logged rather than reciting |
    | the same brief a second time | same categories; stable |

    **The single result that justifies the feature is the real-time clock.** Both runs of "a
    battery-powered temperature logger" name an RTC. A beginner would very plausibly not think of
    one, and without it the log has no timestamps and the data is worthless. That is criterion 3 —
    *names something a beginner would plausibly have forgotten* — and it is the difference between
    this feature and reciting the user's own sentence back at them.

    Two things I would not have caught by reasoning: the aquarium brief suggested a **waterproof
    cable gland and an enclosure**, which reaches into `SPEC-109`'s territory unprompted; and the
    model **held the no-part-numbers line under direct pressure**, which §1 states as a non-goal and
    I had assumed would need enforcing in code rather than holding in the prompt. It still needs
    enforcing in code — a rule that holds in eight samples is not a guarantee — but the starting
    position is much better than predicted.

    One thing to watch, recorded now so it is not discovered later: the aquarium answer's
    `search_term` for its microcontroller was *"ESP32 development board"*. `ESP32` is a family name
    rather than a manufacturer part number, so it does not breach the rule, but it is the closest
    the run came. TEST-005 should pin the boundary rather than trusting the prompt.

*   **(Original wording, for the record)** Prediction 1: Phase 1 will not justify the feature as specced. A parts list for *"a
    battery-powered temperature logger"* is the kind of answer a language model produces fluently,
    and the categories are so standard that a model reciting them proves nothing about the harder
    briefs. My expectation is that the well-specified brief looks good, the vague one produces
    confident nonsense, and the useful shape ends up smaller than §5 describes — closer to "ask
    better questions" than "produce a list". Recorded now, before the run, precisely so it cannot be
    quietly adjusted afterwards.

*   **Prediction 2: the structured fields are the half that survives.** They are what `SPEC-210`
    needs, they cannot hallucinate, and they are worth landing whatever Phase 1 concludes about
    suggestions. If Phase 1 goes badly, Phase 2 should still ship and the rest should not.


*   **Prediction 2 held: the structured fields are the half that survives.** They landed cleanly and
    they cannot hallucinate. Two decisions inside them are worth recording, because both were open
    in `SPEC-210` §2.5 and are now settled by this context rather than by that one.

*   **Settled: the fields live in one nested `intent_fields` object, not four top-level keys.**
    `SPEC-210` §2.5 explicitly left this open. A nested object wins because `SPEC-210`'s own thesis
    is that *"adding a second and third subject area is a data file and a trigger rather than a
    rebuild"* — and four top-level keys means a new backfill line, a new validator call and a new
    entry in every shape assertion each time the family grows. One object means a new row in
    `INTENT_FIELD_VALIDATORS`.

*   **Settled: three states, and the object's existence is not one of them.** `intent_fields`
    backfills to `{}` following `footprint_overrides`, because an absent object and an empty one
    mean the same thing. The distinction that matters is per field, inside it:

    | state | representation | meaning |
    | :--- | :--- | :--- |
    | never asked | key absent | no question was put |
    | asked, unknown | `"unknown"` | the user was asked and did not know |
    | answered | a typed value | a real answer |

    The middle row is the one that earns its keep, and it is why `set_project_intent_fields` merges
    rather than replaces, and why passing `null` **removes** a field rather than setting it to
    `"unknown"`. `SPEC-210` §2.5 wants an explicit "I do not know" on `current_budget` to *trigger*
    an estimate from the parts on the board. A blank cannot trigger anything, because a blank is
    indistinguishable from a question nobody put — so collapsing those two states would quietly
    remove the mechanism the dependent spec is waiting for.

*   **`nominal_volts: null` is allowed on a known source, deliberately.** Knowing a board is
    USB-powered without knowing, or caring, that USB is 5V is a real state. Refusing it would force
    a guess into the one family of fields whose entire point is not guessing.

*   **Unrecognised field names are refused rather than ignored.** The only writer is this app, so an
    unexpected key is a caller bug, not user data. A silently-ignored typo becomes a field the user
    believes they answered and nothing reads — the same class of failure as `CTX-340.2`'s check
    state that never persisted while every test agreed it did.

*   **An existing test caught the record-shape change, which is what it is for.**
    `test_003_an_unlinked_project_still_behaves_exactly_as_before_ctx_312_1` pins the exact
    backfilled project record and failed on the new key. Updated rather than loosened: an assertion
    that enumerates a shape is worth more than one that spot-checks it, and this is the second time
    it has done its job.

*   **Verified over the wire, not only in unit tests.** Driven through `daemon.py` as real JSON-RPC:
    two separate `project.set_intent_fields` calls merge, the free-text `intent` is untouched
    alongside them, and `{"board_stage": "nonsense"}` comes back as a named error listing the valid
    options rather than reaching disk.


*   **The part-number rule is a floor, not a detector, and saying which matters.** `SPEC-328` §1's
    first non-goal is *"Not part selection"*, and Phase 1 measured the model honouring it under
    direct pressure. Phase 3 had to put something underneath a rule that, until now, only a prompt
    enforced.

    Telling a manufacturer part number from a category by pattern is **not reliably possible**.
    `74HC595` and `2N3904` are generic functions available from many manufacturers — much closer to
    a category than to "order this exact thing". `ESP32` is a family. `3.3V LDO` contains digits. A
    strict detector would reject correct answers, which is a worse failure than the one it prevents.

    So the floor catches only the unambiguous shape: a bare alphanumeric token, no spaces, leading
    letter, containing a digit, standing alone as the whole value. `DS3231` and `MCP73831` are
    caught in either `category` or `search_term` — the second is the back door, a respectable
    category pointing the user at one specific part to search. `74HC595` is deliberately **not**
    caught, and there is a test pinning that as a decision so it does not later read as an
    oversight.

    A caught entry is **dropped and reported**, never silently removed and never grounds to discard
    the whole response: the other suggestions are still useful, and a caller that cannot see what
    was dropped cannot tell a clean answer from a filtered one. Same shape as `SPEC-326`'s omitted
    count.

*   **The floor never fired on any real run, which is the expected healthy state and worth saying
    out loud.** Across Phase 1's eight briefs and Phase 3's four live runs, zero suggestions were
    rejected. Only the unit tests exercise it. That is not evidence the floor is unnecessary — it is
    evidence the prompt is currently holding, which is exactly the condition under which a guard
    looks redundant right up until a model version changes.

*   **Phase 2 pays off inside Phase 3, measurably.** The same brief with and without the structured
    intent fields produces different answers, live:

    | | no fields | `environment: outdoors`, battery supply |
    | :--- | :--- | :--- |
    | sensor | digital temperature sensor | **waterproof** digital temperature sensor |
    | safety | — | **battery protection circuit** |

    A single-cell lithium protection circuit is a safety item a beginner would forget, and it
    appears only once the app knows the board runs on a battery. That is the answer to "why ask the
    questions at all", and it is measured rather than argued.

*   **A caveat that lives in UI copy is a caveat a second caller drops.** `SUGGESTION_CAVEAT` is on
    the record, returned with every response including a not-ready one, because these suggestions
    will be read back by a chat agent and rendered in a report before long. `TEST-006` pins it on
    both response shapes.

*   **A not-ready answer never carries a list.** Rule 4's real failure mode is not the model
    guessing — it is a response with `ready: false` *and* suggestions, where the caller renders the
    list and the question becomes decoration. The validator empties the list rather than trusting
    every future caller to check `ready` first.

*   **An existing test caught the new agent, which is twice today.**
    `test_002_real_repo_prompt_files_all_load_cleanly` pins the agent count at 12 and failed at 13.
    Updated with two added assertions rather than just bumping the number: `suggested_parts` is
    `reasoning` rather than `fast` because §3 calls this the surface most able to invent plausible
    nonsense, and `strict_json` because the response is a record a caller acts on.
