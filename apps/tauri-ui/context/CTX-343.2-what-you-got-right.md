# CTX-343.2: What You Got Right

> **Spec Reference:** Links to
> [SPEC-343](../specs/SPEC-343-the-guided-path.md)

## 1. Feature Definition & Execution Plan

`SPEC-343` §2.6 left one question open: what the guided path says when nothing is wrong. It was left
open because `SPEC-210` §2.3 sets a bar generic praise cannot clear — *"telling a user their design
is good is worthless unless the app knows what the bad version would have been."*

**It does know.** A silent pack is silent for a computed reason, and that reason was being calculated
and discarded. `led_series_resistor` says nothing about the maintainer's board because `D1`'s anode
is on `Net-(D1-A)` and so is `R1`. Reported, that is not praise — it is a fact about their board,
naming their parts, teaching the thing they got right.

Chosen over a plain *"nothing is wrong"* because teaching is the point of this app and because that
sentence is a claim this app cannot support: it checked what it can check, and a beginner reads it as
*my board is good*.

### Phase 1: A pack can report what it cleared

*   [x] `considerations.cleared()` — a `computed` claim in `satisfied` state, with the same trigger
        discipline as everything else. Praise anchored to nothing is exactly the generic praise
        `SPEC-343` §3 says is worse than silence.
*   [x] `raisable` excludes cleared items, and `cleared_items` is its own accessor rather than a
        filter every caller must remember to apply.
*   [x] **A pack whose trigger is simply absent reports nothing.** A board with no LEDs has learned
        nothing from *"no LED is missing a resistor"* — true, useless, faintly absurd.
*   [x] `led_series_resistor` reports its silence, which it was already computing.

### Phase 2: The surface — DONE

*   [x] One cleared item at a time, per `SPEC-343` §2.7's first constraint: the `complete` state is
        where a finished project sits forever, and a wall of *"here is everything that is fine"* is
        the overload this whole spec exists to avoid.
*   [x] Paired with what was **not** checked. `complete` is precisely where a novice mistakes
        *checked* for *correct*.
*   [x] Rendered beside the reading rather than replacing it.

## 4. Plan Drift & Architectural Changes

*   **This is a contract change, not a string, and it was accepted deliberately.** Packs returned
    only what they raised; every future pack must now also return what it cleared and why. Worth it
    on its own terms: a pack that can explain its silence is a pack whose reasoning can be read back,
    which helps whoever debugs the next false positive — and this session produced three.

*   **The cathode case is the one that would have shipped.** `led_series_resistor` fired on `GND`
    once already, and the mirror image is subtler: a net carrying only a cathode has no anode, so
    there is nothing it cleared, so praising it would be exactly as wrong as flagging it was. It is
    easier to miss because **a compliment reads as harmless** — nobody checks the praise for false
    positives. Pinned as `TEST-005`.

*   **Two distinct live-LLM tests flaked today, and that is a class rather than two incidents.**
    `test_002_real_google_chat` asserts `usage["output_tokens"] > 0` against a real Google call that
    intermittently omits it. `test_001_real_extraction_and_validation_succeeds_for_a_real_part` asked
    for `ATtiny85` and got `ATtiny85-20PU`, a package variant — a correct answer to a question whose
    answer is not fixed.

    Both pass on re-run, both are invisible to CI because it has no API keys, and both assert on
    variable output from a real model. That combination — fails only on a maintainer's machine,
    passes when re-run — is the shape of a test that gets dismissed rather than read, which is what
    `ci-flake-read-the-failing-attempt` exists to prevent. Neither is touched by this branch.


*   **`project.considerations` returns both halves in one call**, deliberately. §2.7's reinforcement
    *is* the finding that was not raised, so computing them separately would run every pack twice to
    get two views of one answer.

    `checked` names the packs that actually ran, which is what keeps the *"what was not checked"*
    line honest as packs are added — derived from the registry rather than written once and left to
    rot.

*   **The route is guarded on all four modules it needs** — the project record, the project resolver,
    the netlist export and the schematic reader. `CTX-210.1` learned this the expensive way: a route
    registered on fewer guards than it needs exists whenever those import, and fails with a bare
    `AttributeError` when the others do not.

*   **My component broke two of `App`'s tests, and the mechanism is worth writing down.**
    `projectConsiderations` goes through `submitJob`, which `App.test.tsx` mocks with queued
    one-shot responses. Mounting Overview consumed the response the chat tests had queued for
    themselves, so the reply they asserted on never arrived — and the visible symptom was *"unable to
    find the text 'Pin 3 is a GPIO pin'"*, which points nowhere near the cause.

    Any component that calls a mocked transport on mount steals from every test that queues
    responses for that transport. Stubbed in `App.test.tsx` with the reason, since those tests are
    about chat and navigation.

*   **I invented a module name in the degraded-module map and the parity test caught it.** I added
    `structural_checks_direct` to describe an import that never calls `_note_degraded` under that
    name — `structural_checks` is already reported through `chat_agents`. The test compares the map
    against the daemon's real `_note_degraded` calls in both directions, so a description for a
    module that cannot degrade fails exactly as loudly as a module with no description. That is the
    right design and I would not have thought to build it.

*   **Verified over real JSON-RPC**, not only in unit tests: `project.considerations` against the
    maintainer's own linked project returns `R1` needing attention and `Net-(D1-A)` cleared, with
    `checked` naming both packs.
