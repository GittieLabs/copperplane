# CTX-331.1: Enclosure Fit Review

> **Spec Reference:** Links to [SPEC-331](../specs/SPEC-331-enclosure-fit-review.md)

Turns the Enclosure review back on, answering whether the parts on the board fit the box that was
generated.

## 1. Feature Definition & Execution Plan

### Phase 1: Give the agent real, live fit data ✅

*   [x] `_assemble_context`'s enclosure branch runs `component_envelopes` against the linked
        project's board, the same way `_check_status_note` runs ERC/DRC — so a review can never
        assess a box the user has already changed.
*   [x] The block states the minimum interior height, which component sets it, how many components
        have no known height, and the generated parameters if any exist.
*   [x] A project with no linked board, or no generated enclosure, says so as itself rather than
        producing a fit verdict.

### Phase 2: Teach the agent what a fit answer is ✅

*   [x] `chat_enclosure.prompt.md` is rewritten to match the data it actually has — it currently
        describes `kicad.get_component_heights`, removed on 2026-09-02.
*   [x] The prompt is explicit that restating the user's own parameters is not a finding, and that
        an `unknown` height means the answer is provisional.

### Phase 3: Re-enable the panel ✅

*   [x] The `NotBuiltPlaceholder` naming SPEC-331 is replaced by the real `ReviewPanel`.

### Not in this context

*   **Plan-area fit.** The generator sizes the box to the board's bounding box plus clearance, so
    the board fits in plan by construction. Reviewing it would be theatre.
*   **Standoffs** (`SPEC-330`) and anything needing real 3D shape — overhangs, connector cut-outs,
    lid clearance.

## 4. Plan Drift & Architectural Changes

**Deviation 1 — the fit block is measured live, which the spec proposed and this confirms was
right.** `last_results.enclosure` would have been the cheap source, and it is written only when an
enclosure is *generated* — so a user who changed the height and re-ran the review would have been
told about the previous box. That is exactly the staleness the ERC/DRC path was fixed for on
2026-09-02. The generated parameters are still read from storage, because they are a record of a
real generate rather than a measurement, and the prompt now says plainly that they can lag the form.

**Deviation 2 — `daemon` is imported inside the function.** `daemon` imports `chat_agents`, so a
module-level import is circular. The envelope measurement composes `kicad_board`, `kicad_bridge` and
`freecad_bridge` and belongs in `daemon`; re-implementing it here to dodge the cycle would have been
worse than a local import with a comment saying why.

**Deviation 3 — the prompt described data the agent had not had since 2026-09-02.** It still
promised `kicad.get_component_heights`, removed when it was found starving the review of its tool
rounds. Rewriting it was not optional polish: an agent told it can measure something it cannot is
how the enclosure review produced confident advice from nothing in the first place.

**Deviation 4 — the enclosure needed a deterministic fallback, and finding out why was worth more
than the fallback.** Driving the review through the frozen sidecar with a local model produced no
findings block, so it raised: `_findings_from_check_alone` returns `None` for any area without a
check. Reading the captured response was the useful part. The model had reviewed the enclosure by
describing *"a USB connector with a height of 4.7mm"* on a board that has none, with a wall
thickness and standoff height that were never generated — confident advice from no data, which is
the exact failure `SPEC-331` §1 exists to prevent, arriving while the fix for it was being written.

A weak local model is not evidence about the configured one, and this is not claimed as such. But
it is the argument for the floor: the enclosure now falls back to a finding built from the
measurement alone — *"the last enclosure generated is 16mm inside, and the tallest measured part
(BT1) needs 20mm"* — which is the example the roadmap named as the thing worth saying, produced
without asking a model anything.

**Deviation 5 — the prompt now names when an empty review is wrong, and that change is unverified.**
The first frozen-sidecar run returned `[]` for an enclosure that is 16mm inside with parts needing
20mm. The prompt now states that `[]` is wrong when the generated height is below
`fit.min_interior_height_mm` or any component is unmeasured — both things the user cannot check for
themselves, which is the reason the review exists.

Whether that helps is **not established**. The re-run returned two correct findings, but the debug
capture shows the model produced 8 characters, so those came from the fallback, not from the model.
A 1B local model is not a fair proxy for the configured one; all this run proves is that the floor
holds when the model says nothing useful.

**Verified as the user — closed 2026-09-03.** The maintainer ran the review in the app: it reported
that no enclosure had been created yet, and **that finding disappeared after he generated one and
re-ran it**.

The second half is the part that matters. It is direct evidence the review is measured per request
rather than read from `last_results.enclosure` — a stored result would have gone on reporting "no
enclosure yet" after one existed. That staleness was the defect nobody had noticed going in, and it
was confirmed fixed by watching a finding correctly go away.

**Still not verified:** the prompt change telling the agent when an empty review is wrong. The
frozen-sidecar re-run returned two correct findings, but the debug capture shows the model emitted
8 characters, so those came from the fallback. Whether that instruction helps a capable model is
untested. Nothing here has run on Windows or Linux. The fit block is verified against the maintainer's own board
(15.515mm, set by R2, 5 components unmeasured), but nobody has pressed Run Review on the Enclosure
tab and read what the agent makes of it.
