# CTX-311.11: Real root cause, not color: the camera's default near plane was larger than the enclosure

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

`CTX-311.10`'s azimuth fix shipped. The next real screenshot showed a nonsensical, pointed, notched
silhouette -- not a rectangular open-top shell at all -- and the user reported it directly: "when I
moved the enclosure, I noticed clipping or something that is allowing me to see inside by removing a
wall... could we change the light source or background... maybe it's the grey that is the issue."
Investigated instead of trusting the color hypothesis, since a lighting/color problem cannot make a
wall disappear or turn a rectangular silhouette into a pointed, notched one -- that is a geometry/
projection symptom, not a shading one.

## 1. Feature Definition & Execution Plan

### Phase 1: real root-cause investigation
*   [x] **Confirmed live**, not guessed: `new THREE.PerspectiveCamera().near` is `0.1` by real, verified
    default (checked directly against the actual installed `three` package in this repo, not assumed
    from memory). `EnclosureViewer.tsx`'s own `<Canvas camera={{ position, fov }}>` never set `near`/
    `far` explicitly, so every enclosure in this app has always used that real `0.1`-unit near plane.
*   [x] **The real scale mismatch**: post-`CTX-109.4`'s own real unit-scale fix, a real enclosure's
    `.glb` is routinely only `0.02`-`0.15` real meters across -- smaller than, or barely larger than,
    that `0.1`-unit near plane. Any camera position within `0.1` real units of a wall -- trivially
    reached by an ordinary scroll-to-zoom gesture, since `OrbitControls` also had no `minDistance` set
    -- clips straight through that wall. This exactly explains "clipping... allowing me to see inside
    by removing a wall," and the pointed/notched silhouette (a near-plane slicing through part of the
    real geometry at an angle produces exactly this kind of warped, self-intersecting outline under
    perspective projection, not the plain rectangular shell that's actually there).
*   [x] This was real, present, and waiting since this whole viewer's very first version -- not
    introduced by `CTX-311.10`'s own azimuth/polar changes. It only became visible once a user's real
    zoom gesture (or a specific camera angle interacting with real wall thickness) brought the camera
    close enough, which `CTX-311.10`'s new azimuth may have made more likely for this specific board,
    but did not itself cause.

### Phase 2: fix
*   [x] `computeCameraClipping(radius)` -- a real, pure function deriving `near`, `far`, `minDistance`,
    and `maxDistance` proportionally from the same real computed `radius` every other piece of camera
    framing in this file already uses (`computeFrame`'s own output), rather than a fixed absolute
    value tuned to one enclosure's own scale. `near = radius * 0.001` (far smaller than any real wall
    thickness), `far = radius * 1000` (generous headroom), `minDistance = radius * 0.15` /
    `maxDistance = radius * 20` (bounds on `OrbitControls`' own free-orbit zoom, so a user's scroll
    gesture can no longer push the camera inside the mesh at all, independent of the near-plane fix).
*   [x] Wired into the `<Canvas camera={{ ... }}>` prop (`near`/`far`, set once per real mount/
    remount, matching this same file's own existing "initial camera prop" convention) and into
    `<OrbitControls minDistance={...} maxDistance={...}>` (a real, reactive prop, updated every
    render -- correct immediately for a freshly loaded mesh of any real size).

### Phase 3: tests
*   [x] Direct, real unit tests on `computeCameraClipping`: a real, typical small-enclosure radius
    produces a real `near` smaller than both the object itself and the actual confirmed `0.1` default
    that was clipping through it; `far` comfortably exceeds the object's own scale; `minDistance`/
    `maxDistance` bound `OrbitControls`' own zoom to a sensible range that can never reach inside the
    real mesh; all four values scale proportionally with a larger real radius; a degenerate zero
    radius never produces a non-finite or non-positive value.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the user's own hypothesis (color/lighting) was heard, checked against the real
    evidence, and set aside rather than acted on directly.** A pointed, notched, wall-missing
    silhouette is not a shading artifact -- lighting and material color can make edges hard to see or
    a surface read too dark/bright, but cannot delete a wall or reshape a rectangular box's own
    silhouette into something else entirely. Recognizing that distinction before touching any color/
    light code avoided a real wasted round (color tweaks that would not have fixed a projection bug),
    the same kind of "verify against the real thing, not the nearest available knob" discipline this
    repo's own norms already ask for.
*   **Deviation 2: this bug likely predates this entire `CTX-311.3`-`CTX-311.10` chain and was simply
    never triggered by any of this session's own earlier verification, live or automated.** None of
    the real `freecadcmd`/`trimesh` measurements in `CTX-311.1`-`CTX-311.9` render a scene through an
    actual camera, so a near-plane clipping bug had no way to surface there; it took a real human
    zooming and orbiting the actual `<Canvas>` to find it. Worth recording plainly: geometry-level
    verification (does the mesh have the right dimensions) and rendering-level verification (does the
    camera correctly show that mesh) are genuinely different concerns, and this repo's own real
    `freecadcmd` tests only ever covered the first one for this feature.
