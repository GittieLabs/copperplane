# CTX-324.1: Model Listing & On-Demand Validate

> **Spec Reference:** Links to [SPEC-324](../specs/SPEC-324-model-identity-verification.md)

The whole of `SPEC-324`: two daemon routes, a combobox, and a Validate button. Small enough to land
in one slice because it needs no schema change — `ProviderRecord.models` still holds two strings.

## 1. Feature Definition & Execution Plan

### Phase 1: Listing and validation in the daemon

*   [x] `list_models(record, api_key)` returning `{supported, models, reason}`. A per-`kind` lister
    dict rather than an if-chain, so an unknown kind is a data question and a test can substitute
    one entry without patching import machinery.
*   [x] SDK imports are lazy and every failure is caught. A missing SDK, a bad key, an unreachable
    host and a server with no `/v1/models` are all ordinary states to report, not raise on.
*   [x] `validate_model(record, api_key, model)` returning `{valid, reason}`, built on `list_models`
    so it never sends a completion — an existence check costs no tokens.
*   [x] A provider that **cannot list** yields "could not check", never "invalid". Calling a model
    wrong because the server has no `/v1/models` would be worse than saying nothing.

### Phase 2: Two routes, both async

*   [x] `llm.list_models` and `llm.validate_model`, registered in `ROUTES` **and `ASYNC_ROUTES`**.
    Both make real network calls, and sync routes run inline in the daemon's request path —
    `CTX-314.2` records the real bug from getting this wrong, where a GitHub-calling route left out
    of that set blocked every other request while it ran.
*   [x] `_resolve_record_and_key` resolves through the same `migrate_legacy_config` /
    `_resolve_provider_records` path `llm.get_provider_records` uses, so the editor and these
    routes cannot disagree about what a record is.

### Phase 3: A combobox, and Validate

*   [x] `listProviderModels` / `validateProviderModel` in `settings.ts`, via `submitJob` because the
    routes are async-registered.
*   [x] The model fields become a combobox: a `datalist` of what the provider reports, and the input
    stays typeable. With no list available it degrades to exactly the plain text field that shipped
    before.
*   [x] A Validate button per field, disabled when the field is empty, reporting the daemon's reason
    verbatim rather than reducing it to a tick or cross.
*   [x] Listing is fetched on first focus, once. Nothing fetches at startup or on save.

### Not in this context

*   **Filtering or search over long lists** (`SPEC-324` §3). An OpenAI-compatible endpoint can
    return hundreds of entries; `datalist` gives the browser's own type-ahead for free, which is
    enough for now and not enough forever.
*   **Google's `retrieve` path.** `list` was probed and works; `retrieve` was not, so validation
    goes through `list` for every kind uniformly rather than special-casing on unverified behaviour.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — a test caught a real UX duplication, and the component changed rather than the
    assertion.** `TEST-009` failed with "found multiple elements" for the could-not-list notice.
    The cause was not the test: listing state is per **provider**, but the notice was rendered
    inside `renderModelField`, so it appeared once under the reasoning model and again under the
    fast model. Moved to the form level so it renders once. Worth recording because the easy fix
    was `getAllByText`, which would have locked in the duplication and called it passing.

*   **Deviation 2 — the routes had to be async, and that was a finding rather than a choice.** The
    plan assumed a simple synchronous route. Reading `daemon.py`'s dispatch showed sync handlers run
    inline in the request path, and `ASYNC_ROUTES`'s own comment records `CTX-314.2` finding
    exactly this bug for the community-library routes. Both new routes are network calls, so both
    are async-registered, which also settled the frontend shape: `submitJob`, not `dispatch`.

*   **Deviation 3 — Google's `retrieve` was not probed, so no kind uses it.** The SDK probe
    confirmed `models.list` on all three kinds and `models.retrieve` on two. Rather than
    special-case the two that have it and guess at the third, validation goes through `list`
    uniformly. Slightly less efficient for anthropic/openai; honest everywhere. Recorded because
    the spec's own §1 table shows the asymmetry and a future reader might otherwise assume it was
    overlooked.

*   **Non-deviation, checked rather than assumed:** the no-API-key guard would have blocked Ollama,
    which is a local server with no key and has a placeholder-key convention already in
    `llm_providers`. Caught while writing the guard rather than after; `TEST-004` pins both halves.
