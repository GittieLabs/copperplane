# CTX-319.8: Implementation Context: The Review Does Not Repeat the Check

> **Spec Reference:** Links to [SPEC-319](../specs/SPEC-319-ai-review.md). The header line at issue
> is `SPEC-340`'s interim cross-reference; the decision to keep two lists is
> [SPEC-341](../specs/SPEC-341-one-findings-list-per-area.md) (declined, 2026-09-09).

Seen on 2026-10-10 against a fresh production build (`npx @tauri-apps/cli@2.11.4 build --bundles
app`) on the tutorial board `Copperplane_Blink_LEDs`. PCB tab, "Review the board", Run Review. The
panel said:

> The board check (DRC) separately reports 5 problems on this board, listed under Board (DRC)
> above. This review does not repeat them.

and then its first five findings were exactly those five -- four "LED D1 pad N has too little
copper around its hole" annular-width findings and the unrouted GND -- each tagged as a DRC finding.
Only after them came the two the review exists for, marked "Not reported by ERC or DRC". The UI
promised something the content broke.

## 1. Feature Definition & Execution Plan

### Phase 1: decide which side is wrong
*   [x] **The header is the design; the content is the defect.** `SPEC-341` §1 says it in so many
    words -- *"The review deliberately lists only what ERC and DRC do not report, which is
    `SPEC-113`'s entire pitch"* -- and the maintainer declined merging the two lists on 2026-09-09.
    The DRC card above the review already lists and explains every one of those five. Changing the
    header to "this review repeats them" would have made the text true by making the product worse:
    the same five problems explained twice, by two LLM calls, in two places.
*   [x] **Why the content disagreed.** `_REVIEW_PROMPT` (since `43de735`, 2026-09-02) said: *"Every
    finding in the check block you were given is worth flagging: explain each one."* The check
    block carries KiCad's findings as `kicad-N` and ours as `copperplane-N`. The model did exactly
    what it was told. The header (`33fdd69`, 2026-09-08) was written six days later describing what
    the review was *supposed* to do, against a run where it happened to show 2 findings -- nothing
    enforced it.
*   [x] Confirmed the real board's check note, from source with real `kicad-cli`: `kicad-1..4`
    annular_width, `kicad-5` unconnected_items, `copperplane-1` SW1, `copperplane-2` D1. Exactly the
    report.

### Phase 2: enforce it on the id, not the wording
*   [x] `chat_agents.without_the_checks_own_findings(findings, area)`: in `pcb` and `schematic` (the
    two areas with a sibling ERC/DRC card), drops every finding whose `origin` is `kicad`. `origin`
    is already read off the `finding_id` the daemon generated (`_origin_of`, `CTX-113.2`), never off
    the model's prose.
*   [x] Applied on **both** of `review()`'s exits -- the parsed findings block, and the
    `_findings_from_check_alone` fallback used when the model answers without a block. The fallback
    was the worse offender: it converts the whole check, KiCad findings first.
*   [x] A finding citing both a `kicad-` and a `copperplane-` id is ours and stays (`_origin_of`
    already says so). A finding citing no id (`origin` None) is the model's own judgement and stays.
*   [x] `_REVIEW_PROMPT` now tells the model the opposite of what it said: `kicad-` findings are
    already shown and must not be listed; every `copperplane-` one must. The prompt is a request; the
    filter is the guarantee. Both, because a model spending its output on findings that will be
    dropped is wasted tokens and a worse explanation of the ones that matter.
*   [x] `chat.stored_review` applies the same filter on read. A review saved before this fix -- the
    maintainer's own tutorial project has one -- would otherwise keep showing the five under the
    header until someone happened to re-run it. Guarded on `chat_agents` being importable, because
    that route deliberately survives a build that lost the agent layer (`test_001e`).

### Phase 3: the header's count
*   [x] `BoardAdvisor` passed `violation_count + unconnected_count` as the sibling count. The board
    check also reports schematic-parity mismatches (`parity_count`), lists them in the DRC card, and
    the review now drops them too. Left alone, a board with parity problems would have them counted
    nowhere in the header. Added. The schematic side (ERC) has no parity kind.

## 4. Plan Drift & Architectural Changes

**1. The prompt, not the model, produced the duplicates -- and the header was never backed by
anything.** I went in expecting a model ignoring an instruction. The instruction said the opposite of
the header: explain *every* finding in the check block. The header was added six days after the
prompt and described intent, verified against one run that happened to show 2 findings. A sentence
in the UI that states a property of the content needs something in the code that makes it true.

**2. The first frozen `chat.review` probe could not fail, and I nearly counted it.** On the real
tutorial board through local Ollama (`llama3.2:1b`, the only no-key provider here), the fixed binary
returned exactly the two Copperplane findings. Then the *unfixed* binary returned the same two: the
1B model never mentioned the DRC findings at all, so there was nothing for the filter to remove. That
probe proved the route runs end to end in the frozen build and nothing more. The discriminating check
is TEST-013, which seeds the reported shape and reads it through each binary: 7 before, 2 after.

**3. Not verified: the real provider, in the real window.** Nobody has run "Review the board" in the
built app with the maintainer's real model since this change. The deterministic layers are
covered -- both review exits, the stored read, the frozen binary -- but the user-visible claim
("the five are gone and the two remain, under that header") has only been checked through
JSON-RPC, not by looking at the panel. That needs the keychain (a local build prompts for it on every
launch), so it is the maintainer's click.

**4. Known gap, left open on purpose: a model restating a DRC result without citing its id.** Such a
finding has `origin` None and survives the filter. Catching it would mean matching prose against
KiCad's descriptions, which is the guess about origin `CTX-113.2` exists to remove. The prompt now
tells the model to cite ids and not to list KiCad's findings; if this shows up in practice, the fix
is upstream of the filter (a stricter citation contract), not fuzzy matching here.

**5. Seen in passing, not touched: the review and the DRC card may not read the board under the same
rules when a board-house profile is set.** `kicad.check_board` runs DRC through
`fabrication_review.baseline`, which steps around a generated house `.kicad_dru`; `_check_status_note`
calls `kicad_cli.run_drc` directly. With a house file present, the review's notion of "what DRC
reports" could differ from the card's. Moot for this fix, because every KiCad-origin finding is now
dropped regardless of which rules produced it; worth knowing if the review ever starts reasoning about
DRC counts again.

**6. Two process notes.** The worktree has no `.build-venv`; the suite ran on the main checkout's
`services/python-daemon/.build-venv/bin/python` against this worktree's source, and the freeze built
a fresh `.build-venv` inside the worktree. And `develop` moved during the session (`94bd477`,
`CTX-408.7`) -- unrelated files, fetched before opening the PR.
