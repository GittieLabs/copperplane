# CTX-108.4: Wire SPEC-204's Confirmation Gate into the Inject Flow

> **Spec Reference:** Links to [SPEC-108](../../../services/python-daemon/specs/SPEC-108-kicad-write-path-footprint-symbol-injection.md)

**Numbering note:** `.2` stays reserved for schematic symbol injection (`CTX-108.1` Deviation 1);
`.3` already shipped the plain button this context replaces. This is `.4`.

**Real, current-state check before writing any code:** `CTX-108.3`'s own description of a literal
"Inject into Board" button is stale — `SPEC-302`/`CTX-302.1` refactored the trigger into the chat
surface's `inject` command (`apps/tauri-ui/src/App.tsx`'s `handleSend`, `command.type === 'inject'`
branch) some time after `CTX-108.3` shipped. This context targets the real, current code path, not
the button `CTX-108.3`'s prose describes.

**The gap this closes:** `CTX-204.1` built a real confirmation-gating policy in the daemon
(`agent.dispatch_tool`), but nothing in the frontend called it — the `inject` command still called
`submitJob('kicad.inject_component', ...)` directly, mutating the board unconditionally the instant
it recognized the word "inject." A gate nothing uses isn't a finished safety mechanism.

## 1. Feature Definition & Execution Plan

### Phase 1: `dispatchTool` -- a real client for `agent.dispatch_tool` ✅
*   [x] `apps/tauri-ui/src/lib/ipc.ts`: refactored `submitJob`'s job-handle construction into a
    shared `buildJobHandle<T>(jobId)` helper (pure extraction, no behavior change -- `submitJob`'s
    own callers and tests are unaffected).
*   [x] New `dispatchTool<T>(toolName, toolInput, confirmed = false)` calls `agent.dispatch_tool`
    and returns `ToolDispatchOutcome<T>` -- a real discriminated union tagged on `kind`
    (`'pending_confirmation' | 'dispatched'`), not two structurally-distinguished interfaces.
    **Real correction found by `tsc`, not predicted:** an initial version returned
    `PendingToolConfirmation | JobHandle<T>` as a plain union and let call sites narrow on
    `'status' in outcome`; `tsc` rejected the post-narrowing `.result` access because TypeScript's
    structural typing can't prove `JobHandle` *lacks* a `status` field just because its interface
    doesn't declare one. Fixed by giving both branches an explicit `kind` tag instead of relying on
    structural absence.

### Phase 2: Wire the `inject` command through the gate ✅
*   [x] `App.tsx`'s `ChatMessage` gains an `'awaiting_confirmation'` status (only on the `'inject'`
    variant) and a `pendingInput` field carrying exactly the proposed `tool_input`, captured at
    proposal time -- so confirming later re-sends the same schema even if the user has since
    generated a different one.
*   [x] The `inject` command handler now calls `dispatchTool('kicad.inject_component', toolInput)`.
    A `'pending_confirmation'` outcome sets the message to `awaiting_confirmation` and returns
    without touching `handle.result` at all -- no job exists yet to await. A `'dispatched'` outcome
    (shouldn't happen on the first call today, since `kicad.inject_component` is always gated, but
    the code doesn't assume that) proceeds exactly as before.
*   [x] New `handleConfirmInject(id)`: re-dispatches the message's stored `pendingInput` with
    `confirmed: true`, then awaits the real job exactly like the original direct-call code did.
    `handleCancelInject(id)`: purely local -- no daemon call, since the first unconfirmed call
    never started any work to cancel.
*   [x] `ChatMessageView` renders `awaiting_confirmation` with a real amber-bordered confirm card
    and **Confirm**/**Cancel** buttons, wired to the two handlers above via new required props.

### Phase 3: Tests, real verification, and closing SPEC-108's own flagged gap ✅
*   [x] `App.test.tsx`: `dispatchToolMock` added alongside the existing `submitJobMock`. `TEST-002`
    rewritten to assert the proposal step (pending, zero mutation, exact `tool_input` echoed back);
    two new tests (`TEST-002b`/`TEST-002c`) cover confirm (re-dispatches with `confirmed: true`,
    reports success) and cancel (zero additional `dispatchTool` calls, real "board not modified"
    message). `TEST-003` updated to assert on `dispatchToolMock`, not `submitJobMock`.
*   [x] Real verification, not just "tests green": `./node_modules/.bin/tsc -b` (a real type error
    caught and fixed mid-implementation, see Phase 1), `./node_modules/.bin/oxlint` (only the two
    pre-existing, unrelated `EnclosureViewer.tsx` warnings `CTX-108.3` already named), full suite
    `./node_modules/.bin/vitest run` -- 106/106 (3 new, 14 pre-existing in this file unchanged, all
    other files untouched), `./node_modules/.bin/vite build` -- clean.
*   [x] `SPEC-108` §5's own TODO -- flagged by `CTX-901.2` as pre-existing debt, explicitly deferred
    "for real the next time this surface changes" -- filled in for real here, describing the actual
    confirmation prompt this context ships, not an invented answer.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `CTX-108.3`'s literal "Inject into Board" button no longer exists.** Discovered
    by reading the real, current `App.tsx` before writing any code, not by trusting `CTX-108.3`'s own
    prose or the `ROADMAP.md` entry that (until this session) still described a button. `SPEC-302`/
    `CTX-302.1` had already replaced it with the chat surface's `inject` text command. This context
    targets that real, current path. `ROADMAP.md`'s stale wording is corrected in the closeout PR.
*   **Deviation 2: a TypeScript structural-typing gap, caught by `tsc`, not predicted in the plan.**
    See Phase 1 -- a plain `PendingToolConfirmation | JobHandle<T>` union let `.result` be accessed
    on a type that couldn't be narrowed, because `JobHandle`'s interface doesn't declare the absence
    of a `status` field. Fixed with an explicit `kind`-tagged discriminated union instead of relying
    on structural narrowing.
