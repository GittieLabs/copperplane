# CTX-319.1: Implementation Context: AI Review Backend Foundation

> **Spec Reference:** Links to [SPEC-319](../specs/SPEC-319-ai-review.md)

Phase 1: the daemon-side seam SPEC-318 §2.5 named but did not build. Reuses `chat_agents.py`'s own
`_dispatch()` (same router, agent config, tools, context assembly as chat) with a fixed internal
prompt and a read-only-filtered tool registry, returning a validated `ReviewFinding[]` instead of a
persisted turn. No frontend work in this phase -- `chat.review` exists as a real, callable daemon
route with real backend tests, unmounted anywhere in the UI yet (Phase 2+).

## 1. Feature Definition & Execution Plan

### Phase 1: `_dispatch()` gains an optional `tools` override
*   [x] `chat_agents._dispatch()` takes a new `tools: ToolRegistry | None = None` parameter,
    defaulting to the full registry -- `send()`'s own call site is unchanged, passes nothing.
*   [x] `_dispatch()`'s return dict gains `tool_calls_raw` (the untruncated, unparsed tool-call list
    already computed internally) alongside the existing digest-truncated `tool_calls` --
    `review()` needs the real, full `result` JSON `_mechanical_source_refs` re-parses itself, which
    the 200-char-truncated `tool_calls` entries would silently corrupt for any real payload.

### Phase 2: `tool_registry.build_tool_registry()` gains an `exclude` parameter
*   [x] `exclude: set | None = None` -- filters `TOOL_DEFINITIONS` at construction time. **Real
    finding, checked before writing any code:** `ToolRegistry` (upstream `agentflow`) has no
    `remove_tool` method, only `add_tool`/`add_dispatcher`/`dispatch`/`list_tools` -- confirmed by
    introspecting the installed class directly, so filtering has to happen at build time, not by
    building the full registry and removing from it after.

### Phase 3: findings extraction, mirroring the existing citation-extraction contract
*   [x] `_FINDINGS_PATTERN` / `_extract_findings(text) -> list` -- the `<<<FINDINGS>>>...
    <<<END_FINDINGS>>>` counterpart to `_CITATIONS_PATTERN`/`_extract_self_reported`. Same
    resilience contract: a missing or malformed block is an empty list, never a raised error.
    Per-entry validation (`severity`/`title`/`detail` well-formed) is `review()`'s own job, not
    this function's -- it only guarantees every returned item is at least a dict.

### Phase 4: `review()` -- the real route body
*   [x] `chat_agents.review(scope, scope_id, area, project_name=None, secrets=None, provider=None,
    model=None) -> list[dict]`. Fixed internal `_REVIEW_PROMPT` (one, area-agnostic instruction --
    per-area framing lives in each prompt file's own new section, matching how "Citation format"
    already varies its citable-kind subset per area without needing a second prompt file).
    `history=[]` always -- a review has no turn to remember and must not see an unrelated question's
    own framing. Builds its tool registry via `build_tool_registry(exclude=CONFIRMATION_REQUIRED_TOOLS)`.
    Never calls `append_thread_turn` -- a review is a flow step with a typed result
    (`PRODUCT-PLAN.md` §3.3), not a conversation turn.
*   [x] Per finding: `severity` validated against `('info', 'suggestion', 'warning')`, `title`/
    `detail` must be non-empty strings -- a malformed individual finding is dropped, not shown
    broken, same discipline as an unresolvable source ref. `sources` self-reported per finding
    (not once per response, since `SPEC-319` §2.3 caught and corrected `SPEC-318` §2.5's own first
    draft omitting a per-finding `general_practice` flag entirely), enriched and validated through
    the identical `_enrich_source_ref`/`validate_source_refs` path chat turns already use. `area`
    filled in server-side from the route's own parameter -- the model never supplies it.

### Phase 5: daemon route + prompt files
*   [x] `daemon.chat_review(scope, scope_id, area, project_name=None) -> list` -- thin wrapper
    threading `CONFIG`'s provider/model/secrets through, byte-for-byte matching `chat_send`'s own
    shape. Registered in `ROUTES` (same guard as `chat.send`) and `ASYNC_ROUTES` (a real LLM call).
*   [x] Every `chat_{overview,components,schematic,pcb,enclosure}.prompt.md` gains a **Review
    format** section, appended after the existing **Citation format** section -- reuses that
    section's own per-agent citable-kind subset by reference ("follows exactly the same format and
    rules as the citation format above") rather than repeating it, keeping the two sections from
    drifting out of sync with each other.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (real, checked before writing any code, not assumed): `ToolRegistry` has no
    `remove_tool` method.**
    *   *Reasoning:* the natural-looking design ("build the full registry, then remove the gated
        tools from it") was the first thing tried, and introspecting the installed `ToolRegistry`
        class directly (`agentflow.tools.registry`) before writing it showed only `add_tool`/
        `add_dispatcher`/`dispatch`/`list_tools` exist.
    *   *Impact:* `build_tool_registry()` gained an `exclude` parameter that filters at construction
        time instead -- a small, additive change (`send()`'s own call site is unaffected, it never
        passes `exclude`), and arguably cleaner than a two-step build-then-remove would have been.
*   **Deviation 2 (real, found while reviewing `SPEC-319`'s own first draft before implementing it):
    `ReviewFinding` was missing a per-finding `general_practice` flag.**
    *   *Reasoning:* `SPEC-318` §2.5's own original shape (copied forward into `SPEC-319`'s first
        draft) had exactly one, response-wide flag -- fine for chat, where one turn is one answer,
        but wrong for review, where a single call can name several findings with different
        groundedness each.
    *   *Impact:* `SPEC-319` §2.3 corrected before any code was written against the old shape;
        `review()`'s own implementation (this context) was built against the corrected,
        per-finding version from the start, so no rework was needed.
*   **Deviation 3 (real, verified against the actual code rather than trusted from `SPEC-319`'s own
    first draft): the write-tool exclusion is not closing a live safety gap.**
    *   *Reasoning:* `tool_registry.py`'s own `_wrap_route` already refuses to execute any
        unconfirmed `CONFIRMATION_REQUIRED_TOOLS` call for any caller, chat included -- confirmed by
        reading it directly. `SPEC-319`'s own first draft claimed a different, non-existent gated
        tool (`library.save_confirmed_part`) was the real risk; grep against `tool_registry.py`
        showed it isn't even a registered tool today.
    *   *Impact:* `SPEC-319` §1/§2.2 corrected in a follow-up commit before this implementation
        started, with the real rationale (a review has no confirmation UI to complete the exchange,
        so offering the tool at all is a dead end, not a live hazard). Named here because it's the
        kind of thing that's cheap to catch before writing code and expensive to catch after.
