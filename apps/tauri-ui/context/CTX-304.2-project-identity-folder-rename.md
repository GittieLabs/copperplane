# CTX-304.2: Project identity: don't let project.json's name drift from the real folder

> **Spec Reference:** Links to [SPEC-304](../specs/SPEC-304-project-library-storage.md)

Closes a real gap `CTX-110.1` found and deliberately did not fix inline (tracked as task #53):
`library_store.py`'s `list_projects()` derives a project's identity purely from its
`projects/<name>/` folder name on disk, but `load_project()` returned whatever `name` happened to
be persisted inside `project.json` at save time. A user renaming a project's folder outside the app
(Finder, `mv`, a sync tool) left those two disagreeing — `list_projects()` would report the new
name, `load_project(new_name)` would report the old one — with no reconciliation and no error.

## 1. Feature Definition & Execution Plan

### Phase 1: Make the folder name authoritative on read
*   [x] `load_project(name)` overrides the returned record's `name` field with the real folder name
    it was loaded from, instead of trusting whatever `project.json` happened to hold. `name` is
    still required at `save_project` time (identity for a *new* project is still chosen there,
    unchanged) — this only closes the read-side drift after the fact.
*   [x] Regression test: save a project, rename its folder directly on disk (`os.rename`, not
    through `save_project`), then confirm `list_projects()` and `load_project()` both report the new
    name and the rest of the record's fields survive untouched.

## 4. Plan Drift & Architectural Changes

**Scope was deliberately kept to the read path only.** The alternative -- writing a small persisted
project-identity file distinct from the folder name, so identity survives a rename independent of
the directory itself -- was considered (it's closer to what the user originally asked about in
`CTX-110.1`: *"a project file that maps the directory structure ... and not rely on a folder name
alone"*). It was rejected here because `SPEC-304`'s whole storage model, not just `Project`, already
treats the `projects/<name>/` folder name as the one real identity key: `save_artifact`,
`load_artifact`, `list_artifacts`, `load_conversation`, and `append_conversation_turn` all take a
`project_name` string and use it directly as a path segment, with no indirection through a
persisted ID anywhere. Introducing folder-independent identity for `Project` alone would fix the one
field that happens to be visibly duplicated in `project.json` while leaving every sibling record
still silently tied to the folder path -- a bigger, structural change than this task's scope, and one
that would need to touch every one of those functions consistently rather than just `load_project`.
This fix closes the concrete, demonstrated bug (a stale, disagreeing `name` field) without
pretending to solve identity-independent-of-folder-path, which stays open as real follow-up scope if
it's ever prioritized.

**No frontend change was needed.** `apps/tauri-ui/src/lib/projects.ts`'s `loadProject()` wrapper
exists but is not yet called anywhere in the UI (`grep` confirms only `listProjects()` is wired into
`App.tsx` today) -- so this was a live, real gap in the daemon's own contract, not yet a live bug a
user could have hit through the shipped UI. Fixing it now, before any UI code starts trusting
`load_project`'s `name` field, is exactly the kind of thing worth closing before it becomes a harder,
UI-visible bug to diagnose later.
