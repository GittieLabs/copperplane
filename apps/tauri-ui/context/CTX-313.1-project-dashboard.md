# CTX-313.1: Implementation Context: Overview Tab Per-Project Dashboard

> **Spec Reference:** Links to [SPEC-313](../specs/SPEC-313-overview-tab-project-dashboard.md)

Real design decisions this context resolves, left open by the spec: no new backend route is
needed at all -- `project.load` already returns `last_results`/`export_history`
(`CTX-312.1`) and `project.load_conversation` already returns chat turns; the dashboard is pure
frontend composition of data already loaded today. One real gap found while planning, not
assumed away: `ConversationTurn` (`lib/projects.ts`) has no timestamp field, and
`append_conversation_turn` (`library_store.py`) writes whatever dict it's given verbatim -- so
today's chat turns cannot actually be time-merged against `export_history`'s real `exported_at`
values. Phase 1 below closes that gap; it's a real, necessary prerequisite for the spec's own
"merged, time-ordered activity feed," not scope creep.

## 1. Feature Definition & Execution Plan

### Phase 1: Conversation turns gain a real timestamp
*   [x] `lib/projects.ts`: `ConversationTurn` gains `timestamp: string` (ISO 8601 UTC), matching
    `ExportHistoryEntry.exported_at`'s own existing convention (`CTX-312.1`) -- stamped
    client-side, not server-side, for the same reason `exported_at` already is (no server clock
    dependency in `library_store.py`'s thin `append_conversation_turn` passthrough).
*   [x] `App.tsx`: both real `appendConversationTurn` call sites (the user turn and the assistant
    reply, `App.tsx:517-518`) stamp `timestamp: new Date().toISOString()`.
*   [x] No backend schema change -- `append_conversation_turn` already persists whatever turn dict
    it receives verbatim (`library_store.py:813-815`); it needs no code change to carry the new
    field.

### Phase 2: Real per-area status cards
*   [x] New `components/OverviewDashboard.tsx`: renders one status card each for
    PCB/Schematic/Enclosure/Components, reading `currentProject.last_results` (already loaded via
    `project.load`, no new fetch).
*   [x] Enclosure's card renders the real fields `handleExportSuccess` already writes
    (`glb_path`/`step_path`/`wall_thickness_mm`/`clearance_mm`/`standoff_height_mm`,
    `App.tsx:241-247`) -- the one area with real data today.
*   [x] PCB/Schematic/Components render an explicit "Not yet checked this session" state when
    their `last_results` key is absent -- never omitted, never a fake "OK."

### Phase 3: Real activity feed, merged and time-ordered
*   [x] New `lib/overview.ts`: a pure `mergeActivityFeed(turns, exportHistory)` helper -- no new
    daemon route, since both inputs are already loaded (`chatHistory` state, `currentProject.
    export_history`). Sorts descending by `timestamp`/`exported_at`.
*   [x] A turn with no `timestamp` (pre-Phase-1 legacy `conversation.jsonl` data written before
    this context shipped) sorts to the end rather than crashing or sorting first -- a real,
    named migration gap, not silently assumed away (see Plan Drift).

### Phase 4: Wire into Overview + tests
*   [x] `App.tsx`: render `OverviewDashboard` in the Overview area, alongside the existing,
    unchanged chat surface.
*   [x] Tests for Phases 1-3 (see matrix below), plus `App.test.tsx` coverage for the dashboard
    actually rendering in the Overview area.
*   [ ] Real verification: a human click-through of the real running app, per this repo's own
    `native-window-verification-gap` pattern -- does a project with a real Enclosure export show
    its card correctly, does a project with none show the honest "not yet checked" state, does the
    activity feed read in a sane order. **Not yet done this session** -- named honestly below and
    left as an open item, matching this repo's own established pattern for every other new UI
    surface this session (`CTX-311.13`/`.14`, `CTX-312.1`/`.2`/`.3`).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: no new backend route, resolved at planning time, not discovered mid-build.**
    The spec's own Data Flow section explicitly left open "which daemon route(s) assemble the
    merged activity feed." Decided during planning (not implementation): none needed.
    `project.load` already returns `last_results`/`export_history` (`CTX-312.1`) and
    `project.load_conversation` already returns chat turns -- the dashboard is pure frontend
    composition (`lib/overview.ts`) of data the app loads today regardless. Avoids a new route,
    new schema, and new test surface for zero real gain.
*   **Deviation 2: found and fixed a real gap in `ConversationTurn`'s own schema, not assumed
    correct from the spec's text alone.** The spec's own Design Rationale said the activity feed
    "merges and time-orders" conversation history against `export_history` -- but `ConversationTurn`
    (`lib/projects.ts`) had no timestamp field at all before this context, and
    `append_conversation_turn` (`library_store.py`) persists whatever dict it receives verbatim.
    Found by reading the real code before writing the merge helper, not by a test failing.
    Phase 1 closes it: a client-stamped, optional `timestamp`, matching `exported_at`'s own
    existing convention. Real, necessary, in-scope -- not scope creep.
*   **Deviation 3 (named, not fixed): pre-existing turns have no timestamp.** Every
    `conversation.jsonl` line written before this context shipped lacks the new field.
    `mergeActivityFeed` handles this by sorting a missing timestamp to the end (`TEST-003`) rather
    than crashing or guessing a value -- but a project with a long chat history from before this
    ships will show its own old turns clustered at the bottom of the feed regardless of when they
    actually happened. No migration was written; named honestly as a real, accepted limitation of
    shipping an additive schema change without a backfill.
*   **Deviation 4 (unrelated, named for completeness): one pre-existing live-API test failure.**
    `python3 -m pytest services/python-daemon/` found
    `test_002_a_real_search_via_google_does_not_truncate` failing with a real
    `google.genai.errors.ClientError: 403 PERMISSION_DENIED` -- an environment/credential issue
    with the live Google Search API, not a code defect, and entirely unrelated to this context
    (zero `services/python-daemon` files touched by `CTX-313.1`). Not investigated further here,
    named rather than silently ignored.

**Not verified in this session**: a real human click-through of the actual running app --
does the dashboard render correctly for a real project with an Enclosure export already recorded,
does a project with nothing yet show the honest "not yet checked" cards, does the activity feed
read in a sane order on real data. Per this repo's own `native-window-verification-gap` pattern
for every prior UI surface this session, this is the next real step before considering this
feature done, not assumed covered by 268 passing mocked/unit tests.
