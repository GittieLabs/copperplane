# CTX-307.1: Part Detail: real pins, provenanced library save, real .kicad_sym export

> **Spec Reference:** Links to [SPEC-307](../specs/SPEC-307-part-detail-library-export.md)

Replaces `SPEC-306`'s confirmed-candidate dead end with a real Part Detail view. Defines the
Symbol's pin/layout schema (undefined until now, per `SPEC-307` §3's own named debt), assembles
Part provenance from data this context already has (the search candidate + a real extraction call)
rather than reopening `SPEC-202`'s output contract, and writes a genuinely valid `.kicad_sym` file
-- verified with KiCad's own `kicad-cli sym export svg`, not just plausible-looking text.

Real, hands-on verification of the live app (search -> confirm -> Part Detail -> save -> export ->
open) found two more real bugs in code this context's own tests never touched, exactly the pattern
`CTX-306.1` established. Both fixed and recorded below.

## 1. Feature Definition & Execution Plan

### Phase 1: Symbol schema + real `.kicad_sym` writer
*   [x] Defined the Symbol record's pin/layout shape:
    `{symbol_id, reference_prefix, pins: [{number, name, electrical_type}]}`. `symbol_id` is derived
    from a `package + pin-count` signature, not a random id, so identical parts converge rather than
    silently duplicating (`SPEC-307` §3's own named gotcha).
*   [x] `_layout_pins(pins) -> dict`: a pure, testable auto-layout -- pins split evenly left/right,
    stacked on a 2.54mm grid (KiCad's own real convention, confirmed by reading real `.kicad_sym`
    files: pin length 2.54, angle 0 on the left, angle 180 on the right).
*   [x] `export_symbol_kicad_sym(symbol_id) -> str` in `library_store.py`: writes a real, hand-built
    S-expression `.kicad_sym` file, matching the exact real format confirmed by reading actual
    KiCad 10 library files on this machine.
*   [x] Real verification: `kicad-cli sym export svg` against the generated file -- confirmed via a
    real subprocess call, not a plausible-looking string.

### Phase 2: Provenance assembly + daemon routes
*   [x] `library_save_confirmed_part(candidate, extraction)` in `daemon.py`: assembles Part
    provenance from two calls this context already has -- `manufacturer`/`datasheet_url` from the
    `SPEC-306` search candidate (`source: "search"`), `package`/`pins` from this context's own
    extraction call (`source: "llm_extraction"`, CONFIG-resolved provider/model). Saves the Symbol,
    then the Part referencing it.
*   [x] `library.save_confirmed_part` and `library.export_symbol` routes -- both sync, matching
    `library.save_part`'s own precedent.

### Phase 3: Part Detail UI
*   [x] `apps/tauri-ui/src/lib/partDetail.ts`: wraps the extraction re-run, save, and export calls.
*   [x] `apps/tauri-ui/src/components/PartDetail.tsx`: real pin table, "Save to Library", "Export
    Symbol" (revealed once saved), and "Open symbol" (reuses `CTX-306.1`'s `tauri-plugin-shell`
    wiring).
*   [x] `ComponentDiscovery.tsx`'s confirmed state renders `<PartDetail candidate={...}/>` instead of
    the placeholder text.

## 4. Plan Drift & Architectural Changes

*   **Real bug: `component_search.prompt.md`'s `max_tokens` (2048, `CTX-306.1`'s own fix) still
    occasionally truncated mid-JSON on longer real Google responses.** Found running the actual live
    app, not this suite. Raised to `3072`; a 6/6 repro immediately after had comfortable headroom.
    This is now the third round of tuning this exact value (1024 -> 2048 -> 3072) against real,
    non-deterministic LLM output -- each round found by real verification, not predicted in advance.
*   **Real bug: a real extraction call returned `"PDIP-8"`**, a common real-world synonym for
    `"DIP-8"` that `component_extraction.prompt.md`'s own "use the package's real, standard name"
    instruction doesn't reliably prevent. `PACKAGE_REFERENCE` failed closed on it even though the
    geometry is identical to an entry already present -- the *correct* fail-closed behavior for a
    truly unknown package, but wrong here since this was a known package under a different real
    name. Fixed by generating a `P<key>` alias for every existing `DIP-N` entry programmatically,
    not hand-duplicating, so it also covers any future `DIP-N` entry added later.
*   **Non-deviation, confirmed as designed: provenance is assembled at the route layer, not by
    reopening `component_pipeline.py`'s output shape**, exactly as `SPEC-307` §2 planned. Verified
    for real end to end -- a saved Part's `provenance.manufacturer.source` is `"search"` and
    `provenance.package.source` is `"llm_extraction"` with the real CONFIG-resolved model, both
    confirmed against the actual running app's own saved file, not just the unit test.
*   **Real, out-of-scope finding, not fixed here: storage/export locations are not user-configurable.**
    Manual verification of "Export Symbol" surfaced this directly -- the exported `.kicad_sym`
    lands at `~/Library/Application Support/com.gittielabs.hardware-agent-studio/storage/library/
    symbols/...`, a real macOS path but not one an average user will easily find or want as a
    permanent location. This isn't new: `CTX-304.1`'s own Plan Drift explicitly considered and
    rejected a first-run directory picker ("real UI scope this context isn't built to carry") when
    `storage_root` was first established. Real usage now argues that decision is worth revisiting --
    tracked as a new follow-up task (not a `CTX-307.2`, since it's a `SPEC-106`/`SPEC-304`-level
    concern, not specific to Part Detail), not fixed in this context.
*   **State what was not verified:** this ran against exactly one machine (macOS), one KiCad install
    (10.0.3, confirmed via `kicad-cli --version`), and the app's own real, currently-configured
    provider (Google, with Anthropic as the real-test fallback for the automated suite). Not
    verified: `export_symbol_kicad_sym`'s output against KiCad on Windows or Linux (the pin-length/
    grid values are platform-independent real numbers, but the file has only ever been opened by
    this one real KiCad instance); a second real part with a much larger pin count than the ~8-pin
    parts tried by hand; and whether `symbol_id`'s package+pin-count dedup actually converges two
    *genuinely different* real parts sharing a package in the live app (proven directly in the
    automated suite, only indirectly implied by the manual round, which used one part).
