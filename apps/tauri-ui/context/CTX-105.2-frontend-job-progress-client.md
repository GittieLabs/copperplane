# CTX-105.2: Frontend Job & Progress Client

> **Spec Reference:** Links to [SPEC-105](../../../specs/SPEC-105-daemon-async-job-progress-protocol.md)

**Scope note:** this is the frontend slice SPEC-105 names as `CTX-105.2` — consuming `CTX-105.1`'s
daemon-side job protocol from `apps/tauri-ui`. It replaces `CTX-101.1`'s hard single-in-flight
guard with real per-job state, and is where the progress bars/cancel buttons SPEC-105 explicitly
scoped *out* of the spec itself belong.

## 1. Feature Definition & Execution Plan

### Phase 1: Stop dropping job notifications
*   [x] `ipc.ts`'s `daemon://response` listener currently drops any payload whose `id` is
    `null`/`undefined` — which is every `job.*` notification `CTX-105.1` emits (they carry no `id`
    key at all, distinguishing them from a JSON-RPC response, which always has one, even `null` for
    a parse-error). Branch on that distinction instead of discarding.

### Phase 2: Job tracking client
*   [x] `submitJob(method, params)`: dispatches the request, reads `{"job_id": ...}` back from the
    immediate response, and returns a `JobHandle` — `jobId`, a `result` promise that resolves on
    `job.completed` / rejects on `job.failed` or `job.cancelled`, an `onUpdate()` subscription for
    `job.progress` (and every other job event, for a UI that wants live status), and `cancel()`
    (dispatches `job.cancel` for this `job_id`).

### Phase 3: Replace the hard single-in-flight guard
*   [x] Remove `dispatch()`'s `inFlight` boolean and the immediate-rejection guard it enforced.
    JSON-RPC `id`-based response matching already correctly demultiplexes concurrent requests
    regardless of arrival order — the guard's only real purpose (per `CTX-101.1`'s own reasoning)
    was avoiding `stdin` spam, not protocol correctness, and it actively prevents the concurrent
    job tracking this phase's whole point is to enable.

### Phase 4: Wire the proof case into the UI
*   [x] Add a minimal enclosure-generation panel to `App.tsx` using `submitJob('freecad.generate_enclosure', ...)`
    — width/depth/height inputs, a Generate button, a live status line driven by `onUpdate()`, and a
    Cancel button visible only while the job is running.

### Phase 5: Testing
*   [x] Unit tests: a `job.*` notification with no `id` is routed to its job (not dropped); the
    `job.progress` → `job.completed` sequence resolves `result` with the right payload; `job.failed`
    and `job.cancelled` both reject `result`; `cancel()` dispatches `job.cancel` with the right
    `job_id`; two concurrent `dispatch()` calls both resolve correctly by `id`, proving the removed
    guard wasn't protocol-load-bearing.

## 4. Plan Drift & Architectural Changes
*Document any deviations from SPEC-105 encountered during build.*

*   **Deviation 1: notifications are distinguished from responses by the *absence of an `id` key*,
    not by `id === null` — a distinction that actually matters here.**
    *   *Reasoning:* `daemon.py`'s `-32700 Parse error` response sets `"id": null` *explicitly* — the
        key is present, just `null`-valued, because the daemon couldn't recover a real request id
        from unparseable input. A `job.*` notification never includes an `id` key at all (JSON-RPC
        2.0's own definition of a notification). Checking `payload.id === null` would have
        misclassified that one specific error response as a notification and silently dropped it
        instead of resolving/rejecting the caller's pending request. Checking `!('id' in payload)`
        instead gets both cases right.
    *   *Impact:* None on any currently-passing test (no existing test exercises a parse-error
        response reaching the frontend), but worth recording since it's exactly the kind of gap that
        wouldn't surface until a malformed request slipped through in practice.

*   **Deviation 2 (non-deviation, confirmed as designed): the hard single-in-flight guard is removed
    entirely, not narrowed to "only guard synchronous routes."**
    *   *Reasoning:* Considered keeping the guard for non-async routes specifically, reasoning that
        only async jobs need real concurrency. Rejected: `dispatch()`'s `id`-based response matching
        already makes *any* concurrent request pair — sync or async — resolve correctly regardless
        of arrival order (proved directly by `TEST-005`, which deliberately resolves two concurrent
        dispatches out of submission order). `CTX-101.1`'s original guard was a stdin-spam
        precaution, not a protocol necessity (its own context file says so: "preventing stdin
        spam"). A partial guard would have been an arbitrary line with no correctness justification
        on either side of it.
    *   *Impact:* None — `App.tsx`'s existing `kicad.generate_component` flow still disables its own
        button while pending via local `pending` state, so the UI-level "don't let a user double-click"
        concern CTX-101.1 was also partly serving is still handled, just per-component rather than
        globally inside the transport layer.

*   **Deviation 3 (non-deviation, confirmed as designed): `EnclosurePanel`'s cancel path calls
    `job.cancel` but does not itself resolve/reject the UI's pending state — it waits for the
    `job.cancelled` notification like any other outcome.**
    *   *Reasoning:* `JobHandle.cancel()` only *requests* cancellation (SPEC-105 §3: cancellation
        must be real, and the daemon-side worker is what actually observes and reports it). Settling
        `result` optimistically the moment `cancel()` is called, before the daemon confirms it, would
        let the UI show "cancelled" for a job that in fact raced past cancellation and completed
        normally on the daemon side.
    *   *Impact:* None — this is the behavior `CTX-105.1`'s own protocol requires; noting it here so
        a future reader doesn't "fix" `cancel()` into something that resolves eagerly.
