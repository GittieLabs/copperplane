# CTX-321.3: New-Provider Form Legibility & Local Endpoint Discovery

> **Spec Reference:** Links to [SPEC-321](../specs/SPEC-321-provider-configuration-ui.md)

Three findings from one real click-through, reported as one confusion:

> "i do have the previouse ollama model avail. The messages here are confusing. it didn't attempt
> to populate anything for ollama. Are we not trying the common api address to see if ollama is
> running/installed? are we not running the list command to see what models are installed? the
> message that 'blank= can't serve this role' is confusing."

Every observation was correct. The diagnosis underneath them was not the obvious one: **the form
being looked at was not the ollama record.** It was the new-record form, which renders where the
"Add provider" button was -- directly beneath the last provider row, which is ollama -- and said
nothing about being new.

That is why nothing populated. There was no bug in the listing path at all; the record it would
have listed for was not open.

## 1. Feature Definition & Execution Plan

### Phase 1: Say that a new record is new

*   [x] A **"New provider"** heading and an accent border, rendered only when `isNew`.
*   [x] Three signals already distinguished the two states and none of them were a label: `Id` is
    enabled rather than disabled, the built-in-preset warning is absent, and *"Save this provider
    first"* appears. All three are inferences a reader has to make; none of them says "new".
*   [x] Diagnosed from `config.json` first, not from the screenshot. The stored `ollama` record was
    intact -- correct `base_url`, both models `llama3.2:1b`, file untouched since 2026-08-27 -- which
    ruled out corruption before any theory about the UI was formed.

### Phase 2: Stop using a placeholder as documentation

*   [x] `(blank = can't serve this role)` occupied exactly the space where the fetched model
    suggestions are most useful, and read as an instruction rather than a note.
*   [x] The placeholder is now an example: the first listed model when listing succeeded, else
    `llama3.2:1b`.
*   [x] The explanation moved to a hint line, shown only while the field is blank -- the one state
    in which it says anything useful.

### Phase 3: Offer a local endpoint that is actually there

*   [x] `llm.probe_endpoint(base_url)` -- takes a **URL, not a provider id**, because the record
    being configured does not exist yet and `_resolve_record_and_key` has nothing to resolve for a
    draft. That is the whole reason `llm.list_models` could not serve this case.
*   [x] Registered in `ROUTES` **and `ASYNC_ROUTES`**. A real socket connect to a host that may
    have nothing listening must not run inline in the request path.
*   [x] Reuses `_list_openai_compat` rather than adding a second way to reach an OpenAI-compatible
    server, and sends the same placeholder key the `ollama` record uses. No configured key is ever
    read -- there is no record to take one from.
*   [x] Fired once, when the new-record form opens. Never at startup, never on save
    (`SPEC-324` §2.3).
*   [x] **Silent on failure.** The offer appears only when a server actually answered. An
    unreachable endpoint says nothing rather than suggesting a URL that would not work -- the same
    rule `SPEC-324` §2.1 applies to a provider that cannot list, one level up.
*   [x] The offered URL is the `ollama` preset's own `base_url`, shared as `LOCAL_OLLAMA_BASE_URL`,
    so the editor's suggestion and the preset cannot drift apart.
*   [x] Gated to new records. The `openai` preset also has a blank `base_url`, and there blank
    correctly means `api.openai.com`; offering it localhost would be wrong.

### Phase 4: The guard CTX-314.2's bug deserved

*   [x] A test asserting every vendor-calling `llm.*` route is in `ASYNC_ROUTES`. `CTX-314.2`
    records a real bug where a GitHub-calling route left out of that set blocked the daemon's whole
    stdin loop for an entire release. Nothing asserted the property afterwards, so the next route to
    make a network call could reintroduce it silently. This context added the third such route,
    which is why the property is now tested rather than remembered.

### Not in this context

*   **A health/discovery probe of anything but the one local endpoint.** Scanning ports, or probing
    a URL as the user types it, is a different feature with a real privacy surface. This probes one
    well-known loopback address, once, on an explicit user action.
*   **Prefilling `base_url` automatically when `kind` changes to `openai_compat`.** Considered and
    rejected: `openai` itself is `openai_compat` and must stay blank. An offer the user clicks is
    honest where a silent prefill would be wrong half the time.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the reported bug did not exist, and the real one was worse.**
    *   *Reasoning:* The report was that the editor failed to populate models for ollama. Taken at
        face value it points at `list_models`, the listing fetch, or the base URL -- all of which
        were correct and provably working. Reading `config.json` first showed the stored record was
        intact, which forced the question of what was actually on screen rather than what was
        assumed to be.
    *   *Impact:* the defect was that a blank new-record form is visually adopted by the row above
        it. Chasing the reported symptom would have produced changes to a listing path that had
        nothing wrong with it, and left the real confusion in place. **A user's diagnosis and a
        user's observation are different things; the observations here were all exactly right.**

*   **Deviation 2: `llm.list_models` could not be reused, for a structural reason worth naming.**
    *   *Reasoning:* the obvious implementation is to call the existing listing route. It takes a
        `provider_id` and resolves it through `_resolve_record_and_key`, which is correct for a
        saved record and impossible for a draft -- the record being configured does not exist yet.
    *   *Impact:* `probe_endpoint` takes a URL instead. It still reuses `_list_openai_compat`, so
        there is one way to reach an OpenAI-compatible server, not two. The split is at the
        resolution layer, not the transport.

*   **Deviation 3: an unfixed problem from `CTX-314.2` was found sitting open.**
    *   *Reasoning:* that context recorded a real bug -- a network-calling route omitted from
        `ASYNC_ROUTES` blocked the daemon's entire request path for a release -- and fixed the
        instance. It never added a test for the property, so the guarantee lived in a comment and
        in whoever remembered reading it.
    *   *Impact:* adding a third network-calling route made the omission concrete rather than
        theoretical. `TEST-018` now asserts it for all three. Recorded because the pattern is the
        finding: a fixed instance without an asserted property is a bug waiting for its next
        author.
