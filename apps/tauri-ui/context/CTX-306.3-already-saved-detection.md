# CTX-306.3: Implementation Context: Already-Saved Detection

> **Spec Reference:** Links to [SPEC-306](../specs/SPEC-306-component-discovery.md)

Real live-testing feedback: searching for a part already saved to the library (e.g. re-searching
an already-confirmed ESP32-S3) gave no signal that it was already saved, and confirming it re-ran
SPEC-202's LLM extraction from scratch on a part that already has a real, saved record. This closes
that gap on both ends of the flow: a badge in search results, and a real hydration shortcut in
`PartDetail` that skips extraction entirely when the confirmed candidate turns out to already be
saved.

This context supersedes an earlier, never-merged attempt at the same fix (branch
`feat/CTX-306.3-already-saved-detection`, commits `a37b114`/`aa7c588`, written before `CTX-315.4`
added `PartDetail`'s `initialPart` entry point). That branch's own `PartDetail.tsx` approach --
adding a second, parallel "already saved" hydration path alongside the extraction effect -- is
still the right shape; this reapplies it against `initialPart`'s real, current code rather than
the pre-`CTX-315.4` file it was written against, and drops the diff's original `onOpenSavedPart`
prop plumbing through `App.tsx`, since it would have exited the Components tab into the separate
Library view -- not what "already saved" search results inside the Components area need.

## 1. Feature Definition & Execution Plan

### Phase 1: Search-result badge
*   [x] `ComponentDiscovery.tsx`: after a successful search, best-effort `listParts()` populates a
    `savedPartIds: Set<string> | null`. A failure here doesn't block results from rendering -- it
    just means no candidate gets a badge this round.
*   [x] Each candidate row checks `savedPartIds?.has(candidate.part_number)` and renders an
    "Already in your library" badge next to the part number. No separate "Open" shortcut button --
    "This one" already leads to `PartDetail`, which (Phase 2) now hydrates the saved record directly
    instead of re-extracting, so a second button doing the same thing would be redundant.

### Phase 2: `PartDetail` hydration shortcut
*   [x] The confirmed-candidate branch of `PartDetail`'s extraction effect (`candidate`, not
    `initialPart` -- that path already hydrates directly since `CTX-315.4`) now tries
    `loadPart(candidate.part_number)` first. On success, it hydrates `extraction`/`savedPart`/
    `savedSymbol` the same way `initialPart` already does (reusing `initialPartToExtraction`/
    `initialPartToSymbol`) and sets `status('ready')` without ever calling `extractPartDetail`. On
    failure -- the expected, common case for a genuinely new part -- it falls straight through to
    the original extraction call, unchanged.
*   [x] Setting `savedPart` here means the existing `{savedPart && (...)}` render gate (already
    built for `initialPart`) applies identically -- "Save to Library" never appears for an
    already-saved part, matching `initialPart`'s own behavior, with no new gating logic needed.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: dropped the original diff's `onOpenSavedPart` prop and its `App.tsx` wiring
    (`setView({ kind: 'partDetail', partId })`).**
    *   *Reasoning:* that mechanism didn't exist when the original branch was written; it was added
        later by `CTX-315.4` for the Library area specifically, and it navigates *out of* the
        current project's Components tab into the separate top-level Library view. A user searching
        inside Components who finds an already-saved part wants to see it inside Components, not
        get bounced to Library and lose the project/area-tab context. The existing "This one" button
        already leads to `PartDetail` within `ComponentDiscovery` itself, and Phase 2's hydration
        shortcut makes that path just as cheap as the Library one -- no `Open` button needed.
    *   *Impact:* one fewer button/prop than the original diff; same real value (no wasted
        re-extraction, clear "already saved" signal) delivered through the surface that was already
        there.
*   **Deviation 2 (honest, not yet done): the persistent project-level parts list this same user
    feedback also asked for is deliberately out of scope here.** That's a larger, separate feature
    (a project-scoped `parts` reference list, list/detail navigation, "add to project" from Library)
    tracked as its own follow-up, not folded into this narrower already-saved-detection fix.
