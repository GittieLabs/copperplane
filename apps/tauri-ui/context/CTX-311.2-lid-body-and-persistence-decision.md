# CTX-311.2: Backend: lid body generation, and the deferred persistence-safety decision

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

The second backend-only slice of SPEC-311. Builds the real lid body SPEC-311 §2 named as a genuinely
open design question ("two real FreeCAD bodies... either as a second object in the same document/
export or a fully separate `.step`/`.glb` pair") and decides it: a second object in the same
`freecadcmd` document, exported as its own separate `.glb`/`.step` pair. Also picks up SPEC-311 §2's
other named open question -- generated-design persistence -- decides the model, and documents a
real, confirmed risk this context found but deliberately does not fix here.

## 1. Feature Definition & Execution Plan

### Phase 1: lid body generation
*   [x] `freecad_bridge.py`: `_LID_BODY_LINES_TEMPLATE` -- a flat, filleted plate matching the
    shell's own outer footprint, appended into the *same* script/document as the base shell (not a
    second `freecadcmd` subprocess -- SPEC-311 §3 already flags cold-boot cost compounding per
    refine click; doubling it for a lid alone would make that worse for no reason).
    Deliberately a plain flat cover, not a snap-fit/lip design -- real, unproven geometry work and
    outside `SPEC-109` §1's own "not fastener hardware" non-goal.
*   [x] `generate_enclosure()` gains `lid: bool = False`, `lid_thickness_mm: float = None` (defaults
    to `wall_thickness_mm`). Board-driven mode only -- `ValueError` in manual mode, which has no
    open top to close.
*   [x] Real STL→GLB unit-scale fix (`CTX-109.4`) applied identically to the lid's own mesh.
*   [x] The existing "delete the previous successful output, bound the leak to one extra file"
    cleanup (`CTX-301.1`) extended with its own `_last_lid_glb_path`/`_last_lid_step_path` pair.

### Phase 2: daemon.py wiring
*   [x] `freecad_generate_enclosure` gains `lid`/`lid_thickness_mm`, passed straight through.
*   [x] A saved Artifact (`project_name` given) persists the real `lid_glb_path`/`lid_step_path`
    too, when a lid was generated -- otherwise a saved enclosure's lid would be silently forgotten
    on reload.

### Phase 3: tests + real verification
*   [x] Real, no-mocks tests: a real lid's bounding box matches the shell's own outer footprint in
    X/Y and its configured thickness in Z; `lid_thickness_mm` defaults to `wall_thickness_mm`; the
    previous-file cleanup applies to the lid too.
*   [x] Mocked tests: manual mode + `lid=True` raises `ValueError`; `daemon.py`'s param passthrough;
    the saved-Artifact lid-path persistence (present when a lid was generated, absent otherwise).
*   [x] Live, end-to-end verification against a real `freecadcmd` and, separately, through the real
    `daemon.freecad_generate_enclosure` route against the real currently-open KiCad board.

### Phase 4: the persistence decision (SPEC-311 §2's other named open question)
*   [x] Decided: **explicit-save-only**, not auto-save-every-generation. SPEC-311's whole point is an
    iterative refine-and-regenerate loop; most regenerations during that loop are the user trying a
    number, not a decision to keep the result. Auto-saving a real Artifact record on every one of
    those would flood a project's saved-artifact list with throwaway iterations. The existing
    `project_name`-gated `library_store.save_artifact` call (unchanged by this context) already
    implements exactly this: no `project_name` given, no Artifact saved -- matching today's frontend,
    which never sends it. A later, frontend-adjacent context adds the actual "Save" UI action that
    supplies `project_name` deliberately, once the refine loop exists to iterate before saving.
*   [x] **A real, confirmed risk found while making this decision, deliberately not fixed in this
    context** -- recorded honestly rather than silently left as a landmine (see Plan Drift).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: a real, confirmed artifact-file-lifecycle risk was found while deciding the
    persistence model, and is deliberately NOT fixed in this context.** `freecad_bridge.generate_
    enclosure`'s own leak-bounding cleanup (`CTX-301.1`) deletes the *previous* successful glb/step
    the moment a new one is generated -- correct and desired for throwaway preview iterations, which
    is most of them under the new refine loop. But if a user saves an Artifact (`project_name`
    given, creating a durable `library_store` record pointing at that generation's real files) and
    then keeps refining *without* `project_name` on a later call (a plain, unsaved preview), that
    later call's own cleanup will delete the *previously-saved* Artifact's real files out from under
    it -- `library_store` still has a metadata record, but the `glb_path`/`step_path` it points to no
    longer exists on disk. Confirmed by reading the code, not yet reproduced by writing a failing
    test for it: this needs a real fix on the daemon/library_store side (e.g. only deleting a
    previous file when it was never saved as an Artifact), which is properly the same context that
    builds the actual "Save" UI action -- fixing the underlying file-lifecycle bug in isolation here,
    before that UI exists to exercise it, risks getting the real fix wrong without a real workflow to
    validate it against. Named explicitly rather than fixed blind, per this repo's own "state what
    was not verified" norm.
*   **Deviation 2: the lid is a flat, unlipped cover, not a friction-fit/snap-fit design.** SPEC-311
    §1's own Non-Goals already rule out fastener hardware; a lip/step profile that friction-fits into
    the shell's own open top would be real, additional OpenCASCADE profile work (a stepped
    extrusion, not a plain box) with no existing precedent in this repo's FreeCAD scripts. Named as a
    deliberate v1 simplification, not an oversight -- a natural refine-parameter candidate for a
    future context once the base refine loop exists to expose it.
