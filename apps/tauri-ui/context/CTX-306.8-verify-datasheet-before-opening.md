# CTX-306.8: Verify a Datasheet Before Offering It

> **Spec Reference:** Links to [SPEC-306](../specs/SPEC-306-component-discovery.md)

One report — *"error on a datasheet"* with a URL — that turned out to be three defects, the worst
of which nobody was looking for.

## 1. Feature Definition & Execution Plan

### Phase 1: Fetch before opening

*   [x] The candidate card's "view datasheet" handed `datasheet_url` straight to the OS. A real
    `CR2032` search produced
    `https://industrial.panasonic.com/cdbs/www-data/pdf/AAA4000/AAA4000C417.pdf`, which 404s, so
    clicking it dropped the user into a browser error page with nothing in the app explaining why.
*   [x] It now caches first and opens the local PDF — `PartDetail.handleOpenCitation`'s existing
    pattern, applied to the one surface still passing an unverified URL to the OS. Caching *is* the
    check; no new route.
*   [x] Errors are per-candidate, keyed by part number, so one dead link cannot blank another
    card's state.

### Phase 2: Stop presenting a guess as a fact

*   [x] The link reads **"view datasheet (unverified)"** until something fetches it.
*   [x] `component_search.prompt.md` asks for a *"best real guess"* and calls a wrong one
    *"a normal, recoverable outcome"*. That is right for a guess. Rendering it identically to a
    checked fact is not — `confidence` describes the **part identity**, not the URL, but sitting
    directly above the link it reads as covering both.

### Phase 3: HTTP 200 is not evidence the body is a datasheet

*   [x] `cache_datasheet` accepted any 200 and wrote the body to `<part>.pdf`. `keyelco.com`
    answers a missing PDF with its own HTML page **and a 200**, so caching `3003` and `1060`
    produced **byte-identical HTML files — same sha256** — that `SPEC-205`'s text extraction and
    page citations would have read as datasheets.
*   [x] Validated on the `%PDF-` magic bytes, and **deliberately not the `Content-Type` header**: a
    real 404 observed the same day returns `Content-Type: application/pdf` with
    `Content-Length: 0`, so a header check passes exactly the case it exists to catch.
*   [x] Audited the maintainer's real library — no non-PDF files present; the two written by this
    context's own probe were removed.

### Not in this context

*   **Stale candidates during a search.** `handleSearch` clears `error` and `confirmed` but not
    `candidates`, so the previous query's cards stay on screen for the whole of a new search — tens
    of seconds for a real LLM call. That is why a "coin cell battery holder" search appeared to
    return coin cells: the prior `Cr2032` card was still rendered. Real, reported, and a different
    surface from this one.
*   **A `job.failed` that never reached the UI.** With the prompt tree missing, `component.search`
    failed in under a second and the UI showed an indefinite spinner. A failure the user cannot see
    is worse than the failure.
*   **Fixing the URLs themselves.** This makes a bad guess *visible and honest*; it does not make
    the guesses good. See §4 Deviation 2.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — the reported bug was the least important of the three.**
    *   The report was a 404 on one datasheet. Chasing the other candidates' URLs found
        `cache_datasheet` writing HTML to disk as `.pdf` under an HTTP 200 — silent, and already
        reachable by the existing confirm path, which has cached best-effort since `CTX-306.1`.
    *   *Impact:* a loud 404 costs a click. A 200 full of HTML poisons datasheet guidance and page
        citations with no signal at all. The reported defect got a UI fix; the unreported one got
        the real guard.

*   **Deviation 2 — this makes the failure honest, it does not make the URLs good.**
    *   A real "coin cell battery holder" search returned five candidates whose datasheet URLs
        produced three 403s and two 404s. The parts were correct; the provenance was not.
    *   *Impact:* the card now says so instead of pretending otherwise, which is the right floor
        but not a fix. Genuinely fixing it means either dropping `datasheet_url` from search
        results or verifying candidates before display — a latency-versus-honesty trade `SPEC-306`
        should decide deliberately, not one to slip into a bug fix.

*   **Deviation 3 — an earlier claim in this session was wrong and is corrected here.**
    *   The 403s were described as blocked-or-invented URLs. `keyelco.com/pc_pdf/3003.pdf` returns
        **200** to the app's own User-Agent, so those URLs are reachable; the 403s belonged to a
        *different* set of URLs, because the model returns different ones on every run.
    *   *Impact:* worth recording that `datasheet_url` is **non-deterministic across identical
        queries**. Any future work reasoning about "the URL for part X" has to account for there
        not being one.
