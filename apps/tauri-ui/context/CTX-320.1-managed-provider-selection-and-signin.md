# CTX-320.1: Managed Provider Selection & Token Sign-In

> **Spec Reference:** Links to [SPEC-320](../specs/SPEC-320-managed-account-signin-and-usage.md)

The first real slice of `SPEC-320`, scoped narrow on purpose — the same way `CTX-205.1` and
`CTX-308.1` opened their specs. It makes Managed selectable and gets a token into the keychain.
It does **not** build the usage display, the failure cards, or the early-access toggle; each is
named below with what blocks it.

Everything here was planned against the code as it actually exists on `develop` today, not against
the spec's description of it. `SPEC-320` was written 2026-08-25; `SPEC-321` and `SPEC-208` landed
2026-08-26 and moved two things the spec assumes. Both are recorded in §4 before any code is
written, rather than discovered mid-build.

## 1. Feature Definition & Execution Plan

### Phase 0: Two blocking decisions, before any UI

Neither is a code task. Both change what the later phases build, so they are resolved first.

*   [ ] **Decide where Managed appears, given `SPEC-321`.** `SPEC-320` §2.1 says Managed is an
    option in "`SPEC-303`'s existing provider list". That list is now two different things:
    `ALL_PROVIDERS` in `apps/tauri-ui/src/lib/settings.ts` (the five-item picker: anthropic,
    google, openai, perplexity, ollama) and `SPEC-321`'s provider-records editor, whose
    `getProviderRecords()` **deliberately never returns `managed`** — its own doc comment says so,
    citing `SPEC-321` §2.4. Managed cannot simply be appended to the records editor without
    contradicting that decision. Recommendation: add `managed` to the picker only, leave the
    records editor untouched, and treat the exclusion as correct rather than as a bug to undo.
*   [ ] **Decide the two missing failure cards.** `SPEC-320` §2.5 defines four cards and states
    that a screen is selected by code and never by string-matching. The shipped taxonomy in
    `services/python-daemon/llm_providers.py` has **six** codes — its own docstring calls it "the
    six-row structured taxonomy". `managed_rate_limited` (429, carries `retry_after`) and
    `managed_error` (the unmapped-status fallback) have no card. Two of six codes currently select
    nothing. Recommendation: `managed_rate_limited` gets a Retry card carrying its `retry_after`,
    and `managed_error` gets a generic card, so the mapping is total. This needs a `SPEC-320` §2.5
    amendment, not a silent UI default.

### Phase 1: The fake gateway fixture

*   [ ] Build the stub HTTP gateway `SPEC-207` §2.5 requires and `SPEC-320` §3 depends on. It does
    not exist yet — the shipped managed tests construct real `openai` SDK exception objects
    directly (`_fake_status_error`, `_fake_connection_error` in
    `services/python-daemon/tests/test_llm_providers.py`) rather than serving responses.
*   [ ] Point it at `HAS_MANAGED_GATEWAY_URL`, the environment variable `llm_providers.py` already
    reads for the managed record's `base_url`. That variable is the entire seam; no production code
    needs a test hook added to it.
*   [ ] Serve one canned response per row of the six-row taxonomy, plus a success body.

### Phase 2: The account read

*   [ ] Add a daemon route that performs `GET /v1/account` against the managed base URL with the
    stored token, returning plan, allowance, used, and reset date. **No such route exists anywhere
    in the repo today** — `SPEC-207` §2.2 names `GET /v1/account` as the source of period quota
    state but never assigns the route to a module, and `SPEC-320` §2.7 says the daemon "consumes
    nothing from this spec". See §4 Deviation 1: this is a real gap between the two specs, not an
    oversight in either.
*   [ ] The route returns the raw account payload. It does not threshold, warn, or interpret —
    `SPEC-207` §2.2 puts that in presentation, which is `SPEC-320`'s.

### Phase 3: Managed as a selectable provider

*   [ ] Add `managed` to the provider picker per the Phase 0 decision. Selecting it swaps the
    API-key field for the sign-in panel and leaves the rest of Settings untouched.
*   [ ] No upsell surface anywhere. `SPEC-320` §1 holds this as a hard product constraint, not a v1
    simplification — one entry in the picker and nothing else.

### Phase 4: Paste-a-token sign-in and sign-out

*   [ ] Open the account site in the system browser via the existing shell plugin. `CTX-306.1`
    already found that Tauri's `"open": true` silently applies a narrow default regex, so the
    allowlist entry needs checking rather than assuming.
*   [ ] Trim the pasted token aggressively before anything else. `SPEC-320` §3 predicts whitespace
    as a real support cost.
*   [ ] Validate the token against the Phase 2 account read **before** writing it to the keychain,
    so a bad paste fails immediately with a specific message instead of at first AI call.
*   [ ] Write it under the key name `managed_token`, which `core/tauri-rust/src/daemon.rs` already
    allowlists in `KNOWN_SECRET_KEYS` — added by `SPEC-207` with a comment saying sign-in itself is
    `SPEC-320`'s job. The Rust side needs no change.
*   [ ] Never render the token back in full after saving, never log it, never include it in
    `SPEC-107`'s diagnostics bundle.
*   [ ] Sign-out clears the key and returns the provider to unconfigured, with copy that says
    explicitly it does not cancel a subscription.

### Deliberately not in this context

*   **Usage display** (`SPEC-320` §2.3) — the panel is presentation over Phase 2's route. Separated
    so the route lands and is verified before a UI is written against its shape.
*   **The six failure cards** (§2.5) — blocked on Phase 0's second decision, and larger than this
    slice. The frontend currently handles **no** `managed_*` code at all; there is no partial
    implementation to extend.
*   **The early-access channel toggle** (§2.4) — depends on `SPEC-402` extending the update manifest
    with a second channel, which has not happened.
*   **The auto-fallback question** (§3, last bullet) — whether an exhausted allowance should fall
    back to a configured personal key. The spec recommends no. Nothing here forces the decision.

existing file rather than naming a file that does not exist yet.

**Verification this context commits to beyond the matrix:** `SPEC-320` is `user_facing: true`, and
this repo's own norm is that a capability test does not discharge that. `SPEC-302` shipped with
every route green and nobody having tried to look up a part. So this context is not closeable on
green tests alone — someone has to select Managed, paste a token against the stub gateway, see it
accepted, and sign out again, with what they saw recorded. That cannot happen in the container this
plan was written in; it needs a real desktop build.

**Named gap, not deferred quietly:** no test here touches a real gateway, by instruction and by
`SPEC-207` §2.5. Sign-in against the real service is therefore unverified by this context and
stays unverified until one exists.

## 4. Plan Drift & Architectural Changes

Recorded before implementation rather than after, because both were found while reading the code
to write this plan and both change what gets built.

*   **Deviation 1 — `GET /v1/account` is named by two specs and owned by neither.** `SPEC-207` §2.2
    says period quota state comes from `GET /v1/account`, but its §2.6 cross-module list does not
    include an account route among the daemon's deliverables. `SPEC-320` §2.7 says
    `services/python-daemon` is "upstream only; consumes nothing from this spec". Between them, no
    module owns the route, and a repo-wide search finds no implementation of it. Phase 2 builds it
    in the daemon, which contradicts `SPEC-320` §2.7 as written.
    *   *Reasoning:* the token cannot be validated before saving (`SPEC-320` §3's explicit
        requirement) and the usage panel cannot be sourced (§2.3) without it. The alternative —
        calling the gateway directly from the frontend — would put a bearer token in the renderer
        and bypass `SPEC-106`'s spawn-time secret channel, which is worse on every axis.
    *   *Impact:* `SPEC-320` §2.7 needs amending to say the daemon gains one route, or `SPEC-207`
        §2.6 needs to claim it. Flagged for the maintainer; not silently absorbed.

*   **Deviation 2 — the failure taxonomy is six codes, not four.** `SPEC-320` §2.5 tabulates four
    and states that a card is selected by code and never by string-matching prose. The shipped
    implementation emits six. `managed_rate_limited` and `managed_error` have no defined card, so a
    strict code-to-card mapping leaves two real, reachable states rendering nothing.
    *   *Reasoning:* the four-row table was written 2026-08-25 against `SPEC-207` §2.3's table;
        the implementation that landed added a 429 case and an unmapped-status fallback.
    *   *Impact:* Phase 0 resolves it before the cards are built in a later context. Recorded here
        because it would otherwise be found at card-implementation time, after the mapping had
        already been written against the wrong table.

*   **Deviation 3 — the provider list `SPEC-320` §2.1 targets has since split in two.** The spec
    describes Managed joining "Anthropic, OpenAI, Google and Ollama". The picker today also
    includes Perplexity, and `SPEC-321` added a separate provider-records editor that explicitly
    excludes Managed. The spec's sentence is no longer an unambiguous instruction.
    *   *Reasoning:* `SPEC-321` and `SPEC-208` landed the day after `SPEC-320` was written.
    *   *Impact:* Phase 0's first decision. The recommendation preserves `SPEC-321` §2.4's
        exclusion rather than treating it as an obstacle.

*   **Non-deviation, checked rather than assumed:** the Managed keychain key is already wired.
    `managed_token` is in `KNOWN_SECRET_KEYS` in `core/tauri-rust/src/daemon.rs`, added by
    `SPEC-207` with a comment stating sign-in itself is `SPEC-320`'s job. `SPEC-320` §2.7 predicted
    "one new keychain entry name" as work for this spec; it is already done, and Phase 4 reuses it
    rather than adding one.

*   **Open, unresolved:** `SPEC-320` §3 asks this context to confirm what happens when the provider
    is switched mid-job rather than assume it, since `SPEC-105` jobs can be in flight. That was not
    established while writing this plan and is not claimed as known. It must be answered from the
    running app before Phase 3 changes provider selection behaviour.
