# CTX-309.3: Implementation Context: Board Open-State Guidance & Multi-Board Selection

> **Spec Reference:** Links to [SPEC-309](../specs/SPEC-309-board-advisor.md)

Real user feedback exercising the actual running app: "Check Board" surfaced a raw exception
message (a stale scratch path from an unrelated earlier session) with no guidance on what to do
about it. `CTX-309.1`'s own backend silently narrows `get_open_documents(DOCTYPE_PCB)`'s real list
down to `docs[0]` -- discarding any board past the first -- and `CTX-309.2`'s own frontend renders
every failure as flat red text, never distinguishing "nothing open" (a normal, expected state
`kicad_check_board`'s own docstring already says should be "report[ed] plainly," but never actually
was) from a genuine connection failure. This closes that gap: a real empty-state prompt when no
board is open, a real picker when more than one is, and a real, live-discovered bug fix along the
way.

## 1. Feature Definition & Execution Plan

### Phase 1: real, live investigation before writing any code
*   [x] Confirmed real, against this machine's own actually-running KiCad instance (the same live
    IPC socket `test_004_real_round_trip_against_a_live_kicad_instance` already uses): with no PCB
    Editor window open, `get_open_documents(DOCTYPE_PCB)` doesn't return an empty list -- it raises a
    real `ApiError`: `"KiCad returned error: no handler available for request of type
    kiapi.common.commands.GetOpenDocuments"`. The handler isn't registered until a PCB Editor window
    is actually open, the same real constraint `CTX-108.1`'s own Deviation 2 already documented for
    the write path.
*   [x] Confirmed real, by reading `kicad_bridge.get_open_board_path()`'s existing exception
    handling: it catches `ApiError` in the same branch as a genuine `KiCadConnectionError`, calls
    `reset_connection()`, and raises `KiCadUnavailableError("Lost connection to KiCad mid-request.
    It may have been closed.")` -- a real, live-confirmed **bug**: the actual, current, everyday
    "no board open" state was being reported to the user as if KiCad had just disconnected, which is
    not what happened at all.
*   [x] Confirmed real, by reading `kicad_bridge.get_open_board_path()`'s successful path: `docs[0]`
    is returned unconditionally when `docs` is non-empty -- any board past the first, if more than
    one PCB Editor window happens to be open, is silently discarded with no way for the caller (or
    the user) to know it existed.
*   [x] Confirmed real, by reading `BoardAdvisor.tsx`: `boardError` is rendered as flat
    `text-red-400` text from `err.message` with zero branching on what kind of failure occurred --
    every failure mode looks identical to the user today.

### Phase 2: `kicad_bridge.py` -- a real three-state resolver, not a silent pick
*   [x] Replace `get_open_board_path() -> str | None` with `list_open_boards() -> list[str]`: returns
    every real open board's resolved path, never narrowed to one. Catches the real `"no handler
    available"` `ApiError` specifically and returns `[]` for it (a normal "nothing open" state, not
    a `reset_connection()`-worthy failure) -- every other `ApiError`/`KiCadConnectionError` still
    resets the connection and raises `KiCadUnavailableError` exactly as before, since those really
    are connection failures.

### Phase 3: `daemon.py` -- a real three-way response envelope
*   [x] `kicad_check_board(pcb_path=None)`: when no explicit path is given, calls
    `list_open_boards()` and returns one of three real, structured shapes instead of ever raising for
    the "nothing open"/"more than one open" cases:
    *   Zero open: `{"status": "no_board_open"}` -- the frontend owns the actual guidance copy (a
        real UI concern, not backend string formatting).
    *   Exactly one open: unchanged behavior -- auto-resolves and runs DRC.
    *   More than one open: `{"status": "needs_selection", "candidates": [{"path", "label"}, ...]}`,
        `label` a real, human-legible `os.path.basename(path)`.
    *   A successful DRC result now also carries `"status": "ok"` so the frontend can discriminate
        without inspecting which fields happen to be present.
    *   An explicit `pcb_path` always skips resolution entirely and runs DRC directly, unchanged.

### Phase 4: frontend -- a real empty-state prompt and a real picker
*   [x] `lib/boardAdvisor.ts`: `checkBoard`'s return type becomes a real discriminated union
    (`CheckOkResult | NoBoardOpenResult | NeedsSelectionResult`) keyed on `status`, rather than the
    single `CheckResult` shape that only ever described the success case.
*   [x] `BoardAdvisor.tsx`: three real, distinct render states for the Board (DRC) section --
    *   `no_board_open`: a real, concrete numbered walkthrough (open KiCad, open the project, open
        its PCB Editor window specifically, confirm the IPC API is enabled in Preferences → Plugins)
        plus a "Try Again" action -- replacing the current flat error text for exactly this state.
    *   `needs_selection`: a real, clickable list of every open board's `label`, each re-invoking
        `checkBoard(candidate.path)` with that explicit path on click.
    *   `ok`: the existing violation-list rendering, unchanged.
    *   A genuine `KiCadUnavailableError` (real connection failure) still renders as today's flat
        error text -- its existing message is already clear and actionable, and it's a real,
        different failure mode from the two new guided states, not one to blur together with them.

### Phase 5: tests + real live verification
*   [x] Mocked tests for `kicad_bridge.list_open_boards()`: empty list, one board, multiple boards,
    the real `"no handler available"` `ApiError` treated as empty (not a connection failure), and a
    genuine connection error still resetting + raising.
*   [x] Mocked tests for `daemon.kicad_check_board()`'s three-way envelope.
*   [x] Real, live verification against this machine's actually-running KiCad instance, mirroring the
    existing `test_004_real_round_trip_against_a_live_kicad_instance` convention (skips itself
    cleanly with no live socket).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: found by real, live testing on this actual dev machine's own running KiCad
    instance, not assumed from `SPEC-309`'s own prior research.** `SPEC-309` §2 documented that
    `DOCTYPE_PCB` auto-resolution "returns a real, resolvable full path... for whatever board is
    currently open," which is true only once a board *is* open -- the zero-open-boards case wasn't
    live-tested at spec time, and turned out to raise a real `ApiError` rather than return an empty
    list the way `get_open_documents` might be assumed to behave from its name alone. This context's
    own real testing caught it before shipping the new guidance UI on top of a still-mislabeled
    error.
