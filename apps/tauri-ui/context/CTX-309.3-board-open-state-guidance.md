# CTX-309.3: Implementation Context: Board Open-State Guidance & Multi-Board Selection

> **Spec Reference:** Links to [SPEC-309](../specs/SPEC-309-board-advisor.md)

Real user feedback exercising the actual running app: "Check Board" surfaced a raw exception
message (a stale scratch path from an unrelated earlier session) with no guidance on what to do
about it. `CTX-309.1`'s own backend silently narrows `get_open_documents(DOCTYPE_PCB)`'s real list
down to `docs[0]` -- discarding any board past the first -- and `CTX-309.2`'s own frontend renders
every failure as flat red text, never distinguishing "nothing open" (a normal, expected state
`kicad_check_board`'s own docstring already says should be "report[ed] plainly," but never actually
was) from a genuine connection failure. This closes that gap.

**This context was revised in place before its PR merged** (see §4 Deviation 2) once the first cut
was exercised live in the actual running app: it still silently auto-resolved a single open board
without ever showing the user which one, and offered no way to actually open KiCad when none was
running. The description below is the final, shipped design; §4 records both the original plan and
why it changed.

## 1. Feature Definition & Execution Plan

### Phase 1: real, live investigation before writing any code
*   [x] Confirmed real, against this machine's own actually-running KiCad instance (the same live
    IPC socket `test_004_real_round_trip_against_a_live_kicad_instance` already uses): with no PCB
    Editor window open, `get_open_documents(DOCTYPE_PCB)` doesn't return an empty list -- it raises a
    real `ApiError`: `"KiCad returned error: no handler available for request of type
    kiapi.common.commands.GetOpenDocuments"`. The handler isn't registered until a PCB Editor window
    is actually open, the same real constraint `CTX-108.1`'s own Deviation 2 already documented for
    the write path.
*   [x] Confirmed real, by reading `kicad_bridge.get_open_board_path()`'s existing exception
    handling: it catches `ApiError` in the same branch as a genuine `KiCadConnectionError`, calls
    `reset_connection()`, and raises `KiCadUnavailableError("Lost connection to KiCad mid-request.
    It may have been closed.")` -- a real, live-confirmed **bug**: the actual, current, everyday
    "no board open" state was being reported to the user as if KiCad had just disconnected, which is
    not what happened at all.
*   [x] Confirmed real, by reading `kicad_bridge.get_open_board_path()`'s successful path: `docs[0]`
    is returned unconditionally when `docs` is non-empty -- any board past the first, if more than
    one PCB Editor window happens to be open, is silently discarded with no way for the caller (or
    the user) to know it existed.
*   [x] Confirmed real, by reading `BoardAdvisor.tsx`: `boardError` is rendered as flat
    `text-red-400` text from `err.message` with zero branching on what kind of failure occurred --
    every failure mode looks identical to the user today.
*   [x] Confirmed real, by the user directly exercising the running app after the first cut of this
    context landed on this branch (pre-merge): a single open board was still auto-checked with no
    indication of *which* board, and the `no_board_open` state told the user to open KiCad's
    Preferences → Plugins menu without ever mentioning the Tauri app itself has no such menu, or
    offering to launch KiCad at all. Live process inspection (`ps aux`, `osascript` process listing)
    on this same dev machine confirmed KiCad genuinely was not running in both instances this came
    up -- the guidance gap was real, not hypothetical.

### Phase 2: `kicad_bridge.py` -- a real list, not a silent pick
*   [x] Replace `get_open_board_path() -> str | None` with `list_open_boards() -> list[str]`: returns
    every real open board's resolved path, never narrowed to one. Catches the real `"no handler
    available"` `ApiError` specifically and returns `[]` for it (a normal "nothing open" state, not
    a `reset_connection()`-worthy failure) -- every other `ApiError`/`KiCadConnectionError` still
    resets the connection and raises `KiCadUnavailableError` exactly as before, since those really
    are connection failures.

### Phase 3: `daemon.py` -- listing and checking are two separate real routes
*   [x] `kicad_list_open_boards()`: a new, fast, synchronous route (`kicad.list_open_boards`, not in
    `ASYNC_ROUTES`) that calls `list_open_boards()` and returns one of two real, structured shapes:
    *   Zero open: `{"status": "no_board_open"}`.
    *   One or more open: `{"status": "boards_found", "candidates": [{"path", "label"}, ...]}`,
        `label` a real, human-legible `os.path.basename(path)` -- **always** a list, even for a
        single board, so the frontend always shows the user which board it's about to check rather
        than silently picking for them.
*   [x] `kicad_check_board(pcb_path)`: `pcb_path` is now a **required** parameter -- all
    resolution/auto-pick logic moves to `kicad_list_open_boards()` above. Given an explicit path, it
    always runs DRC directly and returns the violations result tagged `"status": "ok"`.

### Phase 4: launching KiCad directly from the app
*   [x] `core/tauri-rust/src/lib.rs`: new `open_kicad` Tauri command. macOS uses `open -a KiCad`
    (Launch Services app-name lookup, verified live on this dev machine -- KiCad's own process
    appeared within ~2s of running it); Windows/Linux fall back to invoking `kicad` directly on
    PATH, the same assumption `find_kicad_cli` already makes elsewhere in this app --
    **not verified on those platforms**, named honestly in the command's own doc comment.

### Phase 5: frontend -- always show the real list, offer to launch KiCad
*   [x] `lib/boardAdvisor.ts`: `listOpenBoards()` wraps `kicad.list_open_boards` (plain `dispatch`,
    matching `kicad.get_version`'s own sync-route precedent); `openKicad()` wraps the new
    `open_kicad` Tauri command; `checkBoard(pcbPath)` now always takes an explicit path and returns a
    plain `CheckResult` or throws -- no more discriminated-union return type, since resolution no
    longer happens inside it.
*   [x] `BoardAdvisor.tsx`: the Board (DRC) section now scans for open boards as soon as the screen
    mounts (`useEffect`, no click required) and always renders one of:
    *   `no_board_open`: a real, concrete numbered walkthrough (open KiCad, open the project, open
        its PCB Editor window specifically, confirm the IPC API is enabled in Preferences →
        Plugins) plus a real **"Open KiCad"** button (shows "Opening…" while pending) and a
        **"Refresh"** button to re-scan once the user has done so.
    *   `boards_found`: a real, clickable list of every open board's `label` and full `path` --
        singular copy ("Board open in KiCad:") for exactly one, plural ("Boards open in KiCad — pick
        one to check:") for more than one -- each click invoking `checkBoard(candidate.path)` with
        that explicit path, plus its own "Refresh" button.
    *   A genuine connection failure scanning for open boards renders as flat error text with a
        "Retry" action -- a real, different failure mode from "nothing open," not blurred together
        with it.
    *   The check result itself (violations list, clean-board message, or a check-time error) renders
        below the picker, independent of it -- picking a different board re-runs the check without
        losing the list.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: found by real, live testing on this actual dev machine's own running KiCad
    instance, not assumed from `SPEC-309`'s own prior research.** `SPEC-309` §2 documented that
    `DOCTYPE_PCB` auto-resolution "returns a real, resolvable full path... for whatever board is
    currently open," which is true only once a board *is* open -- the zero-open-boards case wasn't
    live-tested at spec time, and turned out to raise a real `ApiError` rather than return an empty
    list the way `get_open_documents` might be assumed to behave from its name alone. This context's
    own real testing caught it before shipping the new guidance UI on top of a still-mislabeled
    error.

*   **Deviation 2: the original design (three-way envelope inside `kicad_check_board`, auto-resolve
    on exactly one board) was replaced before this PR merged, based on the user's own real use of
    the running app -- not a hypothetical concern raised at design time.** The first cut kept
    `kicad_check_board(pcb_path=None)` doing double duty: resolving *and* checking, auto-running DRC
    silently whenever exactly one board happened to be open. Exercising the actual app surfaced two
    real problems that design review alone hadn't: (1) a novice had no way to tell *which* board was
    about to be checked before it ran, since the single-board case produced no picker at all, and (2)
    when zero boards were open, the guidance text described KiCad's own Preferences → Plugins menu
    without ever addressing that the user had been looking for it inside the *Tauri app*, and never
    offered to actually launch KiCad. I predicted the single-board auto-resolve would read as a
    helpful shortcut; it read as opaque instead -- a real user, not a hypothetical one, said so after
    clicking through it. The fix required a real architectural split, not a copy change: listing
    (`kicad.list_open_boards`) and checking (`kicad.check_board`) became two separate routes so the
    frontend can always show a real list before ever running a check, plus a genuinely new
    capability (`open_kicad`) neither the original spec nor the original context anticipated needing.
