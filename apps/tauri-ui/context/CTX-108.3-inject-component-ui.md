# CTX-108.3: kicad.inject_component UI Trigger

> **Spec Reference:** Links to [SPEC-108](../../services/python-daemon/specs/SPEC-108-kicad-write-path-footprint-symbol-injection.md)

**Numbering note:** this is `CTX-108.3`, not `CTX-108.2` — `CTX-108.1` already reserved `.2`
explicitly, in writing, for schematic symbol injection once KiCad 11 is available (see `CTX-108.1`
Deviation 1 and `ROADMAP.md`'s `SPEC-108` entry). Using `.2` for this unrelated frontend task would
contradict that written commitment.

**Scope note:** `CTX-108.1`'s own Phase 4 explicitly deferred frontend wiring to "a follow-up
context." `SPEC-108` §2's Cross-Module Impacts section names exactly what that follow-up needs to
be: "a way to trigger this route with a position (even a hardcoded board-origin default for M1's
demo)." This context is exactly that — a plain button, a fixed position, no position-picker UI, no
confirmation gate (`SPEC-204`, not yet written). Real, minimal, not a placeholder for later work.

## 1. Feature Definition & Execution Plan

### Phase 1: The `Inject into Board` button
*   [x] `apps/tauri-ui/src/App.tsx`: once `kicad.generate_component` returns a schema, a new
    `Inject into Board` button appears alongside it. Clicking it calls `submitJob('kicad.inject_component',
    { schema, x_mm: 50, y_mm: 50 })` — the fixed default position `SPEC-108` §2 itself named as
    sufficient for this pass.
*   [x] Success/error/pending states follow the exact same pattern already established by
    `EnclosurePanel` (`CTX-105.2`) for `freecad.generate_enclosure` — no new UI idiom introduced.
*   [x] **Mutates the real board the instant it's clicked — no confirmation step of its own.**
    `kicad_bridge.inject_component` (`CTX-108.1`) already documents this as the caller's
    responsibility; this button *is* that caller, and inherits the same real, live safety boundary.
    `SPEC-204`'s eventual confirmation gate sits in front of this button, not inside it.

## 4. Plan Drift & Architectural Changes

*   **Non-deviation, confirmed as designed: no position-picker UI.** `SPEC-108` §2 explicitly named
    a hardcoded default as sufficient for this pass ("even a hardcoded board-origin default for
    M1's demo"); a real placement UI (drag-to-position, collision-avoidance with existing
    footprints) is legitimate future work this context deliberately doesn't attempt.
*   **Non-deviation, confirmed as designed: `App.tsx` had zero test coverage before this context.**
    Only `EnclosureViewer.tsx`'s internal hooks were tested; the top-level `App` component and
    `EnclosurePanel` were never rendered in a test at all. Adding `App.test.tsx` here is scoped to
    covering the new `Inject into Board` flow this context adds, not retroactively covering
    `EnclosurePanel` or the existing `Generate` flow — those remain as they were, a gap pre-existing
    this context, not one it was asked to close.
