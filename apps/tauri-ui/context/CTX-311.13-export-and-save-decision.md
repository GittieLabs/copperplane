# CTX-311.13: Real Export: STEP/STL/GLB/FreeCAD to a user-chosen location, and fixing the live auto-save bug

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

`SPEC-311` §2 named generated-design persistence as a genuinely open product question and refused
to default to whatever was easiest to code. `CTX-311.2` picked a model -- explicit-save-only, not
auto-save-every-generation -- and named a real, deliberately-deferred risk. Investigating that risk
for this context found it was no longer hypothetical: `daemon.py`'s `freecad_generate_enclosure`
route already called `library_store.save_artifact` on **every single Generate click**, because
`EnclosurePanel.tsx` always forwarded its `projectName` prop as `project_name` -- and
`generate_enclosure()`'s own leak-bounding cleanup deletes the *previous* generation's `.glb`/
`.step` on every new one. Every earlier Artifact JSON record already pointed at deleted files after
one refine-and-regenerate, invisible only because nothing in the frontend read those records back
yet. The user, given this finding, asked to fix it as part of this same work.

Separately -- the actual feature requested -- today's Generate result only ever lived in the app's
own internal `output_dir`, with no way to get a real, durable file (especially a native FreeCAD
file to keep editing) onto a location the user actually chose. This context builds that: a real
**Export** action, offering STEP/STL/GLB/native FreeCAD (`.FCStd`), any combination of body/lid/
combined, to a real native "Save As" location -- while removing the live auto-save bug entirely.

A broader, connected set of product questions (what "Save" means at the project level, project
portability, the missing native app menu, the Overview tab's real purpose, component library
discovery) came up in the same conversation and were deliberately **not** answered here -- recorded
as `ROADMAP.md`'s new `SPEC-312` backlog entry instead of folded into this narrowly-scoped context.

## 1. Feature Definition & Execution Plan

### Phase 0: prototype before assuming feasible
*   [x] `doc.saveAs()` (native FreeCAD project format) had never been used anywhere in this
    codebase. Prototyped directly against the real, installed `freecadcmd 1.1.1` before writing any
    real implementation: built two real STEP files, imported both into one fresh document as two
    real `Part::Feature` objects, `saveAs`'d to `.FCStd`, then re-opened that file in a **separate**
    `freecadcmd` process and confirmed both real objects round-trip. Also prototyped
    `Part.makeCompound([shape1, shape2])` for multi-shape STEP/STL export the same way -- a real,
    standard FreeCAD grouping mechanism, not a boolean fuse.

### Phase 1: backend export (`services/python-daemon/freecad_bridge.py`)
*   [x] `export_enclosure(parts, fmt, dest_path, step_path=None, lid_step_path=None, glb_path=None,
    lid_glb_path=None, timeout_s=30.0, cancel_event=None)` -- never regenerates geometry, only reads
    from files a prior real `generate_enclosure` call already produced.
    - `fmt='glb'`: no subprocess. Single part is a real `shutil.copy` of the already-correct
      existing `.glb`; `'combined'` merges both existing glTF `Scene`s' own geometries into one
      real merged `Scene` via `trimesh` (both meshes' vertices are already in the same shared
      coordinate space the original FreeCAD build placed them in -- no additional transform
      needed).
    - `fmt in ('step', 'stl')`: one real `freecadcmd` subprocess, reading the relevant STEP file(s)
      back and wrapping more than one in `Part.makeCompound` before exporting -- one code path for
      one or two shapes.
    - `fmt='fcstd'`: one real `freecadcmd` subprocess, always the whole real design (ignores
      `parts` -- see Plan Drift).
    - `parts='lid'`/`'combined'` raise a clean `ValueError` (not a confusing downstream
      `FileNotFoundError`) when no lid was actually generated.
*   [x] Real edge case found by this context's own test suite, not hypothesized: a `ValueError:
    not enough values to unpack` the first time `export_enclosure` ran unconditionally against a
    convex, cavity-free shape (unrelated -- this was `_export_glb`'s own inner/outer split from
    `CTX-311.12`, re-encountered while wiring up test fixtures for this context, not a new bug in
    `export_enclosure` itself, but confirms the module's own "verify against the real thing" norm
    is doing real work).

### Phase 2: daemon route + the real auto-save fix (`services/python-daemon/daemon.py`)
*   [x] New route `freecad_export_enclosure`, registered as `freecad.export_enclosure`, added to
    `ASYNC_ROUTES` (export latency varies by format/parts -- some paths are a real subprocess).
*   [x] **Removed** the `if project_name:` / `library_store.save_artifact` block from
    `freecad_generate_enclosure` entirely, along with the `project_name` parameter,
    `board_revision`/`_board_revision_for` (only ever fed that removed block), and the now-unused
    `hashlib` import. Generate no longer implicitly persists anything -- `freecad.export_enclosure`
    is the only real "keep this" action now.
*   [x] New route `project_get_directory` (`project.get_directory`) -- a real, single source of
    truth for a project's own directory path (`library_store.project_directory`, wrapping the
    already-existing `_project_dir` helper), used to default the Export dialog's save location to
    the project's own folder.

### Phase 3: frontend (`apps/tauri-ui`)
*   [x] `lib/enclosure.ts`: `exportEnclosure` (submits the new async route), `pickExportDestination`
    (wraps `save()` from `@tauri-apps/plugin-dialog` -- every prior dialog use in this codebase was
    `open()`; `save()` is genuinely new), `getProjectDirectory`. Dropped `project_name` from
    `EnclosureParams` and `artifact_id` from `EnclosureResult`.
*   [x] `core/tauri-rust/capabilities/default.json`: added `dialog:allow-save` (only
    `dialog:allow-open`/`dialog:allow-message` existed before).
*   [x] `EnclosurePanel.tsx`: dropped the `Generated: {glb_path}` label entirely (an internal,
    soon-to-be-overwritten `output_dir` path the user had no reason to visit -- flagged directly by
    the user as misleading now that the file it names is genuinely transient). Added Export
    controls (parts/format selectors + an Export button) directly beside the existing "Open .step"
    button, per the user's own placement preference. Default export destination is the current
    project's own real directory (via `getProjectDirectory`) plus a sensible filename, still fully
    overridable in the same native dialog.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `.FCStd` export is always the whole design, never gated by `parts` -- a real
    decision, not an oversight.** Confirmed with the user directly (asked, not assumed) rather than
    building real per-part `.FCStd` documents: re-opening the full design (both bodies together,
    ready to keep editing) is more useful than a document with just one box, and per-part `.FCStd`
    would be real, additional freecadcmd work for a use case nobody asked for. Parts selection still
    applies fully to STEP/STL/GLB.
*   **Deviation 2: a real, live, currently-happening bug was found and fixed, not just the
    hypothetical `CTX-311.2` originally named.** `CTX-311.2`'s own Deviation 1 assumed "today's
    frontend... never sends `project_name`." That assumption was already wrong by the time this
    context started -- `EnclosurePanel.tsx` always forwarded it, so every single Generate silently
    wrote an Artifact record whose files the very next regenerate deleted. Fixed by removing the
    concept entirely rather than trying to make the buggy timing safe: Export writes a real,
    independent file to a location the user chose, which needs no cleanup bookkeeping at all --
    strictly simpler and safer than protecting a single internally-tracked "last successful" file
    from itself.
*   **Deviation 3: this context's own test fixture hit the exact bug it was built to fix.** The
    first version of `TestFreecadBridgeExportEnclosure.setUpClass` called `generate_enclosure`
    twice (once with a lid, once without) and tried to read the first result's files afterward --
    they were already gone, deleted by the second call's own leak-bounding cleanup, confirmed live
    via a direct repro (`_last_step_path` is a simple module-level pointer, unscoped by
    `output_dir`). Fixed by copying the first result's files to independent, untracked paths before
    the second `generate_enclosure` call -- the same real fix a durable Export action gives a real
    user, verified by writing the test fixture itself.
*   **Deviation 4: a broader, connected set of real product questions was raised mid-conversation
    and deliberately not answered here.** What "Save" means at the project level, project
    portability (schematic/pcb/enclosure view state currently lives in `$APPDATA`, not the project
    directory), the confirmed-missing native app menu, the Overview tab's undecided real purpose,
    and component library discovery are all real, connected to this work, but each depends on a
    product decision that doesn't exist yet. Recorded as `ROADMAP.md`'s new `SPEC-312` backlog
    entry rather than silently expanding this context's own narrow scope -- this repo's own "Plan
    Drift is not embarrassing" norm exists precisely so a real, named gap survives to the next
    session instead of being either solved blind or quietly dropped.
