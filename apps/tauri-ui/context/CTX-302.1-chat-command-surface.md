# CTX-302.1: Chat & Command Surface

> **Spec Reference:** Links to [SPEC-302](../specs/SPEC-302-chat-command-surface.md)

**Correction found before implementation, not during it:** `SPEC-302` §2 claims real multi-turn
context is achievable because "AgentFlow's `AgentExecutor.run()` already accepts a `history`
parameter." True of `AgentExecutor`, but `llm_providers.chat()` — the function `llm.chat` actually
calls — never goes through `AgentExecutor` at all; it calls the raw provider's own `chat()` directly
with a hardcoded single-message list. The real, correct mechanism is different: the raw provider's
`chat(messages: list[Message], ...)` already accepts a full message list natively (verified against
the installed package before writing this) — multi-turn is still achievable, just via prepending
prior turns to that list, not via `AgentExecutor`. This also means `SPEC-302` §2's "No impact on
`services/python-daemon`" claim was wrong for this one piece — the same class of mistake `CTX-202.1`
Deviation 2 already found once in this repo (a spec's own Cross-Module Impacts claim, untrue the
moment someone actually reads the caller). See Plan Drift.

## 1. Feature Definition & Execution Plan

### Phase 1: Real multi-turn history support — the backend gap `SPEC-302` didn't know it needed
*   [x] `services/python-daemon/llm_providers.py`: `chat()` gains an optional `history:
    list[dict] | None` parameter — each entry `{"role": "user"|"assistant", "content": str}`,
    converted to `agentflow.types.Message`/`Role` objects and prepended to the new prompt's own
    message before calling the provider's real `chat(messages, system=...)`.
*   [x] `daemon.py`: `llm_chat` route gains the same `history` parameter, passed straight through.
    Backward compatible — omitting `history` (as every existing caller does) behaves exactly as
    before, a single-message conversation. Verified for real: `TestHistory.test_001` is a real
    regression check against the pre-existing single-message shape.

### Phase 2: The command recognizer — a small, pure, explicit rule
*   [x] `apps/tauri-ui/src/lib/commands.ts`: `parseCommand(input): Command` — recognizes
    `generate <part number>` and `inject` (case-insensitive, tolerant of surrounding whitespace)
    against a typed message; anything else falls through to a plain chat turn. Returns a
    discriminated union, not a boolean plus side-effects — pure, no knowledge of conversation state.
*   [x] `inject` with no successfully-generated schema yet is **not** this pure function's job (it
    has no conversation state to check) — that empty-state check lives in Phase 4's wiring, which
    actually holds `latestSchema`.

### Phase 3: The message-list UI
*   [x] Replaces `App.tsx`'s single-input/single-`<pre>`-dump UI with a scrollable message list +
    one input box. Each message renders what it actually did: a `generate` message shows the
    returned schema (structured fields plus the full JSON, not a bare `<pre>` dump — `SPEC-302`'s
    own presentational goal); an `inject` message shows success/failure exactly as `CTX-108.3`'s
    button did; a plain chat message shows the model's real text response. Per-message `Status`
    (`'pending' | 'done' | 'error'`), not one global `pending` boolean — `SPEC-302` §3's own named
    risk.
*   [x] `EnclosurePanel` (`CTX-105.2`/`CTX-301.1`/`CTX-301.2`) is unchanged, kept as its own panel
    below the message list — per `SPEC-302`'s own design rationale, enclosure generation isn't part
    of this spec's conversational goal.

### Phase 4: Wiring
*   [x] A plain chat turn calls `llm.chat` with `history` built from every prior plain-chat turn in
    this conversation (`chatHistory` React state, appended to after each successful reply).
    `generate`/`inject` messages are not folded into that history for this pass — a real, named
    limitation, not silently solved (see `SPEC-302` §2's own design rationale).
*   [x] `inject` checks `latestSchema === null` before ever calling `submitJob` — the empty-state
    message `SPEC-302` §3 named explicitly, never a null-pointer-shaped error reaching the daemon.
*   [x] `generate`/`inject` commands call the same real routes `App.tsx` already called
    (`kicad.generate_component`, `kicad.inject_component`), unchanged in shape.

### Phase 5: Testing
*   [x] Mocked + real: `llm_providers.chat()`'s new `history` parameter — `TestHistory` in
    `test_llm_providers.py`: omitting it behaves identically to before (regression, mocked); providing
    it sends the right message list to the provider (mocked); a real, live call proves a second turn
    actually answers using information *only* the first turn established (`"My favorite number is
    42"` → `"What is my favorite number?"` → the model answers `42`).
*   [x] Mocked: the command recognizer's own parsing rules (`commands.test.ts`) — exact matches,
    case/whitespace tolerance, near-misses and unrelated text fall through to plain chat.
*   [x] Mocked: the message-list UI (`App.test.tsx`) — mocks `submitJob` directly, covering a
    `generate` message, an `inject` message (with and without a schema already generated), a plain
    chat message, a second chat turn proving `history` actually gets sent, and a `generate` failure
    showing the real error text.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (found before implementation, not during it): `SPEC-302` §2's own claim about how
    multi-turn context would work was wrong — the same class of mistake `CTX-202.1` Deviation 2
    already found once in this repo.**
    *   *Reasoning:* `SPEC-302` cited `AgentExecutor.run()`'s real `history` parameter as evidence
        multi-turn context needs no new AgentFlow capability. True, but irrelevant: `llm.chat`'s
        real call chain (`daemon.llm_chat` → `llm_providers.chat`) never touches `AgentExecutor` —
        it calls the raw provider's `chat()` directly, with a hardcoded single-message list. Found
        by reading `llm_providers.py`'s actual source before starting Phase 1, not by trusting the
        spec's own citation.
    *   *Impact:* The real, correct mechanism is simpler, not harder: the raw provider's own
        `chat(messages: list[Message], ...)` already accepts a full conversation natively — Phase 1
        threads a `history` parameter through `llm_providers.chat()`/`daemon.llm_chat()` to build
        that list, a small, real, backward-compatible addition to `services/python-daemon`, directly
        contradicting `SPEC-302` §2's "No impact on `services/python-daemon`" claim for this one
        piece specifically.

*   **Deviation 2: the real end-to-end `history` test (`TEST-006`) uses Anthropic, not Ollama —
    found by running it for real, not assumed from `CTX-201.1`'s own Ollama-first convention.**
    *   *Reasoning:* `TEST-006` first used Ollama, matching `CTX-201.1`'s "no key needed" convention
        for this exact test class. It failed: asked to recall "my favorite number is 42" one turn
        later, `llama3.2:1b` answered `86`. Calling `llm_providers.chat()` directly (bypassing the
        daemon entirely) with the identical `history` argument, repeated three times, produced `43`,
        `42`, `42` — genuine model non-determinism, not a wiring bug in this context's own code. The
        same class of unreliability `CTX-202.1` already documented for this exact model on a
        different, structured-extraction task.
    *   *Impact:* `TEST-006` uses Anthropic instead (skips cleanly without a real key, same pattern
        as `CTX-202.1`'s own real-extraction tests). `TestRealLLMChatJob.test_001` (`CTX-201.1`'s own
        pre-existing Ollama test, unrelated to `history`) is untouched — this correction is scoped
        to the one new test that actually needed precise recall to prove anything.

*   **Deviation 3 (found by Keith actually using the shipped feature, twice, in the real native
    window): two real bugs neither of us caught before merge, both fixed the same session.**
    *   *Reasoning 1:* `"Invalid params: Unexpected parameter(s): history"` — the daemon subprocess
        the real app was running had been alive since 11:45am, long before Phase 1's `history`
        param was added to `daemon.py`. Python doesn't hot-reload like Vite does; the running
        process's own `inspect.signature()` check (correctly, from its own stale point of view)
        rejected a parameter its in-memory code didn't know about. Not a code bug — killed and
        relaunched the app; confirmed the fresh process's signature was correct before reporting
        it fixed.
    *   *Reasoning 2:* Immediately after that fix, a second real error: `"No LLM provider
        configured."` — no `config.json` exists anywhere on this machine at all (checked directly),
        because `SPEC-303` (the settings UI that would let a human set `llm_provider`) doesn't
        exist yet. The old code's hard error meant the chat surface's plain-chat fallback could
        never work on any fresh install, with no way to unblock it short of hand-editing a file —
        a real, structural gap this spec's own `App.tsx` implementation introduced (every other
        route it calls has its own hardcoded default; `llm.chat` didn't).
    *   *Impact:* Fixed as its own small commit on this same branch/PR rather than a separate
        context — both are direct consequences of exactly what this context shipped, not unrelated
        work. `llm_chat` now falls back to `llm_providers._DEFAULT_PROVIDER` ("anthropic", matching
        `component_extraction.prompt.md`'s own existing default) when unconfigured; an explicit
        param or a real configured value still wins. Verified for real against the actual running
        app's exact conditions (real keychain secrets, `llm_provider` genuinely unset) after
        restarting the daemon — the same "Python doesn't hot-reload" lesson applied a second time,
        deliberately, instead of trusting a stale process again.
