# CTX-304.1: Library & Project Storage: schemas + file I/O

> **Spec Reference:** Links to [SPEC-304](../specs/SPEC-304-project-library-storage.md)

The first real slice of `SPEC-304`: the six object schemas and real file-based read/write for all
of them, resolving the inherited project-root-location question along the way. Deliberately does
**not** cover the `.index/` SQLite cache or KiCad `.kicad_sym`/`.pretty` import/export — both named
explicitly in `SPEC-304`'s own scope, both deferred to a follow-up context (see Plan Drift).

## 1. Feature Definition & Execution Plan

### Phase 1: Rust `storage_root` resolution
*   [x] `DaemonConfig` gains `storage_root`, resolved via `ensure_storage_root`/`resolve_storage_root`
    -- the exact "Rust-computed, never read from `config.json`" treatment `output_dir` already gets
    (`SPEC-301`/`CTX-301.1`), reused rather than inventing a second mechanism. Resolves the open
    question `PRODUCT-PLAN.md` §8 and `SPEC-304` §3 both name: a fixed location under the app's own
    data directory (`<app_data_dir>/storage`), not a user-chosen picker.
*   [x] Wired into `spawn_daemon` alongside `output_dir`.

### Phase 2: `library_store.py` -- schemas + file I/O
*   [x] Six objects, matching `PRODUCT-PLAN.md` §4's directory layout exactly: Part
    (`library/parts/<id>.part.json`), Symbol (`library/symbols/<id>.json`), Footprint
    (`library/footprints/<id>.json`), Project (`projects/<name>/project.json`), Artifact
    (`projects/<name>/artifacts/<id>.json`), Conversation (`projects/<name>/conversation.jsonl`,
    append-only).
*   [x] Provenance is schema-enforced on Part, not documented as a convention: `save_part` raises
    `SchemaValidationError` if any required field (`manufacturer`/`package`/`pins`/`datasheet_url`)
    has no provenance entry — `SPEC-300` §2.2's "must reject," directly.
*   [x] Enclosure Artifacts must record `board_revision` — the one real gap the `SPEC-304`
    ID-collision resolution carried forward (`ROADMAP.md` §3.3), enforced here, not just named.
*   [x] Decoupled from `daemon.py`'s `CONFIG` global, matching `kicad_bridge`/`freecad_bridge`'s own
    `configure()`-called-from-`_apply_env_config` pattern.

### Phase 3: Wire daemon routes
*   [x] Fourteen `library.*`/`project.*` routes, gated on `library_store is not None` matching the
    existing bridge-import pattern — a broken import here can't take down anything else.
*   [x] `_apply_env_config` calls `library_store.configure(storage_root=...)` alongside the existing
    bridge-configure calls.

## 4. Plan Drift & Architectural Changes

*   **Deviation, deliberate: the `.index/` SQLite cache is out of scope for this pass, despite being
    named in `SPEC-304`'s own scope.** Reasoning: nothing in this codebase yet needs cross-project
    search fast enough to justify it — there is exactly one thing that reads this storage today
    (this context's own tests) and no UI (`SPEC-305`/`306`) to make a query slow in the first place.
    Building the index-rebuild-on-stale-check mechanism `PRODUCT-PLAN.md` §4 describes before
    anything exercises it risks getting the staleness-detection design wrong against an imagined
    access pattern rather than a real one. Impact: `list_parts`/`list_projects`/`list_artifacts`
    above do a real directory listing on every call — correct today, and honestly not what
    `SPEC-304` ultimately wants once there are enough records for that to matter. Tracked as
    `CTX-304.2`'s job, not silently dropped.
*   **Deviation, deliberate: KiCad `.kicad_sym`/`.pretty` import/export is out of scope.**
    `SPEC-307`/`SPEC-308` are the specs that actually need to produce real KiCad library files from
    a Symbol/Footprint record — building that export logic here, before either spec exists, would be
    guessing at a contract neither has defined yet. This context's Symbol/Footprint records are
    plain JSON, not yet round-trippable to a real `.kicad_sym`/`.pretty` file.
*   **Non-deviation, confirmed as designed: `storage_root` reuses `output_dir`'s exact mechanism
    rather than inventing a second one.** Considered a separate env var or a first-run directory
    picker; rejected both — the existing `DaemonConfig`/`build_daemon_env` channel already solves
    "Rust computes a real path, hands it to Python at spawn, and it can never silently disagree with
    where the app's data actually lives," and a first-run picker is real UI scope this context isn't
    built to carry.
*   **Non-deviation, confirmed as designed: provenance is validated per required field, not as one
    blanket flag.** `SPEC-300` §2.2 specifically promises per-field provenance (so a user can correct
    one field without invalidating the rest) — `PART_PROVENANCE_REQUIRED_FIELDS` and
    `_validate_part_provenance` check each field's own entry, matching that promise exactly rather
    than a cheaper single `has_provenance: true` shortcut that wouldn't actually support it.
