# CTX-334.3: KiCad's Own Libraries in Component Search

> **Spec Reference:** Links to
> [SPEC-334](../specs/SPEC-334-footprint-literacy-and-component-detail.md)

## 1. Feature Definition & Execution Plan

The last open question in `SPEC-334` §2 that is still this spec's to answer. The two search
namespaces were never connected, so a footprint-shaped query went to the LLM part search, which
guessed at a manufacturer part number:

> *"I have a hunch that the component I searched for ... is a kicad only reference name and would
> not be searchable with our component search."*

Correct, and the failure was the expensive kind: a paid call returning a confident wrong answer.

### Phase 1: Search KiCad's libraries on every query

*   [x] `ComponentDiscovery.handleSearch` calls `searchFootprints` before `searchComponents`.
*   [x] **Deliberately not a query classifier.** A classifier is a new component that can be wrong,
        and when it is wrong it is silently wrong. `kicad.search_footprints` is local disk I/O:
        free, instant, and unable to hallucinate. Running it always turns *"did we detect
        correctly?"* into *"did we find anything?"* — a question with an observable answer.
*   [x] It runs first because it returns first, so a user who typed a footprint name has their
        answer while the LLM is still working.
*   [x] A failure there is swallowed. A missing `fp-lib-table` is an ordinary state, not an error
        worth interrupting the search the user actually asked for.

### Phase 2: Say what the hits are

*   [x] Rendered above the part candidates and independently of them, so the free answer survives a
        part search that finds nothing or fails outright — the case that used to be worst.
*   [x] Labelled *"These are footprints, not parts — a shape on the board, not something to
        order"*, because the whole defect was two namespaces reading as one.
*   [x] Says the results come straight from KiCad's installed libraries, so nothing is a guess.
*   [x] Capped at 8 with a count of the rest; `DIP-8` really returns 25.

## 4. Plan Drift & Architectural Changes

*   **The measurement made the design argument better than the reasoning did.** I chose
    "always search, never classify" on the grounds that a classifier is a thing that can be wrong.
    That is true but it is an argument about risk, and it left a real objection unanswered: running
    a footprint search on every part query should clutter the results.

    Driving real queries through the frozen sidecar against KiCad's own libraries showed the
    objection is empty — **the search self-selects.**

    | Query | Footprint hits |
    | :--- | :--- |
    | `PinHeader_1x04_P2.54mm_Vertical` | 4 |
    | `DIP-8` | 25 |
    | `555` | 13 |
    | `NE555P` | **0** |
    | `ATtiny85` | **0** |

    A manufacturer part number matches nothing in KiCad's libraries, so a part search gains no
    noise at all. There was never a routing decision to get right. The interesting row is `555`: 13
    hits *and* a real part search, which is exactly the ambiguous case a classifier would have had
    to guess at, and where showing both is obviously correct.

*   **A cheap, certain answer was sitting next to an expensive, uncertain one for months.**
    `kicad.search_footprints` has existed since `CTX-308.1` — synchronous, local, free — while
    `component.search` is a paid LLM call. Nothing connected them, so the failure mode was the worst
    available pair: the app spent money to return a confident guess in the one case where a free
    lookup would have returned the right answer instantly. Worth recording as a shape rather than an
    incident: when a route cannot hallucinate and costs nothing, "run it as well" is almost always
    cheaper than deciding whether to.

*   **What was not verified.** The real-library measurement is macOS with KiCad 10 installed. On a
    machine without KiCad, `fp_lib_table` finds nothing and every query returns zero hits — the
    surface then renders exactly as it did before this change, which is why TEST-004 exists. Not
    click-tested in the running app; the route was driven directly over JSON-RPC.

## 5. What this closes, and what it does not

`SPEC-334` had two open questions. **This answers the first.**

**The second — "which NE555P am I getting" — is deliberately not answered here, and is not being
carried as open work.** It is about disambiguating LLM part-search results by package, temperature
grade and pin layout: a different mechanism from reading a `.kicad_mod` off disk, and `SPEC-306`'s
surface rather than this one. Keeping it inside a spec titled *Footprint Literacy* is how it stays
unaddressed while looking tracked.

The maintainer's decision, recorded because it is a priority call and not an oversight:

> *"q2 isn't really the focus right now. the education of the user for the project is a bigger deal
> to me and we have been building the ground work for the teaching part given a project and
> schematic goal."*

That is consistent with what this family has actually been building — `SPEC-332` for ERC, `SPEC-334`
for footprints, and `SPEC-114`/`340`/`342` for manufacturability all explain rather than decide.
Part-number disambiguation is a procurement question wearing a teaching question's clothes, and it
should be picked up when it is the real focus, from `SPEC-306`.
