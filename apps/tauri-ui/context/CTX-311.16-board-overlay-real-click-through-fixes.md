# CTX-311.16: Real click-through fixes for the board-inside-enclosure overlay

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

`CTX-311.15` shipped with both suites green and real `kicad-cli`/`trimesh` prototyping behind its
coordinate design, but -- exactly as its own Plan Drift predicted -- had not yet had a human
click-through. The first one, against a real board
(`NFC_Reader_ESP32.kicad_pcb`, 49.5x106.5mm), surfaced two real, distinct bugs neither suite caught:
the board rendered entirely disjoint from the enclosure instead of composited inside it, and the
unknown-3D-model disclosure read "REF\*\*, REF\*\*, REF\*\*, REF\*\*" -- four indistinguishable copies
of KiCad's own default unannotated-footprint placeholder.

## 1. Feature Definition & Execution Plan

### Phase 1: root-cause the disjoint render -- verified numerically, not assumed
*   [x] Reproduced directly: exported the real board glb and the real enclosure glb for this exact
    board via the daemon's own functions, loaded both with `trimesh`, and compared bounds.
    `computeBoardOffset`'s original `+marginMm/1000` on Z put the transformed board's Z range at
    `[0.0025, 0.109]` -- entirely outside the enclosure's own real Z range, `[-0.1115, 0]`.
*   [x] Traced the real cause: `freecad_bridge.py`'s own `_Y_UP_ROTATION` (`CTX-311.5`, a -90 degree
    rotation about X fixing the unrelated Z-up/Y-up mismatch) leaves the enclosure's local Z running
    in the *opposite* direction from its own pre-rotation FreeCAD depth axis. The board's own glb (a
    separate toolchain, `kicad-cli`, never rotated) keeps Z increasing in the same direction as
    increasing real KiCad Y -- confirmed directly, not assumed, via `--user-origin`'s own documented
    plain-subtraction semantics and the board's own measured bounds landing exactly at `[0,
    width_mm]`/`[0, height_mm]`.
*   [x] Confirmed the fix numerically before touching any code: mirroring the board's own Z (negate)
    combined with a *negative* margin offset lands the transformed board's Z range at exactly
    `[-0.109, -0.0025]` -- inside the enclosure's `[-0.1115, 0]` with precisely the expected 2.5mm
    (wall + clearance) margin on both ends, cross-checked two independent ways: real standoff-position
    algebra, and a real `trimesh` containment test simulating three.js's own `position` + `scale`
    composition.
*   [x] Confirmed X needs no equivalent mirror: `CTX-311.5`'s rotation is about the X axis and never
    touches it, and both toolchains already agree on its direction (verified the same way, not
    assumed by analogy).
*   [x] `EnclosureViewer.tsx`: `computeBoardOffset`'s Z component flipped to negative; new
    `BOARD_Z_MIRROR = [1, 1, -1]` constant applied as the board `<primitive>`'s own `scale` prop,
    alongside the existing `position`.

### Phase 2: root-cause the "REF\*\*" disclosure -- verified against the real board file, not assumed
*   [x] Confirmed directly against the real `.kicad_pcb` file (`grep`, not guessed): 4 real
    `MountingHole:MountingHole_3.2mm_M3` footprints on this board are genuinely unannotated in KiCad,
    all literally sharing the default placeholder reference text "REF\*\*" -- the disclosure was
    accurate, not a data bug, but unhelpful: four identical strings give the user no way to tell which
    physical parts are affected, and a screw hole was never expected to have a rendered 3D model in
    the first place (it's already represented separately by the enclosure's own standoff geometry).
*   [x] `kicad_bridge.list_footprint_models` gains `is_mounting_hole`, reusing `get_mounting_holes`'s
    own already-established real recognition convention (`"mountinghole" in library` or an `H<digits>`
    reference) rather than inventing a new one.
*   [x] `daemon.py`'s `kicad_get_component_heights` skips any footprint where `is_mounting_hole` is
    true -- neither known nor unknown, since it was never a real candidate for a 3D model at all.
    Verified live against the real board: 4 mounting holes now correctly excluded, the 5 real
    components (`J3`, `D1`, `J1`, `J2`, `R1`) correctly retained.

**Real, hands-on verification beyond the automated suites**: the Z-mirror fix was verified against
the real board+enclosure glb pair via `trimesh` (both the standoff-position algebra and a direct
bounding-box containment simulation of three.js's own transform composition), and the mounting-hole
exclusion was verified against a real, live KiCad connection with this exact board open, confirming
the real 4-vs-5 split. **Not yet verified**: an actual human click-through of these two specific
fixes in the running app -- the original report was a screenshot, not an interactive session, so
whether the board now visually reads as "inside" the enclosure at a glance (not just numerically
contained) and whether the disclosure text now reads cleanly with the noise removed are both still
open until someone looks at the real render again.

## 4. Plan Drift & Architectural Changes

*   **Not a deviation from `CTX-311.15`'s own plan -- a real bug in it, found the way this whole
    `SPEC-311` viewer effort has repeatedly found bugs before: a human actually looking at the real
    render.** `CTX-311.15`'s own Testing Requirements Matrix explicitly named "the real click-through
    in the running app" as unverified; this context is that click-through's own real result. Both
    bugs were root-caused with the same discipline the rest of this viewer's history uses --
    `trimesh`/live-KiCad verification against real files before writing any fix, not guessed from
    reading the code alone (`CTX-311.5`'s own postmortem explicitly warned that bounding-box-extent
    checks alone can hide exactly this class of axis-direction bug, and the Z-mirror investigation
    here started by checking whether the same blind spot applied to this context's own earlier
    prototyping -- it did).
