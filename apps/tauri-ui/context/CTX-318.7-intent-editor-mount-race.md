# CTX-318.7: Implementation Context: The Intent Editor's Mount Race

> **Spec Reference:** Links to [SPEC-318](../specs/SPEC-318-in-context-agent-chat-and-review.md)

Frontend CI failed on a PR that changed only Markdown. The failing assertion was
`Unable to find an element with the placeholder text of: /I want to build/` -- clicking **Add** on
the project intent editor had not opened it. It was a real bug in the component, not a test
problem, and this is the third time it has been treated as a timing number.

## 1. Feature Definition & Execution Plan

### Phase 1: get the actual failure, not the summary
*   [x] Recovered attempt 1's logs from the GitHub API rather than reading the re-run. The failure
    was `TestingLibraryElementError`, not a test timeout, and the DOM at that moment showed the
    editor closed with the **Add** button still present.
*   [x] So waiting longer could never have helped: the state being waited for was never going to
    become true. `src/test-setup.ts` already says this in its own comment -- the deadline had been
    raised from 1s to 5s after two earlier instances -- and it failed at 5s anyway.

### Phase 2: reproduce it locally
*   [x] It reproduces. Six full-suite runs: one failure. Twelve more: one failure, in a **different
    test in the same file**, with the identical message. Roughly one run in eight.
*   [x] The two failing tests differ only in setup; both click **Add** and both find no textarea.

### Phase 3: observe the cause instead of inferring it
*   [x] Two `console.log` probes, one in `IntentEditor`'s reset effect and one in `startEditing`.
    At the failure they printed in this order:

        [probe] startEditing clicked
        [probe] reset effect ran for weather-pcb

    In every passing run the order is reversed. The click sets `editing` to `true`; the component's
    own **mount** effect then sets it back to `false`, and nothing ever sets it again.

### Phase 4: fix the cause
*   [x] `IntentEditor` reset its state in `useEffect(..., [projectName])`. That effect runs on mount
    as well as on a project change, and it runs **after** the commit that put the editor on screen
    -- so a click landing in that window is silently undone.
*   [x] Replaced with a `key`, which is React's own answer to "reset state when a prop changes". A
    remount has no post-commit state write, so the window does not exist.
*   [x] `IntentEditor` mounts only once `Overview`'s conversation load resolves, which is what makes
    the window reachable at all -- and what makes this a real user-facing bug, not only a test one.

## 4. Plan Drift & Architectural Changes

**1. I called it a slow-runner flake, and it was not.** My first read was that a 1000ms `waitFor`
deadline had lost a race under CI load. Two things were wrong with that. The deadline was already
5000ms -- `src/test-setup.ts` had been raised twice for this exact test file, and its own comment
says "raising a number twice is the signal that the number was never the problem". And the failure
was `Unable to find an element`, which is a state that never arrived, not a slow one. I read the
re-run instead of the failing attempt's log, and the summary instead of the evidence.

**2. There is no deterministic regression test for this, and I tried four ways to build one.** A
synthetic mount-window click, an out-of-`act` promise resolution, a microtask-chained real
`element.click()`, and a synchronous assertion straight after `rerender`. All four passed on the
buggy code. The reason is measurable rather than assumed: Testing Library wraps `render`,
`rerender`, `fireEvent` and `waitFor` in `act`, which flushes passive effects, so the window this
bug lives in is closed by the tooling on demand. It opens only under real scheduler pressure. The
honest guard is therefore structural -- there is no longer any post-commit state write to lose --
plus the repeat-run evidence, and this is written down rather than papered over with a test that
looks decisive and is not.

**3. The same pattern is in `ReviewPanel` and I did not change it.**
`ReviewPanel.tsx:52` resets `findings`, `running` and `error` in a `useEffect` keyed on
`[scope, scopeId]` -- the identical shape, and a **Run Review** click in the mount window would be
undone the same way. It is not a copy-paste fix: `ReviewPanel` also has a `menuCommand?.nonce`
effect that calls `handleRunReview()`, and keying the component would make that effect run on every
remount, so switching projects with a stale `menuCommand` would fire a real LLM call nobody asked
for. That is precisely what `SPEC-339` says must never happen. The fix is a `key` plus a ref
holding the last handled nonce, initialised to the current one so the mount pass is a no-op --
worth doing, in its own change, with its own click-through.

**4. Not verified: the user-facing symptom.** The window is reachable in the real app -- the editor
mounts when the conversation load resolves, so a fast click after opening Overview can hit it. I
have not reproduced that by hand in the running window, and given how narrow it is I probably
could not. The claim being made here is that the class of failure is removed, not that a specific
user click was seen to break and then not break.
