# CTX-306.7: Implementation Context: Visual Footprint & Symbol Previews

> **Spec Reference:** Links to [SPEC-306](../specs/SPEC-306-component-discovery.md)

Real, detailed live-testing feedback on the footprint-search flow (an ESP32-S3 footprint search
that came back empty): a footprint's pad layout and a symbol's pin arrangement are inherently
visual, and text alone ("Footprint linked: MyPCBLibs__MP1584EN_5V_Module") never let the user judge
whether a match was right without leaving the app to open it in KiCad. This is item 1 of 3 in the
user's own explicit ordering (visual previews → per-project footprint override → agent-guided
search); `CTX-306.6`'s own Phase 4 already did the real feasibility research this context builds
on -- `kicad-cli sym export svg`/`fp export svg` were already proven, real, working invocations
inside this repo's own test suite, never surfaced to a user before now.

## 1. Feature Definition & Execution Plan

### Phase 1: Backend -- real SVG rendering routes
*   [x] `kicad_cli.py`: `export_symbol_svg(kicad_sym_path)` and `export_footprint_svg(pretty_dir,
    footprint_id)`, mirroring `export_board_glb`'s own real subprocess/error-handling shape. Both
    scan a fresh per-call temp output directory for whatever `.svg` `kicad-cli` actually wrote,
    rather than assuming a filename.
*   [x] `daemon.py`: `library_render_symbol_preview(symbol_id)` and
    `library_render_footprint_preview(footprint_id)` -- each guarantees a real, current
    `.kicad_sym`/`.kicad_mod` file exists first (reusing the already-idempotent
    `export_symbol_kicad_sym`/`export_footprint_kicad_mod`, never assuming "Export Symbol/Footprint"
    was already clicked), then renders and returns the real SVG text inline. Both routes registered
    conditionally (`library_store`/`kicad_cli` both present) and added to `ASYNC_ROUTES` -- a real
    subprocess call, not instant file I/O.

### Phase 2: Frontend -- fetch and render
*   [x] `lib/footprints.ts`: `renderSymbolPreview(symbolId)`/`renderFootprintPreview(footprintId)`,
    both `submitJob`-based (matching `searchCommunityFootprints`'s own "real but not instant"
    precedent), returning the raw SVG string.
*   [x] `PartDetail.tsx`: two `useEffect`s (keyed on `savedSymbol?.symbol_id` /
    `savedPart?.footprint_id`) fetch a preview automatically as soon as a symbol/footprint exists --
    never gated on the user clicking Export first. Rendered inline via `dangerouslySetInnerHTML`
    (kicad-cli's own real SVG output, never user-supplied text) inside a white-background box (a
    KiCad SVG assumes a light background regardless of the app's own dark theme, the same kind of
    render-target exception `EnclosureViewer.tsx`'s own `VIEWER_BACKGROUND_COLOR` already makes for
    its 3D canvas). A failed render (e.g. no local KiCad install) shows a small, non-blocking
    message -- the rest of Part Detail stays fully usable either way.

### Phase 3 (explicitly not attempted): search-result thumbnails
*   [x] Investigated, not built: the user's own feedback asked for a visual "in the search or after
    it is selected." This context builds the "after it is selected" half only. A thumbnail per
    *search candidate* (before any "Use this" click) is real additional scope: an installed KiCad
    library candidate's footprint isn't yet a `library_store` record at all -- it lives in whatever
    real `.pretty` directory KiCad's own `fp-lib-table` points to, which the current
    `export_footprint_kicad_mod`/`render_footprint_preview` pair never touches. Rendering it would
    need a second code path that resolves and renders directly from that external library path,
    not `library_store`'s own on-disk layout. Named here as real, honest follow-up work, not
    silently dropped.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (named up front, not a surprise): search-result thumbnails deferred.**
    *   *Reasoning:* see Phase 3 above -- an installed KiCad library candidate isn't a
        `library_store` record until "Use this" is clicked, so rendering it needs a second,
        real-library-path-aware render route this context doesn't build.
    *   *Impact:* named as real follow-up work; not part of this slice's own scope.
*   **Deviation 2: `bg-white` used deliberately for both preview boxes, not a theming inconsistency.**
    *   *Reasoning:* a KiCad-rendered SVG assumes a light background (dark lines/pads on white);
        rendering it directly against this app's dark surface would make thin lines unreadable.
    *   *Impact:* both preview containers force a white background regardless of the rest of the
        app's own dark theme -- the same category of exception `EnclosureViewer.tsx`'s own
        `VIEWER_BACKGROUND_COLOR` already established for a different real render target. Worth
        re-checking once `SPEC-317` (light/dark/system theme) lands, in case a light theme makes
        this look inconsistent rather than necessary -- not expected to need a code change either
        way, just a visual recheck.
