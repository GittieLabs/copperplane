# CTX-321.2: Implementation Context: Provider Configuration Editor UI

> **Spec Reference:** Links to [SPEC-321](../specs/SPEC-321-provider-configuration-ui.md)

Phase 2 of 2: the real editor `CTX-321.1`'s own text named as its follow-up -- add/edit/remove
provider records, bind `reasoning`/`fast` to them, see a migrated install's real resolved state, all
on top of the wire `CTX-321.1` already built and merged. `managed` never appears anywhere in this
surface, per the user's own explicit product-scope instruction this phase: Managed stays a real,
working backend concept with no reachable UI path until hosting/auth/billing are actually decided.

## 1. Feature Definition & Execution Plan

### Phase 1: one small backend gap `CTX-321.1` left open, needed to render §2.5's own requirement
*   [x] `daemon.py`'s `_detect_capabilities()` gains `configured_secret_refs` -- every secret ref the
    real keychain currently has a value for, vendor and custom alike. `CTX-321.1`'s own
    `collect_known_secrets` (Rust) already pushes a custom `api_key_ref`'s value into
    `CONFIG["secrets"]` exactly like every vendor key; the existing `llm_providers` capability field
    only ever surfaced that for the four fixed vendor names. `SPEC-321` §2.5 requires "whether a key
    is currently saved" per record, for *any* record -- this is the one new field that answers it
    generically, confirmed directly by reading `configure_daemon`'s `CONFIG["secrets"] = dict(secrets)`
    assignment and `collect_secrets_for`'s `filter_map` (Rust) before adding it, not assumed.

### Phase 2: `settings.ts` -- the two small pieces of logic the editor needs, testable in isolation
*   [x] `DaemonCapabilities` gains `configured_secret_refs: string[]`.
*   [x] `isNonLoopbackBaseUrl(base_url)` -- the exact `SPEC-208` §3 / `SPEC-321` §2.5 exfiltration
    check (`null` never a risk; `localhost`/`127.0.0.1`/`::1` never a risk; anything else, including
    an unparseable string, is), pulled out as a pure, directly-testable function rather than inlined
    once in the component.
*   [x] `confirmRemoveRoleBoundProvider(recordId, boundRoles)` -- the same real, harder-to-ignore
    native-modal treatment `confirmStorageLocationChange` already established for a different real
    risk (SPEC-110), applied to the real risk `SPEC-321` §3 names: removing a record a role is still
    bound to.

### Phase 3: `ProviderConfigEditor.tsx` -- the real editor, a new file (matches this repo's own
`ViolationsList`/`AgentChat` precedent of extracting a complex, reusable panel rather than growing
`Settings.tsx` past its current size)
*   [x] Loads its own `records`/`provider_roles`/`provider_roles_saved` via `getProviderRecords()` --
    `config`/`capabilities` are passed down from `Settings.tsx` as props (which already owns fetching
    both), matching `ViolationsList`'s own presentational-child convention.
*   [x] A list of records (id, kind, Edit/Delete) with a per-record key row (only when
    `api_key_ref` is non-null) reusing the exact enter-and-save-only pattern `Settings.tsx`'s old
    four hardcoded key rows already established.
*   [x] Add/Edit form: id (immutable once saved -- disabled, not just discouraged, when editing an
    existing record), `kind` restricted to `anthropic`/`openai_compat`/`google` (never `managed` --
    `PROVIDER_KIND_OPTIONS` is a fixed 3-item array, structurally incapable of offering it), base
    URL, a model field per role (blank allowed, meaning "can't serve this role" per `SPEC-208`
    §2.3.2), two capability checkboxes with the "a claim, not a measurement" reminder `SPEC-208` §2.4
    already established, and a "Requires an API key" checkbox that derives `api_key_ref` as
    `${id}_api_key` when checked, `null` otherwise (a design decision this phase made -- see Plan
    Drift).
*   [x] The record-must-be-saved-before-its-key-can-save ordering (`SPEC-321` §2.2/§3) is enforced
    structurally, not just documented: a not-yet-saved new record's draft form shows no key input at
    all, only a disabled-with-reason note ("Save this provider first").
*   [x] The exfiltration warning (`isNonLoopbackBaseUrl`) shown inline, live, both while editing a
    draft and on every already-saved record's own row -- never blocking a save.
*   [x] Editing a saved preset id shows the "permanently overrides its default" note `SPEC-321` §3
    calls for, non-blocking.
*   [x] Deleting a record checks both roles for a binding to that id first; if either is bound, calls
    `confirmRemoveRoleBoundProvider` and only proceeds on confirmation. Confirmed proceeding leaves
    the dangling binding exactly as the user chose -- no silent auto-reassignment invented (see Plan
    Drift).
*   [x] Role binding: two `<select>`s populated from the current `records` list (so only currently-
    saved ids, presets included, are ever offered), saving immediately on change via the same
    complete-set `saveProviderConfig` contract every other mutation here uses.
*   [x] Migration display: when `provider_roles_saved` is false, a banner states the real resolved
    binding `migrate_legacy_config` already computed server-side (`CTX-321.1`), not a blank slate.
*   [x] `managed` is additionally rejected client-side by id, with a clear message, if somehow typed
    into a new record's id field -- defense in depth on top of `_resolve_provider_records`'s own
    server-side filtering (`CTX-321.1`), which would otherwise silently no-op rather than explain
    why.

### Phase 4: `Settings.tsx` -- wiring, and removing what this replaces
*   [x] The old "LLM Provider" section (one `<select>` over `ALL_PROVIDERS` + a free-text model
    field, writing via `setLlmProviderAndModel`) and the old "API Keys" section (four hardcoded
    `KEY_BASED_PROVIDERS` rows) are both deleted in full, along with their now-dead state
    (`providerModel`, `keyInputs`, `busyProvider`) and handlers (`handleSaveProvider`,
    `handleSaveKey`, `handleClearKey`).
*   [x] Replaced by a single `<ProviderConfigEditor>` under a renamed "Provider Configuration"
    section, rendered once `config` has loaded (never passed a `null` config), wired to `Settings`'s
    own `loadConfig`/`refreshCapabilities` via `onSaved`/`onCapabilitiesChange`.
*   [x] `setLlmProviderAndModel`/`ALL_PROVIDERS`/`KEY_BASED_PROVIDERS`/`secretKeyFor`/
    `KeyBasedProvider` are now unused in `Settings.tsx` and removed from its imports; `saveSecret`/
    `clearSecret` stay imported (the GitHub-token field, `CTX-314.2`, still uses them directly).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: a custom record's `api_key_ref` is derived (`${id}_api_key`) from a "Requires an
    API key" checkbox, rather than the user typing a free-text key-name field.**
    *   *Reasoning:* `SPEC-321` §2.5 lists the draft form's fields (id, kind, base URL, per-role
        models, two capability checkboxes) but does not specify how `api_key_ref` itself gets
        authored, only that "the key field is shown once a record with a non-null `api_key_ref`
        exists and is saved." A free-text key-name field would let a user accidentally alias onto an
        existing vendor's own key name (or a typo'd name that collides with nothing, silently no-op-
        ing); deriving it from the record's own `id` -- the same `${provider}_api_key` convention
        `secretKeyFor` already established for presets -- makes every record's key name predictable
        and collision-free by construction, at the cost of not letting two different records share
        one saved key (a real but narrow use case: e.g. two `openai_compat` records pointed at the
        same vendor with the same key). Judged the right trade for this phase; revisit only with a
        real user request for shared keys across records.
    *   *Impact:* the "Requires an API key" checkbox is the only control governing `api_key_ref`;
        there is no way to author a custom `api_key_ref` string independent of a record's `id`.
*   **Deviation 2: deleting a role-bound record, once confirmed, leaves the dangling binding as-is --
    it does not auto-clear or reassign the role.**
    *   *Reasoning:* `SPEC-321` §3 frames this as "the UI must warn before letting a save proceed,"
        not "the UI must prevent or repair it" -- and the spec's own philosophy elsewhere (the
        exfiltration warning: "states the fact and lets the user decide, rather than refusing to
        save") argues against inventing extra remediation the spec didn't ask for. `resolve()`'s own
        real `LLMProviderError` at the next chat/extraction call is the honest consequence of a
        deliberate choice, not a bug this phase should paper over.
    *   *Impact:* a user who confirms "Remove Anyway" on a role-bound record gets exactly what they
        asked for -- the record gone, the role binding pointing at an id that no longer resolves --
        and must rebind that role themselves on the next visit to this screen.
*   **Deviation 3: `ProviderConfigEditor` is a new, separate file rather than inline in
    `Settings.tsx`.**
    *   *Reasoning:* `Settings.tsx` was already 601 lines before this phase; `ViolationsList.tsx`
        (shared between `BoardAdvisor`/`SchematicAdvisor`) is this repo's own precedent for
        extracting a complex, self-contained panel into its own file rather than growing one
        component past a few hundred lines further. Confirmed this doesn't fight the repo's actual
        convention by checking `AgentChat.tsx`/`ReviewPanel.tsx`'s own extraction and their stub
        pattern in the parent's test file before committing to it.
    *   *Impact:* `Settings.test.tsx` stubs `ProviderConfigEditor` (matching the `AgentChat`/
        `ReviewPanel` precedent exactly) rather than re-mocking `getProviderRecords`/
        `saveProviderConfig` itself -- kept its own test file focused on wiring, not re-testing the
        editor's internals a second time.
