# CTX-333.2: Implementation Context: A Way to Reach Rename

`CTX-333.1` finished rename underneath — `library_store.rename_project`, the `project.rename`
route, nine tests, and a run through the frozen sidecar — and deliberately stopped short of a UI,
because where a rename lives in the project header is the same class of naming decision `SPEC-337`

## 1. Feature Definition & Execution Plan

### Phase 1: Edit the name, on the name
*   [x] **Rename** beside the project title, opening an inline editor on the title itself.
*   [x] Enter saves, Escape cancels.
*   [x] Save is refused for an empty name and for the name it already has — the route treats an
        unchanged name as a no-op, and a button that appears to do something and does nothing is
        worse than a disabled one.
*   [x] A refused name **stays in edit mode** with the typed text intact. A collision is something
        to correct, not to retype.

### Phase 2: The name follows
*   [x] The header, the rail and the open view all key on the project name; all three follow the
        rename directly rather than reloading the list from disk to learn a name already known.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: a native dialog cannot take text, which decided the design.** Every other
    confirmation in this app is a native `ask()` — removal, the storage change, the storage
    restart. Rename needs a *value*, not a yes/no, and Tauri's dialog plugin offers no text input.
    An inline editor on the title is the result, and it is better than the modal would have been:
    the thing being renamed stays visible while you rename it.

*   **Deviation 2: a test asserted the wrong thing twice about the rail, and the code was right
    both times.** The rail's selected entry renders `{'> '}{name}` as two text nodes, so its
    accessible name is `"> gamma"` and `getByText('gamma')` matches nothing at all. Worth recording
    only because the first failure looked exactly like "the rename did not reach the rail" — the
    header had updated and the rail appeared not to have. The distance between "my assertion is
    wrong" and "the feature is broken" was one query.

*   **Where the rename button sits, and what I left alone.** The header's second line now carries
    **Link**, **Close project** and **Remove from list** while the third carries the folder
    actions — so two project-level actions sit on the KiCad-project line. Rename went on the title,
    where it belongs, and the other two were left where they are. Regrouping them is a real
    improvement and it is not this context's, and doing it silently in a rename change is how a
    diff stops being reviewable.
