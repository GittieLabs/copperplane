# CTX-303.1: Settings Plumbing (Tier 1+2) and UI

> **Spec Reference:** Links to [SPEC-303](../specs/SPEC-303-settings-ui.md)

**Pending dependency, not yet merged:** `SPEC-300`'s shell entry-point resolution (PR #48, anchoring
Settings at the bottom of the rail) hasn't landed on `develop` yet as of this branch's creation.
This context's actual code doesn't depend on that PR's content — the Settings screen ships behind a
temporary trigger regardless (see Phase 3) — but the *permanent* home for that trigger is #48's
decision, not this context's to make twice.

## 1. Feature Definition & Execution Plan

Covers `SPEC-303`'s Tier 1 (LLM provider/model/key management) and Tier 2 (KiCad/FreeCAD
reachability + path overrides), end to end: real keychain/config plumbing that doesn't exist yet,
the daemon-side fixes that plumbing depends on, and a real screen a human can click through. Tier 3
(Copy Diagnostics) is deliberately deferred to a follow-up `CTX-303.2` — it has no dependency on
Tiers 1/2 and splitting it out keeps this context reviewable.

**Ground truth this plan is built on** (read directly from source, not assumed):
*   `core/tauri-rust/src/secrets.rs`'s `set_secret`/`delete_secret` exist, work, and are real
    (covered by a real-keychain round-trip test), but carry `#[allow(dead_code)]` — never called by
    anything.
*   `core/tauri-rust/src/config.rs`'s `load_config` only reads; no writer exists.
*   `core/tauri-rust/src/daemon.rs` already has `KNOWN_SECRET_KEYS`, `build_configure_request`, and
    the exact "read every known secret fresh from the keychain" logic this context needs to reuse —
    currently inlined once, in `spawn_daemon`.
*   `apps/tauri-ui/src/lib/ipc.ts`'s `dispatch(method, params)` already sends *any* JSON-RPC request
    to the daemon and resolves with its response — no new Rust command is needed just to talk to the
    daemon; only keychain/`config.json` I/O is genuinely new Rust surface.
*   `services/python-daemon/daemon.py`'s `configure_daemon` only ever touches `CONFIG["secrets"]`;
    `_detect_capabilities()`'s `llm_providers` is hardcoded to `[]`; both are emitted once at boot
    inside `main()`, with no on-demand route to re-check them later.

### Phase 1: Rust — keychain + config write path
*   [ ] `daemon.rs`: make `KNOWN_SECRET_KEYS` `pub`; extract `collect_known_secrets() -> BTreeMap<String, String>`
    from `spawn_daemon`'s inline closure into its own `pub fn`, reused by both `spawn_daemon` and the
    new commands below (so a live update always sends the daemon the *complete* current secret set,
    never a partial delta — sidesteps needing to change `configure_daemon`'s replace-not-merge
    semantics on the Python side at all).
*   [ ] `daemon.rs`: add `pub fn sync_secrets_to_daemon(app: &AppHandle) -> Result<(), String>` —
    rebuilds the secrets map via `collect_known_secrets()`, builds the request via the existing
    `build_configure_request`, and calls the existing `dispatch_to_daemon` directly (plain Rust call,
    not through IPC).
*   [ ] `secrets.rs`: add `#[tauri::command] save_secret(app, key, value)` and
    `#[tauri::command] clear_secret(app, key)` — both validate `key` against `KNOWN_SECRET_KEYS`
    (reject unknown keys), call the existing `set_secret`/`delete_secret`, then
    `sync_secrets_to_daemon`. Remove the now-inaccurate `#[allow(dead_code)]`.
*   [ ] `config.rs`: add `pub fn save_config(app, config) -> std::io::Result<()>` (the writer
    `load_config` never had) and `#[tauri::command]` wrappers `get_config`/`save_config_cmd`.
*   [ ] `lib.rs`: register all four new commands in `generate_handler!`.

### Phase 2: Python — on-demand capabilities + live provider/model update
*   [ ] `daemon.py`: add `_KEY_BASED_PROVIDERS = ("anthropic", "google", "openai", "perplexity")`
    (Ollama needs no key, excluded) and fix `_detect_capabilities()`'s `llm_providers` to
    `[p for p in _KEY_BASED_PROVIDERS if CONFIG.get("secrets", {}).get(f"{p}_api_key")]`.
*   [ ] `daemon.py`: add a new synchronous route `daemon.get_capabilities` — just calls and returns
    `_detect_capabilities()` on demand, so Settings can refresh after a save without waiting for the
    next boot's one-time `daemon.ready` notification.
*   [ ] `daemon.py`: extend `configure_daemon(secrets=None, llm_provider=None, llm_model=None)` to
    update `CONFIG["llm_provider"]`/`CONFIG["llm_model"]` only when explicitly passed (default
    `None` means "no change," not "clear") — Rust's spawn-time call never passes these, so this is
    additive and can't regress the existing spawn-time secrets-only call.

### Phase 3: Frontend — Settings screen, Tier 1 (provider/model/keys)
*   [ ] New `apps/tauri-ui/src/lib/settings.ts`: typed wrappers over `invoke('save_secret', ...)`,
    `invoke('clear_secret', ...)`, `invoke('get_config')`, `invoke('save_config_cmd', ...)`, and
    `dispatch('daemon.get_capabilities')`.
*   [ ] New `apps/tauri-ui/src/components/Settings.tsx`: provider picker, model text field, masked
    API-key inputs per key-based provider with Save/Clear, a "configured" badge per provider sourced
    from `daemon.get_capabilities`'s `llm_providers` (refreshed after every save/clear — never from a
    value the renderer holds itself).
*   [ ] `App.tsx`: a plain, temporary entry trigger (a button, not a rail item — `SPEC-300`'s real
    rail doesn't exist in code yet, same stopgap pattern `CTX-108.3` used for
    `kicad.inject_component`) toggling between the existing chat surface and the new Settings
    screen. Explicitly **not** the permanent placement PR #48 describes — noted in Plan Drift, not
    silently presented as final.

### Phase 4: Frontend — Tier 2 (KiCad/FreeCAD status + path overrides)
*   [ ] `Settings.tsx`: a connectivity panel showing `kicad_available`/`freecad_available` from
    `daemon.get_capabilities`, plus editable KiCad socket-path/timeout and `freecadcmd`-path-override
    fields backed by `get_config`/`save_config_cmd`.
*   [ ] A visible "Restart the app to apply" notice on exactly these three fields — they're read once
    from an env var at daemon *spawn* time (`CTX-106.1`), unlike Tier 1's live-updating secrets/
    provider/model. Getting this distinction wrong (implying a live update that doesn't happen) is
    the single biggest risk this spec's own §3 names.

## 4. Plan Drift & Architectural Changes

*   **Non-deviation, confirmed as designed: the frontend needed almost no new Rust surface for daemon
    communication.** `lib/ipc.ts`'s existing `dispatch()` already sends any JSON-RPC method
    (`daemon.configure`, the new `daemon.get_capabilities`) and resolves with its response — the only
    genuinely new Rust commands are for keychain/`config.json` I/O, which the daemon itself has no
    access to.
*   **Non-deviation, confirmed as designed: `configure_daemon`'s replace-not-merge secrets semantics
    are left alone, not "fixed."** A live update always resends the *complete* current secret set
    (via `collect_known_secrets()`, reused from `spawn_daemon`), so "replace" and "merge" produce the
    identical result by construction — changing Python's own semantics would have been solving a
    problem the Rust-side design already avoids.
*   **Deviation, expected to be recorded once Phase 3 lands:** the Settings entry point ships behind
    a temporary button in `App.tsx`, not the rail item `SPEC-300`/PR #48 describes, because that
    PR hadn't merged when this branch was created and the shell itself (`SPEC-305`) doesn't exist in
    code yet. Matches the precedent `CTX-108.3` already set for `kicad.inject_component`.
