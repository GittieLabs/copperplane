# CTX-311.7: Real root-cause fix: enclosure/lid rendered near-black regardless of lighting

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

`CTX-311.6` tried to fix "can't tell the lid apart from the body" with a frontend color override and
a lighter background/softer lighting. A follow-up real screenshot showed it hadn't worked: both body
and lid still rendered almost solid black (the lid a barely-visible dark maroon), regardless of the
lighting rebalance. Investigated properly this time, rather than tweaking light values again -- and
found the real root cause, one level deeper than `CTX-311.6` reached.

## 1. Feature Definition & Execution Plan

### Phase 1: real root-cause investigation
*   [x] **Confirmed live, not guessed**: parsed a real generated enclosure `.glb`'s own binary glTF
    JSON chunk directly (`struct`/`json`, no library assumptions) -- it had **no `"materials"` key at
    all**. `Part.Shape.exportStl` writes plain, colorless triangle geometry (STL has no material
    concept whatsoever), and the previous `trimesh.load(...); mesh.export(glb_path)` conversion never
    attached one either.
*   [x] **Confirmed why that renders black**: a glTF primitive with no material reference isn't
    "default gray" in any real, spec-compliant viewer -- the glTF 2.0 spec's own default material
    (used precisely when one is omitted) is `metallicFactor: 1, roughnessFactor: 1`, i.e. full metal.
    A fully metallic surface's visible color comes almost entirely from specular reflection of its
    environment, not simple diffuse light-times-albedo shading -- and this app's own `<Canvas>` has
    no environment/IBL map for a metal to reflect. This explains why `CTX-311.6`'s real lighting
    rebalance (higher ambient, dimmer directional, a fill light) could never have fixed the real
    problem: no amount of direct-light tuning changes a metal's near-total lack of diffuse response.

### Phase 2: real fix, at the source
*   [x] `freecad_bridge.py`'s shared `_export_glb()` (already the one real conversion path both the
    base shell and the lid go through, `CTX-311.5`) now assigns a real `trimesh.visual.material.
    PBRMaterial` before export: `metallicFactor=0.0`, `roughnessFactor=0.6` (a real, matte "3D-printed
    plastic" look), and a real, distinct `baseColorFactor` per caller.
*   [x] `_BODY_COLOR_RGB` (slate-400) for the base shell, `_LID_COLOR_RGB` (orange-500) for the lid --
    the same two colors `CTX-311.6`'s frontend override used, now real, portable data baked directly
    into each exported file instead of a runtime override only this app's own viewer applied.
*   [x] Verified live: parsed both the base's and the lid's own real exported glTF JSON --
    `metallicFactor: 0.0` on both, `roughnessFactor: 0.6` on both, and two real, distinct
    `baseColorFactor` values.

### Phase 3: remove the now-redundant frontend override
*   [x] `EnclosureViewer.tsx`'s `applyMeshColor`/`BODY_COLOR`/`LID_COLOR` (all of `CTX-311.6`'s own
    material-forcing code) removed -- the real material now lives correctly in each file itself, and
    keeping a second, frontend-only copy of "the right color" would be two sources of truth for the
    same fact, free to drift. `VIEWER_BACKGROUND_COLOR` and the `CTX-311.6` lighting rebalance both
    stay -- real, independent, still-correct contributions (a light background and gentler lighting
    are legitimately viewer concerns, not mesh data).

### Phase 4: tests
*   [x] `test_freecad_bridge.py`: a new real, no-mocks test confirms both the base's and the lid's
    own real exported `.glb` carry a real `metallicFactor: 0.0` material, and that their two real
    `baseColorFactor` values are distinct from each other.
*   [x] `EnclosureViewer.test.tsx`: the now-obsolete `applyMeshColor` describe block removed along
    with the code it tested.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `CTX-311.6`'s own fix did not work, and this context both fixes the real bug and
    removes `CTX-311.6`'s now-incorrect approach.** Recorded plainly, per this repo's own norm that a
    Plan Drift entry admitting a prior fix didn't work is not an admission of failure but the single
    most useful kind of entry here. `CTX-311.6` diagnosed the *symptom* (hard to tell body from lid,
    harsh-looking lighting) and treated both with real, defensible fixes (distinct colors, softer
    lighting) -- but never established *why* the existing appearance looked the way it did before
    choosing those fixes, so it fixed the wrong layer. This context did the actual investigation
    (parsing the real glTF JSON directly) before touching code again, and found the real root cause
    one level below where `CTX-311.6` looked.
*   **Deviation 2: fixed at the data source (`freecad_bridge.py`'s own export) rather than only in
    `EnclosureViewer.tsx`.** A materialless `.glb` is a real, incomplete CAD interchange file --
    opening it in any other real glTF viewer (Blender, an online viewer, a slicer) would show the
    same near-black result this app's own viewer did. Fixing the frontend alone (forcing metalness/
    roughness/color on load, which was seriously considered and partially drafted before this
    decision) would have left the exported files themselves still wrong for every other real
    consumer. Fixing the source is both more correct and, in this specific case, no more work than
    the frontend-only alternative would have been.
