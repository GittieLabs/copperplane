# CTX-113.2: Implementation Context: A Finding of Our Own Looks Like One

> **Spec Reference:** Links to [SPEC-113](../../../services/python-daemon/specs/SPEC-113-structural-consistency-checks.md)

`CTX-113.1` closed saying nobody had run the review in the app and read the answer. The maintainer
did. The findings were right, and every one of the four carried a chip reading **ERC finding** --
including the two ERC had said nothing about.

## 1. Feature Definition & Execution Plan

### Phase 1: the chip was labelled by the wrong fact
*   [x] `sourceChipLabel` chose between "ERC finding" and "DRC finding" on the file extension.
    `SPEC-113`'s checks read the `.kicad_sch` too, so they came out as ERC's work. The extension
    says which file was opened; only the check itself says which check ran.

### Phase 2: decide origin from an id, never from the model's words
*   [x] Every finding in the check block now carries a `finding_id` -- `kicad-1`, `copperplane-2` --
    generated by the daemon. The prompt tells the model to copy it back with the `source_path` it
    already copies.
*   [x] `review()` reads origin off that id. Asking the model which check found something would put
    the answer back in the place this whole check exists to take it out of.
*   [x] Three states, not two. A finding citing nothing identifiable is `None`, which is honest --
    defaulting it to KiCad is the reported bug, and defaulting it to ours is the same bug pointed
    the other way.

### Phase 3: a measurement is never allowed to be dropped
*   [x] The model decides what is worth flagging. That is right for its own judgement and wrong for
    a measurement: if it omits a symbol/footprint mismatch, the user simply never learns it.
*   [x] Any of our findings the model did not cite is appended in our own words.

### Phase 4: say it above the list and mark it on the card
*   [x] A line above the findings: *"2 of these were found by Copperplane. ERC and DRC do not
    report them."*
*   [x] Each such card gets an accent left border and a pill reading **Not reported by ERC or DRC**.
*   [x] The chip on those findings reads **Copperplane check**.

## 4. Plan Drift & Architectural Changes

**1. The click-through found in one look what `CTX-113.1` could not.** That context tested that the
findings compute, reach both tabs, cite the right file, survive the model failing, and are not
labelled as KiCad's *in the fallback*. Every one of those passed. The path the user actually takes
-- model succeeds, chip renders -- was the one path with no assertion on it, and it was wrong. The
lesson is narrower than "test more": the fallback was tested because I had just written it, and the
main path was not because it already worked.

**2. Origin cannot be a model judgement, and nearly became one.** The first design I considered
added an `origin` field to the findings block for the model to fill in. That is the same mistake
`SPEC-113` was written to fix, one level up: asking a language model to classify something the
process already knows. The id is generated here, copied back, and read here.

**3. `cited` had to come from what the model said, not from what resolved.** Built first from each
finding's *resolved* sources -- and `validate_source_refs` drops a ref whose file cannot be found,
so a stale path made the app print its own finding twice. A citation this app cannot resolve is
still a citation. Caught by a test, not by reasoning.

**4. Duplicate suppression is allowed to be fuzzy; classification is not.** If the model reports one
of our findings and forgets the id, a footprint-id match in its prose suppresses the duplicate. That
heuristic is deliberately never used to decide origin. Getting duplicate-suppression wrong shows the
reader something twice, which they can see; getting origin wrong misattributes silently, which they
cannot.

**5. The theme-token guard had a false positive, and I checked before relaxing it.**
`border-l-accent` and `border-y-line-subtle` were reported as undefined tokens. They are real
Tailwind v4 utilities -- the built CSS contains
`border-l-accent{border-left-color:var(--color-accent)}`, read out of `dist` rather than assumed.
The guard now strips a leading direction segment and still requires the colour underneath to be a
defined token; confirmed by pointing it at `border-l-bogus` and watching it fail. Relaxing a guard
to make new code pass is worth being suspicious of, so the evidence is recorded here.

**6. Not verified: how it actually looks.** The tests assert that the pill renders, the border class
is applied, and the count is right. Nobody has looked at the accent green against the amber
`WARNING` label on a real card, and those two colours sitting next to each other is the one thing a
test cannot judge.
