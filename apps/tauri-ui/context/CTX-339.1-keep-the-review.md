# CTX-339.1: Implementation Context: Keep the Review

> **Spec Reference:** Links to [SPEC-339](../specs/SPEC-339-review-persistence-and-staleness.md)

Reported from a real session: switching to Settings to change the theme and coming back destroyed
both the schematic and the PCB review. Two ERC or DRC runs and two real LLM calls, for files nobody
had touched, because the user changed a colour.

## 1. Feature Definition & Execution Plan

### Phase 1: keep it, against the file it judged
*   [x] `library_store.set_project_review_result` stores findings, when they ran, the provider and
    model, and the identity of the source file at that moment. A second key from `last_results`
    on purpose: that one feeds the agent's context and is capped at 25 because a model reads it;
    this one is read by a person, so truncating it changes what they are shown.
*   [x] The schematic area is judged against the `.kicad_sch`, the PCB and the enclosure against
    the `.kicad_pcb` -- an enclosure is measured from the board, so a board edit is what makes it
    stale, not a schematic edit that has not been pushed across.

### Phase 2: stat, then hash
*   [x] Size and mtime are compared on every read; the hash only when they disagree. KiCad
    rewriting a file it did not alter would otherwise throw away a good review and bill the user
    for another, and a restored backup moves mtime backwards.
*   [x] Verified against real files, all five paths: fresh, rewritten-with-identical-bytes, edited,
    file gone, and checks changed.

### Phase 3: say what changed, and never re-run
*   [x] Four states, each naming what actually happened rather than saying "stale": the file has
    been saved since, the file is gone, the checks changed, or nothing changed.
*   [x] Nothing re-runs on its own. The button is right there; the app volunteering "re-run this"
    would be volunteering the user's money.
*   [x] An area never reviewed shows nothing and says nothing, which is a different sentence from a
    stale one. The old UI said neither.

### Phase 4: close CTX-318.7's open item while the state handling is open anyway
*   [x] `ReviewPanel` reset its own state in an effect keyed on `scopeId` -- the pattern
    `CTX-318.7` proved silently undoes a click landing between the commit and the effect flush.
    That effect now has a second job, loading a kept review, which must not be a reset at all.
*   [x] Replaced with a `key` at all four mount sites, and the `menuCommand` nonce is held in a ref
    initialised at mount, so a remount cannot replay a stale menu command and spend a real LLM
    call nobody asked for.

## 4. Plan Drift & Architectural Changes

**1. Moving the reset to a `key` moves the guarantee to the callers, so the callers are now
checked.** A mount site that forgets the key leaks one project's review into the next, silently,
with nothing inside the component able to notice. `tests/reviewPanelKeyed.test.ts` reads every
`<ReviewPanel` in the source and fails without one -- confirmed by deleting a key and watching it
name the file. It also asserts it found at least one mount site, because a regex that matched
nothing would have passed while proving nothing.

**2. Two tests changed meaning, and that is the point rather than a nuisance.** `TEST-009` mounted
the panel with a `menuCommand` already set and expected a review to run. Under the old design a
remount replayed whatever command was last set; under the new one it does not, and `TEST-009b` now
asserts exactly that -- because a project switch firing a real, billed LLM call nobody asked for is
what `SPEC-339` says must never happen. The test was rewritten to bump the nonce after mount, which
is what a menu click actually is.

**3. A guard caught a gap I had left open one context earlier.** `test_ui_route_parity` requires
every module the daemon can report as degraded to have a plain-language description in the UI.
`CTX-113.3` added `structural_checks` to the degraded list and did not add its description, so a
user hitting it would have been shown a bare module name at the moment they were most confused.
Found by CI-grade tests locally, not by review.

**4. Two live-LLM tests failed in the full run and both pass on re-run.** A real model response
that `parse_json_response` could not read, and the datasheet guidance job. Neither touches this
change. Recorded rather than quietly re-run until green.

**5. Not verified: the thing that prompted this.** Switching to Settings, changing the theme, and
coming back to find both reviews still there, with an honest line saying when they ran. Every layer
is tested and the staleness verdict is exercised against real files on disk, but the round trip
that was reported has not been walked by a person.
