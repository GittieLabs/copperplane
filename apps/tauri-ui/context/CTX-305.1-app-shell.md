# CTX-305.1: App Shell & Navigation: real rail + area tabs

> **Spec Reference:** Links to [SPEC-305](../specs/SPEC-305-app-shell-navigation.md)

Builds the shell `SPEC-300` §2 designed and `SPEC-305` scoped for real: a Projects rail backed by
`SPEC-304`'s real storage, a Library entry, a Settings anchor, and five per-project area tabs.
Replaces `App.tsx`'s single-screen layout (`showSettings` toggle, one floating chat surface, a
floating Enclosure panel) rather than adding a second surface beside it.

## 1. Feature Definition & Execution Plan

### Phase 1: `lib/projects.ts` wrapping SPEC-304 routes
*   [x] Thin typed client for `project.*`/`library.*` daemon routes (`listProjects`, `saveProject`,
    `loadProject`, `listLibraryParts`, `loadConversation`, `appendConversationTurn`), following the
    existing `dispatch`-wrapping pattern the rest of `lib/` already uses.

### Phase 2: `Rail` + `NotBuiltPlaceholder` components
*   [x] `Rail` renders real projects and a real library count (never mocked data), with inline
    project creation and a Settings anchor at the bottom -- exactly `SPEC-300` §2's ordering.
*   [x] `NotBuiltPlaceholder` is the one, reused "visible-but-empty" body: names the owning spec
    instead of a bare "not built" message or an omitted tab.

### Phase 3: Restructure `App.tsx` into the real shell
*   [x] Top-level `view` state (`{kind: 'settings'}` | `{kind: 'project', name, area}` | `null`)
    replaces the `showSettings` boolean; `Rail` drives it instead of a toggle button.
*   [x] Five area tabs per selected project: Overview, Components, Schematic, PCB, Enclosure, in
    the order `SPEC-305`'s own diagram gives them.
*   [x] Overview re-houses the existing chat surface (`ChatMessageView`, `generate`/`inject`/plain-chat
    handling) unchanged in substance, now scoped to the selected project. Plain-chat turns persist
    to `SPEC-304`'s conversation log via `appendConversationTurn`, and are replayed from
    `loadConversation` on mount/project-switch -- resolving `SPEC-305` §3's named hazard (project
    switching must not leak state between projects) by resetting all local state on `projectName`
    change and reloading from the real log rather than keeping one global `chatHistory`.
*   [x] Enclosure re-houses `EnclosurePanel`/`EnclosureViewer` unchanged.
*   [x] Components/Schematic/PCB each render `NotBuiltPlaceholder` naming SPEC-306/308/309
    respectively.
*   [x] A fresh install (no projects yet) shows an explicit empty state instead of a broken or blank
    chat surface.

## 4. Plan Drift & Architectural Changes

*   **Non-deviation, confirmed as designed: Overview's persisted history only ever contains plain
    chat turns, matching `SPEC-302` §2's own named limitation carried forward by `SPEC-305`.** A
    `generate`/`inject` command's own message still isn't folded into `llm.chat`'s context or written
    to the conversation log. Considered widening the log to capture every message kind while
    rebuilding this surface anyway; rejected it as exactly the kind of "re-housing turns into a
    rewrite" `SPEC-305` §3 names as its own named hazard -- widening the persisted shape is a real
    design decision for whichever context finally deletes `parseCommand` (`SPEC-305` §3, still open),
    not a free upgrade to bundle into a shell restructuring.
*   **Non-deviation, confirmed as designed: initial project selection is "first in the list," not
    persisted across app restarts.** `SPEC-305` doesn't ask for a remembered last-open project, and
    `SPEC-304` has no field to store one yet. Selecting the first project on load (or the empty state
    if there are none) is the simplest behavior that satisfies the spec's own "selecting a project
    surfaces its area tabs" requirement without inventing a persistence mechanism the spec didn't
    ask for.
*   **State what was not verified:** this ran against exactly one already-running dev session on one
    machine (macOS), verified visually via screenshots of the live native window covering the empty
    state, Settings via the rail anchor, all five area tabs on a real created project, and the
    re-housed Enclosure panel's controls. Not exercised: creating a second project and confirming no
    conversation state leaks between them (SPEC-305 §3's own named hazard is addressed in code via the
    `projectName`-keyed effect reset in `Overview`, but wasn't independently re-verified by hand in
    the running app beyond the automated test covering it), and a real `kicad.generate_component`/
    `freecad.generate_enclosure` round trip from inside the new shell (both flows are unchanged code,
    already verified for real in `CTX-108.3`/`CTX-105.2`/`CTX-303.2`, just not re-run through this
    specific shell by hand this session).
