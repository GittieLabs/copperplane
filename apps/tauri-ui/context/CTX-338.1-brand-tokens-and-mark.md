# CTX-338.1: Implementation Context: The Copperplane Green, and the Mark

> **Spec Reference:** Links to [SPEC-338](../specs/SPEC-338-brand-in-the-app.md)

The brand kit has been in the repo since 2026-08-25 and the application used none of it. The one
green a user could see was Tailwind's emerald, which is worse than no green: it reads as a palette
nobody chose. `SPEC-336` §1 and §5 both said the first screen carries the app logo; `CTX-336.1`
shipped an `<h1>` and nothing noticed, because a heading reading "Welcome to Copperplane" satisfies
every test anyone would write about it.

## 1. Feature Definition & Execution Plan

### Phase 1: settle which green, by measuring rather than reading
*   [x] The brand table gives contrast "on white" and "on ink". Those are not the pairs this app
    renders: a filled button puts text *on the green*, and the app's grounds are `#0a0a0a` and
    `#ffffff`, not ink and paper. Computed WCAG 2.1 ratios for the real pairs.
*   [x] No single green works for both themes -- Copperplane green is 3.39:1 on the dark ground,
    Bright is 2.27:1 on white. Two tokens per theme, which is also what `SPEC-317` already requires
    of every colour.
*   [x] Dark: accent `#4FC17E` on `#0A1410` = 8.27:1. Light: accent `#10743F` under white text =
    5.85:1. Brand colour as text: 8.73:1 on the dark ground, 5.85:1 on the light one. All four
    clear AA for normal text.
*   [x] Confirmed independently after the fact: `mark.svg` and `mark-on-dark.svg` are byte-identical
    except for stroke colour, and those strokes are exactly `#10743F` and `#4FC17E`. The kit had
    already made this decision; the arithmetic arrived at the same place.
*   [x] Written into all three theme blocks -- `@theme`, the `prefers-color-scheme` block, and the
    explicit `[data-theme="light"]` one. A token in two of three is the `CTX-336.1` defect.

### Phase 2: the mark
*   [x] `BrandMark`, one component used by both screens, rendering both variants with CSS deciding
    which is visible -- following the same three-case structure as the tokens, so an OS theme change
    needs no re-render and no second source of truth for what `index.css` already tracks.
*   [x] Copied into `public/`, served at the app root, bundled into `dist` and therefore into the
    Tauri build. Confirmed the built `dist/` carries all three files.
*   [x] `aria-hidden`, because on both screens the mark sits directly beside an `<h1>` reading
    "Copperplane" and a screen reader should not say the product name twice.

### Phase 3: guards that can actually fail
*   [x] `brandContrast.test.ts` computes the ratio from `index.css` for every theme and fails below
    4.5:1, and separately asserts the greens are colours `brand/README.md` actually lists rather
    than something close to them.
*   [x] `brandAssets.test.ts` asserts each served copy is byte-identical to its generated source,
    and that each mark's own stroke equals the `--color-brand` of the theme it is shown in.
*   [x] Both were demonstrated failing before being trusted -- see Plan Drift 2 and 3.

## 4. Plan Drift & Architectural Changes

**1. A third gap, which the spec did not know about: the app's favicon was another product's.**
`apps/tauri-ui/public/favicon.svg` was a purple `#863bff` mark, template art that has been shipping
as the app's icon since before this product had its current name. `SPEC-338` §1 lists two verified
gaps and this was not among them, because nobody had diffed the served file against the kit.
Replaced, and `brandAssets.test.ts` now makes that class of drift fail rather than persist.

**2. The contrast guard caught a bug in itself on its first run.** `block()` located a theme block
with `indexOf(selector)`, and this repo's `index.css` names `:root[data-theme="light"]` in its own
header comment -- so the lookup resolved to a comment and every block returned the *first* block in
the file. Only the one test that compares two blocks against each other could see it; the ten tests
that read a single block all passed against the wrong data and would have gone on passing. Anchored
on the selector followed by its opening brace.

**3. Then it failed for a second real reason, which is the point.** With the anchor added, four
tests failed: `^` required the selector at column zero, and `:root:not([data-theme="dark"])` is
indented inside its `@media` block. A guard that had been written and never seen to fail would have
carried both defects invisibly. Afterwards it was deliberately broken -- an accent foreground of
`#178F4E` on the Bright accent -- and it reported 1.82:1 against the 4.5:1 floor, then passed again
on restore.

**4. Two files rather than one inlined SVG, chosen against the more elegant option.** The marks
differ only in stroke colour, so inlining the path with `currentColor` and letting `--color-brand`
paint it would need one asset and no CSS toggle. It would also copy the mark's geometry into a
`.tsx` file, where `brand/tools/build.py` cannot reach it -- precisely the staleness `SPEC-338` §3
names. Verbatim copies plus a byte-identity test keep the kit authoritative.

**5. Not verified: any of this on screen.** Every claim here is computed or asserted from files.
Contrast is arithmetic, the assets are byte-compared, the suite passes and the build carries the
files -- but nobody has looked at the welcome screen with the mark on it, in either theme, and
`CTX-336.1` is the standing reminder that a button can satisfy every test and be invisible. This
needs a real click-through in the built app, in dark, in light, and in System with the OS switched
underneath it.

**6. `--color-success` was deliberately left as emerald.** `SPEC-338` §2 raised it and guessed
"probably wrong" to change it; that guess stands. Success, warning and danger are a semantic set,
and promoting one of them to the brand colour would put a green check and a green primary button on
the same screen meaning different things.
