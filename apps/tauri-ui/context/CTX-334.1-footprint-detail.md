# CTX-334.1: Implementation Context: Footprint Detail from the Footprint's Own File

> **Spec Reference:** Links to [SPEC-334](../specs/SPEC-334-footprint-literacy-and-component-detail.md)

Scope of this context is `SPEC-334` §2's settled decision only: read the footprint's own
`.kicad_mod` and decode its name, surfaced from the board components table. The two questions
`SPEC-334` §2 leaves open — connecting the footprint and component-search namespaces, and the
comparative *which of these should I use* answer — are deliberately **not** in this context. See
§4 Deviation 4.

## 1. Feature Definition & Execution Plan

### Phase 1: Read the footprint file
*   [x] `footprint_detail.describe_footprint(footprint_id, footprint_path)` — `descr`, `tags`,
        pad count, through-hole versus surface-mount, datasheet URL.
*   [x] Static decoder for the naming conventions `descr` does not spell out — pitch, Vertical
        versus Horizontal, CircularHoles, HandSolder, ThermalVias, `1x04` grids, package prefixes.
*   [x] Say nothing about a name it does not recognise (`SPEC-326` §1's rule).
*   [x] Unit tests, including against KiCad's own installed libraries, skipping cleanly where
        they are absent.

### Phase 2: The route
*   [x] `kicad.describe_footprint`, registered in `ROUTES` and `ASYNC_ROUTES`.
*   [x] Merge in what `kicad_bridge.resolve_footprint_model` already knows: courtyard, 3D model.
*   [x] Verified by driving JSON-RPC into the frozen sidecar, not the source module.

### Phase 3: The detail view
*   [x] `FootprintDetailView` — description, pads, mounting, keep-clear area, name decoding,
        whether a 3D model exists, datasheet URL, tags.
*   [x] The footprint name in the board components table is itself the affordance; one row is
        explained at a time.
*   [x] Degrades to the name decoding when a library carries no `descr`, rather than an empty
        panel.
*   [x] Component tests, including the no-description and unreadable-footprint paths.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the spec's own stated risk was wrong, and measuring it changed the design.**
    `SPEC-334` was drafted assuming `.kicad_mod` `descr` and `tags` are "often empty or unhelpful",
    which pointed at an LLM as the primary source. Sampling 400 footprints across KiCad 10's 155
    bundled libraries found **400/400 with a non-empty `descr` and 395/400 with `tags`** — and the
    text is better than a parser would produce. `PinHeader_1x04_P2.54mm_Vertical` reads *"Through
    hole straight pin header, 1x04, 2.54mm pitch, single row"*, which answers the maintainer's
    original question directly and for free. The spec's §2 and §3 were rewritten to record the
    measurement, and the LLM was cut from this context entirely. Nothing in this feature can
    hallucinate, because nothing in it generates.

*   **Deviation 2: the frozen-artifact probe caught a stale binary, again — and this time it
    caught my own tooling mistake.** The first `freeze_sidecar.py` run was invoked without
    `--target-triple`. It printed an argparse usage error and the shell reported exit code 0, so
    the wrapper looked successful; only `tail`-ing three lines showed the error, and the binary was
    14 minutes older than `daemon.py`. Driving JSON-RPC into it returned
    `Method not found: kicad.describe_footprint`. Had I trusted the freeze's apparent success, the
    route would have shipped absent from the packaged app while working perfectly from source —
    which is `CTX-407.3`/`CTX-407.4`'s failure mode exactly.

*   **Deviation 3: a defect only the real output could show.** `R_0805_..._HandSolder` came back
    with its description ending mid-clause at *"(Body size source: IPC-SM-782 page 72"*. The URL
    regex `https?://\S+` had swallowed the closing paren of the bracket the URL sat inside, and
    removing the URL then stranded an unbalanced `(`. Every unit test passed, because I had written
    them against descriptions I invented. The fix is `_split_off_url`, and the test that would have
    caught it is `TEST-004`: it sweeps 400 real footprints and asserts no surviving description has
    unbalanced brackets or ends on a separator. This is the same lesson as the review debug capture
    — read what the thing actually produced, do not reason about what it should produce.

*   **Deviation 4: the spec's two open questions are still open, deliberately.** `SPEC-334` §2 asks
    whether component search should answer a footprint-shaped query from KiCad's libraries, and
    what *"which NE555P am I getting"* is answered with. Neither is needed for the surface the
    maintainer actually asked for — *"add an action to the board components table to show a detail
    view that can explain the component and footprint"* — and both involve the component-search
    namespace, which this context does not touch. They remain unanswered in the spec rather than
    being quietly answered by omission here.

*   **Deviation 5: an unconditional `Fragment`, found by a test that was right for the wrong
    reason.** The expanded row was first rendered by returning a `Fragment` only when open. A test
    that clicked the same DOM node twice failed, and the cause was not the test: changing the
    element type at that position from `<tr>` to `Fragment` makes React unmount and remount the row
    itself, throwing away focus in the manual-height input that `SPEC-326` put in the same row. The
    `Fragment` is now unconditional.

*   **Prediction, recorded for the next session to check:** the naming decoder covers eight
    conventions and will meet names it cannot read. I expect the `descr` line to carry the answer
    in almost every case where the decoder is silent, so silence should rarely be visible. If a
    user reports a footprint where both are empty, that is the case for revisiting the LLM
    question, and `TEST-005`'s 200-footprint sample is the place to re-measure it.

## 5. Verification Notes

*   `kicad.describe_footprint` was driven into
    `services/python-daemon/dist/hardware-agent-studio-daemon-aarch64-apple-darwin` over JSON-RPC
    for three real footprints (pin header, CR2032 battery, 0805 hand-solder resistor). All three
    returned a description, pad count, mounting, courtyard and 3D-model flag.
*   The full daemon suite on `.build-venv/bin/python` ran 1001 tests with one failure:
    `TestRealDatasheetGenerateGuidanceJob`, a live-Anthropic test that missed its 60s deadline
    under the full run's concurrent load. It passes on its own (34s, 15 real API calls), and it
    touches nothing this context changed. Reported rather than re-run until green.
*   The full UI suite is 628 tests across 33 files, all passing.
*   **Not verified:** nobody has clicked this in the built Tauri window yet. The Python side is
    proven against the frozen sidecar and the React side against jsdom, which is the same gap
    `SPEC-302` shipped through. This ran on exactly one machine, macOS on Apple silicon, against
    KiCad 10's bundled libraries. No Windows or Linux path has been exercised, and no personal or
    community `.pretty` has been tested — the degraded no-`descr` path is covered by a test, not by
    a real library.
