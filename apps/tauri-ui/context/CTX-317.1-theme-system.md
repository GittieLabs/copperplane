*   [x] `apps/tauri-ui/src/index.css`: `@theme` block defines the semantic token set (dark values,
    matching the app's existing defaults exactly, so no visual change at rest); a
    `@media (prefers-color-scheme: light)` block guarded by `:not([data-theme="dark"])` (System

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the semantic token set is 19 tokens, not the ~12 the approved plan sketched.**
    *   *Reasoning:* The plan's token list was a reasonable first pass from the background audit's
        rough class counts. Before running the actual sweep, a fresh, precise `grep` (word-boundary
        safe, covering every color-utility family, not just the ones the audit happened to mention)
        found the real, complete inventory: 28 distinct class strings, including several the audit
        didn't call out individually — `bg-neutral-100`/`text-neutral-950` used together as a
        recurring "inverted accent pill" button style (needed its own `accent`/`accent-fg` pair,
        since reusing plain `fg`/`base` would have made accent buttons flip to nearly-invisible in
        light mode instead of staying a high-contrast pill in both themes); `text-neutral-200`
        (chip/hover text, brighter than `fg-secondary`) and `text-neutral-600` (dimmer than
        `fg-muted`) as two more granularity levels than the plan's three-tier fg scale; a
        `border-neutral-100` "selected" ring (mapped onto the existing `fg` token as a border
        color, not a new one — Tailwind v4's `@theme` custom properties aren't scoped to one
        utility category, so `--color-fg` already drives `border-fg` for free); and a
        `bg-amber-500`/`border-amber-700` warning-accent pair (a single callout box in `App.tsx`)
        needing its own two tokens distinct from the plain `warning` text/icon color.
    *   *Impact:* `SPEC-317`/this context's file lists are accurate to what was actually built, not
        the plan's earlier sketch. No behavior or visual regression — the extra tokens are strictly
        more precise mappings of colors that were already there, not new colors invented.
*   **Deviation 2: `useThemePreference()` is called only in `Settings.tsx`, not in `App.tsx` as the
    plan said.**
    *   *Reasoning:* The plan's own design already put initial-load application in `index.html`'s
        inline script (necessary regardless, for FOUC prevention) — by the time React mounts, the
        correct `data-theme` is already set. Re-examining the plan's own App.tsx wiring during
        implementation, it added nothing: no other part of `App.tsx` reads the resolved theme (the
        one place that could have — `EnclosureViewer`'s canvas background — is an explicit
        non-goal), so a second, unconnected `useThemePreference()` instance in `App.tsx` would only
        have created a real correctness risk (two independent React state copies of the same
        preference, with no shared source of truth, that could drift out of sync on a future change)
        for zero behavioral benefit. Solved instead by making `setThemePreference()` a plain
        function that writes `localStorage` and the DOM `data-theme` attribute together,
        independent of any component's React state — correct regardless of how many places call it,
        with only one real caller (Settings) needing to also track it in local state for its own
        toggle UI.
    *   *Impact:* `App.tsx` needed no theme-related change at all beyond the mechanical class-name
        sweep already covering it. Simpler and more robust than the plan's original wiring, not a
        shortcut — verified live (Settings toggle changes the whole app's rendered colors
        immediately, confirmed by screenshot) that this still delivers the plan's own stated
        requirement.
