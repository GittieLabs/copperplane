# CTX-109.2: Enclosure tab UI: real board-driven generation + STEP export

> **Spec Reference:** Links to [SPEC-109](../../../services/python-daemon/specs/SPEC-109-parametric-enclosure-generator.md)

The UI-wiring child context `SPEC-109`'s own Cross-Module Impacts section named as likely deferred
-- the same relationship `CTX-108.3` had to `CTX-108.1`. `CTX-109.1` built real board-driven
enclosure geometry and `daemon.py`'s `freecad_generate_enclosure` route (explicit mode selection,
recognized-only standoffs, `project_name`-gated `Artifact` persistence); the Enclosure tab's
`EnclosurePanel` still only offers the original three plain width/depth/height fields and never
supplies `project_name`, so none of `CTX-109.1`'s real work is reachable from the app today.

## 1. Feature Definition & Execution Plan

### Phase 1: `lib/enclosure.ts` -- a typed wrapper over the richer route
*   [x] `EnclosureParams`/`EnclosureResult` interfaces mirroring `daemon.py`'s real
    `freecad_generate_enclosure` signature/return shape (`height` required; `width`/`depth` optional
    -- their presence is the real mode-selection signal per `CTX-109.1`; `wall_thickness_mm`/
    `clearance_mm`/`fillet_radius_mm`/`standoff_height_mm`/`project_name` all optional with the same
    defaults the daemon itself applies; `unrecognized_holes`/`artifact_id` on the result).
*   [x] A thin `generateEnclosure` helper delegating to `submitJob<EnclosureResult>
    ('freecad.generate_enclosure', params)` -- no new logic, matching `lib/projects.ts`'s own
    thin-wrapper convention over daemon routes.

### Phase 2: `EnclosurePanel` -- real board-driven mode, `project_name`, STEP export
*   [x] A mode toggle: "From board" (reads `daemon.get_capabilities().kicad_available` --
    `lib/settings.ts`'s existing `getCapabilities`, no new capability field needed -- to decide
    whether the option is even offered) vs "Manual dimensions" (today's exact width/depth/height
    fields, unchanged, always available as the explicit fallback `SPEC-109` §3 requires).
*   [x] "From board" mode shows `height` plus the real geometry parameters (wall thickness,
    clearance, fillet radius, standoff height) pre-filled with the same defaults `freecad_bridge.py`
    itself applies, and omits `width`/`depth` from the submitted params entirely -- the real signal
    `CTX-109.1`'s route reads to choose board-driven generation.
*   [x] `EnclosurePanel` receives the enclosing project's real name (`view.name`, already available
    at its call site in `App.tsx`) as a `projectName` prop, threaded through as `project_name` --
    for the first time making a real `Artifact` actually get saved through the UI, closing the loop
    `CTX-109.1`'s own Plan Drift named as still-open ("until the UI-wiring child context lands").
*   [x] A real, non-empty `unrecognized_holes` result is surfaced as a plain warning -- naming how
    many `PT_NPTH` pads were found but not recognized as mounting holes, so a user isn't silently
    missing standoffs they expected -- not a blocking error, matching `CTX-109.1`'s own "excluded,
    not fail-closed" design.
*   [x] The result's `step_path` gets the same "Open" affordance `PartDetail.tsx` already uses for
    its own exported file (`@tauri-apps/plugin-shell`'s `open()`, already installed and permitted --
    no new plugin/permission needed), alongside the existing `EnclosureViewer` for the `.glb`.

## 4. Plan Drift & Architectural Changes

**Real click-through verification in the actual native Tauri window was not performed for this
context, and that gap is recorded here explicitly rather than left implicit** (CLAUDE.md's "state
what was not verified" norm; this repo's own memory notes a prior, similar gap). The dev environment
(`vite` + the Rust binary + a freshly-respawned `daemon.py` carrying every change from `CTX-109.1`
and this context) was restarted and confirmed healthy -- `npx @tauri-apps/cli@2 dev` from
`core/tauri-rust`, after the previous long-running dev session's stale `daemon.py` (spawned before
any of this session's Python changes existed) had to be killed and the whole dev process restarted
cleanly, the same recovery this repo has needed before when a daemon process outlives the code
changes made under it. No native-desktop screen-control tool was available in this session to
actually click through the running window the way `CTX-108.3`/`CTX-305.1`/`CTX-306.1` were each
verified. What *is* real: the full mocked test suite (`vitest run`, 104 passed including six
dedicated Enclosure-tab tests), a clean `tsc -b`, and `CTX-109.1`'s own already-completed real,
no-mocks verification of the underlying `freecad_generate_enclosure` route itself (a live KiCad
connection, real `freecadcmd`, a real `Artifact` saved and loaded back). What remains genuinely
unverified is only the last mile -- a human or a screen-control tool actually clicking "From board"
and "Generate Enclosure" in the real window and confirming the rendered result. Flagged as a real
follow-up, not silently assumed equivalent to the mocked coverage.
