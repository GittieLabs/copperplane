# CTX-318.6: Implementation Context: Rehome generate/inject, delete parseCommand

> **Spec Reference:** Links to [SPEC-318](../specs/SPEC-318-in-context-agent-chat-and-review.md)

Phase 6 of 6, the final slice: `foundation` (`CTX-318.1`) → `Components` (`CTX-318.2`) →
`Schematic/PCB` (`CTX-318.3`) → `Enclosure` (`CTX-318.4`) → `project intent/Overview` (`CTX-318.5`) →
**finish deleting `parseCommand`**. Gated on a real design decision the user made before this phase
started (`AskUserQuestion`): `kicad.generate_component` gets a new, explicit entry point in
`ComponentDiscovery`, next to search; `SPEC-108`'s inject flow becomes a real action on `PartDetail`,
available once a Part is confirmed/saved. Both recommended options were chosen.

## 1. Feature Definition & Execution Plan

### Phase 0: understand the real backend shape before designing the UI
*   [x] **Real, load-bearing finding, not assumed:** `PartDetail.tsx`'s existing `candidate` path
    already calls `extractPartDetail(candidate.part_number)`, which is the exact same
    `kicad.generate_component` route Overview's old `generate <part>` command called directly
    (`lib/partDetail.ts`'s own doc comment already said so). There is no separate "generate"
    capability at the backend to rehome -- only a UI entry point that skips search/candidate-ranking
    and hands `PartDetail` a bare part number instead of a real search result.
*   [x] **Real, load-bearing finding: `kicad.inject_component`'s schema needs more than the frontend's
    typed `ExtractedSchema`/`SavedPart` interfaces declared.** Read `kicad_bridge.inject_component`
    directly: it reads `schema["package_dimensions"]` and `schema["courtyard"]` (`CTX-308.5`), which
    the persisted Part record always carries (`library_store.py`'s
    `PART_PROVENANCE_REQUIRED_FIELDS`) but the frontend's `SavedPart` interface never declared. Fixed
    by widening `SavedPart` (`lib/partDetail.ts`) rather than reaching for an untyped cast.

### Phase 1: rehome `generate` into `ComponentDiscovery`
*   [x] A collapsed-by-default "Can't find it via search? Generate directly from a part number…"
    fallback, next to the search box -- not a second way to do what search already does. On submit,
    constructs a synthetic `ComponentCandidate` (only `part_number` real; `manufacturer`/`package`/
    `datasheet_url` honestly empty/unknown, `confidence: 'low'`) and sets it as `confirmed` --
    `PartDetail`'s own existing effect then runs the real extraction automatically, exactly as a real
    search-confirmed candidate would.
*   [x] **Real improvement over the old surface, not just a relocation:** the old Overview
    `generate <part>` command dumped a raw JSON schema into a chat message with no save step at all
    -- the only next action was typing `inject`, writing directly to a board with nothing ever
    persisted to the Library. Routing through `PartDetail`'s existing `candidate` flow means every
    directly-generated part goes through the same review-before-save UI SPEC-306/307 already built.
*   [x] Fixed two real rendering gaps a synthetic, mostly-empty candidate exposed: the "Confirmed:
    ..." header no longer prints a bare trailing `(Unknown, )` when `package` is empty; a genuinely
    unknown datasheet ("generated directly, not found via search") now renders as a distinct, calm
    message rather than falsely claiming a cache attempt failed (`cacheError: null` vs a real error
    string are no longer conflated).

### Phase 2: rehome `inject` into `PartDetail`
*   [x] A new "Inject into board" section, gated on `savedPart` (matches the user's own chosen
    answer, "once a part is confirmed/saved") -- built from the real, persisted `SavedPart` record
    (`part_id`, `package`, `pins`, `package_dimensions`, `courtyard`) rather than an unsaved, in-memory
    schema, so injecting a Part reopened from the Library works identically to injecting one just
    saved this session.
*   [x] The exact same `agent.dispatch_tool`/`SPEC-204` confirmation-gate flow Overview's old code
    used (`dispatchTool` → `pending_confirmation` → explicit Confirm/Cancel → re-dispatch with
    `confirmed: true`), moved verbatim rather than redesigned -- SPEC-204's own confirmation
    requirement is unchanged by where the button lives.

### Phase 3: delete `parseCommand`
*   [x] `lib/commands.ts` and `lib/commands.test.ts` deleted.
*   [x] `Overview.tsx`'s `handleSend` no longer calls `parseCommand` at all -- every message is now
    unconditionally a plain `llm.chat` turn, which is exactly what `parseCommand` already fell
    through to for any text that didn't match `generate <part>` or `inject`. No user-visible behavior
    change for a plain question; the `ChatMessage` union collapses to `user`/`chat` (the `generate`/
    `inject` message kinds, `latestSchema` state, and `handleConfirmInject`/`handleCancelInject` are
    gone). The activity-feed-feeding `loadConversation`/`appendConversationTurn` plain-chat surface
    (SPEC-313's dashboard, explicitly "untouched" per SPEC-318 §2.2) is unchanged -- SPEC-318 §2.7
    says specifically "`parseCommand` import and its `generate`/`inject` branches removed," not "the
    whole chat surface removed," and nothing in the spec calls for retiring the activity feed's own
    ongoing plain-chat contributions.
*   [x] `PRODUCT-PLAN.md` §7's own 2026-08-21 amendment (which named this exact rehoming as the
    remaining blocker) gets a completion amendment recording what actually shipped.

### Phase 4: tests
*   [x] `Overview.test.tsx`: the one test referencing the old placeholder/description text updated
    (plain chat now coexists with `AgentChat`, not "the parseCommand-driven chat").
*   [x] `App.test.tsx`: the six generate/inject-specific tests (`TEST-001`, `TEST-002`, `TEST-002b`,
    `TEST-002c`, `TEST-003`, `TEST-006`) removed -- that behavior no longer lives in `Overview`. The
    two plain-chat tests (`TEST-004`, `TEST-005`) were restored after an over-broad first deletion
    swept them up too (see Plan Drift) -- both still pass unchanged, since a plain question's
    behavior genuinely didn't change. The shared `renderAppOnOverview`/`sendMessage` helpers'
    placeholder regex updated from `/generate ATtiny85/` to `/ask a question/`.
*   [x] `ComponentDiscovery.test.tsx`: five new tests for the "Generate directly" fallback --
    collapsed by default, opens a real input and routes straight to `PartDetail` with no
    search/datasheet-cache call, the honest "no datasheet known" message (distinct from a real cache
    failure), Generate disabled on an empty part number + Cancel discards the draft, and a project
    switch resets any in-progress draft.
*   [x] `PartDetail.test.tsx`: five new tests for "Inject into open board" -- not offered before a
    Part is saved, the real pending-confirmation gate (mutates nothing yet), confirming re-dispatches
    with `confirmed: true` and reports success, cancelling never calls the daemon again, a genuine
    failure shows the real error with a "Try again" affordance. A local `dispatchTool` mock added
    (`../lib/ipc`, not previously mocked in this file).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (real, checked directly rather than assumed): `kicad.generate_component` is not a
    separate capability from what `ComponentDiscovery`/`PartDetail` already implement -- only the UI
    entry point needed rehoming, not a new backend integration.**
    *   *Reasoning:* Overview's old `generate <part>` command and `PartDetail`'s own `candidate`-path
        extraction both call the identical route. Confirmed by reading `lib/partDetail.ts`'s
        `extractPartDetail` and `component_pipeline.py`'s `generate_component` directly before
        designing any UI, rather than assuming a parallel pipeline needed building.
    *   *Impact:* the "Generate directly" fallback is a thin, ~30-line addition to
        `ComponentDiscovery.tsx` that constructs a synthetic candidate and lets `PartDetail`'s
        already-built extraction/review/save flow do the rest -- not a new component, not a new
        backend call, and strictly safer than the old surface (real review-before-save, where the old
        one had none).
*   **Deviation 2 (a real, self-caught mistake during test cleanup, not a design change): an
    over-broad `sed` deletion in `App.test.tsx` removed two still-valid tests along with the four
    obsolete ones.**
    *   *Reasoning:* `TEST-001` through `TEST-006` were interleaved in the source file --
        `TEST-004`/`TEST-005` (plain-chat behavior, genuinely unchanged by this phase) sat between the
        generate tests (`TEST-001`/`TEST-002`/`TEST-002b`/`TEST-002c`/`TEST-003`) and the one
        remaining generate-failure test (`TEST-006`), all contiguous. A single-range deletion meant
        to remove only the generate/inject tests swept up the plain-chat ones too.
    *   *Impact:* caught by re-running the full suite immediately after the deletion and noticing the
        test count dropped by 8 instead of the expected 6, then diffing against the pre-deletion
        content to confirm which two were missing. Restored both verbatim (their assertions needed no
        changes -- sending a plain, non-generate/non-inject message was never routed through
        `parseCommand`'s special-cased branches in the first place). Named here per this repo's own
        norm of recording a wrong prediction honestly, not just the corrected end state.
*   **Deviation 3 (real, deliberate scope boundary, not an oversight): the plain `llm.chat` surface
    and its persisted conversation log/activity-feed contribution were kept, not deleted.**
    *   *Reasoning:* SPEC-318 §2.7 says "`parseCommand` import and its `generate`/`inject` branches
        removed" -- narrower than "delete the whole chat." §2.2 separately says SPEC-313's dashboard
        (activity feed) is "untouched." Deleting the plain-chat surface too would have silently
        stopped the activity feed from ever growing again (new turns are only appended from this
        surface's own `handleSend`), a real, user-visible regression nothing in the spec or the
        user's own two `AskUserQuestion` answers asked for.
    *   *Impact:* Overview now has two coexisting, permanently distinct chat surfaces -- the plain
        `llm.chat` one (feeds the activity feed, no sources, no tools) and `AgentChat` (sourced,
        project-grounded, no activity-feed integration). This is a real, intentional end state, not a
        transitional one -- worth flagging explicitly in case a future session assumes the plain
        surface was meant to be temporary scaffolding now that `AgentChat` exists.
*   **Deviation 4 (a real, pre-existing test flake, found and fixed, not introduced by this phase):
    `Overview.test.tsx`'s `CTX-318.5` intent-editor tests (unrelated to this phase's own changes)
    intermittently failed -- roughly 1 run in 3, even in isolation, with no code changes to the
    editor itself.**
    *   *Reasoning:* several tests fired `fireEvent.click` on "Add"/"Edit" and immediately
        `fireEvent.change`d the textarea it reveals, with no `waitFor` between them -- a real race
        against React's own commit timing under jsdom, not something this phase's `handleSend`
        rewrite touched. Confirmed by running the file five times in isolation post-fix (all green)
        versus the pre-fix intermittent failures.
    *   *Impact:* added `await waitFor(() => screen.getByPlaceholderText(/I want to build/))`
        immediately after every such click, before the following `fireEvent.change`, across all four
        affected tests. Recorded here rather than silently folded into "test cleanup" since it's a
        real bug found and fixed in this phase's own verification pass, on code this phase didn't
        otherwise touch.
*   **Deviation 5 (a real, self-caught commit mistake, not a design change): the first commit landed
    almost none of the intended diff.**
    *   *Reasoning:* a single `git add` listing both the two already-`git rm`'d deleted paths
        (`lib/commands.ts`/`lib/commands.test.ts`, staged earlier via `git rm`) and every other
        changed file failed with `fatal: pathspec ... did not match any files` for the deleted paths
        -- and a failing `git add` invocation stages *nothing* it listed, not just the failing
        argument. The resulting commit only contained the new context file and the (separately,
        correctly staged) deletions.
    *   *Impact:* caught immediately by running `git show --stat HEAD` right after the commit and
        noticing only 3 files were listed against an expected 12 -- not assumed correct from the
        commit command's own exit code (0) or the pre-commit hook's own success message, neither of
        which would have caught a partially-empty commit. Fixed with a second, real commit
        (`7566b05`) containing the actual diff, verified against `git diff origin/develop --stat`
        before proceeding. Worth naming as a general caution: a multi-path `git add` after a prior
        `git rm` in the same session is worth staging in two separate calls, or verifying via
        `git show --stat` immediately after commit rather than trusting the staging step succeeded.
