# CTX-319.6: Implementation Context: Run Review in the Design menu

> **Spec Reference:** Links to [SPEC-319](../specs/SPEC-319-ai-review.md)

Phase 6, the final phase: the native `Design` menu integration `CTX-319.3` deliberately deferred out
of the per-area mount phases. A **Run Review** item joins each of the three real Design submenus
(Schematic/PCB/Enclosure -- `SPEC-316`'s own menu has no Overview or Components submenu at all), each
one dispatching the exact same `handleRunReview` the in-area button already calls -- a second, native
entry point to the same real action, not a separate code path.

This completes `SPEC-319` (AI Review) -- all six phases now shipped.

## 1. Feature Definition & Execution Plan

### Phase 1: `core/tauri-rust/src/menu.rs`
*   [x] Three new event constants (`MENU_DESIGN_{SCHEMATIC,PCB,ENCLOSURE}_RUN_REVIEW_EVENT`), three
    new item ids, one new `MenuItemBuilder` item per applicable submenu (each preceded by a
    separator, matching this file's own visual convention of grouping a submenu's "do the thing"
    actions apart from its "pick a target" ones), three new `handle_menu_event` match arms
    (`app.emit(...)`, identical shape to every existing arm).
*   [x] Verified with a real `cargo build --lib` and `cargo test --lib` (35 tests, including the
    pre-existing `menu::tests` module) -- both clean, no new warnings beyond one pre-existing,
    unrelated deprecation notice (`tauri_plugin_shell::Shell::open`).

### Phase 2: `lib/ipc.ts` + `App.tsx`
*   [x] Three matching frontend event-name constants in `lib/ipc.ts`, string-identical to their
    Rust counterparts.
*   [x] `App.tsx`'s existing `onDesignCommand(area, command)` dispatch reused unchanged -- three new
    `on(MENU_DESIGN_*_RUN_REVIEW_EVENT, () => onDesignCommand(<area>, 'run_review'))` listener
    registrations, matching every existing Design-menu listener's own shape exactly.

### Phase 3: `ReviewPanel` gains a `menuCommand` prop
*   [x] `ReviewPanelProps.menuCommand?: MenuCommand | null` -- a `useEffect` keyed on
    `menuCommand?.nonce`, checking `menuCommand?.area === area && menuCommand.command === 'run_review'`
    before calling the exact same `handleRunReview()` the button's own `onClick` calls. Byte-for-byte
    the same pattern `SchematicAdvisor`/`BoardAdvisor`/`EnclosurePanel` already established for their
    own `menuCommand` props (`open_kicad`/`pick_manually`/etc.).
*   [x] `SchematicAdvisor.tsx`/`BoardAdvisor.tsx`/`EnclosurePanel.tsx` each forward their own already-
    received `menuCommand` prop straight through to their `ReviewPanel` mount -- no new prop threading
    beyond that one line each, since all three already receive `menuCommand` from `App.tsx` for their
    own existing handlers.
*   [x] `Overview.tsx`'s own `ReviewPanel` mount deliberately does **not** receive a `menuCommand`
    prop -- `SPEC-316`'s menu has no Overview submenu, so there is no real event that could ever
    reach it; the prop stays `undefined` there, its own documented legitimate default.

### Phase 4: tests
*   [x] `ReviewPanel.test.tsx`: a matching `run_review` `menuCommand` runs the real review (same
    call as the button); a `menuCommand` for a different area is ignored; the same command fired
    twice (nonce bumped) re-triggers both times -- mirroring `SchematicAdvisor.test.tsx`'s own
    established `menuCommand` test shape exactly.
*   [x] `SchematicAdvisor.test.tsx`/`BoardAdvisor.test.tsx`/`EnclosurePanel.test.tsx`: each gains one
    new test confirming the real `menuCommand` prop is forwarded through to the (stubbed)
    `ReviewPanel` unchanged -- the correct scope for these files (their own wiring), leaving
    `ReviewPanel`'s own internal reaction to `menuCommand` covered once, in its own test file.
*   [x] `App.test.tsx`: extended the existing `./components/ReviewPanel` module-level stub to also
    render its received `menuCommand`, then added one new test mirroring the existing "CTX-316.1: a
    Design menu event switches to the matching area and runs the real handler" test's own shape --
    firing the real `menu://design/pcb/run-review` event and confirming both the area switch and the
    real `menuCommand` reaching the (stubbed) `ReviewPanel`, scoped via `within(screen.getByTestId('pcb-area'))`
    since all five areas' own `ReviewPanel` stubs are simultaneously in the DOM (mount-always).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (a real, deliberate choice, not an oversight): `Overview.tsx`'s `ReviewPanel` mount
    does not receive a `menuCommand` prop at all, rather than being passed `undefined` explicitly.**
    *   *Reasoning:* `Overview` never receives a `menuCommand` prop from `App.tsx` in the first place
        (it's the one area with no Design submenu, and never has been, even before this spec) -- there
        is no real value to thread through, and adding one just to explicitly pass `undefined` would
        suggest a submenu exists where `SPEC-316`'s own menu genuinely has none.
    *   *Impact:* `ReviewPanelProps.menuCommand` stays a real, honest optional -- `undefined` for
        Overview/Components (correctly, since neither has a native menu item), a real value for
        Schematic/PCB/Enclosure. No code change needed to `Overview.tsx` itself for this phase at all,
        confirmed by checking it before assuming it needed one.
