# CTX-312.3: Native File/Edit/View/Help app menu

> **Spec Reference:** Links to [SPEC-312](../specs/SPEC-312-application-shell-project-portability-persistence.md)

`SPEC-312`'s third, still-deferred question: `core/tauri-rust` has never had a real native
`File`/`Edit`/`View`/`Help` menu, in any build mode -- confirmed again by direct grep (zero hits for
`menu`/`Menu` anywhere in `core/tauri-rust/src/*.rs`). `ROADMAP.md` §3.3 named it as "the natural
home for 'open a project not currently in the sidebar' and Save/Save As/Duplicate." `CTX-312.1`/
`.2` already built the real "Save Project" action and real `Project.directory` linking this menu
can now call into.

**Real API surface verified directly against the vendored `tauri` crate before implementing (not
general Tauri knowledge)**: resolved version is `tauri 2.11.5` (`Cargo.lock`), `tauri::menu` is
compiled in unconditionally at this version. Confirmed real, in-source: `Builder::menu`/
`Builder::on_menu_event` (`app.rs:1977,2000`); `MenuBuilder`/`SubmenuBuilder`/`MenuItemBuilder`
(`menu/builders/*.rs`); `PredefinedMenuItem::{copy,cut,paste,select_all,undo,redo,quit,about,
separator}` (`menu/predefined.rs`); `AboutMetadata` (`menu/mod.rs:168`); `WebviewWindow::
open_devtools/close_devtools` (gated `#[cfg(any(debug_assertions, feature = "devtools"))]`). The
one existing Rust→frontend event pattern already in this codebase: `app_handle.emit(
DAEMON_RESPONSE_EVENT, line)` in `daemon.rs:306` -- menu events reuse this exact idiom.

**Real scope decision, made during research, not assumed:** "Open a project not currently in the
sidebar" needs a new backend capability, not just a UI trigger. `CTX-312.1`'s own directory link
only handles "an already-known project gets linked to a folder"; it never built the reverse -- "a
folder someone hands me (or I open on a new machine) becomes a known project here," the actual
payoff of real portability. Kept deliberately narrow: a folder with no
`.hardware-agent-studio/project.json` raises a clean error rather than silently guessing a new
project name from the folder's own basename (avoids a real name-collision risk against
`storage_root/projects/<name>/`) -- creating new projects already has its own real entry point
(Rail's "+ New…").

**Explicit Non-Goals for this pass:** "Save As…" and "Duplicate Project" -- neither has any
existing backend semantics to wire a menu item to yet. Left for a future pass.

## 1. Feature Definition & Execution Plan

### Phase 1: Python -- open an existing portable project from its real linked directory
*   [x] `library_store.py`: new `open_project_from_directory(directory: str) -> dict`. Reads
    `<directory>/.hardware-agent-studio/project.json`; raises `ProjectNotLinkedError` (clean, new)
    if missing. On success, re-registers the storage-root pointer, returns `load_project(name)`.
*   [x] `daemon.py`: new thin `project_open_from_directory` route, registered as
    `project.open_from_directory`.
*   [x] See Deviation 1 below: this phase also found and fixed a real bug in `CTX-312.1`'s own
    `load_project`.

### Phase 2: Rust -- the real native menu
*   [x] New `core/tauri-rust/src/menu.rs`: `build_menu` constructs File (Save Project `CmdOrCtrl+S`,
    Open Project… `CmdOrCtrl+O`, separator, Quit), Edit (native undo/redo/cut/copy/paste/select-all),
    View (`#[cfg(debug_assertions)]`-only Toggle Developer Tools), Help (About, GitHub Repository).
*   [x] `lib.rs`: wire `.menu(...)`/`.on_menu_event(...)` into the existing Builder chain;
    `handle_menu_event` emits real events for the two custom File items, toggles devtools, opens the
    repo URL via the already-integrated shell plugin. Quit/Edit items are handled entirely natively.
    Every API used (`Builder::menu`/`on_menu_event`, `MenuBuilder`/`SubmenuBuilder`/`MenuItemBuilder`,
    `PredefinedMenuItem::*`, `AboutMetadataBuilder`, `Submenu`'s own `IsMenuItem` impl) was confirmed
    directly against the vendored `tauri 2.11.5` source before writing this, not assumed.

### Phase 3: Frontend -- real menu-event listeners reusing existing handlers
*   [x] `MENU_SAVE_PROJECT_EVENT`/`MENU_OPEN_PROJECT_EVENT` constants (matching
    `DAEMON_RESPONSE_EVENT`'s own doc-comment convention).
*   [x] `lib/projects.ts`: `openProjectFromDirectory(directory)` -- thin `dispatch` wrapper.
*   [x] `App.tsx`: a new `useEffect` listens for both menu events -- Save reuses the existing
    `handleSaveProject()`; Open triggers a new `handleOpenProject()` (folder picker →
    `openProjectFromDirectory` → adds/selects the project, matching `handleCreateProject`'s shape).
    Re-subscribes whenever `currentProject` changes so `handleSaveProject`'s own closure is never
    stale (a real React closure bug, caught and fixed while writing this file's own tests -- see
    Deviation 2).

### Phase 4: Tests + real verification
*   [x] Real Python tests for `open_project_from_directory` (success + `ProjectNotLinkedError`)
    against a real filesystem.
*   [x] Frontend tests for `openProjectFromDirectory` and both menu-event listeners.
*   [x] Rust: verified via `cargo build` + the full existing `cargo test` suite (32 tests, all still
    passing) -- no meaningful unit-test surface for native menu construction itself in this
    ecosystem.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: found and fixed a real bug in `CTX-312.1`'s own `load_project`, discovered by
    this context's own first test, not assumed correct.** `test_001_a_real_linked_folder_is_restored
    _as_a_known_project` failed on its first run: `load_project`'s own "disk-truth identity" reasoning
    (already established for `name`, per `CTX-110.1`) was never applied to `directory` too. A real
    portable state file -- one written on another machine, or in this test's own case, simulated
    directly without a `directory` field at all -- left the RETURNED record missing `directory`
    entirely, even though the storage-root pointer (this machine's own real, current answer) had it.
    Fixed by having `load_project` override `record["directory"] = directory` from the pointer, the
    same way it already overrides `record["name"]`. Real, in-scope fix (this exact code path is what
    `open_project_from_directory` calls), not a tangent.
*   **Deviation 2: the menu-event `useEffect` needed to re-subscribe on `currentProject` change, a
    real React stale-closure risk the original plan text didn't call out explicitly.**
    `handleSaveProject` closes over `currentProject`; a `useEffect` with an empty dependency array
    would have captured its very first closure (where `currentProject` is still `null`, before the
    async project load resolves) and never updated it -- the real menu's own Save Project item would
    have silently no-opped forever. Caught by this context's own first attempt at a test for it (the
    `saveProjectMock` call count stayed zero), not assumed correct from the code alone. Fixed with
    `[currentProject]` as the effect's own dependency array; `handleOpenProject` needs no such
    treatment since it closes over no project-scoped state at all.
*   **Deviation 3 (minor, non-blocking): `tauri_plugin_shell`'s `Shell::open` is deprecated in this
    resolved version** (`tauri-plugin-shell 2.3.5`, in favor of `tauri-plugin-opener`), confirmed by
    a real compiler warning on `cargo build`. Kept as-is for this pass rather than adopting a new
    plugin/capability -- this codebase's own established pattern (`EnclosurePanel.tsx`'s original
    "Open .step" buttons, `CTX-311.13`) already uses `tauri_plugin_shell`, and the Help menu's own
    "GitHub Repository" item is the only new caller here. `Shell::open` still works; the deprecation
    is real but not urgent, named honestly rather than silently ignored.
