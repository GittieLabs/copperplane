# CTX-303.2: Fix: generate always used Anthropic, ignoring Settings

> **Spec Reference:** Links to [SPEC-303](../specs/SPEC-303-settings-ui.md)

Follow-up to [CTX-303.1](CTX-303.1-settings-plumbing-and-ui.md) Plan Drift Deviation 2, found only
by Keith manually verifying the shipped Settings screen: `kicad.generate_component` ("generate")
always ran `component_extraction.prompt.md`'s hardcoded `provider: anthropic`, completely ignoring
whatever provider was selected in Settings. Only `llm.chat` (plain chat) ever respected
`CONFIG["llm_provider"]`. Independent of `CTX-303.1`'s own code (`services/python-daemon` only, no
Rust/frontend changes) -- branched directly off `origin/develop`, not off the still-unmerged
`CTX-303.1` branch.

## 1. Feature Definition & Execution Plan

### Phase 1: Thread provider/model through the extraction pipeline
*   [x] `component_pipeline.py`'s `_build_agent_executor`: accepts optional `provider`/`model`,
    overriding the agent's `.prompt.md` frontmatter default via Pydantic's `model_copy` when given.
*   [x] `component_pipeline.py`'s `generate_component`: threads `provider`/`model` through to
    `_build_agent_executor` via its `runner_factory`.
*   [x] `daemon.py`'s `kicad_generate_component`: passes `CONFIG["llm_provider"]`/`["llm_model"]`
    through, the same resolution `llm_chat` already uses -- `None` when unset, never a forced
    default, so a fresh install with nothing configured in Settings behaves exactly as before.

### Phase 2: Fix the real bug found by the real test written for Phase 1
*   [x] **Found running the real end-to-end test, not by inspection beforehand:** switching
    `provider` without an explicit `model` kept the prompt file's own Anthropic-specific model name
    (`claude-sonnet-4-6`), invalid for Google's API -- a real call returned an empty response,
    surfaced as a confusing JSON-parse error rather than an obviously-wrong-model one.
*   [x] Fixed: switching `provider` without an explicit `model` now falls back to that provider's
    own default model (`llm_providers._DEFAULT_MODELS`), the same fallback `_build_provider` already
    applies when `model` is falsy -- applied explicitly here since `config.model` is never falsy on
    its own (`AgentConfig`'s Pydantic field always has some default).

### Phase 3: Tests, at every layer that failed silently before
*   [x] Unit, construction-only (no key needed): no-override / provider-override / model-override /
    provider-uses-its-own-secret-key / provider-switch-uses-its-own-default-model.
*   [x] Real, non-mocked, real Google API call proving the actual fix -- this is the test that
    caught Phase 2's bug in the first place.
*   [x] `daemon.py`-level: `kicad_generate_component` passes `CONFIG`'s provider/model through;
    omitting both passes `None` through, not a forced default.
*   [x] `scripts/ci/check_expected_skips.py`: registered the new real-Google test as an expected
    skip on CI (no `GOOGLE_API_KEY` there either).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1, found by the very test written to prove the fix, not by inspection beforehand:
    overriding `provider` alone silently carried over an invalid, provider-mismatched model name.**
    *Reasoning:* `component_extraction.prompt.md`'s frontmatter hardcodes `model: claude-sonnet-4-6`
    -- a real Anthropic model name. The first version of this fix only overrode `provider`, leaving
    `config.model` at that stale value. A real call against Google with `model=claude-sonnet-4-6`
    returned an empty response body, which `_extract_json` correctly reported as a JSON-parse
    failure -- technically accurate, but a confusing symptom for what was actually an invalid-model
    request.
    *Impact:* `_build_agent_executor` now falls back to the newly-selected provider's own default
    model (`llm_providers._DEFAULT_MODELS[provider]`) whenever `provider` is overridden without an
    explicit `model` -- mirroring the fallback `_build_provider` itself already applies when `model`
    is falsy, just applied one layer up since `config.model` is never actually falsy on its own. This
    is exactly the "verify for real" norm working as intended: the mocked/construction-only unit
    tests (Phase 1) never exercised a real API call and would not have caught this; only the real,
    non-mocked test against Google (Phase 3) did.
*   **Non-deviation, confirmed as designed: this branch is independent of `CTX-303.1`.** Despite
    being a direct follow-up to a bug `CTX-303.1`'s own verification found, this fix touches only
    `services/python-daemon` and needed none of `CTX-303.1`'s Rust/frontend code -- branched cleanly
    off `origin/develop` rather than off the still-open `CTX-303.1` branch, so it can land
    independently in either order.
