# CTX-308.9: Implementation Context: Per-Project Footprint Override

> **Spec Reference:** Links to [SPEC-308](../specs/SPEC-308-footprints-schematic-advisor.md)

Real user feedback, same live-testing session as `CTX-306.7`: "the footprint needs to be
changeable. There is no guarantee that the same footprint would be used in every project for the
component... This means we need to manage footprints to component mappings for each project." Item
2 of 3 in the user's own explicit ordering (visual previews → per-project footprint override →
agent-guided search).

## 1. Feature Definition & Execution Plan

### Phase 1: Backend -- a real, additive override store
*   [x] `library_store.py`: `Project.footprint_overrides: dict[part_id, footprint_id]`, backfilled
    to `{}` the same way `parts` already is. `set_project_footprint_override(project_name, part_id,
    footprint_id)` sets or, with `footprint_id=None`, clears one entry -- one route for both, no
    separate clear endpoint. Deliberately does **not** create, duplicate, or validate a Footprint
    record -- it only ever stores a foreign-key pointer to one the caller already persisted via
    `library.save_footprint`/`library.import_community_footprint`/
    `kicad.generate_footprint_from_part`.
*   [x] `daemon.py`: `project.set_footprint_override` route, thin wrapper, synchronous (fast local
    file I/O, matching `project.add_part_reference`'s own precedent -- not `ASYNC_ROUTES`).

### Phase 2: Frontend -- resolve, display, and set/clear an override
*   [x] `lib/projects.ts`: `Project.footprint_overrides?: Record<string, string>`;
    `setProjectFootprintOverride(projectName, partId, footprintId)`.
*   [x] `lib/footprints.ts`: three new `*ForProjectOverride`/`*ToProjectOverride` functions
    (`attachFootprintToProjectOverride`, `attachCommunityFootprintToProjectOverride`,
    `generateFootprintForProjectOverride`) -- one per existing footprint source. Each reuses the
    existing source's own real persistence step (`saveFootprintRecord`/`generateFootprint`, both
    split out of the original `attachFootprintToPart`/`generateFootprintFromPart` so the logic isn't
    duplicated) but records the result as this project's own override instead of resaving the Part.
*   [x] `PartDetail.tsx`: `effectiveFootprintId` (the project's own override, if any, else the
    Part's global default) replaces every direct read of `savedPart.footprint_id` for *display,
    preview, and export* -- the linked-view gate itself (which UI to show at all) stays keyed on the
    Part's own real `footprint_id`, since an override has nothing to override without a default
    first. A "Use a different footprint for this project…" control (shown only once a project is
    open and a default exists) reopens the same Find-Footprint search UI in "override mode" --
    candidate selection routes to the new `*ForProjectOverride` functions instead of the default-
    setting ones, and a "Reset to default (...)" control clears it. `justSetOverrideFootprintId`/
    `justClearedOverride` overlay onto the `currentProject` prop the same way `justAddedToCurrentProject`
    already does elsewhere in this file, since the prop itself never refreshes mid-session.

### Phase 3: Product-plan honesty -- reversing a prior explicit decision
*   [x] `PRODUCT-PLAN.md` §2.1's Part row said "References one symbol and one footprint" --
    singular, no per-project variation, an explicit, Approved (2026-08-11) decision `CTX-304.3`
    itself had already confirmed with the user at the time ("Deliberately not in scope: Symbols and
    Footprints stay purely global... this is SPEC-304's own already-decided design"). This context's
    own feature directly reverses that specific clause. Amended `PRODUCT-PLAN.md` in place (dated
    2026-08-22, same pattern as the existing 2026-08-21 Conversation-lifetime amendment) rather than
    silently building around it -- the override is additive and doesn't touch the *separate* axis
    that clause also protects (Footprint stays one global library object, never duplicated per
    part/project -- `test_005_one_footprint_record_is_not_duplicated_per_part` in
    `test_library_store.py` still passes, unmodified, because that cardinality is untouched).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (the significant one -- see Phase 3 above): reverses a prior, explicit, Approved
    product decision (`PRODUCT-PLAN.md` §2.1, confirmed with the user via `CTX-304.3`).**
    *   *Reasoning:* the user's own later, more specific real-world feedback ("no guarantee the same
        footprint fits every project") supersedes the earlier, more general "footprints stay purely
        global" framing -- but only on the *Part→Footprint reference* axis, not the *Footprint-is-a-
        shared-global-object* axis, which this feature deliberately leaves untouched.
    *   *Impact:* `PRODUCT-PLAN.md` amended in place rather than silently drifting from documented
        intent; `CTX-304.3` itself is left unedited (a Completed context's own history isn't
        rewritten) -- this context is where the reversal is recorded, per this repo's own "record
        Plan Drift honestly" norm.
*   **Deviation 2: connection guidance (`kicad.generate_connection_guidance`) still reads the Part's
    own global `footprint_id` server-side, not the project's override.**
    *   *Reasoning:* out of scope for this slice -- the daemon route takes only `part_id`, and
        guidance content is about decoupling/protection/power drawn from the part's pins and
        datasheet, not footprint pad geometry specifically. Wiring a footprint-id-aware guidance path
        would be new backend scope, not a frontend display change.
    *   *Impact:* named here as a known, real gap rather than silently glossed over. A future context
        should revisit whether guidance actually needs footprint awareness before building it --
        not obviously needed yet.
*   **Deviation 3 (explicitly not attempted, scoped out up front): community *symbol* import
    (`handleImportCommunitySymbol`) has no override counterpart.**
    *   *Reasoning:* `SPEC-314` §1's own non-goal boundary already excludes schematic symbol
        placement/attachment entirely (symbols import to the library only, never attach to a Part) --
        this is unrelated to footprint overrides and was never in scope for either path.
    *   *Impact:* no change needed; noted only to be explicit that this wasn't overlooked.
