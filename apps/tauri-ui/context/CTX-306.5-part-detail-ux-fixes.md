# CTX-306.5: Implementation Context: Part Detail & Components UX Fixes

> **Spec Reference:** Links to [SPEC-306](../specs/SPEC-306-component-discovery.md)

Real, detailed live-testing feedback on `CTX-306.4`'s own shipped work (the project-picker and
Project Parts list), plus several longer-standing `PartDetail`/`SPEC-306` UX issues found in the
same session: a real bug, a friction point in the "Add to project" flow, layout problems for a
real many-pin part (ESP32-S3), and a genuinely mysterious "Community Libraries" feature that turned
out to work exactly as designed but was never explained anywhere in the UI.

## 1. Feature Definition & Execution Plan

### Phase 1: A real bug -- stale search results block the Project Parts list forever
*   [x] `ComponentDiscovery.tsx`'s `candidates` state only ever reset on a genuine project switch
    (`useEffect([projectName])`) -- once any search had run, its results stayed on screen
    permanently, since the Project Parts list is gated on `candidates.length === 0`. The user's own
    account: after adding a part to its project and clicking back, they saw the "Did you mean" list
    again, not the Project Parts list -- and had to switch tabs and back to clear it.
*   [x] Added `handleClearSearch()` and a real, visible **"← Back to project parts"** link on the
    "Did you mean" results view -- the explicit escape hatch this state model was missing.
*   [x] **Investigated, not changed:** whether `handleOpenProjectPart` also needed to clear stale
    `candidates` was checked directly against the render condition (`candidates.length === 0 &&
    ...`) that gates the "Open" button it's called from -- `candidates` is already provably empty
    whenever that button is clickable, so an extra clear there would have been dead code. Named here
    rather than silently added on a hunch.

### Phase 2: "Add to project" -- skip the picker when the current project is already known
*   [x] Real user feedback: "it asked which project. this should just be the current project if
    you are viewing the component inside a project... if you are reviewing from the library, asking
    which project is appropriate." `PartDetail.tsx` now branches on `currentProject`: when set, a
    single **"Add to project '‹name›'"** button calls `addProjectPartReference` directly, no
    picker; when already linked (either from `currentProject.parts` or just added this session), it
    shows **"✓ In project '‹name›'"** instead of a button. The multi-project picker (`CTX-306.4`'s
    original design) is now reachable only when `currentProject` is null -- the real Library view,
    where there genuinely is no project to default to.

### Phase 3: Combine "Add to library…" and "Add to project…" onto one row
*   [x] Real user feedback: these were two separate bordered sections; combined into one row
    (`flex flex-wrap items-center gap-2`), each picker's own expanded UI still rendering below the
    row when open.

### Phase 4: Actions moved to the top of the part display
*   [x] Real user feedback: "the main actions... feel buried in the component as if the pins above
    are not related to the component." The Save-to-Library/Saved-to-library block and the combined
    Add-to-library/Add-to-project row now render immediately under the part identity header, before
    the pin table -- not after it.

### Phase 5: Collapsible pin table
*   [x] Real user feedback: an ESP32-S3's real 54 pins dominated the whole page. The pin table is
    now wrapped in a real `<details>`, open by default at or below 16 pins (nothing to hide),
    collapsed by default above that, with a `"N pins"` summary either way. A fuller multi-column
    layout was discussed and deliberately deferred -- named as real, separate, still-open follow-up
    work, not attempted here.

### Phase 6: Find Footprint / Community Libraries clarity
*   [x] "Find Footprint"'s placeholder (`"search this machine's own KiCad libraries"`) didn't say
    what to actually type -- changed to `"search by footprint or package name, e.g. SOIC-8"`.
*   [x] Investigated "Community Libraries doesn't work / is a mystery" directly against
    `community_libraries.py`, `footprints.ts`, `Settings.tsx`, and `SPEC-314` itself before touching
    anything -- confirmed this is not a bug: it's a deliberate, fixed, curated two-repo allowlist
    (Espressif, SparkFun), `SPEC-314` §1's own explicit non-goal against an unbounded GitHub-wide
    search, with growth scoped to maintainer-added entries, never a user-facing config surface. The
    real gap was discoverability -- the section silently reuses the "Find Footprint" box above it,
    and nothing said the search was scoped at all. Added one line of caption naming both facts.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (non-deviation, confirmed as designed): `handleOpenProjectPart` was NOT given its
    own defensive `candidates` clear, despite that being the first fix attempted.**
    *   *Reasoning:* traced the real render condition gating the "Open" button this handler is
        called from (`candidates.length === 0 && ...`) -- by construction, `candidates` is already
        empty whenever that button can be clicked. A test written to prove the opposite scenario
        (opening a project part "while a stale search is still on screen") turned out to be
        unwritable through real UI navigation, which is what caught this before it shipped as dead
        code.
    *   *Impact:* the one real fix (the explicit "← Back to project parts" link) is smaller and
        more honest than originally planned; no speculative defensive code was added alongside it.
*   **Deviation 2 (non-deviation, confirmed as designed): Community Libraries was not changed to
    accept user-configured sources.**
    *   *Reasoning:* `SPEC-314` §1 explicitly rejects an unbounded, live GitHub-wide search as a
        non-goal, and its own Design Rationale states the allowlist "grows by adding entries, not
        by broadening a live search" -- a maintainer/code-level action, never scoped as a runtime
        user setting anywhere in the spec. The real user complaint was solvable with a one-line
        caption naming the actual, real scope, not a new feature.
    *   *Impact:* none -- the fixed, two-repo allowlist behaves exactly as it did before; only its
        legibility to a user changed.
*   **Deviation 3 (real, honest gap): multi-column pin layout was discussed and explicitly deferred,
    not attempted.**
    *   *Reasoning:* the collapsible fix alone (Phase 5) already meaningfully addresses the reported
        pain (a huge table dominating the page); an actual column-based re-layout is a real,
        separate visual redesign question, not a small addition to this same patch.
    *   *Impact:* real, named follow-up work if still wanted after seeing the collapsible version in
        use.
