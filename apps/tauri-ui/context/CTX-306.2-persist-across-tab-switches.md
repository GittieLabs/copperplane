# CTX-306.2: Persist Across Tab Switches

> **Spec Reference:** Links to [SPEC-306](../specs/SPEC-306-component-discovery.md)

## 1. Feature Definition & Execution Plan

Real, severe bug reported directly by the user: "After creating a component and doing all of the
work for creating a design guidance and other functions, the work is gone if you switch tabs."

**Root cause, confirmed by reading the real code**: `App.tsx` rendered `ComponentDiscovery` with a
plain conditional (`{view.area === 'components' && <ComponentDiscovery />}`), so switching to any
other area tab (Overview/Schematic/PCB/Enclosure) fully unmounted it -- destroying its own
`confirmed` state (which candidate the user picked) and, with it, the entire `PartDetail` subtree
mounted underneath, including `savedPart` (populated only by in-memory setter results from
`saveConfirmedPart`/`generateDesignGuidance`/`attachFootprintToPart`, never re-fetched). Real,
directly precedented bug: `App.tsx`'s own existing doc comment already describes this exact failure
mode being fixed once before, for `BoardAdvisor`/`SchematicAdvisor`/`EnclosurePanel` -- "switching
tabs away and back threw away a check... that had just finished, with no reason to." Those three
were fixed with a CSS-hide-instead-of-unmount pattern; `ComponentDiscovery` was simply never
included when that fix was made, and kept using the older, broken pattern.

**Fix**: apply the exact same, already-proven pattern. `ComponentDiscovery` now renders inside a
`data-testid="components-area"` wrapper `div`, hidden via a `hidden` class instead of conditionally
unmounted, matching `schematic-area`/`pcb-area`/`enclosure-area`. Takes a new `projectName` prop and
resets its own state via `useEffect(..., [projectName])`, so a genuine project switch still starts
fresh -- the same real distinction (tab switch vs. project switch) the other three areas already
draw.

**Named, honest, real scope boundary**: this fixes the reported symptom for the common case --
switching tabs within the same app session. It does **not** add a way to reload an already-saved
Part's full record from the backend on a fresh mount (e.g. after an app restart, or from the
Library browser) -- `library.load_part` already exists as a real backend route and is already used
by `LibraryArea` for its own summary display, but no `PartDetail`-shaped loader exists yet, and
`PartDetail` itself only ever accepts a `candidate` (a fresh, unconfirmed search result), not an
already-saved Part. That is real, separate, larger scope -- also raised by the same user feedback
("Save to Library button as the only way to get to the main functionality") -- tracked as a distinct
follow-up, not attempted in this pass.

### Phase 1: `ComponentDiscovery.tsx`
*   [x] Accepts a real `projectName: string` prop.
*   [x] `useEffect` resets all local state (`query`, `status`, `error`, `candidates`, `confirmed`,
    `confirmingPartNumber`, `pathCopied`) when `projectName` changes.

### Phase 2: `App.tsx`
*   [x] `ComponentDiscovery` rendered inside a `data-testid="components-area"` wrapper, hidden via
    CSS instead of conditionally unmounted, matching `schematic-area`/`pcb-area`/`enclosure-area`.
    Passes `projectName={view.name}`.

### Phase 3: tests
*   [x] `ComponentDiscovery.test.tsx`: a real test proving a confirmed candidate survives being
    re-rendered with the same `projectName` (what a tab switch away and back actually produces --
    the exact real bug); a real test proving a genuine project switch still resets it. Every
    existing `render(<ComponentDiscovery />)` call updated for the new required prop.

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

Applies an already-established pattern (App.tsx's own CSS-hide mounting for the other three area
panels) to the one area that was missed, rather than inventing a new mechanism. The real, larger
follow-up this same feedback surfaced -- reloading an already-saved Part from the Library browser
via `library.load_part`, requiring a `PartDetail` restructure to accept an already-loaded record
instead of only a fresh `candidate` -- is named above and left for a dedicated future context.
