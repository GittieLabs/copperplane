# CTX-311.14: Real user feedback on the first Export click-through: dead buttons, illogical grouping, misplaced lid toggle

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

`CTX-311.13`'s Export feature shipped and the user's own first click-through confirmed it works, but
named three real, distinct UX problems in the same message: (1) "Open .step"/"Open lid .step" appear
to do nothing when clicked; (2) the parts (Body/Lid/Combined) and format (STEP/STL/GLB/FreeCAD)
controls aren't grouped or ordered logically -- parts shows even when FreeCAD is selected, even
though FreeCAD always ignores it; (3) "Show lid" is mixed in among the Open/Export buttons instead of
living near the rotation/orbit controls it's conceptually grouped with.

## 1. Feature Definition & Execution Plan

### Phase 1: real root-cause investigation for "Open .step" doing nothing
*   [x] Confirmed by reading the code, not guessed: `open(result.step_path)` (`@tauri-apps/plugin-
    shell`) asks the OS to open the file with its default handler. `tauri.conf.json`'s own
    `plugins.shell.open` scope regex (`^(https?://.+|/.+|[A-Za-z]:[\\/].+)$`) does permit an absolute
    path like `result.step_path` -- the ACL isn't the blocker. The real, most likely cause: no
    application is registered as the default handler for `.step` files on a typical macOS install
    (unlike `.pdf`/`.png`, STEP has no common OS-level default), so the OS's own "open with" either
    silently no-ops or shows its own native dialogue the user doesn't associate with this click; the
    call also had no `.catch()`, so any real rejection surfaced nowhere in the UI either way.
*   [x] **Decision: remove both buttons entirely, not fix them.** `CTX-311.13`'s own Export action
    already supersedes their real purpose -- a user-chosen, durable file the user can then open with
    whatever tool they actually have, rather than gambling on OS default-app association. Keeping a
    second, weaker, silently-failing path to the same transient internal file added confusion, not
    value.

### Phase 2: real Export flow redesign
*   [x] Real, ordered two-step flow, per the user's own ask ("first choose to export, then choose
    export type, [then, if relevant,] parts"): a single "Export…" trigger reveals a real, grouped
    card -- Format first (always shown), Parts second (**only rendered when the format actually uses
    it** -- hidden entirely for `.FCStd`, which `CTX-311.13`'s own backend already always exports as
    the whole design regardless of `parts`), then a real "Choose location…" action that performs the
    actual native save-dialog + export, plus a "Close" action that dismisses the card without doing
    anything.
*   [x] A real success message ("Exported to `<path>`") replaces the card once the export completes,
    closing the same "does this button do anything" gap the old Open buttons had -- Export now gives
    real, visible confirmation.
*   [x] Real, minor naming fix found while wiring this up: the export card's own dismiss action was
    initially also labelled "Cancel," identical to the pre-existing Generate-job Cancel button. Not
    proven to coexist visibly in the real app (the real `submitJob` fires a `completed` status
    update that hides the Generate Cancel button before a result -- and therefore Export -- ever
    renders; a mocked test job handle that never fires `onUpdate` was what actually surfaced the
    ambiguity), but renamed to "Close" anyway since it's a clearer, more accurate label for dismissing
    a selection card versus cancelling an in-flight operation.

### Phase 3: move "Show lid" to the camera controls
*   [x] `EnclosureViewer.tsx` gains an optional `onLidVisibleChange` prop; when both `lidGlbPath` and
    the callback are present, it renders "Show lid" directly beside its own `CameraPresetControls`
    (Top/Bottom/rotate) -- a real display toggle for the viewer belongs with the viewer's own display
    controls, not the panel's action-button row. `EnclosurePanel` still owns the actual `lidVisible`
    state (unchanged) -- only where the checkbox itself renders moved.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: removed functionality (`Open .step`/`Open lid .step`) rather than fixing it.** The
    user's own hunch ("this potentially is the only feature needed [exporting] if my hunch that the
    open step files are meaningless") was investigated, not just trusted -- confirmed via the real
    `shell:allow-open` scope regex (not the blocker) and the real, common absence of any OS-registered
    STEP-file handler (the likely actual cause) before agreeing to remove rather than repair. Removing
    dead, confusing functionality in favor of the real replacement (Export) is preferred here over
    keeping two paths to the same file.
*   **Deviation 2: the "Cancel"/"Close" naming collision was a test-mock artifact, not a proven real
    bug -- named honestly as such, not oversold.** The real `submitJob` implementation
    (`lib/ipc.ts`) fires a real `completed` status update before a result (and therefore the Export
    button) ever renders, so the Generate-job Cancel button should already be hidden by the time
    Export appears in the real app. The rename to "Close" is a real, independent clarity improvement
    kept on its own merits, not reported as fixing a confirmed simultaneous-visibility bug it may
    never have actually had.
*   **Deviation 3: `EnclosureViewer.test.tsx`'s own real testing gap was not closed here.** This file
    has never rendered the full `<EnclosureViewer>` component (only its extracted pure functions),
    since this repo's jsdom test environment has no WebGL/Canvas shim. The new "Show lid" checkbox
    living inside this component is therefore only indirectly covered (via `EnclosurePanel.test.tsx`'s
    prop-passing assertions, plus a manual `act()`-wrapped callback invocation standing in for a real
    click) -- named explicitly rather than silently assumed equivalent to a real render test.
