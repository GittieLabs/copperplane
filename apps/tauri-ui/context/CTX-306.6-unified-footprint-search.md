# CTX-306.6: Implementation Context: Unified Footprint Search

> **Spec Reference:** Links to [SPEC-306](../specs/SPEC-306-component-discovery.md)

Real, detailed live-testing feedback on the "Find Footprint" section, using a real ESP32-S3: the
user didn't know what to type (and reasonably tried the part's own name/package first), and found
the layout genuinely confusing -- the installed-library search, "Generate from datasheet
dimensions," and the community-library search all shared one query box but read as three
disconnected steps, with the generate button sandwiched in the middle rather than positioned as the
real fallback it is. This is the first, quick-fix slice of that feedback; a real feasibility check
for visual footprint/symbol previews, per-project footprint overrides, and agent-guided search was
run in the same session and is deliberately **not** attempted here -- named as real, larger,
separate follow-up work.

## 1. Feature Definition & Execution Plan

### Phase 1: Auto-fill the search box with the part's own package
*   [x] A new `useEffect` keyed on `extraction?.package` sets `footprintQuery` to it once, only
    when the query is still empty -- never fighting a user who's already typed something, or who
    deliberately clears the field back to empty to search something else (the effect's own
    dependency doesn't change again for the same part, so it never re-fires and re-fills a
    since-cleared field).

### Phase 2: One search, one combined result list
*   [x] `handleSearch()` runs both `handleFootprintSearch()` and `handleCommunitySearch()`
    concurrently from the single "Search" button -- the separate "Search community libraries"
    button is gone. Both handlers' own internals are unchanged; only how they're triggered changed.
*   [x] Results render as one combined list -- installed/saved-library candidates first, then
    community candidates, each still labeled by its own real source (`· KiCad library`/
    `· previously saved`/`owner/repo · license · kind`) -- rather than two visually separate
    sections. The "no match" message is now a single, honest one, shown only once *both* real
    searches have actually returned and *both* came back empty.
*   [x] **Real bug found and fixed while building this**: with the results list and the
    multi-symbol `.kicad_sym` browse UI both rendering at once, a `.kicad_sym` candidate's own
    "Import" button in the results list stayed live at the same time as each real symbol's own
    "Import" button inside the browse view -- two competing entry points for the same file. A test
    written against the new combined layout (`getAllByRole('button', {name: 'Import'})[0]`) caught
    this directly: it grabbed the wrong button, called `handleImportCommunityCandidate` a second
    time instead of `handleImportCommunitySymbol`, and (since that mock's result had no `symbols`
    key) fell through to attaching an unconfigured mock's `undefined` result onto `savedPart`,
    breaking the whole render. Fixed by hiding the results list entirely while
    `communitySymbolBrowse` is open -- the correct UX regardless of the test that caught it.

### Phase 3: "Generate from datasheet dimensions" moved below the results
*   [x] Real user feedback: this button previously sat between the installed-library results and
    the community-library section, reading as a mid-flow option. It's the real fallback for "found
    nothing installed" -- moved below the combined results, unchanged behavior (still always
    available, never gated on a zero-result search).

### Phase 4 (research only, no code): feasibility of visual footprint/symbol previews
*   [x] Investigated directly, not guessed: the live KiCad IPC bridge (`kicad_bridge.py`) has *no*
    render/export/image capability at all -- confirmed by grep and by two other bridge modules'
    own docstrings independently reaching the same conclusion for their own purposes
    (`kicad_cli.py`, `fp_lib_table.py`).
*   [x] **Real, already-verified-in-this-repo capability found**: `kicad-cli sym export svg` and
    `kicad-cli fp export svg` are both already invoked -- today only inside this repo's own test
    suite (`test_library_store.py`), as a real-KiCad-parses-this-file verification step, never
    surfaced to a user. The exact invocation shape for both (including `fp export svg`'s real,
    tested requirement of the containing `.pretty` directory plus `--footprint <name>`, not the
    `.kicad_mod` path directly) is proven, not theoretical.
*   [x] Confirmed the existing "show the user something visual" precedent in this app
    (`EnclosureViewer.tsx`, fed by `freecad_bridge.py`/`kicad_cli.export_board_glb`) is a live,
    interactive 3D mesh viewer -- correct for a real 3D enclosure, but heavier machinery than a
    flat 2D footprint/symbol image needs. A static SVG (already exactly what `kicad-cli` produces)
    rendered as an inline image is the right-sized approach here, not a second 3D viewer.
*   [x] Confirmed via a repo-wide search this was never previously scoped, discussed, or rejected
    in `SPEC-308` or anywhere else -- a genuine green-field feature, not a revisit.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (real, honest gap): visual previews, per-project footprint overrides, and
    agent-guided footprint search were all discussed at length but deliberately not attempted in
    this context.**
    *   *Reasoning:* each is a genuinely separate, substantial piece of work -- a new backend image-
        generation route plus frontend rendering; a real data-model change (project-scoped
        footprint override, falling back to the Part's own global default); and a feature that
        depends on `SPEC-206`/`SPEC-318`'s own chat-agent work being further along. Bundling any of
        them into this quick-fix pass would have made the diff much harder to review honestly.
    *   *Impact:* named here as real, scoped follow-up work, with the feasibility research already
        done for the visual-preview piece (Phase 4 above) so a future context doesn't have to
        re-derive it.
*   **Deviation 2 (real, found and fixed mid-implementation, not part of the original plan): the
    community-candidate/symbol-browse "two live Import buttons" bug.**
    *   *Reasoning:* this bug already existed in the pre-`CTX-306.6` layout too (the original
        candidate's own "Import" button was never actually hidden while browsing its symbols
        either) -- it simply never surfaced because the *old* render order happened to put the
        browse view's buttons first in the DOM, and no test ever asserted on button order/index
        directly. Writing a real test against the new, combined layout is what caught it.
    *   *Impact:* fixed for both the new unified list and, incidentally, the underlying bug that
        predated this context -- named honestly rather than claimed as something this context set
        out to find.
