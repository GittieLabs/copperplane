# CTX-315.1: Implementation Context: Library Storage Schema, Registry & Routes

> **Spec Reference:** Links to [SPEC-315](../specs/SPEC-315-library-browsing-and-organization.md)

The real storage/backend slice, matching this spec family's own established split
(`CTX-314.1`/`CTX-314.2`): a real `library_ids` field on Part/Symbol/Footprint records, a real
library registry (Default plus user-created custom ones, each with real counts), and the daemon
routes a future `CTX-315.2` builds the actual Library area UI against. No UI in this slice --
`Rail.tsx`'s Library entry keeps pointing at today's placeholder until then.

**Real gaps found while planning this slice, not assumed:** `library_store.py` has no
`list_symbols()` function at all today (`list_parts`/`list_footprints` exist; Symbol never got the
same treatment) -- a real, pre-existing gap this slice closes since a library's own Datasheets/Pins
section needs to list Symbols, not just Parts. Similarly, `daemon.py` never registered
`library.list_footprints`/`library.list_symbols` as routes at all (only `library.list_parts` is
wired) -- confirmed by grepping the real route table, not assumed from the module functions
existing.

## 1. Feature Definition & Execution Plan

### Phase 1: `library_ids` on every Part/Symbol/Footprint record
*   [x] `library_store.py`: `save_part`/`save_symbol`/`save_footprint` accept an optional
    `library_ids: list[str]` param (default `None`), always writing a real `library_ids` field --
    `["default"]` when not given, and `"default"` force-included even when the caller passes a
    custom set (SPEC-315 §2's own real rule: "Default membership is implicit and never shown as
    something to remove").
*   [x] `load_part`/`load_symbol`/`load_footprint`: a record saved before this slice ships has no
    `library_ids` key at all -- the real, honest migration is read-time backfill
    (`record.setdefault("library_ids", ["default"])`), never a crash and never a silent empty
    library. Verified directly against a real, hand-written pre-migration fixture record, not
    assumed to work from the code alone.

### Phase 2: the real library registry
*   [x] `library_store.py`: new `library/libraries.json` -- a real, small registry of custom
    libraries (`{"id": ..., "name": ..., "created": ...}`); `"default"` is never a real entry in
    this file (it's implicit, per Phase 1), so an empty/missing registry file is a normal, honest
    starting state, not an error.
*   [x] `create_library(name: str) -> dict`: real id derivation from the name (slugified,
    collision-checked against the real registry -- a second "ESP32 Boards" gets a real, distinct id,
    never silently overwrites the first).
*   [x] `list_libraries() -> list[dict]`: returns Default (real, computed counts across *every*
    Part/Symbol/Footprint, not just tagged ones -- it's implicit membership) plus every registry
    entry, each with its own real `part_count`/`symbol_count`/`footprint_count` computed by
    scanning `library_ids` across the real, current files. A real, honest O(n) scan over whatever
    exists on disk -- `SPEC-304`'s own `.index/` SQLite cache is explicitly out of scope for this
    slice (named, not silently built or silently ignored); acceptable at this app's real current
    scale, revisited only if it becomes a real, measured problem.
*   [x] `list_symbols() -> list[str]`: new, matching `list_footprints`'s own established pattern --
    the real, pre-existing gap named above.
*   [x] `list_parts`/`list_symbols`/`list_footprints` gain an optional `library_id: str = None`
    filter -- unfiltered call unchanged (every existing caller, e.g. `library.list_parts` today,
    keeps working with zero params).
*   [x] `tag_object(kind: str, object_id: str, library_ids: list[str]) -> dict`: real
    replace-not-append semantics for one object's own custom-library membership (matching the "Add
    to library..." action's own real UI shape from SPEC-315 §5 -- a user picks the full set, not an
    incremental add) -- `"default"` force-included the same way Phase 1's save path does, and a
    `library_id` that isn't in the real registry raises a clear `SchemaValidationError`, never
    silently created.

### Phase 3: daemon routes
*   [x] `daemon.py`: `library.list_libraries`, `library.create_library`, `library.tag_object` --
    thin wrappers, matching every existing `library.*` route's own convention.
*   [x] `daemon.py`: register the real, previously-missing `library.list_footprints`/
    `library.list_symbols` routes (Phase 2's `list_symbols` plus the already-existing
    `list_footprints`), both accepting the new optional `library_id` param.
*   [x] `daemon.py`: `library.list_parts` gains the same optional `library_id` param, passed through
    to `library_store.list_parts`.

## 4. Plan Drift & Architectural Changes

- **A real, serious bug caught before it ever shipped, found while wiring Phase 1, not assumed
  away.** The original plan's own `save_part`/`save_symbol`/`save_footprint` signatures (an
  optional `library_ids` param, defaulting to `["default"]` when absent) would have silently reset
  any real, already-set custom library tags every time an existing code path re-saved an
  already-loaded record without passing `library_ids` explicitly -- and grepping the real call
  sites found three of exactly that shape already in this codebase (`attachFootprintToPart`,
  `generateFootprintFromPart`, and `kicad_generate_footprint_from_part`'s own footprint re-save, all
  via `daemon.py`'s thin `library_save_part`/`library_save_footprint` wrappers, which pass the
  caller's dict straight through). Fixed with a real precedence rule
  (`_resolve_library_ids`): an explicit `library_ids` argument wins; otherwise the record's own
  already-set field (from a prior `load_part`/`load_symbol`/`load_footprint`) is preserved; only a
  record with neither becomes Default-only. `TestLibraryTagging.test_004` verifies this directly --
  re-saving a tagged Part through the exact same shape `attachFootprintToPart` uses keeps its real
  custom tags. Recorded here because the original Phase 1 plan text (as written) would have shipped
  the bug; the fix changed `_normalize_library_ids`'s own call sites, not the public API shape.
- **`list_libraries`'s own Default counts are computed via the unfiltered `list_parts()` /
  `list_symbols()` / `list_footprints()` calls, not a separate code path** -- matches the plan's own
  intent (Default membership is implicit, covering everything) without a second counting
  mechanism that could drift from the real filtered one.
- No other deviation from the original plan. The O(n)-scan filtering, the registry file shape, and
  the deliberately-deferred `.index/` SQLite cache all shipped exactly as scoped.
