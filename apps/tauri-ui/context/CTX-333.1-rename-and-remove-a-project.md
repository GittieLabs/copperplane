# CTX-333.1: Implementation Context: Renaming and Removing a Project

> **Spec Reference:** Links to [SPEC-333](../specs/SPEC-333-project-save-semantics-and-rename.md)

Two operations on the same record, through the same menu, so they are specified and built together
rather than producing two inconsistent affordances a month apart.

*   **Rename** — `SPEC-333`'s original outstanding half. There is no rename route; saving under a
    new name writes a second pointer record and leaves the first, so one folder becomes two
    projects and the old entry loads with a name its own folder contradicts.
*   **Remove** — requested 2026-09-03: *"I believe we need a way to 'soft delete' a project. All
    this should do is remove from the project list in the app."*

## 0. What removal is actually removing from

There is no project registry. `library_store.list_projects` is an `os.listdir` of
`<storage_root>/projects/` filtered to folders holding `project.json`. So "remove from the list"
has to mean one of: stop writing `project.json`, move the folder, or record a flag the listing
respects. Only the third leaves the user's files exactly where they are, which is the whole
request.

## 1. Feature Definition & Execution Plan

### Phase 1: Settle the removal record
*   [x] A flag in the project's own `project.json`, or an entry in `config.json` — `SPEC-333` §2
        states the trade: the flag travels with the folder (consistent with `SPEC-312`'s
        portability), the config list leaves the user's files untouched but makes the state
        machine-local.
*   [x] `list_projects` respects it. Everything else that resolves a project by name must keep
        working, because a removed project is hidden, not gone.

### Phase 2: Remove, and bring back
*   [x] A remove action on the project, with a confirmation that says plainly that **nothing is
        deleted** — the word the user brings to this is "delete", and being wrong in either
        direction costs trust or costs work.
*   [x] Restoring: `project.open_from_directory` already exists for exactly "restore a project from
        a folder" (`CTX-312.3`). If removal is a flag, pointing at the folder again is the undo,
        with no new surface at all. Confirm that before building a "show removed" view.

### Phase 3: Rename
*   [x] A real rename route that moves the record rather than writing a second one.
*   [x] The folder on disk is **not** renamed — `SPEC-333`'s existing non-goal, unchanged.
*   [x] A name that collides with an existing project is refused, not silently merged.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1, before implementation: this context deliberately covers two features.** They are
    the same record, the same route module and the same menu, and building them a month apart is
    how an app ends up with a confirmation dialog for one and none for the other. `SPEC-337` was
    written this week because two related concepts got two different vocabularies; this is the same
    hazard, caught earlier.

*   **Prediction, checked: right about rename, wrong about why.** Rename was the harder half, and
    the name-in-two-places problem resolved cleanly: identity is the `projects/<name>/` folder in
    the **app's own storage**, so renaming moves that and never touches the user's linked folder —
    `SPEC-333`'s non-goal is satisfied by construction, not by care. What actually bit was
    unrelated: `_project_dir` goes through `_ensure_dir`, so merely *computing* the target path
    **created** it, and the collision check then fired every time. The same trap `CTX-110.2` hit
    one function earlier the same afternoon.

*   **Deviation 2: the flag lives on the app's pointer record, not the user's manifest.** `SPEC-333`
    §2 framed this as a trade between `project.json` (travels with the folder) and `config.json`
    (leaves the user's files alone). It is neither: a project's pointer record lives in
    `<storage_root>/projects/<name>/`, which is the app's own bookkeeping. The flag therefore
    travels with the storage root and never touches anything of the user's — both halves of the
    trade, because the question had a third answer.

*   **Deviation 3: listing now reads every pointer instead of checking a file exists.** Respecting
    the flag requires knowing what is in each record. An unreadable pointer is listed rather than
    hidden: hiding a project because its JSON is damaged would be a worse answer than listing it
    and letting `load_project` report the real problem.

*   **Deviation 4: a removal with no route back would have been a trap, so there is one.** The
    request was minimal — "All this should do is remove from the project list" — and an unlinked
    project has no folder to point at, so `project.open_from_directory` could not have been the
    undo for every case. The launch view now shows "N removed from this list" only when there are
    any, expanding to a **Put back** for each.
