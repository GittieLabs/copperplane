# CTX-333.1: Implementation Context: Renaming and Removing a Project

> **Spec Reference:** Links to [SPEC-333](../specs/SPEC-333-project-save-semantics-and-rename.md)

Two operations on the same record, through the same menu, so they are specified and built together
rather than producing two inconsistent affordances a month apart.

*   **Rename** — `SPEC-333`'s original outstanding half. There is no rename route; saving under a
    new name writes a second pointer record and leaves the first, so one folder becomes two
    projects and the old entry loads with a name its own folder contradicts.
*   **Remove** — requested 2026-09-03: *"I believe we need a way to 'soft delete' a project. All
    this should do is remove from the project list in the app."*

## 0. What removal is actually removing from

There is no project registry. `library_store.list_projects` is an `os.listdir` of
`<storage_root>/projects/` filtered to folders holding `project.json`. So "remove from the list"
has to mean one of: stop writing `project.json`, move the folder, or record a flag the listing
respects. Only the third leaves the user's files exactly where they are, which is the whole
request.

## 1. Feature Definition & Execution Plan

### Phase 1: Settle the removal record
*   [ ] A flag in the project's own `project.json`, or an entry in `config.json` — `SPEC-333` §2
        states the trade: the flag travels with the folder (consistent with `SPEC-312`'s
        portability), the config list leaves the user's files untouched but makes the state
        machine-local.
*   [ ] `list_projects` respects it. Everything else that resolves a project by name must keep
        working, because a removed project is hidden, not gone.

### Phase 2: Remove, and bring back
*   [ ] A remove action on the project, with a confirmation that says plainly that **nothing is
        deleted** — the word the user brings to this is "delete", and being wrong in either
        direction costs trust or costs work.
*   [ ] Restoring: `project.open_from_directory` already exists for exactly "restore a project from
        a folder" (`CTX-312.3`). If removal is a flag, pointing at the folder again is the undo,
        with no new surface at all. Confirm that before building a "show removed" view.

### Phase 3: Rename
*   [ ] A real rename route that moves the record rather than writing a second one.
*   [ ] The folder on disk is **not** renamed — `SPEC-333`'s existing non-goal, unchanged.
*   [ ] A name that collides with an existing project is refused, not silently merged.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1, before implementation: this context deliberately covers two features.** They are
    the same record, the same route module and the same menu, and building them a month apart is
    how an app ends up with a confirmation dialog for one and none for the other. `SPEC-337` was
    written this week because two related concepts got two different vocabularies; this is the same
    hazard, caught earlier.

*   **Prediction, recorded now:** I expect the removal flag to be the easy half and rename to
    surface something unpleasant, because a project's name is its directory name in
    `<storage_root>/projects/` **and** a field inside `project.json`, and `SPEC-333` §1 already
    documents them disagreeing. If rename turns out to require touching the folder name, that
    collides with the existing non-goal and needs the maintainer, not a decision made here.
