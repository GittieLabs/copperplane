# CTX-311.6: Real visual contrast fix: body/lid coloring, lighter background, softer lighting

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

Real user feedback, immediately following `CTX-311.5`'s own real fix for the lid not displaying at
all: once the lid *did* render (position and axis both correct), it was still "too hard to see how
big the lid is" -- the body and lid share the same default, colorless material from `freecad_bridge.
py`'s own STL/glTF export, against the same dark, same-toned background the base enclosure has
always used. The user asked for real color contrast between body and lid, and a lighter/white
background. In the same round, the user separately reported the existing lighting reading as "hard
and dark shadows," diagnosing it themselves as "the light is too strong."

## 1. Feature Definition & Execution Plan

### Phase 1: real body/lid color contrast
*   [x] `EnclosureViewer.tsx`: `applyMeshColor(object, color)` -- a real, direct traversal that sets
    a uniform color on every real mesh material found in a loaded scene. Mutates the already-loaded
    scene's own materials in place (each `useGlbScene` load produces a fresh, unshared material
    graph, so nothing else is affected).
*   [x] `BODY_COLOR` (slate-500, `0x64748b`) applied to the base shell; `LID_COLOR` (orange-500,
    `0xf97316`) applied to the lid -- a real, high-contrast accent color chosen specifically to read
    clearly against both the body's own color and the new lighter background.
*   [x] Applied via two small `useEffect`s keyed on `base.scene`/`lid.scene` respectively -- once per
    real new load, not re-applied every render.

### Phase 2: lighter background
*   [x] `VIEWER_BACKGROUND_COLOR` (gray-200, `#e5e7eb`) replaces the previous dark `#3f3f46` --
    directly requested ("the background could also be lighter or white"), and a real, necessary
    precondition for the body/lid colors above to read clearly (a mid-gray body barely stood out
    against the old dark background either).

### Phase 3: softer lighting
*   [x] Real user diagnosis, confirmed correct: a single strong `directionalLight` (`intensity=0.8`)
    with a comparatively low `ambientLight` (`intensity=0.6`) produced a sharp brightness swing
    between a flat-shaded box's lit and unlit faces -- read as "hard, dark shadows" even though no
    real shadow-mapping was ever enabled in this `Canvas` (`shadows` was never set, no light/mesh
    ever opted into `castShadow`/`receiveShadow`; the harshness came entirely from directional-light
    contrast on flat-shaded geometry, not literal shadow maps).
*   [x] Rebalanced: `ambientLight` raised to `1.1` (a real, much higher fill floor so no face reads
    as near-black), the main `directionalLight` lowered to `0.3`, and a second, dim `directionalLight`
    (`intensity=0.15`) added from roughly the opposite corner -- softens the single-light contrast
    further without flattening all sense of real shape.

### Phase 4: tests
*   [x] Direct, real unit tests on `applyMeshColor`: sets color on a real single-material mesh; sets
    color on every material in a real multi-material mesh, not just the first; skips non-mesh nodes
    without throwing; `BODY_COLOR`/`LID_COLOR` are confirmed distinct.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: colors and lighting are hardcoded constants, not user-configurable.** SPEC-311's
    own scope is a real, iterative refine loop for the enclosure's *geometry* parameters; visual
    presentation (material color, background, lighting) was never in that parameter set. Treating
    this as a real, fixed visual-quality fix (like the earlier background-color fix in `CTX-301.2`
    Phase 2) rather than opening a new configurable-appearance surface keeps this fix small and
    scoped to what was actually reported.
*   **Deviation 2: no real shadow-mapping was ever enabled, despite the user's own accurate
    description of "hard shadows."** Confirmed by reading the code, not assumed -- `<Canvas>` never
    set `shadows`, and no light or mesh ever opted into `castShadow`/`receiveShadow`. The real
    perceived harshness came from directional-light-driven per-face brightness contrast on flat-
    shaded geometry, a different (if visually similar) phenomenon from literal shadow acne. Worth
    recording so a future session doesn't go looking for a shadow-map bug that was never there.
