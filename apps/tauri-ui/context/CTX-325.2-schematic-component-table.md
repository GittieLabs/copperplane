# CTX-325.2: The Schematic Component Table

> **Spec Reference:** Links to [SPEC-325](../specs/SPEC-325-kicad-project-integration.md)

The UI half. `CTX-325.1` made the daemon able to read a schematic; this is where a user sees it.
Together they close `SPEC-325`.

## 1. Feature Definition & Execution Plan

### Phase 1: Anchor a project to a `.kicad_pro`

*   [x] `pickKicadProject` filters to `kicad_pro`, so a user cannot pick a board or a bare folder
    and get a confusing failure later.
*   [x] `Project.kicad_project_path`, additive. `save_project` already writes *"every field the
    caller supplied"*, so no daemon or schema change was needed.
*   [x] `SPEC-312`'s `directory` link is untouched — `SPEC-325` §2.1 keeps it for projects with no
    KiCad files yet.
*   [x] A linked project reloads on mount, so the link is picked once rather than every visit.

### Phase 2: A table, not a canvas

*   [x] Reference, value, footprint, and one status column.
*   [x] **"no footprint", "footprint not installed" and "no 3D model" are three different labels**,
    because they are three different problems with three different fixes. Collapsing them into
    "incomplete" would hide which one a user actually has.
*   [x] KiCad already draws the schematic, better, and is usually open beside this app. The
    question this answers is *what is in my design and what is missing from it*, which a drawing
    does not answer well.

### Phase 3: Say what was read, and when

*   [x] Nothing is cached — the file is read fresh on every load (`SPEC-325` §2.3).
*   [x] The header reports the read time, so the table never implies live sync with an editor that
    may hold unsaved changes.
*   [x] A count of components missing a 3D model, because that is the number that decides whether
    the enclosure stage can work.

### Phase 4: Two honest empty states

*   [x] A `.kicad_pro` with no sibling `.kicad_sch` says so rather than rendering an empty table
    that reads as "your schematic has no components".
*   [x] **A multi-sheet project carries a warning that the list may be incomplete** — see §4
    Deviation 1. Showing a possibly-partial list as complete would be the worse failure.

### Not in this context

*   **Selecting a row to open part detail** (`SPEC-325` §5). The table is read-only; wiring a row
    to the existing detail view is small but is its own change.
*   **Matching against the app's own library** (`SPEC-325` §2.5).
*   **Anything about the PCB tab, advice, or volumes** — `SPEC-326`/`SPEC-327`.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — an unverified risk became UI copy rather than being quietly dropped.**
    *   `CTX-325.1` could not retire `SPEC-325` §3's multi-sheet question: no hierarchical
        schematic exists on this machine, so whether `kicad-cli sch export bom` walks the hierarchy
        from a root sheet is still unknown.
    *   *Impact:* rather than assume it works or refuse multi-sheet projects, a project reporting
        more than one sheet gets a visible warning that the list is read from the root sheet and
        **may not include the others — and that this has not been verified.** Putting an unverified
        assumption in front of the user is uncomfortable and correct; the alternative is a
        confidently wrong table. This stays open until someone tests a real hierarchical design.

*   **Deviation 2 — three failure labels instead of one.**
    *   The plan implied a single "missing" state. Building it made clear that *no footprint*,
        *footprint not installed*, and *no 3D model* have nothing in common from the user's side:
        the first is a schematic edit, the second is a library install, the third is `SPEC-326`'s
        placeholder problem and may have no fix at all.
    *   *Impact:* one status column, three labels. A user can tell which problem they have without
        opening anything else.

*   **Deviation 3 — no daemon or schema change was needed to persist the link.**
    *   `Project` was expected to need a schema migration for `kicad_project_path`. Reading
        `save_project` first showed it writes *"every field the caller supplied"*, and
        `_validate_project_intent` only constrains `intent`.
    *   *Impact:* a one-line type addition, no migration, no daemon change. Worth recording because
        the instinct was to write a migration for a store that is deliberately permissive.
