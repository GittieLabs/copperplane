# CTX-303.4: Implementation Context: Connectivity Diagnostics Clarity

> **Spec Reference:** Links to [SPEC-303](../specs/SPEC-303-settings-ui.md)

Real user feedback exercising the actual running app: Settings' Tier 2 Connectivity panel showed
"KiCad: not reachable" with zero explanation, and the three path-override fields (KiCad IPC socket
path, KiCad IPC timeout, `freecadcmd` path override) have no inline guidance on what they are, where
their values come from, or when a user would ever need to touch them. `SPEC-303` §5 already promised
"a clear... cue where that's genuinely required" for this panel; this closes the gap between that
promise and what actually shipped.

## 1. Feature Definition & Execution Plan

### Phase 1: real investigation
*   [x] Confirmed real, directly against this machine's own daemon: `_detect_capabilities()`'s
    `kicad_available` check is `os.path.exists(socket_path)` -- a deliberately cheap, non-blocking
    check (`SPEC-107` §3's own real constraint against paying for a slow handshake on every startup),
    not a live connection attempt. This stays unchanged; only the *reporting* of it needs work.
*   [x] Confirmed real: `freecad_bridge.find_freecadcmd()` already either returns the real, resolved
    path on success or raises `FreeCADUnavailableError` with a real, specific, human-readable message
    on failure -- `_detect_capabilities()` currently discards both, collapsing them to a bare
    boolean.
*   [x] Confirmed real: neither `kicad_socket_path`/`kicad_timeout_ms`/`freecadcmd_path_override` in
    `Settings.tsx` carries any description text -- a user has no way to tell, from the UI alone,
    that these are optional overrides they'll almost never need (KiCad/FreeCAD are found
    automatically at their real, standard locations in the overwhelming common case).

### Phase 2: `daemon.py` -- real, cheap diagnostic detail
*   [x] `_detect_capabilities()` gains `kicad_socket_path_checked` (the real, resolved path that was
    checked -- the configured override, or the real default) so the UI can say exactly where it
    looked, not just that it failed.
*   [x] `_detect_capabilities()` gains `freecad_path_checked` (the real path `find_freecadcmd()`
    resolved to, when it succeeds) and `freecad_error` (the real, specific exception message, when it
    doesn't) -- both already computed as a side effect of the existing call, just discarded today.

### Phase 3: `Settings.tsx` -- real explanations, not bare booleans
*   [x] The Connectivity status line shows the real checked path under "not reachable" for KiCad
    (`Checked: <path>`), plus a short, concrete explanation of the likely real causes (KiCad not
    running, or its IPC API not enabled in Preferences → Plugins).
*   [x] FreeCAD's "not reachable" state shows the real `freecad_error` message directly -- it's
    already specific and accurate, just never surfaced.
*   [x] Each of the three path-override fields gains a short, real description: what it's for, that
    it's an optional override (not something to fill in for a standard install), and -- reusing the
    existing "restart to apply" cue this panel already has for these fields -- when it takes effect.

### Phase 4: tests
*   [x] Mocked tests for `_detect_capabilities()`'s new fields: the real checked KiCad path is
    reported whether or not it exists; a successful FreeCAD resolution reports the real found path
    with no error; a failed one reports the real error message with no path.
*   [x] Frontend tests: Settings renders the checked path and explanation when KiCad is unreachable,
    and the real `freecad_error` text when FreeCAD is unreachable.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the KiCad connectivity check stays a cheap, non-blocking `os.path.exists`, not
    upgraded to a real live connection attempt.** A tempting first instinct is "make 'not reachable'
    more accurate by actually trying to connect" -- but `SPEC-107` §3's own real constraint (no slow
    handshake on every startup) still applies, and a stale socket file left behind by a crashed KiCad
    process is a real, understood edge case of the existing design, not a new one this context
    introduces. This context only makes the *existing* check's result legible, not more thorough.
