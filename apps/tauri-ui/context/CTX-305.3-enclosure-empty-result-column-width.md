# CTX-305.3: Implementation Context: Enclosure Doesn't Reserve Space for an Absent Result

> **Spec Reference:** Links to [SPEC-305](../specs/SPEC-305-app-shell-navigation.md)

Real, user-diagnosed bug, found immediately after `CTX-305.2` shipped, via two of the user's own
screenshots of the Enclosure tab at two different window widths. Their own words, verbatim,
correctly diagnosing the mechanism before any code was read: "I believe the issue is that when the
app is made wider and before we hit the breakpoint, the app is taking into account the enclosure
view that will be displayed when generated and has determined the position to be at the bottom...
After we hit the width breakpoint, the app is now expecting to move the enclosure to the top and
side due to more space... so it would appear that even though the enclosure view is not showing,
it has an allocation in the view and affects wrapping." Confirmed exactly right by reading
`EnclosurePanel.tsx`: the 3D-viewer column (`<EnclosureViewer>` and everything around it) was
unconditionally present in the DOM as an empty `flex-1` div even when `result` was `null` (nothing
generated yet). Once the window crossed the `lg:` breakpoint (1024px), `lg:flex-row` activated and
the layout reserved space for that empty column regardless, squeezing the form's own sidebar down
to a fixed `lg:w-96` (384px) for no real reason.

Also checked, per the user's own follow-up suspicion ("the pcb view is doing something similar and
i suspect the schematic view is too"): confirmed **not** present in `BoardAdvisor.tsx` or
`SchematicAdvisor.tsx` -- neither file uses any responsive breakpoint class at all (`grep` for
`lg:`/`md:`/`flex-row` returns nothing in either), and a direct DOM test against
`BoardAdvisor.tsx`'s own real class names confirmed its content card genuinely does stretch to the
full `max-w-4xl` (896px) width already. What looked similar in the user's PCB screenshot is just
the real, expected `CTX-305.2` result -- an 896px-capped card inside a much wider window -- not a
second instance of this bug.

## 1. Feature Definition & Execution Plan

### Phase 1: Only reserve the two-column split when there's a real result
*   [x] `EnclosurePanel.tsx`: the left sidebar's `lg:w-96 lg:flex-none` width classes are now
    conditional on `result` being truthy -- before a result exists, the form is the row's only
    child and naturally takes the full available width (matching the below-`lg` stacked behavior
    instead of pre-committing to a narrow sidebar).
*   [x] The entire right-hand viewer column -- previously an unconditional `<div>` whose *children*
    were each individually gated on `result` -- is now itself wrapped in `{result && (...)}`, so
    it's completely absent from the DOM (not just visually empty) until there's something real to
    show. Removed the now-redundant `result &&`/`result?.` prefixes on its own children, since the
    whole block is already behind one `result` check.
*   [x] Confirmed via direct grep + a real DOM test that `BoardAdvisor.tsx`/`SchematicAdvisor.tsx`
    have no equivalent bug -- no fix needed there.
