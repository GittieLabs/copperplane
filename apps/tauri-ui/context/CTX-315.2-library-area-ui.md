# CTX-315.2: Implementation Context: Library Area UI

> **Spec Reference:** Links to [SPEC-315](../specs/SPEC-315-library-browsing-and-organization.md)

The real UI slice `CTX-315.1` deliberately deferred: turns the rail's Library entry from a static,
unclickable count into a real destination, following `SPEC-305` §2's own real placeholder note
("the Library rail entry ... a real browsing UI ... is out of scope, deferred to a future spec")
and `SPEC-315` §5's own described surface -- a library list with real counts, a two-section
(Datasheets/Pins vs Footprints) detail view per library, and a real "Add to library..." action from
Part Detail.

**Real, pre-existing gap found while planning this slice:** no frontend wrapper exists yet for
`library.load_part`/`library.load_symbol`/`library.load_footprint` at all -- every existing caller
so far only ever lists ids or saves; nothing has needed to fetch one record's own display details
until now. This slice adds them, in `lib/library.ts`, since that's the first real place they're
needed.

**Real design choice carried over from `CTX-315.1`'s own accepted scope:** listing a library's
members returns ids only (matching `library_store.py`'s own real O(n)-scan shape, `SPEC-304`'s
`.index/` SQLite cache explicitly out of scope). This slice fetches each id's own record via
`Promise.all` after the id list comes back, to render real identifying info (part number/package,
or footprint name/license) -- consistent with this app's own already-accepted real-scale
trade-offs, not a new N+1 concern introduced here.

## 1. Feature Definition & Execution Plan

*   [x] New file wrapping `CTX-315.1`'s routes: `listLibraries()`, `createLibrary(name)`,

    `listFootprints(libraryId?)`.
*   [x] `loadPart(partId)`, `loadSymbol(symbolId)`, `loadFootprint(footprintId)` -- the real,

### Phase 2: the real library list + detail view
*   [x] `Rail.tsx`: Library becomes a real, clickable destination (matching Settings' own
    selected/onClick shape exactly) -- `librarySelected` prop, `onSelectLibrary` callback. The
    existing real part count stays as-is (unfiltered `library.list_parts`, `CTX-305.1`'s own

*   [x] New `LibraryArea.tsx`: on mount, calls `listLibraries()` and renders each with its own real
    `part_count`/`symbol_count`/`footprint_count`, plus a real "+ New library" action

    detail) -- no new `App.tsx`-level routing needed beyond the one new `View` kind, matching how

*   [x] The detail view: real, separate Datasheets/Pins (`listParts`/`listSymbols` for this

## 4. Plan Drift & Architectural Changes

- **Real, live click-through verification method differs from the original plan's own text.**
  The plan named `npm run tauri dev` or the Claude Browser preview; in practice this session
  navigated the Claude Browser directly at an already-running real `vite` dev server for this exact
  project (found listening on port 1420, left running from an earlier session) rather than starting
  a new one. This confirmed real, live behavior for everything a plain browser tab *can* exercise --
  the Rail's Library entry is really clickable and shows the selected state, `LibraryArea` really
  renders its list view (heading, real "+ New library" input/button) with no React crash, and a
  real, honest error surfaces (rather than a silent blank screen or infinite loading) when the
  underlying `dispatch` call fails. **What this could not verify**: the real daemon round trip
  itself -- a plain browser tab has no `window.__TAURI_INTERNALS__`, so every real `invoke` call
  throws `Cannot read properties of undefined (reading 'transformCallback')`, a genuine, structural
  limitation of this environment (Tauri's own IPC bridge only exists inside a real Tauri webview),
  not a bug in this slice's own code. Confirmed this is the *only* class of error present (via
  `read_console_messages`) -- no other React/render/import error appeared, meaning this slice's own
  new code introduces no new failure mode beyond that pre-existing, expected constraint. A real,
  end-to-end click-through inside the actual native Tauri window (create a library, tag a Part,
  confirm it appears) was **not** performed in this session and is named here honestly as the
  remaining real gap, matching this repo's own established pattern (`CTX-312.3`'s own "no
  accessibility/screen-recording permission... named explicitly, not silently assumed covered").
- **Test-authoring found a real, minor UI-text ambiguity, fixed before it shipped.** The initial
  Part/Footprint detail-view rendering split identifying info across multiple adjacent JSX
  expressions (`{id} {manufacturer && <span>}`), which made `@testing-library`'s own `getByText`
  match ambiguously in a real test run once a symbol's own id happened to share a text prefix with
  a part's id (`ATtiny85` vs. `ATtiny85_sym`). Fixed by joining identifying fields into one real
  string (`[a, b, c].filter(Boolean).join(' · ')`) per item -- simpler render code and an
  unambiguous, single text node per item, not just a test-only workaround.
- No other deviation from the original plan. The library-list-then-detail navigation, the two
  real, separate sections, the `Promise.all`-based per-id detail fetch, and the "Add to library..."
  picker's own real replace-not-append confirm flow all shipped exactly as scoped.
