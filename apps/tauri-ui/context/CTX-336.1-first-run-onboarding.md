# CTX-336.1: Implementation Context: First-Run Onboarding, Requirement Banners & the Launch View

> **Spec Reference:** Links to [SPEC-336](../specs/SPEC-336-first-run-onboarding-and-launch.md)

`SPEC-335` takes over the moment a project is created; this context ends where that one begins.

## 0. What the spec left open, and what the code says about it

`SPEC-336` §2 lists seven open questions. Five are settled here from evidence in the repo; two are
genuinely product calls and are flagged for the maintainer rather than answered quietly.

1.  **"Recommended settings" is already defined in code, not invented here.**
    `llm_providers.py:67` sets `_DEFAULT_PROVIDER = "anthropic"`, `_DEFAULT_MODELS` gives a model
    per provider, and `llm_providers.py:473` binds *both* roles to one provider whenever
    `provider_roles` is unset. Guided setup therefore does not decide anything new: it writes the
    provider the user picked into both roles and takes that provider's default model, which is
    exactly what an unconfigured install already does. **Open for the maintainer:** whether the
    pre-selected provider on the picker stays `anthropic`.

2.  **Onboarding completion is recorded as a flag, not inferred.** Inferring from state re-triggers
    the whole wizard on a transient failure — an expired key, KiCad temporarily unmounted — which
    is the "trapped user" failure this spec exists to avoid, in a slower costume. The flag records
    that the user was *offered* setup, and the banners (not the wizard) carry the current truth
    about what is missing. The two are deliberately different questions.

3.  **A banner collapses; it never dismisses.** `SPEC-336` §3 names dismiss-forever as "the trap in
    a different costume". Collapsed leaves a one-line strip with the action still on it, so the
    route back to guided setup is permanently visible without a persistent full-width block.

4.  **"Finish setting up" lives on the banner and in the rail.** The banner is where a user
    notices the problem; the rail is where they look when they come back later, after the banner is
    collapsed and forgotten. The menu is not a third home — `SPEC-316` owns that surface and
    duplicating an action into it without a reason is how a command surface rots.

5.  **The landing view replaces the main pane, and the rail stays.** The rail is how you open a
    project; hiding it on the launch view would remove the fastest route to the thing the launch
    view exists to offer. This also makes "close project" and "launch with no project" the same
    state, rather than two states that look alike.

6.  **Closing a project persists nothing on the way out.** As of `SPEC-333`'s resolution there is
    no unsaved project state to flush — every edit already writes through. Closing is a view
    change, and saying so is the whole point.

7.  **Open for the maintainer: the docs links.** `SPEC-336` §3 is blunt that "a link that 404s on
    first run is worse than no link", and the only external URL in the app today is
    `GITHUB_REPO_URL` (`core/tauri-rust/src/menu.rs:85`). Four provider key pages are needed. Each
    provider's own documentation URL is real and stable and could be linked directly; a
    Copperplane docs page for each is not, and does not exist. **This context assumes linking to
    each provider's own docs** and leaves a Copperplane docs site to its own spec.

### A blocking finding: the KiCad path picker cannot work today

`SPEC-336` step 5 offers a path picker when a tool is missing "from its default location". For
FreeCAD that plumbing is complete: `config.rs:39` carries `freecadcmd_path_override`, and
`daemon.py:262` passes it into `freecad_bridge.configure`.

**For KiCad it does not exist.** `kicad_cli.configure()` accepts a `path_override` parameter and
`daemon.py:276` calls it with `output_dir=` only. `config.rs` has no `kicad_cli_path_override`
field at all, so there is no value to pass and no way for the UI to set one. The parameter has been
dead since `SPEC-309` — its own docstring notes the module's discovery config "existed since
SPEC-309 but was never actually wired". Phase 1 wires it before any UI is built on top, because
building the picker first would produce a control that appears to work and silently does nothing.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1, before a line was written: the spec describes a control that cannot exist yet.**
    §2's "offer a path picker" is complete for FreeCAD and impossible for KiCad —
    `kicad_cli.configure`'s `path_override` has never been passed a value and `config.rs` has no
    field for one. Found by reading the wiring rather than the function signature, which looks
    finished. Phase 1 now precedes every UI phase for this reason: a picker built on the missing
    wire would look like it worked.

*   **Deviation 2: a saved tool path only took effect at the next restart, so Phase 2's promise
    was undeliverable as written.** Phase 2 says a banner clears once the user fixes the tool.
    But `_apply_env_config` reads its env var once at spawn, and `lib/settings.ts`'s own docstring
    states the consequence plainly: socket-path and `freecadcmd`-path fields "only take effect on
    the next daemon restart ... callers must surface that distinction, not imply a live update that
    doesn't happen." Honest, and fatal for a first-run picker: the user points the app at their
    KiCad and keeps looking at the same "KiCad not found" banner.

    So `daemon.configure` now accepts `kicad_cli_path_override` and `freecadcmd_path_override` and
    applies them to the live modules. FreeCAD is included because SPEC-336 step 5 covers both tools
    and a picker that works live for one and needs a restart for the other is worse than either
    behaviour applied consistently.

*   **Deviation 3: `None` could not express "remove this override".** Every existing field on
    `daemon.configure` uses `None` for "leave unchanged", which a picker needs too — Rust's
    spawn-time call and every secrets-only save from Settings pass no path at all and must not wipe
    one. That leaves nothing to mean "clear it", and a picker the user can only ever add to is a
    trap of its own kind. The empty string is that signal, documented on the route and covered by
    TEST-014.

*   **Deviation 4: `configure()` replaces both module globals on every call.** Passing only a path
    would have silently dropped the Rust-computed `output_dir` that SPEC-311's `.glb` export writes
    into — a change with no visible symptom until an export lands in the wrong place. Both calls now
    thread the existing `_output_dir_override` back through. TEST-015 exists because I nearly
    shipped this.

*   **Deviation 5: guided setup would have reported success and changed nothing.**
    `setLlmProviderAndModel` writes the legacy `llm_provider`/`llm_model` pair, and
    `llm_providers.py`'s `_migrate_provider_roles` consults those *only when `provider_roles` is
    unset* — an existing map wins and the legacy field is ignored. So on a fresh install the legacy
    write happens to work, and after any Settings save that persisted `provider_roles` it silently
    would not: the key would be saved, the wizard would advance, and a different provider would
    keep answering. Guided setup now binds both roles explicitly (`bindBothRolesTo`), which is also
    exactly what an unconfigured install resolves to — making the existing default explicit rather
    than inventing a policy.

*   **Deviation 6: two effects raced to decide the first screen.** The project-list effect and the
    onboarding effect both set the initial view when it was still `null`, so on a genuine first run
    the welcome screen appeared or did not depending on which of `list_projects` and `get_config`
    resolved first — a coin flip decided by disk timing. Caught by a test that expected the welcome
    screen and got the landing view. The project effect now sets no view at all; the onboarding
    effect is the single decider, and it decides *before* probing capabilities so a slow probe
    cannot delay the first screen.

*   **Deviation 7: the launch-view change broke 46 existing App tests, all correctly.** Every one
    had relied on the auto-open to find itself inside a project. Rather than restore the behaviour
    the spec exists to remove, they now open a project the way a person does — a `renderAppOpen`
    helper that clicks the project in the rail, and is a no-op when a test deliberately has none.
    Two more asserted the old empty-state sentence and now assert the landing view's own action.
    Worth stating plainly: a behaviour change that touches 46 tests is not evidence the change is
    wrong; it is evidence the old behaviour was load-bearing in the tests, which is exactly what
    made it worth removing.

*   **Deviation 8: `onboarding_completed` is a UI flag living in the daemon's config struct.**
    `config.json` is `DaemonConfig`, which is also serialized into the daemon's environment — so
    the daemon now receives a field it has no use for and ignores. The alternative was a second
    store for one boolean. Recorded because it is a small, deliberate untidiness rather than an
    oversight: the field is documented on the struct as UI-only.

*   **Deviation 9: the first click-through found an invisible button, exactly as predicted.**
    `Guide me through it` rendered black-on-black in light mode and white-on-white in dark. The
    cause: I wrote `text-on-accent`, which is not a token — the theme defines `--color-accent-fg`,
    and every other primary button in the app already uses `text-accent-fg`. Tailwind emits nothing
    for an unknown utility and reports no error, `tsc` cannot see inside a `className` string, and
    a passing test never looks at a colour. **Nothing in 728 tests could have caught it**, and the
    same invented token was in all three new components.

    Two guards now exist in `apps/tauri-ui/tests/themeTokens.test.ts`: every colour class in every
    component must name a token `index.css` defines, and any `bg-accent` button must state
    `text-accent-fg`. Both were confirmed to *fail* on the real bug before being kept — a check
    that cannot fail is not evidence, and this repo has paid for that lesson once already
    (`CTX-407.3` Deviation 2).

*   **Prediction, checked: right, and on the very first screen.** Phase 1 predicted Phase 5 would
    find a defect the earlier phases' tests missed. It did — Deviation 9, found within seconds of
    the maintainer opening the built app, on the first button of the first screen. The prediction
    also guessed *where*: "a real key or a real native file dialog behaving differently from its
    mock." That part was wrong. The defect was in something no test in this repo can see at all,
    which is a worse category than a mock disagreeing with reality: a mock can at least be made
    more honest. Two further defects of the same family (Deviations 5 and 6) turned up inside
    Phases 2-4 without needing the built app.

*   **Prediction, recorded now to be checked later:** I expect Phase 5 — actually running first-run
    in the built app with an empty config — to find at least one defect that all of Phases 1-4's
    tests missed, because that is what happened in `CTX-335.1` (three defects under 645 passing
    tests, including a mislabelled button a test clicked and passed on) and in `CTX-334.1` (a stale
    frozen binary and a truncated description). If Phase 5 finds nothing, that is worth recording
    as the first time.

## 7. Phase 5: The Click-Through, And How To Get A Real First Run

Everything below needs a person. It is written out because "verify as the user" is a repo norm with
a specific meaning: *"only satisfied by a human actually using the surface the way a user would,
with the outcome recorded."*

**Getting back to a genuine first-run state.** The welcome screen appears only when
`onboarding_completed` is not `true` in `config.json`, which on this machine is
`~/Library/Application Support/com.gittielabs.hardware-agent-studio/config.json`. Remove that one key —
or the file, if there is nothing in it worth keeping — and the next launch is a first run. Note that
removing the whole file also clears any configured tool paths and provider records, which is closer
to a real first run and may be what you want.

**Launch the build that was just made**, not whatever Spotlight finds:
`core/tauri-rust/target/release/bundle/macos/Copperplane.app`. A released build in `/Applications`
shares the same bundle identifier, so opening from the Dock or Spotlight can silently launch the
old one — which has none of this in it, and would make the whole check meaningless.

**What to check, in order:**

0.  ~~The primary button is readable.~~ **Checked 2026-09-03, and it was not** — see Deviation 9.
    Fixed, guarded by `themeTokens.test.ts`, and worth re-checking in both light and dark.
1.  The welcome screen appears, with Managed visibly present, disabled, and saying why.
2.  *Guide me through it* → Anthropic pre-selected. **Where do I get a key?** opens
    `console.anthropic.com` in the real browser, not an app window.
3.  Paste a real key → it saves, and the step advances. Then check Settings agrees about which
    provider is bound: this is Deviation 5's failure mode, and it is invisible from inside the
    wizard.
4.  On the tool step, both tools should read *found* with the real path underneath. To exercise the
    picker, quit, point `kicad_cli_path_override` at something that does not exist, relaunch: the
    banner should blame the configured path rather than saying KiCad is missing, and
    **I have it — point to it** should fix it with no restart.
5.  *Continue anyway* with something still missing → the app opens, with the banner naming it.
6.  Collapse the banner. The strip must keep **Finish setting up**. There should be no way to make
    it disappear while the problem remains.
7.  Launch with projects present → the landing view, *not* a project. **Close project** from inside
    one returns there.

**What I expect to be wrong**, recorded before anyone looks, since Phase 1 predicted a defect here:
the most likely place is step 3 or 4 — a real key or a real native file dialog behaving differently
from its mock. The mocks in `GuidedSetup.test.tsx` are mine, and a mock agreeing with the code I
wrote alongside it proves less than any of the numbers above suggest.
