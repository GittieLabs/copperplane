# CTX-336.1: Implementation Context: First-Run Onboarding, Requirement Banners & the Launch View

> **Spec Reference:** Links to [SPEC-336](../specs/SPEC-336-first-run-onboarding-and-launch.md)

`SPEC-335` takes over the moment a project is created; this context ends where that one begins.

## 0. What the spec left open, and what the code says about it

`SPEC-336` §2 lists seven open questions. Five are settled here from evidence in the repo; two are
genuinely product calls and are flagged for the maintainer rather than answered quietly.

1.  **"Recommended settings" is already defined in code, not invented here.**
    `llm_providers.py:67` sets `_DEFAULT_PROVIDER = "anthropic"`, `_DEFAULT_MODELS` gives a model
    per provider, and `llm_providers.py:473` binds *both* roles to one provider whenever
    `provider_roles` is unset. Guided setup therefore does not decide anything new: it writes the
    provider the user picked into both roles and takes that provider's default model, which is
    exactly what an unconfigured install already does. **Open for the maintainer:** whether the
    pre-selected provider on the picker stays `anthropic`.

2.  **Onboarding completion is recorded as a flag, not inferred.** Inferring from state re-triggers
    the whole wizard on a transient failure — an expired key, KiCad temporarily unmounted — which
    is the "trapped user" failure this spec exists to avoid, in a slower costume. The flag records
    that the user was *offered* setup, and the banners (not the wizard) carry the current truth
    about what is missing. The two are deliberately different questions.

3.  **A banner collapses; it never dismisses.** `SPEC-336` §3 names dismiss-forever as "the trap in
    a different costume". Collapsed leaves a one-line strip with the action still on it, so the
    route back to guided setup is permanently visible without a persistent full-width block.

4.  **"Finish setting up" lives on the banner and in the rail.** The banner is where a user
    notices the problem; the rail is where they look when they come back later, after the banner is
    collapsed and forgotten. The menu is not a third home — `SPEC-316` owns that surface and
    duplicating an action into it without a reason is how a command surface rots.

5.  **The landing view replaces the main pane, and the rail stays.** The rail is how you open a
    project; hiding it on the launch view would remove the fastest route to the thing the launch
    view exists to offer. This also makes "close project" and "launch with no project" the same
    state, rather than two states that look alike.

6.  **Closing a project persists nothing on the way out.** As of `SPEC-333`'s resolution there is
    no unsaved project state to flush — every edit already writes through. Closing is a view
    change, and saying so is the whole point.

7.  **Open for the maintainer: the docs links.** `SPEC-336` §3 is blunt that "a link that 404s on
    first run is worse than no link", and the only external URL in the app today is
    `GITHUB_REPO_URL` (`core/tauri-rust/src/menu.rs:85`). Four provider key pages are needed. Each
    provider's own documentation URL is real and stable and could be linked directly; a
    Copperplane docs page for each is not, and does not exist. **This context assumes linking to
    each provider's own docs** and leaves a Copperplane docs site to its own spec.

### A blocking finding: the KiCad path picker cannot work today

`SPEC-336` step 5 offers a path picker when a tool is missing "from its default location". For
FreeCAD that plumbing is complete: `config.rs:39` carries `freecadcmd_path_override`, and
`daemon.py:262` passes it into `freecad_bridge.configure`.

**For KiCad it does not exist.** `kicad_cli.configure()` accepts a `path_override` parameter and
`daemon.py:276` calls it with `output_dir=` only. `config.rs` has no `kicad_cli_path_override`
field at all, so there is no value to pass and no way for the UI to set one. The parameter has been
dead since `SPEC-309` — its own docstring notes the module's discovery config "existed since
SPEC-309 but was never actually wired". Phase 1 wires it before any UI is built on top, because
building the picker first would produce a control that appears to work and silently does nothing.

## 1. Feature Definition & Execution Plan

### Phase 1: Make a tool path settable (Rust + daemon)
*   [ ] Add `kicad_cli_path_override` to `core/tauri-rust/src/config.rs`, alongside the FreeCAD one.
*   [ ] Pass it through `daemon.py`'s `_apply_env_config` into `kicad_cli.configure(path_override=)`.
*   [ ] Report the resolved path and its source in `_detect_capabilities`, so the UI can say *which*
        binary it found rather than only that it found one.
*   [ ] Verify against the frozen sidecar, not the source module.

### Phase 2: Requirement banners
*   [ ] `RequirementsBanner` — names what is missing, what it stops working, and the way to fix it.
        Specific per tool: "KiCad not found, so board checks and the enclosure cannot run."
*   [ ] Collapses to a one-line strip that keeps its action; never dismisses.
*   [ ] Driven by `daemon.get_capabilities`, re-checked on demand, so fixing the problem clears the
        banner without a restart.

### Phase 3: The launch view
*   [ ] `NoProjectLanding` — what the app is, links to the repo, create-or-open actions.
*   [ ] Stop opening `names[0]` on launch (`App.tsx:144`), which today opens the alphabetically
        first project.
*   [ ] A close-project action returning to the landing view.

### Phase 4: Welcome and guided setup
*   [ ] `Welcome` — logo, the two paths, Managed visibly present and disabled with a reason.
*   [ ] `GuidedSetup` — provider choice, key entry with a link to that provider's own docs, then
        the KiCad and FreeCAD check with a path picker where a tool is missing.
*   [ ] Every step skippable, in and out, at any point. The manual path never gated anyone and this
        one must not either.
*   [ ] Record completion as a flag; the banners carry current truth.

### Phase 5: Verify as the user
*   [ ] Drive the whole first-run path in the built Tauri window with a real, empty config — not
        only in jsdom. `SPEC-302` shipped with every capability test green and nobody having tried
        the surface; onboarding is the worst possible place to repeat that.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1, before a line was written: the spec describes a control that cannot exist yet.**
    §2's "offer a path picker" is complete for FreeCAD and impossible for KiCad —
    `kicad_cli.configure`'s `path_override` has never been passed a value and `config.rs` has no
    field for one. Found by reading the wiring rather than the function signature, which looks
    finished. Phase 1 now precedes every UI phase for this reason: a picker built on the missing
    wire would look like it worked.

*   **Prediction, recorded now to be checked later:** I expect Phase 5 — actually running first-run
    in the built app with an empty config — to find at least one defect that all of Phases 1-4's
    tests missed, because that is what happened in `CTX-335.1` (three defects under 645 passing
    tests, including a mislabelled button a test clicked and passed on) and in `CTX-334.1` (a stale
    frozen binary and a truncated description). If Phase 5 finds nothing, that is worth recording
    as the first time.

## 5. Open For The Maintainer

Two calls that change what gets built, neither of them blocking Phase 1:

1.  **Which provider is pre-selected** on the guided picker. The code's answer today is
    `anthropic` (`llm_providers.py:67`), and guided setup will inherit that unless told otherwise.
2.  **Where the "how do I get a key" links point.** This context assumes each provider's own
    documentation. The alternative is a Copperplane docs site, which does not exist and would need
    its own spec — and `SPEC-336` §3 is explicit that a link that 404s on first run is worse than
    no link at all.
