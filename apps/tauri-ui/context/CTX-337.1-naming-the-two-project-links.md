# CTX-337.1: Implementation Context: Naming the Two Project Links

> **Spec Reference:** Links to [SPEC-337](../specs/SPEC-337-naming-the-two-project-links.md)

Settled with the maintainer before any code: the names are **KiCad project** (which is *linked*)
and **project folder** (which is *set*), and a folder containing a `.kicad_pro` **offers** it in
one click rather than linking it automatically.

## 1. Feature Definition & Execution Plan

### Phase 1: One word per concept
*   [x] The folder action never says "linked": `Linked to <path>` became
        `Project folder set to <path>`, and `handleLinkDirectory` became `handleSetProjectFolder`.
*   [x] The header states both links on their own lines — the folder was previously invisible
        unless you noticed a **Copy project path** button, so "is it set?" had no answer on screen.
*   [x] Buttons named for what they change: **Set folder…** / **Change folder…** /
        **Copy folder path**, beside the existing **Link** / **Change** for the KiCad project.
*   [x] The banner says which link it means, and that the other one is not a substitute.
*   [x] The wizard's bare `Linked: <path>` became `KiCad project linked: <path>` — a user's first
        encounter with either concept.

### Phase 2: Offer what the folder contains
*   [x] `kicad.find_projects_in_directory` — every `.kicad_pro` directly inside a folder.
        Not recursive: one two directories down is not "the KiCad project in this folder", and
        walking an arbitrary tree turns a folder pick into an unbounded scan.
*   [x] Setting a folder with no KiCad project linked offers what it found, with **Not now**.
*   [x] Nothing is linked without a click.
*   [x] A failed scan does not turn a successful folder set into a visible error.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the new folder line collided with an older, still-correct decision.** Adding
    `Project folder: <path>` broke a test named *"does not print the project folder path at all"* —
    which encodes the maintainer's own instruction from an earlier session: *"we should change this
    to not show the path of the project and use a copy project path button."* Still right, and the
    fix was not to update the test: the folder line now shows the folder's **name**, the way the
    `.kicad_pro` line beside it already showed a filename, with the full path in the tooltip and on
    the copy button. A test that looks like an obstacle is sometimes carrying a decision.

*   **Deviation 2: renaming copy broke seven tests, and one of them was not about copy.** Six were
    straightforward string updates. The seventh was Deviation 1. Worth separating deliberately: on
    a copy change, "the tests are just asserting the old strings" is the assumption that hides the
    one that is not.

*   **Deviation 3: `vi.mock('./lib/kicadProject')` silently removed the module's other exports.**
    Mocking one new function replaced the whole module, so every panel importing
    `listSchematicComponents`, `componentEnvelopes` and the rest got `undefined` — surfacing as
    seven unrelated failures in areas nothing had touched. Fixed with `importActual` and a spread.
    Recorded because the symptom pointed nowhere near the cause.

*   **Deviation 4: I ran the test suite and the sidecar freeze concurrently and briefly believed
    the app was broken.** 99 errors and 23 failures, including whole modules failing to import.
    PyInstaller churns the same tree the tests import from. Re-running alone: 1037 tests, three
    live-API flakes. **This is the second time this session** — the same mistake, the same
    momentary wrong conclusion. The rule earned: never run the suite and a freeze at once.

*   **Deviation 5 (a good outcome, recorded so it is not lost): the Google path is now positively
    tested.** `CTX-204.2` recorded "Google, OpenAI and Perplexity were not re-tested after the
    rename" as an open risk. `test_002_real_google_chat` failed in the concurrent run, passed alone
    against the live API, so Google chat still works after the rename. That covers plain chat, not
    tool-using chat on Google — the narrower gap remains, and remains recorded.
