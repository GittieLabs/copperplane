# CTX-205.8: Guidance Synthesis UI

> **Spec Reference:** Links to [SPEC-205](../../../services/python-daemon/specs/SPEC-205-datasheet-design-guidance.md)

## 1. Feature Definition & Execution Plan

The frontend half of `CTX-205.7`'s real backend work: renders SPEC-205 §2.1.1's plain-language
`category_summaries` on Part Detail's Design Requirements panel, per §5's amended real interaction
design -- **the summary leads, the underlying cited items sit collapsed below it, available on
demand as proof, not as the first thing the reader has to parse.** This is the piece that actually
lets the user see the real product decision made in `CTX-205.7`, not just read about it -- "we can
decide based on what we're able to show" was the explicit real instruction this session's work is
answering.

**Real, deliberate implementation choice**: collapse/expand uses a native HTML `<details>`/
`<summary>` element, not new React state. No new `useState`, no new event handler for toggling --
the browser's own native disclosure widget does the job SPEC-205 §5 actually asks for (collapsed by
default, expandable on demand), and it is real, working keyboard/accessibility behavior for free
that a hand-rolled toggle would have had to reimplement. `open={!summary}` is the one real piece of
logic: a category with a real summary starts collapsed (the summary is the primary read); a category
with items but no summary yet (a record generated before `CTX-205.7` shipped, or the rare case
where synthesis genuinely produced nothing for a non-empty category) falls back to the exact
pre-`CTX-205.7` behavior -- citations shown open, since there is nothing else to lead with.

**A category with zero items is unaffected** -- still the existing "No guidance found for this
category." empty state (SPEC-205 §5's own first-class empty state), never reached for a summary at
all, since a category with no items structurally cannot have one (`CTX-205.7`'s own real backend
contract).

### Phase 1: types
*   [x] `lib/partDetail.ts`: `DesignGuidance.category_summaries: Record<string, string | null>`.

### Phase 2: rendering
*   [x] `components/PartDetail.tsx`: each category's real summary (when present) renders above a
    `<details>` wrapping its citation list; `open={!summary}` gives the correct default per
    category, with no new component state.

### Phase 3: tests
*   [x] `lib/partDetail.test.ts`: `generateDesignGuidance`'s existing test fixture carries the new
    field.
*   [x] `components/PartDetail.test.tsx`: a real summary renders as the primary text with its
    citations collapsed by default; clicking the citations toggle reveals the underlying cited
    items; a category with no summary yet falls back to citations open by default (the existing
    `DESIGN_GUIDANCE` fixture and its own pre-existing tests, unchanged in behavior, now exercise
    this fallback path explicitly rather than being the only real path tested).

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

None from `CTX-205.7`'s own already-amended `SPEC-205` -- this context implements exactly what
§5's real, amended text already specifies (summary leads, citations collapsed below as proof). The
real open question is not architectural but experiential: whether this alone resolves the
audience-fit problem the user raised, or whether the category taxonomy itself (Power/Decoupling/
Reset/Clock/Layout) also needs to become task-oriented -- left for direct user feedback once this
ships and is actually used, not decided here.
