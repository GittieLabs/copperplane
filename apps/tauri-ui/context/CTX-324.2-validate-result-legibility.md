# CTX-324.2: Validate Result Legibility

> **Spec Reference:** Links to [SPEC-324](../specs/SPEC-324-model-identity-verification.md)

`CTX-324.1` shipped the Validate button with a deliberate, correct decision: report the daemon's
reason **verbatim** rather than reduce it to a tick or a cross. It then rendered every possible
outcome in the same `text-fg-muted` as the hint line directly beneath it. A pass, an unlisted model
id, a hard `Method not found`, and the in-flight `checking...` were all visually identical, and all
identical to help text.

Found on the first real click-through of this dialog, by the maintainer:

> "i get a method error that blends in for the validation failure"

This is the same shape as `SPEC-322` §1 and `SPEC-302` before it -- mechanically correct, every
test green, and still the wrong thing in front of a person. `CTX-324.1`'s own Testing Matrix has a
row for *"Validate runs only on click and reports the daemon's reason verbatim"* which passed, and
passes still. Nothing asserted the reason was **distinguishable**.

## 1. Feature Definition & Execution Plan

### Phase 1: Carry the outcome with the text

*   [x] `modelCheck` becomes `{ ok: boolean | null; text: string }` per role rather than a bare
    string. `ok: null` is the in-flight state, so `checking...` stays muted rather than being
    coloured as either result.
*   [x] `validate_model` already returns `{valid, reason}` and `CTX-324.1` discarded `valid` at the
    call site. It is now kept. No daemon change, no route change, no schema change.

### Phase 2: Style by outcome, using the convention already in the repo

*   [x] A pass is `text-success`, a failure is `text-danger`. Both tokens are defined for light and
    dark in `src/index.css`, and both are already the convention in `App.tsx`, `LibraryArea.tsx`
    and `Settings.tsx`. This file itself already uses `text-warning` twice for the preset and
    perplexity notices -- the validate result was the one place that signalled nothing.
*   [x] A **thrown** error is styled as a failure rather than left neutral. It means the check
    could not run at all -- an unreachable daemon, or a route this build does not have -- which is
    never a passing model. That is precisely the case that shipped looking like a hint.
*   [x] The reason string is untouched. This is a styling fix, not a copy change, so `CTX-324.1`'s
    verbatim-reason test still asserts exactly what it did before.

### Not in this context

*   **The roles-and-kind pair on each provider row** reads as two adjacent bare words with no
    label or separator -- `not in use  anthropic`, `reasoning + fast  google`. Two different facts
    rendered as one run, in a screen whose whole purpose is legibility. Real, seen in the same
    click-through, and `SPEC-322`'s to own rather than `SPEC-324`'s.
*   **Filtering or search over long model lists**, still `SPEC-324` §3 and still deferred.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the visible bug was not the real one, and fixing only it would have hidden the
    real one.**
    *   *Reasoning:* The reported symptom was a `Method not found` error that blended into the hint
        text. Colouring it red makes the report accurate and the screen better. It would also have
        made a genuinely broken build *look* correctly broken, while leaving the actual cause in
        place -- the bundled sidecar was frozen four days before `llm.validate_model` existed, so
        the route was absent from the running daemon. That is `CTX-407.3`.
    *   *Impact:* two independent fixes from one piece of feedback. Worth recording because the
        styling fix is the one that was asked for, and on its own it would have made the deeper
        failure quieter rather than louder -- an error that looks like a proper error invites less
        investigation than one that looks wrong.

*   **Deviation 2: `CTX-324.1`'s Testing Matrix was not wrong, and did not catch this.**
    *   *Reasoning:* TEST-010 asserts the reason is reported verbatim, and it passed throughout.
        Verbatim was never the property in question; distinguishable was, and nothing named it.
    *   *Impact:* the three tests added here assert on rendered class rather than on text, because
        the text was already correct. A test that asserts what a user can *read* does not
        necessarily assert what a user can *see*.
