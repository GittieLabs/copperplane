# CTX-308.2: Implementation Context: Footprint Search UI

> **Spec Reference:** Links to [SPEC-308](../specs/SPEC-308-footprints-schematic-advisor.md)

**Why this comes before `CTX-308.2`'s originally-discussed successor (resolving KiCad's built-in
library set):** `CTX-308.1` shipped a real, working `kicad.search_footprints` route, but nothing in
`apps/tauri-ui` calls it -- a capability with no consumer isn't a finished feature, the same gap
`CTX-108.4` closed for `SPEC-204`'s confirmation gate. Building more backend search coverage before
anything can use the search that already exists would repeat that mistake. Resolving `Table`-type
`fp-lib-table` entries becomes the *next* `CTX-308.x` after this one, renumbered from the earlier
placeholder mention.

**Where this lives, decided by reading the real current app, not invented:** `PartDetail.tsx`
(rendered inside the Components area, after `ComponentDiscovery`'s "Save to Library" step) already
has a `SavedPart` type with a real `footprint_id: string | null` field (`SPEC-307`/`CTX-307.1`) --
but the component currently discards the `part` half of `saveConfirmedPart`'s response entirely,
tracking only `savedSymbol`. This is exactly the real product-stage `SPEC-308` §5 already names:
"After a Part exists... but before it's usable on a real board." No new area tab or route into the
app shell is needed -- this is the natural next step already wired into an existing, real flow.

## 1. Feature Definition & Execution Plan

### Phase 1: `lib/footprints.ts` -- a real client for the new route ✅
*   [x] `searchFootprints(query: string): Promise<FootprintCandidate[]>` -- wraps
    `dispatch('kicad.search_footprints', {query})`, **not** `submitJob` -- `CTX-308.1`'s own route
    is deliberately synchronous (local filesystem I/O, not `ASYNC_ROUTES`), and using `submitJob`
    here would throw (`"did not return a job_id"`).
*   [x] `attachFootprintToPart(part: SavedPart, library: string, footprintName: string):
    Promise<SavedPart>`: builds a real footprint_id using KiCad's own `library:name` reference
    convention, persists it via the already-existing `library.save_footprint` route, then re-saves
    the part via the already-existing `library.save_part` route with `footprint_id` set -- no new
    backend route needed for linking.
*   [x] **Real finding, caught before it became a bug: `library.save_part` re-validates
    `Part.provenance` on every save, and `SavedPart`'s own TS interface never declared that field.**
    Verified directly against a real, running daemon (a real `save_confirmed_part` → `save_part`
    round trip, storage configured against a real temp directory) before writing any React code:
    `library_store.save_part` returns `{**part, "schema_version": 1}` -- the real object the
    frontend already receives from `saveConfirmedPart` genuinely contains `provenance`, it was just
    never typed. Re-saving with only `{...part, footprint_id}` works correctly *because* the real
    runtime object already carries `provenance` through the spread -- TypeScript's structural typing
    doesn't strip untyped-but-present fields. Fixed by declaring `provenance: Record<string,
    unknown>` on `SavedPart` (honest typing, not a new requirement), rather than either inventing a
    new backend route or (worse) reconstructing a fake provenance object client-side.

### Phase 2: wire it into `PartDetail.tsx` ✅
*   [x] Track the `part` half of `saveConfirmedPart`'s response (previously discarded) as real
    `savedPart` state.
*   [x] Once `savedPart` exists and has no `footprint_id` yet, a real "Find Footprint" section
    appears -- search input + button + candidate list, matching `ComponentDiscovery.tsx`'s own
    established shape (the same search/select interaction this app already uses for parts, reused
    for footprints rather than inventing a new pattern).
*   [x] Selecting a candidate calls `attachFootprintToPart`, updates `savedPart`, and the section
    switches to showing the real linked footprint (`library:name`) instead of the search form.
*   [x] A real, honest empty state when `kicad.search_footprints` returns zero results -- distinct
    from an error, since "no match in your configured libraries" is an expected, not exceptional,
    outcome given `CTX-308.1`'s own real scope limit (only direct `fp-lib-table` entries).

### Phase 3: fill in `SPEC-308` §5 for real, tests, verification ✅
*   [x] `SPEC-308` §5's "What the user sees and does" bullet, previously "not yet decided," now
    describes exactly what this context shipped.
*   [x] `PartDetail.test.tsx` extended with 4 new tests (mocked `searchFootprints`/
    `attachFootprintToPart`): the section only appears once a part is saved and has no footprint
    yet; a real search round-trip renders candidates; selecting one calls `attachFootprintToPart`
    and shows the linked result; zero results renders the honest empty state, not an error. All 9
    tests in the file pass (5 pre-existing unchanged, 4 new).
*   [x] `tsc -b`, `oxlint` (only the two pre-existing, unrelated `EnclosureViewer.tsx` warnings),
    full `vitest run` -- 110/110, `vite build` -- clean.
*   [x] **Not verified this session**: live human click-through in the real native window (no
    accessibility permission -- see `native-window-verification-gap`).

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Deviation 1: `SavedPart` needed a real, previously-undeclared `provenance` field before
    `attachFootprintToPart` could work at all -- caught by real verification against a live daemon
    before writing any React code, not discovered mid-implementation.** See Phase 1 above for the
    full account. The original plan assumed a simple spread-and-resave would work without checking
    whether `library.save_part`'s own schema validation had any requirement beyond `part_id`; it
    does (`Part.provenance`, enforced on every save per `PRODUCT-PLAN.md` §2.2's provenance model).
    Verified the real returned object already carries it at runtime before concluding a TS-only fix
    (declaring the field) was sufficient, rather than assuming and finding out via a failing test.
