# CTX-325.1: Project Resolution & Schematic Component Read

> **Spec Reference:** Links to [SPEC-325](../specs/SPEC-325-kicad-project-integration.md)

The daemon half of `SPEC-325`. A `.kicad_pro` in, every component in the schematic out, **with
KiCad closed**. The UI half is `CTX-325.2`.

## 1. Feature Definition & Execution Plan

### Phase 1: Resolve a project to the files it owns

*   [x] `kicad_project.resolve_project(pro_path)` — reads the project JSON, resolves the schematic
    and PCB by KiCad's own naming convention (the same one
    `kicad_bridge.list_project_schematics` already relies on).
*   [x] A project with no board yet reports `pcb_path: None` rather than refusing to load. A
    schematic-only project is ordinary, and saying "no PCB" is more useful than failing.
*   [x] `sheet_count` from the project's own `sheets` list, **reported rather than acted on** — see
    §3, the multi-sheet question is unverified. `None` when the key is absent, because "the file
    did not say" and "this project has no sheets" are different claims.

### Phase 2: Read the components from the file

*   [x] `kicad_cli.export_schematic_bom` runs `kicad-cli sch export bom` on a **closed**
    `.kicad_sch`.
*   [x] Ungrouped into one entry per reference designator. `kicad-cli` emits a *BOM's* shape —
    identical parts collapsed onto one row with a comma-separated `Refs` field — which is not a
    component list.
*   [x] An unrecognised column set **raises**. Returning `[]` would read to a user as "your
    schematic has no components": a silent wrong answer, and `SPEC-325` §3's named risk.

### Phase 3: Answer the model question honestly

*   [x] `kicad_bridge.resolve_footprint_model(footprint_id)` resolves through `fp_lib_table` and
    reuses `_resolve_3d_model_path`, which already returns `None` for a dangling reference.
*   [x] **The check is the file, not the footprint's `(model ...)` line.** That line is a claim:
    KiCad's `Battery` library ships 53 footprints against 29 STEP models with no `.wrl` fallbacks,
    so trusting it would be wrong 25 times out of 53.
*   [x] Never raises for an unresolvable footprint — a library this install lacks is a state the
    user needs told about, not an error that blanks a whole table.

### Phase 4: Two routes, with the right sync/async split

*   [x] `kicad.resolve_project` — **sync**. One small JSON read and two stats; making it async
    would cost a job round trip for nothing.
*   [x] `kicad.list_schematic_components` — **`ASYNC_ROUTES`-registered**. `kicad-cli` is a real
    subprocess, `SPEC-107` §3 requires slow calls out of the request path, and `CTX-107.2` records
    what happened when a `freecadcmd` call was added to the capability probe.
*   [x] Footprint resolution is best-effort per component, so one bad footprint cannot cost the
    table.
*   [x] Reports `read_at`, so a caller can say what it read and when rather than implying live sync
    with an editor holding unsaved changes.

### Not in this context

*   **All UI.** The Schematic tab, project-file picker, and the component table are `CTX-325.2`.
    Nothing here is visible to a user yet.
*   **Netlist / connectivity.** `kicad-cli sch export netlist` was verified to work and returns
    real nets down to `pinfunction`, but nothing consumes it yet. `SPEC-327` is where that pays off.
*   **Matching against the app's own library** (`SPEC-325` §2.5). Needs the table first.

Full daemon suite: 882 tests. Three errors are **live-KiCad IPC tests** failing with *"KiCad is busy
and cannot respond to API requests right now"* — confirmed environmental by stashing this context's
changes and reproducing them unchanged.

**Verified against the real thing.** The maintainer's own `Hello_World_Blinky` project, KiCad
closed: 10 components read, and `BT1` correctly flagged as having **no 3D model** — its footprint
references `Battery_Panasonic_CR2032-HFN_Horizontal.step`, which does not exist on disk. That is
the exact gap that prompted `SPEC-325`, now visible instead of silent.

**Not verified, and it matters.** No multi-sheet project exists on this machine — every candidate
turned out to be a single root sheet duplicated across directories. So whether
`kicad-cli sch export bom` walks a hierarchy from the root sheet is **still unverified**, exactly as
`SPEC-325` §3 warned. `sheet_count` is reported so a caller can be suspicious; it is not a fix.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — the existing code already documented the problem this fixes.**
    *   `kicad_bridge.list_project_schematics`'s own docstring records, from live verification, that
        `get_open_documents(DOCTYPE_SCHEMATIC)` *"raises the same `no handler available` ApiError
        unconditionally"* — KiCad's IPC server has never implemented schematic listing. It works
        around this by deriving the schematic from whichever **board** is open.
    *   *Impact:* the workaround was correct given IPC, and unnecessary given `kicad-cli`. This
        context does not remove it — `SPEC-325` §2.2 keeps the IPC path at its current scope — but
        the file-based route should become the default the UI reaches for.

*   **Deviation 2 — the multi-sheet risk could not be retired, and reporting replaced verifying.**
    *   `SPEC-325` §3 named hierarchical schematics as unverified. Two local projects appeared to
        have two sheets each; both turned out to be the same root sheet duplicated across
        directories, with no `Sheetfile` reference anywhere on this machine.
    *   *Impact:* rather than assume, `resolve_project` reports `sheet_count` and
        `export_schematic_bom` returns whatever the root sheet yields. A caller can tell that a
        project has more than one sheet and treat the list with suspicion. **This is a mitigation,
        not a resolution**, and `CTX-325.2` must not present a multi-sheet project's table as
        complete until someone tests one.

*   **Deviation 3 — `import fp_lib_table` moved into `kicad_bridge`'s module scope.**
    *   `resolve_footprint_model` needs library resolution, and `fp_lib_table` already does it well
        (156 libraries parsed on this machine, correctly locating `Battery.pretty`).
    *   *Impact:* `kicad_bridge` now imports a sibling module at import time. That module has no
        heavy dependencies and `daemon.py`'s own per-module `try/except` guard still isolates a
        failure, so a broken `fp_lib_table` degrades `kicad_bridge` rather than the daemon —
        matching `SPEC-107` §2's existing pattern rather than inventing one.
