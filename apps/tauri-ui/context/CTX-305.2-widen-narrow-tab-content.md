# CTX-305.2: Implementation Context: Widen the Narrow max-w-md Tab Content Column

> **Spec Reference:** Links to [SPEC-305](../specs/SPEC-305-app-shell-navigation.md)

Real, user-reported bug, found by a live click-through of `CTX-313.1`'s own Overview dashboard: on
a wide window, the app's real content -- every tab except Enclosure -- renders inside a fixed
`max-w-md` (28rem/448px) column flush against the sidebar, leaving most of the window's own width
as unused black space. The user's own words: "the content width is fixed. The screen real estate
is wasted but not expanding horizontally," confirmed as systemic with a direct follow-up: "this
occurs on every tab." Not new -- `EnclosurePanel.tsx`'s own comment already named this exact gap
when it widened itself to `max-w-6xl` for `SPEC-311`: "every other tab keeps its existing
`max-w-md` column unchanged; a repo-wide shell/layout redesign is a deliberate, separate
follow-up." This context is that follow-up, scoped narrowly to the real complaint (width), not a
full shell redesign.

## 1. Feature Definition & Execution Plan

### Phase 1: Widen every remaining max-w-md content column to max-w-4xl
*   [x] `App.tsx`: the shared project header (Linked/Save Project row), the area tab bar, the
    `loadError`/`projectActionError`/`projectActionMessage` banners, and `Overview`'s own outer
    wrapper -- six spots total, all previously `max-w-md`.
*   [x] `BoardAdvisor.tsx`, `SchematicAdvisor.tsx`, `ComponentDiscovery.tsx` (both of its own two
    wrappers), `PartDetail.tsx`, `Settings.tsx` -- each area's own outer content column.
*   [x] `EnclosurePanel.tsx`'s own comment updated -- it no longer claims every other tab is stuck
    at `max-w-md`, since this context closes that gap.
*   [x] `NotBuiltPlaceholder.tsx` deliberately left untouched -- confirmed unused (grep found zero
    real call sites; every area tab is now a real, built component), so widening dead code has no
    user-visible effect.
*   [x] `max-w-4xl` (56rem/896px) chosen deliberately over matching `EnclosurePanel`'s own
    `max-w-6xl` -- these are single-column text/list/form areas without Enclosure's own
    responsive `lg:flex-row` two-column layout; a large but not edge-to-edge width gives real
    breathing room without stretching plain text/results lists uncomfortably wide. `Overview`'s
    dashboard (`CTX-313.1`, the trigger for this fix) also benefits directly -- its 2-column status
    card grid now has real room instead of squeezing into 448px.

### Non-Goals (deliberately not done here)
*   No change to `<main>`'s own `items-center` alignment, and no `mx-auto` added to these columns.
    A real, separate quirk was found while investigating (a flex item combining `w-full` with
    `max-w-*` inside an `items-center` flex-col container does not actually get centered by
    flexbox alignment -- the box renders flush to the start edge instead), but the user's own
    complaint was specifically about wasted width, not misalignment, and `EnclosurePanel` already
    exhibits the identical flush-left behavior today without complaint. Named honestly here rather
    than silently "fixed" as an unrequested side effect (see Plan Drift).
*   No change to `EnclosurePanel.tsx`'s own `max-w-6xl`/responsive layout -- already real, already
    wider than everything else, not touched.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: found a real, separate centering bug while investigating, deliberately not
    fixed here.** `<main>`'s own `flex flex-col items-center` was presumably intended to center
    each area's content column within the available space. It doesn't: a flex item that combines
    an explicit `w-full` with a `max-w-*` cap does not get centered by `align-items: center` in a
    `flex-col` container -- the box renders flush against the container's start edge regardless
    (confirmed by the reported screenshot: content sat immediately right of the sidebar with all
    empty space piled up on the right, not split evenly). The standard fix would be adding
    `mx-auto` to each column. Not done here: the user's own reported complaint was specifically
    "wasted... not expanding horizontally," not misalignment, and `EnclosurePanel.tsx` already
    renders with this same flush-left behavior today without it ever being flagged as wrong --
    changing the *visual position* of every tab's content as an unrequested side effect of a
    width fix risked solving a problem nobody reported while potentially surprising the user with
    a new layout they didn't ask for. Named honestly as a real, known, separate issue for a future
    pass rather than silently bundled in or silently ignored.
*   **Deviation 2: scoped as a small fix context, not the "repo-wide shell/layout redesign"
    `EnclosurePanel.tsx`'s own comment named as the eventual real follow-up.** The user's own
    report was specific and mechanical (columns are too narrow, everywhere) -- addressed directly
    with a class-name change across every affected file. A genuine shell redesign (e.g., a
    responsive multi-column dashboard layout, per-area custom widths beyond a single shared
    constant) remains real, separate, future work if ever wanted; not invented here beyond what
    was actually asked for.

**Not verified in this session**: a real human click-through confirming the new `max-w-4xl` width
actually looks right across every affected tab (Overview, Components, Schematic, PCB, Settings,
Part Detail) on the user's own real, wide window -- only the Overview screenshot that triggered
this fix has been seen directly. Named honestly per this repo's own `native-window-verification-gap`
pattern, not assumed covered by the passing mocked test suite.
