# CTX-101.1: Tauri UI & Rust Process Supervisor

> **Spec Reference:** Links to [SPEC-101](../specs/SPEC-101-ui-ipc-bridge.md)

## 1. Feature Definition & Execution Plan

### Phase 1: Project Scaffolding
*   [x] Scaffold React/Vite/TypeScript frontend in `apps/tauri-ui` with Tailwind configured.
*   [x] Scaffold the Rust Tauri project in `core/tauri-rust`, with `tauri.conf.json` pointed at `apps/tauri-ui` as the frontend dist/dev server.
*   [x] Verify `cargo tauri dev` boots the shell app against the Vite dev server.

### Phase 2: IPC Transport Layer
*   [x] Implement the `dispatch_to_daemon` `#[tauri::command]` holding an `Arc<Mutex<ChildStdin>>`.
*   [x] Spawn `services/python-daemon/daemon.py` as a child process on app startup.
*   [x] Stream the daemon's `stdout` back to the frontend via a Tauri event.
*   [x] Frontend IPC client wrapper around `invoke("dispatch_to_daemon", ...)`, parsing responses with `JSON.parse` only (never `eval`).

### Phase 3: Process Supervisor ("Crash Shield")
*   [x] Windows: bind the Python `Child` to a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.
*   [x] Linux: call `libc::prctl(PR_SET_PDEATHSIG, SIGKILL)` before exec.
*   [x] macOS: `RunEvent::Exit` lifecycle hook (graceful-exit backstop only — see Plan Drift).

### Phase 4: Frontend Concurrency Guard
*   [x] Loading state that disables new dispatches while a request is in flight, preventing `stdin` spam.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: macOS crash coverage is graceful-exit only.**
    *   *Reasoning:* `RunEvent::Exit` only fires when the app quits normally; it cannot catch a hard crash. SPEC-101 calls for pairing it with "a Python-side heartbeat ping," which lives in `services/python-daemon` and is out of scope for this UI/Rust-focused context.
    *   *Impact:* Tracked as follow-up work in the Python daemon's own context file before macOS crash coverage can be considered complete; not blocking for this feature.
*   **Deviation 2: `tauri.conf.json` relative paths resolve one directory shallower than the `src-tauri` convention assumes.**
    *   *Reasoning:* Flattening `core/tauri-rust/src-tauri/*` up into `core/tauri-rust/` (to match the README's documented layout) meant the Tauri CLI resolves `frontendDist`/`beforeDevCommand`/`beforeBuildCommand` relative to `core/tauri-rust`'s parent, not `core/tauri-rust` itself — discovered by actually running `cargo tauri dev` and watching it resolve the wrong path. Paths were adjusted from `../../apps/tauri-ui` to `../apps/tauri-ui` accordingly.
    *   *Impact:* None beyond the path fix; documented here so a future rename of `core/tauri-rust` doesn't silently reintroduce this.
*   **Deviation 3: Windows Job Object path is implemented and has a real test (`TEST-005`), but neither has ever been compiled.**
    *   *Reasoning:* This is a macOS development machine with no Windows target available locally; `#[cfg(target_os = "windows")]` code — production and test alike — isn't parsed for type errors here at all, only for syntax. Added `.github/workflows/rust-core-ci.yml` (matrix over `ubuntu-latest` / `windows-latest` / `macos-latest`) so `TEST-002` and `TEST-005` actually run on real OS-specific runners once this PR's CI executes.
    *   *Impact:* `TEST-005`'s status can't move to ✅ until that workflow has actually run once on `windows-latest` — there is a real chance the Windows code has a compile error that's only visible there. Should be double-checked against the first CI run on this PR before treating the Windows path as verified.
*   **Deviation 4: the first real CI run (`ubuntu-latest` + `windows-latest`) failed, exactly as Deviation 3 warned it might — this is exactly what the CI was added to catch, and it worked.**
    *   *Findings, `windows-latest` (compile failure, never even reached the test):*
        1. `Cargo.toml`'s `windows` crate feature list was missing `Win32_Security` and `Win32_System_Threading` — `CreateJobObjectW` and `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` are gated behind those and weren't visible at all (`E0432`).
        2. `HANDLE(child.as_raw_handle() as isize)` in both `daemon.rs` and the new test was wrong — `as_raw_handle()` already returns `*mut c_void` (`HANDLE`'s actual inner type in `windows` 0.58); casting through `isize` doesn't match (`E0308`).
        3. `HANDLE` wraps a raw pointer, so `JobHandle` (and therefore `DaemonHandle`, which holds one on Windows) wasn't `Send + Sync` — which Tauri requires for anything passed to `app.manage(...)`. Fixed with a manual `unsafe impl Send/Sync for JobHandle`, justified by a HANDLE being an opaque OS value safe to share across threads as long as it isn't closed concurrently (it isn't — `Drop` only runs once). Several of the other reported errors (`no field 'stdin' on State<...>`, `no method 'shutdown' found`) were downstream noise from this one root cause, not separate bugs.
    *   *Findings, `ubuntu-latest` (compiled fine, test failed at runtime):*
        4. `TEST-002` itself had a genuine race: the intermediate process forked the grandchild and could reach `_exit(0)` before the grandchild's own `prctl(PR_SET_PDEATHSIG)` call had actually run — forking doesn't guarantee the child has executed anything yet. If the intermediate exits first, there's nothing registered for the kernel to enforce. Fixed by adding a second, private pipe: the grandchild now signals readiness *after* calling `set_kill_on_parent_death`, and the intermediate blocks on that signal before reporting the grandchild's pid and exiting. This was a bug in the test's synchronization, not in `supervisor::linux::set_kill_on_parent_death` itself.
    *   *Impact:* All four fixed in a follow-up commit. Confirms the CI investment (Deviation 3) was worth it — `TEST-005` in particular would have silently never compiled if left unverified, and `TEST-002` would have been flaky/misleading if it happened to pass by timing luck on a different run. Both tests need to go green on the next CI run before this path is trusted.
