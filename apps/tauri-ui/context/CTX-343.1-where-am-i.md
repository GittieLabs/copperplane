# CTX-343.1: Where Am I

> **Spec Reference:** Links to
> [SPEC-343](../specs/SPEC-343-the-guided-path.md)

## 1. Feature Definition & Execution Plan

`SPEC-343` §2.4 claims stage is computable from the project record, with nothing new stored and
nothing for the user to declare. Everything else in that spec rests on it: one sentence saying where
someone is, one action that moves them forward, and a non-linear flow that reports its own
regressions.

**So the first question is whether that claim survives real projects**, and it has two halves that
fail differently:

*   **Is the reading unambiguous?** If two states are true at once — a schematic checked and a board
    that has never been opened — the surface has to pick, and picking wrong is worse than saying
    nothing. §3: a guided surface speaks with the app's whole voice, so its first sentence is where
    trust is spent fastest.
*   **Is there a real next action, or does every state collapse to "run a check"?** If it does, this
    is a button that already exists on the tab it points at, and the honest outcome is a smaller
    feature.

Both are measurable today against the maintainer's three real projects and the four this session has
already read. That is the `CTX-341.1` and `CTX-328.1` ordering: measure the assumption the design
rests on before building the thing that rests on it.

### Phase 1: Does the record actually say where you are

*   [ ] Compute a stage reading for every real project on this machine, from the record alone.
*   [ ] **Count the ambiguous ones** — states where more than one reading is defensible — rather
        than reporting the ones that worked.
*   [ ] For each state, write down the next action it implies, and mark the ones that are just
        *"run the check on the tab this points at"*.
*   [ ] Judge against a bar written before the run, in this commit: a reading is useful when it is
        unambiguous **and** its action is something the user would not already be looking at.
*   [ ] Write the finding into `SPEC-343` §2, including if it says build less.

### Phase 2: The reading, as a computed fact

*   [ ] A pure function over the project record — no new storage, nothing declared, per §2.4.
*   [ ] **A stage regression is reported, not inferred from ordering.** `SPEC-339`'s `stale_reason`
        already says the schematic moved after the PCB check; §2.4's whole claim is that the DAG
        reports itself.
*   [ ] Every state names the evidence that produced it, so a wrong reading is debuggable by the
        person who sees it rather than only by its author.

### Phase 3: One sentence and one action on Overview

*   [ ] Rendered on Overview, beside the existing cards, never in front of the tabs (§2.1).
*   [ ] The action is a link to a tab that already exists. It never navigates on its own, never
        advances a stage, never mutates the project — `SPEC-300`'s AI boundary applies to this
        surface even though it is not an AI surface, because the user cannot tell the difference.
*   [ ] What it says when nothing is wrong, which §2.6 leaves open and §3 warns about: generic
        praise is worse than silence.

### Phase 4: The toggle, and what off means

*   [ ] Off per project, on at any point, per §5.
*   [ ] Settles §2.6's open question: quiet entirely, or *where am I* without the teaching.
*   [ ] Settles whether a new project defaults it on.

### Phase 5: Absence-shaped triggers — deliberately its own phase

*   [ ] `SPEC-343` §2.6 names this as where the value probably is, and `CTX-210.1` withdrew a pack of
        exactly this shape for being ungroundable. What a novice is missing is usually a part that is
        not there.
*   [ ] The rule to settle: an absence must still name something real (`SPEC-210` §2.2). *"No
        capacitor on `+5V`"* names `+5V`; *"no ESD protection"* names nothing and must not be said.
*   [ ] Measured against a board broken on purpose, with false positives counted, per `SPEC-210` §3.

## 4. Plan Drift & Architectural Changes

*   **Prediction 1: the ambiguity is real and concentrated in one place** — a project with a linked
    KiCad project, a schematic that has been checked, and a board that has never been opened. Both
    *"check your board"* and *"your schematic has findings to read"* are defensible, and I expect
    that state to be common rather than exotic, because it is what every project looks like halfway
    through.

*   **Prediction 2: most next actions will be "run the check on the tab this points at", and that is
    fine for exactly one state and thin for the rest.** If Phase 1 bears that out, the honest shape
    is smaller than §5 implies: a *where am I* line without a *what next* action, which is still
    worth having and is a different feature from the one the spec describes.

*   **This context is on the spec's own branch, not its own.** `/new-context` says to branch from
    `origin/develop` and re-check the spec survived — it would not, since `SPEC-343` is not merged.
    Recorded because it is a deviation from the documented flow rather than an oversight.
