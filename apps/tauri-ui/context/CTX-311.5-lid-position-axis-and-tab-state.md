# CTX-311.5: Three fixes found by a second real click-through: lid position, up-axis, and tab state loss

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

`CTX-311.4` fixed the "empty gray rectangle" bug and the user clicked through the real app again, as
requested. That second real click-through found three more real, concrete bugs -- none of them
things this session's own mocked test suite could have caught, since none of them involve wrong
*logic* so much as wrong *real geometry* and wrong *real component lifecycle*, both only visible by
actually looking at (or navigating) the real running app.

## 1. Feature Definition & Execution Plan

### Phase 1: real lid Z-position bug
*   [x] **Confirmed live** (`freecadcmd`, real generation): `_LID_BODY_LINES_TEMPLATE`'s
    `Part.makeBox({outer_w}, {outer_d}, {lid_thickness})` had no position vector, so it built at the
    world origin -- the exact same z-range as the shell's own solid floor (`z=[0, wall_thickness]`),
    not the shell's real open top (`z=[height, height+lid_thickness]`). Measured directly: a real
    height=20 enclosure's own lid came back with z=[0, 2] (its thickness), identical to the shell's
    own floor thickness -- the lid was rendering fused into the floor, invisible as a separate cap.
*   [x] **Fixed**: `Part.makeBox({outer_w}, {outer_d}, {lid_thickness}, FreeCAD.Vector(0, 0,
    {height}))`, threading `height` into `_LID_BODY_LINES_TEMPLATE`'s own `.format()` call (it
    wasn't passed before). Verified live: the lid's real bottom now lands exactly at the shell's
    real top, gap `~0`.

### Phase 2: real Z-up vs Y-up axis mismatch
*   [x] **Confirmed live**: `freecad_bridge.py`'s STL→trimesh→glb export path performs no axis
    remapping -- FreeCAD's own Z-up convention (`box.Height` is always the Z extent throughout this
    module's build scripts) stays Z-up in the exported glTF, even though glTF's own spec convention
    (and `EnclosureViewer.tsx`'s own camera math, `CTX-311.3`/`CTX-311.4`) is Y-up. Measured directly:
    a real height=20mm enclosure on a 50x30mm board came back with the smallest bounding-box extent
    (~20mm, the real height) on the glTF file's own **Z** axis, not Y. This is a real, independent
    bug from `CTX-109.4`'s own unit-scale fix -- same export path, different defect. It explains the
    user's exact reported symptoms: the default view showing the enclosure "upright on a side," and
    "Top" looking "into the inside of the box as if on a flat surface" -- both are what a Y-up camera
    looking at Z-up data actually produces.
*   [x] **Fixed**: a single, shared `_export_glb()` helper (both the base shell and the lid now go
    through it, replacing two near-duplicate inline blocks) applies a real -90° rotation about X
    (`trimesh.transformations.rotation_matrix(-pi/2, [1,0,0])`) before the existing unit-scale fix
    and export -- verified directly (a real 1x2x3 test box's own "3" extent moved from Z to Y after
    this exact transform) and against a real generated enclosure (height now lands on the real Y
    axis, confirmed both larger real X and Z extents on the same real board-driven shape).

### Phase 3: Enclosure tab state loss across navigation
*   [x] **Confirmed live**: `App.tsx` rendered `EnclosurePanel` via `{view.area === 'enclosure' &&
    <EnclosurePanel .../>}` -- the only area component still conditionally mounted/unmounted, unlike
    `BoardAdvisor`/`SchematicAdvisor`, which stay mounted and are hidden via CSS specifically so a
    real, just-finished result survives switching tabs away and back (`CTX-309.3`'s own real fix for
    exactly this class of bug, on a different tab). `EnclosurePanel` never got the same treatment,
    so a real, just-generated enclosure (and every other local param/mode/lid choice) was silently
    discarded on every tab switch.
*   [x] **Fixed**: `EnclosurePanel` now renders inside `<div className={view.area === 'enclosure' ?
    undefined : 'hidden'}>`, matching `BoardAdvisor`/`SchematicAdvisor`'s own pattern exactly. Added
    `data-testid`s to all three always-mounted area wrappers (`schematic-area`/`pcb-area`/
    `enclosure-area`) -- needed for real reasons, not just convenience: with `EnclosurePanel` now
    always mounted, its own board picker renders the same real open-board text `BoardAdvisor`'s own
    picker does, so tests (and, structurally, any future accessibility tooling) need a real way to
    tell the two apart.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: a shared `_export_glb()` helper replaced two near-duplicate inline export
    blocks, discovered as the natural place to fix the axis bug once.** The base shell and lid
    previously each had their own separate `trimesh.load(...); mesh.apply_scale(...); mesh.export(...)`
    block (the lid's added in `CTX-311.2`, mirroring the base's own `CTX-109.4` fix by hand). Fixing
    the axis bug in only one of the two would have left the other silently still broken -- unifying
    them first, then fixing the shared function once, is safer than patching both copies in parallel
    and risking one drifting from the other, the same real risk this repo's own norms warn about
    for duplicated logic in general.
*   **Deviation 2: all three of these bugs were found in a SECOND live click-through, immediately
    following the FIRST one (`CTX-311.4`) that had already found and fixed a different real bug.**
    Two consecutive rounds of "ship a fix, click through it for real, find more real bugs" is worth
    naming plainly: real UI surfaces accumulate more real defects than either code review or a
    comprehensive mocked test suite catches on the first pass, even within the same session, even
    right after a previous real bug was just fixed. This is the `native-window-verification-gap`
    memory's own thesis playing out twice in immediate succession, not a one-off.
