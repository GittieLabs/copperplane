# CTX-306.4: Implementation Context: Project Parts List & Manual Project Linking

> **Spec Reference:** Links to [SPEC-306](../specs/SPEC-306-component-discovery.md)

Real, detailed live-testing feedback: "after we save a component and navigate away, the component
view will just show the last component or no component at all. We should instead have a list of
project added components that are saved to the library... use the discovered component that we
select to use and make that the detail view with navigation back to the list of project
components... our library parts view should have an option to add the part to the project."

`CTX-304.3` built the backend half of this (`Project.parts`, auto-link on a fresh Save) but
deliberately left the frontend list/navigation UI and the manual "add an already-saved part to a
project" action as separate, larger follow-up work -- this context builds that other half.

## 1. Feature Definition & Execution Plan

### Phase 1: Persistent Project Parts list in Components
*   [x] `ComponentDiscovery.tsx`: a new `projectParts: SavedPart[] | null` state, hydrated from
    `currentProject.parts`' bare id list (`CTX-304.3`) via `Promise.allSettled(ids.map(loadPart))` --
    best-effort, same philosophy as `CTX-306.3`'s `savedPartIds` lookup: a part_id the project
    references but that's no longer loadable (deleted from the Library outside this app) is silently
    omitted, not an error that blocks the rest of the list.
*   [x] Rendered above the search's "Did you mean" results, only when there are no active candidates
    (`candidates.length === 0`) and the project has at least one real part -- persistent context for
    the default landing state of the Components tab, not clutter alongside active search results.
*   [x] Each row: part_id, manufacturer, package -- matching "Did you mean"'s own row shape at a
    glance, and an "Open" button.

### Phase 2: Detail view with real back-navigation
*   [x] A new, separate `openedPartId`/`openedPart` state -- deliberately distinct from the existing
    `confirmed` (search-confirm) state, since opening an already-saved part from this list needs no
    datasheet-caching UI or re-confirmation step, just a straight `loadPart` + `PartDetail
    initialPart={...}` render (mirroring `App.tsx`'s own `PartDetailView` shape, but kept local to
    `ComponentDiscovery` rather than routed through `App`'s view state, so opening a project part
    stays inside the Components tab the user is already in rather than jumping to the top-level
    Library area).
*   [x] "← Back to project parts" returns to the list; opening a search-confirmed candidate clears
    `openedPartId` and vice versa, so the two detail states never overlap.

### Phase 3: Manual "Add to project…" for an already-saved Part
*   [x] A real, separate discovery mid-implementation: `currentProject` is **not** a usable signal
    here -- `App.tsx` resets it to `null` the instant `view.kind` leaves `'project'` (a real,
    pre-existing, deliberate reset for stale-state-flash prevention), so it's always `null` on the
    Library (`initialPart`) path this feature explicitly needs to cover. Building a picker over every
    real project (`listProjects()`) is the only mechanism that works on both the Library path and the
    Components path alike -- so `PartDetail.tsx` gained one, replacing an earlier, narrower
    `currentProject`-gated single-button design that was built, then found broken by this discovery,
    and reverted before shipping (see Plan Drift).
*   [x] Mirrors `CTX-315.2`'s existing "Add to library…" picker exactly (same open-picker/multi-
    select-checkboxes/Confirm-or-Cancel shape) -- the same kind of problem (0+ real targets to tag a
    saved object into) already solved once in this file. Available wherever `savedPart` is set,
    regardless of how the Part got there (a fresh save, `initialPart` from Library, or `CTX-306.3`'s
    `loadPart`-first hydration from search) -- covers re-linking an already-saved part (found via
    search in a *different* project's Components tab) to a second project too, which the
    auto-link-on-save path alone can't do.
*   [x] A per-project failure during Confirm is collected and reported by name (`Couldn't add to:
    <names>.`), rather than the whole action failing opaquely on the first error.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (real, corrected mid-session): the first "Add to project" design assumed
    `currentProject` was a usable single-target signal everywhere `PartDetail` renders. It isn't.**
    *   *Reasoning:* `App.tsx`'s own effect (lines ~165-168) explicitly resets `currentProject` to
        `null` the instant `view.kind !== 'project'` -- a real, deliberate, pre-existing guard
        against a stale previous project's state flashing into a different view, not a bug. This
        means the Library path (`view.kind === 'partDetail'`, rendering `PartDetail initialPart=...`)
        *always* sees `currentProject: null`, discovered only after already building and testing a
        `currentProject`-gated single-button "Add to project" action and threading `currentProject`
        into `App.tsx`'s `PartDetailView`.
    *   *Impact:* that first design (a `manuallyLinked`/`manualLinking` single-target button, plus
        `currentProject` threaded into `PartDetailView`) was fully reverted before shipping --
        replaced with the project-picker design in Phase 3 above, which needs no `currentProject` at
        all and therefore works identically on every path `PartDetail` can be reached from. Caught by
        re-reading `App.tsx`'s real state-management code before assuming the prop would carry a
        meaningful value, not by a failing test (no test yet covered the Library path specifically,
        which is itself worth noting honestly rather than glossing over).
*   **Deviation 2 (non-deviation, confirmed as designed): the Project Parts list does not filter out
    parts already known to be missing a footprint, or otherwise sort/group by completeness.**
    *   *Reasoning:* out of scope for this pass -- the user's own ask was for the list and
        navigation to exist at all, not a richer completeness view. Named here so a future session
        doesn't assume this was considered and rejected for a substantive reason.
    *   *Impact:* none yet; a real, separate future enhancement if requested.
