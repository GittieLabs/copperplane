# CTX-310.3: Implementation Context: Enclosure Tab Board-Picker Redesign

> **Spec Reference:** Links to [SPEC-310](../specs/SPEC-310-enclosure-from-board-profile.md)

Real user feedback exercising the actual running app: the Enclosure tab's "From board" mode showed
five number inputs with no visible labels. Each field's label text was passed as an HTML
`placeholder`, but every field was pre-filled with a real default number (`height: 20`,
`wall_thickness_mm: 2.0`, etc.) -- a `placeholder` never renders once a value is present, so the
user saw an unlabeled stack of numbers with no way to tell what they meant or whether they were
optional.

Beyond the labeling bug, the mode structure itself didn't match how someone would actually work.
"From board" (live IPC only, gated behind a `kicad_available` capability check) and "Import board
file…" (always available, a blind file dialog) were really the same underlying capability --
generate from a real PCB -- split into two tabs because `SPEC-310` added file import after
`SPEC-109`'s original live-only mode. Neither one reused a board the user already had open in
KiCad, even though `lib/boardAdvisor.ts`'s `listOpenBoards()` (built for the PCB/Schematic tabs)
already does exactly that lookup. "Manual dimensions" also defaulted to being selected, even though
a plain hand-typed rectangle is the least useful starting point for someone who has a real board.

## 1. Feature Definition & Execution Plan

### Phase 1: real investigation before writing any code
*   [x] Confirmed, by reading `EnclosurePanel`'s existing render code: every one of the five
    geometry fields uses `placeholder={label}` with `value={realDefaultNumber}` -- the exact,
    confirmed cause of the "unlabeled numbers" complaint, not a hypothetical.
*   [x] Confirmed, by reading `freecad_bridge.py`'s `generate_enclosure` and
    `kicad_bridge.get_board_outline()`'s own docstring ("the real, sufficient board-outline data
    for SPEC-109's fixed-rectangular-enclosure scope -- not a fallback standing in for a true
    polygon trace this spec was never going to build"): every mode produces the same shape, a
    rectangular `Part::Box`, whether the dimensions come from typed numbers or a board's real
    bounding box. The "board isn't rectangular" concern the user raised applies to every mode
    equally -- this needed to be said honestly in the UI, not implied to be solved by "From board."
*   [x] Confirmed `lib/boardAdvisor.ts`'s `listOpenBoards()`/`openKicad()` (built for `BoardAdvisor`/
    `SchematicAdvisor`, CTX-309.3/.4) are real, already-tested, directly reusable for this redesign
    -- no new backend route needed.

### Phase 2: extract `EnclosurePanel` into its own component
*   [x] Moved the inline `EnclosurePanel` function out of `App.tsx` into
    `apps/tauri-ui/src/components/EnclosurePanel.tsx`, matching the pattern already established for
    `BoardAdvisor.tsx`/`SchematicAdvisor.tsx`.
*   [x] `App.tsx`'s Enclosure area now imports and renders the extracted component with the same
    `projectName` prop; no change to its mount lifecycle (still conditionally rendered on
    `view.area === 'enclosure'`, unlike `BoardAdvisor`/`SchematicAdvisor`'s always-mounted pattern --
    out of scope for this redesign, not requested).

### Phase 3: redesign into two modes, "Board" default and primary
*   [x] Merged "From board" and "Import board file…" into one "Board" mode -- the default, first
    tab. On mount, calls `listOpenBoards()` (no `kicad_available` capability pre-check, mirroring
    `BoardAdvisor`'s own just-try-it-and-handle-failure pattern instead of the old gate).
*   [x] Exactly one open board found: auto-selected immediately (`pcbPath` populated with no click
    required) -- directly addresses "if we know that a pcb file has been loaded, we should have
    that as selected." Still shown as a real, highlighted, clickable list item so the user can see
    what's selected and override it.
*   [x] More than one found: real list shown, nothing pre-selected (mirrors `BoardAdvisor`'s own
    multi-board handling -- never guesses which one the user means).
*   [x] None found, or `listOpenBoards()` fails: calm guidance (mirrors `BoardAdvisor`'s merged
    no-board/connection-failure state) with "Open KiCad" and "Refresh," plus "Choose a .kicad_pcb
    file…" given equal visual weight -- unlike the PCB/Schematic check tabs, generating from a file
    needs no live KiCad connection at all, so this path always works regardless of whether KiCad is
    even running.
*   [x] "Choose a different file…" is always available alongside the list too, not just in the
    empty state -- a manual pick always overrides the list's own selection.
*   [x] Selecting a board (click or auto-select) only sets `pcbPath` -- it does not auto-generate.
    Generation still requires clicking "Generate Enclosure," so the user can review/adjust geometry
    parameters first.
*   [x] "Manual (no PCB)" kept (per explicit confirmation, not removed outright), demoted to the
    last/least-prominent tab position and no longer the default, with real visible `<label>`s
    (fixing the same placeholder-only bug) and an explicit caveat that it's unrelated to any real
    board.

### Phase 4: real, visible labels and explanations
*   [x] Replaced every `placeholder`-only field with a real `<label>` wrapping the input, an
    explicit required/optional tag, and a one-line plain-language explanation (e.g. "Standoff height
    (mm) -- optional. How tall the mounting posts are that hold the board above the enclosure
    floor.").
*   [x] Added one honest disclosure line above the Board-mode fields: "Enclosures are generated as a
    rectangular box sized to your board's bounding box -- non-rectangular board outlines aren't
    traced precisely yet."
*   [x] Added a one-line, non-functional text hint ("Already checked your board on the PCB tab? Use
    the same file here.") nodding at the check-schematic → check-PCB → generate-enclosure flow,
    without wiring real cross-tab navigation -- a larger change deliberately deferred, named
    explicitly rather than silently left out.

### Phase 5: tests
*   [x] New `EnclosurePanel.test.tsx` (extracted and rewritten from `App.test.tsx`'s old
    `describe('App: Enclosure tab', ...)`): default mode is Board; auto-select on exactly one open
    board; multi-board list with no auto-select and Generate disabled until a pick; guidance state's
    Open KiCad/Refresh/manual-pick actions; a manual pick overriding an auto-selected board; real
    visible labels/hints for every field; Board-mode submission omits width/depth and includes
    `pcb_path`; Manual mode's own labels and always-enabled Generate; existing `unrecognized_holes`
    warning and `.step`-open behavior, unchanged.
*   [x] Removed the old Enclosure tests from `App.test.tsx` along with the
    `generateEnclosureMock`/`pickPcbFileMock`/`./lib/enclosure` mock (no longer needed there --
    `getCapabilitiesMock`/`./lib/settings` and `shellOpenMock`/`@tauri-apps/plugin-shell` kept, both
    still used by `Settings.tsx`/`ComponentDiscovery.tsx` respectively, rendered by other tests in
    that file).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: this branch had to be rebased onto the still-unmerged `CTX-309.3` branch instead
    of `origin/develop`, discovered only after starting the branch, not planned in advance.** The
    plan assumed `lib/boardAdvisor.ts`'s `listOpenBoards()`/`openKicad()` were already available to
    import -- they aren't, on `develop`, since `CTX-309.3`'s own PR (which built them) hasn't merged
    yet. Recreated the branch stacked on `feat/CTX-309.3-board-open-state-guidance` instead. This
    means this context's own PR has a real merge-order dependency: `CTX-309.3` must merge first, or
    this PR's diff will include all of that work too. Named explicitly here rather than silently
    assumed to not matter.
*   **Deviation 2: "Manual dimensions" was not removed outright, despite the user's own framing of
    it as "an old testing option that isn't useful now."** Asked directly rather than assumed --
    the user confirmed keeping it as a real but demoted, last-position option (a plain rectangular
    box is still useful before any board file exists), not deleting it. Recorded here since it was a
    genuine two-way option, not an obvious call either direction.
*   **Deviation 3: real click-through against the actual running app confirmed this context's own
    redesign works, but surfaced two real, deeper product questions this context didn't scope in --
    both pre-existing limitations of `SPEC-109`/`SPEC-310`, not caused by this redesign.** The user
    generated a real enclosure from a real open board and asked why no lid appeared, why the
    optional geometry fields exist at all, and whether the bounding box could instead trace the
    board's real shape. Investigation confirmed both are real, deliberate, already-documented scope
    decisions, not bugs introduced here: `SPEC-109` §1's own Non-Goals rule out lid/fastener
    hardware ("Fixed rectangular box geometry only... Not fastener hardware selection... lid-latching
    mechanism is out of scope"), and both the live IPC path (`kicad_bridge.get_board_outline`) and
    the file-based path (`kicad_pcb_import.extract_board_outline`, literally named
    `_parse_dxf_edge_cuts_bbox`) reduce the real Edge.Cuts polygon to a bounding box before it ever
    reaches FreeCAD -- true for every mode, not just Manual. Recorded as a new backlog entry,
    `SPEC-111` (`ROADMAP.md` §3.1), rather than attempted here: a real lid needs per-component
    Z-height data this pipeline doesn't capture at all yet, and a true polygon-traced shell is real,
    non-trivial OpenCASCADE work (arbitrary closed-wire extrusion, inward offset, concave-corner
    handling) neither of which is a small tweak to the existing `Part.makeBox` script.
