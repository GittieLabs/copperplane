# CTX-205.4: Design Requirements UI

> **Spec Reference:** Links to [SPEC-205](../../../services/python-daemon/specs/SPEC-205-datasheet-design-guidance.md)

## 1. Feature Definition & Execution Plan

Makes `CTX-205.1`-`.3`'s real, working pipeline actually visible to a user for the first time: a
real "Design Requirements" panel on Part Detail (`SPEC-205 §5`), grouped by category, with a real
citation button per item that opens the cached datasheet at that page. Class A (typed facts) and
Class C (general practice) still don't exist on the backend -- this panel renders only what's real
(Class B, cited prose), named honestly rather than showing an empty placeholder for classes that
don't exist yet.

**Real research performed before planning, not assumed:**
*   **`PartDetail.tsx`'s real, current structure** -- a single scrolling column (no CSS grid, no
    pin diagram yet -- the "pin table" is a plain `<table>`), not the two-column "beside the pin
    diagram" layout `SPEC-205 §5`'s own prose describes literally. Placed as a real sibling
    section inside the already-existing `savedPart &&` card, after the "Add to library…" picker
    and *before* the footprint-conditional branch -- deliberately not gated on `footprint_id` the
    way Connection Guidance is, since decoupling/reset/layout guidance is useful before any
    footprint exists.
*   **A real, honest gap between `SPEC-205 §5`'s fuller vision and what the backend actually
    produces today**, found by reading the real pipeline output shape directly
    (`datasheet_guidance.py`, `datasheet_structure.CATEGORY_PATTERNS`): every returned item is
    `{quote, page, category}` -- no Class marker, no `pin_number`, and the real category keys
    (`absolute_maximum_ratings`, `recommended_operating_conditions`, `power`, `decoupling`,
    `reset`, `clock_oscillator`, `layout`, `typical_application`) don't map 1:1 onto §5's own
    friendly grouping (`reset/boot` and `protection` don't exist as real backend categories at
    all). This context does **not** attempt §5's Class A/B/C grouping, the "General practice — not
    from this datasheet" section, or per-pin filtering -- all of that needs real backend work that
    doesn't exist yet (Class A/C extraction, pin association). A real, honest label per real
    category key is used instead of guessing at the eventual fuller shape.
*   **The real async-action convention already established in this exact file** -- Connection
    Guidance (`handleGetGuidance`) is the closest, most direct precedent: one `useState` triple
    per action (result/loading/error), reset in the existing `useEffect` on `candidate.part_number`
    change, `handleX` naming, a button whose label swaps to a `"…ing…"` gerund while loading, no
    incremental progress UI anywhere in this file for any job (every existing action just
    `await`s `handle.result`). Mirrored exactly -- except the *result* itself isn't a separate
    state var, since `datasheet.generate_guidance`'s route persists onto and returns the whole
    updated Part (matching `attachFootprintToPart`/`generateFootprintFromPart`'s own "re-save
    returns the fresh whole record" shape already used in this file) -- `setSavedPart(updated)` is
    the real result-storage mechanism, avoiding a second, redundant piece of state that could
    drift from `savedPart.design_guidance`.
*   **Opening a citation at a real page** -- no PDF-page-anchor precedent exists anywhere in this
    repo (confirmed by grep). `datasheet.generate_guidance`'s own response never returns a local
    PDF path (only a `content_hash`), so the real, already-existing `cacheDatasheet(partNumber,
    datasheetUrl)` (used today by `ComponentDiscovery.tsx`'s own "Open" button) is reused to
    resolve the real local path, then opened via the real, already-used `@tauri-apps/plugin-shell`
    `open()` with a `#page=N` fragment -- a standard PDF-viewer URL convention, but **not verified
    working through this app's own real, packaged webview** in this session (no way to click
    through the actual native app here, same real constraint `CTX-315.2`/`CTX-316.1` already
    named). Stated honestly as unverified, not assumed to work.
*   **A real bug caught while typing the frontend interface, before it ever shipped**:
    `save_part` (`library_store.py`) only backfilled `design_guidance` via `load_part`, never on
    `save_part` itself -- meaning `library.save_confirmed_part`'s own real response (the very
    first save, never routed through `load_part`) could omit the key entirely rather than
    carrying a real `null`, making the frontend's `design_guidance: DesignGuidance | null` type a
    lie for that one real code path. Fixed in `library_store.py` (this context, not `CTX-205.3` --
    the bug shipped there, the fix lands here) by having `save_part` itself call
    `_backfill_design_guidance` before writing/returning the record, so every real caller gets the
    same real shape `load_part` already guaranteed.

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Deviation 1: a real backend fix landed in this context, not `CTX-205.3` where the bug
    shipped.** Discovered while writing the frontend's `SavedPart.design_guidance` type: `save_part`
    never backfilled the field itself (only `load_part` did), so `library.save_confirmed_part`'s
    real, first-save response could omit the key entirely. Fixed here (`save_part` now calls
    `_backfill_design_guidance` before returning) rather than treating it as pre-existing debt to
    route around on the frontend with an extra `| undefined` in the type -- the real, correct fix
    was cheap and makes every caller's shape consistent going forward. *Impact:* real, positive; a
    latent inconsistency closed before any real UI code depended on the wrong assumption.
*   **Deviation 2: `SPEC-205 §5`'s own fuller UI vision (Class A/B/C grouping, the separate
    "General practice" section, per-pin filtering) is not built here, and this is a real, deliberate
    scope decision made during this context, not a spec change.** The backend genuinely doesn't
    produce that data yet (confirmed by reading `datasheet_guidance.py`'s real output shape) --
    building UI for data that doesn't exist would mean either fabricating placeholder sections
    (dishonest) or blocking this entire context on Class A/C extraction work first (a much larger
    scope than "make the existing real capability visible"). This context ships what's real: Class
    B guidance, grouped by real category key, with a real empty state per category. The fuller
    grouping remains real, open work for a future context once Class A/C exist.
*   **Deviation 3: `spec_ref`'s relative path needed three `../`, not two -- caught by the real
    validator, not assumed correct.** This is `CTX-205.1`-`.3`'s own SPEC-205 spec (which lives in
    `services/python-daemon/specs/`), but this context itself lives in `apps/tauri-ui/context/`
    since this slice is frontend-only -- a real, cross-module context, unlike every prior
    `CTX-205.x`. The first two attempts (`../specs/...`, then `../../services/...`) both resolved
    wrong; `scripts/validate_spec_context.py` caught both, and the real, correct path
    (`../../../services/python-daemon/specs/SPEC-205-datasheet-design-guidance.md`) was confirmed
    with a real `ls` before the third attempt, not guessed a third time.
