# CTX-326.1: Courtyard Envelopes & Sourced Heights

> **Spec Reference:** Links to [SPEC-326](../specs/SPEC-326-component-volume-placeholders.md)

The measurable half. Every component gets an X/Y extent from its real footprint and a height whose
**source is reported**, so `SPEC-311` can size an enclosure for a board whose parts KiCad ships no
model for. The placeholder solids themselves, the entry surface, and the 3D labelling are
`CTX-326.2`.

## 1. Feature Definition & Execution Plan

### Phase 1: X/Y from the real footprint

*   [x] `read_footprint_courtyard` reads `F.CrtYd`/`B.CrtYd` geometry from the `.kicad_mod`.
*   [x] **Coverage measured before relying on it:** 902 of 903 footprints across `Battery`,
    `LED_THT`, `Capacitor_THT`, `Package_DIP` and `Resistor_THT` — 99%.
*   [x] A footprint with no courtyard returns `None`, not zero. "No X/Y source" and "zero size" are
    different claims.
*   [x] Folded into `resolve_footprint_model`, so one lookup answers both *is there a model* and
    *what are its extents*.

### Phase 2: Z sourced in `SPEC-326` §2.3's order

*   [x] A resolvable STEP is **read**, not merely noted — see §4 Deviation 2.
*   [x] Then a user-supplied height, keyed by **footprint**, per §2.5.
*   [x] Then `unknown`, with `z_mm: None`. No default, ever.
*   [x] An unreadable model falls through to the next source rather than blanking the set.

### Phase 3: Make measured and stated distinguishable

*   [x] `source` per component, and `measured`/`stated`/`unknown` counts.
*   [x] `x_within_courtyard` records that X/Y is an approximation — §2.1's calibration shows it is
    **not a bound**.

### Not in this context

*   **The placeholder solids themselves.** Turning an envelope into geometry `SPEC-311`'s enclosure
    can subtract, reusing `SPEC-109`'s parametric generation, is `CTX-326.2`.
*   **The height-entry surface and 3D labelling** (`SPEC-326` §2.4, §5). Nothing is user-visible
    yet, so the `user` source is currently only reachable programmatically.
*   **`package_dimensions` as a source** (§2.3 step 2). It needs the schematic-to-library matching
    `SPEC-325` §2.5 defers, so the implemented order is model → user → unknown.

```

C1     5.50 x  5.50 x  7.00   model
R1     5.44 x  3.70 x 15.52   model
U2     9.73 x 10.66 x  6.98   model
```

**`BT1` is the tallest part on that board** — the one component with no model deciding the enclosure
height, exactly as `SPEC-326` §2.2 predicted.

**Not verified.** No enclosure has actually been generated using these envelopes; that needs
`CTX-326.2`'s solids. And nothing is user-visible, so `SPEC-326` is `user_facing: true` with its
§5 obligation entirely outstanding.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — `SPEC-326` §2.1's own calibration numbers were wrong, and are corrected here.**
    *   The spec cited `BatteryHolder_Keystone_1060_1x2032` as courtyard **32.90 × 17.00** against a
        real STEP box of 31.86 × 17.96, concluding the courtyard was 1mm *narrower* in Y. The 17.00
        came from an ad-hoc script that omitted arc midpoints — an arc bulges past its endpoints, so
        the true courtyard is **32.90 × 21.40**, 3.4mm *wider*.
    *   *Impact:* the conclusion survived but the evidence for it did not, so it was replaced with a
        **ten-part calibration** against footprints that have real models. The courtyard is smaller
        than the true body in **4 of those 10** — in X, in Y, or both. That is a far stronger basis
        for §2.1's "good approximation, not a bound" than the single mismeasured part originally
        cited. Recorded because a spec written from a buggy measurement is exactly the failure the
        measurement was supposed to prevent.

*   **Deviation 2 — "has a model" was briefly reported as "measured" with no height behind it.**
    *   The first implementation set `source: "model"` whenever a model path resolved, without
        reading it, so a first run reported `measured=9` while every one of those carried
        `z_mm: None`.
    *   *Impact:* a resolvable STEP is now actually read via `get_step_bounding_box_mm`. It costs a
        `freecadcmd` subprocess per component, which is why the calling route is already
        `ASYNC_ROUTES`-registered. A count that says "measured" must mean something was measured.

*   **Deviation 3 — a circle's courtyard was being read as zero-height.**
    *   `CP_Radial_D5.0mm_P2.50mm`'s courtyard is a single `FpCircle`. Taking only its `center` and
        `end` gave **2.75 × 0.00 mm** for a part that is 5.5mm across — an envelope of zero height
        in one axis, which would have silently contributed nothing to a clearance check.
    *   *Impact:* circles now expand to centre ± radius. Found only because the first real run over
        `Hello_World_Blinky` printed `y_mm: 0` for both capacitors, which is the kind of number that
        is obviously wrong on sight and invisible in a passing unit test.

*   **Deviation 4 — `package_dimensions` is specced as source 2 but is not yet reachable.**
    *   §2.3 orders it above a user height, but using it needs the schematic-to-library matching
        `SPEC-325` §2.5 explicitly defers.
    *   *Impact:* the implemented order is model → user → unknown. Stated here rather than silently
        skipped, because a reader comparing spec to code would otherwise find a gap with no
        explanation.
