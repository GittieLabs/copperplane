# CTX-311.4: Camera-framing fix: found by live user testing, not this module's own tests

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

Immediately after `CTX-311.3` merged, the user actually ran the real app and generated a real,
board-driven enclosure (the `NFC_Reader_ESP32` board, with a lid). The Enclosure tab's own new,
larger preview panel rendered a plain gray rectangle — no mesh at all, despite the UI correctly
reporting a real generated `.glb` path, a working lid checkbox, working camera preset buttons, and
working Open/Show-lid controls around it. A real, live, human-found bug, not caught by this
session's own extensive mocked test suite, because that suite never actually renders a WebGL scene
(this whole module's real test convention, see `EnclosureViewer.test.tsx`'s own header, avoids
Canvas rendering in jsdom entirely).

**Root cause, confirmed by re-deriving it from this exact session's own prior work, not guessed:**
`EnclosureViewer`'s `Canvas` camera has always opened at a hardcoded `position: [80, 80, 80]` — a
distance of `80√3 ≈ 138.6` scene units from the origin. Before `CTX-109.4` (this session, merged
earlier the same day), every generated enclosure `.glb` was exported with a real, confirmed bug: its
raw millimeter values were written directly into the mesh with no unit conversion, so a real 20mm box
came out with vertex coordinates around `20` — which glTF's own spec defines as *meters* — making the
mesh's own scene-space size numerically close to the camera's fixed 138-unit distance, by pure
coincidence of two independent, uncorrected numbers landing in the same rough range. That's exactly
what "empirically tuned" (this camera's own prior docstring) meant: it was tuned around the *bug*,
not around real geometry. `CTX-109.4` fixed the real unit-scale bug — a real enclosure's `.glb` now
correctly reports a real, small size (a 20mm box is `0.02` scene units, not `20`) — but nothing
updated the camera to match, because nobody yet had a script or a human click-through that combined
"the real fix" with "actually look at the viewer" until this session's own `CTX-311.3` merge, when
the user did exactly that for the first time. `CTX-109.4`'s own Testing Requirements Matrix already
named this as a real, un-verified risk ("a real enclosure generated post-fix may now render far too
small in the existing viewer until the camera/controls are also adjusted") — this context is that
prediction landing.

## 1. Feature Definition & Execution Plan

### Phase 1: real fix
*   [x] `EnclosureViewer.tsx`: `computeFrame(objects)` computes a real `THREE.Box3` over whichever
    of the base/lid meshes have actually loaded, and derives a real camera radius (the box's own
    diagonal length times a fixed headroom multiplier) and center (the box's own real centroid) --
    correct at any real enclosure size, not tuned to one.
*   [x] The camera's initial position is computed synchronously during render (not an effect) from
    whichever mesh is already loaded, so the very first frame the Canvas mounts already has the
    right camera -- no wrong-then-snapping flash.
*   [x] A `useEffect` keyed on `[base.scene, lid.scene]` re-frames an already-mounted
    `OrbitControls` imperatively -- handles the real case where the lid's own `.glb` finishes loading
    slightly after the base's (two independent, parallel `useGlbScene` calls).
*   [x] `OrbitControls`' own `target` prop now follows the real computed center too, not a hardcoded
    origin -- correct even if a future enclosure body isn't built starting exactly at `(0,0,0)`.
*   [x] Camera preset buttons (`CTX-311.3`) now operate relative to this same real, computed frame
    (shared `cameraState` ref, lifted from the presets component up into `EnclosureViewer` itself) --
    "Top"/"Bottom" orbit around the real object's real center at the real computed distance, not the
    old fixed 138-unit radius around the origin.

### Phase 2: tests
*   [x] Direct, real unit tests on `computeFrame` (exported for this purpose): a real small
    (post-fix-scale) mesh gets a real small radius; radius scales with real mesh size; center follows
    a real off-origin mesh's own true centroid; a base+lid union frames wider than the base alone;
    an empty input returns `null`, never a guessed frame.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: this bug was predicted in writing, in this exact session, before it happened --
    and still shipped anyway, then was caught by the user, not by re-reading that prediction.**
    `CTX-109.4`'s own Testing Requirements Matrix explicitly named "a real enclosure generated
    post-fix may now render far too small in the existing viewer until the camera/controls are also
    adjusted" as unverified risk. `CTX-311.3` then added real camera-preset math on top of the same
    unadjusted hardcoded distance, without connecting it back to that earlier, self-authored warning.
    Worth recording plainly: writing down a risk is not the same as checking for it before shipping
    the next piece of work that depends on the same assumption -- the fix here is exactly what that
    earlier note already said would be needed, arriving one context later than it could have.
*   **Deviation 2: real per-scene-unit `THREE.Box3` framing was chosen over simply rescaling the
    hardcoded constants by 1000x.** A pure "divide the old constants by 1000" fix would have matched
    today's board-driven scale but silently broken again the next time enclosure sizes vary
    meaningfully (a tiny manual box vs. a large board) or if the underlying unit-scale ever changes
    again -- the same class of bug repeating. Computing the frame from whatever mesh is actually
    loaded is real, slightly more work, but correct independent of scale, matching this repo's own
    preference for deriving from real data over a second hand-tuned constant.
