# CTX-321.1: Implementation Context: Provider Configuration Backend

> **Spec Reference:** Links to [SPEC-321](../specs/SPEC-321-provider-configuration-ui.md)

Phase 1 of 2: the real wire, tested end to end, with no UI on top yet. Closes the three gaps
`SPEC-321` §2.1 found by reading the installed code -- the frontend type never carried
`providers`/`provider_roles`, `daemon.py` never read either field into `CONFIG`, and a custom
record's `api_key_ref` couldn't actually be saved at all. Phase 2 (`CTX-321.2`) builds the real
editor on top of what this phase makes reachable.

## 1. Feature Definition & Execution Plan

### Phase 1: Rust -- secret validation and syncing become config-aware
*   [x] `secrets.rs`'s `validate_known_key` split into an `AppHandle`-free core
    (`validate_known_key_against(key, custom_refs)`) and an `AppHandle`-dependent wrapper that loads
    the real current `config.json` to gather custom `api_key_ref`s -- the same split `config.rs`
    already established for `ensure_output_dir`/`resolve_output_dir`. A key is valid if it's in the
    fixed `KNOWN_SECRET_KEYS` **or** named by some currently-saved `providers[].api_key_ref` --
    meaning a record must be saved before its own key can be, by construction, not by convention.
*   [x] `daemon.rs`'s `collect_known_secrets` gets the identical split
    (`collect_secrets_for(keys)` / `collect_known_secrets(app)`), unioning the fixed allowlist with
    custom refs from the same config load. Both real call sites (`sync_secrets_to_daemon`,
    `spawn_daemon`) already had a real `AppHandle` in scope -- confirmed by reading each one before
    changing the signature, not assumed.
*   [x] Real tests added for the custom-ref acceptance/rejection path, plus a real OS-keychain round
    trip for a key name that isn't in `KNOWN_SECRET_KEYS` at all (`collect_secrets_for_reads_a
    _custom_ref_that_is_not_a_known_vendor_key`) -- proving the mechanism works against the real
    keychain, not just the in-memory logic.

### Phase 2: daemon -- `providers`/`provider_roles` actually reach `CONFIG`
*   [x] `_apply_env_config()` gains the same two lines the existing `llm_provider`/`llm_model`
    reads already have -- both default to `None`/absent exactly like a pre-`SPEC-208` install, so
    `migrate_legacy_config` (real and tested since `CTX-208.2`) does exactly what it already does.
*   [x] `configure_daemon()` gains `providers`/`provider_roles` parameters, following the identical
    "`None` means leave unchanged, otherwise replace wholesale" contract `secrets`/`llm_provider`/
    `llm_model` already use -- `SPEC-208` §2.5's "always the complete current set" rule, applied at
    the `CONFIG` layer rather than left as an unenforced expectation.
*   [x] The initial `CONFIG` dict literal gained explicit `"providers": None, "provider_roles": None`
    keys, so `CONFIG.get(...)` is never relying on `_apply_env_config` having already run.

### Phase 3: a new route -- the resolved provider set, for a future UI to render
*   [x] `llm.get_provider_records` -- calls `llm_providers.migrate_legacy_config` then
    `_resolve_provider_records` against the real `CONFIG` (both real and tested since `CTX-208.1`/
    `.2`, not new logic), returning `{records, provider_roles, provider_roles_saved}`. `records`
    filters out `"managed"` unconditionally -- `SPEC-208` §2.2.3 already stops a `config.json` entry
    from *claiming* that id; this route is the one place that stops it from ever being *rendered*,
    a distinct guarantee `_resolve_provider_records`'s own contract never made on its own.
*   [x] `provider_roles` in the response is always the **migrated** view, not a raw, possibly-empty
    `CONFIG["provider_roles"]` -- so a pre-`SPEC-208` install sees its real, resolved binding
    immediately (`SPEC-321` §2.5's migration display), distinguished from a real explicit save via
    the separate `provider_roles_saved` boolean.
*   [x] Registered as a synchronous route (a dict lookup and a filter, no network, no LLM call) --
    not in `ASYNC_ROUTES`.

### Phase 4: frontend -- the typed wire, no UI yet
*   [x] `settings.ts` gains a real `ProviderRecord` interface (mirroring `llm_providers.py`'s own
    `ProviderRecord` TypedDict) and a `ModelRole` type; `DaemonConfig` gains `providers`/
    `provider_roles` fields it should have had since `CTX-208.1`.
*   [x] `getProviderRecords()`/`saveProviderConfig()` -- the same `dispatch`/`saveConfig` pattern
    `getCapabilities()`/`setLlmProviderAndModel()` already establish, not a new IPC convention.
    `saveProviderConfig` sends both `providers` and `provider_roles` as a complete pair, matching
    the daemon-side contract Phase 2 just built.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: `llm.get_provider_records` returns the *migrated* `provider_roles`, not the raw
    `CONFIG["provider_roles"]` value, with a separate `provider_roles_saved` boolean distinguishing
    the two.**
    *   *Reasoning:* `SPEC-321` §2.5 asks for a real migration display -- a pre-`SPEC-208` install
        (no `provider_roles` ever saved) should see what it would actually get today, not a blank
        map that reads as "nothing is configured." Returning the raw value would have pushed this
        computation onto a future frontend, duplicating `migrate_legacy_config`'s own logic in
        TypeScript -- exactly the kind of drift risk `SPEC-321` §2.4 already reasoned about for the
        presets themselves.
    *   *Impact:* the response carries both the resolved value and whether it's a real save, so
        `CTX-321.2`'s editor can render "currently bound to X (not yet saved)" without needing its
        own copy of the migration rule.
*   **Deviation 2: `_apply_env_config()`'s new lines have no dedicated test.**
    *   *Reasoning:* no existing test exercises this function at all -- it runs once at import time
        against a real env var, and isolating that without re-importing the whole `daemon` module
        (which every other test in this suite also imports) wasn't worth inventing new test
        infrastructure for two lines that are a direct structural copy of two already-tested,
        adjacent ones.
    *   *Impact:* named explicitly here rather than silently assumed covered -- if this ever
        regresses, it would surface as `CONFIG["providers"]` staying `None` on a real daemon spawn
        despite a real `config.json` carrying real records, not as a failing unit test.
