# CTX-315.3: Parts/Symbols Section Split

> **Spec Reference:** Links to [SPEC-315](../specs/SPEC-315-library-browsing-and-organization.md)

## 1. Feature Definition & Execution Plan

Real, confirmed bug shown in a live screenshot: the user's Library, with exactly one saved
component (the ATtiny85), showed a "Datasheets / Pins (2)" section listing TWO entries -- the real
Part, and `DIP-8_8pin`, which looked like an unrelated second component. Root cause: `LibraryArea`
rendered `parts` and `symbols` as siblings under one combined section/count. `DIP-8_8pin` is the
ATtiny85's own generated Symbol record -- `library.save_confirmed_part`'s real symbol_id convention
(`<package>_<pincount>pin`) -- not a second Part.

`CTX-315.2`'s own module doc comment already states the real principle this violated, just never
applied it to Symbols: a Footprint is "a real, independently-shared object... never bundled with
whichever Part happens to reference it," rendered in its own separate section. A Symbol shares that
same real property and should have gotten the same treatment. Fixed by splitting into two real,
separately-labeled sections ("Parts", "Symbols"), matching Footprints' own already-correct
precedent.

### Phase 1: `LibraryArea.tsx`
*   [x] Combined "Datasheets / Pins" section split into "Parts" and "Symbols", each with its own
    real count and empty state.

### Phase 2: tests
*   [x] `LibraryArea.test.tsx`: a real test proving Parts and Symbols render under two distinct
    labeled sections, not one merged count; the existing empty-state test updated for both new
    labels.

## Files
