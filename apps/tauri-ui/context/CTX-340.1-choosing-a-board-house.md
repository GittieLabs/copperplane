# CTX-340.1: Implementation Context: Choosing a Board House, and Seeing What It Changes

> **Spec Reference:** Links to
> [SPEC-340](../specs/SPEC-340-ordering-this-board-from-a-real-house.md)

## 1. Feature Definition & Execution Plan

`SPEC-114` is built, merged, and verified against the frozen sidecar. Not one line of it is
reachable by a person. This context is the whole distance between those two facts, and it is
mostly wiring — which is the point. `CTX-114.1` deliberately put the dangerous, measured work
behind three routes so that this part could be small.

The order below front-loads the two things that are *not* wiring: persistence (because a profile
belongs to a project, and getting that wrong means a user silently checks board B against board A's
house) and the result surface's three states (because `SPEC-340` section 2.1 names that as the only
real design decision in the spec).

### Phase 1: The profile belongs to the project

*   [x] Persist the chosen profile on the project record in `library_store`, alongside `intent` and
    `last_results`, round-tripping through `load_project`/`save_project` so `CTX-312.1`'s
    pointer/manifest routing comes free rather than being re-derived.
*   [x] A `project.set_fabrication_profile` route that validates before it stores. Storing an
    unvalidated profile would push the failure to review time, where it reads as a broken check
    rather than a bad number.
*   [x] A profile travels with a linked project folder, and does not leak between projects. Test
    both directions explicitly — this is the failure that would silently check the wrong board
    against the wrong house.

### Phase 2: The client

*   [x] `lib/fabricationReview.ts` wrapping the three routes, with the result types mirrored from
    the daemon rather than re-guessed. `boardAdvisor.ts` already types `ignored_checks` as
    `{ key, description }`, which is the shape the daemon actually returns — reuse it, do not
    redeclare it differently.
*   [x] `fabrication.review_board` goes through `submitJob` from `lib/ipc.ts`, like `checkBoard`
    does. It is in `ASYNC_ROUTES` and takes roughly five seconds.
*   [x] Surface `SidecarDiscarded` as its own error, distinct from a transport failure. The user
    needs to know their rules did not run, not that something went wrong.

### Phase 3: Choosing the house

*   [x] A picker offering the unbranded starting point or the user's own numbers, per project.
*   [x] Each field shows the date it was recorded and whether it has been confirmed. The bundled
    profile ships with all nine fields unconfirmed precisely so this has something true to say.
*   [x] Name the process the numbers describe, next to the numbers — `SPEC-340` section 3's
    mitigation for the too-strict-profile risk.
*   [x] Say plainly which recorded numbers can never be checked, and why. The daemon already returns
    the sentences via `describe_unenforceable`; render them rather than inventing new wording.
*   [x] An empty state for a project with no linked board, which is honest rather than an error
    (`SPEC-114` section 2.9).

### Phase 4: The before and after

*   [x] Both counts, always together. Never the after-count alone: `SPEC-340` section 2 is explicit
    that "27 findings" on its own reads as a broken board.
*   [x] Group findings by what the fab would do — built silently wrong first, then rejected, then
    cosmetic. The daemon ranks them already; preserve that order rather than re-sorting.
*   [x] The three verification states, which is section 2.1's named decision. `applied` shows the
    result. `indeterminate` shows the result **and** says the rules could not be observed taking
    effect, without reading as either a pass or a failure. A discarded sidecar shows no result at
    all, because there is nothing trustworthy to show.
*   [x] Render `not_checked` in full: ignored checks, profile rules gated off by them, and
    unenforceable fields. Reuse `ViolationsList`'s existing ignored-checks treatment from
    `SPEC-332`.
*   [x] No string anywhere in this phase tells the user the board is good to order.

### Phase 5: Into the PCB area, and in front of a person

*   [x] Mount in `BoardAdvisor`, which already owns board selection and stays mounted across tab
    switches.
*   [x] Reset profile state on a genuine project switch, not a tab switch — the distinction
    `BoardAdvisor` already draws for its check result, and for the same reason.
*   [ ] **A real human click-through in the running native window**, against the tutorial board,
    with the outcome recorded here. Not the automated suite. `SPEC-340` section 5 states the bar:
    someone watches the count go from 4 to 27 and can say which findings would have come back as a
    working board that was quietly wrong. Until that happens this context is not done, however
    green the tests are.

## 4. Plan Drift & Architectural Changes

*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Deviation 1: `dispatch_to_daemon_typed` does not exist.** The client was first written
    against an invented Tauri command. The real convention is `dispatch(method, params)` from
    `lib/ipc.ts` with an explicit `response.error` check, exactly as `listOpenBoards` does, and
    `submitJob` only for `ASYNC_ROUTES` members. Caught by reading `boardAdvisor.ts` rather than by
    a test, because a test written against the same wrong assumption would have mocked it happily.
    The same pass caught `handle.completion`, which is really `handle.result`.

*   **Deviation 2: `@testing-library/user-event` is not a dependency of this app.** Every existing
    component test drives clicks with `fireEvent` from `@testing-library/react`. Switched to match
    rather than adding a dependency to make one new test file's style work.

*   **Deviation 3: the "never says good to order" guard was too blunt to ship as written.** It
    initially forbade the bare word `passed`, which matched the ignored-checks note -- "your board
    can look clean because a check is off rather than because it passed" -- a sentence that says the
    *opposite* of a verdict. It then caught `ready to order` inside the disclaimer "that is not the
    same as a board being ready to order". Rather than weaken the guard with negative lookbehind,
    the component copy was reworded to "not a verdict on the whole board", so the assertion can stay
    a plain substring check. A guard that has to understand negation is a guard that will eventually
    be wrong.

*   **Deviation 4: adding a project field broke an exhaustive-shape test, correctly.**
    `test_library_store`'s `test_003_an_unlinked_project_still_behaves_exactly_as_before_ctx_312_1`
    asserts the entire loaded record, and its comment names every field added since `CTX-312.1`.
    `fabrication_profile` was added to both, following that pattern -- this test is doing its job,
    and the right response is to extend the list deliberately, not to loosen the assertion.

*   **Observed, not caused by this work:** `test_llm_providers`'
    `test_002_real_google_chat` failed once during a full-suite run with
    `TypeError: '>' not supported between instances of 'NoneType' and 'int'` -- Google's live API
    returned `output_tokens: None`. It passed on an isolated re-run, and this branch touches no
    provider code. Flagged as its own task rather than papered over here.

*   **Prediction 1 was half right.** Persistence was indeed where the risk sat, but not for the
    reason predicted: project identity resolution was fine, and the real cost was the exhaustive
    shape test above. The `indeterminate` state, predicted as the harder half, was
    straightforward once the copy was written -- the difficulty was in the wording, not the code.

*   **Prediction 2 is unresolved and must stay that way until someone uses this.** It predicted the
    click-through would find at least one thing the component tests could not. No click-through has
    happened, so the prediction is neither confirmed nor refuted, and this context is not finished.

*   **Prediction 1, recorded before implementation starts:** most of this will be genuinely
    uneventful, because `CTX-114.1` already absorbed the measurement risk. The two places that
    prediction is most likely to be wrong are per-project persistence, where `CTX-110.1` and
    `CTX-304.2` both found real bugs in how project identity resolves, and the `indeterminate`
    state, which has no precedent in this UI to copy.
*   **Prediction 2:** the click-through in Phase 5 will find at least one thing the component tests
    cannot. That has happened in `CTX-109.3`, `CTX-301.2`, `CTX-305.2`, `CTX-306.x` and
    `CTX-311.16`, and there is no reason this surface is the exception. If it finds nothing, that
    is itself worth recording, because it would be the first time.

## 5. What was verified, and what was not

**Verified.** The full daemon suite (1252 tests) and the full frontend suite (885 tests, 51 files)
are green, and `tsc --noEmit` is clean. The four routes this surface depends on were driven into the
**rebuilt frozen sidecar** over JSON-RPC: `fabrication.generic_profile` returns its unbranded
starting point, and `project.set_fabrication_profile` fails with a storage-configuration error
rather than `-32601`, which is what proves it is registered. Both probes carried a negative control
-- a deliberately misspelled route returning `-32601` -- so a pass means the probe could have
detected a missing route.

**Not verified, and this is the one that matters.**

**Nobody has used this.** `SPEC-340` section 5 sets the bar explicitly: a person who has never heard
the phrase "annular ring" picks a profile on the tutorial board, watches the count go from 4 to 27,
and can say out loud which of those findings would have come back as a working board that was
quietly wrong. That has not happened. Phase 5's last checkbox is deliberately still unticked.

This is not a formality. `SPEC-302` shipped with every capability test passing and nobody able to
look up a part; `CTX-109.3`, `CTX-301.2`, `CTX-305.2` and `CTX-311.16` each found real bugs that
only a human clicking found. The component tests here assert wording and structure against fixtures
copied from real daemon output, which is worth something and is not the same thing.

Running the frontend in a browser would not close this gap either: the Tauri `invoke` bridge is not
present there, so every `fabrication.*` call would fail and the surface would render its empty
state. Reporting that as verification would be precisely the kind of check that cannot fail.

**Also not verified:** everything `CTX-114.1` listed -- one machine, one board, KiCad 10.0.3, macOS
aarch64 -- still holds, unchanged, underneath this.
