# CTX-340.1: Implementation Context: Choosing a Board House, and Seeing What It Changes

> **Spec Reference:** Links to
> [SPEC-340](../specs/SPEC-340-ordering-this-board-from-a-real-house.md)

## 1. Feature Definition & Execution Plan

`SPEC-114` is built, merged, and verified against the frozen sidecar. Not one line of it is
reachable by a person. This context is the whole distance between those two facts, and it is
mostly wiring — which is the point. `CTX-114.1` deliberately put the dangerous, measured work
behind three routes so that this part could be small.

The order below front-loads the two things that are *not* wiring: persistence (because a profile
belongs to a project, and getting that wrong means a user silently checks board B against board A's
house) and the result surface's three states (because `SPEC-340` section 2.1 names that as the only
real design decision in the spec).

### Phase 1: The profile belongs to the project

*   [ ] Persist the chosen profile on the project record in `library_store`, alongside `intent` and
    `last_results`, round-tripping through `load_project`/`save_project` so `CTX-312.1`'s
    pointer/manifest routing comes free rather than being re-derived.
*   [ ] A `project.set_fabrication_profile` route that validates before it stores. Storing an
    unvalidated profile would push the failure to review time, where it reads as a broken check
    rather than a bad number.
*   [ ] A profile travels with a linked project folder, and does not leak between projects. Test
    both directions explicitly — this is the failure that would silently check the wrong board
    against the wrong house.

### Phase 2: The client

*   [ ] `lib/fabricationReview.ts` wrapping the three routes, with the result types mirrored from
    the daemon rather than re-guessed. `boardAdvisor.ts` already types `ignored_checks` as
    `{ key, description }`, which is the shape the daemon actually returns — reuse it, do not
    redeclare it differently.
*   [ ] `fabrication.review_board` goes through `submitJob` from `lib/ipc.ts`, like `checkBoard`
    does. It is in `ASYNC_ROUTES` and takes roughly five seconds.
*   [ ] Surface `SidecarDiscarded` as its own error, distinct from a transport failure. The user
    needs to know their rules did not run, not that something went wrong.

### Phase 3: Choosing the house

*   [ ] A picker offering the unbranded starting point or the user's own numbers, per project.
*   [ ] Each field shows the date it was recorded and whether it has been confirmed. The bundled
    profile ships with all nine fields unconfirmed precisely so this has something true to say.
*   [ ] Name the process the numbers describe, next to the numbers — `SPEC-340` section 3's
    mitigation for the too-strict-profile risk.
*   [ ] Say plainly which recorded numbers can never be checked, and why. The daemon already returns
    the sentences via `describe_unenforceable`; render them rather than inventing new wording.
*   [ ] An empty state for a project with no linked board, which is honest rather than an error
    (`SPEC-114` section 2.9).

### Phase 4: The before and after

*   [ ] Both counts, always together. Never the after-count alone: `SPEC-340` section 2 is explicit
    that "27 findings" on its own reads as a broken board.
*   [ ] Group findings by what the fab would do — built silently wrong first, then rejected, then
    cosmetic. The daemon ranks them already; preserve that order rather than re-sorting.
*   [ ] The three verification states, which is section 2.1's named decision. `applied` shows the
    result. `indeterminate` shows the result **and** says the rules could not be observed taking
    effect, without reading as either a pass or a failure. A discarded sidecar shows no result at
    all, because there is nothing trustworthy to show.
*   [ ] Render `not_checked` in full: ignored checks, profile rules gated off by them, and
    unenforceable fields. Reuse `ViolationsList`'s existing ignored-checks treatment from
    `SPEC-332`.
*   [ ] No string anywhere in this phase tells the user the board is good to order.

### Phase 5: Into the PCB area, and in front of a person

*   [ ] Mount in `BoardAdvisor`, which already owns board selection and stays mounted across tab
    switches.
*   [ ] Reset profile state on a genuine project switch, not a tab switch — the distinction
    `BoardAdvisor` already draws for its check result, and for the same reason.
*   [ ] **A real human click-through in the running native window**, against the tutorial board,
    with the outcome recorded here. Not the automated suite. `SPEC-340` section 5 states the bar:
    someone watches the count go from 4 to 27 and can say which findings would have come back as a
    working board that was quietly wrong. Until that happens this context is not done, however
    green the tests are.

## 4. Plan Drift & Architectural Changes

*Document any deviations from the original SPEC definitions encountered during build time.*

*   **Prediction 1, recorded before implementation starts:** most of this will be genuinely
    uneventful, because `CTX-114.1` already absorbed the measurement risk. The two places that
    prediction is most likely to be wrong are per-project persistence, where `CTX-110.1` and
    `CTX-304.2` both found real bugs in how project identity resolves, and the `indeterminate`
    state, which has no precedent in this UI to copy.
*   **Prediction 2:** the click-through in Phase 5 will find at least one thing the component tests
    cannot. That has happened in `CTX-109.3`, `CTX-301.2`, `CTX-305.2`, `CTX-306.x` and
    `CTX-311.16`, and there is no reason this surface is the exception. If it finds nothing, that
    is itself worth recording, because it would be the first time.
