# CTX-303.3: Settings Tier 3: Copy Diagnostics

> **Spec Reference:** Links to [SPEC-303](../specs/SPEC-303-settings-ui.md)

The last remaining piece of `SPEC-303`: "one button bundling capability flags, the daemon's log
file location, and relevant versions to the clipboard" (§2). Scoping this found that none of the
three pieces of data it needs were actually exposed anywhere yet, and the clipboard plugin wasn't
installed on either side.

## 1. Feature Definition & Execution Plan

**Ground truth this plan is built on** (read directly from source, not assumed):
*   `daemon.py`'s resolved log file path was a local variable inside `_configure_logging()`, never
    stored anywhere else, never returned from a function, never in `_detect_capabilities()`.
*   No route or Tauri command returned the app version anywhere; it existed only as static strings
    in `Cargo.toml`/`tauri.conf.json`/`package.json`, none reachable from the frontend.
*   `kicad.get_version` (`SPEC-103`) already returns a real version string when KiCad is reachable,
    and already raises when it isn't -- reused as-is, wrapped in a try/catch rather than duplicated.
*   `freecad_bridge.py` has no version capability at all, only a presence check
    (`find_freecadcmd()`) -- FreeCAD's own version is out of scope for this pass, reported as
    reachable/not-reachable only, matching what's actually available.
*   Neither `@tauri-apps/plugin-clipboard-manager` nor any Rust clipboard crate was installed.

### Phase 1: Expose the missing data
*   [x] `daemon.py`: `_configure_logging()` now stores the resolved log path in a module-level
    `_LOG_FILE_PATH` (`None` if only `stderr` logging is active, e.g. a read-only log dir --
    reported honestly, not papered over). `_detect_capabilities()` (feeding both `daemon.ready` and
    `daemon.get_capabilities`) gained `log_path` and `python_version` fields.
*   [x] `core/tauri-rust`: new `get_app_version` command, a compile-time `env!("CARGO_PKG_VERSION")`
    constant -- no I/O, no chance of disagreeing with what actually got compiled.

### Phase 2: Clipboard plugin
*   [x] Installed `@tauri-apps/plugin-clipboard-manager` (npm) and `tauri-plugin-clipboard-manager`
    (cargo); registered the plugin in `lib.rs` and granted `clipboard-manager:allow-write-text` in
    `capabilities/default.json`.

### Phase 3: The diagnostics bundle + UI
*   [x] `lib/settings.ts`: `getAppVersion()` (wraps the new command) and `copyDiagnostics()` --
    fetches capabilities + app version concurrently, looks up KiCad's real version only when
    `kicad_available` is true (degrading to "unreachable" on failure rather than failing the whole
    bundle), and writes a plain-text summary to the clipboard via `writeText`.
*   [x] `components/Settings.tsx`: a "Diagnostics" section with a single "Copy Diagnostics" button
    and a success/error confirmation, following the same pattern Tier 1/2 already established.

## 4. Plan Drift & Architectural Changes

*   **Non-deviation, confirmed as designed: FreeCAD's version is not included.** `freecad_bridge.py`
    has no version-detection capability at all, only `find_freecadcmd()`'s presence check. Adding a
    real FreeCAD version probe (invoking `freecadcmd` with a version flag and parsing its output)
    would be new scope beyond what `SPEC-303` §2 actually asked for ("relevant versions" was read as
    "the ones already available," not "build a new probe for every tool"). The diagnostics bundle
    reports FreeCAD as reachable/not-reachable only, same as Tier 2's own connectivity panel.
*   **Non-deviation, confirmed as designed: KiCad's version lookup degrades gracefully, doesn't
    block the bundle.** `kicad.get_version` raises when KiCad isn't actually reachable (confirmed
    directly, see below) -- `copyDiagnostics()` wraps that call in a try/catch and reports
    "unreachable" rather than letting one unavailable tool prevent copying anything at all.
*   **Resolved, not left open: the 3 KiCad/Google failures noted when this PR was opened were
    transient, confirmed by re-running.** At the time this context's own commit landed, the full
    `services/python-daemon` suite had 2 real-KiCad-connectivity errors (IPC server not reachable
    despite the app running) and 1 Google API call failure, in files this context never touched
    (`test_kicad_bridge.py`, `test_kicad_write.py`, `test_async_jobs.py`, `test_llm_providers.py`).
    Re-run on request after merge: all three passed, and the full suite is 98/98 green (1 expected
    skip, no OpenAI key). Recorded as transient rather than a real regression, and specifically
    *not* left as a standing caveat once it was actually checked.
