# CTX-311.3: Frontend: wider Enclosure layout, lid toggle, camera presets, mounting-hole honesty in the UI

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

The first frontend slice of SPEC-311, wiring the backend work `CTX-311.1`/`CTX-311.2` already shipped
into the real Enclosure UI. Directly answers three of the user's own original requests: "every tab
view has a fixed width which is a true waste [of] screen real estate... An [sic] large view of an
enclosure is a big plus", "we would have generated 2 separate bodies in freecad for this and would
like to have an option in the preview to show/hide the lid", and "I want to include some presets to
show the top, bottom, rotate left/right on axis increments." Deliberately does not touch the
last-open-board list pattern (`EnclosurePanel`'s `useEffect`-on-mount scan already matches
`BoardAdvisor`'s own pattern -- confirmed by reading the code before assuming more work was needed,
not just from the spec's own older wording) or the board-inside-enclosure overlay (needs its own
context: it composes two independently-sourced `.glb`s from different daemon routes, real, separate
scope).

## 1. Feature Definition & Execution Plan

### Phase 1: wider Enclosure layout
*   [x] `EnclosurePanel.tsx`'s own root changed from `max-w-md` (448px, shared by every other tab's
    own root) to a real two-column `max-w-6xl` layout: a fixed-width controls column (picker, params,
    lid toggle, Generate button) and a flexible results column (warnings, the 3D preview, action
    buttons) that grows to fill the extra room. No other tab's layout touched -- SPEC-311 §1's own
    Non-Goal names a repo-wide shell redesign as a deliberate, separate follow-up.
*   [x] `EnclosureViewer.tsx`'s own `Canvas` grew from a fixed `h-64` to `h-96` -- a real, direct
    "bigger 3D view" benefit of the wider layout, not decorative.

### Phase 2: lid toggle
*   [x] `lib/enclosure.ts`: `EnclosureParams` gains `lid?`/`lid_thickness_mm?`; `EnclosureResult`
    gains `lid_glb_path?`/`lid_step_path?`/`no_mounting_holes_found?` -- mirroring the real backend
    shape `CTX-311.1`/`CTX-311.2` already ship, previously untyped on the frontend side.
*   [x] `EnclosurePanel.tsx`: an "Add a lid" checkbox in Board mode only (lid is board-driven-only on
    the daemon side -- the checkbox simply doesn't exist in Manual mode, rather than existing and
    silently failing), revealing an optional lid-thickness field when checked.
*   [x] `EnclosureViewer.tsx`: gains real multi-model support -- `lidGlbPath?: string | null` and
    `lidVisible?: boolean` props, each independently loaded via its own `useGlbScene` call and
    composited as a second `<primitive>` in the same `<Canvas>`. A `null`/absent `lidGlbPath` is a
    real, permanent "no lid to load" state (`useGlbScene`'s own docstring), not a load error.
*   [x] A "Show lid" checkbox appears in the results column only when a result's own
    `lid_glb_path` is present, toggling `lidVisible` -- the two independently-loaded models are
    composited in one scene, exactly the "two separately-loaded scenes" approach `CTX-311.2`'s own
    docstring named as the option needing no further scene-graph rework here.

### Phase 3: camera presets
*   [x] `EnclosureViewer.tsx`: `sphericalToCartesian(radius, polar, azimuth)`, a pure, directly
    testable function -- Y-up (matching glTF's own convention, confirmed live in `CTX-311.1`'s own
    research). `DEFAULT_CAMERA_RADIUS`/`DEFAULT_CAMERA_POLAR`/`DEFAULT_CAMERA_AZIMUTH` reproduce the
    viewer's own original `[80, 80, 80]` corner view exactly (verified by a direct test, not just
    asserted).
*   [x] A `CameraPresetControls` toolbar (Top / Bottom / Rotate Left ⟲ / Rotate Right ⟳) sits below
    the `Canvas`, driving the camera via a ref into `OrbitControls` (`controls.object.position.set`
    + `controls.update()`) -- a real, bounded addition alongside the existing free-orbit
    `OrbitControls` (`CTX-301.2`), not a replacement for it. A preset click jumps to a canonical
    view; the user can keep free-dragging from wherever it lands, same as before.

### Phase 4: mounting-hole honesty in the UI
*   [x] `EnclosurePanel.tsx`: a result's `no_mounting_holes_found` (`CTX-311.1`, already returned by
    the daemon route, previously unread by any UI) now renders its own amber warning, distinct from
    the existing `unrecognized_holes` warning -- "No mounting holes were found on this board... the
    enclosure has no standoffs," matching SPEC-311 §2's own named honesty requirement.

### Phase 5: tests
*   [x] `EnclosureViewer.test.tsx`: `sphericalToCartesian` (default view reproduces `[80,80,80]`,
    top/bottom/rotate-quarter-turn geometry), and `useGlbScene(null, ...)` staying `'loading'` with a
    `null` scene rather than erroring.
*   [x] `EnclosurePanel.test.tsx`: lid checkbox only in Board mode; checking it reveals the thickness
    field; submitting sends real `lid`/`lid_thickness_mm` (present, omitted-when-blank, and `false`
    when unchecked); a result with `lid_glb_path` passes it and `lidVisible` through to the (mocked)
    viewer and shows/toggles "Show lid"; a result with no `lid_glb_path` never shows that toggle;
    `no_mounting_holes_found` renders its own warning.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the last-open-board list pattern SPEC-311 §2 named as a gap turned out to already
    be satisfied, confirmed by reading the code before doing any work on it.** SPEC-311 §2's original
    wording (written before `CTX-310.3` shipped) described `EnclosurePanel` as only showing a board
    "once the user has explicitly scanned or picked a file" -- but the current, already-merged
    `CTX-310.3` implementation already calls `listOpenBoards()` in a `useEffect` on mount, identical
    to `BoardAdvisor`'s own pattern. Re-verified directly in this context (via `EnclosurePanel.test.
    tsx`'s own existing "scans for open boards as soon as the screen mounts" test, still passing
    unmodified) rather than assuming the spec's older prose was still accurate and duplicating work
    that was already done.
*   **Deviation 2: the board-inside-enclosure overlay (SPEC-311's other major frontend piece) is
    deliberately out of scope here, not an oversight.** It needs to compose the board's own real
    `.glb` (`kicad.export_board_glb`, `CTX-311.1`) with the enclosure's `.glb` in the *same* scene,
    with real relative positioning (the board sits *inside* the enclosure's cavity, not floating at
    the origin) -- genuinely different, harder work than this context's flat two-independent-models
    compositing (base + lid, both built from the same coordinate origin already). Named as the next
    real frontend context.
*   **Deviation 3: camera presets snap the camera but never re-sync this component's own tracked
    spherical state from a user's free-drag.** After a preset click, the user can keep orbiting
    freely via `OrbitControls`' own internal state; if they click a preset again afterward, it jumps
    from this component's last *preset-set* azimuth/polar, not wherever free-dragging left the
    camera. Matches the user's own stated intent ("presets... to go with the orbiting," not a
    replacement for it) -- named explicitly so a future session doesn't "fix" this as an unintended
    bug.
