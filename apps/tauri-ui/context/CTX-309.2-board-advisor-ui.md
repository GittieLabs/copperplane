# CTX-309.2: Implementation Context: Board Advisor UI

> **Spec Reference:** Links to [SPEC-309](../specs/SPEC-309-board-advisor.md)

The frontend half of `SPEC-309`, following `CTX-309.1`'s backend. Split deliberately, matching
`CTX-308.1`/`CTX-308.2`'s own precedent.

## 1. Feature Definition & Execution Plan

### Phase 1: `boardAdvisor.ts` lib
*   [x] `checkBoard(pcbPath?)`: `submitJob('kicad.check_board', ...)`, matching every other real
    async `kicad.*`/`component.*` route's own established call shape.
*   [x] `pickSchematicFile()`: a real native file picker (`@tauri-apps/plugin-dialog`'s `open`,
    already a dependency -- `settings.ts` already uses it for `SPEC-110`'s folder picker), filtered
    to `.kicad_sch`. `SPEC-309` §2's own confirmed finding (live IPC has no schematic-document
    resolution at all) is exactly why this exists -- `checkSchematic` never attempts
    auto-resolution the way `checkBoard` can.
*   [x] `checkSchematic(schPath)`: always takes an explicit path, no default.

### Phase 2: `BoardAdvisor` component + wiring
*   [x] Replaces the PCB area's `NotBuiltPlaceholder` in `App.tsx` -- that placeholder already
    named `specId="SPEC-309"`, confirming this was already the intended home before this context
    started.
*   [x] Offers **both** Check Board (DRC) and Check Schematic (ERC) from the PCB area, rather than
    splitting DRC into PCB and ERC into Schematic -- the Schematic area's own placeholder already
    names `SPEC-308` as its reserved owner (connection guidance, not board-level ERC), so splitting
    ERC into that tab would collide with already-planned content instead of extending it.
*   [x] Two independent result sections (Board/Schematic), each with its own checking/result/error
    state -- checking one never clears or affects the other's already-shown result.
*   [x] Each violation renders KiCad's own real `description` plus the real `explanation`/
    `suggested_fix` `CTX-309.1`'s pipeline already produced, a severity label (color-coded, no
    emoji), and its `sheet_path` when present (ERC only). A `truncated_count > 0` is shown
    explicitly ("+N more violation(s) not shown"), never silently dropped.
*   [x] A clean result (`violations: []`) renders an honest "No violations found." message, not an
    empty section that looks broken.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: a real block-comment bug caught by `tsc`, not by review -- a literal
    `*/` substring inside a JSDoc comment (`kicad.*/component.*`) closed the comment early,
    producing three cascading real TypeScript parse errors.** Fixed by rewording the comment to
    avoid the asterisk-slash sequence entirely. A small, mechanical thing, but worth naming: `tsc -b`
    is what caught it, not a human reading the file -- exactly the value of running the real
    typecheck before considering a phase done, not just eyeballing the diff.
*   **Deviation 2: both ERC and DRC live in the PCB area, not split across PCB/Schematic --
    a real scope decision, not an oversight.** `SPEC-309` §2 itself only says the frontend goes
    "most naturally [in] a new area of the shell... rather than another sub-panel inside Part
    Detail," without specifying which area for which check. Reading `App.tsx`'s own existing
    placeholders directly resolved it: the PCB area already named `specId="SPEC-309"`, and the
    Schematic area already named `specId="SPEC-308"` (reserved for connection guidance). Splitting
    ERC into Schematic would have meant either colliding with `SPEC-308`'s own reserved space or
    guessing at how the two features should share one tab -- neither was this context's call to
    make unilaterally, so both checks live together under PCB instead, where the reservation was
    already unambiguous.
*   **Deviation 3: no live click-through in the real running Tauri window this session --
    consistent with this project's own documented, recurring verification gap** (`CTX-308.5`
    Plan Drift Deviation 4 names the same gap for its own UI work). Every real behavior is verified
    through Testing Library against the real component tree with real mocked lib calls, and the
    lib calls themselves route to routes `CTX-309.1` already verified for real (live `kicad-cli`,
    live IPC, live LLM). What's specifically unverified: the real native file-picker dialog opening
    and behaving as expected, and the real visual layout in the actual app window. Stated
    explicitly, not silently omitted.
