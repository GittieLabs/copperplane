# CTX-306.1: Component Discovery: search, ranking, and the disambiguation card

> **Spec Reference:** Links to [SPEC-306](../specs/SPEC-306-component-discovery.md)

Builds the first real slice of `SPEC-306`: a free-text search that returns ranked candidates with a
confidence signal, a real disambiguation card in the Components area (replacing `SPEC-305`'s
`NotBuiltPlaceholder` there), and a real datasheet cache -- the one piece of `PRODUCT-PLAN.md` §4's
storage layout `library_store.py` names as "not managed by this module yet." Stops at a confirmed
candidate, per `SPEC-306`'s own non-goal: no pin display, no `library.save_part` call. That's
`SPEC-307`'s job.

This context ran through five full rounds of real, hands-on verification in the live app (not just
this suite's own tests) and a real bug surfaced in every single round. Each is recorded below,
because per `CLAUDE.md`'s own norm, that record is more valuable than a clean-looking diff.

## 1. Feature Definition & Execution Plan

### Phase 1: `component_pipeline.search_components` -- a new agent, not a reuse
*   [x] A new AgentFlow prompt, `agentflow/agents/component_search.prompt.md`, distinct from
    `component_extraction.prompt.md` -- takes a free-text query and returns a JSON array of ranked
    candidates: `{part_number, manufacturer, package, datasheet_url, confidence, rationale}`, where
    `confidence` is one of `"high"|"medium"|"low"` (a closed enum, matching
    `component_extraction.prompt.md`'s own `electrical_type` enum pattern).
*   [x] `search_components(query, secrets=None, provider=None, model=None) -> list[dict]` in
    `component_pipeline.py`: a single standalone `AgentExecutor.run()` call (no `WorkflowExecutor`
    DAG -- there's no deterministic validate step the way `generate_component` has one), reusing
    `_build_agent_executor`'s provider/model override and `_extract_json`'s fence-tolerant parsing.
*   [x] Always returns a list, never auto-selects -- `SPEC-306` §2's own rule: even a single
    high-confidence candidate still requires an explicit confirm.

### Phase 2: `library_store.cache_datasheet` -- closing the named gap
*   [x] `cache_datasheet(part_number, datasheet_url) -> str` in `library_store.py`: a real
    `urllib.request` GET (stdlib) written to `library/datasheets/<part_number>.pdf`.
*   [x] Fails closed with `DatasheetFetchError` on any failure, never writes a partial file.
*   [x] Does not touch `save_part`/`_validate_part_provenance`.

### Phase 3: Wire daemon routes
*   [x] `component.search` and `component.cache_datasheet`, both registered in `ASYNC_ROUTES` (a
    real LLM call, a real network fetch).
*   [x] `component_search` threads `CONFIG["llm_provider"]`/`["llm_model"]` through exactly like
    `kicad_generate_component` already does.

### Phase 4: Components area -- real search UI
*   [x] `apps/tauri-ui/src/lib/components.ts`: `searchComponents`/`cacheDatasheet`, wrapping the
    two new routes via `submitJob` (both are async-registered, so `dispatch` alone would only ever
    return `{job_id}`).
*   [x] `apps/tauri-ui/src/components/ComponentDiscovery.tsx`: search box, ranked candidate list,
    explicit "This one" confirm per candidate, a confirmed state naming `SPEC-307` as not built yet.
*   [x] `App.tsx`'s Components area tab renders `<ComponentDiscovery/>` instead of
    `NotBuiltPlaceholder`.

## 4. Plan Drift & Architectural Changes

Five real bugs, found across five separate rounds of live-app verification, none visible from this
suite's own tests alone at the time they were found:

*   **`component_search.prompt.md`'s `max_tokens: 1024` truncated Gemini's response mid-JSON on the
    app's actual configured provider (Google) roughly 60% of the time.** Real search calls against
    Anthropic never showed this (its responses ran shorter); only testing against the real,
    Settings-configured provider surfaced it. Fixed by raising to `2048`, matching
    `component_extraction.prompt.md`'s own budget -- confirmed 6/6 real Google calls succeed after.
    `TEST-002b` guards this specific regression going forward.
*   **The prompt's own "fall back to the manufacturer's site root URL when uncertain" instruction
    was actively counterproductive.** A real search+cache loop found every candidate in several real
    runs pointing at `www.microchip.com/en-us/product/...` -- a marketing page sitting behind Akamai
    bot protection that rejects any plain HTTP client outright, browser-spoofed headers included.
    Rewritten to always prefer a best real guess at the *direct document* URL instead, and to note
    that multiple parts sharing one family datasheet is correct, not a reason to invent distinct
    URLs. 17/17 real fetches succeeded in the verification round immediately after.
*   **This Python build's own baked-in default SSL cert path is invalid on any real machine.** It's
    a path from the build's own CI runner (`/Users/runner/work/...`), so `urlopen`'s default context
    failed `CERTIFICATE_VERIFY_FAILED` on every real HTTPS host. Fixed by using `certifi`'s real CA
    bundle explicitly (already an installed transitive dependency; promoted to a direct one).
    `TEST-004b` is a real HTTPS fetch specifically because the plain-HTTP `_OneShotServer` tests
    above it can never exercise certificate verification at all.
*   **A stalled read after a successful connection raised a bare, uncaught `TimeoutError`.**
    `urlopen`'s connection phase wraps failures in `urllib.error.URLError`; a timeout during
    `response.read()` itself does not go through that wrapping. Found by a real search+cache loop
    against real search-agent output where one candidate's host connected but stalled. Fixed by
    catching `TimeoutError`/`OSError` alongside `URLError`; `TEST-004c` reproduces it with a real
    local server that accepts the connection and then blocks.
*   **Confirming a candidate whose datasheet fetch fails used to block confirmation entirely.**
    Real testing against a genuinely blocked vendor URL showed this would make a correctly-identified
    real part permanently unconfirmable through no fault of the identification itself -- a design
    flaw in the original plan, not just a bug. **Deviation from the original design:** datasheet
    caching is now best-effort, not a gate on confirmation; a failed cache still confirms, with a
    fallback "open externally" action.
*   **Non-deviation, but a real gap closed anyway: no way back to a previous search's candidate list
    without re-running the search.** Reported directly during manual verification. Candidates are no
    longer cleared on confirm; a "Back to results" action restores them.
*   **Plain `<a target="_blank">` does not reliably escape the Tauri webview**, for both the original
    datasheet URL and (worse) a local cached file path, which has no meaningful browser-navigable
    representation at all. `tauri-plugin-shell` was already an unused npm dependency with no Rust
    registration or capability grant -- wired up for real (Cargo dependency, plugin registration,
    `shell:allow-open` permission) rather than working around it with copy-to-clipboard alone (which
    was tried first, at the user's own suggestion, and confirmed too clunky by hand).
*   **`"open": true` in `tauri.conf.json` does not mean unrestricted -- it silently applies a narrow
    built-in regex** (`^((mailto:\w+)|(tel:\w+)|(https?://\w+)).+`) that rejects local absolute file
    paths outright, and only that one signature. Found only after wiring the plugin up and testing
    for real; fixed with an explicit regex covering both `https://` URLs and local absolute paths
    (Unix and Windows), verified against the app's own real paths/URLs with Python's `re` module
    before applying.
*   **State what was not verified:** every fix above was confirmed against this one machine (macOS),
    this one configured provider pairing (Google as primary, Anthropic as the real-test fallback),
    and a handful of real vendor URLs (microchip.com, python.org). Not verified: Windows/Linux path
    handling for the shell-open regex (written to match the pattern, never run on those platforms);
    a second, different bot-protected vendor site (only Akamai/microchip.com was actually observed
    blocking a request); and SPEC-307's eventual real hand-off mechanism, which this context
    deliberately leaves undecided per `SPEC-306` §3.
