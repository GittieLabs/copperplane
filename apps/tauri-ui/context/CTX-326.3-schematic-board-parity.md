# CTX-326.3: Schematic/Board Parity, and the Board as Source of Truth

> **Spec Reference:** Links to [SPEC-326](../specs/SPEC-326-component-volume-placeholders.md) §2.7

`CTX-326.1` and `CTX-326.2` derive an interior height from the **schematic**'s footprints. The
enclosure is built around the **board**. This context surfaces the case where those two files no
longer describe the same design — which silently invalidates every number the previous two
contexts produce.

## The defect this exists for

Found while starting placeholder geometry, which needs component positions and therefore reads the
board for the first time. On the maintainer's own `Hello_World_Blinky`:

| | footprint for `BT1` | courtyard |
| :--- | :--- | :--- |
| schematic | `Battery_Panasonic_CR2032-HFN_Horizontal_CircularHoles` | 22.59 × 20.50 mm |
| board | `Battery_Panasonic_CR2032-VS1N_Vertical_CircularHoles` | 20.61 × 6.23 mm |

A horizontal and a vertical CR2032 holder are different heights, so `CTX-326.2`'s 20.0mm
recommendation — the one the maintainer click-through-verified and which closed `SPEC-326` §1's
motivating case — describes a part that is not on the board. KiCad does not push a schematic edit
to the board; a user runs *Tools → Update PCB from Schematic* by hand. Both files open and render
correctly on their own, so neither KiCad view shows a problem.

Running the same check across the maintainer's three other boards found real desyncs in **all
three** — 7, 21, and 14 issues, including components in the schematic with no footprint on the
board at all. This is not a one-off.

## 1. Feature Definition & Execution Plan

### Phase 1: Detect, using KiCad's own check

`kicad_cli.check_schematic_parity(pcb_path)` wraps `kicad-cli pcb drc --schematic-parity`, which
reads the `.kicad_sch` beside a **closed** board and reports disagreements under its own
`schematic_parity` key. ~1.7s on a real small board.

### Phase 2: Route it

`kicad.check_schematic_parity`, in `ASYNC_ROUTES` because it spawns a subprocess (CTX-314.2's
bug shape). Returns `in_sync`, `issue_count`, and each issue's type/severity/description; KiCad's
internal `items` uuids are dropped as meaningless to a user.

### Phase 3: Say so, above the claim it qualifies

A warning in `SchematicComponents`, rendered **above** the height recommendation, naming
*Tools → Update PCB from Schematic* as a thing the user does in KiCad.

### Phase 4: Make the board the source of truth

`services/python-daemon/kicad_board.py`'s `read_board_footprints` reads the `.kicad_pcb` directly; `kicad.list_board_components`
resolves those footprints the same way the schematic reader does; `kicad.component_envelopes` takes
both paths and prefers the board, reporting `measured_from` so a schematic fallback is never
mistaken for a board measurement.

### Not in this context

*   **Triggering the sync.** The only mechanism is `kipy`'s
    `run_action("pcbnew.EditorControl.importNetlist")` — the action behind the menu item, whose own
    docstring says it is unstable, not for use outside API development, and may have unintended
    side effects. It needs KiCad running with the board focused and opens a modal dialog. That is
    `SPEC-329` territory, deliberately deferred by the maintainer.
*   **Placeholder geometry** — the work this context interrupted. Moves to `CTX-326.4`.
*   **Reading envelopes from the board rather than the schematic.** Arguably the real fix; see
    Plan Drift.

issues, `TEST-016` proves only that the function returns a non-empty list. Both UI branches were

Fixtures are a **pair** of files (`parity_match.kicad_pcb`/`.kicad_sch` and the `parity_mismatch`

issues and the clean case is not clean.

## 4. Plan Drift & Architectural Changes

**Deviation 1 — a hand-rolled comparison was written first, and was wrong.** The first
implementation diffed `sch export bom` footprints against `pcb export pos` packages. On the
maintainer's board it produced **five** findings, of which **one** was real: the other four were
mounting holes `H1`–`H4`, which are board-only by design and carry no schematic symbol at all. A
footprint-name diff cannot tell a legitimate absence from a desync. `kicad-cli pcb drc
--schematic-parity` — found only after the hand-rolled version already "worked" — reports the one
real issue and stays silent about the mounting holes. Deleted rather than kept as a fallback: a
check with a 4-in-5 false-positive rate trains a user to ignore it.

**Deviation 2 — this context did not exist, and displaced the one that did.** `CTX-326.3` was
reserved for placeholder geometry (§2.4). That work needs component positions, which meant reading
the board, which is how the mismatch was found at all. Placeholder geometry moves to `CTX-326.4`.

**Open question this raises and does not answer.** If the enclosure is built around the board, the
envelopes should arguably be read from the **board**'s footprints, not the schematic's — which
would make parity a warning about the schematic view rather than a caveat on the geometry. That is
a source-of-truth change across `CTX-326.1`, `CTX-326.2` and `SPEC-325`, not a detail, and it is
put to the maintainer rather than decided here.

**Deviation 3 — the source-of-truth question was answered, not deferred.** This context originally
reported the mismatch and left the numbers coming from the schematic, recording the source-of-truth
change as an open question. The maintainer settled it directly: use the board, and tell the user to
run *Update PCB from Schematic* if the schematic is the version they want. Stating "the board is
truth" in the UI while still measuring the schematic would have been a lie in the interface, so the
pipeline changed with the wording.

**Deviation 4 — two obvious ways to list a board's components are both wrong, and one fails
silently.** `kicad-cli pcb export pos` honours `exclude_from_pos_files`, so mounting holes,
fiducials and test points can vanish from it — verified by setting the attribute on a fixture and
watching the CSV come back with a header and no rows. Those are exactly the board-only mechanical
parts that decide enclosure fit, so the failure mode is an enclosure that is wrong in the one way
nobody checks. `kiutils` cannot read a full board at all (`IndexError`, as `CTX-314.1` recorded).
`services/python-daemon/kicad_board.py` reads the file instead. Two format traps found against real boards while building
it: values containing parentheses defeat a paren count, and the pre-KiCad-7 `(fp_text reference)`
spelling makes all 31 footprints of a real 2021 board read as `None` — silent, not a crash.

**What this cost the maintainer's own result, stated plainly.** Under board truth their supplied
20.0mm no longer applies — it is keyed to the schematic's horizontal holder, which is not on the
board — so the recommendation drops to 15.515mm and `unknown` rises from 0 to 5. That is correct:
the earlier 20.0mm described a part that is not there. `CTX-326.2`'s click-through result is
therefore superseded rather than preserved, and the motivating case is **re-opened** until a height
is entered for the board's actual `Battery_Panasonic_CR2032-VS1N_Vertical_CircularHoles`. Because
§2.5 keys by footprint, that is 2 entries, not 5.

**Not verified:** no click-through yet — the frozen sidecar carries the route, but nobody has seen
the warning in the running app. Detection has been exercised against four real boards and two
fixtures; the *wording* has only been read in a test.
