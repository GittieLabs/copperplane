# CTX-326.3: Schematic/Board Parity, and the Board as Source of Truth

> **Spec Reference:** Links to [SPEC-326](../specs/SPEC-326-component-volume-placeholders.md) §2.7

`CTX-326.1` and `CTX-326.2` derive an interior height from the **schematic**'s footprints. The
enclosure is built around the **board**. This context surfaces the case where those two files no
longer describe the same design — which silently invalidates every number the previous two
contexts produce.

## The defect this exists for

Found while starting placeholder geometry, which needs component positions and therefore reads the
board for the first time. On the maintainer's own `Hello_World_Blinky`:

| | footprint for `BT1` | courtyard |
| :--- | :--- | :--- |
| schematic | `Battery_Panasonic_CR2032-HFN_Horizontal_CircularHoles` | 22.59 × 20.50 mm |
| board | `Battery_Panasonic_CR2032-VS1N_Vertical_CircularHoles` | 20.61 × 6.23 mm |

A horizontal and a vertical CR2032 holder are different heights, so `CTX-326.2`'s 20.0mm
recommendation — the one the maintainer click-through-verified and which closed `SPEC-326` §1's
motivating case — describes a part that is not on the board. KiCad does not push a schematic edit
to the board; a user runs *Tools → Update PCB from Schematic* by hand. Both files open and render
correctly on their own, so neither KiCad view shows a problem.

Running the same check across the maintainer's three other boards found real desyncs in **all
three** — 7, 21, and 14 issues, including components in the schematic with no footprint on the
board at all. This is not a one-off.

## 1. Feature Definition & Execution Plan

### Phase 1: Detect, using KiCad's own check

`kicad_cli.check_schematic_parity(pcb_path)` wraps `kicad-cli pcb drc --schematic-parity`, which
reads the `.kicad_sch` beside a **closed** board and reports disagreements under its own
`schematic_parity` key. ~1.7s on a real small board.

### Phase 2: Route it

`kicad.check_schematic_parity`, in `ASYNC_ROUTES` because it spawns a subprocess (CTX-314.2's
bug shape). Returns `in_sync`, `issue_count`, and each issue's type/severity/description; KiCad's
internal `items` uuids are dropped as meaningless to a user.

### Phase 3: Say so, above the claim it qualifies

A warning in `SchematicComponents`, rendered **above** the height recommendation, naming
*Tools → Update PCB from Schematic* as a thing the user does in KiCad.

### Phase 4: Make the board the source of truth

`services/python-daemon/kicad_board.py`'s `read_board_footprints` reads the `.kicad_pcb` directly; `kicad.list_board_components`
resolves those footprints the same way the schematic reader does; `kicad.component_envelopes` takes
both paths and prefers the board, reporting `measured_from` so a schematic fallback is never
mistaken for a board measurement.

### Not in this context

*   **Triggering the sync.** The only mechanism is `kipy`'s
    `run_action("pcbnew.EditorControl.importNetlist")` — the action behind the menu item, whose own
    docstring says it is unstable, not for use outside API development, and may have unintended
    side effects. It needs KiCad running with the board focused and opens a modal dialog. That is
    `SPEC-329` territory, deliberately deferred by the maintainer.
*   **Placeholder geometry** — the work this context interrupted. Moves to `CTX-326.4`.
*   **Reading envelopes from the board rather than the schematic.** Arguably the real fix; see
    Plan Drift.

## 4. Plan Drift & Architectural Changes

**Deviation 1 — a hand-rolled comparison was written first, and was wrong.** The first
implementation diffed `sch export bom` footprints against `pcb export pos` packages. On the
maintainer's board it produced **five** findings, of which **one** was real: the other four were
mounting holes `H1`–`H4`, which are board-only by design and carry no schematic symbol at all. A
footprint-name diff cannot tell a legitimate absence from a desync. `kicad-cli pcb drc
--schematic-parity` — found only after the hand-rolled version already "worked" — reports the one
real issue and stays silent about the mounting holes. Deleted rather than kept as a fallback: a
check with a 4-in-5 false-positive rate trains a user to ignore it.

**Deviation 2 — this context did not exist, and displaced the one that did.** `CTX-326.3` was
reserved for placeholder geometry (§2.4). That work needs component positions, which meant reading
the board, which is how the mismatch was found at all. Placeholder geometry moves to `CTX-326.4`.

**Open question this raises and does not answer.** If the enclosure is built around the board, the
envelopes should arguably be read from the **board**'s footprints, not the schematic's — which
would make parity a warning about the schematic view rather than a caveat on the geometry. That is
a source-of-truth change across `CTX-326.1`, `CTX-326.2` and `SPEC-325`, not a detail, and it is
put to the maintainer rather than decided here.

**Deviation 3 — the source-of-truth question was answered, not deferred.** This context originally
reported the mismatch and left the numbers coming from the schematic, recording the source-of-truth
change as an open question. The maintainer settled it directly: use the board, and tell the user to
run *Update PCB from Schematic* if the schematic is the version they want. Stating "the board is
truth" in the UI while still measuring the schematic would have been a lie in the interface, so the
pipeline changed with the wording.

**Deviation 4 — two obvious ways to list a board's components are both wrong, and one fails
silently.** `kicad-cli pcb export pos` honours `exclude_from_pos_files`, so mounting holes,
fiducials and test points can vanish from it — verified by setting the attribute on a fixture and
watching the CSV come back with a header and no rows. Those are exactly the board-only mechanical
parts that decide enclosure fit, so the failure mode is an enclosure that is wrong in the one way
nobody checks. `kiutils` cannot read a full board at all (`IndexError`, as `CTX-314.1` recorded).
`services/python-daemon/kicad_board.py` reads the file instead. Two format traps found against real boards while building
it: values containing parentheses defeat a paren count, and the pre-KiCad-7 `(fp_text reference)`
spelling makes all 31 footprints of a real 2021 board read as `None` — silent, not a crash.

**What this cost the maintainer's own result, stated plainly.** Under board truth their supplied
20.0mm no longer applies — it is keyed to the schematic's horizontal holder, which is not on the
board — so the recommendation drops to 15.515mm and `unknown` rises from 0 to 5. That is correct:
the earlier 20.0mm described a part that is not there. `CTX-326.2`'s click-through result is
therefore superseded rather than preserved, and the motivating case is **re-opened** until a height
is entered for the board's actual `Battery_Panasonic_CR2032-VS1N_Vertical_CircularHoles`. Because
§2.5 keys by footprint, that is 2 entries, not 5.

**Deviation 5 — the click-through found a bug the whole test suite missed, again.** The maintainer
ran the rebuilt app and the panel showed the schematic's 10 components in the table under a summary
counting the board's 14 — "9 measured, 0 stated, 5 still unknown" above a `BT1` whose footprint was
`HFN_Horizontal`, the one that is *not* on the board. Phase 4 changed `component_envelopes` to read
the board and left `setRead` calling `listSchematicComponents`, so the table and the summary read
two different files. Every test passed, because each mock was internally consistent.

The fix is structural rather than careful: `kicad.component_envelopes` now returns the components it
measured, and the UI renders *those*. Two reads of two files cannot be kept in step by discipline;
one read cannot drift. The panel heading follows `measured_from` too, so it no longer says
"Schematic components" above the board's.

**Deviation 6 — the same click-through found a second, older defect in `SPEC-309`'s board check.**
The maintainer said the PCB review looked wrong, and it was. `kicad_check_board` explained
`report["violations"]` alone. On his board that is **0** — while `unconnected_items` held **18
entries, every one severity `error`**, and parity held 1. The tab called the board clean while
KiCad's own DRC dialog would show 19 problems. Both are separate top-level keys in KiCad's JSON, so
neither arrived by accident, and parity only runs when asked for. The route now runs DRC with
`schematic_parity=True`, explains all three kinds, and counts each separately — a user reads "18
unconnected" very differently from one undifferentiated number. This predates this context; it is
fixed here because it was found here.

**Deviation 7 — the reviews could not have worked, and `chat_agents.py` said so.** The maintainer
reported the PCB review finding nothing on a board with real errors. `_check_status_note` feeds the
review and chat agents `Project.last_results[area]`, and its own docstring already named the gap:
*"today `Project.last_results` is only ever populated for `enclosure` — SchematicAdvisor/
BoardAdvisor hold their own check results in local React state only, never persisted anywhere this
route can read. Real ERC/DRC persistence is a separate, later prerequisite."* So the PCB review
agent was handed `"No DRC check result is available this session."` every time, and it has no tool
to run DRC itself — it found nothing because it was shown nothing. Built here as
`project.set_check_result`, a dedicated route rather than a full project save, matching
`set_project_intent`'s reason for existing. Bounded at 25 findings because the record is read
straight into an LLM context; the *counts* stay exact, so an agent is never told a 200-problem
board has 25.

The enclosure review had the same shape for a different reason: `last_results.enclosure` was written
only on **export**, so a generated-but-not-exported enclosure left that agent with nothing but the
project intent. It is now written on generate, and carries what the parts need
(`min_interior_height_mm`, the tallest component, the count with no known height) so the agent can
reason about fit rather than repeat parameters back.

**Deviation 8 — caching the check was the wrong repair, and the maintainer caught it.** Deviation 7
persisted ERC/DRC results so the review agents could read them. He rejected the whole shape: *"The
user could run these checks without our app running and we would not know... Re-running or clicking
review would still just show cached and potentially stale results."* And: *"Even the 'nothing stood
out' message is misleading bc the user may never have run the checks."*

He is right, and the fix is smaller than the one he proposed. He assumed the checks needed KiCad
open and that we would therefore have to cache, date-stamp and warn. **They do not.** `kicad-cli`
reads a closed `.kicad_sch`/`.kicad_pcb` in about two seconds — the same `SPEC-325` §2.2 insight the
Schematic tab already runs on. So `_check_status_note` now *runs the check* rather than reading a
stored one. There is nothing to go stale, no instruction to remember to check first, and no way to
say "nothing stood out" without a real run having happened. The one honest caveat left — the file
lags an editor holding unsaved changes — is stated in the note itself.

`project.set_check_result` from Deviation 7 is kept: `OverviewDashboard` reads `last_results` for
per-area status, which is a legitimately different job from grounding an agent.

**Deviation 9 — the enclosure review is switched off rather than left running.** Also his call:
*"I don't even know what the run review check is supposed to show for the enclosure. This may have
been a planned feature and if so, we need to disable it until we fix it."* It is a real feature —
`chat_enclosure.prompt.md` defines it as physical fit — but its one data tool,
`kicad.get_component_heights`, goes through `kipy` and needs KiCad **running**, so with KiCad closed
it advised from nothing. `SPEC-326` since built a better closed-file source
(`kicad.component_envelopes`); repointing it is `SPEC-331`. Shown as `NotBuiltPlaceholder` rather
than hidden, per `SPEC-305` §2 — a review button that silently advises from no data is worse than
one that admits it is not built.

**Not verified:** the review agents' *output* has not been seen with real findings in context —
only that the findings now reach them (asserted directly against `_check_status_note`, which goes
from the "not available" string to the real JSON). Whether the advice is any good is a separate
question from whether it has anything to work with.

**Not verified:** no click-through of the fixes yet — the frozen sidecar carries the route, but nobody has seen
the warning in the running app. Detection has been exercised against four real boards and two
fixtures; the *wording* has only been read in a test.

**Deviation 10 — the context outgrew its own title, and that is the honest record.** This began as
"detect schematic/board parity". It ends having moved the source of truth to the board, replaced
cached check results with live ones, removed KiCad-must-be-running from all three tabs, built the
DRC teaching surface (`SPEC-332`), rendered the agents' Markdown, and fixed four defects in the
review path. Every one of those came from the maintainer using the app and reporting what he saw;
none was planned here. Splitting it retroactively into five contexts would be tidier and would
misrepresent how the work actually happened.

**Deviation 11 — three of the four review failures were my own fixes.** The review reported
"nothing worth flagging" on a board with two errors; then reported raw findings instead of
explanations; then kept doing so after two more attempts. In order the causes were: the review read
a cache nothing wrote; my own prompt edit contradicted the review-mode rule; a tool that needs KiCad
running, which our own KiCad-optional work had just broken; and finally `max_tokens: 2048` shared
with a thinking model's reasoning. Only the last was pre-existing.

The pattern worth keeping: each of the first three was a **guess at what the model returned**,
because the daemon's stderr goes to a parent with no console when the app is launched from Finder.
Writing the raw response to a file ended it in one round. A log nobody can read is not a diagnostic.
