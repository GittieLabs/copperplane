# CTX-322.1: Model Role Legibility

> **Spec Reference:** Links to [SPEC-322](../specs/SPEC-322-model-role-legibility.md)

Copy, layout and one derived string in `ProviderConfigEditor.tsx`. No daemon change, no schema
change, no IPC change — deliberately, per `SPEC-322` §1 Non-Goals.

## 1. Feature Definition & Execution Plan

### Phase 1: Connect the two levels of the screen

*   [x] A `describeRole` helper resolving each role through its bound provider record to the model
    that will actually be used, rendered under the dropdown as "Uses `<model>`".
*   [x] When the bound record has no model for that role, say so and name the consequence —
    "`<provider>` has no `<role>` model set — this role cannot run" — instead of rendering a
    selection that looks ordinary and fails at call time.

### Phase 2: Say what the section is

*   [x] A "Model roles" heading and one sentence: features ask for a role rather than naming a
    model, and the model comes from the provider record above.
*   [x] Per role, a short line naming the kind of work it does — categories, not an enumerated
    agent list, which would be a second copy of `.prompt.md` frontmatter that goes stale silently.
*   [x] A closing sentence stating that which role a feature asks for is fixed by the app, so the
    question the maintainer actually asked ("address agents by type") is answered on the screen
    rather than left to be re-derived.

### Not in this context

*   **Reasoning-effort / thinking-budget control.** A real gap — provider records carry a model id
    per role and nothing else — but it is new capability needing a `SPEC-208` schema change.
*   **Per-agent model binding.** Contradicts `SPEC-208` §2.3.1's "exactly two roles, deliberately",
    so it needs that argument reopened first, not a UI change.
*   **A test pinning the copy against the real `.prompt.md` role split** (`SPEC-322` §3's named
    drift risk).

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — the reported problem was copy, but the material find was a broken state the
    screen rendered as normal.** The complaint was that the screen is not self-explanatory. While
    reading `ProviderConfigEditor.tsx` to fix that, a worse case appeared: `SPEC-321`'s own record
    editor permits a record with no model for a role (its placeholder literally says "blank = can't
    serve this role"), and the role dropdown then lists that record indistinguishably from any
    other. Every feature asking for that role fails at call time with nothing in Settings hinting
    why. `TEST-003` covers it. Recorded because it widened the change beyond the request — from
    "explain this" to "explain this, and surface a state that was silently invalid".

*   **Deviation 2 — agent categories are described rather than enumerated, against the first
    instinct.** Listing all twelve agents under their roles would have been more concrete and was
    the obvious first draft. Rejected on reading `agent_roles.py`: the binding lives in each
    `.prompt.md`'s own frontmatter, so a list in the UI is a second copy with nothing keeping it
    honest. Categories survive an agent being re-bound; a list would silently lie. The cost is
    vagueness, and `SPEC-322` §3 records that no test pins even the categories to reality.

*   **Non-deviation, checked rather than assumed:** `router` appears in the agents directory listing
    with no `model_role`, which `load_agent_roles` would treat as a load-time error. Checked before
    reporting it as a bug: `router.prompt.md` lives in `agentflow/`, while `load_agent_roles` scans
    `agentflow/agents/`, so it is never parsed — and it is deterministic routing with no LLM on the
    path (`CTX-206.6`), so it correctly has no model role at all. Not a defect.
