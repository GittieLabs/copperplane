# CTX-311.1: Backend foundation: real component-height derivation and mounting-hole honesty

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

The first implementation slice of SPEC-311's much larger scope -- deliberately backend-only, no
lid, no persistence, no frontend refine loop or wider layout, no camera presets. This context
builds the real data foundation SPEC-311 §2 named but didn't yet wire in: real, honest
per-component height derivation from KiCad's own 3D models, a real assembled-board `.glb` export
for the future board-inside-enclosure preview, and an honest "zero mounting holes found" flag. All
three were end-to-end verified live against a real, currently-open KiCad board and a real
`freecadcmd`, not just mocked.

## 1. Feature Definition & Execution Plan

### Phase 1: per-footprint 3D model height derivation
*   [x] `kicad_bridge.py`: `_resolve_3d_model_path` resolves a real KiCad `${VAR}/...` 3D model
    filename to a real path on disk -- the real environment variable first, then real per-OS KiCad
    install locations (the same fallback pattern `kicad_cli.py`'s own `_CANDIDATE_GLOBS` uses),
    never a guessed path.
*   [x] `kicad_bridge.py`: `list_footprint_models()` reads every real footprint's own
    `.definition.models` (kipy's real `Footprint.models`, confirmed against this environment's
    installed kipy) and reports each model's filename, resolved path, and visibility. No
    `freecad_bridge` dependency -- stays independently importable per SPEC-107 §2.
*   [x] `freecad_bridge.py`: `get_step_bounding_box_mm()` reads a real STEP/IGES file via a headless
    `freecadcmd` subprocess (`Part.Shape().read()`) and returns its real bounding box in mm.
*   [x] `daemon.py`: `kicad_get_component_heights()` composes the two into `{"known": [...],
    "unknown": [...]}` -- the same composition pattern `freecad_generate_enclosure` already uses
    for board outline plus mounting holes. Never guesses: no model, a non-STEP model, an unresolved
    path, or a real `freecadcmd` failure all land in `unknown`, not a defaulted number.

### Phase 2: real assembled-board `.glb` export
*   [x] `kicad_cli.py`: `export_board_glb()` wraps `kicad-cli pcb export glb`, mirroring the
    existing `run_erc`/`run_drc` subprocess pattern but writing a real binary file to `--output`
    rather than parsing a JSON report.
*   [x] `kicad_cli.py`: `configure()` extended to accept `output_dir` (the same, already
    Rust-wired SPEC-301 §2 config value `freecad_bridge.configure` already receives) -- this
    module's own executable-discovery `configure()` existed since SPEC-309 but was never actually
    called from `daemon.py`'s `_apply_env_config` until this route needed a real persistent output
    path too.
*   [x] `daemon.py`: `kicad_export_board_glb(pcb_path)` route, `_apply_env_config` wired to call
    `kicad_cli.configure(output_dir=...)`.

### Phase 3: mounting-hole zero-found honesty flag
*   [x] `daemon.py`'s `freecad_generate_enclosure`: `result["no_mounting_holes_found"]` set
    whenever real board data was read (file or live mode) and neither `recognized_holes` nor
    `unrecognized_holes` found anything -- distinct from the existing `unrecognized_holes` warning,
    which only ever fires when *some* NPTH pads exist but aren't recognized. Not set in manual mode
    (no board data to have found holes on).

### Phase 4: route wiring
*   [x] `kicad.get_component_heights` and `kicad.export_board_glb` registered in `_build_routes()`,
    each guarded on its real dependency having imported (SPEC-107 §2), and added to `ASYNC_ROUTES`
    (both run a real subprocess per call).

### Phase 5: tests + real verification
*   [x] Mocked unit tests for `_resolve_3d_model_path`, `list_footprint_models`,
    `kicad_get_component_heights`'s composition/honesty logic, `kicad_export_board_glb`'s
    delegation, the `no_mounting_holes_found` flag, and route-registration guards.
*   [x] Real, no-mocks tests: `get_step_bounding_box_mm` against a real `generate_enclosure`-produced
    `.step` file; `export_board_glb` against the existing `empty_board.kicad_pcb` fixture (real glTF
    magic bytes, respects a configured `output_dir`).
*   [x] Live, end-to-end verification against a real, currently-open KiCad board (see §4 Plan
    Drift) -- not just unit tests in isolation.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: composition lives in `daemon.py`, not inside `kicad_bridge.py`, to preserve
    SPEC-107 §2's independent-import guarantee.** The natural first instinct was to have
    `kicad_bridge.py` call directly into `freecad_bridge.py` to turn a resolved model path into a
    height. Rejected: `kicad_bridge.py`'s own existing routes (`kicad.get_version`,
    `kicad.inject_component`, etc.) must keep working even when `freecad_bridge`'s dependencies
    (`trimesh`) aren't installed, and vice versa -- a broken FreeCAD install shouldn't take down
    KiCad IPC routes. `kicad_bridge.list_footprint_models()` stays a pure, read-only lookup with no
    `freecad_bridge` import; `daemon.py`'s `kicad_get_component_heights()` is the composition layer,
    mirroring exactly how `freecad_generate_enclosure` already composes `kicad_bridge`'s board
    outline/mounting holes with `freecad_bridge.generate_enclosure`.
*   **Deviation 2: VRML (`.wrl`) models are explicitly out of scope for this context, not silently
    treated as millimeters.** SPEC-311 §2 named this as unverified research from the prior spec-
    writing session; rather than assume `trimesh.load()`'s raw VRML coordinate output is already in
    mm (an assumption that would violate this repo's own "never present a guess as fact" norm), this
    context reports any non-`.step`/`.stp` model as `unknown`, same as no model at all. A future
    context can add real, verified VRML unit handling once that convention is actually confirmed
    against a real KiCad-shipped `.wrl` file.
*   **Deviation 3: a model's own `scale`/`rotation`/`offset` transform is not yet applied before
    computing its bounding box.** `get_step_bounding_box_mm` reads the raw STEP shape's own bounding
    box; a real `Footprint3DModel` carries a real transform KiCad applies when rendering it. Named
    explicitly in both the function's own docstring and `kicad_get_component_heights`'s -- a rotated
    or non-unit-scaled component's reported height may not match its true installed height. Every
    real footprint checked live during this context's own verification (`PinHeader_1x04`,
    `LED_SK6812_PLCC4`, `PinHeader_1x19` x2, an axial resistor) happened to be unrotated/unscaled, so
    this gap did not surface in practice here, but it is real, unresolved scope, not an oversight.
*   **Deviation 4: `kicad_cli.configure()` had never actually been called from `daemon.py`, a
    pre-existing gap discovered while wiring `output_dir` for `export_board_glb`.** The function
    existed since SPEC-309 accepting a `path_override` for a "future SPEC-106-style setting" that
    was apparently never followed up on. Fixed alongside the new `output_dir` parameter this context
    actually needed, rather than left dangling a second time.
*   **Live verification performed (per CLAUDE.md's "verify against the real thing" norm), not just
    unit tests:** `list_footprint_models()` against a real, currently-open board reproduced the same
    real per-footprint model paths and the same "4 of 9 footprints have zero attached models" gap
    recorded in `SPEC-311` §2's own research; `get_step_bounding_box_mm` against that same real
    resolved STEP path reproduced the exact same `2.54 x 10.16 x 11.54mm` bounding box; `daemon.
    kicad_get_component_heights()` run end-to-end against the real board produced 5 known / 4
    unknown, matching that same real board's real composition; `kicad_cli.export_board_glb()`
    against that same real board produced a real 634KB `.glb` file, matching `SPEC-311` §2's own
    recorded figure exactly.
