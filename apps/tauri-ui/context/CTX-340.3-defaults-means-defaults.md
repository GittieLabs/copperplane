# CTX-340.3: Defaults Has To Mean Defaults

> **Spec Reference:** Links to
> [SPEC-340](../specs/SPEC-340-ordering-this-board-from-a-real-house.md)

Reported from a screenshot on 2026-09-24. The PCB tab read **"Against KiCad's own defaults"** above
sixteen violations — while the board carried a generated `.kicad_dru` from an earlier board-house
review. The annular minimum in force was that house's **0.15mm**, not KiCad's own, and twelve of the
sixteen were the verification canary that file also carries.

The label was wrong, the numbers were a house's, and nothing on screen said so.

---

## 1. Feature Definition & Execution Plan

### Phase 1: Pin the hazard before fixing it — DONE

*   [x] Prove a leftover sidecar really does change a raw DRC run, so the fix is not speculative.
*   [x] Prove `fabrication_review.baseline` already reads the board without it.
*   [x] Prove stashing does not delete the user's board configuration.
*   [x] Prove a **hand-written** sidecar is left alone — those are the user's real design rules.

### Phase 2: The default check reads the board the way it says it does — DONE

*   [x] The no-profile branch of `kicad.check_board` uses `baseline` rather than `run_drc`.
*   [x] The route guarded on `fabrication_review`, which both its branches now need.

## 4. Deviations & Discoveries (Plan Drift)

*   **The fix already existed one function away, and the codebase had written down the hazard.**
    `fabrication_review.baseline` stashes a generated sidecar, runs DRC, and restores it. Its
    docstring says why, in 2026-09-07's words:

    > *"a leftover file from an earlier run would quietly make the 'before' side of the comparison
    > into another 'after', and the whole proof surface would be a tautology."*

    The **comparison** path knew. The **plain check** called `kicad_cli.run_drc` directly and did
    not. One function understood the trap and its neighbour walked into it, which is a more useful
    thing to record than the one-line diff.

*   **The leftover file is not itself a bug**, and that took working out. `review()` writes the
    sidecar and deliberately leaves it: that file is what makes the house's numbers real inside
    KiCad, so a user who opens the board sees the rules they chose. Deleting it after a review would
    break the feature. What was wrong was the *other* path reading the board as though it were not
    there.

*   **The route needed a guard it had never had.** `kicad.check_board` is registered on `kicad_cli`,
    `component_pipeline` and `kicad_bridge` — but its profile branch has always called
    `fabrication_review.review()` unguarded. Adding `baseline()` to the default branch made that
    latent gap total, so the guard is now on the route. `CTX-210.1`'s lesson, found for the third
    time in this repo: a route registered on fewer guards than it needs exists whenever those import
    and fails with a bare `AttributeError` when the others do not.

*   **Two suite errors were environmental and were checked rather than assumed.** `test_async_jobs`
    and `test_kicad_bridge` both failed with `ConnectionError: Failed to connect to KiCad` — live
    IPC tests, and KiCad was closed. Confirmed by stashing the change and watching the same test
    fail on a clean tree, rather than reasoning from the traceback.

*   **The maintainer's own board was carrying the leftover.** Removed, with a dated backup beside it.
    The board now reports what the tutorial says it does: four annular violations and one unconnected
    item, KiCad's own defaults, no canary.

*   **Still open, and not fixed here: nothing cleans the sidecar up when the house is deselected.**
    Choosing "check against KiCad's defaults instead" leaves the file on disk, so KiCad itself — and
    anything else reading that board — still sees the house's rules. This change makes the *app's*
    check honest; it does not make the *board* match what the app says is selected. Those are
    different problems and the second one needs a decision about what deselecting a house is
    supposed to mean.
