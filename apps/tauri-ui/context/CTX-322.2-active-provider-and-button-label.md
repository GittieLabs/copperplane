# CTX-322.2: Active Provider Indicator & Button Label

> **Spec Reference:** Links to [SPEC-322](../specs/SPEC-322-model-role-legibility.md)

The second and last legibility slice, from the maintainer's follow-up after using the screen
`CTX-322.1` changed:

> "we are misleading a user that adds multiple providers bc only one would be used and it is not
> clear as to which provider would be used [...] the edit button for each provider is not
> descriptive enough for it's function"

Per-agent configuration, raised in the same message, is **not** here — it is new capability with a
schema change, and is `SPEC-323`.

## 1. Feature Definition & Execution Plan

### Phase 1: Say which providers are actually called

*   [x] Each provider row shows the roles it serves — `reasoning`, `fast`, or `reasoning + fast` —
    in the accent colour.
*   [x] A record bound to no role reads **"not in use"** rather than being left blank, so an inert
    provider is a stated state rather than a rendering gap. This is the actual defect: a user can
    configure three providers and three API keys, and only the role-bound ones are ever called.

### Phase 2: Name the button for what it does

*   [x] `Edit` → **`Edit provider`**, with the accessible name `Edit provider <id>`.
*   [x] Existing tests updated to the new accessible name.

### Not in this context

*   **Per-agent provider/model/reasoning-effort overrides, the advanced toggle, and reset to
    defaults** — `SPEC-323`. New capability, needs a config-schema addition and daemon resolution
    changes, not a copy fix.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 — the requested button label was rejected, and the reason matters.** The
    maintainer proposed renaming `Edit` to **"Edit Agents"**. Checked what the button opens before
    implementing: a provider form holding id, kind, base URL, reasoning model, fast model, and the
    two capability checkboxes — **no agents at all**. "Edit Agents" would have promised agent
    configuration and delivered a provider form, making the screen more misleading rather than
    less, which is the opposite of the request's intent. Put back to the maintainer with what the
    form actually contains; **"Edit provider" was chosen instead.** Recorded because the literal
    instruction and the underlying goal pointed in opposite directions, and following the literal
    one would have satisfied neither.

*   **Deviation 2 — "only one provider is used" was very slightly wrong, and the fix is shaped by
    the correction.** Up to **two** records are live at once, one per role, not one. That is why
    the indicator lists roles per record and renders `reasoning + fast` when a single record serves
    both, rather than a boolean "active" badge, which would have been the obvious implementation of
    the request as stated and would have hidden the two-role structure the user was already
    confused by.

*   **Non-deviation, checked rather than assumed:** the existing tests referenced the button by its
    old accessible name in eight places across four provider ids. A first pass renamed only the
    three ids that appeared in the fixtures and left `my-server` behind — caught by the suite, not
    by inspection, and fixed with a general pattern rather than another enumerated list.
