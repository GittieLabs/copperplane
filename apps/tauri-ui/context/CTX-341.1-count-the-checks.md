> **Spec Reference:** Links to
> [SPEC-341](../specs/SPEC-341-one-findings-list-per-area.md)

## 1. Feature Definition & Execution Plan

`SPEC-341` §2.1 opens by saying the spec needs a measurement before anyone builds from it, and names
the risk directly: the belief that a check runs three times per area is *"inference from reading the
code, not a measurement"*. Phase 1 takes it. Everything after depends on what it found, so the later
phases are deliberately not filled in yet.

### Phase 1: Count the checks

*   [x] Instrument the real `kicad_cli.run_drc` / `run_erc` and drive each user-visible action
    through the real routes, rather than reasoning about call graphs.
*   [x] Count LLM agent constructions on the same runs; `SPEC-341` §3 names the explanation call as
    the expensive part, so the subprocess count alone would answer the wrong question.
*   [x] Write the numbers into `SPEC-341` §2.1, replacing the inference — including where the
    inference was wrong.
*   [x] State plainly what the numbers do to the case for merging.

### Phase 2 onward: deliberately not planned yet

The measurement changes the argument (§4, Finding 3). Writing phases now would be planning against
the assumption Phase 1 was built to test. The next phase is a decision, and it belongs to the
maintainer:

*   Merge anyway, for one list and one count, accepting that the saving is one DRC run and one LLM
    call per area rather than the 3-4x the spec implied.
*   Do less: keep two panels and reconcile only the counts, which `SPEC-340`'s cross-reference has
    already half-built.
*   Do nothing here and spend the effort on `SPEC-342`, where the open question is a feature users
    have actually asked for.

## 4. Plan Drift & Architectural Changes

**Finding 1: the inference was wrong, and wrong in the direction that matters.** `SPEC-341` §2.1
predicted three DRC runs on the PCB tab with a house selected, enumerating them as
"`kicad.check_board`'s own DRC, the baseline-plus-verified pair inside `fabrication_review`, and a
third inside `_check_status_note`" — which is four, not three, and the sentence contradicted its own
count. Measured, one user action at a time:

| Action | DRC/ERC runs | Wall clock | LLM calls |
| :--- | :--- | :--- | :--- |
| Board check, no house | 1 | 2.7s | 1 (`board_advisor`) |
| Board check, house selected | 2 | 3.6s | 1 (`board_advisor`) |
| Run Review on PCB | 1 | 1.9s | its own review agent |
| Run Review on Schematic | 1 | 1.5s | its own review agent |

`kicad.check_board` does not add a DRC run on top of `fabrication_review`'s — it delegates, and
`CTX-340.1` deliberately threaded `schematic_parity` through so the same run serves both. The
prediction double-counted a run the fold-in had already removed.

**Finding 2: the second profile run is conditional and did not fire here.** `write_and_verify` runs
DRC twice only when the verification canary has to share a constraint class with one of the
profile's own rules. With the generic profile on this board it found a free class, so the cost is
two runs, not three. A profile using every candidate class would cost three; that is a real
worst case and it is not the common one.

**Finding 3: this materially weakens the case the spec was written on.** `SPEC-341`'s stated
practical benefit was doing the work once instead of three or four times. The measured duplication
is **one redundant DRC run (~1.9s) and one redundant LLM call per area** — the review's. That is
worth having, but it is not the prize the spec implied, and the honest consequence is that the
merge's value now rests almost entirely on the *user comprehension* half of the argument: one
action, one list, one count. Which was always the stronger half, and is now the only one.

Recorded rather than smoothed over, because a spec that keeps its original cost argument after the
measurement contradicts it is exactly the kind of artifact this repo's norms exist to prevent.

**Finding 4: I repeated a lesson I had written down the day before.** `unittest -k` does not
support `or`; `-k "runs_drc or explains_once"` reported `Ran 0 tests ... OK`. `CTX-340.2` §4 records
this exact trap from the previous session. Writing something down is not the same as reading it
back, and a passing result that ran nothing looks identical to a passing result that ran everything.

**Finding 5: the wall clock is not where the cost is.** A DRC run is under two seconds. The LLM
explanation call is the part that costs money and the part `explain_violations` already caps at 15
findings. Any merge that produces one longer list makes *what gets explained* a visible product
decision, which `SPEC-341` §3 already anticipated — and that, not the subprocess count, is the real
design work waiting.
