# CTX-318.5: Implementation Context: AgentChat in Overview + Project Intent

> **Spec Reference:** Links to [SPEC-318](../specs/SPEC-318-in-context-agent-chat-and-review.md)

Phase 5 of 6 in the user's own confirmed order: foundation (`CTX-318.1`) → Components (`CTX-318.2`) →
Schematic/PCB (`CTX-318.3`) → Enclosure (`CTX-318.4`) → **project intent/Overview** → finish deleting
`parseCommand`. The largest single phase in this spec: extracts `Overview` out of `App.tsx`, migrates
it to the mount-always pattern every other area already follows, adds the project intent editor
(§2.4), and mounts a second, separately-scoped `AgentChat` alongside the still-functional
`parseCommand`-driven chat -- §2.6 explicitly defers deleting `parseCommand` to Phase 6.

## 1. Feature Definition & Execution Plan

### Phase 1: extract `Overview` into its own file
*   [x] Moved `Overview`, `ChatMessageView`, the `ChatMessage`/`Status`/`InjectStatus` types,
    `newMessageId`/`nextMessageId`, and `_INJECT_DEFAULT_POSITION_MM` out of `App.tsx` verbatim into
    a new `apps/tauri-ui/src/components/Overview.tsx` -- no behavior change to the existing
    `parseCommand`-driven generate/inject/chat flow in this step.
*   [x] `App.tsx` imports `Overview` from `./components/Overview` instead of defining it locally;
    every import that was only needed for the extracted code (`submitJob`, `dispatchTool`,
    `parseCommand`, `appendConversationTurn`, `loadConversation`, `ConversationTurn`,
    `OverviewDashboard`) moved with it.

### Phase 2: migrate Overview to the mount-always pattern
*   [x] `App.tsx`'s `{view.area === 'overview' && <Overview .../>}` conditional render replaced with
    the same `<div data-testid="overview-area" className={view.area === 'overview' ? 'w-full' : 'hidden'}>`
    wrapper every other area already uses (`CTX-306.2`) -- `Overview` itself already resets its own
    state in a `useEffect` keyed on `projectName`, so no new reset logic was needed, only the mount
    strategy around it.
*   [x] `CTX-305.4`'s own "every area wrapper stretches full width when active" regression test
    extended to include `['Overview', 'overview-area']` in its loop, and two new App-level tests
    added confirming a half-typed question in the old chat input survives a tab switch and resets on
    a real project switch -- the same class of regression `CTX-306.2` fixed for every other area.

### Phase 3: project intent (SPEC-318 §2.4)
*   [x] **Real, verified backend already existed, not built here:** `library_store.py`'s
    `_validate_project_intent`/`_backfill_project_intent`, the `Project.intent` field, and the
    `project.set_intent` daemon route (`daemon.py`'s `project_set_intent`) were all already shipped
    under `CTX-206.1`, confirmed by reading the installed backend directly before writing any
    frontend code. This phase is purely a frontend consumer of an existing, already-tested route.
*   [x] `lib/projects.ts`: `Project` gains `intent?: string | null`; new `setProjectIntent(projectName, intent)`
    calling `project.set_intent` directly (not a full `saveProject(project)` round-trip, so an intent
    edit can't race a stale in-memory `last_results`/`export_history` into the saved record).
*   [x] `Rail.tsx`: the project-creation flow gains an optional textarea beside the name input,
    skip-first-class -- `onCreateProject`'s signature widens to `(name: string, intent?: string)`,
    called with **exactly one argument** when the textarea is left blank (not a second, `undefined`
    argument), so `App.tsx`'s existing `saveProject({ name })` path for a skipped intent is
    byte-for-byte unchanged, matching §2.4's own explicit requirement.
*   [x] `App.tsx`'s `handleCreateProject(name, intent?)`: `saveProject(intent ? { name, intent } : { name })`.
*   [x] `Overview.tsx` gains a new `IntentEditor` sub-component: shows the real stored intent (or an
    honest "Not stated yet" message) with an Add/Edit toggle; editing reveals a textarea with
    Save/Cancel; Save calls `setProjectIntent` and reports the updated `Project` back to the caller
    via `onProjectUpdated` (mirroring `handleLinkDirectory`/`handleSaveProject`/`handleExportSuccess`'s
    own existing "child calls the route, parent's `setCurrentProject` stays the source of truth"
    convention); its own local `editing`/`draft` state resets on a real project switch (keyed on
    `projectName`, same pattern as `Overview`'s own chat-history effect).

### Phase 4: mount `AgentChat` in Overview, alongside the old chat
*   [x] `area="overview"`, `scope="project"`, `scopeId={`${projectName}:overview`}` (SPEC-206 §2.2's
    real `<project_name>:<area>` format), `title="Ask about this project"`, `projectName={projectName}`,
    `promotionTargets={[{ label: 'this project', scope: 'project', id: projectName }]}` -- same shape
    as Schematic/PCB/Enclosure (`CTX-318.3`/`.4`), mounted below the existing `parseCommand` chat
    input, not replacing it. SPEC-318 §2.6 (rehoming `generate`/`inject`, deleting `parseCommand`) is
    Phase 6, gated on a real design decision the user has not yet made.

### Phase 5: tests
*   [x] New `Overview.test.tsx`: `AgentChat` wiring tests (real `area`/`scope`/`scopeId`/`title`/
    `projectName`/`promotionTargets`, re-scoping on project change), and the full `IntentEditor`
    behavior (empty state, populated state, Add/Edit toggle, Save round-trips through the real mocked
    `setProjectIntent` and a small stateful test wrapper mirroring `App.tsx`'s own
    `onProjectUpdated={setCurrentProject}` convention, Cancel discards the draft, a genuine save
    failure shows the real error and stays in edit mode, a project switch resets any in-progress
    edit). The pre-existing `parseCommand`-driven chat tests (generate/inject/plain-chat, `TEST-001`
    through `TEST-008`) were **left in `App.test.tsx` rather than moved** -- see Plan Drift.
*   [x] `Rail.test.tsx`: the existing "Add calls onCreateProject" test's assertion updated to note it
    now specifically covers the skip case (still exactly `toHaveBeenCalledWith('new-proj')`, no second
    argument); a new test confirms a typed intent is passed through as the second argument.
*   [x] `App.test.tsx`: `CTX-305.4`'s wrapper loop extended; a new describe block covers Overview's
    own mount-always persistence at the App level (half-typed question survives a tab switch, resets
    on project switch) -- no `App.test.tsx`-level `AgentChat` wiring test was needed, since
    `App.test.tsx`'s own `./components/AgentChat` module-level stub (added in `CTX-318.3`) already
    covers Overview's new mount with no further change, confirmed the same way `CTX-318.4` already
    confirmed it for `EnclosurePanel`.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1 (a real, deliberate scoping decision, not an oversight): the pre-existing
    `parseCommand`-driven chat tests (`TEST-001` through `TEST-008`, `App.test.tsx`) were left where
    they are rather than moved into `Overview.test.tsx`.**
    *   *Reasoning:* every one of those tests already renders the real, unmocked `Overview` through
        `<App />` (matching the established precedent for `SchematicAdvisor`/`BoardAdvisor`/
        `EnclosurePanel`, which are also real and unmocked in `App.test.tsx`, each with its own
        *additional* dedicated test file rather than a full migration out of `App.test.tsx`) --
        moving 200+ lines of already-passing, already-correct test code carries real risk of
        introducing a transcription error for zero behavior change, since Phase 1's extraction was
        itself verified to be behavior-preserving (`npx vitest run` passed unchanged immediately
        after the extraction, before any new code was added).
    *   *Impact:* `Overview.test.tsx` is scoped to exactly the code this phase actually adds (the
        intent editor, the new `AgentChat` mount) rather than re-testing already-covered
        `parseCommand` behavior a second time. `App.test.tsx` keeps its full, real coverage of the
        `generate`/`inject`/plain-chat flow, which stays load-bearing until Phase 6 deletes it.
*   **Deviation 2 (real, checked directly rather than assumed): confirmed the backend for project
    intent needed zero new work.**
    *   *Reasoning:* SPEC-318 §2.4 describes project intent as new work; grepping the installed
        `services/python-daemon` source directly (not assumed from the spec's own wording) found
        `Project.intent`, its validation/backfill, and the `project.set_intent` route were already
        shipped under `CTX-206.1`, before this phase started.
    *   *Impact:* this phase is a pure frontend consumer -- no backend changes, no new backend tests.
        Named explicitly so a future reader doesn't assume `CTX-206.1`'s own intent support was this
        phase's work.
*   **Deviation 3 (real, checked directly per `CTX-318.4`'s own recorded prediction): the
    `App.test.tsx` AgentChat-unmocked trap did not recur a fifth time either.**
    *   *Reasoning:* `CTX-318.4` predicted future phases would only need to re-check this, not
        re-fix it, since the `App.test.tsx` stub is module-level (`vi.mock('./components/AgentChat', ...)`),
        covering every consumer including ones added later. Verified directly by running the full
        suite before writing `Overview.tsx`'s own `AgentChat` mount -- it needed no new `App.test.tsx`
        fix, confirming the prediction held for a second phase in a row.
