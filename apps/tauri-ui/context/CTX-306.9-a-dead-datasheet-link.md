# CTX-306.9: A Dead Datasheet Link Becomes a Live One

> **Spec Reference:** Links to
> [SPEC-306](../specs/SPEC-306-component-discovery.md)

## 1. Feature Definition & Execution Plan

Reported from the running app, of a Components tab where every result carried a red datasheet
failure: *"part of this seems to work."*

`SPEC-212` measured the cause before anything was changed, driving the app's own
`library_store.cache_datasheet`:

| search | datasheets fetched |
| :--- | :--- |
| `ATtiny85 microcontroller` | **3 of 3** |
| `220 ohm resistor LED current limiting` | **0 of 3** |
| `0.1uF ceramic capacitor switch debounce` | **0 of 3** |

Guessing a datasheet URL works for ICs and cannot work for generic passives: a passive's datasheet
is a family document covering hundreds of values, so there is no per-part URL to guess and the model
invents one. **No prompt change fixes that.**

Nothing regressed to cause this. `SPEC-328` changed *which searches get run* — from ICs a user
already named to the resistors and capacitors a first board is mostly made of — so a path that was
almost always fine became almost always broken without either spec changing.

`SPEC-212` proposed resolving datasheets through TME and was declined the same day: the terms work
only because the user holds their own key, and *"i don't want to deal with licenses or having users
use their own vendor api keys"* removes the approach rather than an implementation detail. So the
fix is `SPEC-203` §3's own row for this need — *"a constructed deep link. No API, no key, compliant
everywhere."*

### Phase 1: Stop offering a retry of something that cannot work

*   [x] Once the guess has failed for a candidate, the "view datasheet" button is replaced rather
        than left there to be clicked again.
*   [x] Say the actual cause in the user's terms — manufacturers publish one document per family,
        not per part — instead of a bare HTTP status.
*   [x] Keep the underlying error, subdued. `CTX-306.8`'s point was that an invented URL must fail
        **in** the app rather than silently in a browser; that guarantee stays, it just stops being
        the loudest thing on the card.

### Phase 2: Hand over a next step instead of a dead end

*   [x] `datasheetSearchUrl` builds a search carrying the part number, the manufacturer and the word
        datasheet.
*   [x] **Neutral, not a distributor's own search.** Routing every failed lookup to one vendor picks
        a commercial partner on the user's behalf — a business decision this app has not made and
        should not make silently. Pinned by a test rather than left to the comment.
*   [x] Opened through `tauri-plugin-shell`, reusing `handleOpen` — `CTX-306.x` already found that a
        plain anchor does not reliably escape the Tauri webview.

### Phase 3: Leave the working case alone

*   [x] A datasheet that resolves is untouched: no explanation, no search link, no extra click. The
        guess works for ICs and costs nothing, and this must not make the already-fine case worse.

## 4. Plan Drift & Architectural Changes

*   **My first cut deleted something a test was protecting, and the test caught it.**
    `CTX-306.8`'s own test asserts both that the failure surfaces **in** the app and that the
    invented URL is never handed to the browser. Replacing the red error wall wholesale kept the
    second and dropped the first: the raw `HTTP Error 404` disappeared entirely.

    That is a real loss, not just a failing assertion — a user does not need the status, but anyone
    diagnosing this does, and "the app said nothing" is the exact complaint `CTX-306.8` was written
    to fix. The fix keeps both: the cause in plain words as the primary line, the underlying error
    subdued beneath it. The old test was updated to match the new wording while keeping both of its
    real guarantees.

*   **A neutral search rather than a distributor's, and this is a decision not a default.**
    `SPEC-203` §3 describes the constructed deep link as *"compliant everywhere"* precisely because
    it commits to nothing. Sending every failed lookup to one vendor's search page would pick a
    commercial partner on the user's behalf — which is exactly the class of decision `SPEC-203` §2.2
    documents this project getting wrong when it assumes. `TEST-003` pins it, and that test will
    look pointless right up until somebody adds an affiliate link.

*   **This closes the defect without closing the underlying gap, and the difference matters.** The
    user still cannot read a 220Ω resistor's datasheet from inside the app. What changed is that the
    app now says why and hands them a working search, instead of showing a failure that reads as the
    app being broken. `SPEC-212`'s tombstone records what would actually close the gap: a source of
    per-part datasheet URLs needing no user-held credential, which per `SPEC-203` §2.2 does not
    currently exist.

*   **What was not verified.** No click-through in the running app; the search URL is asserted in
    tests rather than opened. The measurement it is built on came from real live calls through the
    app's own fetch path, recorded in `SPEC-212` §1.
