# CTX-336.2: Implementation Context: Open a Project Actually Opens One

> **Spec Reference:** Links to [SPEC-336](../specs/SPEC-336-first-run-onboarding-and-launch.md)

Follows [CTX-336.1](CTX-336.1-first-run-onboarding.md). Reported from the built app: *"I clicked
open a project and nothing happened."*

Correct report. `NoProjectLanding`'s **Open a project** called
`onOpenProject={() => setProjectActionMessage('Pick a project from the list on the left.')}` — and
`projectActionMessage` renders only inside the project view. So the button set a message that no
one could ever see, from a view where it does not render, on a screen the user reaches before
opening any project. It did nothing at all, in every case, always.

## 1. Feature Definition & Execution Plan

### Phase 1: Make it an action
*   [x] The landing view takes the project list, not a count, and reveals it inline.
*   [x] Clicking a project opens it, through the same `handleSelectProject` the rail uses.
*   [x] The list is hidden until asked for, so the view stays a landing page rather than a
        second project list competing with the rail.

### Phase 2: Guard the class, not the instance
*   [x] A test asserting every control on this view invokes a handler — the specific failure was a
        control wired to a state setter whose output renders somewhere else, which no assertion
        about *this* button would have caught.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the original design reasoning was sound and the implementation did not honour
    it.** `CTX-336.1` §0.5 argued the rail should stay visible on the landing view because it is
    the fastest route to opening a project — which is true, and which I then used to justify making
    the button *point at* the rail instead of doing anything. A button whose entire effect is "look
    over there" is barely a button; one whose message renders on another view is not one at all.
    The list now lives here too. Two lists of the same projects is a smaller cost than a control
    that lies.

*   **Deviation 2: seven tests covered this view and none of them pressed this button meaningfully.**
    `CTX-336.1`'s own test asserted `onOpenProject` was called — with a mock, which was satisfied by
    a handler that did nothing real. The mock agreed with the code because I wrote both, which is
    the failure mode that context already recorded for `GuidedSetup`, repeated one file over. The
    new guard checks that every control invokes a handler, which the old shape would have passed
    too — so the honest statement is that **the click-through is what found this, and the test
    added here would not have.** It guards a regression, not the discovery.
