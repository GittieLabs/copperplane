# CTX-342.1: Implementation Context: A Global Library of Board Houses

> **Spec Reference:** Links to
> [SPEC-342](../specs/SPEC-342-a-library-of-board-houses.md)

## 1. Feature Definition & Execution Plan

`SPEC-340` shipped exactly one profile, stored per project. This makes it a library: houses live
once, projects choose between them, and cloning an existing house is how a user gets their own
without retyping nine numbers.

The order below puts the store and the history question first, because both are hard to change
later and both can be got wrong quietly. The UI is last and the bundled vendors are last of all —
deliberately, since `CTX-114.1` Deviation 6 already declined to invent numbers for a named business
and nothing here reopens that.

### Phase 1: The store

*   [x] A global `library/houses/` collection with save, load, list and delete, following
    `list_parts`'s existing scan-and-filter shape rather than inventing a second convention.
*   [x] Every write validated through `capability_profile.validate`, so the library cannot hold a
    record the checker would refuse.
*   [x] **Delete is new behaviour in this module** — `library_store` has no `delete_*` today. It
    needs to say what happens to a project still pointing at the removed house, and the answer must
    not be a crash or a silent fallback to different numbers.

### Phase 2: What a project stores, and why it is not just a reference

*   [x] A project records the house it chose **and** the numbers it was last checked against —
    already true, since `SPEC-340` stores the whole profile on the project. Pinned by TEST-004 and
    TEST-005 rather than assumed, because it is the property the whole history argument rests on.
*   [x] Editing a house must not rewrite what an existing project's findings were produced against.
    `SPEC-342` §2.1 is explicit that a profile is a historical record; storing a bare reference
    would silently rewrite history the next time someone edited a shared house.
*   [ ] Migrate the existing per-project profile from `SPEC-340` into the library on first read,
    without losing its provenance.

### Phase 3: Clone, which is what makes this usable

*   [x] Clone any house, rename it, override the fields that differ.
*   [x] A clone resets `confirmed_by_user` on every field it did not change, and takes its own
    `recorded_on`. Inheriting someone else's confirmation is the attribution failure per-field
    provenance exists to prevent (`SPEC-114` §2.6).
*   [x] Most houses differ from a standard process in two or three numbers, so this is the path
    that avoids a nine-field data-entry session — and a half-finished one is wrong in a way the app
    cannot detect.

### Phase 4: Import and export

*   [ ] Export one house, or the library, as JSON.
*   [ ] Import treats the file as untrusted: validated through the same path as anything else, with
    a name collision reported rather than silently overwriting the user's own edits.

### Phase 5: The surface

*   [ ] Pick a house per project from the library; clone, rename, edit, remove.
*   [ ] Each entry shows where its numbers came from and when they were read.
*   [ ] Switching a project's house keeps `CTX-340.2`'s staleness warning honest.

### Phase 6: Bundled houses — blocked on a decision, not on code

*   [ ] **Not started, and not to be started by guessing.** `SPEC-342` §2.3 permits a bundled house
    only once someone has actually read that vendor's published page. Until then the library ships
    with the unbranded generic entry alone.
*   [ ] `SPEC-342` §2.5's open question — whether "generic" is a house at all, or a template that
    can only be cloned — is a product decision and is recorded in §4 below rather than assumed.

## 4. Plan Drift & Architectural Changes

*   **Open decision, recorded rather than assumed: is "generic" a house?** `SPEC-342` §2.5 leaves
    this open and it shapes Phase 5's surface. Measured 2026-09-08: the generic profile is stricter
    than KiCad's defaults on six of nine fields and looser on two, so it is neither a floor nor a
    default — it is a plausible standard process. Listing it beside real vendors invites exactly the
    question that was asked of it. Making it a clone-only template says what it is. This is a
    product call and Phase 5 should not start without it.

*   **Prediction 1 was wrong, and cheaply.** It predicted the Phase 2 migration would be the
    awkward part. There is nothing to migrate: `SPEC-340` already stores the whole profile on the
    project, which is exactly what §2.1 asks for, so the history property was true before this
    context started. Two tests now pin it rather than leaving it as an accident of the earlier
    design — TEST-005 in particular, which revises a shared house and checks the project's own
    numbers do not move.

*   **Prediction 1, as originally recorded:** the migration in Phase 2 will be the awkward part,
    not the store. `CTX-110.1`
    and `CTX-304.2` both found real bugs in how project identity resolves, and this adds a second
    place a project's profile can live while the first one still has readers.

*   **Prediction 2:** delete will surface a question nobody has asked yet — what a project pointing
    at a removed house should show. The honest answer is probably that it keeps the numbers it was
    checked against and says the house is gone, which is only possible because Phase 2 stores them.
    If that turns out to be wrong, it belongs here.
