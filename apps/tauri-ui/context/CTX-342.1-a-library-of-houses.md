# CTX-342.1: Implementation Context: A Global Library of Board Houses

> **Spec Reference:** Links to
> [SPEC-342](../specs/SPEC-342-a-library-of-board-houses.md)

## 1. Feature Definition & Execution Plan

`SPEC-340` shipped exactly one profile, stored per project. This makes it a library: houses live
once, projects choose between them, and cloning an existing house is how a user gets their own
without retyping nine numbers.

The order below puts the store and the history question first, because both are hard to change
later and both can be got wrong quietly. The UI is last and the bundled vendors are last of all —
deliberately, since `CTX-114.1` Deviation 6 already declined to invent numbers for a named business
and nothing here reopens that.

### Phase 1: The store

*   [x] A global `library/houses/` collection with save, load, list and delete, following
    `list_parts`'s existing scan-and-filter shape rather than inventing a second convention.
*   [x] Every write validated through `capability_profile.validate`, so the library cannot hold a
    record the checker would refuse.
*   [x] **Delete is new behaviour in this module** — `library_store` has no `delete_*` today. It
    needs to say what happens to a project still pointing at the removed house, and the answer must
    not be a crash or a silent fallback to different numbers.

### Phase 2: What a project stores, and why it is not just a reference

*   [x] A project records the house it chose **and** the numbers it was last checked against —
    already true, since `SPEC-340` stores the whole profile on the project. Pinned by TEST-004 and
    TEST-005 rather than assumed, because it is the property the whole history argument rests on.
*   [x] Editing a house must not rewrite what an existing project's findings were produced against.
    `SPEC-342` §2.1 is explicit that a profile is a historical record; storing a bare reference
    would silently rewrite history the next time someone edited a shared house.
*   [x] ~~Migrate the existing per-project profile into the library on first read.~~ **Dropped by
    decision:** *"the project is new enough that no one is affected. i'm the only user."* Nothing to
    migrate, so writing a migration would be code with no case to exercise it.

### Phase 3: Clone, which is what makes this usable

*   [x] Clone any house, rename it, override the fields that differ.
*   [x] A clone resets `confirmed_by_user` on every field it did not change, and takes its own
    `recorded_on`. Inheriting someone else's confirmation is the attribution failure per-field
    provenance exists to prevent (`SPEC-114` §2.6).
*   [x] Most houses differ from a standard process in two or three numbers, so this is the path
    that avoids a nine-field data-entry session — and a half-finished one is wrong in a way the app
    cannot detect.

### Phase 4: Import and export

*   [x] Export one house, or the library, as JSON, dated so an imported set can say how old it is.
*   [x] Import treats the file as untrusted: validated through the same path as anything else, with
    a name collision reported rather than silently overwriting the user's own edits.
*   [x] Imports arrive marked shipped, so editing one produces the user's own copy and the imported
    original stays available to reset back to — which is what makes a periodic re-import
    non-destructive.

### Phase 5: The surface

*   [x] Pick a house per project from the library; clone, edit, remove, reset, import and export.
*   [x] Each entry says whether it came with the app or is the user's own copy.
*   [x] Switching a project's house keeps `CTX-340.2`'s staleness warning honest — the choice goes
    through the same `setProjectProfile`, so the existing stale-result cue and re-check still apply.
*   [ ] **Not done: a real click-through.** Every defect in this family so far was found by using
    the app, not by the suite. This surface has not been used by a person.

### Phase 6: Bundled houses — blocked on a decision, not on code

*   [x] **Four houses researched from their own published pages** — JLCPCB, PCBWay, OSH Park and
    AISLER — each field carrying its source URL, the date it was read, and the exact published
    wording. Absent where a vendor publishes nothing. In `board-houses/`, importable rather than
    bundled, so shipping them stays a separate decision.
*   [ ] Ship any of them with the app. Still a decision, and see the finding below first.
*   [x] `SPEC-342` §2.5's open question is **settled: generic is a template, not a house.** Enforced
    in three places rather than documented — `save_house` refuses one, a project cannot be checked
    against one, and `clone` clears the flag so a clone is always a real house.

## 4. Plan Drift & Architectural Changes

*   **Decided: generic is a clone-only template.** The open question is settled. It is neither a
    floor nor a default — measured stricter than KiCad's defaults on six of nine fields and looser
    on two — so listing it beside real vendors would make it answer a question it cannot: *which
    house is this?* Every field would also stay `confirmed_by_user: false` forever, because there is
    no published page for anyone to check it against.

    Enforced rather than documented, which matters because a rule written only in prose is a rule
    that gets bypassed by the next caller: `save_house` refuses a template, a project cannot be
    checked against one, and `clone` clears the flag.

    The user-visible cost is zero. "Start from standard 2-layer numbers" is still one click; it now
    produces a house of the user's own, which they can edit, rather than silently adopting numbers
    attributed to nobody. An existing copy is reused rather than cloned twice, because the library
    is global and two projects starting the same way should share one house.

*   **Prediction 1 was wrong, and cheaply.** It predicted the Phase 2 migration would be the
    awkward part. There is nothing to migrate: `SPEC-340` already stores the whole profile on the
    project, which is exactly what §2.1 asks for, so the history property was true before this
    context started. Two tests now pin it rather than leaving it as an accident of the earlier
    design — TEST-005 in particular, which revises a shared house and checks the project's own
    numbers do not move.

*   **Prediction 1, as originally recorded:** the migration in Phase 2 will be the awkward part,
    not the store. `CTX-110.1`
    and `CTX-304.2` both found real bugs in how project identity resolves, and this adds a second
    place a project's profile can live while the first one still has readers.

*   **The discarded hash survived in the Implementation Log after I removed it from the
    frontmatter.** The validator checks `commit_hashes` and not the §3 table, so `9a4ed9a` sat there
    reachable-looking and wrong until I read the table for another reason. Same rewrite, same stale
    value, two places — fixing one is not fixing it.

*   **I committed the build venv, and the fix rewrote history.** `git add services/python-daemon`
    swept in `.build-venv/` (8,727 files) and the 47MB frozen sidecar — two of the four artifacts
    this repo's working tree deliberately keeps untracked — and it was pushed before I noticed. The
    remedy was a reset, a re-commit naming the nine real files explicitly, and a
    `--force-with-lease` push on an unmerged branch.

    That left a dangling hash behind: the context still recorded the discarded commit, because the
    reset kept the working tree. `CTX-902.2`'s reachability check caught it in CI, which is exactly
    the case it was built for. The lesson is the plainer one though — `git add <directory>` is how
    this happens, and naming files is not pedantry.

*   **An unplanned consequence, and the right one: saving over a house is now refused by default.**
    Making the UI clone-then-save exposed that `save_house` would happily replace an existing record.
    `SPEC-342` §2.4 asks for a collision to be reported on import; it is the same rule everywhere,
    because the thing being replaced is a set of numbers a board gets judged against. Editing a
    house is now an explicit overwrite, which one existing test had to be updated to say.

*   **The research found that the bundled template manufactures findings, which is the failure
    `SPEC-114` §3 predicted.** Four houses read from their own capability pages, then run against the
    tutorial board: PCBWay 4, OSH Park 4, AISLER 6, JLCPCB 11 — against the bundled template's
    **27**.

    **Sixteen of those 27 (59%) come from `min_silk_clearance: 0.15`, and not one of the four houses
    publishes a silkscreen-to-copper clearance at all.** The largest single group of findings the
    feature produces comes from a limit no board house states.

    `SPEC-114` §3 named this in advance — *"a too-strict profile is worse than none ... the app
    manufactures findings and spends the credibility this family runs on"* — and it shipped anyway,
    because the template's numbers were plausible-sounding rather than read off anything. The research
    is what caught it, which is what the research was for.

    **Decided and done.** The field is gone from the bundled profile, and `SPEC-114` §2.4, §2.8 and
    §2.9 are corrected to the re-measured figures rather than left carrying a number the research
    disproved. The tutorial board now reads **4 → 11**: `annular_width` 4, `hole_to_hole` 3,
    `text_height` 2, `text_thickness` 2 — seven of them the built-silently-wrong class, and all
    three headline findings still landing on D1.

    Eleven is exactly JLCPCB's count, the strictest of the four researched houses. The corrected
    profile now sits at the strictest real house instead of at more than twice it.

    Worth stating plainly, because a spec that quietly restates its numbers is worse than one that
    was wrong: the old §2.4 was a real measurement of a real run. What was wrong was the profile it
    measured, and the spec now says so with the reason attached.

*   **Two things the nine-field schema cannot express, both found by trying to fill it in.** Vendors
    publish separate annular-ring and drill minimums for vias and for plated through holes — AISLER
    wants 300 um annular on a PTH and 200 um on a via, with 0.5 mm and 0.3 mm drills — and the
    profile has one field for each, mapped to KiCad's via-oriented setup keys. Each entry records the
    value its field maps to and puts the other in the note. And silkscreen-to-copper clearance is
    published by none of the four, which is why the field is absent everywhere.

*   **A concept removed, which is the rarer kind of correction.** Decided after seeing the library
    in the app: *"Read only would just be reserved for our generic import included template. and
    everything else would be editable which is fine bc you could always reimport a house file."*

    `is_bundled` is gone entirely. It existed so that a house shipped with the app could be
    read-only and therefore recoverable — but houses ship as an importable file, so any of them can
    be got back by importing again, and locking one protected nothing while costing the user the
    ability to fix a number. Nothing ever set the flag, which was the first sign; the second was
    that explaining it took a four-row table.

    The rule is now one sentence: **the template is read-only, every house is editable.** The
    template is the exception because it is not a house at all.

*   **Import asks instead of deciding.** `import_houses` takes `on_collision`: `report` (the
    default, which imports nothing that clashes and names it), `overwrite`, or `rename`. The UI
    offers "Keep both" and "Replace mine" with nothing changed until the user picks.

    Defaulting either way would be wrong: only the user knows whether the copy they already have is
    one they edited, and replacing an edited house discards work on numbers a board gets judged
    against. The rename suffix is `-2` rather than the `-mine` the earlier auto-clone used — an
    imported house that collided is not somebody's copy, and the helper now takes the suffix as a
    parameter because its two callers mean different things by it.

*   **The read-only rule protected nothing, and I shipped it that way.** Reported in four words:
    *"i can edit or remove any board settings."* Correct, and the data agreed — **no code path ever
    set `is_bundled`.** Every reference to it read, checked or cleared the flag; nothing wrote one.
    So every house in the library was the user's own, everything was editable, and the rule I had
    just written up in `SPEC-342` §2.6 and covered with tests applied to zero records.

    The tests passed because they constructed a bundled house by hand and asserted the store and the
    UI honoured it. Both do. What no test asked was whether anything ever *creates* one — the same
    shape as `CTX-340.2`'s mocked persistence route, one level up: every part verified, and nothing
    checking that the parts were connected to anything real.

    It also left the user's original concern unanswered. The point of the read-only rule was "getting
    back to default settings", and there were no default settings in the library to get back to: the
    template existed but was never listed, because the library only shows saved houses.

    The standard numbers are now always shown as a read-only entry, sourced from
    `fabrication.generic_profile` rather than stored — so it cannot drift, be edited, or be deleted.
    It offers Clone and nothing else, which keeps `SPEC-342` §2.5 intact: a template is still never
    what a board is checked against. `is_bundled` stays for vendor houses if any are ever shipped.

*   **Requested mid-flight, then corrected: a house that came with the app is read-only.**

    The first version had a bundled house auto-clone on edit, on the reasoning that the clone is the
    mechanism and refusing would be a step with no visible reason. Corrected on sight of the
    running UI: *"we should only allow edits on a cloned template ... you can clone any template
    though. allowing edits to template bundled with the app would prevent us from getting back to
    default settings."*

    Auto-cloning did preserve the original, so the recovery property held. What it got wrong was the
    interface: pressing Edit and getting a differently-named house back answers a question nobody
    asked. Refusing, and offering Clone instead, says the same thing without the surprise — and puts
    the rule in the interface rather than only in the outcome. Bundled houses now offer neither Edit
    nor Remove, since deleting one loses the known-good copy just as surely as editing it.

    **The sharper correction was in the model, not the UI.** I had one flag, `is_shipped`, covering
    both "came with the app" and "was imported". The same message separated them: *"we should also
    only allow edits on templates that were uploaded or imported from external sources."* The rule
    is about **recovery, not origin** — a bundled house is the only thing a user cannot get back any
    other way, while an imported one can simply be imported again. So `is_bundled` now means
    strictly what came with the app, and imports arrive fully editable.

*   **Prediction 2 was right, and the answer was already available.** It predicted delete would
    surface a question nobody had asked: what a project pointing at a removed house should show. It
    does, and the honest answer was the one Phase 2 had already made possible — the project keeps
    the numbers it was checked against, and `delete_house` names the projects still showing them.

*   **Prediction 2, as originally recorded:** delete will surface a question nobody has asked yet — what a project pointing
    at a removed house should show. The honest answer is probably that it keeps the numbers it was
    checked against and says the house is gone, which is only possible because Phase 2 stores them.
    If that turns out to be wrong, it belongs here.
