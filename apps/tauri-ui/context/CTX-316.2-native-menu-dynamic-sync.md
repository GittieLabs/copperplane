# CTX-316.2: Native Menu Command Surface -- Dynamic Library Sync & Design Enable/Disable

> **Spec Reference:** Links to [SPEC-316](../specs/SPEC-316-native-menu-command-surface.md)

## 1. Feature Definition & Execution Plan

`CTX-316.1` shipped the full static menu structure and named two real gaps as this context's own
scope, per `SPEC-316`'s own Known Constraints: the `Library` menu only ever shows `Default Library`
(no real custom libraries, since the native menu is built before the daemon is ready to answer
`library.list_libraries()`), and the `Design` menu is always enabled regardless of whether a
project is actually open.

**Real API surface verified directly against the vendored `tauri 2.11.5` and `muda 0.19.3` source
before planning:** `AppHandle::set_menu(Menu<R>) -> Result<Option<Menu<R>>>` and `AppHandle::menu()
-> Option<Menu<R>>` are both defined via the `shared_app_impl!(AppHandle<R>)` macro invocation
(`app.rs:1231`), confirming they're real, callable methods on `AppHandle` (the type a
`#[tauri::command]` function receives), not `App`-only. `Menu::get<I>(&self, id: &I) ->
Option<MenuItemKind<R>>` requires `MenuId: PartialEq<&I>` (`menu/menu.rs:362`) --
`muda::MenuId` (`muda-0.19.3/src/menu_id.rs`) implements `PartialEq<&str>` directly, so
`menu.get("menu_design")` compiles and works as a plain string lookup, no `MenuId::new(...)`
wrapping needed. `Submenu::set_enabled(&self, bool) -> Result<()>` confirmed real
(`menu/submenu.rs:367`). An existing struct-argument precedent for a `#[tauri::command]` already
exists (`config::save_config_cmd(app: AppHandle, config: DaemonConfig)`,
`core/tauri-rust/src/config.rs:106`) -- this context's own `Vec<LibraryMenuEntry>` argument is the
first `Vec` argument on a command in this crate, but follows the exact same
`#[derive(Serialize, Deserialize)]` struct pattern already established, not a new convention.

**Real design decision: rebuild the whole menu on every library-list sync, not incremental
append/remove.** `Menu`/`Submenu` do expose `append`/`remove`/`remove_at`, but tracking exactly
which items are "the static ones" vs. "the ones from the last sync" (to remove only the latter)
adds real bookkeeping for no real benefit here -- menu construction is cheap, stateless, and already
factored into one function (`build_menu`) from `CTX-316.1`. This context splits that function into
a private `build_menu_inner(app, custom_libraries: &[LibraryMenuEntry])` and a thin
`build_menu(app)` wrapper (`build_menu_inner(app, &[])`), so `update_library_menu` reuses the exact
same construction path via `app.set_menu(build_menu_inner(&app, &custom)?)` -- no drift between the
menu's initial shape and any later rebuild.

**Real design decision: the frontend drives the sync, matching this app's own established
architecture.** Every other feature in this app keeps business logic and data-fetching in the
frontend/daemon, with `core/tauri-rust` as a thin native shell (`daemon::dispatch_to_daemon` is the
only place Rust talks to the daemon, and it's a generic pass-through, not a routes-aware caller).
Rather than teach Rust how to call `library.list_libraries()` on the daemon directly (new,
one-off plumbing this app has never needed before), the frontend calls a new native command
(`update_library_menu`) with an already-fetched library list. **Real, honest limitation, named
explicitly rather than solved:** this is sync-on-fetch, not a live push subscription -- the native
menu reflects "the last time the frontend asked," matching every other real-time-adjacent surface
in this app (e.g. the Library sidebar count), not a guarantee of instant cross-window consistency.
Two real call sites cover the practical cases: `App.tsx` on mount (so the menu is populated even
before a user ever opens the Library area) and `LibraryArea`'s own `refreshLibraries()` (already
called after every real list load, including right after creating a new library).

**Real design decision: `listLibraries()` itself stays a pure read, unchanged.** The sync call
lives in a new, separate `lib/menu.ts` function (`syncLibraryMenu`) that callers invoke explicitly
with an already-fetched list, rather than being a hidden side effect bolted onto `listLibraries()`
itself -- keeps the existing, already-tested `lib/library.ts` module untouched and makes every call
site's intent explicit.

**Real design decision: `MENU_OPEN_LIBRARY_EVENT` breaks `CTX-316.1`'s own
one-dedicated-const-per-action convention, deliberately.** Every other menu action (Design/Settings/
Manage Libraries/Default Library) is a fixed, compile-time-known action with its own const and
event -- but a custom library's *identity* is inherently open-ended and user-defined, so it cannot
have a compile-time const. This context introduces exactly one payload-carrying event
(`menu://open-library`, payload = the real library id) for this one dynamic case, matching
`daemon.rs`'s own `DAEMON_RESPONSE_EVENT` (which already carries a real payload) more closely than
`CTX-316.1`'s own zero-payload events -- not a new pattern invented from scratch, but the other
half of a precedent that already existed in this codebase.

### Phase 1: Rust -- `update_library_menu` command & dynamic Library items
*   [x] `menu.rs`: new `#[derive(Debug, Clone, Serialize, Deserialize)] pub struct LibraryMenuEntry {
    pub id: String, pub name: String }` (crosses the Tauri command boundary from the frontend's
    already-real `LibrarySummary` shape, trimmed to just what the menu needs).
*   [x] New pure, directly-unit-testable helper: `fn filter_custom_libraries(libraries: Vec<LibraryMenuEntry>)
    -> Vec<LibraryMenuEntry>` -- excludes any entry whose `id == "default"` (a comment names this
    must match `library_store.DEFAULT_LIBRARY_ID` in `services/python-daemon/library_store.py`),
    preserves the real order of everything else. No `AppHandle` involved, so this is real,
    meaningful Rust test surface this crate has never had for menu-adjacent code before.
*   [x] Split `build_menu` into `fn build_menu_inner(app: &AppHandle<Wry>, custom_libraries:
    &[LibraryMenuEntry]) -> tauri::Result<Menu<Wry>>` (all of `CTX-316.1`'s existing logic, with the
    `Library` submenu's construction extended: `Default Library`, then one real
    `MenuItemBuilder::with_id(format!("library_open_custom_{}", entry.id), &entry.name)` per custom
    library, then a separator (only when at least one custom library exists -- zero custom libraries
    renders byte-identical to `CTX-316.1`'s own static shape), then `Manage Libraries…`) and
    `pub fn build_menu(app: &AppHandle<Wry>) -> tauri::Result<Menu<Wry>> { build_menu_inner(app, &[]) }`
    (the function `lib.rs`'s `.menu(...)` closure still calls, unchanged from its own call site's
    perspective).
*   [x] New `pub const MENU_OPEN_LIBRARY_EVENT: &str = "menu://open-library"` (payload: the real
    library id) and `const LIBRARY_OPEN_CUSTOM_PREFIX: &str = "library_open_custom_"`.
*   [x] New `#[tauri::command] pub fn update_library_menu(app: AppHandle<Wry>, libraries:
    Vec<LibraryMenuEntry>) -> Result<(), String>`: `filter_custom_libraries(libraries)`, then
    `app.set_menu(build_menu_inner(&app, &custom).map_err(...)?).map_err(...)?`.
*   [x] `handle_menu_event` gains one new match arm, placed before the final `_ => {}`: `id if
    id.starts_with(LIBRARY_OPEN_CUSTOM_PREFIX) => { let library_id =
    &id[LIBRARY_OPEN_CUSTOM_PREFIX.len()..]; let _ = app.emit(MENU_OPEN_LIBRARY_EVENT, library_id); }`.

### Phase 2: Rust -- `set_design_menu_enabled` command
*   [x] New `#[tauri::command] pub fn set_design_menu_enabled(app: AppHandle<Wry>, enabled: bool) ->
    Result<(), String>`: looks up `app.menu()` (real `None` case -- menu not yet built -- returns a
    clean `Err`, not a panic), `.get("menu_design")`, `.as_submenu_unchecked().set_enabled(enabled)`.
*   [x] `lib.rs`: register both new commands in the existing `tauri::generate_handler![...]` list.

### Phase 3: Frontend -- `lib/menu.ts` + wiring
*   [x] New `apps/tauri-ui/src/lib/menu.ts`: `syncLibraryMenu(libraries: LibrarySummary[]):
    Promise<void>` (maps to `{id, name}` pairs, `invoke('update_library_menu', { libraries })`) and
    `setDesignMenuEnabled(enabled: boolean): Promise<void>` (`invoke('set_design_menu_enabled', {
    enabled })`) -- both best-effort: a real `try`/`catch` that swallows failures, since a stale or
    unsynced native menu is a real but non-blocking degradation, never something that should surface
    as a UI error for an otherwise-successful library list load.
*   [x] `lib/ipc.ts`: new `MENU_OPEN_LIBRARY_EVENT = 'menu://open-library'` constant, joining the 11
    already there, with the same "must match its own const in menu.rs" doc comment convention.
*   [x] `App.tsx`: new mount-only effect calling `listLibraries().then(syncLibraryMenu).catch(() =>
    {})` (best-effort at the call site too, matching `syncLibraryMenu`'s own contract in case
    `listLibraries()` itself rejects before `syncLibraryMenu` ever runs). New effect watching
    `view?.kind === 'project'`, calling `setDesignMenuEnabled(...)` with that boolean whenever it
    changes. New `listen(MENU_OPEN_LIBRARY_EVENT, (event) => setView({ kind: 'library',
    initialLibraryId: event.payload as string }))` added to the existing menu-listener effect's
    `unlisten` array (this one needs the real event payload, unlike every other listener in that
    effect, so it's wired directly with `listen(...)` rather than through the existing
    payload-less `on(...)` helper).
*   [x] `LibraryArea.tsx`: `refreshLibraries()` calls `syncLibraryMenu(result)` immediately after a
    successful `listLibraries()` -- covers both initial mount and the post-create refresh
    (`"+ New library"` already calls `refreshLibraries()` today) with one real change, not two.

### Phase 4: Tests + real verification
*   [x] Rust: real unit tests for `filter_custom_libraries` (excludes "default", preserves order and
    every other real entry, empty input stays empty) -- the one piece of this context's Rust code
    with a real, meaningful test surface with no `AppHandle`/window involved.
*   [x] Rust: `cargo build`/`cargo check` for the two new commands and the `build_menu` split --
    matching `CTX-312.3`/`CTX-316.1`'s own established, honest precedent that native menu
    construction itself has no real unit-test surface in this crate.
*   [x] Frontend: `lib/menu.test.ts` (new) -- `syncLibraryMenu`/`setDesignMenuEnabled` call the real
    `invoke` with the right args, and each swallows a rejected `invoke` without throwing.
*   [x] Frontend: `App.test.tsx` -- the mount-time sync call, the Design-menu-enabled effect firing
    `true`/`false` at the right transitions, and the `MENU_OPEN_LIBRARY_EVENT` listener setting
    `view` with the real payload.
*   [x] Frontend: `LibraryArea.test.tsx` -- `refreshLibraries()` (both the initial load and the
    post-create path) calls the real sync.
*   **Named, honest, not-yet-closeable gap, same as `CTX-312.3`/`CTX-316.1`:** no real human
    click-through of the actual native menu showing real custom libraries, or actually graying out
    while no project is open, is possible in this session (no accessibility/screen-recording
    permission) -- named explicitly here, not silently assumed covered by `cargo build`/`vitest`
    succeeding.

## 4. Plan Drift & Architectural Changes
*Document any deviations from the original SPEC definitions encountered during build time.*

Implementation matched this context's own plan closely -- no real design changes during the build.
One real, worth-naming ripple: `App.tsx` now unconditionally calls `listLibraries()` on every mount
(the new sync effect), which every test in `App.test.tsx` exercises (it renders `<App />`) whether
or not that specific test cares about libraries. Rather than add per-describe-block boilerplate,
added one real, file-scope `beforeEach` (before any `describe`) giving `listLibrariesMock`/
`syncLibraryMenuMock`/`setDesignMenuEnabledMock` sensible defaults -- the first genuinely
file-scope `beforeEach` in `App.test.tsx` (every other one is describe-scoped). *Impact:* none on
product behavior; named here because it's a real, new pattern in that test file, not because
anything broke.
