# CTX-311.10: Real, shape-aware default azimuth: the deferred risk CTX-311.8 named came true

> **Spec Reference:** Links to [SPEC-311](../specs/SPEC-311-enclosure-refinement-interactive-preview.md)

`CTX-311.9`'s lighting rebalance shipped. The next real regeneration -- the same real, elongated
`NFC_Reader_ESP32` board this whole chain has been testing against -- rendered as "still unusable,"
a plain solid-looking slab with no visible opening at all: "still can[not] see anything from this
view... is this a light source issue?" A real, different cause again, and one this session had
already predicted in writing: `CTX-311.8`'s own Plan Drift named the fixed 45° default azimuth as a
real, deferred risk for exactly this board's own elongated proportions, left unfixed at the time in
favor of the more universal polar-angle fix. This context is that deferred risk, now actually fixed.

## 1. Feature Definition & Execution Plan

### Phase 1: diagnosis
*   [x] Re-derived, not re-guessed: the fixed 45° default azimuth, combined with `CTX-311.8`'s own
    steeper 35° polar angle, interacts badly with a real elongated board (this session's own earlier
    research already measured the real `NFC_Reader_ESP32` footprint at ~49.5mm x ~106.5mm -- over 2:1).
    Looking at a long, narrow open-top shell nearly along its own long axis makes the near end wall's
    on-screen footprint dominate the view, and a steep polar angle simultaneously minimizes the
    *side* walls' own on-screen height (the only real surfaces whose lighting differs from the floor,
    with no real shadow-mapping in this `Canvas` to otherwise reveal depth) -- between the two, the
    real cavity became invisible again, this time for a materially different reason than `CTX-311.4`'s
    original bug (that was a *rendering* failure; this is a real *framing* failure of correctly
    rendered geometry).

### Phase 2: fix
*   [x] `EnclosureViewer.tsx`: `computeDefaultAzimuth(object)` -- a real, direct, pure function
    deriving azimuth from the loaded mesh's own real horizontal (X/Z) extents via `atan2(sizeX,
    sizeZ)`, biasing the camera toward a real "broadside" view of whichever horizontal axis is
    longer. A roughly-square footprint lands back near the original fixed 45° (no behavior change for
    the common case); an extreme aspect ratio is clamped to a real minimum 15° perspective offset on
    either side so the default view never collapses into a fully flat, axis-aligned side-on shot.
*   [x] Wired via a new `azimuthInitializedFor` ref, computed exactly once per distinct `base.scene`
    (a genuine new generation) rather than on every re-render -- an unrelated re-render (e.g.
    toggling "Show lid") must never silently discard a user's own manual rotation, the same real
    concern `CTX-311.4`'s own synchronous-render-time radius/center computation already had to solve.
*   [x] `DEFAULT_CAMERA_POLAR` also eased back from `CTX-311.8`'s `35°` to `42°` -- still steeper than
    the original isometric `~54.7°`, but with the azimuth fix now doing its own real part to avoid
    occlusion, a less extreme polar restores more real, visible wall height for the lighting-based
    depth cues `CTX-311.9`'s own rebalance depends on.

### Phase 3: tests
*   [x] Direct, real unit tests on `computeDefaultAzimuth`: a roughly-square footprint reproduces the
    original 45°; the real, measured `NFC_Reader_ESP32` board's own aspect ratio produces a real,
    meaningfully large bias (verified in the correct direction after an initial test-authoring mistake
    -- see Plan Drift); an extreme aspect ratio still respects the real minimum perspective clamp;
    swapping which horizontal axis is longer swaps the bias direction; a degenerate (empty) object
    falls back to the fixed default, never a guess.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: this context is `CTX-311.8`'s own, honestly-recorded deferred risk coming true.**
    `CTX-311.8`'s Plan Drift said plainly: "a per-board azimuth... was considered but not built here...
    Left as a real, named follow-up if a future click-through shows the fixed azimuth still causing
    occlusion on similarly elongated boards, rather than solved speculatively now." That is exactly
    what happened, on the very next real click-through of the same real board. Recorded here as a
    real, working example of this repo's own norm that an honestly-named deferred risk is worth more
    than a silently-scoped-out one -- the next session (this one) knew exactly where to look.
*   **Deviation 2: the first version of `TEST-002` above asserted the bias in the wrong direction, an
    authoring mistake caught immediately by the real test run, not silently left wrong.** The real
    `NFC_Reader_ESP32` footprint used in the test (`49.5 x 106.5`) has its own long axis on Z, not X;
    the initial assertion expected azimuth *above* 45° when the correct, intended behavior (confirmed
    by re-deriving the `atan2` direction by hand) is *below* 45° for that specific shape. Fixed by
    correcting the test's own expectation to match the already-correct implementation, not by
    changing the implementation to match a wrong test -- worth naming so a future reader trusts the
    swap-direction test (`TEST-004`) as the real behavioral contract, not this one's initial draft.
