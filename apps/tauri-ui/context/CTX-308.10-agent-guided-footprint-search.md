# CTX-308.10: Implementation Context: Agent-Guided Footprint Search

> **Spec Reference:** Links to [SPEC-308](../specs/SPEC-308-footprints-schematic-advisor.md)

Real user feedback, same live-testing session as `CTX-306.7`/`CTX-308.9`: "the footprint search
currently feels like you need to know more than what the user probably knows about footprints...
We should help with this and even use an agent to guide the search and just have the user confirm."
Item 3 of 3 in the user's own explicit ordering (visual previews → per-project footprint override →
**agent-guided search**).

## 1. Feature Definition & Execution Plan

### Phase 1: Scope the safe boundary before writing any code
*   [x] Confirmed the right shape: the agent only ever suggests a *search term* -- it never asserts
    a specific footprint exists, never picks one on the user's behalf, and never bypasses the
    existing, already-real `kicad.search_footprints`/`library.search_community_footprints` routes.
    Every real result the user ultimately sees and confirms still comes from a real library lookup,
    the same safety boundary `component_pipeline.py`'s own fail-closed validation already enforces
    for other agent outputs -- here there's simply nothing *to* validate against a real-world fact,
    since a suggested string is never "wrong," only more or less useful.
*   [x] Confirmed this needed none of the deferred `SPEC-206`/`SPEC-318` chat.send/router/SourceRef
    machinery -- `kicad.generate_connection_guidance` (`CTX-308.7`) was the exact, already-real
    precedent for a single standalone agent call (`_build_agent_executor` + `_run_agent_and_close`,
    no `WorkflowExecutor` DAG), mirrored here directly.

### Phase 2: Backend -- a single-shot suggestion route
*   [x] `agentflow/agents/footprint_query_suggestion.prompt.md`: new prompt, same frontmatter/JSON-
    only-response convention as `connection_guidance.prompt.md`. Explicitly instructs the model
    never to invent a specific footprint's exact library path or claim a match exists.
*   [x] `component_pipeline.py`: `_validate_footprint_query_suggestion` (shape-only checks --
    `query`/`alternates`/`reasoning` present and correctly typed) and `suggest_footprint_query(...)`,
    mirroring `generate_connection_guidance`'s own real shape (`_build_agent_executor`, resolved
    `provenance`, `_extract_json`).
*   [x] `daemon.py`: `kicad_suggest_footprint_query(part_id)` route -- loads the real Part, threads
    `CONFIG["llm_provider"]`/`["llm_model"]`/secrets exactly like the connection-guidance route.
    Registered in `ASYNC_ROUTES` (a real LLM call). Deliberately **not** persisted onto the Part
    record -- a search-term suggestion has no durable value once the user has run the search.

### Phase 3: Frontend -- a manual, confirmable suggestion
*   [x] `lib/footprints.ts`: `suggestFootprintQuery(partId)`, `submitJob`-based like every other real
    LLM route here.
*   [x] `PartDetail.tsx`: a "Suggest a search term" button next to the Find-Footprint search input
    (shown in both the default-setting and CTX-308.9 override-mode views, since it's the same search
    UI either way). Clicking it fills the search box with the real suggestion and shows a short
    reasoning caption plus any alternates -- it never runs the search itself; the user still reviews,
    can edit, and confirms by clicking Search against real results, same as typing a term in by hand.
    Deliberately overwrites whatever the user already typed on click (an explicit action the user
    just took), unlike `CTX-306.6`'s passive package-name auto-fill effect, which must never fight a
    user who's already typing.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: no deviation from the planned scope -- named here because it was a real risk
    worth checking, not because anything went wrong.** The original concern (noted when this item
    was queued behind items 1 and 2) was that agent-guided search might depend on the still-deferred
    `SPEC-206`/`SPEC-318` chat.send/router/SourceRef pipeline. It doesn't: `generate_connection_
    guidance`'s existing single-standalone-agent-call shape was a complete, sufficient precedent, so
    this shipped as a peer of that route rather than waiting on the chat pipeline.
*   **Deviation 2: this item's real safety property is structural, not a validation check.**
    Every other agent-backed route in this file (`validate_schema`, `_validate_connection_guidance`,
    `_validate_candidates`) fails closed against a real-world fact the response could get wrong (a
    hallucinated pin, an impossible footprint geometry). A suggested search *term* has no such fact
    to fail against -- the safety property here is architectural instead: the suggestion is *only*
    ever fed back into the box the user would have typed into by hand, and the same real search
    routes and real result confirmation already in place from `CTX-306.6` are what the user actually
    acts on. `_validate_footprint_query_suggestion` therefore only checks response *shape*, not
    content -- documented explicitly in its own docstring so a future reader doesn't assume a missing
    content check is an oversight.
