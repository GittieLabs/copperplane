# CTX-319.7: Implementation Context: A Finding Names the Real Component

> **Spec Reference:** Links to [SPEC-319](../specs/SPEC-319-ai-review.md)

The review explained a real ERC error on the maintainer's own tutorial project like this:

> The ERC check found that pin 8 on the part labeled 'A1' -- this is the power supply input pin
> (VCC/VIN) on the **NE555 timer chip** -- isn't wired up to anything that actually supplies power.

A1 is an Arduino UNO. There is no NE555 in that schematic and never was.

## 1. Feature Definition & Execution Plan

### Phase 1: find out what was actually in the context
*   [x] The real ERC finding reads `Symbol A1 Pin 8 [VIN, Power input, Line]` at
    `x=1.1303, y=0.5461`. Every detail in the explanation traced back to it -- A1, pin 8, VIN,
    power input, both coordinates. **Only the part's identity was invented, and it was the only
    fact not supplied.**
*   [x] Rebuilt the exact context the agent was handed, against the real project record. It
    contained `project_intent`, `check_status`, and a bare `parts` key holding the NE555's full
    per-pin guidance -- including its pin 8. It contained **no component list at all**.
*   [x] The project record explains where the NE555 came from: `parts: ["NE555"]`, attached during
    the injection experiment on 2026-09-04, which reached the board and never the schematic.
*   [x] So the model had two blocks mentioning pin 8 and no way to tell them apart. Pin 8 is an
    NE555's single most famous pin. This was not a random hallucination; it was the only
    conclusion available.

### Phase 2: give the finding its component
*   [x] `_design_components` reads the real component list from the linked `.kicad_sch` or
    `.kicad_pcb` -- `kicad_cli.export_schematic_bom` and `kicad_board.read_board_footprints`, both
    of which already existed.
*   [x] Every finding location now carries the component it names, resolved by reference
    designator, so the agent never has to join anything: `Symbol A1 Pin 8` arrives beside
    `{"reference": "A1", "value": "Arduino_UNO_R3", "footprint": "Module:Arduino_UNO_R3_..."}`.
*   [x] A reference that is **not** in the list says so, in the location itself. Silence is what
    produced the NE555; an absent fact has to be stated, because the model will otherwise supply
    one.
*   [x] A component list that cannot be read is reported as unreadable, never as an empty design.

### Phase 3: stop the library parts reading as the design
*   [x] `parts` is now `library_parts_attached_to_this_project`, beside a note saying that a part
    appearing there is not evidence it is in the schematic or on the board, and that every
    reference designator resolves against `check_status.components` and nothing else.

### Phase 4: the prompts were lying
*   [x] `chat_schematic.prompt.md` said, in its second sentence: *"nothing in this app reads a
    `.kicad_sch`'s component list or wiring."* `SPEC-325` built exactly that in v0.4.0 and no
    prompt was told. The agent was instructed to believe it could not know what A1 was.
*   [x] Both the schematic and PCB prompts now describe the component list and state where a
    designator is resolved.

## 4. Plan Drift & Architectural Changes

**1. This was not a hallucination problem and treating it as one would have produced a prompt
tweak.** The instinct on reading the report was "the model made something up, tighten the
instructions". The context said otherwise: nine facts in that sentence were correctly grounded and
one was not, and the one that was not was the only one absent from the context. The fix is supplying
a fact, not asking harder for honesty.

**2. `SPEC-325` shipped a capability and no prompt was told.** The schematic agent's own second
sentence asserted the app could not read a component list, months after it could. There is no
mechanism in this repo that would have caught that: the prompts are prose, the capability is Python,
and nothing compares them. Worth naming as a class -- a prompt is documentation of the system, and
documentation goes stale.

**3. The key name was doing real damage on its own.** `parts` next to a block full of reference
designators reads as "the components in this design". Renaming it to
`library_parts_attached_to_this_project` is most of the fix and cost nothing.

**4. Not verified: whether the model now gets it right.** Every deterministic layer is tested --
the component reaches the context, the annotation is attached, the prompt says where to resolve.
Nobody has run the review against the real project and read the answer. That is the only check that
closes this, and it is the same check that would have caught the bug in the first place.

**5. Two unrelated live-LLM tests failed in the full suite run and both pass on re-run.**
`test_component_pipeline` `test_003` asserted a model returns exactly `ATtiny85` and got
`ATtiny85-20SU`; `test_async_jobs`' real guidance job hit malformed JSON from the API and its retry
also failed that run. Neither touches `chat_agents`. Recorded rather than quietly re-run until
green, because "the suite passed" was not true on the first attempt.
