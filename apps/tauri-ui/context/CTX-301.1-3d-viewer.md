# CTX-301.1: 3D Viewer

> **Spec Reference:** Links to [SPEC-301](../specs/SPEC-301-3d-viewer.md)

## 1. Feature Definition & Execution Plan

### Phase 1: Relocate `.glb` output out of the shared OS temp directory
*   [x] `core/tauri-rust/src/config.rs`: `ensure_output_dir` (pure, real-filesystem-testable) creates
    `<app_data_dir>/generated`; `resolve_output_dir` resolves the real `app_data_dir()` via Tauri's
    own `$APPDATA` path variable, so it's guaranteed to agree with `tauri.conf.json`'s
    `assetProtocol.scope`. `DaemonConfig` gains an `output_dir` field — unlike every other field,
    always Rust-computed, never read from `config.json`.
*   [x] `services/python-daemon/freecad_bridge.py`: `configure()` gains `output_dir`;
    `generate_enclosure` writes its `.glb` there (falling back to the shared OS temp dir if unset,
    e.g. running the module standalone). The intermediate script/`.stl` stay in the OS temp dir —
    only the persistent `.glb` output needs to live somewhere `assetProtocol.scope` can reach.

### Phase 2: Scoped asset protocol (the spec's own resolved gotcha)
*   [x] `core/tauri-rust/Cargo.toml`: `tauri`'s `protocol-asset` feature — required by Tauri's own
    build-time validation once `assetProtocol` appears in `tauri.conf.json` (discovered by the build
    itself failing with an exact, actionable error, not guessed in advance).
*   [x] `tauri.conf.json`: `app.security.assetProtocol` — `enable: true`, `scope:
    ["$APPDATA/generated/**"]`, narrowed to exactly the directory Phase 1 creates.

### Phase 3: Bound the known `.glb`-leak debt `SPEC-301` flagged
*   [x] `freecad_bridge.py` tracks the last successful output path and deletes it once a new one
    succeeds — bounds the leak to at most one extra file at a time, not unbounded growth. Documented
    as a deliberate, partial fix (not zero-leak) in Plan Drift.

### Phase 4: R3F viewer
*   [x] `apps/tauri-ui/src/components/EnclosureViewer.tsx`: `useGlbScene` (loading/ready/error state,
    explicit rather than Suspense-based, with the loader injectable so tests never need to mock the
    `three` module) + `disposeScene` (releases geometry/material/texture GPU buffers on every scene
    replacement or unmount — the standard Three.js leak `SPEC-301` §3 named) + `EnclosureViewer`
    itself (an R3F `<Canvas>` with default camera/lighting, rendering the loaded scene).
*   [x] Wired into `App.tsx`'s existing `EnclosurePanel` (`CTX-105.2`): renders once `glbPath` is set.

### Phase 5: Testing
*   [x] Rust: real-filesystem tests for `ensure_output_dir` (creation + idempotency); extended
    `build_daemon_env` coverage for the new field.
*   [x] Python: real tests (skip cleanly without FreeCAD, same pattern as `CTX-104.1`'s `TEST-004`)
    for the `output_dir` override and the previous-`.glb` cleanup.
*   [x] Frontend: `useGlbScene`'s loading→ready/error transitions and dispose-on-replace, `disposeScene`'s
    geometry/material/texture disposal — all against real `three.js` objects (`vi.spyOn` on real
    `.dispose()` methods), not fakes.
*   [x] A real production build (`npm run build`, the same `vite build` Tauri's `beforeBuildCommand`
    runs) confirms the `three/examples/jsm/loaders/GLTFLoader.js` deep import resolves correctly
    under Vite's bundler, not just its dev server.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: enabling `assetProtocol` in `tauri.conf.json` requires the `protocol-asset`
    Cargo feature — discovered by the build itself, not anticipated in the spec.**
    *   *Reasoning:* `cargo build` failed immediately with an exact, actionable error: *"The `tauri`
        dependency features on the `Cargo.toml` file does not match the allowlist defined under
        `tauri.conf.json`... add the `protocol-asset` feature."* Tauri validates this itself at
        build time — no guessing required, just reading the error and fixing `Cargo.toml`.
    *   *Impact:* Added `protocol-asset` to `tauri`'s feature list. Worth recording as a concrete
        example of Tauri's own build-time checks doing the verification work, matching this repo's
        broader "verify for real" norm even when the "verification" is just paying attention to a
        compiler/build-tool error instead of guessing ahead of it.

*   **Deviation 2 (non-deviation, confirmed as designed): the previous-`.glb` cleanup bounds the leak
    to one extra file, it does not eliminate it.**
    *   *Reasoning:* `SPEC-301` §3 explicitly asked this context to decide the strategy (cleanup on
        next-generation, on app quit, or defer as documented debt) rather than pre-deciding it.
        Cleanup-on-next-generation was chosen: simple, requires no Rust-side shutdown-hook
        integration, and converts "unbounded growth" into "at most one stale file exists, and only
        until the daemon is killed/restarted without a further generation." An app-quit hook would
        close that last gap but adds real complexity (Rust must know to ask the daemon to clean up,
        or track+delete the path itself) for a bounded, low-severity residual.
    *   *Impact:* One un-deleted `.glb` can survive a daemon restart if no further enclosure is ever
        generated in that session — documented here explicitly rather than silently implied as fully
        fixed by `TEST-004`'s passing.

*   **Deviation 3 (non-deviation, confirmed as designed): loading/error state is explicit `useState`,
    not React Suspense + an error boundary.**
    *   *Reasoning:* `SPEC-301` §1 asks for "loading and error states" without prescribing the
        mechanism. `EnclosurePanel` (`CTX-105.2`) already manages its own job status via explicit
        `useState`, not Suspense — matching that existing pattern keeps the codebase's async-state
        style consistent, and avoids introducing a class-based (or library) error boundary for a
        single component's failure mode.
    *   *Impact:* None on correctness; a future spec introducing Suspense-based data fetching
        elsewhere wouldn't need to touch this component to stay consistent, since the two approaches
        don't conflict.

*   **Deviation 4 (non-deviation, confirmed as designed): the production bundle is ~1.1MB
    (gzip ~309KB) with a chunk-size warning, and this context does not address it.**
    *   *Reasoning:* `three.js` is a large library; a single-chunk bundle warning from `vite build`
        is expected the moment any 3D library is added to a previously-tiny frontend. Code-splitting
        (dynamic `import()` for the viewer) is a real, legitimate future optimization, but this
        context's job is proving the render pipeline works end-to-end, not tuning bundle size for a
        one-window desktop app where initial load time isn't yet a measured, complained-about
        problem.
    *   *Impact:* None on functionality. Flagged here so a future session doesn't mistake the
        warning for something this context missed fixing.
