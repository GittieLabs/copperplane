# CTX-332.1: Implementation Context: The Schematic Check Reports What the Board Check Does

> **Spec Reference:** Links to [SPEC-332](../specs/SPEC-332-erc-as-a-teaching-surface.md)

## 0. How much of this was already built

`SPEC-332`'s first draft claimed the schematic check "got none of" the board check's treatment.
The maintainer pushed back — *"this seems like we just added to the schematic review"* — and he was
right. Checking rather than defending found:

*   ERC violations **already carry their location**. `items[].description` reads
    `Symbol #PWR03 Pin 1 [Power input, Line]`.
*   `_explain_or_report_plainly` and `_finding_for_agent` are **already shared** by both routes, so
    `CTX-326.3`'s "keep `items`, they are the component and the pin" work already applied to ERC.
*   `SchematicAdvisor` and `BoardAdvisor` **already share `ViolationsList`**, which already renders
    `IgnoredChecks` and runs `explainTerms` over every finding.

So the UI needed **no changes at all**. What was missing was what the route discarded from a report
it already had, and four glossary entries. The spec was corrected before any code was written.

## 1. Feature Definition & Execution Plan

### Phase 1: Stop discarding the report
*   [x] `kicad_check_schematic` returns `ignored_checks` — a schematic reported clean may simply
        not have been checked for the thing that is wrong.
*   [x] It returns `included_severities` — a result filtered to errors only, presented as "no
        problems", is a lie of the same shape.
*   [x] The ignored-checks block names the right checker. Sharing `ViolationsList` between the two
        tabs put DRC's wording on the Schematic tab — *"3 DRC tests switched off"* and
        *"Inspect → Design Rules Checker"*. Both paths are now read from KiCad's own binaries:
        `eeschema` and `pcbnew` each carry **Edit ignored tests** under their own checker.
*   [x] The "worth turning back on" commentary the board review has now applies to ERC too, from
        the same `IGNORED_CHECK_NOTES` table with the four ERC keys added.
*   [x] **And the UI says so.** The field reached the daemon and was neither typed nor rendered
        until this was caught: `SeverityFilter` now names what was left out, and stays silent on an
        ordinary full run, because saying "errors and warnings were included" every time is noise
        and noise is how a real warning gets ignored.
*   [x] A report lacking either key degrades to `[]` rather than raising.

### Phase 2: ERC's own vocabulary
*   [x] The four ERC `ignored_checks` keys get notes saying what each would have caught, and
        whether a maker should care — `single_global_label` and `footprint_filter` do,
        `four_way_junction` and `simulation_model_issue` mostly do not.
*   [x] Five ERC terms in the glossary. The one that earns its place is **power input / not
        driven**: the schematic is usually correct and missing only a `PWR_FLAG`, which is a KiCad
        convention rather than an electrical fact, so a maker reads "not driven" and hunts for a
        wiring fault that is not there.

## 4. Plan Drift & Architectural Changes

*   **Deviation 1: the spec overstated its own gap, and the maintainer caught it.** Comparing the
    two routes' return values suggested a missing surface; comparing what they actually produce
    showed three discarded fields. The correction is committed in the spec itself rather than
    quietly applied, because a spec that overstates its gap is how work gets done that did not need
    doing. **The whole feature is one line in the route plus nine glossary entries**, and it is
    worth saying that plainly rather than dressing it up.

*   **Deviation 2: no UI change was needed, which is the payoff of an earlier decision.**
    `SchematicAdvisor` already renders through `ViolationsList`. Both new fields and all the new
    vocabulary appeared with zero component edits. Recorded because "share the renderer" decisions
    look like overhead when they are made and only pay off later, silently, like this.

*   **Deviation 3: I shipped a field that nothing displayed, and said three omissions were
    closed.** `included_severities` reached the route's return value and was neither added to
    `CheckResult` nor rendered anywhere — so the third of the three omissions this context exists
    to fix was half-done while the commit message claimed it was fixed. Caught by the maintainer
    asking a different question entirely (about tab structure), which sent me back through the
    presentation layer. A field in a return value is not a feature until something reads it.

*   **Deviation 3b: sharing the renderer paid off twice and cost once.** No component change was
    needed for the new fields — and the same sharing silently put DRC's vocabulary on the Schematic
    tab: *"3 DRC tests switched off. Turn them on under Inspect → Design Rules Checker."* Wrong
    tool, wrong menu, on a schematic. `ViolationsList` now takes a required `kind`, deliberately
    not defaulted: a default would have reintroduced exactly this. Both menu paths were read out of
    KiCad's own binaries rather than recalled.

*   **Deviation 4: the tab-structure question was already answered, in the surface this one
    copies.** `SPEC-332` §2 listed "whether to mirror KiCad's own tab structure" as open. The board
    review had already decided against it, for a reason the spec never recorded — *"since some tabs
    could be left empty"* — and `ViolationsList` already implements the alternative: one sentence
    naming each kind KiCad actually reported with counts, one findings list, and a collapsible for
    switched-off checks. It works for ERC unchanged **because** it is category-agnostic: ERC has
    one kind of finding, so the counts sentence stays silent and nothing looks missing. Tabs would
    have required deciding what to put in three empty ones.

*   **Deviation 5: the explanation path had never run on ERC findings, and now has.** Driven into
    the frozen sidecar on Anthropic against a deliberately broken schematic, it returned:

    > *"The schematic has four ERC errors, all related to power connectivity: two power symbols
    > with dangling unconnected pins, and two pins on U2 (reset and ground) that lack a driving
    > power source, indicating missing wiring to the power/ground nets."*

    That is the first time this code path has produced a real answer since it was written.
